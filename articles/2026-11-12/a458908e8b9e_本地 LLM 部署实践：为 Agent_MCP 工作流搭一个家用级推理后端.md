## 背景

Agent 自动化真正跑起来之后，调用量远比想象中大：一次任务里路由、摘要、信息抽取、格式校验各自要打好几发请求，全走云端 API，成本和隐私都是问题。但其中相当一部分子任务是「结构化、高频、难度低」，这类活儿本地小模型完全够用。这篇帖子记录我在一台 16GB 显存的家用机上，把本地推理接进 OpenClaw 工作流的过程——目标不是"能跑"，而是"跑得稳、可复用"。

## 问题

三个真实痛点：

1. 不知道手头硬件能吃下多大的模型，量化等级怎么选全靠猜；
2. 小模型接进 Agent 后工具调用质量明显下滑：参数幻觉、不输出终止符、循环刹不住车；
3. 模型标称 128K 上下文，默认配置下超出部分被静默截断，Agent 表现为莫名"失忆"。

## 做法

1. **先算账再下模型**。显存占用 ≈ 参数量 × 位数 / 8，7B 的 Q4_K_M 大约 4~5GB，再给 KV cache 留 1~2GB。16GB 显存跑 14B Q4 比较从容，32B 就得部分层下沉到内存。
2. **运行时选 Ollama**，理由是它的 OpenAI 兼容端点接入成本最低，`base_url` 一改就能挂进现有 Agent 配置，迁移到 llama.cpp 也只是换后端。
3. **模型按任务分层**：路由、分类、抽取用 7B~8B；最终生成和复杂规划留给云端大模型或本地 14B+。中文场景 Qwen 系列性价比不错。
4. **显式设置上下文**：`num_ctx` 直接写在请求参数里，不依赖运行时默认值。
5. **建自己的评测集**：从任务日志里抽 30 条真实样本，量通过率和 P95 延迟，不追榜单。MCP 工具链的调用链路尤其要单独测一轮。

## 踩坑点

- Ollama 默认上下文很短（不同版本 2K~4K），超出静默截断，系统提示词被砍一半都不报错。要么请求里带 `num_ctx`，要么设 `OLLAMA_CONTEXT_LENGTH`。
- 工具调用参数幻觉是小模型通病。用 JSON Schema 做结构化输出约束能压住大半；更稳的分工是：本地小模型负责"决定调哪个工具"，参数校验和执行交给 Agent 框架侧。
- 并发要显式配 `OLLAMA_NUM_PARALLEL`，Agent 并行调工具时默认排队，延迟尖刺很难看。
- 部分层 offload 到 CPU 有时反而更慢，PCIe 来回搬运的开销要实测，别凭感觉。
- 采样参数别照抄云端默认：本地模型 temperature 偏高加上 EOS 不稳定，容易在 Agent 循环里停不下来。

## 可复用建议

- 把本地模型包一层 OpenAI 兼容网关，云端/本地切换只是改配置；
- 分层下沉省的钱是真实的：先统计各任务的 token 分布，把高频低难度那部分挪到本地，剩下留给云端；
- 量化默认 Q4_K_M，只对质量敏感的任务试 Q8，别一上来追求 FP16；
- 显存预算按「模型 + KV cache + 20% 余量」计算，跑满必 OOM。

## 总结

本地 LLM 不是用来替代前沿大模型的，它的合理定位是 Agent 工作流里的"量级分担层"：高频、结构化、隐私敏感的子任务下沉到家用机，难任务留给云端。把它当成一个容量规划问题来处理——先算账、再实测、留余量——稳定性和成本都会好很多。后续如果大家有 MCP 工具调用在本地模型上的对比数据，欢迎跟帖补充。
