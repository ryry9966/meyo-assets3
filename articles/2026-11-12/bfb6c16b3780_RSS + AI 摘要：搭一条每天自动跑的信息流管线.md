## 背景

信息源没有死，只是分散了。我订阅的技术博客、GitHub Release、几个常用项目的 changelog 都有 RSS，但阅读器里每天几百条未读，值得看的不到十分之一。也试过让 Agent 直接上网"看看今天有什么"，效果不可控：抓不全、失败无感知、无法复现。所以换个思路：抓取和存储用确定性代码，LLM 只负责中间的摘要这一步。

## 问题

三个核心痛点：一是原文太长，逐篇人工筛选成本高；二是纯 LLM 抓取不稳定，漏了什么你不知道；三是摘要要有用，必须保留原文链接和上下文，而不是一段漂亮的空话。

## 做法

整体结构很朴素：cron 定时任务 → 拉取 RSS → 去重 → 全文抓取 → LLM 摘要 → SQLite 存储 → 推送日报。

1. **订阅源管理**：feed 列表放 YAML 配置，每个源带独立参数（是否抓全文、用哪个模型、摘要侧重）。站点只给 summary 的，走 readability 类正文抽取。
2. **去重**：以 entry 的 GUID 哈希为主键落 SQLite，链接变了内容相同的，再做一次标题相似度兜底。这步看着不起眼，省的 token 最多。
3. **两级摘要**：先批量粗筛，每条喂给便宜模型，输出三要素——发生了什么 / 为什么值得注意 / 一句话结论，低于阈值直接丢弃；留下的聚合一份日报，贵模型只跑这一步。prompt 里强制要求：摘要中的判断必须对应到原文句子，对应不上就输出"信息不足"。
4. **接入 OpenClaw**：日报和原始条目都入库，再把查询封装成 MCP 工具暴露给 Agent。早上问一句"昨晚有什么动静"，Agent 调工具返回摘要加链接，而不是现场瞎抓。

## 踩坑点

- **全文抓取被拒**：部分站点对无 UA 的请求直接 403。老老实实带 UA、控频，失败进重试队列，别在主流程里卡死。
- **日期时区**：有的 feed 用本地时间，按 UTC 一律解析会漏"今天"的条目。存储统一转 UTC，过滤窗口用拉取时间而非发布时间兜底。
- **幻觉**：feed 只有标题没正文时，模型会自由发挥。硬性规则：每条结论附一句原文引用（截取，不许生成），给不出就跳过，宁缺毋滥。
- **成本失控**：初期所有条目走同一个模型，一天下来账单难看。改成"粗筛便宜模型 + 精读贵模型"后，成本降到原来的三分之一左右。

## 可复用建议

- **原始内容永远落盘**，摘要只是派生数据。prompt 改了想重跑，基于原始库重来即可，不用重新抓。
- 每一步打印计数（拉取 N 条 / 去重掉 M 条 / 摘要失败 K 条）。没有这些数字，一个坏掉的 feed 你一周都发现不了。
- 订阅源定期清理：连续一个月摘要全被过滤的源，要么源质量不行，要么阈值有问题，两头都值得查。
- 别急着上向量检索。先跑两周纯摘要加关键词过滤，确认信息流真的稳了，再考虑加语义搜索。

## 总结

这条管线没用到什么新东西：RSS 是老协议，SQLite 是老数据库，LLM 只在两个明确的点位介入。它可靠的原因恰恰是"不智能"的部分够多——抓取、去重、存储、计数全是确定性代码，模型只做被约束好的摘要。Agent 负责交互和查询，管线负责生产和兜底，边界清楚，出了问题十分钟能定位到层。建议从五个订阅源开始跑通全链路，再慢慢加量。
