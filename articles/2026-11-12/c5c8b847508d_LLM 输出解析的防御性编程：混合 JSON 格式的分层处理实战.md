## 背景

在 OpenClaw 的 agent 和 MCP 工具开发里，只要下游环节需要结构化数据，几乎都绕不开同一件事：让 LLM 按约定吐 JSON。Prompt 里写明“只输出 JSON，不要任何解释”，合同看似已签，实际上模型会用各种方式违约——markdown 代码围栏包裹、`<json>` 标签包裹、前后夹解说文字、混入推理标签，甚至同一响应里出现两种格式。最麻烦的不是完全解析不出，而是 80% 的调用正常、20% 偶发失败，问题被稀释得很难定位。

## 问题

裸写 `json.loads(response)`，第一次遇到脏输出就崩；用一条正则抽 `{...}`，第二种格式就崩；再加个 strip，第三种又崩。防御性解析的目标不是把代码写得更多，而是把失败模式显式化：每一层只处理一类已知脏格式，全部失败时能拿到原始输出和明确错误，进入重试或人工兜底。

## 做法：从便宜到昂贵的分层管线

按成本排序依次尝试，命中即停：

```python
def extract_json(text: str) -> dict:
    # 1. 直接解析
    # 2. 剥 markdown 围栏（```json ... ```）
    # 3. 抽取 <json>/<result>/<output> 标签内容，跳过 think 类标签
    # 4. 字符串感知的花括号配平扫描，取第一个完整对象
    # 5. 保守修复：尾逗号、全角引号
    raise JsonExtractError(raw=text)
```

几个实现要点：

1. **围栏剥离用非贪婪匹配**，且优先取最后一个完整围栏——模型经常在正文示例里也写 ```json，外层那个才是答案。
2. **标签抽取建白名单**：`<json>`、`<result>` 各写一条规则；遇到 `<think>` 直接整段丢弃，不要试图从推理文本里捞 JSON。
3. **花括号配平必须感知字符串**：逐字符扫描，进入字符串状态后忽略内部的 `{}` 和引号，并处理 `\"` 转义。天真计数在字段值含大括号时必然截错位置。
4. **修复动作要保守**：尾逗号这类无损修复可以直接做；单引号转双引号这类有语义风险的交给专门的 repair 库，修复后必须再过一遍 schema 校验。
5. **最终用 pydantic 校验结构**，失败时把解析错误和原始输出回喂给模型重试一次，仍失败就落盘待人工。

## 踩坑点

- **截断的 JSON 比脏 JSON 更危险**。max_tokens 用尽时会输出“看起来配平完整但缺字段”的残缺对象，配平扫描救不了，只能靠 schema 必填字段兜住。
- **贪婪正则会吞掉多个对象**。模型一次输出两个 JSON 块时容易取错，永远取第一个能通过校验的，而不是正则的最后那个 match。
- **过度修复掩盖上游问题**。如果 90% 的调用靠 repair 才能过，说明是 prompt 的问题，不是解析器不够强。raw response 必须原样落日志，否则查不到根因。
- **嵌套转义**：输出里包含代码示例时，示例中的引号会让字符串感知的状态机出错，测试语料里必须有这类样本。

## 可复用建议

- 把整条管线沉淀成团队共享的 util 模块，禁止各插件复制粘贴各自的正则。
- 持续收集线上脏输出，做成回归测试语料，每次改解析逻辑先跑一遍。
- 接口支持 function calling 或结构化输出时优先用，防御解析只做兜底，不做主路径。
- Prompt 里放一个具体的 few-shot 输出示例，比重复十遍“只输出 JSON”有效得多。
- 重试只做一次。无限重试会把偶发解析问题放大成账单问题。

## 总结

对 LLM 输出做防御性解析，本质上不是不信任模型，而是承认“输出格式是整条链路里最不可靠的一段 I/O”。分层处理、schema 校验、原始日志，三件事齐了，自动化链路的解析故障就从“偶发必现”降到一个可归因、可接受的水平，剩下的长尾交给重试和人工兜底。
