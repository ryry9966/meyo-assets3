## 背景

Agent 长期跑下来会攒一堆记忆条目：用户偏好、项目上下文、踩过的坑。`memory_recall` 负责在对话时把相关条目捞回来，捞得好不好，直接决定 agent 是“越用越懂你”还是“张冠李戴”。我给自己的 assistant 先做了语义检索，跑了一阵后又补了全文检索，这里记录对比结论。

## 问题

两套方案各有舒适区：

- **语义搜索**：条目和查询都转向量，算余弦相似度。能处理换说法的提问——存了“部署脚本在 /srv/deploy”，用户问“上线工具在哪”也能命中。
- **全文搜索**：SQLite FTS5 / BM25 按词匹配。精确词几乎必中，且可解释——你知道为什么返回这条。

单用哪个都会翻车：纯语义对 ID、版本号、命令片段这类 token 不敏感；纯全文对换个说法零容忍。

## 做法

现在的方案是双通道混合召回：

1. 条目入库拆两份：原文写 FTS5 表，同时算 embedding 存向量列。本地用 bge-small-zh 级别的小模型，够用。
2. recall 时两路各取 top-5，用 RRF（倒数排名融合）合并，公式简单到不值得引库。
3. 融合分数叠加两个经验信号：时间衰减（30 天半衰期）和访问次数。记忆和普通搜索不同，“最近常用”权重很高。
4. 条目写作规范：每条是一个自包含短句，主动把关键 token 写进去（路径、命令、版本号），日期显式带上。

效果：在 40 条人工标注的测试查询里，混合召回命中率明显高于单语义，优势主要来自专有名词场景。

## 踩坑点

- **中文 FTS5 默认分词器会把整句当 token**，等于搜不中。要么上 trigram，要么外挂分词器，这个坑一上来就会遇到。
- 小模型对生僻专名、中英混排的向量区分度很差，"bun" 和 "pnpm" 的向量可能很近。这类条目靠 FTS 兜底。
- 语义检索会返回“看起来像但不是”的条目，相似度分数还很高。必须设阈值，并允许两路都空手而归——宁可不召回，也别灌错记忆。
- 过期记忆不清理会持续污染召回。加了个每日任务，把带日期且已过期的事实条目标记失效。
- 几百条记忆的 embedding 存 SQLite blob 就行，别急着上向量数据库。

## 可复用建议

- **先上 FTS5 起步**，一天能跑通，很多场景已经够用；语义是增强，不是必需。
- **条目质量 > 检索算法**。写入时多花十秒把 token 写全，比反复调融合权重管用。
- **攒 30~50 条真实查询做回归测试集**，换检索策略前后各跑一遍，避免“感觉变好了”这种结论。

## 总结

语义搜索解决“换了说法能不能找到”，全文搜索解决“精确 token 会不会丢”。memory_recall 这类小规模、强事实、要可解释的场景，混合召回 + 时间衰减是性价比最高的落点，实现成本也远低于传闻。建议从全文起步，用测试集的数据决定要不要加语义通道。
