## 背景

信息源越来越散，但 RSS 依然是最可控的订阅方式：格式标准、无算法干预、随时可退订。真正的问题不在订阅，而在**消化**——我订阅的三十多个源每天产生两三百条 entry，人读不完；直接全部丢给模型，又贵又容易失真。这篇记录我用 OpenClaw 搭的一条管线：定时抓取 → 清洗去重 → 分级摘要 → 推送到 IM，全程无人值守，核心代码几百行。

## 问题

拆开后是四个具体问题：

1. 多数源只给 summary，信息量不够；硬抓全文又涉及反爬；
2. 同一事件在多个源重复出现，摘要重复推送很烦人；
3. 模型摘要爱"补写"，出现原文没有的细节；
4. 不筛选就过模型，token 成本失控。

## 做法

**1. 抓取层**：写了一个 fetch 工具（后来封装成 MCP server，方便其他 agent 会话复用），输入 OPML 或 URL 列表，输出结构化 entry。用 rss-parser 解析，readability 做正文抽取，抽不出来就回退用源自带的 summary。

**2. 清洗层**：guid/link 做 hash 去重；标题做相似度合并同事件；按关键词白/黑名单先粗滤一轮。这一层不花一分钱模型费用，但能砍掉一半以上条目。

**3. 摘要层**：两段式。先用便宜的小模型给每条打重要性分（0–10 附一句话理由），低于阈值的丢弃；达标的批量喂给主力模型，要求输出不超过三句的摘要加关键事实列表，并在 prompt 里明确"只基于给定文本，不得补充任何信息"。

**4. 编排与排程**：整条链路注册为 OpenClaw 的 cron 任务，每天 7:30 跑一次，产出 Markdown digest。agent 只负责编排和异常兜底，具体逻辑都在独立函数里。

**5. 推送**：digest 通过 channel 插件推到 Telegram，超长时分段发送。

实测每天约 60 条进入摘要环节，成本基本可以忽略。

## 踩坑点

- **幻觉**：早期版本摘要里出现了原文没有的数字。改成强制引用原文句子、允许输出"信息不足"后才收敛。
- **去重不彻底**：同一事件换标题就漏。补了一层事件关键词粗聚类才压下来。
- **cron 时区**：容器默认 UTC，digest 每天下午才到。显式指定时区解决。
- **非法字符**：某些 feed 里混入非法 XML 字符会导致整个源解析失败，try-catch 必须下沉到单条 entry 级别。
- **反爬**：对抽不出正文的源别硬上，容易被封 IP，回退 summary 够用。

## 可复用建议

- 每一层独立成函数/工具，方便单测、换模型、单独重跑；
- prompt 模板放配置文件并做版本管理，效果回归时有据可查；
- 摘要永远附原文链接——它的定位是**索引**，不是替代阅读；
- 重要性阈值做成配置项，跑两周再调，别拍脑袋定；
- 每次运行落一份原始 JSON，复盘和重放都靠它。

## 总结

这条管线的价值不在代码量，而在分层：抓取、清洗、摘要、推送解耦之后，任何一层都能独立演进。下一步计划把"我实际点开了哪些链接"回灌给打分模型，让过滤阈值随使用习惯自适应——信息管线的终点不是自动化，是越来越懂你的自动化。
