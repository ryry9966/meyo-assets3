## 背景

OpenClaw 里有两套“定时”机制，很多人第一次用会混淆：

- **cron job**：由 gateway 内置调度器管理，用 cron 表达式定义触发时刻，到点把一条 payload 投递给 agent。可以开隔离会话干净执行，也可以送进主会话。
- **heartbeat**：主会话的周期性心跳。gateway 默认每 30 分钟注入一次心跳提示，agent 去读工作区的 `HEARTBEAT.md`：有事就做，没事回一句 HEARTBEAT_OK（或直接跳过）。

两者差异不只是“触发方式不同”，而是**执行模型**不同：会话上下文、时间保证、成本结构都不一样。

## 问题

常见误区是把所有周期任务都塞进 HEARTBEAT.md，或者全建 cron。典型症状：

- “每天 9 点的日报”变成 9:40 才来——错用了 heartbeat；
- 心跳间隔压到 5 分钟，token 账单上涨——把重活塞进了心跳；
- cron 任务“不认识”昨天聊过的内容——期望错了会话模型；
- 凌晨 3 点莫名跑了一波——时区问题。

选错的代价：时间不准、成本失控、上下文错位。

## 怎么选 + 步骤

一句话判断：**时间精确性优先选 cron；依赖主会话上下文的“环境巡检”选 heartbeat。**

### 用 cron 的场景和步骤

适合固定时刻的日报/摘要、定时提醒、周期抓取——任何“几点几分”语义的任务。

1. 通过 cron 工具集创建 job，写清表达式、payload、投递目标；
2. 一次性任务跑完即删，避免残留堆积；
3. 明确会话模式：需要干净上下文用隔离会话，需要“接着主会话说”投递主会话；
4. 显式指定时区，别赌运行环境的系统时区。

### 用 heartbeat 的场景和步骤

适合低频、对时刻不敏感的巡检：盯文件变化、检查待办、看邮箱有没有值得提醒的东西。核心优点是改任务只需编辑 `HEARTBEAT.md`，且自带主会话记忆。

1. 保持 HEARTBEAT.md 极简，一条一行，写清“何时需要动作、何时只回 OK”；
2. 严格遵守“无事发生回 HEARTBEAT_OK / 跳过”的约定，这是省 token 的关键；
3. 间隔维持默认 30 分钟量级或更大，别压到分钟级；
4. 巡检逻辑让 agent 做成幂等的：重复检查不产生重复副作用。

## 踩坑点

1. **时区**：容器里经常是 UTC，cron 表达式按 UTC 触发。要么显式传时区，要么设好 TZ 后实测一次真实触发时间。
2. **heartbeat 不保证准时**：它是“间隔不早于”语义，负载高会顺延。“15:00 提醒我”必须用 cron。
3. **HEARTBEAT.md 膨胀**：每一项都随心跳反复消耗 token。做完立刻删，只留长期任务。
4. **隔离会话无上下文**：cron 隔离任务只知道 payload，别指望它记得聊天历史；投递主会话虽能带上下文，但会和交互使用排队互斥。
5. **宕机补跑**：gateway 停机期间的 cron 触发默认按错过处理，关键任务要么接受丢失，要么在 payload 里自检“上次跑没跑”。
6. **重叠执行**：短间隔 cron + 慢任务会排队堆积，payload 里带去重条件。

## 可复用建议

- 背下这条决策规则：**有明确时刻 → cron；只是“每隔一阵看一眼” → heartbeat；既要时刻又要上下文 → cron 投递主会话。**
- 任务命名带语义：`report-daily-0930`、`watch-inbox-30m`，排查时一眼可辨。
- 每周审一次 cron 列表：清残留、把轻巡检挪进心跳。
- 把 HEARTBEAT.md 当“常驻预算”管理：行数越多，心跳成本越高。

## 总结

cron 和 heartbeat 不是竞争关系，而是两种执行模型：cron 是“确定性时刻 + 可控会话”，heartbeat 是“常驻上下文 + 松散节拍”。按时间精度和上下文需求分派任务，各司其职，定时自动化才既准时又省钱。
