## 背景

Agent 有两个能力组合起来最让人不安：能读文件系统，能执行 shell。OpenClaw 作为跑在本机的 agent 网关，默认拿着你用户账号的权限。社区里隔三差五就有人问：让 agent 清理目录，它会不会一个 `rm -rf` 把 home 干掉？

答案不是“模型足够聪明所以不会”，而是：OpenClaw 的设计假设是**模型不可信，环境必须可信**。它靠系统结构把“能做”和“被允许做”隔开。这篇文章拆一下这套沙箱模型的分层结构。

## 问题

误删通常不是模型“想删”，而是三种典型工程失误：

1. **路径算错**。模型拼接相对路径，实际 cwd 和它以为的不一致，`rm -rf ./build` 落在了别的目录。
2. **上下文污染**。用户随口一句“把没用的清一下”，模型对“没用”的理解和人类不一致。
3. **工具误用**。exec 里一条复合命令，前半段失败，后半段清理逻辑跑在错误前提下。

这三类是概率行为，prompt 约束解决不了。所以 OpenClaw 的思路是：即使模型犯错，爆炸半径也要被压在一个可控范围里。

## 做法：四层防御

**第一层：工作区路径约束。** 文件类工具（读/写/编辑/删除）都以 agent workspace 为根。路径先做规范化，解析 `..` 和软链接后如果落在 workspace 之外，直接拒绝。模型“看到的世界”就是 workspace，出界操作在默认配置下根本不存在。

**第二层：exec 容器沙箱。** exec 可以配置在 Docker 容器里执行，只把 workspace 挂载进去。容器内看不到宿主机文件系统，`rm -rf /` 删的只是挂载点。这是无人值守场景的关键一层。

**第三层：工具策略。** 按 agent 粒度配置工具 allow/deny 清单。只读会话直接 deny 掉 write/exec——策略层的拒绝，比提示词里的“请不要删除”可靠得多。

**第四层：审批门。** 检测到删除类命令、sudo、批量写时进入确认队列，人批准才执行。有人盯着的交互会话，这层是最后的刹车。

## 踩坑点

- **沙箱静默降级。** 配了 Docker 沙箱但宿主机没装 Docker，某些版本会回落到宿主机执行。别信配置文件，信运行时状态——启动后查日志确认沙箱初始化成功。
- **把 home 挂进容器。** 图省事把整个 home bind-mount 进去，沙箱就成了摆设，容器内照样删得到宿主机文件。挂载最小化，只给任务目录。
- **workspace 里的软链接。** 链接指向外部敏感目录，路径规范化一旦没跟链就会逃逸。定期检查 workspace 里有没有可疑链接。
- **为省事放白名单。** 把 rm 从审批门放出去，当天没事，出事那天你不会记得是为什么。

## 可复用建议

1. 最小 workspace 原则：agent 拿到的目录恰好覆盖任务即可，多一分都是风险面。
2. 默认拒绝、显式放行，工具清单宁窄勿宽。
3. 一条简单规则：无人值守 = 容器沙箱必开；有人盯着的会话可以放宽。
4. 做一次“逃逸演练”：明确让 agent 删 workspace 外的文件、读敏感配置，逐层验证真的被拒。防御没验证过，等于没配。
5. 沙箱不是备份。防御降低的是概率，备份兜底的才是后果，关键目录照常做快照。

## 总结

“Agent 不会误删文件”的准确版本是：即使它试图误删，也要连续穿过路径校验、容器隔离、工具策略、人工审批四道墙，且每道墙默认都是关着的。OpenClaw 不指望模型可靠，指望的是**把犯错的成本系统性压低**。这套思路对任何 agent 系统的权限设计都通用：不要信任调用方，约束执行环境。
