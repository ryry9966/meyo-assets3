# 背景

我们服务端有几个模块，日志分散在不同机器和文件里。日报此前靠人肉：早上翻一遍日志、凭印象写几句，容易漏、格式不统一，换个值班的人风格就变。上个月我们把这件事流水线化：定时任务加一个通过 MCP 挂载工具的 OpenClaw Agent，每天固定产出结构化日报。跑了两周多比较稳定，记录一下做法。

# 问题

直接让模型读日志有两个硬伤：

- **量太大**：一天几百万行远超上下文，信噪比也差，DEBUG 和正常 INFO 会把真正的异常淹没；
- **输出不稳定**：自由文本没法归档、没法对比、没法进下游统计。

另外还有三个工程问题：日志是 UTC 时间戳而日报按本地日切；任务静默失败导致“日报看起来正常但其实是旧数据”；重跑时产生重复报告。

# 做法

流水线分四层，只有第三层涉及 LLM：

1. **采集归一化**：脚本按窗口拉取日志（本地文件 + HTTP 接口），统一成 `{timestamp, level, service, message}` 的 JSON。丢掉 DEBUG，WARN 按 1/10 抽样，时间戳在这一层统一转成带时区的形式。
2. **聚合**：按服务分组，算错误计数、p95 耗时；对 message 做简单指纹归并（去掉数字、ID 等变量段）得到 Top N 错误。给模型的是这份聚合结果，不是原始日志。
3. **Agent 摘要**：cron 触发一次无状态 Agent 调用，MCP 挂两个工具：`query_daily_aggregate(date)` 和 `send_report(report)`。Prompt 要求严格按预定义 JSON Schema 填充：整体状态、异常事件列表（指纹、次数、首末次出现时间）、与前一日对比、待跟进项。
4. **校验投递**：输出先过 JSON Schema 校验，失败重试最多 2 次；仍失败则降级——直接把聚合表格投出去并告警。报告以日期为主键，重跑覆盖不追加。投递走 webhook 到 IM 群，同时落盘一份带日期的 JSON。

# 踩坑点

- **别让模型直接读日志**。第一版把 tail 的几千行塞进去，重点全被淹掉，摘要基本不可用。改成“先聚合后摘要”才稳定。
- **时区**。第一天日切切错了 8 小时。日切时区必须显式配置，不要依赖机器默认值。
- **模型在 JSON 外附解释文字**。靠 schema 校验加重试解决，别指望 prompt 一句话约束住。
- **静默失败最危险**。有天 MCP 工具超时，流水线挂了但群里“昨天的日报”看着没问题，中午才发现。现在无论成败都发一条带状态的哨兵消息——日报缺失本身也是一种告警。

# 可复用建议

- **Schema 先行**：先定报告结构再写 prompt，校验器和 prompt 引用同一份 schema 定义。
- **职责切干净**：计算、过滤、去重全放确定性脚本里，LLM 只做摘要和措辞，数字永远不来自模型。
- **Agent 保持无状态、单次调用**：调度、重试、告警放在普通脚本层，出错就整体重跑。
- **流水线自己也打日志**：排查“今天的报告为什么长这样”时，这份日志比模型输出有用得多。

# 总结

这套东西没有黑魔法：一个确定性的数据准备层，加一次受 schema 约束的 LLM 调用。把不确定性压缩到最小，日报才敢真正无人值守。整体就几百行脚本加两个 MCP 工具封装，难点在 schema 设计和失败路径。社区里做类似事情的同学，欢迎交流各自的 schema 和降级策略。
