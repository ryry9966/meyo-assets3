## 背景

我们组里长期跑着一批自动化任务：定时巡检、Agent 日常执行、数据抓取，日志各自落在不同目录。之前每天早上要人工翻四五处日志拼一份日报，快则十几分钟，慢则半小时，还经常漏掉某台的异常。

## 问题

原始日志有三个特征：分散、噪音大、无结构。直接整包丢给 Agent 总结行不通——几万行先撑爆上下文，而且模型会"顺手"改写数字，日报里出现约数甚至编造值。对一份要拿去做决策的报告，这是不可接受的。

## 做法

最后收敛成一条四段流水线，全程由 OpenClaw 定时任务串联：

1. **采集归一化**：纯脚本，把各处日志收敛成统一 JSON Lines，字段固定为 `ts / source / level / summary`，时区在采集层统一转本地。这一步完全不碰模型。
2. **预聚合降噪**：按 source 分组计数、去重、白名单过滤，错误全保留，心跳类折叠成一行。同时用代码算出精确统计：成功/失败次数、耗时分位数。数字只来自代码。
3. **Agent 叙述层**：定时触发 Agent，经 MCP 文件工具读入预聚合数据和固定提示词模板，要求输出固定 schema 的 JSON（关键事件/异常/待办/一句话趋势），再由渲染脚本把 JSON 转成 Markdown。模型只负责"说话"，不负责"算数"。
4. **校验与投递**：JSON Schema 校验失败自动重试一次，再失败就降级成纯模板报告（只有数字没有叙述），webhook 推送到频道并落盘归档。任务本身加心跳检测——收不到日报比收到坏日报更危险。

## 踩坑点

- 初版直接喂原始日志，token 爆掉且总结不稳定；预聚合后输入量降了两个数量级。
- 时区坑：日志是 UTC，日报标题的"今天"是本地时间，统计窗口曾差出 8 小时。
- 模型偶尔把"失败 3 次"写成"约 3 次"。解法是数字全部以占位符注入，提示词里明确禁止改写数值。
- 换模型或改提示词后 JSON 结构漂移，渲染脚本挂掉。Schema 校验 + 重试 + 降级三件套必须常驻。
- 日志里混着 token 和内网地址，渲染前加了一层脱敏正则。

## 可复用建议

- 把日报 schema 当 API 契约维护，改格式带版本号。
- 数据准备与叙述生成严格分离：前者是可单测的确定性代码，后者才交给模型。
- 保留原始快照，报告可重放重生成，方便回查"昨天的日报为什么少一条"。
- 叙述层用小模型足够，成本和延迟都友好。

## 总结

这条流水线的核心不是"让 AI 写日报"，而是把日报拆成确定性计算与受控生成两层。跑了一个多月，每天 20 分钟的人工缩到零，期间两次异常都被降级路径兜住。代码量很小：一个采集脚本、一个渲染脚本、一段定时配置，值得复刻。
