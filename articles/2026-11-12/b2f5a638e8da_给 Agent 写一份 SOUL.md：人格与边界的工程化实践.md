## 背景

OpenClaw 工作区里有几个默认加载的 Markdown 文件：AGENTS.md 管操作规范，TOOLS.md 管工具说明，MEMORY.md 管记忆沉淀，而 SOUL.md 管的是"这个 Agent 是谁"。它每轮对话都会注入上下文，改完即生效，本质上是一份持久生效的人格与边界声明。

很多人只写两行"你是一个友好的助手"就完事。但在一个接了 MCP 工具、跑定时任务、长期运行的 Agent 里，SOUL.md 是少数能稳定控制其行为倾向的手段，值得认真对待。

## 问题

没认真写过 SOUL.md 的 Agent，跑久了常见四类症状：

- **语气漂移**：多会话之间人格不一致，上周正经这周油腻；
- **边界模糊**：接了 shell 和文件系统工具后"热心过头"，你随口抱怨磁盘满，它直接动手删文件；
- **讨好倾向**：没有明确边界时，被追问几句就放弃自己原本正确的判断；
- **多 Agent 串味**：几个不同职责的 Agent 共用默认配置，结果全是一个性格。

根源是一样的：行为约束只存在于单次对话里，没有沉淀成持久配置。

## 做法

一份能用的 SOUL.md，建议按四段写，整体控制在 40 行以内：

1. **身份（1-2 句）**：一句话说清它是谁、服务谁。比如"你是我的个人运维助手，服务对象是我本人"。
2. **语气（2-3 条）**：用可判定的描述，别写"有趣一点"这种模糊词。"回复先给结论、再给解释"比"保持幽默"有用得多。
3. **边界（3-5 条，写具体动作）**：这是核心。不要写"别做危险的事"，要写"删除超过 10 个文件前必须列清单等我确认""涉及付款、给真人发消息、改生产配置的操作，一律先停下问我"。
4. **升级策略（1-2 条）**：明确什么情况下该停下来而不是硬猜，比如"不确定我的意图时，先问一句再动手，不要默认揣测"。

写完放工作区根目录，下一轮对话即生效，然后跑几个真实任务观察反应。

## 踩坑点

- **写太长**：SOUL.md 每轮都在上下文里，几百行的人生观陈述只会稀释关键指令，我见过 300 行的版本，核心边界反而被淹没。
- **混淆职责**："部署前先跑测试"是流程，属于 AGENTS.md。SOUL.md 管"是谁"，AGENTS.md 管"怎么干活"，混着写两边都会失效。
- **人设压制任务**："永远谨慎、绝不冒险"这种写法，会让 Agent 在自动化场景反复拒执行、反复确认，定时任务直接卡死。边界要圈的是具体危险操作，不是性格上畏手畏脚。
- **改完不验证**：每次改动后至少跑一轮日常任务，重点看它对边界条款的实际反应，而不是脑内默认"应该没问题"。
- **多 Agent 共用一份**：运维 Agent 和写作 Agent 的边界完全不同，宁可各写一份短的。

## 可复用建议

- **边界条款从真实事故反推**：出过一次误操作，就补一条具体规则，比凭空预想有效得多；
- **SOUL.md 进 git**：像代码一样 review，人格变更留记录，出问题能回滚；
- **硬边界和软偏好分开写**：资金、删数据、联系真人这类硬边界用"必须/一律"，语气格式属于软偏好，措辞可以松一点；
- **每月清理一次**：删掉没起作用的条款，保持文件短小。

## 总结

SOUL.md 不是给 Agent 算命的人设卡，而是一份持久生效的行为配置：身份一句话、语气可判定、边界写具体动作、升级策略明确。它的价值不在文采，而在跑一个月后 Agent 的行为仍然可预测。先从 20 行开始，用真实日志迭代，比一次写一份完美版本靠谱得多。
