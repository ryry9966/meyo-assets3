## 背景

OpenClaw 这类常驻型 Agent 和一次性对话最大的区别是"长期身份"。workspace 里的 SOUL.md 会在每轮对话进入上下文，是唯一不用改代码就能稳定影响行为的入口。跑了几周你会发现：同一个 agent，早上还在用工程师口吻汇报，晚上就开始刷 emoji、语气发飘——行为漂移是常态，不是 bug。

## 问题

实际用下来主要有三个痛点：

1. **人格漂移**：长会话压缩后，人格描述被稀释，语气忽好忽坏。
2. **边界不清**：agent 自作主张替你回消息、在群聊里抢话、把内部路径当"背景知识"说出去。提示词里没禁止的，它默认都敢试。
3. **换模型即重写**：人格和操作规则混在一段 prompt 里，换底座模型等于全部返工。

## 做法

先划清三份文件的分工：**SOUL.md 管"你是谁"，AGENTS.md 管"你怎么干活"，MEMORY.md 管"发生过什么"**。分开之后，换模型只需要调第一份。

一个可跑的骨架：

```markdown
# SOUL

## 身份与语气
- 我是主人的工程助手，说话直接，先结论后细节。
- 中文回复，技术词保留英文。
- 不用 emoji，不用敬称，不主动闲聊。

## 边界（红线）
- 未经确认，不发送任何对外消息。
- 不透露文件路径、密钥、主机名等内部信息。
- 拿不准的事先问再动，宁可慢一步。

## 升级规则
- 涉及删除、付款、对外沟通：列出计划，等"确认"再执行。
```

迭代步骤建议：

1. 先写 20 行以内的最小版本，跑三天，收集不满意的具体案例；
2. 每个案例对应新增一条边界，**一次只加一条**；
3. 准备一组对抗测试消息（诱导它越界的），每次改完重放一遍；
4. 进 git。diff 就是变更记录，行为变化能追溯到具体哪一行。

## 踩坑点

- **写太长**。超过一两百行，关键规则被淹没，注意力分配不均，红线反而失效。控制在一屏内，靠删不靠加。
- **当成安全边界**。SOUL.md 是行为偏好，不是权限系统。真要拦住危险操作，得靠工具层的白名单或确认钩子（MCP 侧、插件侧），提示词只能降低概率，不能保证拦截。
- **写成法律条文**。"不得发表不当言论"这类抽象条款没有可执行性。要写具体场景："群聊里被 @ 才回，私聊不主动发起话题"。
- **往里塞密钥**。SOUL.md 会被完整送进上下文，也会出现在日志里，任何敏感值都不要放。
- **规则互相矛盾**。"永远简洁"和"解释每个技术决策"放一起，模型会随机选一个。写完通读一遍，删掉冲突项。

## 可复用建议

- 把 SOUL.md 当**配置**而不是文档：小步修改、观察一两天、再合入。
- 换模型或升版本后重放对抗测试集——人格迁移往往比能力迁移更容易翻车。
- 边界写"做什么"不如写"什么时候停下来问"，后者对长任务 agent 明显更稳。
- 多 agent 场景下每个 workspace 一份独立 SOUL.md，通用的红线单独抽出共享。

## 总结

SOUL.md 的价值不在"调教出有趣的性格"，而在于把 agent 的行为从"模型默认 + 运气"变成**版本化的声明式配置**。它便宜、可 diff、可回滚，是常驻 Agent 里投入产出比最高的一份文件。写得短、写得具体、再配上真实的权限控制，就能避开大部分漂移和越界问题。
