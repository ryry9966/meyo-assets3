## 背景

在 OpenClaw 的 Agent 和 MCP 工具链里，让模型输出 JSON 是日常操作：工具参数、结构化中间结果、插件间传递的数据。但实践下来你会发现，即便 prompt 里写了「只输出 JSON，不要任何多余文字」，拿回来的东西依然五花八门：代码围栏包裹、前后带解释句、全角引号、尾逗号、字符串值里嵌 Markdown……解析失败不是偶发，是常态。这篇记录我在插件链路里沉淀的一套防御性解析做法。

## 问题

同一个任务，实测出现过三类输出：

1. JSON 外面套了代码围栏，且语言标记大小写混乱，甚至写 `json5`；
2. 先说一句「好的，以下是结果」，再给 JSON，结尾再补一句提醒；
3. JSON 本身带尾逗号、单引号、值里含未转义换行，混入 Python 风格的 `True/None`。

如果解析只有一行 `json.loads(content)`，这三种全挂，且日志里只有一条 `SyntaxError`，无法定位是哪种形态。

## 做法

把解析拆成四层，每层只做一件事，任一层产出就交给下一层校验：

1. **围栏剥离**：用正则匹配围栏（语言标记可有可无、大小写不敏感），取围栏内内容；无围栏则原文继续。
2. **边界提取**：不假设 JSON 从首字符开始。写一个小状态机，扫描第一个 `{` 或 `[`，维护 in_string 和转义状态，做括号配对，截出完整子串。不要用贪婪正则抓花括号，字符串值里带括号必翻车。
3. **容错修复**：全角引号冒号转半角、去尾逗号、单引号转双引号、`True/False/None` 转 JSON 字面量。直接用 `json_repair` 这类成熟库，比自堆正则可靠。
4. **Schema 校验 + 受限重试**：用 pydantic 校验字段与类型，可选字段给默认值；失败时把原始输出和报错拼回 prompt 让模型自纠，最多重试 2 次，仍失败就落默认值并打标记转人工。

两条铁律：永远保留原始输出用于排查；解析失败率进监控，按失败类型分类计数。

## 踩坑点

- **括号计数不考虑字符串**：`{"code": "if (a) {b}"}` 会把计数器搞乱，必须维护 in_string 与 escape 状态。
- **贪婪正则**：`{.*}` 配 `re.S` 会把两个独立 JSON 对象拼成一个「貌似合法但语义错误」的结果，比直接报错更危险。
- **Python 的 `json.loads` 默认接受 NaN/Infinity**，这不是合法 JSON，下游序列化时才炸，用 `parse_constant` 拒掉。
- **修复库静默改语义**：可能把非法输入「修」成另一个合法但错误的 JSON，所以修复后必须过 schema，不能修完直接用。
- **重试放大成本**：长输出自纠很贵，设上限；流式场景等结束标记再解析，别对半截 JSON 做修复。

## 可复用建议

- 沉淀一个 `robust_json_loads(text, schema)` 工具函数 + 真实失败样例测试集，每次线上失败就往里加一条，回归跑住。
- 能用结构化输出（tool call 参数、`response_format`、MCP 工具的 JSON Schema 约束）就别靠自由文本解析，约束解码比事后修复可靠一个量级。
- 「只输出 JSON」在 prompt 里仍要写——它降低失败率但不消除失败，解析器按最坏情况设计。
- 失败日志至少包含：原始输出全文、命中的解析层、失败类型。没有这个，修复全靠猜。

## 总结

LLM 输出解析的本质，是把一个概率性文本源当成不可信输入做校验。围栏剥离、边界提取、容错修复、schema 校验四层流水线一天能写完，但它能把插件链路里「偶发解析失败」变成「可分类、可监控、可自愈」的常规工程问题。防御性编程在这里不是过度设计，是必需品。
