## 背景

过去一年做 Agent 落地，真正卡住进度的往往不是模型能力，而是“接得上”：内部数据库、工单系统、本地文件、第三方 API，每一个都要单独写一层胶水代码。更麻烦的是，各家 Agent 框架的插件格式互不兼容——同一个“查询数据库”的工具，在框架 A 里实现一遍，换到框架 B 又要重写一遍。

MCP（Model Context Protocol）就是针对这个问题提出的开放协议：把“AI 应用如何连接工具与数据”这件事标准化。可以把它理解成工具生态的 USB-C 接口。

## 它到底解决了什么问题

本质是 N×M 集成问题：M 个 AI 应用 × N 个工具，就是 M×N 份适配代码。引入 MCP 后变成 M+N——工具方按协议实现一次 MCP Server，应用方实现一次 MCP Client，双方通过协议对接，不需要知道对方是谁。

三个核心概念值得先分清：

- **Tools**：模型可以主动调用的动作（发请求、写文件、跑查询）；
- **Resources**：应用可以读取的上下文数据（文件内容、数据库 schema、配置）；
- **Prompts**：预置的提示词模板。

底层是 JSON-RPC 2.0，传输层常用两种：本地进程走 stdio，远程服务走 Streamable HTTP。连接建立时会先做一次 initialize 握手，协商双方能力，之后再列工具、发调用。

## 最小落地步骤

1. 用官方 SDK（Python 或 TypeScript）起一个最小 MCP Server，先只暴露两三个只读工具；
2. 工具描述按“给模型看的 API 文档”标准来写：做什么、参数含义、返回结构、失败时是什么样；
3. 参数 schema 用 JSON Schema 严格声明：类型、必填项、枚举值都写清楚；
4. 在客户端（如 Claude Desktop 的配置文件，或 OpenClaw 的 MCP 接入配置）注册 server 的启动命令；
5. 先手动确认 tools/list 注入的 schema 正确，再让模型实际调用，对照日志核对参数。

## 踩坑点

- **stdio 下 stdout 被协议独占**：任何 print 或日志打到 stdout 都会污染 JSON-RPC 流，连接直接挂掉。日志一律走 stderr 或写文件。
- **工具描述含糊是头号坑**：模型会选错工具或编造参数。描述写得越像文档，调用越稳。
- **工具数量失控**：一次注入几十个工具，上下文膨胀、选择准确率明显下降。按场景拆分 server。
- **schema 偷懒**：缺 required、类型宽泛，模型填参就会很随意。
- **长耗时工具不做超时和进度反馈**，客户端侧表现为“卡死”。
- **权限问题**：写操作、删除操作不要裸暴露，至少加确认机制或白名单。

## 可复用建议

- 把 MCP Server 当“面向模型的产品”来设计：描述即提示词，值得花大部分时间打磨这一层；
- 工具粒度宁大勿碎：少量语义完整的工具，好过一堆细碎原语让模型自己拼；
- 错误返回结构化、模型可读的文本，并在描述里写清“失败后该怎么办”，模型具备自愈重试的空间；
- 固化一套脚手架模板：日志、错误处理、鉴权、schema 校验统一处理，新工具只填业务逻辑；
- 只读先行，链路验证稳定后再逐步放开写操作。

## 总结

MCP 解决的不是“模型更聪明”，而是“集成标准化”。对实践者的实际价值是：把过去花在写胶水代码上的时间，转移到把工具描述和 schema 写清楚上——后者才是真正决定模型调用质量的变量。协议本身仍在演进（尤其授权部分），建议从只读、本地、小规模起步，完整跑通一次调用链路后再扩展。
