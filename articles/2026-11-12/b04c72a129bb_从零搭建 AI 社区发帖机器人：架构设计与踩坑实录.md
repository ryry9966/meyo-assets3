## 背景

社区运营里有一类高频但机械的活：每日精华汇总、新帖打标签、回复 @提及、活动预告同步。人工做费时且容易漏。我们基于 OpenClaw 的 Agent + MCP 工具链搭了一个发帖机器人，跑了两个月，发布内容的人审通过率从 61% 提到 92%。这篇帖子记录架构设计和真实踩过的坑，给想动手的同学一个参考。

## 问题

核心诉求三条：

1. 定时产出内容：每日摘要、精选帖推荐；
2. 对 @机器人 的提问做引用回复；
3. 全程可审计：每条发出的内容能追溯到当时的 prompt 与决策。

约束条件：社区 API 有限流；内容质量不能低于人工底线；原则是**宁可漏发，不可错发**。

## 做法与步骤

按职责分五层：

- **调度层**：cron + 任务队列，每个任务带唯一 task_id；
- **生成层**：Agent 读取素材源（RSS、精华帖、issue），按模板产出草稿；
- **审核层**：规则过滤（敏感词、长度、格式白名单）+ LLM 按 rubric 自评打分，低分进人工队列；
- **发布层**：社区 API 适配器，负责 token 刷新、限流、重试，是唯一能写外部世界的模块；
- **状态层**：SQLite 记录帖子状态机 `draft → reviewed → scheduled → published / failed`。

实现顺序很关键：先跑通发布适配器的 dry-run 模式（只写日志不落帖）→ 再接生成层 → 最后才放开自动发布。

## 踩坑点

1. **定时任务重复执行**。cron 和手动触发撞车，同一篇摘要发了两次。修复：以 `hash(素材id + 日期 + 槽位)` 做幂等键，发布前查库拦截。
2. **内容同质化**。模板固定后连续十篇结构雷同，被版主点名。修复：素材池随机化，并把近期已发标题注入 prompt 做相似度排除，embedding 余弦超过 0.85 直接重写。
3. **token 过期打断批量发布**。中途 401 导致半批成功半批失败。修复：适配层统一管理 token，指数退避并尊重 Retry-After。
4. **Markdown 渲染差异**。表格和嵌套列表在社区渲染器下错乱。修复：发布前按社区同款渲染规则做一次白名单清洗。
5. **Agent 自由调用发布工具**。调试期一条畸形草稿直接被发了出去。修复：发布工具加 dry_run 参数和二次确认包装，Agent 默认只能产出草稿，"提交"动作单独走审核队列。
6. **排障困难**。多环节日志散落，无法定位失败点。修复：全局 run_id 贯穿链路，每一步的 prompt/response 全量落库。

## 可复用建议

- 幂等键在调度层生成，发布层只认键、不认时间；
- 限流与重试放适配层，调度层保持极简；
- 把"发布"做成最小权限的独立插件，其余环节随便重跑；
- 衡量指标看**人审通过率**和**撤回率**，不看产量；
- 上线顺序永远是 dry-run → 人工审核 → 低风险版面自动发；
- LLM 输出全量落库，方便回归测试与事后审计。

## 总结

发帖机器人的难点不在生成，而在**边界**：什么能发、何时能发、错了怎么办。把发布权限收窄、把状态落库、把审核做成独立层，剩下的都是普通工程问题。整体代码结构并不复杂，业余时间一个月可以复刻。欢迎在评论区交流幂等设计和风控细节。
