## 背景

社区内容组每周要稳定产出 2-3 篇技术帖，纯人力写选题、查资料、排版，单篇经常超过一小时。我们的目标很克制：不做“全自动内容工厂”，只做一个**选题聚合 + 初稿生成 + 人工送审**的发帖助手，把单篇耗时压到十分钟以内。技术栈全用现成的：OpenClaw 网关负责调度和对话入口，MCP 工具负责抓取与发布，SQLite 存状态。

## 做法

1. **数据源接入**：写了一个小型 MCP server，暴露三个工具：`fetch_rss`、`fetch_releases`、`fetch_issues`，抓到的条目统一落库，带去重 hash。
2. **选题与初稿**：每天早上 cron 触发一次 agent 任务，从库里挑 3 条素材，按固定 schema 输出 JSON（标题/正文/标签/来源 ID），校验不过就重试。
3. **审核流**：初稿以卡片形式推到聊天频道，人工回复“发/改/弃”，bot 才执行发布；发布走社区 API 插件，成功后把 post_id 回写数据库。
4. **监控**：任何一步失败，错误信息和 task_id 直接推到同一个频道，方便复跑。

## 踩坑实录

1. **模型编造引用**。初版允许 agent 自由发挥，正文里出现了根本不存在的链接和版本号。修复：素材只允许来自库里抓到的条目，引用必须携带来源 ID，发布前校验存在性。
2. **重复发帖**。发布接口超时后任务重试，同一篇帖子发了两次。修复：以“标题 hash + 日期”做幂等键，发布前查库，请求带幂等头。
3. **时区坑**。cron 默认按 UTC 跑，本想早上九点发，实际下午五点才触发。修复：显式指定 Asia/Shanghai，日志里打印实际触发时间。
4. **Markdown 渲染不一致**。生成的表格和嵌套列表在社区编辑器里直接乱掉。修复：发布前跑一遍格式白名单清洗，只保留标题、段落、代码块、列表。
5. **状态丢在内存里**。网关重启后“待审核”队列清空，初稿石沉大海。修复：所有状态落库，重启后从数据库恢复队列。
6. **质量翻车**。放开全自动发了两天，被指出语气生硬、有幻觉，立刻回退到人审模式。

## 可复用建议

- **先半自动，再灰度全自动**。人审跑稳两周，再对低风险内容（如 changelog 汇总）放开自动发布。
- **工具粒度小一点**。一个动作一个工具，失败定位会容易一个数量级。
- **幂等键 + 状态落库**是自动化任务的生命线，别信内存。
- **结构化输出 + schema 校验**，不要去解析自由文本。
- **“弃稿”也算成功状态**。没有合适素材就空过一天，比硬凑一篇强。

## 总结

这套东西真正难的不是接模型，而是把“发帖”拆成可校验、可重试、可回滚的小步骤：AI 负责产出，规则负责兜底，人负责最后判断。目前跑了三周，发帖耗时确实降到十分钟左右，只翻过一次车（就是上面第 6 条）。适合内容节奏固定、又不想为运营专门写一套后台的小团队直接参考。
