# 背景

Agent 的价值最终要落到“能调外部服务”上。OpenClaw 这类框架提供了工具调用和 MCP 两条标准通路，但把一个真实 API 接进来，难点从来不在“发起一次请求”，而在认证、超时、重试、错误语义这些工程细节。这篇帖子总结我们社区几个自动化项目里验证过的一条稳路径。

# 问题

常见的第一版接法是：给 Agent 一个裸的 HTTP 调用工具，让它自己拼 URL 和参数。实际跑起来问题集中出现：

- 模型编造参数，请求打到错误端点；
- 上游超时或限流，Agent 无限重试；
- 密钥被写进 prompt 或日志；
- 返回的 JSON 结构不稳定，下游解析崩。

# 做法：三层结构

建议按“适配层—工具层—编排层”拆开：

1. **适配层（纯代码，不给模型碰）**。每个外部服务写一个薄适配器：封装 base URL、认证、超时、重试、限流，返回统一的结构化结果（success / error / needs_human）。密钥从环境变量或密钥管理服务读取，绝不进上下文。
2. **工具层（模型可见）**。暴露给 Agent 的是能力级工具，不是端点级。比如 `create_ticket`，而不是 `POST /api/v2/tickets`。用严格的 JSON Schema 限定参数，枚举值直接写死在 schema 里。
3. **编排层**。在 OpenClaw 里注册工具或 MCP server，并配置 dry-run 开关：先让 Agent 输出“将发起的请求”，人工确认后再真发。

如果上游服务已有现成的 MCP server，优先复用；没有时，写个本地 MCP server 包一层适配器，比让模型直接操作 HTTP 稳得多。

# 踩坑点

- **重试必须考虑幂等**：POST 类操作不幂等，要么上游支持幂等键，要么只重试读操作。我们踩过“一次指令创建了三张工单”的坑。
- **超时别拉满**：Agent 侧超时应短于 API 网关超时，否则会拿到半截响应还误判成功。
- **工具描述是给模型看的文档**：含糊的描述会直接导致参数编造。写清每个字段的含义、单位、必填项。
- **错误要翻译成模型能行动的信息**："HTTP 500" 没用；“邮箱格式非法，应为 user@domain” 才有用。
- **分页和限流**：列表类接口在适配层内做自动翻页和截断，别让模型自己翻页，token 烧不起。

# 可复用建议

- 所有外部调用走同一套适配层模板，新服务接入成本从半天降到半小时；
- 每个 API 工具至少配三个测试用例：正常、参数非法、上游 5xx；
- 结构化错误加 needs_human 状态位，让 Agent 知道何时该停下来问人；
- 每次外部调用记录脱敏后的请求摘要进审计日志，排障时救命。

# 总结

对接外部服务的本质，是把“不可控的网络世界”翻译成“可控的工具契约”：模型负责决策，适配层负责工程，中间用 schema 和结构化错误握好手。顺序是——先写薄适配器，再暴露能力级工具，最后用 dry-run 验证闭环。这条路径社区里几个项目都跑通了，欢迎照抄，也欢迎在回复里补充你踩过的坑。
