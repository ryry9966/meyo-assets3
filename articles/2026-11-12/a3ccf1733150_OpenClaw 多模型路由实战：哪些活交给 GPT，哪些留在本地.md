## 背景

在 OpenClaw 的 agent 主管线里，模型调用远不止"一次对话"：主循环的规划推理、MCP 工具调用的结构化输出、历史上下文的压缩摘要，还有各种插件里的高频小任务。当同时接入云模型（GPT 系列）和本地模型（我这边是 Ollama 跑 Qwen 系列）两路 provider 后，绕不开的问题就是：这些调用到底怎么分流？

我的动机很直接：隐私敏感的本地文件检索不想上云，但纯本地跑复杂 agent 循环时，工具调用格式时常崩，重试成本比省下的 API 费还高。所以路由不是"选更强的那个"，而是按任务特性分派。

## 问题

两个极端我都试过：

- **全走 GPT**：成本和隐私都难受，尤其 MCP 工具会把本地文件内容带进上下文一起发出去；
- **全走本地**：长任务链上 JSON 输出不稳，一步解析失败，整个循环重跑。

分界线靠感觉判断不可靠，得拆成显式规则。

## 做法

**1. 先给任务分类。** 我把 OpenClaw 里的模型调用归成四类：

- 规划/推理：多步决策、复杂工具编排 → GPT
- 结构化输出：工具参数生成、schema 校验 → GPT（失败率敏感）
- 高频轻量：摘要压缩、分类打标、文本改写 → 本地
- 隐私敏感：本地文件内容、内网数据相关处理 → 本地

**2. 路由规则显式写进配置**（示意，按你的实际 schema 调整）：

```jsonc
{
  "routing": {
    "default": "local",
    "rules": [
      { "match": "task_type=plan|tool_call", "model": "gpt" },
      { "match": "context_has_private=true", "model": "local" }
    ],
    "fallback": "local -> gpt"
  }
}
```

**3. 每条链路定验收指标**：结构化输出成功率、P95 延迟、每千次调用成本。跑一周日志再调规则，比拍脑袋准。

**4. 降级链路做成单向**：本地失败 → GPT 兜底 → 打标记记录，避免来回震荡。

## 踩坑点

- **本地模型的指令遵循是量化后才崩的**：14B 的 Q4 版做工具调用明显不如 FP16。路由规则要按"模型 + 量化等级"粒度写，不是按模型名。
- **上下文窗口差异**：把 GPT 压好的摘要交给本地模型续跑，本地窗口小，得再做一次裁剪，否则关键约束会被截丢。
- **隐私判断别只看输入**：MCP 工具的输出、错误堆栈也可能带敏感信息。我把"上下文含本地路径/内网地址"也加进了路由条件。
- **高频小任务走本地不一定快**：模型冷加载几秒，比一次 mini 级 API 还慢，常驻或预热要单独处理。
- **兜底要限次数**，否则上游抖动时会打出重试风暴，账单和显存一起遭殃。

## 可复用建议

- 用"能力分级"想问题：规划级、结构化级、轻量级、隐私级，模型只是这些级别的实现，换了型号规则不变。
- 路由规则放显式配置，别让主模型自己"猜"该用谁——猜不稳，也没法审计。
- 每类任务配一个可量化指标，改路由前先看数据。
- 本地模型专挑"输入输出短、容错高"的任务，这是它最稳的生态位。

## 总结

多模型路由的价值不在省钱本身，而在把"哪些调用允许出网、哪些必须留在机器上"变成一条可审计的规则。在 OpenClaw 里我建议的切入顺序：先摘高频轻量任务给本地，再把隐私相关的钉死在本地，规划链路留给 GPT。规则要能被日志验证、被指标驱动，而不是跟着感觉改。
