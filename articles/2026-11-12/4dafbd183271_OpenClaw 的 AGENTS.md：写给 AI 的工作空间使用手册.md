先把结论放在前面：在我们所有 OpenClaw 配置里，AGENTS.md 是投入产出比最高的一个文件。它决定 agent 每个会话"带着什么常识开工"。

## 背景

OpenClaw 的工作空间里有几个约定文件，分工其实很清楚：SOUL.md 管"我是谁"，MEMORY.md 管"记得什么"，而 AGENTS.md 管"活儿怎么干"。关键区别在加载机制——记忆靠检索召回，可能漏；AGENTS.md 每个会话完整注入上下文，永远在场。这意味着它是唯一可靠的、跨会话生效的行为约束入口。

## 问题

没有这份手册时，重复出现的场景很典型：

- 每次新会话都要重新交代"测试怎么跑、哪些文件不能动"；
- agent 按默认习惯行事：用错包管理器、直接改生成文件、重要操作不先确认；
- MCP 工具和插件装了一堆，但 agent 不知道什么场景该用哪个，最后凭名字瞎猜。

这不是模型能力问题，是上下文缺失问题。修复成本便宜得惊人：一个 Markdown 文件。

## 怎么写

我们的 AGENTS.md 迭代了三版，现在稳定在 80 行内，五个板块：

1. **环境速览**：运行环境、工作目录布局、各文件的角色；
2. **命令区**：构建/测试/部署命令，一条一行写死，不写"见 package.json"；
3. **禁区**：generated 目录、lockfile、凭证文件——明确"不要主动修改"；
4. **工具路由**：查数据用哪个 MCP 工具、什么操作必须先征求确认、什么可以放手做；
5. **完成定义**：改动后必须跑什么验证才算"做完"。

写法三原则：祈使句、可执行、不超过两屏。

## 踩坑点

- **写成论文**。第一版写了 300 行"项目理念"，实测 agent 明显漏读后半段。压到 80 行后遵守率肉眼可见地回升——注意力是固定预算，每句废话都在稀释关键指令。
- **写"详见某文档"**。agent 不一定真去读链接。关键信息直接内联，允许重复。
- **指令太虚**。"代码要整洁"零约束力；"commit message 用 conventional commits"才有效。
- **过期不更**。脚本改名后没同步手册，agent 连续两周调用已不存在的命令。改了工具链就顺手看一眼 AGENTS.md，把它纳入 review 范围。

## 可复用建议

- 当 runbook 维护，别当文档：短、可验证、进版本库。
- 建"错题本"机制：agent 重复犯同一个错，就往手册加一行。它应该由真实事故驱动增长，而不是想象中的需求。
- 验证方法朴素但有效：开全新会话派个小任务，观察遵守率，这是最诚实的指标。
- 任务复杂时拆子目录各自的 AGENTS.md，根文件只留全局约定，避免单文件膨胀。

## 总结

把 AGENTS.md 当成写给"一个读得很快但毫无背景的新同事"的入职手册，方向就不会错：他知道去哪找东西、什么不能碰、做完以什么为标准。半小时的维护成本，换来每个新会话少踩一遍坑，这笔账很划算。
