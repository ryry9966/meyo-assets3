# 背景

同一套 Agent 工作流，在不同机器上表现经常不一致：本机有 `uv`，同事的机器只有 `pip3`；CI 里 docker 可用，个人笔记本上没装；端口 3000 被占用后 Agent 反复重试直到超时。这些差异的根源不在模型，而在 Agent 每次启动会话时，对“这台机器长什么样”一无所知。

# 问题

常见的错误做法是把环境信息散落在三处：

- **系统提示词里写死路径**：换台机器立刻失效；
- **README 里顺手记一段**：混入了只有人类才关心的内容，Agent 反而被干扰；
- **让 Agent 运行时自己探测**：浪费 token 和时间，还容易猜错、猜出危险命令。

更糟的是，有人直接把 API key 写进提示词模板——环境差异管理和密钥管理从此搅在一起，出一次事故就够记一辈子。

tools.md 的定位就是收敛这件事：用一个约定俗成的入口文件，声明这台机器/这个项目的**工具事实**。注意，它不是说明书，而是资产清单。

# 做法

推荐三层结构：

1. **仓库级 `tools.md`**（提交 git）：写跨机器稳定的事实——依赖 Python 3.11+、测试命令是 `pytest -x`、构建产物在 `dist/`。团队共享这一份。
2. **本地级 `tools.local.md`**（加入 .gitignore）：写机器差异——macOS 用 `brew`，WSL 里 docker 需要 sudo，本机代理端口是 7890。
3. **会话级覆盖**：临时差异用命令行参数注入，不落盘。

生成基线可以写一个十行的探测脚本（检查 `which python`、`docker version`、剩余磁盘空间），输出后人工修订。关键原则：**tools.md 描述“状态”，不描述“流程”**。“怎么跑测试”应该进 Makefile；“测试命令存在，但需要先启动本地数据库”才值得写进 tools.md。

# 踩坑点

- **写入密钥**。tools.md 会被 Agent 全文读取，还可能进入日志。密钥走环境变量，tools.md 只写“密钥从 `~/.secrets/xxx` 加载”。
- **膨胀成第二个 README**。超过 60 行，Agent 读取成本上升，人也懒得维护。经验上限：一屏以内。
- **信息过期比没有更糟**。Agent 会默认信任这里的内容。装了新工具、删了旧依赖，必须同步更新，否则它会坚持调用一条已经不存在的路径，并且解释得头头是道。
- **和可探测事实重复**。Python 版本 Agent 一条命令就能查到，写进 tools.md 只会制造两处“真相”，迟早打架。

# 可复用建议

- 在 CI 里加一个 `doctor` 脚本，校验 tools.local.md 中列出的命令真实存在，防止本地文件悄悄漂移。
- 模板随仓库分发：新人 clone 后只填 local 部分，五分钟接入。
- 依赖声明变更的 PR，要求同步检查 tools.md——把它当作环境依赖的“锁文件”对待。
- 保持可验证性：每条信息旁边附上验证命令，例如 `node >= 20（用 node -v 验证）`。

# 总结

tools.md 解决的不是技术问题，而是信息架构问题：把“机器差异”从提示词、口口相传和个人脚本里抽出来，放进一个分层、可版本化、可校验的单一入口。做到**短、真、不含密钥**，它就是多机 Agent 协作里最省心的一份配置。
