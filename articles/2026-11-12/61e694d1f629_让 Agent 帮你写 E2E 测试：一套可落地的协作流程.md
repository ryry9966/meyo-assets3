E2E 测试大概是所有团队“知道该有、但一直欠账”的部分：写得慢、维护贵、失败难定位，覆盖率常年停在几条冒烟用例上。过去两个月，我们在 OpenClaw 上让 Agent 通过 MCP 接管了一部分 E2E 的编写与维护，覆盖了 11 条核心用户旅程。这篇记录可复现的流程和踩过的坑。

## 背景

Agent 适合干这件事的原因很朴素：E2E 的痛点——生成样板代码、修选择器、分诊失败——恰好是 Agent 擅长的机械劳动。前提是给它正确的工具和边界：Playwright MCP 负责浏览器操作，shell 工具负责跑测试，文件读写负责改代码，全部以插件形式挂载，权限逐项确认。

## 问题

直接说“给这个页面写测试”，产出通常不可用，三个典型症状：

1. 只有 happy path，断言浅——检查元素存在，不检查业务结果；
2. 选择器脆弱，爱写 CSS 路径和 nth-child，页面一改全崩；
3. 失败就用 sleep 和 retry 糊，把 flaky 掩盖成“修好了”。

根因是 Agent 缺两样东西：真实用户旅程的上下文，和一套测试书写规范。

## 做法与步骤

1. **给工具、限边界**。挂 Playwright MCP、文件读写、shell（跑 `playwright test`）。目标环境只指向本地/沙箱，凭据走测试账号 fixture + storageState，不让 Agent 接触真实登录态。
2. **先出计划，再出代码**。把用户旅程写成简短 charter（旅程 → 步骤 → 应断言的业务结果），Agent 先产出测试计划表，人审通过后再生成代码。计划才是评审对象，代码只是产出物。
3. **规范注入**。写一份测试约定文档，随每次任务自动携带：

```text
- 选择器：getByRole / data-testid，禁 CSS 路径、nth-child
- 禁止 waitForTimeout；等待交给 expect 自动重试
- 登录统一走 fixtures/auth.storageState
- 每条用例至少 1 个业务结果断言
- flaky 处理：先给根因，禁止无解释地加 retry
```

4. **CI 闭环**。失败时只喂 trace 文件和错误摘要（不要倒全量日志），让 Agent 分类：真 bug / 选择器漂移 / 环境抖动，输出修复 diff 或 issue，附根因说明。
5. **人工门禁**。Agent 产出永远走 PR，不碰 CI 配置，不直接合并。

## 踩坑点

- **自证清白的测试**：Agent 会断言自己刚造的数据。约定里明确要求断言落在用户可见结果上。
- **用 retry 掩盖问题**：遇到 flaky，它的默认动作是加 wait。必须先给根因，否则不给合并。
- **浏览器 MCP 权限过大**：务必只连沙箱，给每次会话设操作预算，防止误点触发真实副作用（发通知、下单这类操作尤其危险）。
- **上下文膨胀**：全量日志很快撑爆窗口，只给 trace + 失败用例摘要。
- **一次生成太多**：单 PR 限 5 条用例，按旅程风险排序，否则没人认真审。

## 可复用建议

- 先盖登录、核心提交类的冒烟旅程，稳定跑两周再扩；
- 维护一份共享 fixture / storageState 库，别让 Agent 每次重新发明登录；
- 度量用“旅程覆盖率”，不用“用例数”；
- 每次踩坑沉淀回约定文档——这份文档才是这套体系真正的资产。

## 总结

分工其实很清楚：Agent 干机械部分（脚手架、选择器修复、失败分诊），人负责意图（断言什么、什么算真 bug）。把规范写清、边界收窄、评审计划而非代码，E2E 的欠账是可以一点点还上的。
