## 背景

订阅源越攒越多，真正读完的越来越少。RSS 虽然老，但它是少数完全由自己控制的输入通道：格式统一、无算法干预、天然适合程序化处理。所以我的思路不是换一个"更聪明的阅读器"，而是把 RSS 当作管线的上游，让 AI 只承担中间的压缩和筛选工作。

## 问题

直接把文章丢给 LLM 总结，会遇到几个现实问题：

1. **成本不可控**——源一多，每天几百条全量摘要，token 消耗很快失控；
2. **摘要失真**——不少源只输出 summary 而非全文，对摘要再做摘要，信息两次衰减；
3. **产出没人看**——几十条摘要堆在一起，和没过滤差别不大，关键是排序和淘汰。

## 做法

管线拆成四层，每层独立可替换：

**1. 抓取层**：Miniflux/FreshRSS 自托管聚合，配 RSSHub 补齐没有官方源的站点。这层只负责标准化输出，不碰 AI。

**2. 粗筛层**：纯规则，零 token。按关键词、来源权重、发布时间做第一道过滤，通常能砍掉六成以上。别小看这层，它是成本控制的命门。

**3. 摘要层**：把 RSS 读取封装成一个 MCP tool（输入 feed 地址，返回标准化条目），交给 OpenClaw agent 调度。prompt 强制结构化输出：一句话结论、三个要点、相关度评分（1-5）。低于阈值的直接丢弃。

**4. 输出层**：每天固定时间聚合成一份 digest 推到 Telegram。摘要永远带原文链接——AI 的角色是帮我决定"哪些值得点进去"，不是替我读。

## 踩坑点

- **全量摘要必挂**：第一天让 agent 处理了全部新条目，200 多条跑了一个多小时，费用感人。加上粗筛层和每日条目上限后才稳定。
- **只有摘要的源要降权**：有的源 feed 里就两行 summary，让 LLM 基于这个输出要点纯属浪费。抓取层给这类源打标，摘要降级为一句话判断"是否值得抓全文"。
- **去重要在摘要前做**：同一件事常被多个源重复覆盖。用标题相似度（编辑距离 + 关键词重合）先合并，否则 digest 全是重复项，还重复烧 token。
- **agent 重试风暴**：某天源站超时，agent 无限重试把队列堵死。给 MCP tool 加了失败上限和退避，超限条目进死信列表，第二天随下一批重跑。
- **时区归一化**：RSS 的 pubDate 时区混乱是真实存在的。digest 按本地时区聚合，否则"每日"会漏掉半夜发布的条目。

## 可复用建议

1. **先规则后模型**：规则能解决的别上 LLM，粗筛层省下的成本比任何 prompt 优化都多。
2. **摘要分级**：一句话 → 要点 → 全文，按需取用。digest 里只放一句话 + 链接，感兴趣再让 agent 深挖。
3. **结构化输出是聚合的前提**：自由文本没法排序合并，prompt 里强制 JSON schema。
4. **每层留观测**：粗筛砍了多少、评分分布、digest 打开率——这些数字决定该调哪一层。

## 总结

管线跑了一个多月，每日 digest 稳定在 10 条以内，真正值得点开的两三条。它没有让我"读得更多"，而是让阅读回到少数高信噪比的入口。RSS + AI 的正确组合，是把 AI 放在压缩和筛选的位置，而不是让它生成一堆你根本不会看的"内容"。管线本身价值不大，可复用的是分层思路：上游标准化，中层按成本分级处理，下游只输出决策所需的最小信息。
