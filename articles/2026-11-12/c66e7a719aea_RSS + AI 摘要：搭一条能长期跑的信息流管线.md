## 背景

RSS 这两年被反复唱衰，但在技术博客、GitHub Release、安全公告、论文这类源头，它依然是最稳定、最无算法干预的订阅方式。问题从来不是 RSS 死了，而是订阅源一多就读不完。让 LLM 做摘要是很自然的想法，但把所有条目全量塞给模型，成本和摘要质量都会失控。这里记录我用 OpenClaw 搭的管线和几轮调整过程。

## 核心问题拆开看

- **读不完**：日均 100+ 条，人工精读不现实
- **读不全**：大量 feed 只输出 summary，信息密度极低
- **没沉淀**：看完就忘，没有按主题归档
- **直接上 LLM 的副作用**：重复条目重复计费、模型补全幻觉、日期混乱导致排序错乱

## 管线设计：四段解耦

我把整条链路拆成四段，每段独立可重跑：

**1. 采集层**。feed 列表放在配置文件里，定时任务每 2 小时触发一次抓取。按 guid + link 做哈希去重，所有原始条目先无差别落库（SQLite 就够），不做任何加工。

**2. 清洗层**。对只有摘要的 feed 二次抓正文（readability 类工具），统一抽出标题 / 正文 / 发布时间。过一遍关键词黑名单做粗筛，这一步能砍掉 60% 以上的无关条目——是控制成本最有效的一环。

**3. 摘要层**。粗筛后的条目按来源分批（8–10 条一批）送 LLM，要求结构化输出：每条一行摘要、2–3 个要点、主题标签、重要度 1–5。提示词里明确限定"只基于给定文本归纳，禁止补充外部信息"。

**4. 分发层**。重要度 4 以上即时推送到 IM，其余攒到每晚汇成日报。在 OpenClaw 里，抓取和摘要封装成两个独立的 MCP 工具，定时任务只负责编排，互不影响。

伪代码大致如下：

```
fetch_feeds() -> dedupe(hash) -> store_raw()
clean(items)  -> fulltext_filter() -> keyword_prefilter()
summarize(batch, schema) -> validate(json_schema)
route(score >= 4 ? push_now : daily_digest)
```

## 踩坑点

- **partial feed 必须二次抓正文**，否则模型只能对着两行 summary 硬编，摘要质量极差。
- **feed 的日期不可信**。见过不少源 pubDate 是错的，去重和排序都要拿入库时间兜底。
- **成本最容易在去重上失守**。同一条新闻被多个源转发，不去重就是重复计费。落库前查哈希 + 摘要结果缓存，双保险。
- **幻觉靠 schema 压不住**，只能靠提示词约束 + 摘要强制带原文链接，方便人工抽查核对。
- Atom、RSS 2.0、JSON Feed 的字段差异比想象中大，`content:encoded` 和 `enclosure` 别漏处理。

## 可复用建议

1. 原始数据永远先落库再加工，管线任何一段出问题都能重放。
2. LLM 输出必须过 schema 校验，失败的单条重试，别让一条坏输出污染整批。
3. 推送分层：日报是默认，即时推送是例外。打扰太频繁的管线会被自己关掉。
4. 来源宁缺毋滥。管线会放大烂源的影响，一个低质源比没有源更糟。
5. 每周抽 10 条摘要对照原文人工看一遍。摘要质量漂移比想象中快，换模型、改提示词都可能触发。

## 总结

这条管线跑了两个月，日均处理 120 条左右，实际进入摘要层的只有 30 条上下，token 成本稳定在很低水平。核心经验就一句话：LLM 摘要不是管线的全部，前置的采集、去重、粗筛才是决定这套东西能不能长期跑的关键。模型换成谁都行，工程底座换不了。
