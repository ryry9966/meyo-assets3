## 背景

Agent 默认是被动响应式的：用户发消息，它才动。但一旦想做“主动型助手”——定时汇总、监控仓库、盯告警、到点提醒——就必须解决一个问题：**谁在合适的时间把 Agent 唤醒**。

OpenClaw 的 heartbeat 是典型的轮询实现：定时器每隔 N 分钟向主会话注入一条 heartbeat prompt，由 Agent 自己检查待办、cron 任务和未读事件。这个设计够用，但不是唯一解。

## 问题

两条路线各有硬伤：

- **轮询**：实现简单、无需公网入口、失败可重试。代价是空转烧 token，事件延迟最多一个周期；周期一短，成本线性上涨。
- **推送**：事件发生即触发，低延迟、省 token。但需要可达的 webhook 端点、签名校验，还得处理重放、去重、乱序，以及最麻烦的——Agent 离线期间事件不能丢。

多数真实系统最后是混合的。关键在于**怎么划线**。

## 做法

我的实践步骤：

1. **按延迟敏感度分类任务**。分钟级可接受的（每日摘要、邮件巡检）走轮询；秒级关键的（CI 结果、告警回调）走推送。
2. **轮询侧控制成本**：基础间隔拉长到 30 分钟，配合一份本地状态快照文件，heartbeat prompt 保持极短——先做廉价检查，状态有变化再展开完整动作。
3. **加退避与抖动**：连续无事发生则间隔倍增，有事件后回到基础间隔；起始时刻加随机偏移，避免多实例整点齐步走。
4. **推送侧先落队再处理**：webhook 收到事件后写入本地队列（SQLite 或追加文件），Agent 被唤醒后从队列消费。这样天然解决离线丢事件，heartbeat 顺便兼任“扫队列 + 兜底巡检”。
5. **幂等**：每个事件带唯一 ID，消费前查已处理表，重复投递直接丢弃。

## 踩坑点

- **heartbeat prompt 写得太开放**，Agent 每次醒来都自由发挥给用户发消息，两天就被嫌弃。后来限定为动作清单 + quiet hours，才安静下来。
- **长工具调用与下一次心跳重叠**，两个循环并发写同一 session。加了互斥锁：重叠周期直接跳过。
- **webhook 直接触发 LLM 调用**，上游一重试就重复消费。必须先落队，再由 Agent 单点消费。
- **成本只算了对话 token**，heartbeat 的固定开销没计入，月账单对不上。现在把每次心跳的 token 数也记进日志。

## 可复用建议

- **默认轮询，被成本或延迟逼急了再上推送**。推送引入的基础设施复杂度容易被低估。
- 心跳间隔是产品参数，不是技术参数——按用户的使用节奏调，而不是按工程师的洁癖调。
- “状态快照 + 事件队列”是 Agent 可恢复性的最小架构，值得一开始就搭。
- heartbeat prompt 本身值得像代码一样 review：它决定了 Agent 醒来后的行为边界。

## 总结

轮询买的是简单和可靠，推送买的是时效和成本。对个人 Agent 而言，长间隔轮询做兜底、推送做加速、队列做缓冲，三者叠加就能覆盖绝大多数场景。先让它按时醒来，再让它醒来后做对的事——顺序别反。
