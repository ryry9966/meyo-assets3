## 背景

默认情况下，Agent 是被动的：用户不发消息，它就不动。但真实自动化场景里，很多事需要它"自己醒"：定时巡检、到点提醒、盯着一个长任务跑完没有。OpenClaw 的 heartbeat 就是为此设计的——Agent 每隔一段时间被唤醒一次，读一遍待办清单（HEARTBEAT.md），有事处理，没事沉默。

另一条路是推送：外部事件（CI 失败、邮件到达、监控告警）通过 webhook 主动打进来。两种机制看起来只是触发方式不同，实际取舍比想象中大。

## 问题

轮询的核心矛盾是粒度和成本：间隔太短，每次唤醒都要跑一遍模型，token 和消息频道的配额被空转吃掉；间隔太长，"5 分钟内告诉我构建挂了"这种需求直接作废。

推送的核心矛盾是可靠性：webhook 到达时 Agent 可能在重启、断网、正处理别的会话；事件可能重复、乱序、风暴式涌入。而且你得对外暴露一个入口，鉴权、重试、防重放都要自己做。

一句话：轮询用成本换简单，推送用复杂度换实时。

## 做法：混合式，而不是二选一

我们现在的方案分四步：

1. **事件分类**。时间驱动（每日早报、每小时巡检）走轮询；事件驱动（告警、邮件、CI 结果）走推送。这一步做完，80% 的纠结就消失了。
2. **轮询侧做减法**。heartbeat 的唤醒 prompt 保持极简，HEARTBEAT.md 只放"真正需要定期看"的条目，并明确写上"无事可做时直接沉默"。没事的 tick 不产生工具调用、不发消息，成本趋近于一次短对话。
3. **推送侧加缓冲**。webhook 不直接驱动 Agent，而是先落盘：写进一个 inbox 文件或 SQLite 表，带上事件 ID、时间戳、来源。Agent 被轻量信号唤醒后批量消费，处理完标记 done。
4. **共享一套防护**。去重（按事件 ID 幂等）、合并（1 分钟内同类告警合成一条）、静默时段（深夜只攒不发）、补漏（醒来先对账：上次处理到哪，中间漏了什么）。

## 踩坑点

- **最贵的坑是 heartbeat prompt 太重**。早期每次唤醒都带完整系统上下文和一堆工具，一天几十个 tick，token 账单翻倍还没产出。现在 tick 只带清单和一句"无事则沉默"。
- **webhook 直连 Agent 等于裸奔**。重启窗口内的事件全丢，重试风暴还会把 Agent 打挂。缓冲层必须有，且要持久化。
- **推送方默认会重试**。没做幂等时，同一条告警处理了三遍，用户收到三条重复消息，信任度直接归零。
- **忘了静默时段**。凌晨三点机器人热心播报，第二天就被要求下线。
- **事件乱序**。推送不保证顺序，处理时必须看时间戳，不然"部署失败"会盖过之后的"已恢复"。

## 可复用建议

- 低频、模糊、容忍延迟的 → 轮询；高频、精确、要实时的 → 推送。拿不准就先轮询，痛了再上推送。
- 所有外部事件收敛到一个 inbox 抽象，Agent 侧只认 inbox，不关心来源是轮询捡到的还是推送进来的。
- 给每个 tick 记账：单次 token 成本 × 频率，这个数字决定你敢不敢调小间隔。
- 状态放文件，不放内存。Agent 随时会被杀，醒来要能续上。

## 总结

heartbeat 的本质不是"轮询还是推送"，而是唤醒策略要和事件的时间特性匹配。轮询给你简单和兜底，推送给你实时和省 token，缓冲层加幂等让两者可以共存。先把事件分好类，再让 heartbeat 只做它擅长的事——大部分 Agent 的"主动性"问题，到这一步就够用了。
