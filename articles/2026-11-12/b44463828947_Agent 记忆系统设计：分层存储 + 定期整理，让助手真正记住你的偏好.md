## 背景

LLM 本身无状态，每次会话开始，模型对你的了解都归零。OpenClaw 这类常驻 Agent 的核心价值恰恰在"长期相处"——时区、代码风格、常用部署方式、讨厌的措辞，如果每次都要重说一遍，助手就只是个更贵的无状态 API。所以记忆系统的目标很明确：把用户画像从对话中沉淀出来，并在正确时机注入回上下文。

## 问题：三种常见做法为什么都不够

1. **全量塞上下文**。把历史对话全丢进 system prompt，几天后核心偏好被淹没，token 成本线性上涨，模型对近期指令的服从度反而下降（注意力稀释）。
2. **只上向量检索**。语义召回擅长找"相关内容"，但偏好是规则不是内容——"用户用 pnpm 不用 npm"和某次聊 npm 的对话向量距离很远，大概率漏检。
3. **让模型口头记**。会话里说"记一下"，下次会话它自己都找不到。没有持久化写入路径的记忆等于没有记忆。

## 做法：分层存储 + 一条写入链路

**第一层：核心记忆文件（常驻加载）**。workspace 里放一个 `MEMORY.md`，分节组织：身份与环境（时区、语言、编辑器）、工作偏好（代码风格、提交规范）、硬性规则（禁用词、输出格式）。设死预算，比如 800~1200 token，超了必须先删再写。这层每次必注入，宁少勿多。

**第二层：情景记忆（只存不载）**。会话日志按日期落盘，不进上下文，只提供检索工具。查询用"关键词 + 时间过滤"为主、向量召回为辅——偏好类问题往往带时间锚点（"上周那次部署"）。

**第三层：候选事实池**。关键中间层。Agent 通过 MCP 记忆工具（`memory_write`）写入候选事实，每条带结构化字段：内容、置信度、来源会话、时间戳。**不直接进核心记忆**。

**第四层：规则区**。只有两类事实能升级进来：用户明确确认过的（"以后都这样"），或重复出现 ≥3 次的模式。升级由整理任务完成，不靠模型临场发挥。

**整理链路**：cron 每天跑一次批处理——读近期会话日志 → 抽取候选事实 → 与事实池去重（模糊匹配 + LLM 判重）→ 满足条件的写入核心记忆并 git commit。核心记忆文件进版本库，改动可 diff、可回滚。

## 踩坑点

- **核心记忆膨胀**：没有硬预算的 MEMORY.md 一个月能长到 5k+ token，模型开始"忘事"。预算必须强制，删除优先于新增。
- **新旧偏好冲突**：半年前说喜欢详细输出，上周嫌啰嗦。整理任务要做冲突检测——同主题新条目覆盖旧条目，条目内留一行变更原因。
- **写入太勤**：模型会把一次性闲聊（"周末去了家不错的川菜馆"）也存起来，噪音淹没信号。候选事实 90 天未被检索命中就降级或删除。
- **格式漂移**：放开让模型自由书写，三个月后文件变成无法解析的散文。分节模板要写死在系统提示里。
- **隐私泄漏**：用户随手贴的 API key 会被当成"重要事实"记住。写入路径加一道敏感信息扫描，命中即拒绝持久化。

## 可复用建议

- 先设计写入路径，再考虑读取。写入乱的系统，读什么都救不回来。
- "小而常驻 + 大而可检索"永远优于"大而常驻"。
- 把记忆文件当代码管理：git 跟踪、变更留痕、定期 review。
- 事实升级设门槛（确认或频次），模型默认的热情会污染记忆。
- 像测代码一样测记忆：维护一组固定问题（"我的部署流程是什么"），每次改记忆链路后跑回归。

## 总结

让 Agent 记住你，不靠模型自觉，靠工程：分层存储控制注入范围，结构化写入控制质量，定时整理控制生命周期，版本管理控制风险。四件事单独看都平凡，组合起来就是"它真的懂我"的体感。
