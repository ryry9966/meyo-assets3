## 背景

我们社区有几个跑在 OpenClaw 上的自动化任务：每日更新摘要、插件发布通知、每周精选整理。实现不难——Agent 定时触发，MCP 调发帖接口，内容由 LLM 组织。跑了两周后，有成员在群里说："每天 9:00:00 准时出现，比闹钟还准。"这句话让我意识到问题所在：内容没问题，节奏太机器了。

## 问题

回看发帖记录，"机器味"主要来自四个信号：

1. 时间戳过于精确，永远整点、秒级对齐；
2. 间隔均匀，工作日和周末一个节奏；
3. 队列积压后补发，短时间内连发四五条；
4. 格式高度一致，模板、emoji、篇幅几乎不变。

人不会这样发帖。结果是有成员直接屏蔽了频道——对社区自动化来说，被静音约等于失败。

## 做法

我们把节奏控制拆成调度层和内容层，各自加"人味"。

**调度层：抖动 + 窗口 + 合并**

- **随机抖动**：目标 9:00，实际在 8:50–9:35 之间取值，粒度到分钟而不是秒。
- **活跃窗口**：查了频道消息热力分布，只在 8:30–22:30 发，凌晨一律排队顺延。
- **周末差异化**：周末只发高优先级内容，摘要类顺延到周一。
- **最小间隔 + 合并**：设 3 小时最小间隔；队列里有多条待发时，合并成一条 digest，而不是逐条倾泻。
- **重试重新抖动**：失败后不能原样立刻重试，要换随机偏移并指数退避，否则重试流量会自己制造"连发"。

**内容层：可控的变化**

- 事实固定，表述变化。数据、链接、版本号由脚本产出，开头句式和篇幅让 LLM 在 2–3 套风格里选，再用校验步骤确认关键事实没丢。
- 结构轮换。列表式、段落式、问答式轮着来，避免每条长得一样。

**状态感知与人审**

- 发帖前看一眼频道状态：如果正有人热烈讨论，摘要类内容自动延迟半小时，别打断。
- 抽 20% 帖子进人工复核队列，另外留一个 kill switch，一条命令全停。

## 踩坑点

- **随机种子每次运行重置**：结果每天"随机"出同一个时间。改成提前一天生成调度表并落库，持久化。
- **时区坑**：调度器按 UTC 算窗口，社区在 UTC+8，凌晨判断全错。所有窗口计算必须显式带时区。
- **过度随机**：抖动范围一度放到 ±3 小时，结果 5:40 发过一条帖，比准时更假。抖动必须约束在活跃窗口内。
- **合并过头**：把六条通知并成千字长文，没人读完。合并要有条数上限，超了就拆两条、拉开间隔发。

## 可复用建议

把节奏参数全部配置化：`base_time`、`jitter_minutes`、`active_window`、`min_interval`、`weekend_policy`、`merge_limit`。我们最后抽成了一个独立的 rhythm 模块，任何定时发帖的 Agent / MCP 工具都能直接挂上。核心原则一句话：**先模仿一个正常人类的发帖时间分布，再谈自动化。**

## 总结

自动发帖不像机器人，关键不在内容生成，而在调度层的时间分布和发帖前的状态判断。抖动、窗口、合并、退避这四件事做完，"被静音"的抱怨就消失了。自动化在社区里的目标从来不是"发得多、发得准"，而是"发得像个靠谱的成员"。
