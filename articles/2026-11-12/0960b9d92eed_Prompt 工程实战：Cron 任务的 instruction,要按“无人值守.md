## 背景

OpenClaw 的 cron 任务本质上只有两样东西：一条 cron 表达式 + 一段自然语言 instruction,到点后 agent 在一个**全新会话**里执行。机制很灵活，但很多人把 instruction 写成了日常聊天的口吻——“每天帮我看看 xx,有情况告诉我”。交互场景里这样说没问题，因为上下文和追问都在；放到定时任务里，问题就来了。

## 问题：Cron 执行是“冷启动”

定时任务和对话有三个本质区别：

1. **没有上下文**：每次执行都是新会话，之前澄清过的约定全部不存在。
2. **没有追问机会**：agent 理解偏了，没人当场纠正；等你发现时可能已经空跑了一周。
3. **没有默认出口**：对话里“告诉我”是发给坐在对面的人；定时任务里“告诉我”发给谁？不写清楚，结果要么沉淀在无人查看的会话里，要么 agent 自作主张。

所以 cron instruction 的写法原则只有一句话：**把它当成一段无人值守、失败不可逆的程序来写，而不是一条聊天消息。**

## 做法：六段式结构 + 对比

我目前固定用的结构：任务性质、时间语境、数据来源、判断标准、输出动作、异常处理。

反例(大多数人一开始都这么写)：

> 每天早上帮我检查仓库有没有重要 issue,有的话告诉我。

改写后：

```text
这是定时任务,每天 09:00(Asia/Shanghai)自动触发。没有人在会话里
等你,不要提问,直接执行。

1. 用 GitHub 工具读取 org/frontend-app 近 24 小时新增的 issue。
2. 只保留:带 bug 标签、或评论数 ≥ 3、或标题含 error/crash 的。
3. 有结果:发到 Telegram 的 ops 频道,每条一行「标题 / 链接 / 一句话原因」。
   无结果:不发消息,只在本地日志记一条 "cron: no matches"。
4. 工具调用失败重试 1 次,仍失败则向 ops 频道发「检查失败: <原因>」,
   不要静默退出。
```

两段字数差不多，可靠性差距很大。核心差异在于：判断标准从“重要”变成了可枚举的规则；补上了“无结果怎么办”和“失败怎么办”——这两项最容易被忽略，却决定任务能不能长期挂机。

## 踩坑点

- **相对时间歧义**：“今天”“最近”依赖 agent 对“现在”的理解。写明时区，时间窗口用“近 24 小时”这类显式表述；同时确认 cron 表达式按哪个时区解释，别想当然。
- **没写空结果处理**：轻则每次都发“没有新内容”刷屏，重则 agent 为了“有产出”硬凑内容。
- **输出渠道不明确**：“告诉我”是无效指令，要写到具体频道、文件或日志路径。
- **一条任务塞多个步骤**：三步以上的链路，中途失败会留下半截状态。宁可拆成多条 cron,每条单一职责。
- **忘了声明“这是定时任务”**：agent 可能把澄清问题发进空会话，然后一直等回复。

## 可复用建议

- **先手动验证再上 cron**:先手动触发一两次，确认输出符合预期，观察两三天再挂正式计划。
- **失败必须可见**：另加一条每周“巡检”任务，汇报各任务近期的运行与失败情况。静默挂掉的任务比没有任务更糟。
- **规则替代形容词**：“重要”→“评论数 ≥ 3 或带 bug 标签”；“异常”→写明阈值。
- **维护 instruction 台账**：每条任务的指令、创建时间、最后验证日期记在同一处，季度复查，及时清掉没人看的输出。

## 总结

写 cron 任务的 instruction,考验的不是提示词技巧，而是接口设计：输入(数据来源)、规则(判断标准)、输出(渠道与格式)、错误处理，四者共同决定了它能否无人值守地跑下去。写完后问自己一句：**如果它连续失败三次，我会知道吗？**答案是“不会”，就回去补异常处理。
