## 背景

过去半年我把 OpenClaw 里一部分 Agent 任务从云端 API 迁到了本地模型。动机很朴素：Agent 循环的 token 消耗是普通聊天的几十倍——多轮工具调用、长 system prompt、MCP schema 注入，账单涨得比预期快。另外部分自动化任务涉及本地文件和私有数据，走云端始终有顾虑。

## 问题

本地部署的核心矛盾在于：Agent 是「长上下文 + 高频调用」的负载，和聊天场景完全不同。家用显卡的显存决定模型上限，而 Agent 对工具调用（function calling）质量的要求，比对话流畅度苛刻得多。很多「能跑」的模型，接上 MCP 工具后就露馅。

## 做法

1. **先算显存账**。粗略公式：参数量 × 量化字节数 + KV cache 预留。7B Q4 约占 5GB，14B 约 9GB，32B 约 20GB。KV cache 别忽略，32k 上下文在 14B 上还要额外吃 2-4GB。
2. **选运行时**。图省事用 Ollama / LM Studio，追求吞吐上 vLLM。关键是都暴露 OpenAI 兼容接口，OpenClaw 侧只需改 base_url。
3. **选模型**。优先验证工具调用能力，其次才是通用智力。14B 级别里带原生 function calling 的模型是甜点位，上下文至少支持 32k。
4. **量化默认 Q4_K_M**。显存富余再上 Q5/Q6，不要碰 Q2 以下，工具调用格式会崩。
5. **接入后做真实任务压测**，而不是聊天测试。记录 tokens/sec 和首次响应延迟，Agent 场景这两项比跑分榜靠谱。

## 踩坑点

- **Ollama 默认上下文只有 4k**。Agent 跑到一半静默截断，表现为「模型忘了工具定义」，第一次遇到非常迷惑。务必显式设 `num_ctx`。
- **KV cache 是中途 OOM 的主因**。启动不报错，跑到长任务才爆显存。预留 20% 余量。
- **工具太多小模型会乱**。暴露 20 个 MCP 工具时，14B 模型开始幻觉出不存在的工具名。收敛到 8 个以内，或按任务分组动态加载。
- **temperature 高于 0.7 时，工具调用 JSON 格式错误率明显上升**。Agent 场景建议压到 0.2-0.4。
- 笔记本有热节流，跑分和持续输出实际差 30% 以上，别拿短跑成绩做容量规划。

## 可复用建议

- **分层路由**：本地模型处理规划草稿、格式化、简单检索这类低风险步骤，复杂推理和关键工具调用回退云端。OpenClaw 里配一条 fallback 链即可。
- **固定配置快照**：模型名、量化版本、ctx 长度、运行时版本写进项目的一个 config 文件，避免「上周还好好的」这类悬案。
- **schema 裁剪**做成标准动作：把 MCP 工具的 description 砍到一行、删掉参数示例，上下文占用能降一半。
- 每个任务记录 tokens/sec，连续观测比单次跑分有意义。

## 总结

家用硬件跑本地模型，如今不是「能不能」的问题，而是「哪些环节值得」的问题。我的结论：14B Q4 + 32k 上下文是当前消费级显卡的实用甜点，能稳定承接 Agent 中约六成的低风险调用。把它当成降本和隐私的补充层，而不是云端的全量替代，是更务实的定位。
