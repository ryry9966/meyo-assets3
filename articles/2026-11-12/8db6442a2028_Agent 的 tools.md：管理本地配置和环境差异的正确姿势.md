## 背景

Agent 真正跑起来之后，最先暴露的往往不是模型能力问题，而是环境问题。同一份 skills / MCP 配置，在我的笔记本上表现正常，换到同事的 Windows 机器或 CI 容器里就开始出错：选错 python、假设 jq 存在、把产物写进不存在的路径。模型并不知道“这台机器”长什么样——它只知道上下文里写了什么。

常见的两种做法都有缺陷：把环境说明塞进全局 system prompt，它不随项目走；写进项目 README，又混在人类文档里，Agent 不一定读到。tools.md 就是补这个缝隙的：一份专门写给 Agent 看的、描述当前执行环境的最小文件。

## 问题

实际踩过的坑可以归成三类：

1. **环境漂移**：venv、conda、系统 Python 并存，Agent 每次选中的都不一样；
2. **跨平台差异**：路径分隔符、shell、包管理器、代理与镜像源，在本地/服务器/CI 上各不相同；
3. **信息过期**：硬编码的端口、数据目录、临时路径在环境变动后悄悄失效，Agent 按旧信息执行，错得不明显、排查成本高。

## 做法与步骤

核心思路是**分层**，而不是维护一个大文件：

**第一层：仓库级 `tools.md`（提交进 git）**
只写“项目对工具链的要求 + 如何自检”：

- 运行时与版本下限（如 Python ≥ 3.11、Node 20）
- 关键 CLI 及用途（jq、ffmpeg、docker compose 等）
- 自检命令：要求 Agent 动手前先跑一条探测命令确认
- 环境变量约定：只写变量名，不写值

**第二层：本地级 `tools.local.md`（加入 gitignore）**
只写“这台机器的事实”：

- 实际使用的解释器路径与激活方式
- 本地服务端口、数据目录、代理配置
- 已知怪癖（例如某条命令在 Windows 下需走 Git Bash）

**第三层（可选）：脚本生成**
用小脚本探测 OS、版本、端口占用，生成 `tools.local.md` 骨架，人工补齐；环境变了就重跑一次。

加载顺序上，让本地层覆盖仓库层；并在文件里明确写一句“动手前先验证，不要假设本文件永远准确”。这句话能挡掉大部分因信息过期导致的误操作。

## 踩坑点

- **别写密钥**。tools.md 是进模型上下文的，任何 token 都不该出现，只写“从 `ENV_NAME` 读取”。
- **别写成散文**。长段落会被模型弱化处理，用短 bullet，一行一条。
- **别重复依赖清单已有的信息**。requirements / lockfile 已声明依赖，tools.md 只写它们声明不了的：路径、怪癖、本地服务。
- **注意加载时机**。部分框架只在会话启动时读一次，关键约束放文件前部，别指望每轮都会重读。
- **别让 Agent 自己改 tools.local.md**，否则它会把“临时绕过”写回配置，形成漂移闭环。

## 可复用建议

- 把仓库级 tools.md 当“环境契约”纳入 review：改工具链必须同步改它。
- 本地层模板化：`tools.local.md.example` 进 git，真实文件不进。
- 团队内统一命名（如 `LOCAL_PYTHON`、`DATA_DIR`），Agent 跨机器迁移成本最低。
- 每次环境升级后花两分钟重跑生成脚本，比事后排查省一个下午。

## 总结

tools.md 不是又一个配置文件，而是把“机器差异”从运行时的意外，变成启动时的显式输入。分层、声明式、自检优先——守住这三条，Agent 在不同环境下的行为就会稳定很多。它治不了所有问题，但能把“为什么在我机器上是好的”这句话，从人嘴里挪到文件里。
