# 背景

最近半年我把一部分 Agent 任务的推理从云端 API 挪到了家里那台 4070 的机器上。动机很朴素：批量跑离线任务时 API 费用心疼；一些含隐私数据的日志摘要不想出本地；断网或限流时需要一个兜底。对 OpenClaw 用户来说，本地模型的现实定位是**补充而非替代**——先把预期摆正，后面的选择才不会跑偏。

# 问题

家用环境有三个硬约束：

1. **硬件碎片化**：显存/内存直接决定能跑什么模型，没有商量余地；
2. **信息噪音大**：量化格式、运行时、ctx 长度，新手很容易被参数淹没；
3. **Agent 场景门槛更高**：本地模型做对话还行，但 function calling 的可靠性明显低于旗舰云端模型，工具调用一崩整条链路就废。

# 做法

**第一步：盘点硬件，确定上限。** 显存是第一约束。我实测的大致边界：16GB VRAM 舒服跑 14B Q4；32GB 勉强跑 32B Q4（ctx 还不敢开大）；纯 CPU 或集显建议不超过 7~8B，且内存带宽决定速度，DDR4 双通道会很慢。

**第二步：选运行时。** Ollama 上手最快，llama.cpp 可控性最强（参数全部可调），LM Studio 适合快速试模型。三者都提供 OpenAI 兼容接口，接入 Agent 框架的成本很低。

**第三步：选模型。** 中文任务优先 Qwen 系列 7B/14B，也可试 DeepSeek 蒸馏版。量化从 Q4_K_M 起步，对代码和数学任务不够再升 Q5/Q6。拉模型前看社区实测，别只看参数量。

**第四步：调上下文。** 很多人忽略这点：运行时默认 ctx 往往只有 2k~4k，Agent 多步循环很快撑爆。手动调到 8k~16k，同时注意 KV cache 显存占用会随之明显增长，量入为出。

**第五步：接入 OpenClaw 做混合路由。** 把 OpenAI 兼容 endpoint 配进模型配置后，我的做法是分层：摘要、分类、格式清洗这类廉价任务走本地；复杂推理和关键工具调用仍走云端。本地模型降级为"意图分类器"后，工具调用稳定性问题基本消失。

# 踩坑点

- **ctx 不是免费的**：拉满上下文后 OOM，报错信息往往不直观，先查 KV cache 占用；
- **小模型 function calling 不可靠**：参数幻觉、漏调用是常态。解法是简化工具 schema、在系统提示里给 few-shot 示例，或者干脆不让她直接调工具；
- **量化损失不均匀**：代码、数学对量化更敏感，别在 Q4 上硬扛复杂推理；
- **并发约等于 1**：本地推理基本串行，Agent 循环里记得把超时调大，否则误判失败触发重试，雪上加霜；
- **复读问题**：本地模型容易重复输出，repetition penalty 和 temperature 要单独调，云端参数照搬不一定对。

# 可复用建议

1. **建模型档案表**：记录模型名、量化、ctx、显存占用、实测 tok/s、擅长任务，换机器或换模型时直接查表；
2. **用自己的真实任务做基准**：通用跑分和你 Agent 里的实际表现可能完全两回事，一组固定的测试 prompt 比 leaderboard 靠谱；
3. **固定版本**：模型文件和运行时都 pin 住，避免"升级后行为变了"这种难排查的问题；
4. **封装成独立服务**：把本地模型包成独立的 endpoint 或 MCP 服务，路由和回退逻辑放在上层，随时可切。

# 总结

本地部署换来的三样东西是：成本确定、数据不出门、离线可用；付出的代价是能力上限低、吞吐小。务实的路线是**混合路由**——先拿 7B~14B 模型在你自己的 Agent 任务上验证价值，确认收益再加硬件。别一开始就为跑大模型升级显卡，先用真实任务算清楚这笔账。
