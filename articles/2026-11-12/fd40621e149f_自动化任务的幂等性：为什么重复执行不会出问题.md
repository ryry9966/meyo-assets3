## 背景

自动化系统里，“同一件事被执行多次”不是异常，而是常态：MCP 工具调用超时后自动重试、agent 重新规划后又调了一遍同一个工具、定时任务上一轮没跑完又被触发、消息队列的至少一次投递。与其把重复当成偶发故障去“尽量避免”，不如在设计层面承认它必然发生。

幂等性（idempotency）解决的就是这个问题：同一操作执行一次和执行十次，最终效果一致。它是自动化任务能放心重试的前提。

## 问题

社区里很典型的一个场景：写了一个“在任务系统里创建工单”的 MCP tool。agent 调用它，网络超时，框架自动重试——而服务端其实已经创建成功，结果一个需求对应两张工单。类似的还有：发通知的插件重试后在同一个群里 @ 了三遍；定时同步脚本上次跑了一半超时、这次从头跑导致重复插入；webhook 重复推送连续触发两次部署。

共同点很清楚：**副作用不可逆，执行入口又无法保证“恰好一次”**。

## 做法

按投入从低到高，几个可落地的层次：

1. **优先用天然幂等的操作形态。** 更新用 upsert（按业务键覆盖写），删除按 key 删，状态写入用 PUT 语义。不少重复问题在接口设计阶段就能消掉。
2. **引入幂等键。** 每个有副作用的调用带一个确定性键，服务端先查这个键是否处理过。关键细节：键必须从业务内容推导（比如源事件 ID 的 hash），不能每次调用随机生成——否则重试时键变了，等于没有。
3. **存储层唯一约束兜底。** 给幂等键加唯一索引，插入冲突时视为“已处理”并返回成功。先查后写在并发下不可靠，唯一索引才是硬保证。
4. **状态机推进代替重复执行。** 定时任务不每次“执行动作”，而是推进状态：`UPDATE ... WHERE status = 'pending'`，只有抢到状态变更的那一次才触发下游动作。条件更新天然防重。
5. **不可逆副作用“先记录后执行”。** 发消息、付款这类动作无法回滚，先写 intent 记录（与业务数据同一事务），成功后标 done；恢复时只处理“有 intent 无 done”的条目。

## 踩坑点

- **超时 ≠ 失败。** 客户端超时重试时，服务端大概率已成功。重复执行最大的来源在这里，而不是逻辑 bug。
- **幂等键生命周期错误。** 键在重试循环里重新生成，或 agent 重新规划后参数微变导致键变了，幂等就失效。键要绑业务事件，不绑调用过程。
- **把事务回滚当幂等。** 数据库写入会回滚，HTTP 调用和发消息不会；混在一个事务里，外部副作用是漏网之鱼。
- **去重记录与业务写入不在同一事务。** 中间宕机两边状态不一致，照样重复。
- **去重窗口太短。** 重试可能发生在几分钟后，一小时的 TTL 挡不住。

## 可复用建议

写 tool / 插件时照这个清单过一遍：

- 每个 tool 明确标注幂等语义：天然幂等 / 幂等键 / 不幂等需加锁
- 副作用入口收敛到统一封装，集中处理幂等键与去重
- 服务端对重复请求返回与首次相同的结果，而不是报错——否则上层重试逻辑会误判
- 监控去重命中率：突然升高往往说明上游在疯狂重试，本身就是告警信号
- 重试策略与幂等设计配套看，只调 retry 次数治标不治本

## 总结

自动化的可靠性不是靠“保证只执行一次”——分布式环境里几乎做不到——而是靠“执行多次也无害”。把重复执行当作设计输入而非异常，用幂等键、唯一约束和状态机把副作用钉住，重试、重新调度、agent 重新规划这些机制才能真正为你所用，而不是反过来制造事故。
