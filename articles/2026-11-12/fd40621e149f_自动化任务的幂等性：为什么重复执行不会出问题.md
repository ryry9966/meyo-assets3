## 背景

在 OpenClaw 这类 agent 自动化场景里，任务很少只跑一次。cron 触发器可能因调度器重启而重放，gateway 断线重连后会补发积压消息，MCP 工具调用超时后你会手动重试，插件的消息处理器也可能被框架重新投递。自动化系统天然倾向"至少一次执行"（at-least-once），而不是"恰好一次"。这不是缺陷，是分布式环境的基本现实。

## 问题

问题在于副作用不可重放。一个每天早上发日报的任务，调度器当天触发两次，群里就出现两条一模一样的日报；一个"把新工单同步到表格"的工具，重试一次就多插一行重复数据；一个 webhook 处理器失败后被重放，用户收到两条相同通知。这些都不是调度器的 bug，而是任务本身不具备幂等性。

幂等性的定义很朴素：**同一操作执行一次和执行多次，最终状态一致。**

## 做法

1. **优先用声明式替代执行式。** 把"追加一条记录"改成"把某键的状态设置为 X"。状态设置天然幂等，追加天然不幂等。能改成同步期望状态（desired state）的任务，优先这么改。

2. **为副作用分配确定性的幂等键。** 键必须从任务身份派生，而不是从时间戳派生，否则每次重试都生成新键，等于没做。例如日报任务用 `daily-report:{日期}`，同步任务用 `sync:{来源}:{记录ID}`。

3. **用持久化存储记录已处理的键。** 不要放内存变量——进程重启就丢了。一个 SQLite 表或工作区里的 JSON 文件足够：

```js
const key = `daily-report:${day}`;
if (await store.has(key)) return { skipped: true };
await sendReport();
await store.set(key);
```

4. **有数据库的场景，靠唯一约束兜底。** `INSERT ... ON CONFLICT DO NOTHING` 比应用层"先查再插"可靠得多，后者在并发下有竞态。

5. **外部 API 支持幂等键就传。** 不少支付、工单类 API 接受幂等键参数，重试时带上同一个键，服务端会返回首次结果而不是重复执行。

## 踩坑点

- **先查再插的竞态。** 两个 worker 同时判断"不存在"，然后都执行插入。用数据库唯一约束或加锁，别只靠应用层判断。
- **幂等键粒度不对。** 只用日期做键，当天就无法合法重跑（比如手动修复数据后再发一次）；用时间戳做键，重试永远命中不了。想清楚哪些重复该拦、哪些该放行。
- **把"现在"写进请求体。** payload 里有 `generated_at: new Date()` 时，两次重试内容不同，内容指纹去重会失效。内容类任务用任务身份做键，而不是内容指纹。
- **去重状态没持久化。** 存在内存或被重启清理，重启后所有任务都被当成首次执行。
- **半成功状态。** 操作实际成功了但响应丢失，客户端误判失败而重试。这时只有远端幂等（唯一约束或幂等键）能救你。
- **重试循环里嵌套通知。** 主逻辑去重了，但失败告警没做，一次失败收十条告警。

## 可复用建议

- 用一条验收标准检验所有自动化任务：**同一任务连续跑两遍，第二遍应全部 skip，且外部世界无任何变化。** 把它写进自检脚本。
- 把 `ensureOnce(key, fn)` 封装成插件层公共工具，所有副作用统一走它，而不是每个任务各写一遍。
- 给去重存储设计清理策略，无限增长本身也会变成故障源。
- 每个任务留 dry-run 模式，上线前先看会触发哪些副作用。

## 总结

自动化系统的可靠性，不来自"调度器永远不出错"——它一定会出错、重试、重放。可靠性来自任务面对重复执行时行为正确。把副作用改造成幂等的，是自动化工程里投入产出比最高的改造之一：不需要引入复杂框架，一个确定性的键加一张小表，就能让"至少一次执行"在效果上等于"恰好一次"。
