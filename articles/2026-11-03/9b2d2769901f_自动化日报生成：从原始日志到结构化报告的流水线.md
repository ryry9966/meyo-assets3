## 背景

团队的日常进展散落在 git 提交、CI 运行记录、工单系统和 Agent 任务日志里。日报这件事本身不难，难在"每天坚持"和"格式统一"。手写日报靠自觉，漏写、补写、口径不一是常态。我们的思路是：不让人写日报，而是把已经存在的机器数据汇成一条流水线，每天定时产出结构化报告，人只做最后审阅。

## 问题

落地前有三个具体问题：

1. **数据源分散**：git、CI、告警、Agent 执行记录各有一套格式，没有统一的中间表示。
2. **直接丢给 LLM 不行**：原始日志量大且噪声多，token 开销高，摘要还容易编造"看起来合理"的条目。
3. **可靠性要求**：日报是定时任务，失败要可重试、可追溯，不能默默吞掉错误。

## 做法

整条流水线分五步，由定时任务驱动：

1. **采集**：为每类数据源写一个适配器（MCP tool 或插件均可），只负责拉取原始数据并存档，如 `commits.jsonl`、`ci_runs.jsonl`。原始数据落盘，后续任何环节出错都可以重放。
2. **清洗与结构化**：把异构数据映射到统一的中间 schema，一条记录至少包含 `source`、`timestamp`、`actor`、`action`、`target`、`status`、`extra`。字段放不下的塞进 `extra`，不要为省事丢信息。
3. **聚合与过滤**：按时间窗口（注意时区）切片，去重、合并同一对象的连续事件，压缩掉心跳类噪声。这一步的输出是"日报素材"，通常比原始日志小一到两个数量级。
4. **Agent 摘要**：素材以 JSON 传入，prompt 中要求只基于给定数据输出、禁止推断未出现的事件，并按固定 JSON Schema 返回：`highlights`（3–5 条）、`risks`、`metrics`。返回后做 schema 校验，不通过则重试；连续失败则降级为纯统计表格版报告。
5. **渲染与推送**：摘要经模板渲染成 Markdown/HTML，通过 webhook 推送到群。发送记录写入本地状态文件，避免重试导致重复推送。

## 踩坑点

- **时区与窗口边界**：定时任务跑在 UTC 容器里，第一次上线把"昨天"切错了 8 小时。窗口计算务必显式指定时区。
- **schema 漂移**：不同模型版本对 JSON 输出的遵循度不同，校验失败要重试，不能放行脏数据。
- **敏感信息**：日志里常有 token、内网地址，脱敏要在清洗阶段做，不要指望 LLM"注意一下"。
- **幻觉**：即使 prompt 写了"禁止编造"，仍出现过摘要引用素材外的时间戳。加了一道校验：摘要中的实体必须能在素材中找到，否则剔除并记警告。
- **幂等**：重试机制上线后某天推送了三遍，后来用"日期 + 数据指纹"作为幂等键解决。

## 可复用建议

- 中间 schema 是整条流水线的核心资产，先定 schema 再写适配器。
- 采集、摘要、推送解耦，各自可独立重跑。
- 每天归档原始数据与最终报告，出问题时能完整回放。
- 摘要失败要有降级路径：宁可发一版枯燥的统计表，也不要不发。

## 总结

这套流水线的价值不在"AI 写日报"这个点，而在于把散落的机器数据收敛成一份可信的中间表示。Agent 只负责最后一步的表达，schema 校验和降级机制保证了它不会成为单点故障。上线一个多月，日报的准确率和按时率都稳定了，人工介入只剩早上扫一眼。建议从单一数据源（比如 git）跑通最小闭环，再逐步接入其他源。
