## 背景

OpenClaw 里每个会话都有自己独立的上下文历史。跑长任务时我们常用 `sessions_spawn` 起子 Agent：主会话负责拆解和汇总，重活——批量抓取、代码检索、长文档摘要——交给子会话。听起来天然隔离，但实际用下来，"隔离"只对默认配置成立，稍不注意，子 Agent 的痕迹还是会渗回主会话。

## 问题

三类典型污染：

1. **上下文回灌**。把主会话历史整段塞进子 Agent 的 task 当"背景资料"，子 Agent 的中间过程再通过消息转发原样流回主会话，一轮跑完主会话 token 翻倍。
2. **文件系统串台**。子 Agent 和主会话共用 workspace，跑批时往同一批临时文件写，互相覆盖。
3. **会话复用**。子会话结束后没清理，下次 spawn 复用了旧 session key，模型"记得"上次的中间结论，行为变得不可预测。

## 做法

我的固定流程，四步：

**第一步：spawn 时强制新会话。** 子 Agent 用独立 session key，不继承主会话历史。需要背景就在 task 里写清楚，两三句话说清目标、边界、交付物，不要贴原始上下文。

**第二步：约定结构化返回。** 在 task 里明确要求子 Agent 只回一段紧凑摘要：结论、产物路径、失败项。产物（文件、截图、日志）落到自己名下的目录。

**第三步：workspace 按次隔离。** 每次运行建 `workspace/runs/<run_id>/` 子目录，子 Agent 只在自己的目录里读写。主会话需要哪个文件，按路径去取，不靠"我记得它写过什么"。

**第四步：跑完即清。** 子会话结束后主动清理，或在配置里设子会话保留时长，避免下次复用到带脏历史的 session。清理、sandbox 相关的字段名各版本差异不小，动手前先 `openclaw config dump` 核对当前版本的实际键名。

验证方法很简单：spawn 前后各看一次主会话的上下文占用和消息条数，隔离做对了，增长应该只有那一小段结构化摘要。

## 踩坑点

- **"多给点上下文总没错"是最大的坑。** 把主会话历史塞给子 Agent，等于亲手把隔离拆了，token 和干扰双双上升。
- **流式输出别直连主会话。** 想看进度，让子 Agent 定期往自己目录写状态文件，主会话按需读，而不是把子会话的消息流转发进主会话。
- **MCP 工具有共享状态。** 浏览器、登录态这类跨会话共享的服务端状态，session 隔离管不到，需要单独约定，比如固定 profile、跑完登出。
- **升级先验证。** 子会话清理相关配置变动较频繁，升级后先跑一个小任务确认行为，再上批量。

## 可复用建议

- 把"任务简报 + 返回结构"写成模板放进 agent 的说明文件（如 `AGENTS.md`），所有子任务统一格式，省去每次口述。
- run_id 用时间戳 + 短随机串，事后排查能对上现场。
- 排查污染优先看两处：主会话消息列表里有没有"不属于它的消息"，workspace 根目录有没有散落的临时文件。
- 批量任务先单条 dry run，确认摘要体积可控再放量。

## 总结

session 隔离不是 OpenClaw 自动送的保险——默认行为帮你挡住了大部分，但上下文回灌、共享文件、会话复用这三处还得自己守住。原则一句话：子 Agent 只带任务走、只带摘要回、只在自己的地盘干活、干完就清。
