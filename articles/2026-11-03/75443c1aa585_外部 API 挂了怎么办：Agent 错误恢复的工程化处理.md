## 背景

跑 Agent 或接 MCP 工具链，迟早撞上这一幕：任务执行到一半，某个外部 API 开始 429、503，或者干脆超时。传统服务挂了会向用户报错，Agent 的麻烦在于它有一条 LLM 主循环——工具失败后模型还会继续推理。处理不当，轻则任务卡死、token 白烧；重则模型“脑补”一个结果接着往下走，输出格式完好、内容却是错的。

## 问题拆开是三层

1. **重试策略**：哪些错该重试、重试几次、间隔多久；
2. **状态一致性**：写操作重试后会不会重复执行；
3. **模型行为**：失败信息怎么喂给模型，才能让它降级而不是编造。

## 做法

**1. 错误分类放在工具层。** 429/503/超时可重试；400/401/404 重试只会白烧钱。工具层（MCP server 或插件）先把错误归类，别把原始异常直接抛进主循环。

**2. 退避 + 抖动 + 重试预算，写死在代码里。** 指数退避配随机抖动，再设两个硬上限：最大次数（如 3 次）与最大总耗时（如 30 秒），任一触发就停。重试是 harness 的职责，不要写进 prompt 让模型自由发挥。

**3. 结构化错误喂给模型。** 失败时返回类似：

```json
{"ok": false, "error": "rate_limited", "retryable": true, "retry_after_s": 20}
```

模型看到干净字段而非堆栈，才能在“换工具 / 跳过 / 标记失败”里做选择。把堆栈原样喂进去，典型后果是模型开始道歉并猜测。

**4. 写操作带幂等键。** 下单、发消息、写库这类有副作用的调用，重试时必须复用同一个幂等键，否则退避重试就是在批量制造重复数据。

**5. 熔断与预设计的降级路径。** 连续 N 次失败即熔断，冷却期内直接走降级：备用 provider、带“数据可能过期”标注的缓存、或明确告知该功能暂不可用。降级方案要提前设计好，别指望模型现场发挥。

**6. 长任务做检查点。** 多步任务把中间状态持久化，恢复时从断点继续，而不是从头再来一遍。

## 踩坑点

- **退避不加抖动**：多实例同一时刻重试，打出同步洪峰，429 更严重；
- **对 400 反复重试**：参数错了，重试一次烧一次 token，还可能触发封禁；
- **超时设太长**：一个挂起的调用能把整个 agent 循环阻塞几分钟，每个工具调用都要套超时；
- **静默吞错返回空值**：模型会理解为“查询结果为空”，输出似是而非的结论——宁可失败得明确；
- **降级静默切换**：主模型挂了自动换小模型，质量下降但无人知晓，降级必须打标、留痕。

## 可复用建议

- 所有外部调用收敛到统一 wrapper：超时 + 重试 + 熔断 + 结构化错误，改一处全局生效；
- 预算在代码里，策略在模型手里，但选项必须是你预先设计好的；
- 留“人工介入”出口：重试与降级都失败时标记 needs_human 并停住，别让 agent 空转；
- 按 tool 维度监控错误率，突增即告警，并记录上游 request id / trace id，方便与 provider 的事故页对账。

## 总结

错误恢复不是 prompt 问题，是系统设计问题。一句话原则：**预算由代码控制，策略由模型在给定选项中选择，副作用必须有幂等保护，降级必须留痕**。把这几件事做进 harness，外部 API 挂掉时，agent 的表现就从“抽风”变成“可预期的降级”。
