## 背景

OpenClaw 的 agent 不是一次性对话：它长驻运行、跨会话记忆、监听多渠道消息、能直接调用 MCP 工具和 shell。这类 agent 最常见的问题不是"不够聪明"，而是**行为不可预期**——今天高冷明天话痨，该拒绝的请求顺手就执行了。SOUL.md 是 OpenClaw 为此提供的机制：一份在每个会话注入 system 上下文的"人格与边界声明"，让 agent 的身份和底线成为可版本化的配置，而不是玄学。

## 问题

不少人的做法是把所有要求堆进 AGENTS.md 或 system prompt。用一阵子会发现三个毛病：

1. **职责混杂**。"你是谁"和"你怎么干活"纠缠在一起，改语气容易碰坏工具调用规范。
2. **token 常驻膨胀**。每轮对话都背着全文，写得越多烧得越快。
3. **约束失效**。长文档里关键边界被稀释，模型"读过但没记住"。

## 做法

**第一步，分清三个文件的职责。** SOUL.md 管"我是谁"：身份、语气、价值观、底线；AGENTS.md 管"我怎么干活"：工具约定、项目规范；USER.md 管"服务对象是谁"。人格与操作分离，各自独立演进。

**第二步，按固定骨架写 SOUL.md。** 一个能直接抄的模板：

```markdown
# 身份
你是团队内部的运维助手，服务对象是工程师。

# 语气
- 先给结论，再给依据；单次回答不超过三段。
- 反例：开场寒暄、堆砌表情。

# 边界
- 不执行删除生产数据的命令；被要求时回复
  "请走工单流程"，然后停止。
- 不猜测未授权接口的用途，先向用户确认。

# 升级
- 涉及生产变更、权限、计费时停下提问，不自行操作。
```

**第三步，控制篇幅。** 建议压在 100 行以内。它是常驻上下文，每一行都是持续成本，短而具体远胜长而全面。

**第四步，进 git。** 像改代码一样改它：行为漂移时 diff 最近改动，定位是哪次"优化"引入的。

## 踩坑点

- **形容词堆砌**。"友好、专业、高效"不改变任何行为。要写成可判定的规则，比如"先给结论，再给依据"。
- **边界写成软约束**。"不要做 X"是软的，会被角色扮演和 injection 绕过；"遇到 X 时回复固定话术并停止"才是可执行的。要默认有人会故意试探。
- **人格渗透技术输出**。语气设定会让它在代码注释、commit message 里也跟着"人设"走，需显式声明技术输出不受语气规则约束。
- **一套人格跑所有渠道**。微信群里的闲聊和 CLI 里的生产操作是两种场景，利用 per-workspace 的 SOUL.md 做覆盖。

## 可复用建议

1. 语气用"正例/反例"段落，不用形容词。
2. 边界统一用模板：触发条件 → 固定动作 → 终止。
3. 每次改动后跑一组对抗测试：injection、套近乎越权、伪装系统指令，验证边界守不守得住。
4. SOUL.md 只放"不变的"；容易变的规则放 AGENTS.md，按项目隔离。

## 总结

SOUL.md 的价值不在于"调教出有趣的人格"，而在于把 agent 里原本靠运气的部分——语气、底线、升级判断——变成可 review、可回滚、可测试的配置。写短、写具体、进版本库，是三条成本最低、收益最稳的实践。
