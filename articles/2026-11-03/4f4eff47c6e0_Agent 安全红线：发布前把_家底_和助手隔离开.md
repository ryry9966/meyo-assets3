## 背景

近几个月，社区里用 Agent 写帖、答疑、做自动摘要的人明显变多。这些 Agent 通常挂着 MCP 工具：文件系统访问、浏览器控制、内部知识库检索。便利的另一面是，它们天然接触大量内部信息——部署脚本、工作日志、内网地址、密钥文件。一旦产出流向社区，泄漏不再需要攻击者，一条普通的自动化流程就够了。

## 泄漏的真实路径

实际发生过的几类：

1. **上下文携带**：Agent 为"理解业务"读了内部文档，之后写公开内容时顺带引出内部端点、项目代号。
2. **调试泄漏**：排障时把完整配置或日志整段贴进求助帖，token 和内网域名一起出门。
3. **工具过权**：filesystem MCP 挂载点直接给了 `$HOME`，`.env`、`.ssh` 全在射程内。
4. **记忆残留**：长期记忆存了内部细节，几天后在另一个会话里被自然带出。
5. **间接注入**：Agent 抓取的网页或第三方插件里藏着指令，诱导它外传上下文。

## 做法：按爆炸半径收敛

**实例分离**。内部工作和社区产出用两套 Agent profile：不同工作目录、不同 MCP 配置。公开向实例永远不挂内部知识库。

**最小挂载**。公开向实例的文件系统根指向专门的 `publish/` 目录，里面只放待发布草稿。不给 `$HOME`，不给部署脚本。

**出站过滤**。发布前跑 hook 脚本，正则扫 `sk-`、云厂商 AK/SK 格式、内网域名、CI 地址。命中即阻断，人工确认后才放行。

**人在回路**。所有自动发布走审核队列，审核看的是"生成稿到发布稿的 diff"，成本压到一条命令，而不是靠自觉。

**记忆策略**。公开向实例关闭长期记忆，或按任务开一次性会话；内部实例才允许积累记忆。

**插件白名单**。第三方 MCP 只在隔离实例里试跑，且该实例不挂任何内部资源。

## 踩坑点

- **System prompt 不是控制手段**。写"不要泄漏"属于软约束，长上下文或注入场景下必然失效。真正的控制是权限，不是嘱咐。
- **"这次先跳过审核"**。泄漏几乎都发生在图省事的瞬间。解法是把审核做得足够便宜，而不是依赖自律。
- **手工脱敏不可靠**。先跑自动扫描，人只做最后确认；顺序反了等于没扫。
- **删帖不等于善后**。内容泄漏后第一件事是轮换凭据，其次才是处理帖子。
- **共享环境的浏览器态**。Agent 有浏览器控制权时，共享 profile 里的登录态本身就是资产。

## 可复用建议

- 维护一份**红线清单**文件：内网域名、项目代号、拓扑结构、人员信息、密钥格式。扫描脚本直接读它，清单即配置。
- 把发布前检查封装成**一条命令**（如 `make prepub`），让正确的事情成为最省力的事情。
- 每个 session 记录**工具调用与文件读取审计日志**，出了事能立刻回答"它看过什么"。
- 默认假设：你发布的每一句话都会被截图存档。

## 总结

Agent 安全的核心不是"更信任模型"，而是收敛爆炸半径：实例分离、最小挂载、出站过滤、人在回路。模型迟早会在某个长上下文里失手，工程上要做的是让它失手时，手边没有值钱的东西。
