“服务器繁忙，请稍后再试。”——2025年初，这句报错大概是中文互联网出镜率最高的机器文案。DeepSeek-R1 发布后流量暴涨，服务多次不可用，"DeepSeek崩了"几度冲上热搜。很多人以为"崩"就是断电断网，其实背后是一整套大模型推理系统的容量账。这篇就把“崩”拆开讲：它到底崩在哪，为什么大模型服务特别容易挤爆，平台怎么自救，以及我们能做什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-03/6a33466384677f04.png)

## 崩溃现场：到底发生了什么

- **时间线**：2025年1月20日，DeepSeek 发布推理模型 R1，性能对标国际一线、API 定价只有同级闭源模型的几分之一；一周内登顶中美 App Store 免费榜；随后官方限制新用户注册（当时公告提到遭遇大规模恶意攻击），此后数月网页端和 API 又多次出现“部分服务不可用”，官方状态页都有记录可查。
- **“崩”的三种形态**：一是超时，请求在队列里排不到算力；二是限流，直接返回 429；三是拒绝新会话，老用户还能聊、新用户进不来。三种形态本质是同一个问题：需求暂时超过了实时算力供给。
- **一个背景**：DeepSeek 同时押注“免费 App + 超低 API + 开源权重”，等于用相对精简的自有基础设施，接住了行业顶级量级的免费流量。参照系是 2023 年初的 ChatGPT——当时它常年挂着"at capacity"，负载被打爆是行业通病，不是某一家的锅。

## 推理为什么贵：大模型的算力账单

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-03/60e9502ea7eba3e9.png)

1. **自回归生成**：大模型吐字是一个 token 一个 token 来的，每吐一个都要完整跑一遍前向计算。输出 1000 字，就是上千次前向推理——它不像传统 API“读库返回”，更像是让一台机器现场手写一篇长文。
2. **显存是硬天花板**：V3/R1 是 671B 总参数的 MoE 架构，虽然每个 token 只激活约 37B 参数，但全部权重都要常驻显存，即便 FP8 精度也得几百 GB，必须多卡组成节点才能装下。
3. **KV cache 吃显存**：每个在线会话都要在显存里存一份自己的上下文“记忆”。并发人数越多，显存越挤；显存一满，要么减小 batch，要么让部分用户等待。
4. **瓶颈常在带宽**：解码阶段主要是 memory-bound，卡的不是 FLOPS 而是显存带宽，所以“再加几张卡”并不等于线性扩容，组网、调度、并行策略都要跟着改。
5. **推理模型雪上加霜**：R1 这类 reasoning 模型会先生成很长的思维链，单请求输出 token 是普通对话的好几倍，一个请求占用算力的时间更长，同样显存能同时服务的并发反而更少。

一句工程师式总结：传统网站是无状态的，崩了重启就行；大模型每个会话都带着“记忆”，扩容更像搬家，不像开灯。

## 洪峰压垮服务的完整链条

1. **需求与供给的时间差**：用户一周涨出千万级，而 GPU 从下单、交付、上架、组网到压测上线，按月计。需求是脉冲，供给是匀速，中间必然出现剪刀差。
2. **排队论的非线性**：并发一旦逼近容量上限，延迟不是匀速恶化，而是陡增。以最简的 M/M/1 排队模型为例，平均排队时间与 ρ/(1-ρ) 成正比——利用率从 50% 拉到 90%，排队时间直接放大一个数量级。
3. **重试风暴**：超时之后，用户手动狂点重试，客户端 SDK 还带自动重试，这些无效流量进一步挤占本就紧张的算力，形成恶性循环。
4. **没法用 CDN 兜底**：图片视频可以缓存到边缘节点就近返回，推理必须“回源”到实时算力，一个 token 都绕不过去。这就是为什么静态内容很难崩、AI 服务反而容易崩。

## 平台的自救工具箱

- **限流与排队**：按用户、按 API key 限速，超出容量就明确排队，把“挤爆”变成“有序等待”。
- **降级**：高峰期切小模型、压上下文长度、收紧免费额度，先保住大多数人的基本体验。
- **分流**：开源权重本身就是泄洪渠——R1 发布后各大云厂商纷纷上线官方及蒸馏版本，第三方 API 承接了溢出的流量。
- **错峰**：深夜释放额度、给 API 用户划分独立容量池，把脉冲流量尽量摊平。
- **透明沟通**：状态页 + 事故复盘。稳定性的目标从来不是“永不崩”，而是崩得可预期、恢复得快、用户知道去哪看进展。

## 三条实用建议与一点冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-03/3f3cd0db4750836c.png)

1. **普通用户**：高峰期别硬刚。可以改用第三方托管的 API 渠道，或者用 Ollama 之类工具本地跑蒸馏小模型；重要任务错峰提交，成功率比玄学刷新高得多。
2. **开发者**：生产环境别绑死单一供应商。做好超时、指数退避重试（exponential backoff）、备用模型路由和结果缓存；选型时把 SLA 和状态页当成与跑分同级的指标，别只看评测榜单。
3. **冷思考**：“崩”某种意义上是免费、低价、爆款叠加出来的“幸福的烦恼”，它证明的是需求侧的热情，而不是技术失败。真正值得记住的是：在这个行业里，“高峰期还能不能用”，和“跑分多高”一样重要——前者才决定它能不能进你的工作流。
