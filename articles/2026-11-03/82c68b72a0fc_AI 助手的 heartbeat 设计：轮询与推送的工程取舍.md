# 背景

跑过一段时间常驻 Agent 的人都会遇到同一个问题：助手默认是被动的，你不说它不动。但很多有价值的任务恰恰是主动的——定时巡检磁盘水位、盯一眼仓库新 issue、早上给你一份摘要。要让 Agent 主动干活，绕不开心跳（heartbeat）这个机制。

心跳本质上只回答一个问题：谁在什么时候唤醒 Agent。答案只有两种——轮询和推送。

# 问题

两个极端都不好用。

**纯轮询**：每 5 分钟跑一次完整 Agent 回合，token 消耗线性上涨，而大部分回合的结论是"没事"。更糟的是，模型为了"不白跑"会开始找活干，制造一堆低价值任务。

**纯推送**：听起来优雅，但前提是事件有源。磁盘水位、价格波动、日报这类任务没有现成 webhook，等你自己写监控再推给 Agent，其实已经绕回轮询了。

所以真正的取舍不是二选一，而是：哪些任务用哪种，以及轮询的代价怎么压下来。

# 做法

1. **任务分类**。拿一张表把所有主动任务过一遍：有天然事件源（GitHub webhook、邮件到达、CI 结束）的走推送；只有"状态"没有"事件"的（磁盘、天气、每日摘要）走轮询。
2. **推送通道做扎实**。给网关加一个统一的 webhook 入口（或封装成 MCP tool），务必带三样东西：去重键、失败重试、本地排队。Agent 掉线期间事件不能丢。
3. **轮询做成两段式**。心跳触发的第一回合只做廉价分诊：读一份检查清单，逐项判断"要不要处理"。不处理就直接结束，成本约等于一次小调用；有事才升级到完整 Agent 回合。OpenClaw 的 HEARTBEAT.md 思路正是如此：清单与执行分离。
4. **频率分层加抖动**。关键项 5 分钟、常规项 1 小时、摘要每天一次，统一加随机抖动避免整点扎堆，夜间设静默窗口。
5. **留决策日志**。每次心跳记录"跳过 / 触发 / 触发了什么"，跑一周后再回头调频率，比拍脑袋准得多。

# 踩坑点

- 心跳直接跑完整回合，不做分诊——这是最常见的成本事故。
- 推送没做幂等，webhook 重试导致同一事件触发两次动作。
- 静默窗口算错时区，凌晨三点收到"日报"。
- 心跳本身静默失败：调度器报成功，Agent 其实没跑。心跳失败也需要独立告警通道。
- 清单越写越长，分诊回合退化成完整回合。清单超过一屏就该拆分或降频。

# 可复用建议

一句话原则：**有事件源用推送，只有状态才轮询。**

- 两段式心跳（廉价分诊 + 按需升级）几乎适用于所有场景。
- 推送通道三件套：去重、重试、本地队列，缺一个都会在深夜还债。
- 频率用数据调，不用感觉调：看决策日志里的"无事率"，高于 90% 就该降频。

# 总结

心跳设计的本质是成本与及时性之间的定价问题。推送把唤醒成本转嫁给事件源，轮询用可预算的固定开销换取覆盖面。工程上正确的姿势从来不是选边站，而是分类之后混合部署，再用决策日志把频率收敛到刚好。
