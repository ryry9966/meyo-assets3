## 背景

跑过生产级 Agent 的人多半有同感：Agent 本体很稳，先挂的往往是它依赖的外部 API——搜索接口限流、行情源超时、MCP server 半死不活。传统服务里“依赖故障”有一整套成熟打法，但 Agent 的特殊之处在于，错误最终会流进一个会“自由发挥”的模型手里。处理不当，问题会从“接口挂了”升级成“Agent 编了个答案”。

## 问题

裸跑的 Agent 在工具失败时通常有三种反应：

1. **原地重试，没有上限**。失败→重试→失败，一轮烧掉大量 token，账单比故障本身更疼。
2. **幻觉兜底**。模型看到报错后改用训练数据“凭记忆”作答，语气自信，用户无法分辨真假。
3. **链路卡死**。工具超时 30 秒，Agent 干等，并发一上来直接雪崩。

根因一致：把错误处理的决策权交给了模型，而不是代码。

## 做法

我们的原则：重试、降级、熔断全部在工具/MCP 插件层用代码实现，模型只接收结构化的、诚实的结果。

**第一步，错误分类。** 在插件里把错误分成三类：瞬态（超时、429、502/503）、永久（401/403、参数错误、接口下线）、业务错误（余额不足、无权限）。分类后返回统一结构：

```json
{ "status": "degraded", "error_class": "transient",
  "data": { "…缓存数据…" }, "data_age": "2h" }
```

**第二步，代码层重试。** 指数退避加抖动，设重试预算（如最多 3 次、总耗时 20 秒）。预算耗尽后，把“暂时不可用”作为正常结果返回给模型，而不是抛异常。

**第三步，降级链路。** 每个关键工具至少准备一层兜底：本地缓存最近一次成功结果（标注数据时间）、备用数据源、或者直接返回“此步骤跳过”。关键是把降级状态显式告诉模型，让它能向用户如实说明。

**第四步，熔断。** 插件内维护失败计数，连续失败超过阈值就打开熔断器 T 秒，期间快速失败。既省得 Agent 每次干等 30 秒，也避免重试风暴打死上游。

**第五步，给模型逃生通道。** 在 system prompt 和工具描述里明确：工具不可用时，允许向用户提问、跳过该步骤或建议稍后重试，禁止用旧知识冒充实时代答。

## 踩坑点

- **让模型自己决定重试**：不确定性极高，重试逻辑必须写死在代码里。
- **对写操作盲目重试**：POST 下单、支付这类非幂等接口，重试必须带幂等键，否则会重复扣款。
- **把原始异常栈直接喂给模型**：模型会试图去“修”它，还可能把内部信息透传给用户；报错文本含上游内容时甚至有注入风险。
- **超时不对齐**：Agent 侧超时比工具侧短，会出现 Agent 已放弃、工具还在执行的双跑。
- **没有 run 级预算**：熔断只保护单个工具，整轮 run 还需要总步数/总 token 上限，防止 Agent 在多个坏工具之间反复横跳。
- **MCP stdio 连接半死**：进程活着但管道已断，需要心跳检测和自动重连，不能只靠异常捕获。

## 可复用建议

抽成一个最小检查清单，新插件上线前过一遍：

1. 所有错误返回结构化 JSON，带 `error_class`；
2. 重试在代码层：退避 + 抖动 + 预算上限；
3. 写操作必须有幂等键；
4. 至少一层降级（缓存/备用源/跳过），且降级显式声明；
5. 插件级熔断 + run 级步数预算；
6. 结构化日志记录工具名、错误类、尝试次数、延迟，方便复盘和重放。

## 总结

外部 API 挂了是常态，不是事故。好的 Agent 错误恢复，本质是让模型永远拿到一个诚实且可行动的视图：能重试的，代码里已经重试过了；不能重试的，明确告诉它“这条路不通”。模型是最后一道防线，不该是第一反应。确定性的活交给代码，判断和沟通留给模型，故障时系统才不会从“慢一点”变成“错得离谱”。
