## 背景

Agent 的价值在于能动手。OpenClaw 在本地跑起来、接上消息渠道之后，用户一句“查下库存”或“把这个工单转给售后”，最终都要落到一次真实的 API 调用上。怎么让模型可靠地“伸出手”，而不是每次都靠临场发挥，是对接外部服务时最值得花时间的部分。

## 问题：三种常见但不对的做法

1. **把 API 文档塞进 system prompt，让模型自由发挥 curl。** 端点靠猜，密钥直接进了模型上下文，出问题无从审计。
2. **每个接口包成一个巨型工具。** 十几个参数、职责模糊，模型选错工具、填错参数的概率直线上升。
3. **不设超时和重试策略。** 对方一限流，agent 要么卡死，要么连环重试打出重复订单。

本质是同一个问题：握手协议没约定。谁认证、谁兜错、谁重试，必须事先讲清楚。

## 做法：把 API 包成“窄工具”

以对接一个内部工单 API 为例，我的分层：

**第一层：认证与配置。** 密钥放环境变量，skill 配置里只引用变量名。密钥绝不出现在 prompt、工具描述或日志里。

**第二层：MCP server / skill 做适配器。** 用 MCP 把 API 包成结构化工具，或者写一个薄脚本。原则是：

- 一个工具只做一件事，`query_ticket` 和 `update_ticket` 分开；
- 参数 schema 收窄，状态字段用枚举而不是自由字符串；
- 工具描述写给模型看：说清“什么场景该用我”，而不是复述接口文档。

**第三层：调用治理。** 超时必须有（10~15s 起步）；读操作可以自动重试、指数退避；写操作默认不重试，或强制带幂等键。错误信息是给模型读的提示词——返回 `rate_limited, retry after 30s` 远比 `Error 429` 有用。

**第四层：可观测。** 每次工具调用记一行日志：工具名、参数摘要、耗时、结果状态，密钥脱敏。排查“agent 为什么没调对接口”时，这行日志比翻聊天记录快得多。

## 踩坑点

- **密钥进了上下文**：调试时把 Authorization 头打进了工具返回值，模型原样复述给了用户。返回值要做脱敏，只留白名单字段。
- **工具太多**：挂了 20 个工具后模型开始选错。砍到 8 个以内、按场景分 profile 动态加载，准确率明显回升。
- **限流引发的循环**：agent 收到 429 后立刻重试，雪上加霜。现在适配器层先退避，错误信息里也明确写出等待时间。
- **非幂等写操作**：一次网络重试创建了重复工单。写接口要么带幂等键，要么拆成“先查再写”两步，写之前由用户确认。

## 可复用建议

1. 外部服务一律走适配器层，API 变更只改一个文件；
2. 错误消息当成 prompt 来写，读者是模型不是人；
3. 读写分离：写操作要么幂等，要么落到人工确认；
4. 工具数量克制，按任务场景挂载，宁少勿多。

## 总结

Agent 与 API 的握手，难点从来不是“能不能调通”，而是契约：认证、错误、重试、幂等，每一项都要在适配器层明确约定。OpenClaw 的 MCP 和 skill 机制提供了干净的挂载点，剩下的工程纪律——窄 schema、干净错误、完整日志——才是稳定对接的真正成本所在。先把这些约定写下来，再写第一行工具代码，会省掉后面大量的返工。
