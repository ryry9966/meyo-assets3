## 背景

OpenClaw 的自动化任务里，Agent 很少只靠自己完成事情：查数据要调搜索 API，发通知要走 webhook，读写状态要连内部服务。这些外部依赖绝大多数时候是好的，但"绝大多数"不等于"永远"。一个跑 20 步的流程，只要中间某一步的 API 超时或返回 5xx，整个任务就可能中断——或者更糟，带着错误继续跑下去。

## 问题

外部 API 故障对 Agent 的伤害分两层：

**第一层是常规工程问题**：超时、限流（429）、服务端错误、返回结构悄悄变了。这和普通后端开发遇到的没区别。

**第二层是 Agent 特有的**：LLM 面对失败的工具调用时，行为不可控。常见三种翻车——把报错原文当结果继续推理；自己发起重试，一烧几十轮 token；干脆编一个"看起来合理"的数据填上。实践中第二层造成的损失往往比第一层更大。

## 做法

我们的原则很明确：**重试和兜底放在工具封装层（MCP server / 插件），模型只负责决策，不负责机械重试。**

1. **先分类错误**。可重试的（超时、429、5xx）走自动重试；不可重试的（参数错误、鉴权失败）直接结构化上报，别浪费重试预算。
2. **工具层三件套**：timeout + 指数退避重试（加 jitter）+ 熔断。连续失败 N 次后短路，避免雪崩式重试。
3. **准备降级路径**：缓存最近一次成功结果并标记时间戳；有条件就配备用 API；都没有，就让 Agent 明确说"该数据暂不可用"，而不是沉默或编造。
4. **给模型的错误信息要结构化**：错误码、是否临时故障、建议动作（跳过/降级/终止）。一段三行的 JSON 比一坨 HTML 错误页有用得多。
5. **设重试上限和失败出口**。整个任务有一个全局重试预算，超了就把任务标记为 failed 并落盘现场，等人工或定时任务接管。

## 踩坑点

- **让 LLM 自己决定重试次数**，等于把预算控制权交给一个不会数数的执行者。
- **对有副作用的 API（下单、发消息）裸重试**。没有幂等键的重试等于重复执行，我们吃过一次重复推送的亏。
- **降级用了缓存数据但没标时间**，用户把三天前的数据当实时数据用。
- **超时 × 重试次数算总账**：超时 30 秒重试 5 次，一个坏依赖能挂住任务队列两分多钟，注意单次超时要小于下游实际的耐心。

## 可复用建议

- "调用外部服务"统一走封装层，禁止 Agent 直接拼裸 HTTP 调用。
- 幂等键 + 请求 ID 落日志，事后能对账。
- 降级数据必须带 staleness 标记，并在提示词里写明"过期数据要主动声明"。
- 任务支持 checkpoint：挂掉能从上一步恢复，而不是从头再来。

## 总结

错误恢复的本质不是让 Agent "更聪明"，而是在系统层把不确定性框住：机械的重试交给封装层，语义的判断（跳过、降级、上报）才交给模型。做到这一点，外部 API 挂掉时，你的 Agent 表现会从"行为诡异"变成"可靠地报告坏消息"——后者才是生产环境真正需要的能力。
