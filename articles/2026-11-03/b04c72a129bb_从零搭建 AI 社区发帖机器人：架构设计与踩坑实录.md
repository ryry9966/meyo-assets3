## 背景

社区每周需要一篇「本周动态」汇总帖，内容来自 GitHub Issues、论坛热帖和群里的讨论。之前靠人工整理，经常拖到周四种。于是我用 OpenClaw agent 加 MCP 工具搭了一个自动发帖机器人，现在稳定跑了一个多月。这篇帖子里不聊提示词技巧，只聊把它当**发布系统**来做时遇到的架构问题和真实的坑。

## 问题

让模型写一段汇总并不难，难的是四件事：不编造内容、不重复发帖、失败不静默、成本不失控。社区发帖是有公信力的，机器人发错一条链接的代价远高于省下的十分钟。

## 架构与做法

最终落地的结构是五层单向管道，各层独立进程，靠队列衔接：

1. **采集层**：GitHub API + 论坛 RSS，统一产出结构化 JSON（标题、链接、状态、时间戳），不做任何自然语言处理。
2. **调度层**：cron 触发，任务带幂等键（日期 + 槽位号）进队列。
3. **生成层**：agent 通过 MCP 工具读取结构化数据，两段式生成——先让模型提炼要点列表，再基于要点组装正文。模型只做转述和排版，不做信息增量。
4. **校验层**：规则校验所有链接可达性、日期格式、字数上限，不过就重试一次，仍失败转人工队列。
5. **发布层**：调社区 API 发帖，发布前查重，prompt 原文和模型输出全量落库。

关键设计原则就一条：**采集与生成分离**。换模型、调提示词不影响管道，回滚也只回滚一层。

## 踩坑实录

- **幻觉链接**：早期让模型直接读网页原文，它会编出格式完美但编号不存在的 issue 链接。后来强制所有数据经 MCP 工具注入，校验层再对每条链接做 HEAD 请求，问题归零。
- **重试导致重复帖**：发布超时后重试，结果发出两条。修法是幂等键入库 + 发布前查重，而不是靠模型「记得自己发过」。
- **频率限制**：测试期连续触发触发了论坛限流。改为单队列串行发布 + 指数退避，别并发。
- **token 成本**：第一版把全部 issue 原文塞进上下文，单次成本是预估的六倍。改成「先摘要后组装」两段式，降了 70%。
- **静默失败**：最坑的一次——机器人挂了三天没人发现，因为没人去看日志。加了心跳上报，连续两次未心跳就告警到群。
- **质量漂移**：模型升级后文风突变，老用户不买账。应对是前两周 100% 人工审核，之后降到 30% 抽检，保留一键撤帖。

## 可复用建议

- 把发帖机器人当发布系统，不当脚本：幂等、状态机、可观测，三样缺一不可。
- 人工审核开关必须是默认项，自动化程度可以渐进放开，但入口不能封死。
- prompt 和模型原始输出都要落库，排障时能完整回放，比猜高效十倍。
- 校验用规则而不是让模型自查——模型检查自己的输出，约等于没查。

## 总结

这个项目里，真正花时间的不是生成部分（两天），而是幂等、校验、告警这些「不性感」的工程闭环（十天）。AI 社区机器人的瓶颈从来不是模型能力，而是你愿不愿意把它当生产服务来对待。管道代码我整理在社区仓库了，欢迎抓 bug。
