## 背景

OpenClaw 的工作区里有一组 markdown 文件决定 agent 的行为：`AGENTS.md` 管流程，`USER.md` 管用户事实，`SOUL.md` 管人格和边界。SOUL.md 会被拼进每次会话的上下文，相当于一份长期生效的“性格说明书”。默认模板能跑，但多数人要么从不改，要么把它当成第二个系统提示词仓库——两种极端在真实使用中都会出问题。尤其当 agent 接了定时任务和 MCP 工具开始自主行动时，边界比语气更要紧。

## 问题

不改的后果是行为漂移：语气忽冷忽热、过度道歉、该拦的操作不拦、同一件事换个会话给两种答案。乱改的后果是指令稀释：任务步骤、人格设定、红线规则混在一起，越写越长，模型对中间内容的注意力越差，越写越不管用。

另一个常见误解是把 SOUL.md 当安全边界。它是软约束，靠模型自觉执行。真正危险的操作（删文件、发消息、执行 shell）必须靠工具白名单和系统权限兜底，文档拦不住 `rm -rf`。

## 做法

1. **先读默认模板，增量修改。** 不要从零写。模板条目是社区踩坑后的收敛结果，删掉前先想它为什么在那。
2. **分离关注点。** SOUL.md 只放三样东西：我是谁（2-3 行）、说话方式（3-5 条可验证规则）、红线与升级规则。任务流程归 AGENTS.md，用户偏好归 USER.md。
3. **边界写成可判定的句子。** “保持友好”没有信息量；“删除操作必须先复述目标并等确认”“引用外部信息给来源，找不到就说找不到”才能被执行。
4. **加少量正反示例。** 各一段“希望这样回 / 不希望这样回”，比十条形容词有效。
5. **用 git 管工作区。** 每次改 SOUL.md 单独提交，行为变了能 diff 回去。
6. **定期收漂移。** 跑两三周，把表现不对的对话摘出来，每类问题补一条纠正规则，而不是推倒重写。

## 踩坑点

- **写太长。** 我见过 200 行的 SOUL.md，每次会话都注入，token 翻倍且中间规则基本被忽略。经验值：控制在 40 行以内。
- **放秘密。** 有人图方便把 key 写进去，SOUL.md 会进上下文，还可能被读工作区的插件拿到。
- **规则互相矛盾。** “简洁优先”和“每个回答都要完整解释”放一起，输出就变成抽签。
- **忽视子代理。** 部分配置下子会话不一定加载同一组文件，主会话测试通过，子代理照样裸奔。改完用调试手段确认实际注入内容。
- **模型升级后不复测。** 上游模型换了，人格表达方式常变，老规则可能失效甚至起反作用。

## 可复用建议

- 定一个骨架：身份 3 行 + 语气 5 条 + 红线 5 条 + 升级规则 1 条，总共一屏。
- 维护 drift log：出问题记一行，攒够一类再改文件，避免情绪化重写。
- 红线分层：语气类放 SOUL.md，权限类放 MCP 工具白名单和操作系统权限，各管各的。
- 建一个 10 条左右的测试 prompt 集，每次改动后跑一遍，确认语气和边界稳定。

## 总结

SOUL.md 本质是“配置即文档”。把它当代码对待：短小、版本化、有测试、按需演进。人格部分决定它像不像你想要的助手，边界部分决定它敢不敢替你做危险的事——后者往往才是真正值得花时间写的部分。
