## 背景

单 Agent 跑长任务有两个老毛病：一是上下文越滚越大，后期模型注意力被早期噪音稀释；二是工具调用串行排队，一个慢环节拖住整条流水线。当任务天然可拆分——比如把 40 多个插件配置迁移到新格式、或对一个仓库做多维度审查——串行执行既慢，中途的上下文污染还会让后半段输出质量明显下滑。Subagent 编排就是针对这个问题的工程化解法：主 Agent 负责拆解和验收，子 Agent 在各自隔离的上下文里并行干活。

## 一个真实场景

之前迁移一批 MCP 插件配置，最初让主 Agent 逐个文件处理，跑到二十多个之后它开始“记混”不同插件的字段差异，返工了三次。改成 subagent 并行后，每个子 Agent 只看一个文件，互不干扰，一次跑完，错误率反而降了。

## 具体做法

1. **主 Agent 只做拆解与汇总**。它不亲自改文件，只产出子任务清单：每个子任务包含输入路径、目标格式、明确边界（“只处理这个文件，不许动其他文件”）。
2. **子任务必须是叶子任务**。如果子 Agent 拿到任务后自己又开始拆，说明拆得不够细，宁可多加一层也不要让它自由发挥。
3. **结果一律落盘**。每个子 Agent 把结果写进自己的输出文件（固定命名，如 `result/{task_id}.json`），主 Agent 汇总时只读文件，不依赖对话回传。
4. **强制输出 schema**。约定 JSON 结构，解析失败就按失败处理，避免汇总阶段人工清洗。
5. **并发控制在 3–5**，每个子任务带超时，失败重试一次，仍失败就标记跳过，最后由主 Agent 出一份失败清单。
6. **工具权限最小化**。子 Agent 通常只需要读输入、写自己的输出，不给全局写权限。

## 踩坑点

- **并发写冲突**：让多个子 Agent 直接改同一个文件必炸。要么各写各的，要么主 Agent 统一合并。
- **上下文大包大揽**：把主 Agent 的全部对话塞给子 Agent，成本翻倍还稀释重点。只传路径和必要约束。
- **没有超时**：一个子 Agent 死循环，整批任务被拖住。超时和重试上限必须硬编码。
- **全信汇总结果**：并行加速容易掩盖单点错误，务必留一次人工抽查。

## 可复用建议

判断一个任务值不值得并行，看两点：子任务之间**没有共享可变状态**，且**单个子任务的上下文需求足够小**。满足这两条，收益主要来自失败隔离和上下文隔离，速度只是副产品。并发数保守起步，先验证结果质量再加量。

## 总结

Subagent 编排本质是分治：主 Agent 管拆解、调度和验收，子 Agent 管隔离执行。它解决的不是“快”，而是长任务里上下文污染和单点失败这两个更隐蔽的问题。先把任务拆干净，再谈并行。
