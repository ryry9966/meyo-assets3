## 背景

Agent 要真正干活，绕不开外部服务：查数据库、发工单、调内部 RPC、对接第三方 SaaS。在 OpenClaw 里，这一层主要由工具调用和 MCP 服务承载。工具层写得稳，Agent 就可控；写得糙，每次对接都是一次重新踩坑。这篇把我们团队几轮对接沉淀下来的做法整理一下。

## 问题

最省事的做法是把 API 调用直接写进 system prompt，或者为每个服务手写一次性函数。问题很快暴露：

- 密钥跟着配置文件到处漂，甚至进过仓库；
- Agent 遇到失败就反复重试，把非幂等接口打出一串重复订单；
- 第三方接口改了字段，工具描述没跟上，Agent 开始"脑补"参数；
- 返回的大段 JSON 直接灌进上下文，token 开销和出错率一起涨。

本质问题是：Agent 需要的不是"能调 API"，而是一个边界清晰、错误可解释、副作用可控的握手层。

## 做法

1. **盘点接口，先读鉴权**。确认服务用 API Key、OAuth 还是内网 token，摸清限流策略；写操作（POST/PUT/DELETE）单独标记出来。
2. **一层适配，永远只做一层**。每个外部服务包成独立工具或一个 MCP server，工具描述写清楚三件事：干什么、要什么参数、什么时候不该调。业务逻辑不要堆进 prompt。
3. **Schema 收紧**。参数用严格的 JSON Schema，是枚举就写枚举，别留自由字符串让模型发挥。
4. **写操作加幂等键**。客户端生成 idempotency key 传下去（或本地去重表），Agent 重试不至于重复下单。
5. **超时与重试外置**。连接超时设短（3–5s），读超时按服务实际 P99 定；重试只对幂等操作开，指数退避。
6. **返回值做减法**。适配层过滤、摘要、截断，只把决策需要的字段吐回去。错误信息要"写给 Agent 看"：说清是参数错、权限错还是服务端错，它才知道该重试还是上报。
7. **先 mock 后联调**。用假数据跑通对话流，再切真实环境，权限按最小化给。

## 踩坑点

- 密钥只走环境变量或密钥管理服务。曾有同事把 key 写进工具描述"方便调试"，扫描工具当场报红。
- 工具描述和实际接口会漂移。接口升级时把 schema 当契约维护，加一层契约测试跑在 CI 里。
- 某个下游抽风返回过 10MB JSON，直接把上下文打爆。适配层必须设返回体积上限，超限就截断并附说明。
- Agent 对 429 的天然反应是立刻重试，恰好撞进限流窗口。退避逻辑放在适配层，别指望模型自己学乖。

## 可复用建议

- 粒度原则：一个服务一个工具组，高频操作拆细粒度工具，低频的合并。
- 每个 MCP server 暴露一个 `health_check` 工具，排障时先探活再追日志。
- 所有外部调用打结构化日志（工具名、参数摘要、耗时、结果码），出问题三分钟能定位是 Agent 的锅还是服务的锅。

## 总结

对接外部服务的核心不是"调通"，而是把鉴权、限流、幂等、错误语义这些工程细节收进一个薄的适配层，让 Agent 只面对稳定、可解释的工具面。工具面稳定了，Agent 的行为才可预测。这套流程在我们多个服务对接中反复验证过，建议从下一个新对接开始就照此执行。
