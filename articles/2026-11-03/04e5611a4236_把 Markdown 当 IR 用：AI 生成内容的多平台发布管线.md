## 背景

用 Agent 产出内容时，输出基本都是 Markdown。但 Markdown 是一个"家族"，不是一种格式：GFM、CommonMark、各家方言互不兼容。而真正的交付对象——公众号、知乎、掘金、Notion、静态站——各自接受的子集差别很大。我们团队现在的做法是把 Markdown 当成管线里的 IR（中间表示）：AI 只负责生成，所有格式适配都发生在 AST 层，而不是 prompt 层。

## 问题

最早的方案是每个平台写一份 prompt，让模型"直接输出该平台能用的格式"。踩到的坑：

- 同一内容多份来源，改一处漏一处，没有单一事实源；
- 模型对平台方言的记忆不可靠，经常混入原生 HTML、脚注、任务列表这些不兼容语法；
- 用正则做后处理，反复误伤围栏代码块里的 `*` 和 `<`。

核心矛盾是：格式决策散落在生成端和发布端，没人对最终格式负责。

## 做法

**1. 定方言契约。** 先写一页"允许的 Markdown 子集"：标题层级、列表、表格、围栏代码块、图片引用；明确禁用原生 HTML、脚注、任务列表。把这份契约放进 Agent 的 system prompt（在 OpenClaw 里做成 skill 的一部分），从源头约束，而不是靠事后清洗。

**2. 归一化。** 用 `remark-parse` 解析成 mdast，跑几个自写插件：CJK 与西文之间补空格、统一段落换行策略、图片 URL 重写为自有 OSS 地址。所有操作都在 AST 上做，纯函数、可单测。

**3. 按平台 profile 转换。** 每个目标平台一份 YAML profile：允许/拒绝的节点类型、节点映射（如表格降级为列表）、样式参数。转换器读 profile 后分发给不同渲染端：公众号走 `markdown-it` 渲染内联样式 HTML；掘金/Notion 输出原生 Markdown 或走 blocks API；静态站走 `rehype`。

**4. 发布前 gate。** dry-run 渲染 + 快照对比，出现白名单之外的节点直接报警拦截。

## 踩坑点

- **不要在字符串层做正则。** 围栏代码块内的任何符号都可能被误改，AST 层天然规避这个问题。
- **公众号会剥外部图片和大部分标签。** 图片必须先传素材库再替换 URL，CSS 必须内联，表格在移动端很容易溢出，建议默认降级。
- **换行语义各家不一。** 有的渲染器把单换行当 `<br>`，有的不当。契约里要写死"段落之间空一行"，禁止行尾双空格。
- **Agent 输出会漂移。** 偶尔塞进 HTML 或嵌套强调。我们用 lint 报错回传给 Agent 重写，而不是静默修复——静默修复会让契约名存实亡。

## 可复用建议

- 单一事实源 + target profile，永远不要人工维护多份平台版本。
- 把管线封装成 MCP tool（如 `md.render(target)`），Agent 和人共用同一接口，行为一致。
- 用一批样例文档做 CI：任何插件或 profile 改动，全平台跑一遍快照 diff 再合入。
- 中文排版规则（标点全角、中西文空格）放在归一化层，不要写进 prompt——prompt 是给人改的，代码是给机器跑的。

## 总结

这条管线的本质是把格式决策从模型和人工手里抽出来，变成确定性代码：AI 负责内容，契约负责边界，AST 负责转换，profile 负责平台差异。实现并不复杂，一个下午能搭出骨架，但它省掉的是此后每一次深夜手动调格式的时刻。内容生产越自动化，格式确定性就越值钱。
