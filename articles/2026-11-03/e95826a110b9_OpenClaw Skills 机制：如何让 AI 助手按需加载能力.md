## 背景

做 Agent 的人大多经历过同一个过程：一开始把所有工具说明、操作规程、领域知识全塞进 system prompt。上下文从 2K 涨到 20K，token 账单涨了，模型对关键指令的遵循反而不稳定了——不相关内容越多，真正要用的那部分越容易被稀释。

OpenClaw 的 Skills 机制就是针对这个问题：把一项"能力"封装成独立目录，平时只暴露几十个 token 的元数据，模型判断当前任务相关时才加载完整内容。

## 问题

全量注入 prompt 有三个具体代价：

1. **成本与窗口**：指令文档常驻上下文，多轮会话里反复计费；
2. **能力发现**：模型不知道"什么时候该用什么"，工具再多也等于没有；
3. **维护困难**：改一条 SOP 要重新发布整个 prompt，回滚没有粒度。

## 做法

Skills 的目录结构很简单：

```
skills/
  log-triage/
    SKILL.md        # 必需：元数据 + 正文
    scripts/        # 可选：确定性脚本
    references/     # 可选：长文档
```

SKILL.md 的 frontmatter 只需要 `name` 和 `description` 两个字段。核心在于加载是分三级的：

- **第一级**：启动时只把每个 skill 的 name + description 注入系统提示，单个 skill 也就几十个 token；
- **第二级**：模型判断当前任务命中某个 description，才读取 SKILL.md 正文（步骤、约束、示例）；
- **第三级**：正文引用的 scripts 和 references，执行到那一步才打开。

所以 description 是整个机制的开关，要写成**触发条件**而不是功能清单。反例："日志分析工具，支持 grep、聚合、告警查询"。正例："当用户要求排查线上服务报错、分析异常日志或定位告警根因时使用"。

写完跑几轮真实会话，看日志里 skill 是否在预期时机被触发，这一步不能省。

## 踩坑点

- **description 太泛或太窄**。太泛会抢戏（不该触发时触发），太窄就永远沉默。用"用户会怎么提这个需求"的句式来写。
- **两个 skill 触发条件重叠**。模型会在两者之间摇摆，保持单一职责，宁可合并。
- **把长文档全塞进正文**。第三级加载就失去意义了，超过一屏的内容拆到 references。
- **在 skill 里写死路径或放密钥**。skill 目录会被当作能力分发，敏感信息一律走环境变量，脚本要对输入做校验。
- **不做版本管理**。skill 的变更应该像代码一样走 review，否则排查"为什么行为变了"会很痛苦。

## 可复用建议

- 把 skill 当**运维手册**写：步骤可执行、每步有验证标准，而不是散文。
- 确定性步骤用脚本，判断性步骤用自然语言——别用一大段文字描述一个 awk 能干的事。
- 先沉淀 3~5 个高频技能验证机制，再批量迁移，不要一上来搬整个知识库。
- 维护一个小型评测集（10 条典型请求即可），每次改动后回归验证触发是否正确。

## 总结

Skills 机制的本质是**渐进式披露 + 关注点分离**：元数据负责"被发现"，正文负责"被正确执行"，附属文件负责"按需深读"。对团队来说，它更大的价值是把散落在个人脑子里的 SOP 变成可版本化、可复用的能力单元——这比省 token 重要得多。
