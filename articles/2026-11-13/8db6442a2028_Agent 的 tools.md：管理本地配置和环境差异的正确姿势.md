## 背景

Agent 跑久了会遇到一个尴尬现实：它在不同机器上的表现不一致。笔记本上有 ffmpeg，NAS 上没有；公司网络要走代理，家里直连；开发机的 Python 在 conda 里，服务器上是系统自带。在 OpenClaw 的多机场景下更明显：网关机、树莓派、手机节点，各处可用的工具集都不一样。这些问题不会立刻暴露，往往在 Agent 某次自信地调用一个不存在的工具时才炸出来。

tools.md 的思路很简单：与其指望模型"记住"环境，不如把本机工具的真实状态写成一份结构化文档，Agent 启动时读取，作为行动前的事实依据。和 AGENTS.md 约束"怎么干活"不同，tools.md 约束的是"手上有什么"。

## 问题

没有这份文档时，常见症状有四类：

1. **工具幻觉**：prompt 里提过 yt-dlp，Agent 就默认它存在，实际机器上根本没装。
2. **路径硬编码**：`/Users/xxx/data` 写死在系统提示词里，换机器或换操作系统直接失效。
3. **网络环境差异**：同一份配置，在家直连正常，在公司内网就超时，Agent 完全不知情。
4. **排障盲区**：出问题时你不知道 Agent "眼中"的环境是什么样，只能靠猜。

## 做法

建议分两层维护，职责清晰：

**全局层**（如 `~/.openclaw/workspace/tools.md`）：机器级事实。操作系统、shell、包管理器、常驻服务、是否走代理、GPU 与磁盘余量。只写这台机器独有的东西。

**项目层**（`<repo>/tools.md`）：随仓库走。项目依赖的 CLI、启动命令、端口、外部服务、测试方式。团队共识放这里，进 git。

环境差异用显式小节声明，例如：

```markdown
## 网络
- 默认直连；检测到 `https_proxy` 存在时必须走代理（公司环境）

## 自检
- `command -v ffmpeg` 不存在时，上报并停止相关任务
```

三条原则：

- **只写事实，不写愿望**。"应该装 xxx"没有意义，装好并验证后再写进去。
- **每条尽量可验证**。给 Agent 一条能自己跑的自检命令，让它发现文档与实际不符时主动上报，而不是硬着头皮执行。
- **机器私有内容不进仓库**。绝对路径、账号、本机怪癖放 `tools.local.md`，gitignore 掉。

## 踩坑点

1. **把密钥写进去**。tools.md 会被完整读进上下文，等于明文泄密。只写"从哪个环境变量取"，值本身永远不落盘。
2. **文档腐烂**。装了新工具忘了更新，Agent 按旧文档行动比没有文档更糟。把"更新 tools.md"固化为装完工具的固定动作，再用上面的自检机制兜底。
3. **写得太多**。每个字都占上下文，控制在几十行内；细节写清文件路径，让 Agent 按需再读。
4. **与 MCP 声明重复**。MCP server 已经声明了工具和参数，tools.md 别抄第二遍，只写 MCP 覆盖不到的本地事实，否则两处不一致时 Agent 会困惑。
5. **绝对路径**。统一用 `~` 和项目相对路径，跨平台成本几乎为零。

## 可复用建议

- 把全局 tools.md 纳入 dotfiles，新机器初始化时一并铺好。
- 项目模板里预置一份 tools.md 骨架，降低同事补文档的门槛。
- 定期（或每次大改动后）让 Agent 跑一遍文档里所有自检命令，输出差异清单，人工确认后修订文档。
- 项目层进 git 做版本化，机器层用私有仓库同步。

## 总结

tools.md 的价值不在文件本身，而在于把环境事实从 prompt 里的硬编码，变成可分层、可版本化、可自检的单一事实源。Agent 行为的稳定性，取决于它对环境认知的准确性——这份认知值得你花半小时认真维护。
