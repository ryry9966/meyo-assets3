## 背景

OpenClaw 类 Agent 的长期记忆通常落在 SQLite 或文件存储里，`memory_recall` 是每轮对话前的那次检索：把"用户此刻的问题"映射到历史记忆条目。它高频调用、延迟敏感、召回错了模型就会一本正经地胡说，所以检索方案的选择很关键。

最常见的纠结就是：语义搜索（embedding + 余弦相似度）还是全文搜索（FTS5/BM25）？

## 问题：单腿走路都不行

我们早期全量上了 embedding。中文转述、同义改写的召回确实不错，但很快暴露两类失败：

- **精确 token 丢失**。用户问"那个 ERR_CONN_RESET_1043 报错怎么处理"，向量检索把"网络连接相关经验"排在前面，真正的错误码条目掉到第 7。版本号、文件路径、库名这类强标识词在向量空间里被语义背景稀释。
- **短查询不稳定**。"那个部署脚本"这种三五个字的查询，向量相似度区分度很差。

反过来，纯 FTS 又搜不到"上次部署超时的问题"和"CI 流水线卡住"这类同义表达。结论：两者互补，不是二选一。

## 做法：三段式混合检索

以 SQLite + 本地 `bge-small-zh` 为例：

1. **双路检索**。每条记忆写入时同时产出 FTS5 索引（标题 + 正文）和 embedding 向量。查询时 BM25 取 top10，向量取 top10。
2. **RRF 融合**。`score = Σ 1/(60 + rank)`，两路按排名相加，取 top5 回填。它不需要对齐两边的分数量纲，比加权线性融合省心得多。
3. **元数据过滤**。每条记忆带 `{project, date, type}`，先按 project 过滤再检索，避免 A 项目的经验污染 B 项目。

## 踩坑点

- **FTS5 默认分词器对中文基本无效**。unicode61 会把一整句中文当单个 token，只有整句完全一致才命中。要么换 trigram，要么写入前自己过一遍 jieba 分词再落库。这个坑排了我们半天。
- **记忆条目粒度**。早期把整段对话存成一条，召回回来全是噪声。改成"一条记忆 = 一个事实 + 时间 + 项目"后，precision 明显上来。
- **余弦阈值别照抄英文社区**。中文短句在小模型上相似度普遍偏高，0.75 以下基本是噪音，0.9 又漏召回。拿自己的数据画一遍分布再定。
- **时效性**。三个月前的"临时方案"不该和上周的"最终方案"同权重。我们在 RRF 分数上乘了一个半衰期 30 天的时间衰减系数，简单但有效。

## 可复用建议

- **先 FTS，再向量，最后融合**。FTS 零模型依赖，很多团队 80% 的查询它就能接住，没必要一步到位。
- **维护 20~30 条评测集**：把真实问过的问题 + 应命中的记忆条目记下来，每次调参跑一遍 hit rate，别靠感觉。
- **给 memory_recall 留日志**：记录召回了什么、模型实际引用了哪些。这份数据是后续所有优化的依据。
- **写入端做去重和合并**，检索端的复杂度就省下来了。

## 总结

语义搜索解决"换了说法还能找到"，全文搜索解决"精确 token 一定能找到"。对 memory_recall 这种高频、低延迟、容错低的环节，混合检索 + RRF 是目前性价比最高的方案：两张 SQLite 表加一个 200MB 以内的本地模型就能跑起来。先让它可用，再让它可靠，别指望一步到位的"智能记忆"。
