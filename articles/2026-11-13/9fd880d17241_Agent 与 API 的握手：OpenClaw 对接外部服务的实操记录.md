## 背景

OpenClaw 的内核再强，也只是个会聊天的脑子。真正的生产力来自它能不能"伸手"——查数据、写日历、调内部接口、触发自动化脚本。这一步的工程名词叫 tool use，落地路径主要两条：挂一个 MCP server，或者写一个直接发 HTTP 请求的插件。我们团队最近把几个内部服务接进了 OpenClaw，把过程和踩过的坑整理如下。

## 问题

调通一个 API 只要十分钟，让 agent 稳定、安全地用它是另一回事。典型症状：

- 工具描述含糊，该调 A 接口时调了 B；
- 接口报错返回一堆 HTML，agent 把错误页当正常数据继续推理；
- 写操作被重试，订单建了两条；
- 大 JSON 直接塞进上下文，一轮对话烧掉一半 token；
- 密钥出现在对话记录里，跟着日志一起落盘。

## 做法

我们的接入流程固定成了七步：

1. **盘点能力，拆成单一动作的工具。** `create_ticket` 和 `list_tickets` 分开，不要做一个带 mode 参数的万能接口——模型对工具名的分辨力远好于对枚举参数的分辨力。
2. **优先复用现成 MCP server。** 文件、数据库、浏览器这类通用能力，社区基本都有现成实现，先起一个跑通，再决定要不要自己写。
3. **把 schema 当 prompt 写。** description 里写清单位、时区、取值范围，附一个调用示例。这段文字是模型唯一能"读到"的文档，值得花时间打磨。
4. **密钥走环境变量，最小权限。** token 只给只读或单服务范围，配置放对话可见范围之外，并确认日志不会把 env 原样打出来。
5. **超时、重试、幂等三件套。** 显式设超时；写操作带幂等键；重试用指数退避且封顶两三次；错误返回结构化的 `{ok, error, hint}`，别让原始堆栈进上下文。
6. **裁剪响应。** 列表类接口默认分页加摘要，超阈值只回统计和头部几条，agent 需要时再翻页。
7. **先 dry-run 再放量。** 每个写工具留一个 dry-run 参数，接完先跑只读场景，逐条核对调用日志。

## 踩坑点

- **重试 GET 没事，重试 POST 会出事。** 早期 `create_event` 没加幂等键，一次网络抖动产生了重复日程，之后所有写操作默认带 idempotency key。
- **错误页比报错更危险。** 某网关 5xx 时返回 HTML，agent 拿去解析，输出一本正经的错误结论。现在非 2xx 一律转成结构化错误。
- **描述里漏了时区。** 日历工具没写死 UTC+8，跨天日程全飘。时间参数现在强制 ISO 8601 带时区。
- **工具数量失控。** 一个 server 挂了三十多个工具后，选择准确率明显下降。按业务域拆成多个 server，单个控制在十几个以内。

## 可复用建议

- 读操作与写操作分开注册，写操作默认要求人工确认，宁可多一步。
- 统一错误契约：所有工具返回同一种结构，agent 才能学会"失败后怎么办"。
- 每次调用落一条审计日志：工具名、参数摘要、耗时、结果状态，排障全靠它。
- 接新服务前先问一句：这个动作该不该由 agent 触发？不该触发的不做成工具。

## 总结

对接外部服务，本质是把一套给人用的 API，翻译成 agent 能可靠使用的动词表。工作量的大头不在"调通"，而在 schema 打磨、错误契约和边界控制。把这三件事做扎实，OpenClaw 才算真正握上了手。
