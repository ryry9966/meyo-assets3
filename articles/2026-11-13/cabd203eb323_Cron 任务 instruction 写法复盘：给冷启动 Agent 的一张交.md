## 背景

OpenClaw 的 cron 任务本质很简单：到点唤醒一个**全新的隔离会话**，把 instruction 塞进去，让 agent 跑完逻辑，再把结果投递到指定 channel。它不是"定时提醒"，而是"定时冷启动的一次性 agent 运行"。

这个认知差异决定了 instruction 的写法。很多任务翻车，不是 cron 配错了，而是 instruction 被当成了给一个"有记忆的同事"的口头备注。

## 问题

我最早写的任务大概是这样："每天早上整理一下昨天的消息，有重要的发给我。"实际跑起来三种翻法：

- agent 不知道"昨天的消息"存在哪，自己编了个搜索路径；
- 没事发生的日子也发一条"今天没有重要消息"；
- 偶尔自由发挥，输出一大段没人看完的总结。

问题的根源：cron 会话没有主对话的上下文、没有昨天的记忆、没有默契，instruction 是它唯一的世界观。

## 做法：四段式模板

写一条 cron instruction，我现在的固定结构是：

1. **目标一句话**：这次运行要产出什么，一句话说死。
2. **数据来源**：明确工具、MCP server、文件路径。路径写全，不要写"工作区里那个文件"。
3. **判断逻辑**：什么条件下播报、什么条件下保持沉默。这是最常被省略、也最影响体验的一段。
4. **输出与投递**：发到哪个 channel、格式约束（几行以内、要不要列表）、失败时怎么办。

一个实际的简化示例：

```
读取 ~/notes/inbox.md 中未标记 done 的条目。
只挑出带 [urgent] 标签的；没有则不发任何消息。
有则发送：每条一行，格式为「条目名 — 建议动作」，总长不超过 5 行。
若文件不存在，发送一条"任务文件缺失"的简短提示。
```

时间处理上，避免写"今天"这种模糊词：要么在 instruction 开头让 agent 先确认当前时间，要么把时间职责完全交给 cron 表达式，instruction 只描述相对逻辑。

## 踩坑点

- **依赖对话记忆**："继续上次那个"在冷启动会话里等于零。跨任务的状态写到 workspace 文件，instruction 里写清读写路径。
- **没有沉默条件**：空跑也发消息，一周后你会亲手关掉这个任务。
- **时区错位**：cron 表达式按网关所在时区执行，服务器在 UTC 时，"早上八点"可能不是你以为的八点。
- **不约束输出格式**：agent 默认爱写长文，定时消息尤其要短，否则通知价值归零。
- **把密钥写进 instruction**：任务描述会留在任务列表里，引用配置项或环境变量即可。
- **失败静默**：任务挂了却没有任何通知，你会在两周后才发现它早就没在跑。

## 可复用建议

- **先手动触发，再上线**：调好 instruction 后先立即运行一两次，看输出稳定了再挂 cron。
- **沉默是默认，播报是例外**：判断逻辑按这个优先级设计，噪音会少一半。
- **状态走文件，不走对话**：文件是 cron 会话之间唯一的可靠记忆介质。
- **一条任务只做一件事**：复杂逻辑拆成多个小任务，别堆一条巨型 prompt。
- **失败必须可见**：宁可收到一条"出错了"，也不要静默成功。

## 总结

写 cron instruction 的心智模型：你在给一个能力很强但每次都失忆的值班员写交接便签。它没有上下文、没有默契，只有这张纸。把目标、数据来源、判断条件、输出投递四件事写清楚，定时任务就从"玄学"变成"工程"。如果你的某个 cron 一直在乱跑，先别调参数，回头重读一遍那张便签——大概率是它没写完。
