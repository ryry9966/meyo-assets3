## 背景

我们团队有几个跑在 OpenClaw 上的自动化任务：定时抓数据、跑批处理、触发 agent 做巡检。跑久了发现问题——任务都在正常执行，但"到底发生了什么"没人说得清。日报靠人肉翻日志拼出来，写的人烦，看的人基本是略过。

信息其实都在，缺的是一条从原始日志到可读报告的固定流水线。这篇帖记录我们搭的这套东西，思路简单，但踩的坑值得说。

## 问题

直接让 LLM 读原始日志生成日报，是最容易想到、也最先要排除的方案：

- 日志量大，token 成本高，上下文塞不下；
- 数字靠模型"读"出来，幻觉风险直接进报告；
- 输出格式不稳定，今天一段散文，明天一个表格。

日报的本质是"事实 + 叙述"。事实必须确定性产出，叙述才能交给模型。

## 做法

流水线分四步，由 OpenClaw 定时任务串联：

1. **采集归一**：各数据源（服务日志、agent 运行记录、任务执行结果）统一 dump 成 JSONL，每条带 source、level、timestamp 和关键字段。格式不齐的打上 raw 标记，进"未解析"桶。
2. **结构化聚合**：纯代码完成，不经过模型。按错误类型分类计数、统计任务成功率、提取关键事件（部署、告警、超时）。产出一个固定 schema 的中间 JSON，所有数字在这里算死。
3. **模型叙述**：LLM 的输入是聚合后的 JSON，不是原始日志。输出同样走 JSON schema（标题、要点、异常说明、风险提示），再渲染成 Markdown 模板。模型只负责把数字"说成人话"和给归因建议，不允许产生任何新数字。
4. **推送与留档**：渲染结果通过插件 webhook 推到群里，中间 JSON 和最终 Markdown 按日期落盘。报告里每个数字附溯源链接，指向原始日志片段。溯源查询我们顺手封成了只读 MCP 工具，日报之外随时让 agent 下钻查证。

## 踩坑点

- **时区**：cron 定在 00:05，日志时间戳是 UTC，第一版跨天数据对不齐。统一按业务时区划统计窗口，采集时做转换。
- **schema 漂移**：上游改了一次日志格式，解析器静默失败，日报连着几天只有一半数据。加了兜底：未解析占比超过 5% 就在报告头部标红。别让流水线安静地烂掉。
- **流水线自身失败**：日报挂了没人发现，比没有日报更糟。生成失败时推送一条降级消息（"今日日报生成失败，原因 X"），并保留重跑入口——中间 JSON 落盘的意义就在这，重渲染不用重新采集。
- **模型自由发挥**：早期 prompt 没约束死，模型会补一句"今日共处理 XX 条"，数是它自己算的。改成 schema 校验，字段缺失或类型不对就重试，两次不过降级为纯模板输出。

## 可复用建议

- 严格分开"事实层"和"叙述层"，这是整条流水线能稳住的核心。
- 中间产物用带版本的 JSON schema 固化，它既是模型输入，也是渲染输入，还是重跑缓存。
- 日报应该是无聊的：结构固定、风格稳定、数字可溯源，比写得花哨重要得多。
- 接新数据源只改采集和聚合层，叙述层不动。

## 总结

这套东西没什么高级技巧，本质是把"人肉看日志写日报"拆成确定性管道，加一段受约束的模型调用。上线后最大的收益不是省了写日报的时间，而是日报数字终于和日志对得上，大家开始真的看它了。如果你的 agent 和定时任务也在持续产出日志，建议先从最小闭环做起：一个数据源、一张固定模板、一条推送通道，跑稳了再扩。
