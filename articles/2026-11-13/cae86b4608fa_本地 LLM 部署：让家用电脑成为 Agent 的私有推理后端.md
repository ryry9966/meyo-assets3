## 背景

做 Agent 和自动化的同学大多有两个诉求：一是日志、私人文档、内部代码这类内容不便发给云端 API；二是想要一个不依赖网络、不计次收费的推理后端，用来跑批量脚本和本地 MCP 工具链。把模型搬回家用电脑，本质上是把推理服务当成一项本地基础设施来运维，而不是追新模型评测。

## 问题

实际动手时通常卡在三件事：

1. 硬件账算不清：显存到底够跑多大的模型？
2. 技术栈选型多：Ollama、llama.cpp、vLLM、LM Studio 各适合什么场景？
3. 接入 Agent 后表现判若两模：工具调用成功率低，长上下文被悄悄截断。

## 做法

**第一步：算显存账。** 权重不是全部，KV cache 也吃显存。经验值：7B 模型 Q4 量化约需 5–6GB，14B 约 9–10GB，32B 约 20GB 以上，再预留 2–4GB 给上下文。12GB 显存跑 14B Q4 是比较稳的起点；纯 CPU 也能跑，但只适合批处理，不适合交互式 Agent。

**第二步：选推理栈。** 想省事用 Ollama，一条命令起服务，自带 OpenAI 兼容接口；想精细控制参数和量化用 llama.cpp；显存充足、追求并发吞吐用 vLLM。建议从 Ollama 起步，遇到瓶颈再迁——接口兼容，迁移成本几乎为零。

**第三步：选模型。** 优先选官方支持 tool calling 的 instruct 模型，量化取 Q4_K_M 这个甜点位。再往下压，指令跟随和 JSON 输出稳定性会明显劣化，而工具调用恰恰最吃这块能力。

**第四步：接入 Agent。** 把 OpenClaw（或任意 Agent 框架）的 base_url 指到本地端点，模型名填本地标签即可。本地 MCP server + 本地模型，可以组成一条完全不外发的自动化链路，这是纯云端方案给不了的。

## 踩坑点

- **上下文默认值偏小。** Ollama 默认上下文长度很小，Agent 长对话会被静默截断，表现为"模型忘了前文"。务必显式设置上下文参数，并把这部分显存算进预算。
- **聊天能用 ≠ 工具能用。** 很多本地模型闲聊流畅，生成工具调用时 JSON 却不稳定。升级模型或推理栈后，用固定的冒烟用例集回归测试，别只看聊天体验。
- **笔记本别硬撑。** 移动端 GPU 有功耗墙，长时间推理会降频掉速；Windows 的显存共享机制也会造成"看着够用、实际 OOM"。
- **别忘嵌入模型。** 做本地 RAG 需要单独跑一个嵌入模型，它很小，但端口和内存要一起规划。
- **别追榜单。** 榜单分高不代表你的工作流能跑通，用真实任务做小规模评测再定版。

## 可复用建议

- 把模型清单、量化格式、上下文参数写成配置文件进版本库，换机器一键复现。
- 统一走 OpenAI 兼容协议，后端可在 Ollama / llama.cpp / vLLM 之间随时切换。
- 维护一套 10–20 条的工具调用冒烟用例，每次升级后跑一遍。
- 混合路由：隐私敏感和 routine 任务走本地，复杂推理走云端，按任务类型分流而不是二选一。
- 记录 tokens/sec 和失败率，用数据决定哪些任务值得本地化。

## 总结

家用电脑跑大模型，如今是工程问题而非玄学：显存账算清楚，选 Q4 档的主流 instruct 模型，用 OpenAI 兼容接口接进 Agent，再用固定用例守住工具调用质量。做到这四点，本地推理就是一个可靠的私有后端，而不是玩具。
