## 背景

让 Agent 跑过 shell 的人，大概率经历过那个瞬间：它回一句「我已经帮你清理完了」，你的手就开始摸备份目录。但真正的问题从来不是「模型够不够聪明」，而是**系统有没有把单次错误的爆炸半径限制住**。OpenClaw 在这块的设计思路值得展开讲一遍，因为它决定了你敢不敢让 Agent 做批量文件操作。

## 问题

Agent 误删文件的典型路径有这么几条：

- **路径误解**：模型对相对路径的假设错了，或者自己拼出了一个看起来合理但实际指向别处的绝对路径；
- **变量展开**：`rm -rf "$TMP_DIR/"` 里变量恰好为空，命令退化成了删除根下的某个目录；
- **权限过大**：Agent 进程和宿主同用户运行，能读能写的范围等于你自己；
- **旁路**：第三方 MCP 工具或插件绕过了你对内置工具的所有假设。

单靠提示词约束这些，本质上是在赌概率。

## OpenClaw 的做法：三层约束

**1. 路径层：工作区边界。** 所有文件工具（读、写、编辑、删除）都以 workspace 为根。每次操作前先做路径归一化（realpath），解析结果必须仍在 workspace 内，否则拒绝执行。这条规则顺带处理了 symlink 逃逸——指向工作区外的软链接会在解析阶段暴露。另外删除操作默认不是 unlink，而是移动到工作区内的 trash 目录。

**2. 执行层：进程沙箱。** exec 类工具跑在容器化沙箱里，只挂载 workspace。宿主文件系统、`~/.ssh`、环境变量里的凭证，对沙箱内进程不可见。就算 Agent 生成了灾难性命令，它 能碰到的磁盘也只有那一个挂载点。

**3. 行为层：策略闸门。** 匹配破坏性模式的命令（递归删除、批量覆盖等）默认需要确认或直接拦截；每个 Agent/会话可以配置工具白名单；所有工具调用连同参数写进审计日志。

三层的关系是：路径层挡住「去错地方」，执行层挡住「带错工具」，行为层挡住「做错动作」。任何一层失守，下一层兜底。

## 自己验证一遍

安全模型不该靠信仰，建议花五分钟做一次金丝雀测试：

```bash
mkdir -p /tmp/canary-out
echo keep > /tmp/canary-out/keep.txt
echo drop > <workspace>/drop.txt
# 然后对 Agent 说：清理工作区里的临时文件
```

预期结果：工作区外的文件原封不动，`drop.txt` 出现在 trash 里而不是消失，审计日志里能看到这次调用的完整参数。如果你的实测结果不符合预期，先停下来排查配置，再谈自动化。

## 踩坑点

- **图方便挂太多目录**：把 `$HOME` 挂进沙箱，等于亲手拆掉执行层边界，这是最常见的自我破坏；
- **symlink 行为没实测**：不同版本对工作区内软链接的解析策略可能有差异，别靠文档想象，跑一遍上面的金丝雀测试；
- **MCP 工具不自动继承沙箱**：跑在宿主上的 MCP server 能碰到什么，取决于它自己的实现。启用任何第三方插件前，先搞清它的工具面覆盖哪些路径；
- **为效率关闸门**：把确认策略关掉换流畅度，是在把兜底逻辑换成运气；
- **多 Agent 复用同一个 workspace**：一个 Agent 的误操作会影响另一个的上下文，边界从空间上就该分开。

## 可复用建议

- 一个 Agent 一个 workspace，挂载最小化；
- 保留「删除进 trash」的默认行为，不要改成硬删；
- 任何批量自动化上线前，先跑一次金丝雀演练；
- 启用 MCP/插件前审查其工具面，把第三方工具当外部程序对待；
- 头几次真实运行后翻一遍审计日志，确认行为和你预期一致。

## 总结

Agent 不误删文件，不是因为它不会犯错，而是因为系统把「犯错」约束在了可恢复、可回滚、可审计的范围内：路径有边界、执行有隔离、删除可撤销、操作有记录。模型负责干活，sandbox 负责兜底。信任应该交给机制，而不是交给概率。
