# 背景

OpenClaw 的 agent 不是一段固定的 prompt，而是一套由 workspace 文件驱动的体系：`AGENTS.md` 管操作规范，`USER.md` 记用户偏好，而 `SOUL.md` 承担的是"这个 agent 是谁"的部分。很多人装完就跑，agent 能力在线，但表现时好时坏。SOUL.md 就是补齐这一环的开关。

# 问题

没有 SOUL.md 时，常见三类毛病：

1. **人格漂移**：同一个 agent，今天克制、明天话痨，长会话尤其明显；
2. **边界缺失**：删除文件、群发消息、跑安装命令，agent 觉得"用户提过"就直接干；
3. **语气失控**：默认模型的客气腔和你的真实场景（开发、工作、家庭）不匹配。

# 做法

在 workspace 根目录创建 `SOUL.md`，从最小模板起步：

```markdown
# 我是谁
XX 的开发助理：克制、直接、不寒暄。

# 说话方式
- 中文回复，代码与术语保留英文
- 先给结论，再给依据；不确定就说不确定
- 不用感叹号，不自我表扬

# 能力分级
- 直接做：读代码、查资料、写草稿、本地只读命令
- 确认后做：写文件、git push、安装依赖
- 禁止：删除数据、对外发消息、支付相关操作

# 底线
凡涉及"确认后做/禁止"项，先复述操作和影响面，等明确指令再执行。
```

操作节奏：

1. 用上面的模板起步，篇幅控制在 500–800 字；
2. 跑一周，把不顺手的场景记下来，逐步转成条款；
3. 每次修改后重载 workspace / 重开会话验证效果；
4. 放进 git 管理，改动留 diff，方便回滚。

# 踩坑点

- **写成小作文**：几千字的 SOUL 每轮注入，token 成本翻倍，且靠后的规则被稀释。规则要短、可判定。
- **空话没有约束力**："做一个有用的助手"模型根本无法执行。要写成"删除操作前必须复述并等待确认"。
- **只写一遍不够**：长会话后期人格会漂。红线条款建议在 `AGENTS.md` 里同步留一份硬规则，双保险。
- **三个文件职责打架**：SOUL 管"是谁、怎么说、什么不做"，AGENTS 管操作流程，USER 管用户偏好。内容重叠会导致自相矛盾的执行。
- **边界一刀切**：所有操作都要确认，体验崩坏。按风险分级：读/查/草稿直接做，写/删/外发要确认。

# 可复用建议

- **风险分级表是核心**：把"直接做 / 确认后做 / 不做"三列清单写清楚，比任何形容词都管用；
- **多 agent 分身**：不同 channel 可以挂不同 SOUL（工作号克制、生活号松弛），但红线部分保持一致；
- **把翻车案例沉淀成条款**：agent 每越界一次，就回 SOUL.md 加一条对应规则，这是它最有效的迭代方式；
- **定期 review**：模型升级后行为会变，建议按季度过一遍全文。

# 总结

SOUL.md 不是"调调语气"的装饰品，而是 agent 的行为契约。写短、写具体、分级授权、持续迭代，它能把一个"能用"的 agent 变成"稳定可信"的 agent。先从最小模板跑起来，让翻车记录替你写完剩下的部分。
