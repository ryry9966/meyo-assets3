# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

Agent 接上工具之后，问题就从"它能说什么"变成了"它能做什么"。OpenClaw 这类框架里，一个 Agent 可能同时持有 shell、文件系统、若干 MCP server 和插件。权限给多了，它会在你不在场时把事情做到生产环境；给少了，它每一步都停下来问你，最后你闭着眼睛点确认——两种都不可用。

## 问题：两个失败方向

实践中最常见的不是"没控制"，而是控制得不对：

- **过度请示**：每个工具调用都要审批。三天之后审批变成仪式，人开始无脑放行，安全机制名存实亡。
- **过度放权**：默认全开。Agent 读到一篇带注入内容的网页，就"顺手"执行了删除或对外发消息。

两个方向的共同根源是：没有按动作的性质分级，而是按"信不信任这个模型"一刀切。

## 做法：按可逆性 × 影响面分层

先给每个工具调用打两个标签：**是否可逆**，**影响面是否超出你自己的工作区**。然后划四层：

1. **L0 自动执行**：只读、本地、可逆。读文件、检索、沙箱里跑代码。不打扰人，但留审计日志。
2. **L1 静默放行 + 记录**：写操作但限制在工作区内，且一切走 git。Agent 自己干，事后可回滚。
3. **L2 首次确认 + 白名单**：装依赖、跑长脚本、改配置。第一次问，人确认后把"这条具体命令/这个 MCP 工具"加入白名单，周期内不再问。
4. **L3 必问**：不可逆或影响出界的动作——对外发消息、部署、删数据、花钱、改权限。这类没有白名单，每次确认时必须展示 diff 或 dry-run 结果，而不是一个孤零零的"是否执行？"。

落地到 OpenClaw：MCP server 按 read-only / write 拆开挂载，插件声明自己需要的最高层级，审批钩子里强制 L3 带 diff，全量调用写审计日志。

## 踩坑点

- **审批疲劳**：请示频率是成本。一天超过十来次，人就退化成橡皮图章。这时宁可收紧 L2、减少弹窗，也别让人习惯性点"是"。
- **"读"不是无害的**：读外部内容 + 拥有写权限 = 注入风险。规则要写死：来自外部数据源的内容只能影响 L0/L1，永远不能触发 L2/L3。
- **组合越权**：单看每个工具都安全，连起来能外传数据（读密钥 + 能联网）。分层要审"能力组合"，不只是单个工具。
- **会话级授权悄悄变永久**：白名单要有过期时间，定期清一遍。
- **问的方式不对**：只给"是/否"不给上下文的确认毫无意义。看不到 diff 的人类确认，等于没有确认。

## 可复用建议

- **先把事情变得可逆，再谈放权**：一切进 git、先 dry-run、有 staging 环境，大量 L3 会降级成 L1，Agent 的自主空间自然变大。
- **按计划批准确认**：让 Agent 先输出行动计划，人对计划批一次，执行时逐条校验，比每步弹窗体验好且更安全。
- **默认拒绝"不可逆 + 出界"**：这是唯一不该妥协的一条。
- 每月复查一次白名单和审计日志，删掉不再需要的授权。

## 总结

权限边界不是"信不信任模型"的问题，而是每个动作的工程属性问题：可逆吗、出界吗、可验证吗。把这三个问题做成机器可判定的分级规则，让 Agent 在 L0/L1 里放开跑，在 L3 前老老实实停下来——人和 Agent 的分工就稳定了。
