## 背景

自动化任务跑久了会发现一个规律：失败不可怕，可怕的是"成功了，但执行了两次"。

调度器超时重试、Agent 判断失误后自己重来、webhook 至少一次投递、同事手动补跑——在 OpenClaw 这类 Agent + 工具调用的体系里，重复执行不是异常路径，而是常态。MCP 工具、插件、定时任务，每一次"再跑一遍"都是对幂等性的考验。

## 问题

非幂等操作的典型翻车现场：

- 建单工具被重试，工单系统里出现两条一模一样的记录；
- 通知插件重发，群里连刷三遍同样的告警；
- 初始化脚本重跑，把已改好的配置覆盖回旧值；
- Agent 上一轮其实执行成功了，但结果没返回，它判定失败又调了一次工具。

根因相同：**操作的副作用与执行次数成正比**。执行两次，副作用就翻倍。

## 做法

我的习惯是把操作分三类，区别对待：

1. **只读操作**：天然幂等。查询、列表、健康检查，随便重试。
2. **覆盖式操作**：把"做某事"改写成"确保达到某状态"。不是"创建配置"，而是"将配置设置为 X"，执行一次和十次终态相同。文件写入用覆盖而非追加，同理。
3. **追加式操作**：最危险，必须加防重机制：

- **幂等键**：从任务上下文派生确定性 key，如 `任务ID + 步骤名 + 日期窗口`，随调用传给工具；服务端按 key 去重，同一 key 第二次进来直接返回第一次的结果。
- **唯一约束兜底**：数据库层加唯一索引，靠约束挡住并发重复，而不是只靠先查再插。
- **执行台账**：一张记录表存每次调用的 key、状态、结果；重跑前先查台账，已完成就跳过。

设计 MCP 工具时，建议把 `idempotency_key` 作为一等参数暴露，重复 key 返回已有结果而非报错——这点很关键，见下文。

## 踩坑点

- **"先查再插"挡不住并发**。两个 worker 同时查，都发现不存在，然后都插入。查询只是乐观检查，唯一约束或锁才是真兜底。
- **幂等键混入随机性**。每次运行现场生成 UUID 当 key，重试时 key 也变了，等于没防。key 必须来自任务的稳定输入，不能来自 LLM 现场发挥——同一个任务，模型两次的措辞可能完全不同。
- **重复执行返回"已存在"报错**。第二次调用返回冲突错误，Agent 把它当失败，进入重试或升级人工，绕一圈问题还在。正确姿势是返回已存在的资源，或明确的"已完成"信号。
- **任务级幂等 ≠ 步骤级幂等**。三步流程第一步成功、第二步失败，整体重跑时第一步又执行了一遍。长流程要么每步自带幂等键，要么靠台账跳过已完成步骤。
- **删除类任务**：目标不存在时应返回成功——终态已是"不存在"，报错只会触发无意义的重试。

## 可复用建议

- 工具/插件默认走"确保终态"语义，把幂等当默认属性，不是加分项。
- 至少一次投递 + 幂等消费，比追求精确一次现实得多：前者是工程方案，后者多数时候是执念。
- 把"同一任务连续跑两遍，结果是否一致"加入上线前验证清单，与功能测试同级。
- 台账表值得投入：排查"到底执行了几次"时，它比翻日志快得多。

## 总结

幂等性不是让系统"不会重复"，而是让系统"重复了也无所谓"。在 Agent 自动化里，重试、补跑、重触发永远会发生，你能控制的是副作用是否与执行次数解耦。写下一个工具调用前先问自己：这个操作跑两次，会不会出两份结果？会，就先补防重，再上线。
