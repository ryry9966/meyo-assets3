## 背景

在 OpenClaw 这类 agent 环境里，重复执行不是异常，而是常态：定时任务超时重试、模型对一次工具调用的结果拿不准又调一次、webhook 事件重投递、人工手动补跑。网络抖动、网关超时、agent 重新规划，都会让同一段逻辑跑不止一次。

## 问题

一个不幂等的任务，重跑就会翻车。几个典型场景：

- 每天定时把 issue 汇总发到群里，第一次实际成功了但响应超时，重试后群里出现两条一样的消息；
- agent 循环里“创建工单”被调了两次，产生重复工单；
- 插件对同一事件处理两遍，数据被重复写入。

这类问题往往不在代码逻辑本身，而在执行模型：我们默认任务只跑一次，但底层基础设施保证的其实是“至少一次”。

## 做法：四步把任务改成幂等的

**1. 先分类操作。** 读操作天然幂等，不用管。写操作分两种——“增量式”（追加一条记录、发一条消息）和“收敛式”（把某状态设为 X、按唯一键 upsert）。优先把任务改写成收敛式：不是“再发一条通知”，而是“确保群里存在一条今天的汇总”。落库用 upsert 带唯一键，天然防重。

**2. 生成确定性幂等键。** 键必须从任务上下文推导，且在重试之间保持不变，比如 `task_id + 目标对象 + 业务时间窗口`。不能混入时间戳、随机数或 run 实例 ID——重试一次键就变了，防线形同虚设。

**3. 原子登记，不要先查后写。** 幂等键落进一个账本：Redis 的 SETNX，或 SQLite/Postgres 的唯一约束加 INSERT OR IGNORE 都行。关键是用原子操作“抢占”，而不是先 SELECT 再 INSERT——并发触发时两个执行都能通过检查，照样重复。

**4. 写前核验，写后记录。** 对不支持幂等键的第三方接口，用查询代替盲重试：执行前先查目标状态是否已满足（工单是否已存在、消息是否已发出），不满足才动手。执行完把结果连同幂等键写进日志，事后能审计哪些执行被拦下。

## 踩坑点

- **键里混入时间戳或随机数**：每次重试都生成新键，等于没有防重。
- **先查后写的竞态**：并发下检查失效，必须依赖唯一约束、SETNX 这类原子原语。
- **业务窗口与重试窗口错位**：昨天的任务拖到今天重试，按新日期算出新键，隔天重复照样发生。窗口粒度要匹配业务的去重需求。
- **指望“模型不会重复调用”**：agent 超时后重规划、对模糊结果再次确认，都会触发第二次调用。防线必须做在工具/插件层，不能建立在模型行为上。
- **账本无限增长**：给幂等键设 TTL 并定期清理，TTL 要大于最大重试跨度。

## 可复用建议

- 把“生成键 → 原子登记 → 执行 → 记录”封装成一个 helper 或中间件，所有对外写操作强制走它，不要每个插件各写一套。
- 设计 MCP 工具时优先声明式收敛：暴露 `ensure_state` 风格的接口，而不是 `append_item` 风格的增量动作。
- 用重跑测试验证幂等：同一任务连跑两次，外部状态应完全不变。这是最便宜也最有效的回归手段。

## 总结

幂等不是可选的优化项，而是自动化系统的默认设计假设。定时器、agent、webhook 的可靠投递模型都是“至少一次”，重复执行一定会发生。把每个任务当作“可能跑不止一次”来设计，重复就从事故变成了无感。
