## 背景

写自动化任务久了，你会发现一个反直觉的事实：**重复执行不是异常，而是常态**。

定时任务被调度器重试、webhook 因超时被对方重发、Agent 因为工具调用结果不明确而再次尝试、插件在崩溃恢复后重放队列——这些场景下，你几乎不可能拿到“恰好一次”的执行保证。多数基础设施给你的承诺是 at-least-once：至少一次，可能会多，不会更少。

幂等性（idempotency）就是在这个前提下生存的能力：**同一个操作执行一次和执行十次，最终状态一致**。

## 问题

举一个典型的翻车现场：一个每天跑的数据同步脚本，里面有一步“为异常数据创建工单”。某天上游 API 变慢，脚本超时重试，结果同一个异常创建了 5 张重复工单，群里被 @ 了 50 次。

问题不在于重试机制本身，而在于“创建工单”这个写操作没有幂等保护。类似的还有：重复扣款、重复发通知、重复插入记录、状态被回退。这些 bug 在测试环境几乎不会复现——因为测试时没人去掐网线。

## 做法

**1. 先分类，识别危险操作。** 把任务里的步骤过一遍：读操作天然幂等，可以不管；写操作（创建、更新、发消息）逐个标记，这些才是要处理的对象。

**2. 设计幂等键。** 两类来源：
- 自然键：业务上本来就唯一的标识，比如外部单号、`日期 + 资源ID`。同步类任务首选这个。
- 显式键：业务上没有天然唯一性时（比如“用户手动触发的操作”），由调用方生成一个 UUID，重试时携带同一个键。

**3. 用唯一约束兜底，不要“先查后插”。** 这是最关键的一条。先 SELECT 再 INSERT 在并发下一定有竞态窗口，两个进程同时查到“不存在”，然后都插入。正确做法是依赖数据库的唯一索引 + upsert：

```sql
INSERT INTO sync_records (biz_key, status)
VALUES ('20240601-order-8899', 'done')
ON CONFLICT (biz_key) DO NOTHING;
```

冲突即跳过，判断和写入是原子的。

**4. 状态机式判断。** 对更新类操作，先检查当前状态：如果已经是目标状态就直接返回成功。把“重复执行”变成“无效执行”。

**5. 外部副作用单独处理。** 发邮件、调第三方 API 这类动作无法回滚。做法是先把“待执行”落库，执行成功后更新为“已执行”，重试时只处理“待执行”的记录。开关动作落在数据库，而不是落在内存或调用链上。

**6. Agent / MCP 工具的实践。** 给写操作类的工具统一加一个 `task_id` 参数，Agent 重试时复用同一个 `task_id`，工具侧按幂等键判重，重复请求直接返回第一次的结果而不是再执行一遍。把幂等语义写进工具描述里，让模型知道可以安全重试。

## 踩坑点

- **先查后写**：并发下照样重复，唯一约束才是真保险。
- **键的粒度错了**：键太粗（比如全局每天一个）会漏掉本该执行的任务；键太细（每次随机生成）等于没做。键必须对应“一次业务意图”。
- **重试时换了新键**：框架层重试没问题，但自己包一层 retry 时不小心重新生成了键，幂等形同虚设。
- **只保护了远端，忘了本地**：远端判重了，但本地状态每次都覆盖写，照样把好的数据冲掉。
- **判重表无限膨胀**：幂等记录需要 TTL 或归档策略，否则半年后这个表成为新的性能问题。
- **把幂等当事务**：幂等只保证单步操作重复无害，多步骤任务部分成功部分失败，仍然需要补偿逻辑或断点续跑，两者不能互相替代。

## 可复用建议

- 团队约定：所有写操作工具默认接受幂等键，缺了就不合入。
- 验收动作：上线前把任务**连续手动跑两遍**，diff 两轮的产出，有差异就是幂等缺口。
- 监控指标：统计幂等键的冲突/命中率。长期为 0 不一定是好事，可能说明键的设计有问题，重复根本没被拦截到。
- 文档里写明每个工具的幂等语义：“重复调用返回原结果”还是“重复调用报错”，让调用方（包括 Agent）能做出正确的重试决策。

## 总结

幂等性不是让任务“不重复执行”——在 at-least-once 的世界里你做不到这一点——而是让重复执行变得**无害**。它成本很低：一个唯一索引、一个约定好的键、一次双重执行的验证。换来的，是定时任务敢重跑、重试敢放开、Agent 敢自动化的底气。下意识地给每个写操作配上幂等保护，应该成为自动化开发的基本功。
