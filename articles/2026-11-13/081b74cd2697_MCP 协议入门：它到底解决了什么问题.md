## 背景：M×N 的胶水代码困境

在 MCP 出现之前，给 Agent 接外部能力靠的是各家自定义的 function calling 格式。假设有 M 个 Agent 应用和 N 个工具（文件系统、数据库、浏览器、内部 API），理论上要做 M×N 份适配：每个应用为每个工具写一遍 schema、鉴权和调用逻辑。这套东西重复、脆弱，工具方任何格式变更都要逐家同步。

MCP（Model Context Protocol）做的事就是把 M×N 压成 M+N：工具方实现一次 MCP server，任何实现了 MCP client 的 Agent 都能直接用。协议层基于 JSON-RPC 2.0，约定了能力发现（tools/list）、调用（tools/call）、资源读取，以及本地 stdio 和远程 Streamable HTTP 两种传输方式。

## 它具体解决了什么

- **标准化工具发现**：Agent 运行时动态拉取 server 暴露的工具列表和参数 schema，不用硬编码。
- **供需解耦**：写工具的人不需要知道消费方是哪个 Agent，反过来也一样。
- **三类原语分工清晰**：Tools（模型决定何时调用）、Resources（应用控制的数据）、Prompts（用户触发的模板），比“什么都叫 tool”的粗糙抽象更可控。

一个常见误解要先纠正：MCP 不解决鉴权、审计和安全，这些仍然要自己做。

## 最小接入步骤（以 OpenClaw 为例）

1. 先明确一个具体需求，比如“让 Agent 只读访问某个目录”，不要一上来装一堆 server。
2. 选一个成熟 server（官方 filesystem、fetch 都可以），先用 MCP Inspector 单独跑通：`npx @modelcontextprotocol/inspector`，确认工具能列出、能调用。
3. 在 OpenClaw 配置中添加该 server 的 stdio 命令或远程 URL，重启生效。
4. 发一条真实任务，验证 Agent 是否正确选中和调用工具，观察调用参数是否符合预期。

## 踩坑点

- **stdio 路径漂移**：command/args 里的相对路径会随工作目录变化，一律写绝对路径；Windows 上跑 npx 需要包一层 `cmd /c`。
- **工具重名冲突**：多个 server 暴露同名工具时行为不可预期，确认客户端做了 server 前缀隔离。
- **上下文膨胀**：每个工具的 schema 都会注入提示词，挂十几个 server 后 token 消耗明显上升，不用的 server 直接关掉。
- **注入风险**：工具返回内容会进入模型上下文，恶意网页可能借 fetch 类工具诱导 Agent 执行危险操作，写权限工具务必加确认机制。

## 可复用建议

- 按**最小权限**顺序接入：先只读（fetch、只读 filesystem），跑稳了再放开写操作。
- 给内部系统写 MCP server 时，围绕“Agent 要完成的任务”设计工具粒度，不要把 REST 接口一比一搬过来——几十个细碎工具远不如十个语义清晰的工具。
- 保留工具调用日志，出问题能回放定位。
- 本地个人用 stdio，团队共享的 server 走 HTTP 并加鉴权。

## 总结

MCP 不是革命性的 AI 技术，它是一个薄而务实的集成标准，价值在于把重复的胶水层标准化，让工具生态可复用。对 OpenClaw 用户来说，正确的姿势是把它当基础设施用：少而精地挂 server，管好权限和上下文成本，剩下的才交给模型。
