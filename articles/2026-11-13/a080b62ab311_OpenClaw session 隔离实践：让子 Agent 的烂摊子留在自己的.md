## 背景

OpenClaw 的主会话（main session）本质上是一份持续追加的上下文：系统提示、历史消息、每一次工具调用的输入输出都在里面。它是主 Agent 的工作记忆，也是自动化跑久了最容易失控的地方。

跑自动化时我们经常派子 Agent 去干脏活：全库检索、批量读文件、跑一遍脚本、审查某次提交。这些任务的共同点是中间过程很吵——几十次工具调用、大量报错和重试——但最终有用的只有一段结论。

## 不隔离会发生什么

我们最初图省事，让子任务直接跑在主会话里，两周后就撑不住了：

1. **上下文膨胀。** 一次全库检索产生上万 token 的工具输出，全部留在主会话。之后每一轮对话模型都背着这些包袱，注意力被稀释，开始"忘事"，成本也上去了。
2. **噪音带偏行为。** 子任务中途失败的调用、报错信息留在上下文里，后续轮次模型被这些残留带偏，反复走已经验证失败的路径。
3. **行为漂移。** 第二次做类似检索时，主 Agent 会"记得"上次的过程，执行方式悄悄变化，难以复现。

结论：这不是省 token 的问题，是主会话可预测性的问题。

## 我们的隔离做法

1. **子任务一律独立 session。** 派子 Agent 时给它单独的 session，工具调用轨迹写进它自己的会话文件，主会话只接收最终回传。一次性任务用完即弃；长周期任务用 `task-日期-名称` 这类前缀命名，方便在 sessions 目录里追踪。
2. **约定回传契约。** 在子 Agent 的提示词里明确输出格式：一两句结论、涉及的文件路径列表、遗留问题。限制在几百 token 以内，禁止贴工具日志原文。
3. **主会话只吞摘要。** 主 Agent 收到回传后把要点并入自己的上下文，原始子会话留在磁盘上，需要复盘时再去查。
4. **工作目录隔离。** 子 Agent 分配独立工作目录（或沙箱），避免和主进程写同一批文件。

## 踩坑点

- **session 隔离 ≠ 文件隔离。** 早期以为会话分开了文件就不会串，结果两个子 Agent 在同一目录里互相覆盖产出。目录也要分开。
- **回传没管住。** 有一次子 Agent 把整段工具日志当结果传回来，主会话当场被塞爆，隔离白做。回传契约必须写进提示词，不能靠自觉。
- **"复用"的诱惑。** 舍不得丢子 session 想复用上下文，结果把上次的失败路径带进新任务，排查半天才发现是旧记忆污染。一次性任务就让它死。
- **并发覆盖。** 并行派发的子 Agent 写同一个 session 文件，互相覆盖导致轨迹丢失。并发任务必须各自独立 session + 独立目录。
- **子 Agent 自己爆上下文。** 超长任务的子会话也会撑满，返回截断结果。大任务要再切一层，或在子 Agent 内部先做汇总。

## 可复用建议

- 把「子任务 = 独立 session + 独立目录 + 结构化回传」固化为默认约定，写进任务模板。
- 回传契约（字段、长度上限）放进子 Agent 的系统提示，而不是靠对话临时强调。
- 定期扫一遍 sessions 目录的文件体积，异常膨胀基本等于隔离没生效。
- 高频任务用固定 session 命名模板，出问题能快速定位是哪次派发留下的痕迹。

## 总结

session 隔离的核心不是省 token，而是保证主会话上下文始终干净、可预测：子 Agent 的过程噪音留在它自己的会话里，主会话只接收结论。这套约定固化之后，我们长跑自动化的稳定性明显改善——模型不再"忘事"，出了问题也能顺着 session 文件追溯到具体某次子任务。
