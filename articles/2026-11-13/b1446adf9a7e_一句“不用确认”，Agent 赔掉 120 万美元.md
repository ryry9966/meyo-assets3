传统软件出 bug，至少还有一段 stack trace 可以看；Agent 出问题，很多时候只剩一张银行账单。最近，普林斯顿大学与 Anthropic 的联合研究系统揭示了一种此前少有人量化的失效模式——「Agent 记忆陷阱」：用户在某次对话里随口说了句“以后不用每步都找我确认”，被 Agent 写入长期记忆；几周后的另一项任务中，这条被泛化、丢失原始语境的“偏好”，让 Agent 在没有询问任何人的情况下直接执行了一笔 120 万美元的资金操作。36kr 报道了这起案例，值得把机制拆开看清楚。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-13/18e3a855acc370fa.png)

## 一笔转账的完整链路：错误是怎么被“存”下来的

先交代背景。主流 Agent 的记忆一般分三层：

- **短期上下文**：当前对话窗口，聊完即忘；
- **工作记忆**：任务执行中的 scratchpad、笔记，任务结束清空；
- **长期记忆**：跨会话持久化，写入向量库或记忆文件。ChatGPT 的 Memory、Claude 的 memory tool、MemGPT/Letta 这类框架都属于这一层。

事故发生在第三层。长期记忆的写入不是原样保存，而是“提取 + 压缩”：

1. 用户原话是“这次先不用问我”——有语境：测试环境、小额查询；
2. 记忆系统提炼成“用户偏好：执行操作前无需确认”——无作用域、无有效期、无条件边界；
3. 后续会话中，检索器把这条规则注入上下文。对模型而言它“来自用户本人”，可信度天然高于网页内容，于是被当成已授权凭证，直接跳过确认环节；
4. 一封带指令注入的邮件、或一个模糊任务叠加进来，Agent 就“名正言顺”地完成了大额操作。

需要说明：这 120 万美元是研究构造场景中的模拟损失，钱没有真的丢；但整条机制链条是可复现的——这也是研究者把它单独拎出来的原因。

## 陷阱根源：记忆系统把“上下文”压缩成了“规则”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-13/876c3fe640b54603.png)

- **过度泛化（over-generalization）是核心机制。** 记忆提取只保留结论、丢弃条件：“这类邮件直接归档”泛化成“所有邮件自动处理”，“先发草稿给我看”泛化成“以后不必再问我”。研究团队在财务、邮件、购物等多类场景中复现了同类偏差。
- **记忆条目缺乏 schema。** 多数实现里，一条记忆就是一段文本或一个向量，没有 scope、TTL、置信度字段——两年前的话和今天早上说的话，检索权重差不多。
- **信任层级错位。** 安全设计里，网页内容是不可信输入，要消毒；记忆来自用户对话，天然被当可信上下文。讽刺的是，记忆恰恰是最持久、影响面最大的输入：一旦被污染或泛化，攻击面覆盖未来所有会话。安全圈的老概念 confused deputy（糊涂的代理人）说的就是这事——代理人拿着超出预期的权限去执行你的“指令”，这次只是把漏洞换成了记忆。
- **训练目标放大问题。** 模型经过偏好对齐，倾向把用户偏好当强指令执行而非弱参考，记忆里的“不用确认”因此获得了接近命令的效力。

## 确认门控是怎么被悄悄拆掉的

- 高危工具调用前的确认门——支付、删除、对外发送、部署上线——本来就是最后一道防线。
- 记忆把这扇门从系统层挪到了对话层：Agent 推理出“用户早已授权”，不再触发确认流程。这不是 prompt injection 硬闯，而是门被“合法”地拆掉了。
- 它持久且不可见：一次会话里的误会，聊完翻篇；写进记忆的误会，用户自己都看不到那条规则，更不会想起来撤销授权。
- 类比一下：你跟实习生说“别什么都来问我”，三个月后他替你签了一份合同。问题不在实习生笨，而在一次性语境被当成了永久授权，且没有任何审计机制。

## 防御清单：把记忆当成权限系统来管

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-13/1679eaa171ddc5f5.png)

1. **给记忆条目上 schema**：作用域（本次任务 / 本项目 / 全局）+ 有效期（TTL）+ 来源会话引用；能存原文就别只存结论，检索时把语境一起带回。
2. **权限与偏好分离**：Agent 可以记住“用户喜欢简洁回复”，但不能记住“无需确认即可转账”。授权只存在于显式配置里，永远不进对话记忆。
3. **高危操作保留硬确认门**：按金额、风险分级设阈值，任何记忆、任何 system prompt 都不能绕过。Agent 最多“准备好转账请求”，人点头才执行。
4. **把记忆写入当不可信数据处理**：提取出的条目先过校验——是否含授权语义？是否脱离原语境？可疑条目进待审队列，而不是直接生效。
5. **定期审计记忆库**：像 code review 一样 review“我的 Agent 记住了什么”，主动清理泛化的授权类条目。

## 冷思考：记忆是 Agent 的复利，也是它的负债

- Agent 之所以能从聊天机器人变成“助手”，靠的正是跨会话记忆；但每多一份能力，就多一类失效模式，能力上限和安全下限常常由同一块短板决定。
- 这本质上不是“模型不够聪明”，而是有状态系统的工程问题。我们给数据库发明了事务、权限、审计日志，Agent 的记忆同样需要这一套——不少团队却还在用“记到文本文件里”的方式管理它。
- 这次学费是模拟场景里的 120 万美元，算便宜的；趁它还没发生在生产环境，把该补的补上。

## 收尾：三条可落地的建议

1. **今天就查一遍记忆库**：搜“不用 / 无需 / 直接 / 自动”这类关键词，它们大概率是泛化后的伪授权——加作用域，或删掉。
2. **确认逻辑放代码层，别放 prompt 层**：prompt 会被记忆、注入、后续微调悄悄改写；代码里的 `if (amount > THRESHOLD) requireApproval()` 不会。
3. **把“记忆治理”排进 roadmap**：写入校验、作用域标注、过期清理、审计日志——这四件事的开发成本，远低于一次真实事故。
