## 背景

E2E 测试一直是性价比最低的那一层：写起来慢、维护贵、还容易 flaky，团队里通常只有个别人愿意碰。随着 OpenClaw 这类 agent 框架和 MCP 工具链逐渐成熟，"agent 起草测试、人来审"变成一件实际可行的事。过去两个月我把这条流程在两个内部项目上跑通了，记录一下做法和教训。

## 问题

直接让模型"给这个页面写个 E2E"，产出基本不可用，典型问题有三类：

1. **选择器是编的**：class 名、aria-label 看着合理，但页面里根本不存在；
2. **sleep 硬等**：`waitForTimeout(3000)` 满天飞，CI 上随机挂；
3. **断言空洞**：跑完点一遍只 assert URL 没变，测试永远绿，但什么都没验证。

根因是模型只看到代码，没看到真实运行的页面。所以核心思路是：**把"跑浏览器"和"跑测试"做成 MCP 工具交给 agent，让它先验证再落笔**。

## 做法

1. **准备工具**：接一个 Playwright MCP server（navigate / snapshot / click），再把"执行测试并回传输出"封装成一个小插件挂进 OpenClaw。
2. **双 agent 分工**：探索 agent 先走一遍核心路径，输出无障碍树快照和操作序列；编写 agent 只基于这份快照生成测试，不凭记忆猜选择器。
3. **修复闭环**：测试失败时把失败输出喂回编写 agent，**限定最多 3 轮修复**，超过就转人工。
4. **人工 review 作为硬门槛**：生成物走 PR，重点看断言是否真的验证了业务结果，而不是过程是否"跑通"。

## 踩坑点

- **用 accessibility snapshot，别喂原始 DOM**。后者轻松吃掉几十万 token，还让 agent 更容易抄到动态 class。
- **agent 很爱用重试掩盖 flaky**。规范里明确写死：禁止 retry 超过 1 次，flaky 必须查根因。
- **别让 agent 直接写 selector**。中间垫一层 page object，它只调用稳定 API，后续维护成本至少降一半。
- **探索轨迹要落盘存档**，否则下次回归没有参照，探索 agent 等于每次从零开始。

## 可复用建议

- 把团队测试规范写进项目级 prompt 文件（禁 sleep、断言模板、命名约定），agent 的遵守程度比想象中高。
- 从"核心路径 + 高频回归"切入，不要一上来铺全量页面。
- 工具粒度宁小勿大：几个小工具的组合，可靠性远高于一个万能 tool。
- 统计生成测试的**首轮通过率**，这个指标能直接告诉你上下文给得够不够。

## 总结

Agent 写 E2E 的价值不在于"全自动"，而在于把写测试的成本从体力活变成设计护栏。你花在 MCP 工具和规范沉淀上的精力，决定了生成质量的上限。模型只是执行者，工程化的那部分，仍然是你。
