## 背景

Agent 的价值不在“会聊”，而在“能动手”。OpenClaw 里的 agent 要查工单、拉数据、触发构建，最终都落在对外部 API 的真实调用上。我们把这叫“握手”：模型负责决定调什么，适配层负责把这次决定变成一次可靠、可观测的请求。这个握手做不好，agent 就只是个会说话的 demo。

## 问题

实际对接时，坑几乎都不在“调不通”，而在调通之后：

1. 工具描述写得含糊，模型传参靠猜，错一次后面连环错；
2. 原始报错堆栈直接回给模型，模型开始自由发挥，重试逻辑混乱；
3. 写操作没有幂等保护，模型一重试就产生重复工单、重复下单；
4. 密钥写进配置文件，随手就提交进了仓库；
5. 一次返回几十 MB 的 JSON，直接撑爆上下文。

## 做法：四步接好一个服务

**第一步：选接入形态。** 标准协议的服务优先封装成 MCP server，一次写好、多处复用；内部私有接口就写个轻量 tool adapter。判断标准很简单——这个封装会不会被第二个 agent 用到。会，就走 MCP。

**第二步：定义工具边界。** 不要把 REST 端点一对一映射成工具，而是按“意图”拆：叫 `create_ticket`，而不是 `post_api_v2_tickets`。每个参数的 description 认真写清楚格式、单位、必填原因。工具描述就是给模型看的文档，文档质量直接决定调用质量。

**第三步：适配层干脏活。**

- 鉴权从环境变量读，绝不进 prompt、不进会被提交的配置；
- 超时和重试在适配层做，指数退避，模型只看到最终结果；
- 错误归一化，返回 `{ok, error_code, hint}` 结构，`hint` 用一句人话告诉模型下一步该干嘛——换参数、放弃、还是问用户；
- 响应裁剪：只回传模型需要的字段，长列表分页截断。

**第四步：先灰度再放开。** 加 dry-run 模式，写操作默认只打印不执行；每次工具调用记一条结构化日志（入参、出参、耗时、状态码），出问题能回放。

## 踩坑点

- **描述与实现不一致**是最常见的坑：description 说返回列表，实际返回对象，模型会基于错误假设继续推演。改接口先改描述。
- **别让模型管重试**。适配层重试三次仍失败，就返回明确的终态错误；把重试决策交给模型，等于把副作用放大器交给概率。
- **注册工具超过二十个后，选择质量明显下降**。按场景分组、按需加载，别把全家桶一次塞进去。
- **写操作必须带幂等键**，最好由适配层从请求上下文自动生成，别指望模型记得传。

## 可复用的建议

- 一个服务一个 adapter，统一错误结构，新服务照模板抄；
- 工具描述纳入 code review：reviewer 只看 description 就能复述出正确调用方式，才算过关；
- 日志先行：没有调用日志的 agent 对接，等于没有对接；
- 工具 schema 加版本号，破坏性变更走新工具名，别原地改语义。

## 小结

Agent 与 API 的握手，本质是一次工程契约：模型负责决策，适配层负责可靠。把鉴权、重试、裁剪、幂等这些“不性感”的活儿沉到适配层，工具调用成功率会稳定一个量级。OpenClaw 的插件体系已经把接入点留好了，剩下的就是老老实实写工程。
