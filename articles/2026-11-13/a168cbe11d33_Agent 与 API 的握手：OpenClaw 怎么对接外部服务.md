## 背景

跑 Agent 这段时间最大的体会是：模型只负责"想"，真正产生价值的是"手"。OpenClaw 作为常驻的 Agent 网关，能力边界基本取决于它能稳定调用多少外部服务——查工单、发通知、读写数据库、触发构建。这篇帖记录我们把几个内部 HTTP 服务接入 OpenClaw 的过程，聚焦 MCP 封装这条路径。

## 问题

把 API 直接扔给 Agent，会遇到三层问题：

1. **协议层**：每个服务的鉴权方式、分页规则、错误码格式都不一样，模型无法凭空猜。
2. **语义层**：工具描述写得含糊，模型就乱传参，甚至在只读接口上"自作主张"做写操作。
3. **工程层**：超时、限流、幂等，这些传统后端问题在 Agent 场景会被放大——模型会重试、会并发、会变着花样组合调用。

## 做法

我们采用"薄封装"模式，每个外部服务包成一个独立的 MCP server：

1. **拆接口，不搬接口**。一个服务暴露给 Agent 的工具控制在 5 个以内，命名用动词+宾语（如 `ticket_get`、`ticket_assign`）。内部 API 有 20 个端点，Agent 真正用到的往往只有几个。
2. **鉴权走配置，不进上下文**。API key 放环境变量，server 启动时注入。任何情况下不要让 key 出现在工具描述或返回值里。
3. **返回值做裁剪**。上游 JSON 压成模型友好的结构：只留关键字段，单条超过约 2KB 就截断并附摘要，避免上下文被一次调用撑爆。
4. **错误要"给模型看"**。返回结构化错误：错误码 + 一句人话 + 建议动作，比如 `RATE_LIMITED，请 30 秒后重试`。这比裸堆栈好处理得多。
5. **写操作加闸门**。区分 read / write 两类工具，write 类默认要求人工二次确认，并在 OpenClaw 配置里做工具白名单。
6. **先 dry-run 再上线**。给每个 MCP server 加了 `--dry-run` 标志：只记录"本应发出的请求"而不真正执行，跑两天确认调用模式没问题再放开。

## 踩坑点

- **分页接口裸奔**：模型为了"看全"疯狂翻页，一次任务烧掉几十次调用。改成工具参数里强制 `limit` 上限。
- **非幂等写操作被重试**：网络抖动导致重复建单。现在所有 create 类工具都带幂等键，重试返回同一结果。
- **长任务同步死等**：一个导出任务要跑 3 分钟，Agent 干等到超时。改成提交任务返回 job_id，另配一个 `job_status` 工具轮询。
- **错误信息太"诚实"**：把上游堆栈原样返回，模型开始试图"读懂"并修复上游服务……错误信息只保留可行动的部分。

## 可复用建议

接入新服务时按这个清单过一遍：**工具数 ≤5 → 鉴权进配置 → 返回值裁剪 → 错误结构化 → write 分离 + 幂等键 → dry-run 观察两天**。按这个顺序，一个服务半天能接完，后续基本不用救火。

## 总结

Agent 对接外部服务，本质不是"多接几个 API"，而是替模型设计一套它读得懂、用不错、闯不了祸的接口层。薄封装 + 严格的工具契约 + 可观测的 dry-run，是我们目前验证下来成本最低、最稳的组合。欢迎在评论区交流你们的接入实践。
