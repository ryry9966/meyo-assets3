## 背景

Agent 要真正干活，光靠模型本身不够。查工单、发通知、读数据库，最终都要落到对外部 API 的调用上。OpenClaw 在这里做的事是把模型和工具串起来：模型负责决策，工具负责执行。对接外部服务这件事，看起来只是"配个工具"，实际做起来坑不少。这篇以对接一个内部工单系统（REST API + Bearer token）为例，记录一次完整的对接过程。

## 问题

实际对接中常见的三类问题：

1. **鉴权不统一**：有的 API 用 Bearer token，有的用 API key，还有的要在 header 里塞签名；
2. **模型调用不可靠**：工具描述写得含糊，模型乱传参数、编造字段；
3. **失败处理混乱**：超时、限流、返回体过大，原始报错直接丢给模型，模型开始自由发挥。

## 做法

走 MCP 这条路，步骤如下：

**1. 先手动验证 API。** 用 curl 把要用的几个端点跑通，确认鉴权、参数、返回结构。别直接上来写封装。

**2. 决定工具粒度。** 不要一个工具包所有操作。拆成 `create_ticket`、`list_tickets`、`close_ticket` 三个，每个只做一件事。

**3. 写 MCP server。** 用官方 SDK 起一个 stdio server，把三个端点包成三个 tool。关键是 tool description：写清楚参数含义、单位、必填项。这不是文档，是给模型看的提示词。

**4. 收敛返回体。** API 返回 30 个字段，工具只取模型需要的五六个；列表类接口加默认 limit。

**5. 错误信息翻译成人话。** 404 返回"工单不存在，请先确认 ticket_id 是否来自查询结果"，而不是抛整个响应体。

**6. 注册到 OpenClaw，灰度验证。** 先用简单指令测："帮我查一下今天的工单"，观察参数是否正确，再放开写操作。

## 踩坑点

- **写操作必须考虑幂等**。模型可能重试，`create_ticket` 要么带幂等键，要么让模型先查再建。
- **超时要设**。内部 API 偶尔慢，agent 侧没超时会一直挂着。建议 10–15 秒，超时后返回可读错误。
- **密钥别写进配置文件**。用环境变量注入，MCP server 启动时读取。
- **只读先上**。新工具先只开查询类，观察一段时间再放开写入。

## 可复用建议

- 工具数量控制在个位数以内，宁缺毋滥；
- 所有工具返回统一结构 `{ok, data, message}`，模型解析稳定；
- 高危写操作在 OpenClaw 里配人工审批，点头再执行；
- 每次调用记日志（入参、耗时、结果码），排查"模型为什么这么调"全靠它；
- 封装抽成模板，换一个 API 改三处就能复用。

## 总结

对接外部服务的本质不是"把 API 接进来"，而是"把 API 翻译成模型能稳定使用的工具"。工具描述、返回收敛、错误处理这三件事做到位，调用准确率会明显提升。先手动验证、只读先行、幂等兜底——这套流程后来在对接消息推送和监控告警时直接复用，没有返工。
