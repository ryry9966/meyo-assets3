## 背景

订阅源没有死，只是被算法推荐淹没了。我长期关注几十个博客、周刊和技术论文源，但打开阅读器的次数越来越少——不是不想看，是"未读 800+"的压力让人直接放弃。目标很朴素：每天早上收到一条消息，三百字以内说清"过去 24 小时哪些值得点开"。

## 问题

手工筛选不可扩展；把全文直接丢给 LLM 又贵又不稳定。真正要做的是一条管线：抓取、去重、过滤、摘要、汇总、推送，每一步可独立失败、独立重放。OpenClaw 在这里的角色是**编排者**：定时触发 agent，agent 通过 MCP 工具调用各阶段能力，而不是把所有逻辑塞进一个巨型 prompt。

## 做法

架构分四层：

1. **抓取层**：一个轻量 MCP 工具 `rss_fetch`，支持 ETag/Last-Modified 条件请求，返回解析后的条目列表。feed 源列表放 YAML，进 git 版本化。
2. **状态层**：SQLite 存 guid、链接归一化后的 hash、抓取时间、处理状态。幂等的关键全在这张表。
3. **摘要层**：两段式。第一段对每条新条目输出单行摘要 + 相关性打分（强制 JSON）；第二段只把 score 过阈值的条目合并成日报，按主题分组。
4. **推送层**：一个 `notify` 工具，webhook 出去，接什么渠道都行。

agent 的 system prompt 只写编排约定：调用顺序、失败处理、日报格式。业务逻辑都在工具和 prompt 模板里。

## 踩坑点

- **只有标题的 feed 占多数**。模型只拿到标题就会脑补内容，需要加一步正文抓取（readability 提取）再进摘要。
- **GUID 不可信**。有源改版后 guid 全变，导致整批"新"条目。用 link 归一化 + 标题 hash 做双键去重才稳。
- **一次性塞几百条进模型**，上下文和预算一起爆。分批 map-reduce，批大小 20 条左右，token 消耗可控。
- **幻觉防护**：prompt 里明确"仅基于给定文本，原文未展开就写'未见细节'"，实测比 temperature=0 有效。
- **cron 时区与重复推送**：管线设计成幂等，同一天重跑不会重发已推送的日报。
- **feed 偶发返回 HTML 错误页**，XML 解析失败要重试并告警，不能静默吞掉。

## 可复用建议

- **先落库再处理**。任何阶段崩了都能从断点重放，这比跑得快重要得多。
- **工具保持无状态**，状态全在 SQLite；换模型、换调度器都不影响管线。
- **给摘要 prompt 塞负面样例**（好摘要 vs 编造摘要的对比），输出稳定性明显提升。
- **每周人工抽查 10 条**：摘要对照原文。score 阈值是抽查校出来的，不是拍出来的。

## 总结

管线跑了几个星期，每天一条日报，未读焦虑基本消失。核心经验一句话：LLM 只该出现在"摘要"这一小段，抓取、去重、状态、推送这些脏活交给确定性代码，agent 负责编排。分层的好处是任何一环可替换——以后想加音频转文字源、换推送渠道，只动一层即可。
