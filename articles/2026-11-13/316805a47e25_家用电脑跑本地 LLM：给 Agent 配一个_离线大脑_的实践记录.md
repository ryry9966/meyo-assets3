## 背景

做 Agent 自动化的同学多半纠结过：任务不敏感但量大，走云 API 账单不低；或者本地日志、私有文档根本不方便出网。最近我把日常的摘要、整理、字段抽取类任务切到了本地模型，机器是一台很普通的家用主机：32GB 内存 + RTX 4060Ti 16GB。这篇记录从选型到接入 OpenClaw 工具链的完整过程，重点讲踩坑。

## 问题

本地部署的难点不在"跑起来"，而在"跑得值"：

- 显存、模型尺寸、量化等级、上下文长度四者互相挤压，预算很容易算错；
- Agent 场景对模型的工具调用（function calling）能力要求高，不是所有小模型都靠谱；
- 跑起来之后还得有标准接口，才能喂给 Agent 框架和 MCP 工具。

## 做法

**1. 摸清硬件底牌。** 先确认显存。粗略经验：7B/8B 级别 Q4 量化约占 5–6GB 显存，14B 级别约 10GB 出头，都能全进显存；更大的模型要么量化更狠，要么 CPU+显存混合 offload，速度明显下降。

**2. 选推理运行时。** 日常服务我用 Ollama，部署简单、自带 OpenAI 兼容端点（`/v1/chat/completions`）；llama.cpp 编译版留作调参实验。追求吞吐可以上 vLLM，但家用单卡场景收益有限。

**3. 选模型。** 中文场景主力是 Qwen 系列：Qwen2.5-7B-Instruct Q4 干轻活（摘要、格式化、分类），14B 干重活（多步推理、工具调用规划）。显存紧张可以试 Qwen3-30B-A3B 这类 MoE，激活参数少，部分 offload 到内存后仍有可用速度。

**4. 接入 Agent。** base_url 指到 `http://localhost:11434/v1`，API key 随意填，模型名写 Ollama 里的 tag，OpenClaw 侧就当普通 OpenAI 兼容端点用。MCP 工具的 schema 照常下发，关键是验证模型能稳定输出结构化 tool call。

**5. 用真实负载压测。** 拿自己日常 prompt 跑 20–50 次，看首 token 延迟、吞吐、工具调用成功率，别只信社区跑分。

## 踩坑点

- **上下文是显存杀手**：128K 上下文的 KV cache 能额外吃掉好几个 GB。实际用不到就降，我把 `num_ctx` 压到 16K 后，14B 才稳定不爆。
- **温度太高毁工具调用**：默认 0.7+ 时模型偶尔在 JSON 里加注释或改字段名，Agent 侧解析直接失败。工具调用场景压到 0.1–0.3，立竿见影。
- **量化不是越低越好**：Q3 以下小模型的多步工具调用明显劣化，宁可换小一档的模型用 Q4/Q5。
- **别靠虚拟显存硬撑**：显存溢出到内存后速度掉一个数量级，不如直接换小模型。
- **确认量化版带 tool 模板**：有些社区量化版丢了 chat template 里的工具调用部分，接 Agent 前先发一条带 tools 的请求验证。

## 可复用建议

1. 接口层坚持 OpenAI 兼容格式，本地/云端模型随时互换，Agent 代码零改动；
2. 轻重分离：小模型扛高频轻任务，大模型只接关键节点，省显存也省时间；
3. 把"工具调用成功率"当一等指标，它比通用 benchmark 更能预测 Agent 实际体验；
4. 用 systemd/pm2 把推理服务做成常驻进程并加健康检查，自动化流水线才稳。

## 总结

家用电脑跑本地 LLM 在今天已经是很现实的选项：一张 16GB 显存的卡 + 32GB 内存，足以支撑"轻任务全本地、重任务可切换"的 Agent 工作流。它不会替代云端模型的智力上限，但在隐私、成本、离线可用性上，给自动化实践多了一个可靠的底座。建议从 7B + Ollama 起步先打通工具链，再按真实负载逐步加码。
