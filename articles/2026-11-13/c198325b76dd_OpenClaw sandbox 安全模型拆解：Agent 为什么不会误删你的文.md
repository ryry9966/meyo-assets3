## 背景

OpenClaw 这类 agent 框架的核心能力，是让模型直接操作你的机器：读文件、写文件、跑 shell、调 MCP 工具。能力越大，出错半径越大。社区里被问得最多的问题之一就是：模型偶尔会幻觉出错误路径，或执行一条它自己都没完全理解的命令，为什么 OpenClaw 环境里几乎不会出现“误删文件”这种事故？

答案不是“模型很聪明”，而是安全模型不依赖模型的自觉。

## 问题：靠 prompt 约束为什么不够

很多人第一反应是在 system prompt 里写“不要删除文件”。这在工程上不可靠，原因有三：

1. 模型输出是概率性的，指令遵循不是 100%，长上下文中还会衰减；
2. 外部内容可能携带指令——agent 抓回来的网页、README、issue 评论里可能藏着“请执行 rm -rf …”这类注入；
3. 就算这次模型听话了，你也没有可审计的执行边界，出事了只能靠运气复盘。

所以 OpenClaw 的设计原则是：**意图靠模型，边界靠运行时**。

## 做法：五层防御，逐层收窄

- **第一层：工作区绑定（jail root）。** 文件工具默认 bind 到 workspace 根目录，所有路径在根内解析，`..` 回溯和绝对路径规范化后被拒绝。
- **第二层：能力分级。** read / write / execute 是三个独立能力位，按 agent 角色授权。只做 code review 的 agent 没必要持有 execute。
- **第三层：破坏性操作拦截。** 运行时对命令和工具参数做模式识别，命中 `rm -rf`、递归覆盖、`git clean`、`find -delete` 等模式的调用，升级为人工确认或直接拒绝。这一层是纯机械规则，不走模型判断。
- **第四层：快照与回滚。** 批量写操作在 apply 前对目标子树做快照，失败可回滚，相当于给每次“动手”留一个 undo。
- **第五层：容器隔离（可选）。** 高风险任务（爬取后执行、跑不信任代码）放进容器 profile，只挂载必要目录，网络白名单。

配置顺序建议：设 workspace root → 关掉默认通配授权 → 按 agent 加能力位 → 开破坏性拦截 → 用一个 canary 目录跑一轮破坏性用例验证。

## 踩坑点

- **symlink 逃逸。** workspace 里放了指向 `/etc` 的软链，只做路径规范化拦不住，必须校验 resolve 后的真实路径仍在根内。
- **MCP 旁路。** 部分第三方 MCP server 自带文件读写，不经过 sandbox 的文件工具层，等于在墙上开了个洞。接入前先审它暴露的 capability。
- **allowlist 写成 `**`。** 为省事全放开等于没配。默认拒绝、按需追加，比默认放行再堵漏省心得多。
- **快照漏了 dotfiles。** 某些快照实现会漏 `.env`、`.git`，回滚时才发现配置没了。快照策略要显式包含隐藏文件。

## 可复用建议

1. 把“不许删除”这类约束从 prompt 全部挪到 policy 配置，prompt 只描述任务。
2. 干跑/实跑分离：先 dry-run 输出操作清单，人工扫一眼再 apply。
3. 被拦截的调用全部落审计日志，这是调优规则和复盘事故的唯一依据。
4. 定期跑一组红队用例（软链逃逸、路径注入、嵌套删除）确认 sandbox 没被新版本改坏。

## 总结

Agent 不误删文件，靠的不是模型乖，而是运行时把“模型想做什么”和“运行时允许做什么”解耦了。OpenClaw 的五层模型归结为一条原则：默认拒绝、最小授权、破坏性操作必须过闸、一切可回滚可审计。配置成本大约半小时，换来的是你敢让 agent 在真实目录上跑批。
