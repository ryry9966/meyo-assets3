## 背景

内部服务和几个 Agent 会话每天产生大量日志，过去日报靠人肉翻日志加手写，费时且口径不稳定。OpenClaw 自带 cron 定时任务、工具调用和 IM 推送能力，正好能把"采集—统计—叙述—投递"整条链路串起来。这条流水线在我这里稳定跑了三周，记录一下思路和踩坑。

## 问题

直接"让 Agent 读日志写日报"看起来最省事，实际有三个硬伤：

1. **token 爆炸**：一天几万行日志塞不进上下文，截断后信息随机丢失；
2. **数字不可信**：让模型自己数错误次数，多次运行结果不一致，偶尔还编数；
3. **格式漂移**：无约束时每次生成的结构都不一样，无法按天对比。

## 做法

核心原则一句话：**脚本算数，模型说话**。LLM 只负责把已经算清楚的事实组织成叙述，不参与任何计算。

1. **采集层用脚本，不用 Agent**。cron 触发脚本把各来源日志统一成 jsonline（字段：ts、level、service、msg），落在固定工作区目录。采集没有不确定性，没必要引入模型。
2. **预处理产出"中间产物 JSON"**：按时间窗口（昨天 00:00–24:00，显式传 TZ）过滤，对 error 做模板聚类（数字、ID 替换为占位符后归并），统计各服务错误数和 Top 变化项，附带每类 2–3 条原始样本。这个 JSON 是整条流水线的核心资产。
3. **Agent 阶段只做叙述**：把统计 JSON 和少量样本喂给模型，要求按固定 schema 输出，脚本校验字段完整性；不合格重试一次，仍失败则降级为纯模板渲染。
4. **渲染投递**：渲染成 Markdown，OpenClaw 推送到群里，同时按日期归档到本地目录，方便回溯对比。
5. **监控兜底**：任何一步失败，单独推一条"日报生成失败 + 错误摘要"。静默失败是自动化任务最贵的事故——我吃过连续三天没收到日报、回头才发现 cron 挂了的亏。

## 踩坑点

- **时区**：宿主机 cron 走 UTC，日报窗口错位八小时，排查一晚上，显式指定 TZ 解决；
- **脱敏放在预处理**：日志里的 token、手机号必须在脚本层过滤，不要指望模型"记得别输出"；
- **聚类阈值别太激进**：同一报错文案可能对应不同根因，保留原始样本链接供人核查；
- **prompt 里别写"今天"**：传显式日期参数，否则手动补跑历史日期时全错。

## 可复用建议

- 中间产物 JSON 与渲染解耦：换模型、换模板、加维度都不用动上游；
- 把每个 Agent 任务当函数对待：明确输入文件、输出文件、退出码，出问题能二分定位；
- 从最小可用开始：先只报错误总数和异常服务，跑稳了再加指标；
- 模板和脚本一起进 git，日报格式变更可追溯。

## 总结

这条流水线的价值不在"AI 会写日报"，而在数据管道稳定、口径一致、失败可见。LLM 在其中只占很小的一环——把算清楚的事实讲成人话。动手前先想清楚哪些环节允许不确定性、哪些不允许，边界画对了，自动化才立得住。
