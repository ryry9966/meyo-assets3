## 背景

多数人用 Agent 仍是一问一答：你不开口，它不动。但一个跑在自己机器上的个人助理，理想状态应该有基本的"巡检"能力——RSS 有更新、磁盘快满、某个仓库有新提交，这些事不值得你每天记得去问，却值得它主动看一眼。

OpenClaw 给了一个很轻的机制：HEARTBEAT.md。在工作区根目录（默认 `~/.openclaw/workspace/`）放一个 Markdown 文件，Agent 按固定间隔（默认约 30 分钟，可配置）读一遍，判断这轮心跳有没有活儿：有就干，没有就静默。没有新框架、没有新协议，一个文件加一个定时器。

## 问题

传统方案两头不讨好：

- cron/定时脚本够准时，但没有判断力。"这个异常要不要通知我"这类事，它决定不了。
- 让 LLM 高频自由发挥，成本和噪音又不可控。

HEARTBEAT.md 的思路是：定时器负责唤醒，文件里的任务清单负责约束，Agent 自己的工具（shell、MCP、插件）负责执行。

## 做法

1. 确认工作区路径，新建 `HEARTBEAT.md`。
2. 用 checklist 写任务，每个条目尽量是三段式：**触发条件 + 动作 + 抑制条件**。例如：

```markdown
# Heartbeat tasks
- 检查 RSS 源，与 state/last-rss.txt 对比，有新条目才汇总发我，否则 HEARTBEAT_OK
- df 检查磁盘，使用率 ≥ 85% 才通知并附关键行，否则 HEARTBEAT_OK
- 工作日 9:00–19:00 之外一律 HEARTBEAT_OK
```

3. 间隔在配置里调整：个人巡检 30 分钟够用，监控类可缩短，但要算成本。
4. 多渠道接入时，用文件里的 Target 提示把主动消息定向到指定会话。
5. 跑几天，观察哪些条目触发过频或从不触发，回头改措辞。

`HEARTBEAT_OK` 是关键细节：Agent 判断无事可做时回复这个字面量，OpenClaw 会把它吞掉、不推送给用户。没有它，你每半小时都会收到一条"这轮没什么事"，很快就会把整个机制关掉。

## 踩坑点

- 每次心跳都是一次真实的模型调用，文件越长越贵。写触发条件，不要写背景故事。
- 条件模糊等于没写。"帮我留意服务器状态"不可判定，要写成"X 超过阈值则 Y"。
- 重活别放进心跳。大扫描、长爬虫交给真正的 cron，心跳只做"读结果 + 判断 + 通知"。
- 重复告警比不告警更毁信任。用一个小状态文件记录上次通知内容，"状态没变就不发"要显式写进条目里。
- Agent 主动执行命令意味着更宽的权限面。删除、重启这类动作不要进 HEARTBEAT.md，或至少写清白名单。

## 可复用建议

- 把每个条目当作"最小监控规则"来写：条件、动作、渠道、抑制，四要素齐了再放进去。
- 分层执行：便宜的本检查先跑，LLM 只做判断和汇总，别每轮全量调用工具。
- 按 crontab 的方式维护：每月 review 一次，删掉从未触发的条目。
- 与 MCP/插件组合时，心跳只负责调度与判断，具体能力下沉到工具层，任务文件保持可读。

## 总结

HEARTBEAT.md 没有任何魔法，它只是把"定时"和"判断"接在了一起，用一个谁都会写的 Markdown 文件做契约。真正的门槛在条目的工程质量：条件可判定、动作有边界、通知有抑制。把这三件事做对，Agent 才会从应答机器变成一个安静的、值得信任的值班员。
