# 背景

社区内容运营有个老问题：好帖靠人肉。选题、查资料、成稿、排版、发布，一篇像样的技术帖至少一小时。我们试着用 OpenClaw 搭了一个发帖机器人，目标不是全自动灌水，而是把「起草—审查—发布—回访」这条流水线自动化，人只保留最终审核权。跑了一个月，发了三十多篇，把架构和踩过的坑记录如下。

# 问题定义

动手前先划清边界，机器人要解决四件事：

1. 选题从哪来：社区热帖、置顶 issue、群聊里的高频问题；
2. 草稿质量不稳：LLM 直出的帖子风格飘、爱编参考链接；
3. 发布必须可控：防重复、可回滚、出事能急停；
4. 发完要有闭环：没人看的帖子要能被发现并调整方向。

# 架构与实现

整体流水线：

```
cron 定时触发 → 选题器 → Agent 起草 → 双层审查门
→ 人工确认 → MCP 发布工具 → 反馈采集 → SQLite 状态库
```

几个关键决策：

- 发布不走网页自动化，封装成独立 MCP 工具 `publish_post`，入参带幂等键（`hash(选题ID+日期)`），内部处理重试与退避；
- 全部状态落 SQLite：选题、草稿版本、审查结果、post_id、发布时间、24 小时后的回复/点赞数据；
- 审查门做两层：便宜的规则先行（标题+首段 embedding 余弦相似度 > 0.85 判重、外链白名单、字数下限），规则过了再走一次 LLM rubric 打分，双过才进人工确认队列；
- 前 20 篇强制人工放行，之后只对低分草稿抽查。

# 踩坑实录

**1. 重启即重发。** 第一版没把 `publish_post` 返回的 post_id 落库，进程重启后状态库认为「未发布」，同一篇连发两次。教训：发布工具的返回值必须写库，幂等校验放在工具内部，agent 层不负责去重。

**2. 幻觉参考链接。** 模型会煞有介事地引用「相关讨论」，链接全是编的。解法：prompt 里禁止模型生成任何 URL，引用一律由选题器注入真实链接，模型只能引用、不能构造。

**3. Markdown 塌了。** API 发帖和网页编辑器对换行、嵌套列表、代码块的解析不一致，发出来排版稀碎。解法：发布前用社区同款渲染器本地预渲染一遍，与草稿做 diff，差异超阈值直接打回。

**4. 重试风暴。** 网络超时后 agent 自作主张连环调用发布工具，一分钟发出 5 条重复帖。解法：重试逻辑全部收进 MCP 工具内部（指数退避 + 幂等键），agent 层只拿到 success/failure，不给它重试的想象空间。

**5. 质量漂移。** 跑两周后帖子越来越模板化，开头永远是「今天聊聊」。解法：每周人工抽评打分，把差评原因整理成反例回灌 few-shot，同时定期轮换选题源，避免单一来源主导风格。

# 可复用建议

- 发布动作封装成带幂等键的最小 MCP 工具，别让 agent 直接摸 HTTP；
- agent 无状态化，一切可重放，崩溃不心疼；
- 审查门先规则后模型，成本和延迟都友好；
- 人工确认开关永远保留，别相信任何「全自动」；
- 内容机器人最大的坑不是技术，是质量衰减——反馈回路要和发布逻辑一起设计，而不是事后补。

# 总结

一个月下来，单篇人工成本从约 40 分钟降到 10 分钟，剩下的是审核和选题微调。回头看，架构本身不复杂，难点有两个：一是把「发布」当成数据库操作来设计（幂等、落库、可回滚），二是持续对抗内容质量的缓慢下滑。前者靠工程纪律，后者靠运营介入，缺一不可。欢迎在评论区交流你们的自动化实践。
