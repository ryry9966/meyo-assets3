## 背景

OpenClaw 的 agent 默认靠 heartbeat 醒来——定时扫一遍消息、待办和自动化任务。这套机制简单可靠，但任务一多，“多久醒一次”就成了成本和延迟之间的平衡点。另一边，webhook、网关 hook、MCP 通知这些通道都能把事件“推”给 agent。两种机制怎么混着用，是我们踩了不少坑之后才理清楚的。

## 问题

纯轮询的三个痛点：

1. **空转成本**：每次醒来都走一遍 prompt，哪怕无事可做。OpenClaw 里虽然可以约定心跳回复 `HEARTBEAT_OK` 短路掉消息，但模型调用本身的开销省不掉。
2. **延迟下限由间隔决定**：30 分钟的心跳意味着平均 15 分钟的感知延迟，对“邮件到了提醒我”这类事太慢。
3. **间隔与重叠**：间隔调太短、上一轮还没跑完下一轮又醒了，轻则浪费，重则重复处理。

纯推送也有代价：入口要公网可达且必须鉴权；事件丢了就真丢了，没有兜底；推送处理函数变成关键路径，挂了整条链路就断。

## 做法：推信号，轮扫描

我们的模式一句话：**推送只做“信号”，心跳做“执行”**。

1. **任务分层**：按延迟敏感度分三档——秒级（对话内）、分钟级（推送触发）、容忍半小时以上（心跳兜底）。
2. **推送侧只写状态**：webhook 收到事件 → 验签 → 写入本地 inbox（文件或 SQLite）→ 立即返回。绝不在推送路径里调模型。
3. **心跳侧统一消费**：heartbeat 醒来先查 inbox，有事件就处理；没有就走短路径退出（无事时返回约定的短路 token）。
4. **兜底扫描**：心跳同时充当定时任务的兜底——推送丢了、webhook 挂了，下一轮心跳照样能捡回来。
5. **可观测**：记录唤醒次数、空转率、事件从产生到处理的 p95 延迟，用数据调间隔。

配置示意（字段名以你手头版本为准）：

```json
{
  "heartbeat": { "every": "30m", "quietHours": "23:00-07:00" },
  "push": { "auth": "hmac", "dedupe": true }
}
```

## 踩坑点

- **空转不便宜**：空转率超过 70% 就该拉长间隔，或确认短路路径真的没走完整 prompt。
- **重复消费**：webhook 重试 + 心跳兜底天然产生重复事件，inbox 必须带幂等键去重。
- **重叠唤醒**：心跳加进程锁，上一轮没跑完就跳过本轮，别硬拼并发。
- **夜间推送**：别让 webhook 半夜把 agent 叫醒跑模型。quiet hours 的语义是“延迟到早上”，不是“丢弃”。
- **推送里做重活**：验签、落库之外还想“顺手跑个 agent”，链路就会脆得像纸。重活一律留给心跳。

## 可复用建议

- “推送当信号，轮询当扫帚”——这个模式几乎能套到所有 agent 自动化上。
- 外部事件先落本地状态再决定何时处理；agent 的输入永远从状态读，不从回调参数读，这样随时可以重放和排查。
- 间隔不是全局常量，按任务档位拆开配。
- 上线先跑一周纯轮询，拿到延迟和成本的基线，再逐项把高价值事件改成推送，对照收益，别一步到位。

## 总结

轮询和推送不是二选一。轮询买的是“简单和兜底”，推送买的是“延迟和省 token”。我们的结论：让推送负责叫醒，心跳负责把事做完并兜底，用幂等 inbox 连接两者。改完之后事件延迟从分钟级降到秒级，心跳频率反而能调得更稀——两头都赚，代价只是多一张 inbox 表。
