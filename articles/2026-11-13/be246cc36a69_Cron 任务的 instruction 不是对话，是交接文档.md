## 背景

OpenClaw 的 cron 能力用起来很顺手：写一句 instruction，定个时间，agent 每天自动跑。很多人（包括我自己）最初的写法，是把平时聊天用的 prompt 直接搬过去——"帮我看下昨天的数据有没有异常，有问题告诉我"。手动触发一两次没毛病，挂上 cron 跑三天就开始出状况。

## 问题

根本原因在于：**cron 触发的是一次无人值守的运行**。交互式会话里你可以追问、可以补充上下文、可以中途纠偏；cron 运行里这些都没有。instruction 写得像对话，agent 只能靠猜。典型翻车三种：

1. **跑飞**：指令太开放（"看看数据有没有问题"），agent 自由发挥，装了不该装的包，读了不该读的目录。
2. **静默失败**：工具调用报错后没有失败处理逻辑，任务看似跑完，实际什么都没产出。
3. **重复执行**：没有幂等检查，每次触发都重新推送一遍日报，群里连收三条一模一样的消息。

## 做法

我的做法是把 cron instruction 当成一份**交接文档**来写，而不是聊天消息。结构固定成六段：

```markdown
## 运行上下文
- 以系统当前时间为准，时区 Asia/Shanghai，禁用"昨天"这类相对词
- 工作目录：/data/reports，仅读写该目录及子目录

## 输入
- 读取 daily-YYYYMMDD.csv（YYYYMMDD 用当天日期）
- 调用 MCP 工具 stats_query，参数固定 range=1d

## 步骤
1. 校验文件存在且行数 > 0，否则走失败处理
2. 计算三个指标：总量、环比、异常点（偏离均值 3σ）
3. 结果写入 summary-YYYYMMDD.json，必须含 status 字段

## 成功标准
- summary 文件生成且 status=ok

## 失败处理
- 输入缺失：写 status=missing，不发通知，直接结束
- 工具报错：重试一次，仍失败则写 status=error，经 webhook 发一条含错误摘要的通知

## 边界
- 不安装依赖、不修改任何非输出文件、不发起额外网络请求
```

关键点三个。第一，**所有指代落地成具体路径、具体工具名、具体参数**，"最新的那个文件"在无人值守时是灾难。第二，**失败处理按类型分开写**，哪些重试、哪些跳过、哪些报警，交互时靠人判断的事，这里要提前写死。第三，**副作用前做幂等检查**——写文件、发通知之前，先确认目标是否已存在。

## 踩坑点

- **相对时间**。"昨天"取决于时区和触发时刻，零点前后跑出来的"昨天"未必是你想要的。让 runner 注入日期，或明确时区并要求 agent 先取系统时间。
- **关键约束埋在长文中间**。指令超过半屏后，硬性边界要单独成段放在显眼位置，不要混在叙述里。
- **"有问题告诉我"**。告诉谁？走什么渠道？没写渠道，agent 可能选择在日志里"说"，等于没说。通知渠道和格式都要指定。
- **一个任务塞多个职责**。日报+巡检+清理写在一条 instruction 里，任何一环失败都会污染整体状态，拆成多个 cron 任务各自独立。
- **没做手动演练**。上线前手动触发三五次，重点测失败路径：把输入文件删掉再跑，看它是否按你写的失败处理执行。

## 可复用建议

- 把六段结构做成模板放进仓库，和代码一起做版本管理，instruction 的每次修改都能 diff。
- 输出尽量机器可校验：一个状态文件加 status 字段，比一段自由文本的"总结"可靠得多，也方便上层监控接入。
- 指令控制在一屏内，写不下说明任务拆得不够细。
- 每次踩坑后把对应约束补进模板，让模板长成团队自己的 runbook。

## 总结

Cron instruction 的本质区别只有一句话：它写给一个**不能提问的执行者**。上下文给足、边界划清、失败路径写死、产出可校验，任务就能稳定替你值夜班。写的时候多问一句"如果它现在拿不到这个东西，会怎么办"，大部分翻车都能提前避免。
