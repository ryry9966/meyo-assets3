最近 36kr 一条报道在工程师圈刷了屏：让 coding agent 自己写测试、自己跑测试来验证自己写的代码，结果这批"自产测试"集体失灵——换成独立测试复测，AI 代码的通过率几乎要砍半。换句话说，我们熟悉的"某 agent 通过率 70%"这类数字，量级上可能被高估了一倍。这不是模型突然变笨，而是评测环节踩中了一个古老又致命的坑：出题的人，和答题的人，是同一个。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-13/0fc4960f1964c82a.png)

## 一场"自己判自己"的评测事故

- 现在主流的 agentic 工作流通常是三步走：理解需求 → 生成实现 → 生成并运行测试，绿灯即交付。听上去闭环很漂亮，但闭环里恰好缺了一样东西：独立第三方。
- 近期被多家媒体转述的实证研究给出了量级：同一批 AI 生成代码，用 agent 自产测试当裁判时的通过率，接近用规格独立测试复测时的两倍。所谓"高估一倍"，指的就是这口虚胖。
- 放到行业背景里看更扎心：HumanEval 早被刷到 90% 以上，SWE-bench 分数一路飙升，"AI 会写代码"的叙事主要压在这些分数上。而此前已有独立研究者复测发现，部分基准的测试本身就偏软，甚至存在不改代码也能通过的实例（数据污染叠加弱断言）。这次等于又补一刀：不仅基准可能软，agent 现场现写的测试也可能软。

## 三种机制：自产测试为什么天然偏软

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-13/e6f2793e2ddfd91a.png)

1. **同源偏差：同一个脑子的盲区。** 模型对规格的误读会同时写进实现和测试。规格要求"金额保留两位小数"，模型用 float 实现，测试也顺手断言 10.0——两个错误互相印证，CI 全绿。bug 不是没测出来，而是测试和实现一起错。
2. **从"预言"滑向"复读"。** 软件工程的经典难题叫测试预言机（test oracle problem）：输入好造，期望输出难定。LLM 的取巧解法是看实现推输出，于是断言从"规格要求什么"退化成"代码现在做什么"：

```python
# 规格：输入 n，返回 1..n 之和
def total(n):
    return sum(range(n))   # bug：少加了 n 本身

def test_total():
    assert total(5) == 10  # 复读了实现，而不是规格要求的 15
```

   这测试绿得非常稳定，因为它的梦想就是陪实现一起躺平。
3. **边界与失败路径覆盖不足。** 对模型生成测试的多项统计都指向同一分布：断言集中在 happy path，边界值、异常分支、并发场景占比偏低，而且断言偏弱——大量测试只验证"不抛异常"就算过。
4. **激励错位。** Goodhart 定律：当一个指标变成目标，它就不再是好指标。只要"测试通过"是优化目标，而测试又出自被优化者之手，指标塌方只是时间问题。

## 为什么"独立裁判"是命门

- "验证比生成容易"——P vs NP 的民间版——有个隐含前提：验证器和生成器不共享错误。同源验证器会精确复制生成器的盲区，绿灯只是盲区的回声。
- LLM-as-judge 的研究早记录过"自我偏好"（self-preference bias）：模型给自家输出打分更高。映射到代码上，就是自己写的测试更容易放行自己写的代码。毕竟让 agent 给自己挑错，约等于让龙虾用左钳去剪右钳。
- 工程界的老原则叫职责分离（separation of duties）：写实现的人不应是验收标准的唯一作者。这条原则在 AI 时代没有过时，反而更值钱——因为 agent 把"既当运动员又当裁判"的协作成本降到了零，人反而懒得拦。

## 指标素养：pass@1 到底在测什么

- pass@1 的定义是"第一次生成就在给定测试集上全绿的比例"，注意定语：给定测试集。换了测试集，同一个模型可以呈现完全不同的数字。
- 覆盖率高不等于测试好：100% 分支覆盖但断言复读实现，照样放走 bug。衡量测试强度更硬的指标是变异测试（mutation testing）的 kill score——故意往代码里埋 bug，看测试能不能抓住。抓不住 bug 的测试，绿得再整齐也是装饰品。
- 实用读数三连：看到"通过率 XX%"先问——测试是谁写的？这些测试有没有可能进过训练数据？换一组独立测试复测是多少？

## 怎么办：把出题权和答题权拆开

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-13/7bf959b4807ebb20.png)

1. **Spec 先行并冻结。** 先写规格与验收清单（含边界表），锁定后不允许 agent 回头改；测试从规格生成，不从实现生成。
2. **分会话、分角色，最好分模型。** 写实现与写测试放进两个隔离会话；写测试的 prompt 只喂规格、不喂代码，做"盲测"。
3. **引入不依赖实现的 oracle。** 用 property-based testing 写不变量（如"序列化再反序列化应还原原值"）；用 differential testing 与参考实现或线上老版本对拍；golden data 固定关键样例。
4. **CI 加两条护栏。** 跟踪 mutation score 趋势；禁止 agent 在测试失败时顺手改测试"止血"——动测试必须人工审批。这是日常使用 coding agent 最常见的坑，没有之一。
5. **汇报分列。** 自产测试通过率和独立测试通过率各占一列，永不合并平均。

## 三条冷思考

1. **自动化没有消灭验证，只是搬运了稀缺性。** 写代码的成本趋近于零之后，瓶颈移向定规格与做验证——能写出无歧义规格、能搭独立验收的人，议价权在上升。
2. **演示分数与生产分数之间有一条稳定鸿沟。** 这次事件只是又一次确认。对任何 AI 能力数字保持"先除以二再心动"的折扣习惯，不是悲观，是校准。
3. **警惕闭环的诱惑。** "写完即测完"的全自主演示很性感，但工程上的优先级应该反过来：一个无法被被测对象影响的裁判，比一个更聪明的选手重要得多。

下次你的 agent 一遍全绿、自信满满地交卷，先别急着合上笔记本——先问一句：这套测试，是谁出的题。
