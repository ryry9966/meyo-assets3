## 背景

接云端 API 做自动化很省事，但有几类场景让人不踏实：日志里带隐私数据、批量任务持续烧钱、断网整条链路停摆。把模型搬到本地，配合 OpenClaw 的 Agent 编排和 MCP 工具链，可以让自动化闭环完全离线。这篇帖记录我在一台 32GB 内存 + RTX 4070 TiS（12GB 显存）的家用机上跑 7B~14B 模型的过程。重点不是跑分，而是"能不能稳定干活"。

## 问题

动手前先回答三个实际问题：

1. 我的硬件到底能跑多大的模型，量化到什么档位？
2. 本地模型能否可靠完成 tool calling / MCP 工具调用，而不是频繁幻觉参数？
3. 上下文开多长合适——KV cache 的显存开销经常被忽略。

## 做法

**第一步：算显存预算。** 权重 + KV cache + 系统占用，留 1~1.5GB 余量。粗算：7B 的 Q4_K_M 权重约 4.5GB，8K 上下文的 KV cache 约 1~2GB（取决于是否有 GQA）。我最终落在 7B~9B Q4 档 + 8K 上下文。

**第二步：选运行时。** Ollama 上手快，llama.cpp 控制粒度细，vLLM 吞吐高但显存门槛高。家用单卡场景选 Ollama / llama.cpp，开启 OpenAI 兼容端点即可。

```yaml
provider: local
base_url: http://127.0.0.1:11434/v1
model: qwen2.5:7b-instruct-q4_K_M
```

**第三步：接入 Agent。** OpenClaw 侧把 provider 指向本地端点，优先选对 function calling 支持较好的模型家族（Qwen、Llama 3.1 系实测较稳）。

**第四步：验证 MCP 工具链。** 先只挂 2~3 个只读工具（列文件、查时间、HTTP GET），跑固定测试集统计调用成功率，再逐步放开写操作类工具。

## 踩坑点

- **显存只算权重不算 KV cache。** 一开 16K 上下文直接 OOM。KV cache 随上下文线性增长，长上下文先看显存余量再谈能力。
- **量化档位别贪低。** Q3 以下闲聊还行，做结构化输出和函数调用时参数幻觉明显增多。经验值：工具调用任务至少 Q4_K_M，稳定生产建议 Q5。
- **工具调用模板不统一。** 不同模型家族的 function calling 格式差异很大，用 llama.cpp 时要确认 chat template 带工具标记，否则模型会把工具描述当普通文本读。
- **长上下文等于慢。** prefill 是线性开销，塞 10K tokens 的系统提示，每轮响应都慢一截。Agent 的系统提示要精简，工具描述按需注入。
- **家用机散热是隐藏变量。** 普通机箱风道差，长时间推理降频，吞吐能掉 20% 以上，夏天建议限功率跑。

## 可复用建议

- 先用 Ollama 半小时跑通最小链路验证可行性，再决定是否迁到 llama.cpp 调参。
- 固定一套 20~50 条的测试任务（覆盖工具调用、结构化输出、长文本摘要），每次换模型或量化档位都跑一遍，用数据决策。
- 做本地 + 云端混合路由：隐私任务和高频简单任务走本地，复杂推理走云端 API，一个 fallback 规则就够。
- 模型文件哈希、配置、测试集全部进版本管理，出问题能快速回滚。

## 总结

12GB 显存的家用机已经能承担轻量 Agent 任务，前提是把显存预算、量化档位、上下文长度三笔账算清楚，并用固定测试集验证工具调用质量。本地模型不会取代云端大模型，但在隐私、成本、离线三个维度上是实打实的补充。建议路径：先跑通最小链路，再逐步扩大工具面，别一上来就堆十几个 MCP server。
