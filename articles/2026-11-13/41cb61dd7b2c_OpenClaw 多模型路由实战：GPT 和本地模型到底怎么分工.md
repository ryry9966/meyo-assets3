## 背景

OpenClaw 默认的跑法是"一个主模型包办所有事"：主循环规划、MCP 工具调用、会话压缩、定时任务输出，全走同一个端点。跑一段时间后问题就出来了——全走 GPT，账单随消息量线性上涨；全切本地模型（Ollama/vLLM），多步工具调用的成功率肉眼可见地往下掉。

实际观察下来，Agent 的负载是明显分层的：会话摘要、消息清洗、格式化输出这类"搬运活"，本地 7B~14B 完全够用；而多步规划、长上下文推理、链式工具调用这类"思考活"，目前还是云端大模型稳。路由的价值就是把这两类流量拆开。

## 问题

目标很朴素：不改 skill 代码、失败能兜底、行为可复现。但在 OpenClaw 里落地时有几个现实约束——不同模型的上下文窗口不一样，工具调用协议行为不完全一致，回退发生时用户不该感知到突变。

## 做法

1. **登记两类 provider**。在配置的 models 段里同时挂云端（如 `openai/gpt-4.1`）和本地端点（如 Ollama 起的 `qwen3:14b`），本地走 OpenAI 兼容端点即可。
2. **主 agent 云端为主、本地兜底**。primary 设云端模型，fallback 链设本地模型。这样 API 配额用尽或网络抖动时，会话不至于直接断。
3. **旁路任务定向到本地**。利用 agent 级模型覆盖，把摘要、会话压缩、定时通知生成这类内部任务固定路由到本地模型。这部分流量通常占大头，收益最直接。
4. **隐私敏感的自动化固定本地**。凡是读本地文件、剪贴板、截图的 skill，强制走本地模型，不进回退链。
5. **压上下文阈值**。压缩触发条件按回退链里上下文最短的模型来设，而不是按主力模型。

## 踩坑点

- **"OpenAI 兼容"不等于 function calling 兼容**。本地端点能接上不代表工具调用能用，小模型经常吐出格式坏的 JSON，skill 拿不到参数后表现为"静默失败"。选本地模型时先单独验证工具调用，别看跑分。
- **长会话回退会溢出**。主力 200k 上下文，本地 32k，回退瞬间长会话直接装不下。
- **消费级显卡 prefill 很慢**。长上下文回退到本地，首 token 可能等十几秒，体验比报错还差。回退链里建议垫一层更便宜的云端小模型。
- **中途换模型，风格和记忆会突变**，用户能明显感知。同一条会话里尽量锁定模型。
- **本地模型默认没有视觉和音频能力**，多模态消息别路由过去。

## 可复用建议

- 按"任务类别"路由，别把模型名硬编码进 skill。
- 从自己的会话日志里抽 10~20 条真实任务做回归集，每次调路由跑一遍再上线。
- 本地模型先当 fallback，跑稳了再升级为主力的旁路任务承担者。
- 记录每个路由分支的失败率和 token 花费，没有数据支撑的调优都是猜。

## 总结

多模型路由本质上是分层架构：把"思考"留给云端大模型，把"搬运"交给本地小模型，用 fallback 链保证可用性。先拆流量、再谈省钱；先验证工具调用，再谈替换。
