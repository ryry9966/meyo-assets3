# OpenClaw 的 AGENTS.md：写给 AI 的工作空间使用手册

## 背景

OpenClaw 里每个 agent 都有一个工作空间（默认 `~/.openclaw/workspace`），这是它的“家目录”：文件读写、memory、心跳任务都以这里为根。`AGENTS.md` 就放在这个目录下，每次会话启动时被注入上下文，是 agent 行为的常驻说明。可以粗略分工为：`SOUL.md` 管它是谁，`USER.md` 管你是谁，`AGENTS.md` 管“在这个工作空间里怎么干活”。

## 问题

实际用下来，AGENTS.md 常被写废，典型有三种形态：

- **许愿池式**：“要有条理、要谨慎、要主动”——agent 无从执行；
- **大杂烩式**：把性格、用户偏好、工具说明全塞进去，和 SOUL.md、TOOLS.md 内容打架；
- **超长式**：几百行规则互相稀释，真正关键的几条被淹没。

结果就是“写了但没生效”，然后归因到模型不行。

## 做法

按 onboarding 文档的思路写，四步：

1. **先分工**。性格一句都不用写（那是 SOUL.md 的事）；用户背景交给 USER.md；外部工具和插件的用法说明放 TOOLS.md。AGENTS.md 只保留“操作规则”。
2. **分区写规则**。常用四块：记忆使用（什么时候写 memory、什么时候只留在会话里）、工具约定（跑 bash 前先说明意图、改动文件后汇报 diff）、消息礼仪（什么情况主动通知、回复控制在多长）、安全边界（哪些目录不碰、删除类操作先确认）。
3. **每条规则带触发条件和动作**。写“改动超过 3 个文件时，先列计划等我确认”，不要写“做事要有规划”。规则三要素：条件 + 动作 + 反馈方式。
4. **控制篇幅并验证**。目标几十行以内；改完开一个新会话，直接问“你当前的工作规则有哪些”，看它能否复述，再观察真实行为是否对齐。

## 踩坑点

- **改完不生效**：AGENTS.md 在会话开始时注入，旧会话不会热刷新。调规则务必重开会话再验证。
- **规则没有例外条款**：比如要求“每次都确认”，agent 在批量小改动时也会反复打扰你。给规则留逃生通道：“纯只读操作可跳过确认”。
- **路径越权**：工作空间内的相对路径是安全的，但规则里写死绝对路径，agent 会顺着往外写文件。边界要用目录约束，而不是靠语气词。
- **和 HEARTBEAT.md 打架**：心跳任务同样受 AGENTS.md 约束，“不要主动发消息”这类规则会让定时汇报静默失败，两处要互相照应。
- **只在出问题时才想起它**：AGENTS.md 是纠偏的沉淀层，不是事后补丁堆。

## 可复用建议

- 把 workspace 纳入 git。每次和 agent 纠缠完同一类问题，把纠偏结论固化成一条规则提交进去，形成闭环。
- 每月 review 一次，删掉不再触发、或已被工具默认行为覆盖的规则——陈旧规则和新规则冲突的概率不低。
- 多 agent 部署时每个 agent 有独立工作空间，共享规则抽成一份母版再分发，别靠复制粘贴对齐。

## 总结

AGENTS.md 不是一个更大的 prompt，而是 agent 的行为层配置。写它的标准很简单：短、具体、可验证。你给 AI 的手册越像一份正经的工程文档，它干活就越像一个靠谱的同事。
