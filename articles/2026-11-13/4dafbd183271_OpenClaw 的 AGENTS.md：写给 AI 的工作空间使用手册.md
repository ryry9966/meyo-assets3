## 背景

OpenClaw 的 agent 每次会话启动时，会从工作区加载一组 Markdown 文件拼进上下文。其中 SOUL.md 管人格，USER.md 记用户偏好，而 AGENTS.md 的定位更工程化：它是一份操作手册，告诉 agent 在这个工作区里怎么干活——能用什么工具、执行命令前要确认什么、输出往哪落盘、哪些目录不许碰。

## 问题

没有 AGENTS.md 时，agent 行为全靠模型默认值。实际用下来有三个反复出现的问题：

1. **规矩留不住**。"跑命令前先给我看一眼"口头说了一次，下个会话就忘。
2. **工具调用随意**。想到就 `curl` 拉外网数据、随手 `pip install`，出了问题很难溯源。
3. **多环境不一致**。笔记本和 VPS 各跑一个 gateway，两边行为习惯完全不同。

这些本质上不是模型能力问题，而是缺一份持久的、随工作区走的约定。

## 做法

我的 AGENTS.md 现在约 60 行，分五段：

1. **工具与命令**：优先用哪些命令、禁止哪些（如批量改配置前必须先备份到指定目录）。
2. **安全边界**：非只读操作先列计划等确认；密钥相关目录只读；通过 Telegram/WhatsApp 外发消息时，什么内容可直接发、什么要先问。
3. **消息与输出**：回复长度上限、代码块标注语言、报告类输出统一落到哪个目录。
4. **MCP/插件约定**：接了哪些 server、各自适用场景、冲突时以哪个为准。
5. **维护规则**：告诉 agent 自己——发现本文档与实际不符时，先报告再动手改。

写法上坚持一条：每条规则可执行、可验证。"回复要友好"没用，"单条回复不超过 150 字，除非用户要求展开"才有用。

## 踩坑点

- **写太长**。第一版 200 多行，agent 会"选择性失忆"，中间段落的规则常被忽略。压到 60 行后遵守率明显上升。
- **规则冲突**。SOUL.md 写"简洁"，AGENTS.md 又要求"详细列步骤"，模型只能瞎猜。文档之间应互相引用，不要重复定义。
- **过期内容**。MCP server 换了端口、目录重构了，文档没跟着改，agent 会自信地按旧路径操作。把 AGENTS.md 纳入 git，改工作区结构时顺手过一遍。
- **写愿望不写规则**。"注意安全"不是规则，"删除超过 10 个文件前先列清单"才是。

## 可复用建议

- **分层**：通用规矩放全局工作区，项目特有的放各项目自己的 AGENTS.md，按工作区路径就近生效。
- **把踩坑反向写进去**：agent 犯过的错，修完就固化成一条新规则，这份文档就是你们的"事故复盘合集"。
- **定期规则审计**：让 agent 复述它理解的关键规则，对不上的条目，就是写得含糊的地方。

## 总结

AGENTS.md 的价值不在写得多全，而在于把"和 agent 相处的经验"固化成一份随工作区版本化的资产。先写一版能跑的，再像维护代码一样迭代它，比一开始就追求完美手册务实得多。
