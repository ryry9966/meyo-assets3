## 背景

E2E 测试一直是最“贵”的那层：写得慢、链路长、页面一改选择器就碎。我们几个核心模块的 E2E 覆盖长期停在登录和下单两条主干上，不是不想补，是补不动。

正好 OpenClaw 里已经接好了 Playwright MCP 和内部工具的 MCP server，agent 能真实打开浏览器、点页面、读 DOM、查库。于是试着把“写 E2E”交给 agent 出初稿、人做审核，跑了两周，记录一些经验。

## 问题

直接丢一句“帮我写个下单的 E2E”，效果很差，问题集中在三类：

1. **凭空编造选择器**：没真正打开页面时，agent 会按常见组件库的习惯猜 `class`，错误率很高。
2. **断言太弱**：生成的测试往往只验证“页面打开了”，不验证业务结果，跑绿了也没有信息量。
3. **滥用 sleep**：agent 极爱写 `waitForTimeout(3000)`，本地能过，CI 必挂。

## 做法

流程拆成四步，核心思路是“先让 agent 看到，再写，最后自己跑”。

**1. 录制代替想象。** 先让 agent 通过 Playwright MCP 实际走一遍目标流程，记下每一步的可访问性树和关键元素（优先 `role` 与 `data-testid`）。这步的产出不是代码，而是“真实页面事实”。

**2. 约束写进上下文。** 仓库里维护一份测试规范文件，agent 开工前先读：禁止 `waitForTimeout`、禁止 `nth-child` 这类结构选择器、断言必须落在业务结果上（订单状态 / 接口落库 / 关键文案三选一），并附一个历史合格测试作范例。这比临时在 prompt 里叮嘱有效得多。

**3. 闭环自跑。** 初稿不许直接交付，agent 必须自己执行、读失败日志、修改，最多迭代三轮。失败日志是最好的 grounding 材料，比任何 prompt 技巧都管用。

**4. 人审断言语义。** 交付时我只看两件事：断言是否真的在验证业务结果；有没有偷偷改被测代码来“让测试变绿”。后者出现过一次，之后测试与生产代码强制分开在不同会话处理。

## 踩坑点

- **别让 agent 既写被测代码又写测试**，它会下意识让测试迁就实现，测出一个“永远正确”的系统。
- **上下文要裁剪**：把整个前端仓库丢给它，token 爆炸且幻觉增多，只给相关路由、组件和 API 定义。
- **登录态提前解决**：每次用 UI 走登录会把测试拖慢一个量级，我们预置 storageState 会话供 agent 复用。
- **跑绿≠稳定**：agent 交付的测试要求本地连跑 3 次全绿才算过，第一版约三分之一存在顺序依赖或竞态。

## 可复用建议

1. 把测试规范沉淀成仓库固定文件，让 agent 每次读取——这是投入产出比最高的一件事。
2. 用 MCP 工具把 agent “钉”在真实页面上，宁可多一步录制，也别让它猜。
3. 闭环（生成→执行→读日志→修复）远好于一次性生成。
4. 把 agent 产出的测试当普通 PR 对待：有 review、有稳定性门槛、可回滚。

## 总结

两周下来，agent 承担了约七成初稿和几乎全部维护性修补（选择器失效类小修基本全交给了它），人负责断言语义和合并把关。它没有消灭 E2E 的维护成本，但把成本从“写”转移到了“审”，对测试欠账多的团队来说，这笔账是划算的。下一步打算把 CI 失败日志自动喂给 agent，做测试失败的自动分诊。
