## 背景

在 OpenClaw 社区里，不少人给 Agent 挂了自动发帖能力：定时汇总、RSS 同步、公告推送、插件运行结果回帖。实现路径通常很短——一个 cron 加一段模板渲染，半小时就能跑起来。

但能跑起来和能长期留在社区里是两回事。观察几个跑了自动发的频道，过程高度一致：头一周没人注意，第二周开始有人抱怨刷屏，第三周被折叠或禁言。

## 问题出在哪

把失败案例拆开看，"机器人感"来自三个具体行为，而不是"它是程序"这个事实：

1. **整点触发**：每天 09:00:00 准时发出，秒级不差。真人的发帖时间天然带噪声，这种规律一眼可辨。
2. **突发批量**：一次任务生成 8 条内容，for 循环 40 秒内全部发完，信息流被瞬间占满。
3. **模板复读**：标题句式、开头结尾完全一致，历史记录翻两页就能拼出模板。

这些行为不仅让用户反感，还会撞上平台频控：429、限流、静默丢帖，排查成本比写脚本本身还高。

先说清楚一点：节奏控制的目的不是伪装成人类。Bot 身份该标就标，社区规则该守就守。要解决的是**扰动最小化**——让自动化输出在时间分布和内容密度上，表现得像一个有分寸的维护者。

## 做法

按依赖顺序拆成五步：

**1. 先定配额，再写调度。** 每个频道每天几条、每周上限多少，收进一个中央限流器，而不是散落在各任务里。所有插件、MCP 工具共享同一个配额池，避免三个插件各自"觉得自己只发一条"。

```yaml
pacing:
  daily_quota: 3        # 每频道每日上限
  min_gap_minutes: 45   # 两帖最小间隔
  window: "08:00-22:00" # 允许发帖的时间窗
```

**2. 抖动代替整点。** 目标时间加随机偏移（±30 分钟量级）。偏移量别小于平台的展示粒度，否则等于没抖。

**3. 先排日程，再打散。** 常见的坑是逐条 `randint` 生成间隔，结果随机出了聚集。更稳的做法：按配额生成当日 N 个槽位，加抖动后整体 shuffle，再校验最小间隔。密度均匀，但次序不可预测。

**4. 内容层去重与合并。** 发送前对内容做 hash 加相似度比对，与最近 7 天历史撞车就并进下一篇摘要。能用一条汇总解决的，绝不拆成五条——真人本来就不爱刷屏，这比任何时间抖动都更有效。

**5. 失败退避与静默时段。** 429/5xx 走指数退避并设上限；社区出事（事故公告置顶）时主动暂停定时任务；深夜时段直接不排，而不是指望"没人看见"。

## 踩坑点

- **时区**：服务器 UTC、社区本地 UTC+8，调度器排的"上午十点"实际落在傍晚。所有窗口时间显式带时区。
- **抖动导致重复发送**：调度路径和重试路径都要带幂等键（内容 hash + 目标频道），否则一次网络抖动产出两条一样的帖。
- **为了排查牺牲随机性**：逐条随机难以复现。给每天固定一个 seed，日程可重放，日志里同时记录计划时间与实际时间。
- **把节奏当内容的遮羞布**：排得再优雅，内容是复读机，用户照样屏蔽。节奏控制是下限工程，不是上限。

## 可复用建议

把这套东西做成共享的 pacing-limiter 插件或 MCP 工具，只暴露三个接口：`acquire(channel)`、`release(key)`、`schedule(batch)`。所有自动发帖任务走同一入口，配额、抖动、退避只实现一次。审计日志单独落盘，出问题先看日志再动代码。

## 总结

自动发帖的"机器人感"，本质是调度太规律、密度太集中、内容太重复三件事的叠加。配额先行、加抖动、先排后散、去重合并、退避静默——组合起来不复杂，一个下午能落进现有的 OpenClaw 插件里。记住目标：不是让 Agent 假装是人，而是让它表现得克制、靠谱。这样的自动化，才可能在社区里长期活下来。
