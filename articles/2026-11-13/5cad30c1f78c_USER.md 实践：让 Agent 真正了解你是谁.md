## 背景

用 OpenClaw 这类长期运行的 Agent 一段时间后，你会发现一个尴尬的事实：它记得你做过什么，却不记得你是谁。每次新会话都要重新交代一遍"我在用 Linux""回复用中文""别给我生成 Python"。Memory 解决的是"发生过什么"，而"你是谁"这类稳定事实，一直缺少一个正式的落点。OpenClaw 的 workspace 约定里有 AGENTS.md（怎么干活）、SOUL.md（什么性格），USER.md 正好补上第三块：你是谁。

## 问题

没有用户画像时，Agent 只能靠猜：

- **环境假设错误**：默认给 macOS 路径，而你跑在无桌面的 Debian 上；
- **风格不稳定**：这次极简，下次又写三千字小作文；
- **重复沟通成本**：时区、技术栈、命名习惯，每条渠道、每个插件都要交代一次；
- **越界建议**：不知道你的红线，随手推荐你不碰的方案。

本质是同一个问题：缺少一份结构化、随会话加载的"用户说明书"。

## 做法

在 workspace 根目录放一个 `USER.md`，视角与 AGENTS.md 相反——它描述的不是 Agent 的规则，而是"我"这个用户。

**第一步，只写稳定事实，分五段：**
- 环境与身份：操作系统、时区、语言习惯（中文交流、英文注释）；
- 技术栈：主力语言、部署方式（比如"只写 Go，别推 Python 方案"）；
- 沟通偏好：先结论后细节、代码优先于描述；
- 红线：不自动执行的操作、不碰的目录、不引入的依赖；
- 常用上下文：固定项目路径、常用 MCP 工具。

**第二步，控制体积。** 我压到 40 行以内、约 1KB。它随 system prompt 进上下文，每多一行都是真实 token 成本。

**第三步，接进启动流程。** 在 AGENTS.md 或引导提示里明确一句"会话开始先读 USER.md"，或在 gateway 配置里注入。文件写了没人读，等于没写。

**第四步，进 git。** 它和 `.gitconfig` 一样属于个人配置，改动可追溯，换机器可带走。

## 踩坑点

- **写成日记**。我把"本周三个需求"塞进去过，两周后还在污染上下文。易变信息走 memory/journal，USER.md 只放三个月内不会变的。
- **偏好太虚**。"回复简洁一点"没有约束力，改成"默认不超过 10 行，例外需说明原因"才可执行。
- **与 AGENTS.md 冲突**。两边都规定回复语言，Agent 执行时随机偏向其一。原则：AGENTS.md 管工作方式，USER.md 管用户事实，重叠条目只留一处。
- **塞敏感信息**。这份文件会随请求发给模型服务商，密钥、住址都别放。
- **只写不改**。每两周删一次过期条目，它才持续可信。

## 可复用建议

1. **冷启动技巧**：让 Agent 反过来采访你——"请问我 10 个问题，生成 USER.md 初稿"，比从零写快得多。
2. **分层**：全局一份 USER.md，项目级事实放各仓库的 AGENTS.md，别混。
3. **验证加载**：写完问一句"根据 USER.md，说说你对我的了解"，答对才说明链路通了。
4. **多用户部署**：按用户各挂一份 profile，比共享一份干净得多。

## 总结

USER.md 是个很小的文件，投入半小时，但它把 Agent 与你的关系从"每次重新认识"变成"持续累积的理解"。把它当成你和 Agent 之间的接口契约来维护——像对待 shell rc 一样版本化、定期修剪，它就是整个自动化体系里性价比最高的一块配置。
