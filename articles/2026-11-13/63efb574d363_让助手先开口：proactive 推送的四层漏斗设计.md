## 背景

多数 AI 助手的使用模型是“你问它答”，所有动作都由用户发起。但日常用下来，价值最高的反而是它先开口的时刻：CI 挂了你还没看到告警邮件，它已经把报错摘要和可疑 commit 推给你；你盯的一批单号、库存、域名到期日，状态变化时它主动同步。在 OpenClaw 里这类能力有天然抓手——heartbeat 和 cron 让 agent 定期醒来，配合插件和 MCP 工具检查外部状态，再把值得说的内容推到你的 IM 频道。

## 问题

Proactive 极容易做过头。常见结局有三种：变成垃圾信息源，你开始习惯性忽略它；token 成本失控，每次心跳全量跑一遍工具；或者更糟——它在没有任何确认的情况下替你执行了写操作。主动推送本质上是在消费你的注意力，而这个预算非常小，设计时要当成稀缺资源对待。

## 做法

我们的经验是搭一个四层漏斗：

**1. 触发层。** 三类来源：cron 定时巡检、外部系统 webhook 事件、heartbeat 自查记忆里标记的关注点。这一层以读操作为主，不直接产生通知。

**2. 过滤层。** 原始检查结果不能直接推人。先用规则筛一遍（阈值、状态变化检测、去重窗口），再让模型做一次“值不值得打扰用户”的判断，输出三档：静默记录 / 进日报 / 立即推送。判断标准写进 prompt，例如“仅状态反转或超过用户设定阈值时才立即推送”。

**3. 投递层。** 分级路由：紧急事项走私聊强提醒，日报聚合后每天固定时间发一条，其余写进日志和会话记忆。配置 quiet hours，夜间只允许最高优先级穿透。

**4. 反馈层。** 用户回一句“这种别推我”必须能落地：把偏好持久化到配置，下次过滤层直接引用。没有反馈闭环的 proactive 系统只会越来越烦。

## 踩坑点

- **自激循环**：agent 自己发出的消息被当成新事件再次进入触发层，无限自嗨。给消息打来源标记，处理事件前先判断是否自己产生。
- **去重缺失**：同一问题每小时推一次。用“问题指纹”（服务 + 错误类型）做去重窗口，未恢复不重复推，恢复时补一条收尾。
- **陈旧上下文**：agent 凭几小时前的记忆直接执行写操作。写动作前强制重新拉取状态，且默认走确认或 dry-run。
- **心跳太密**：五分钟一次全量巡检，成本与噪音双杀。巡检分层，重检查低频跑，轻检查高频跑。
- **幂等性**：定时任务重试后重复下单、重复发消息。关键写操作必须带幂等键。

## 可复用建议

先只做“读 + 推”，跑两周积累“什么值得推”的真实样本，再考虑放开任何写操作。过滤判断和巡检执行拆成两次调用，别让一个 prompt 既干活又决定要不要吵你。所有主动行为留审计日志，出问题能回放。宁缺毋滥：日报是兜底，强提醒是奢侈品。

## 总结

Proactive 的目标不是“做得多”，而是“在对的时刻只说必要的话”。触发、过滤、分级、反馈四层中，过滤层决定成败——它把无意义的自动行为挡在用户注意力之外。从 OpenClaw 的 cron / heartbeat 起步，接几个 MCP 工具，先把日报跑稳，再逐步提高即时性，是验证下来比较稳的路径。
