## 背景

OpenClaw 的 agent 任务五花八门：工具调用、结构化抽取、代码生成、长文摘要、兜底对话。全走 GPT 这类云端模型，成本和延迟都扛不住；全走本地模型（Ollama / vLLM 跑 Qwen、DeepSeek 蒸馏版），复杂任务的质量又明显下滑。多模型路由本质上是在回答一个问题：**哪些任务值得为质量付费，哪些任务本地模型已经足够**。

## 问题

我们最初的配置是"全局默认 GPT，个别插件手动切本地"，跑了一段时间后发现：

- 80% 的简单调用（分类、字段抽取、格式化）贡献了 60% 以上的 token 成本；
- 涉及日志和内部数据的关键词仍然流向云端 API，隐私口径说不清；
- 手动切换依赖人的记忆，review 时经常发现某个插件一直跑在贵的模型上。

## 做法 / 步骤

1. **给任务分类打标**。把 agent 内所有 LLM 调用归为四类：轻量判断（分类 / 抽取 / 路由）、工具调用编排、生成类（代码 / 长文）、兜底对话。
2. **在路由层按 tag 分流**。轻量判断和兜底对话走本地模型（我们用 vLLM 部署 32B 级模型），工具编排和代码生成默认 GPT，长文摘要按上下文长度动态选。
3. **入口处打 tag**。用规则匹配（tool 名单、任务模板）为主，加一个本地小模型做意图分类兜底，再交给路由层。
4. **校验 + 升级（escalation）**。本地模型输出先过 JSON Schema 校验，失败就自动升级到 GPT 重试一次。这是整套方案的核心，比"预估难度再路由"可靠得多。
5. **记录路由决策**。每次调用记录模型、耗时、是否升级、token 数，跑两周再回来调阈值。

## 踩坑点

- **本地模型的 function call 格式漂移**：偶发在 JSON 外面包一层自然语言，或字段名大小写不一致。必须强校验 + 剥壳，别假设输出是干净的。
- **升级失控**：早期校验阈值定太严，接近全部流量升级到 GPT，成本比全 GPT 还高。后来给每个会话设了升级次数上限。
- **端到端延迟的错觉**：本地 14B 在消费级显卡上首 token 不慢，但吞吐低，长输出反而比云端 API 慢。路由要按 p95 端到端延迟算，不是看模型参数量。
- **上下文截断是静默的**：本地模型超上下文不会报错，会自己"消化"掉中间内容，摘要任务因此出过丢段事故。入口处先查 token 数。
- **提示词不迁移**：给 GPT 调好的 prompt 直接丢给本地模型，工具调用成功率掉一截。按模型家族各维护一套 prompt，别共用。

## 可复用建议

- 按"**任务类型 × 出错代价**"分流，而不是按个人对模型的偏好。
- 起步阶段别做预测式路由，就用"默认本地 + 校验失败升级"这一招，能覆盖大部分场景。
- 盯三个指标：**升级率、单任务成本、p95 延迟**。升级率长期高于 30%，说明分类边界画错了，回头修 tag。
- 涉及用户隐私的调用直接锁死本地路由，这条和成本无关，是底线。
- prompt 按模型家族分版本管理，和代码一样进仓库、走 review。

## 总结

多模型路由不是一次性的选型问题，而是一个反馈回路：分类 → 校验 → 升级 → 统计 → 调阈值。OpenClaw 的路由层只是提供了挂载点，真正决定成本和质量的是校验策略和升级预算。先跑起来、先有数据，再谈精细化——这个顺序反过来走，基本都是返工。
