## 背景

Agent 的主循环是事件驱动的：没有新消息进来，模型不会自己"醒着"。想让助手具备主动性——定时巡检、到期提醒、清理过期任务——必须引入唤醒机制。常见两条路：轮询（heartbeat，网关按固定间隔拉起 agent）与推送（webhook/事件源主动触发）。OpenClaw 默认走前者：Gateway 按 HEARTBEAT_INTERVAL 定时唤醒 agent，读取 HEARTBEAT.md 检查清单，无事则返回 HEARTBEAT_OK 直接短路，不产生输出。

## 问题

两条路都不是免费的：

- **轮询的代价是持续消耗。** 即使无事可做，每次心跳也是一次真实的模型调用，token 成本与频率成正比；间隔太短烧钱，太长则"主动性"退化成滞后响应。
- **推送的代价是基础设施。** 需要一个可达的入站端点：公网部署还好，跑在家用 NAT 后面的网关得配隧道或反向代理；事件源还要有 webhook 能力，鉴权、重试、幂等全要自己兜。

真正的取舍不在"哪个更先进"，而在事件源是否存在、是否可达、是否值得为它搭一条链路。

## 做法

我的实践是分层混合，规则很简单：

1. **有现成事件源且能打通 → 推送。** GitHub PR、监控告警、日历变更这类，webhook 直接触发 agent，延迟秒级，token 零浪费。
2. **时间驱动与自检类任务 → 心跳。** HEARTBEAT.md 里只写"检查项 + 触发条件"：长任务是否超时、证书是否临期、收件箱是否需要摘要。
3. **心跳兜底推送。** 推送链路会挂（隧道断了、webhook 丢了），心跳清单里加一条"核对最近事件 ID，发现断档就拉一次补偿"，保证最终一致。

关键实现是 HEARTBEAT_OK 短路：心跳 prompt 明确要求"无事可做只返回 HEARTBEAT_OK"，Gateway 识别后丢弃本轮，不进会话、不发消息。没有这个约定，心跳会把主会话塞满噪音。

## 踩坑点

- **抄默认间隔不动。** 30 分钟对巡检合适，对"上午十点提醒"太粗。时间敏感任务后来改用 cron 精确调度，心跳只管模糊巡检。
- **设备休眠导致计时漂移。** 笔记本上的 Gateway 睡眠恢复后，心跳可能堆积或长时间不触发，要决定"错过的心跳"是跳过还是合并，别默认全部补跑。
- **推送端点静默失败。** 隧道断了 webhook 全丢且无任何报错，只能靠心跳对账事件 ID 才能发现断档。
- **心跳清单越写越长。** 每加一条"顺手检查"，成本就线性上涨。把确定性检查（文件存在、端口存活）下沉给脚本，agent 只看脚本结论，并定期删减清单。

## 可复用建议

- 先盘事件源：有现成 webhook 的场景一律推送，别用轮询硬凑。
- 心跳 token 单独统计预算，超支先砍清单，而不是先降频。
- 推送必须带事件 ID 去重、保证幂等；心跳必须可短路。
- 心跳输出默认不落主会话，只在"有话要说"时投递。

## 总结

轮询和推送不是二选一，而是分工：推送负责事件即时性，心跳负责时间确定性和兜底自检。OpenClaw 的 heartbeat + HEARTBEAT_OK + cron 组合基本覆盖了两类需求，剩下要管住的是清单膨胀与静默失败——前者靠定期删减，后者靠对账。主动性的成本不在架构，而在日常维护上的克制。
