## 背景

用 Agent 批量产出技术内容后，真正的开销往往不在生成，而在发布。同一份 Markdown，公众号要转 HTML 且不支持外链，知乎会吞掉部分标签，掘金和静态站基本按 GFM 走，RSS 又是另一套 HTML 子集。手工逐平台调整既容易出错，也塞不进自动化流程。

在 OpenClaw 里我们把这段链路做成了一条管线：Agent 只负责产出一稿规范的 Markdown，后续格式适配全部交给插件化的转换层。这篇帖记录设计思路和踩过的坑。

## 问题

归纳下来三类：

1. **方言差异**：表格、脚注、任务列表、公式、Mermaid，各家支持程度参差。
2. **AI 输出的非确定性**：同一主题两次生成，标题层级、代码块语言标注（sh/bash/shell 混用）、列表缩进都可能不一致，下游转换会放大这些问题。
3. **资源策略**：图片外链在不少平台被防盗链或二次转存，链接和图片必须单独处理。

## 做法

核心原则：**以 AST 为枢纽，不拿字符串做转换。**

1. **归一化（ingest lint）**。Agent 产出先过 lint：剥离“以下是……”类前言、统一从 h2 起排、代码块语言映射（sh/bash/shell → bash）、禁止内嵌原始 HTML。规则写成 JSON 配置，按项目调整。
2. **解析为 AST**。用 remark/mdast 解析，之后每一步只操作 AST。正则替换收敛在归一化阶段，能少则少。
3. **平台适配器**。每个平台一个纯函数：`render(ast, platform)`。公众号适配器把外链转成文末引用列表、样式内联；知乎适配器把脚注降级为括号内联、剥离不支持标签；静态站基本透传。适配器只做降级，不做增强。
4. **发布前 dry-run**。完整渲染一遍，对产物做断言：图片可达、链接协议白名单、代码块语言合法。dry-run 产物落盘，diff 作为回归 fixture。
5. **接入 Agent**。整条管线封装成 MCP 工具（如 `publish.markdown`，参数带 target），Agent 只看到“写稿 → 调工具 → 拿结果”。转换规则对 Agent 不可见，避免它自作聪明生成平台方言。

## 踩坑点

- 公众号外链几乎全灭，`<a>` 会被剥掉。统一转成“文末参考”编号列表，正文用上标标记。
- CommonMark 对 tab 和混合缩进的处理各实现不同，AI 又偏爱 4 空格嵌套列表，跨平台渲染会错位。归一化阶段统一转 2 空格。
- Mermaid/公式块多数平台不渲染。管线内置静态渲染成图片再引用，代价是构建时间，可控。
- 图片防盗链：图床外链在部分平台直接裂图。自建图床 + 预检里的可达性检查是最低配置。
- Agent 偶尔把 HTML 混在 Markdown 里输出。ingest lint 必须把原始 HTML 当错误而非警告，否则标签被静默吞掉，排查很痛苦。

## 可复用建议

1. 把 AST 当集成点，适配器写成纯函数，测试就是 fixture 进 fixture 出。
2. 平台约束配置化，接入新平台 = 一份 JSON + 一个渲染器。
3. 转换链路留日志：每次发布记录走过的 transform，格式问题可二分定位。
4. 管线只保证不劣化，不负责修复烂稿，源稿质量决定上限。

## 总结

这条管线没用到什么新技术，价值在于把格式适配从每次发布的手工劳动，变成一次性的工程投入：单一源稿、AST 枢纽、平台适配器、发布前预检。封装成 MCP 工具后，Agent 侧的心智负担降到最低——写好标准 Markdown，其余交给管线。后续加平台，成本收敛为一份配置加一个纯函数。欢迎在社区帖下交流各平台适配器的具体实现细节。
