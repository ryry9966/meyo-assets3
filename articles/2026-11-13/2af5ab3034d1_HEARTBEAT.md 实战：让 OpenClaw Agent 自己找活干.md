## 背景

大多数 Agent 的使用模式是被动的：你提问，它回答，然后挂起。但 OpenClaw 这类常驻在个人服务器上的 Agent，天然具备"值守"条件——进程一直在跑，只是缺一个唤醒理由。HEARTBEAT.md 就是这个理由：Agent 每隔一段时间自动醒来，读取工作区根目录（默认 `~/.openclaw/workspace/`）下的这份文件，按条目决定要不要干活。

## 问题

被动模式的痛点不在"不能做"，而在"你得记着问"。备份跑完没有、RSS 里有没有值得读的、某个目录是不是又堆了文件——你不上心，Agent 就永远沉默。传统解法是 cron + 脚本，但判断逻辑一复杂（"有变化才通知""失败才报警"），维护成本迅速上升。心跳机制把"何时醒"交给调度器，把"醒来干什么"交给 Agent + 工具链，中间那层判断用自然语言写就行。

## 做法

1. 在工作区根目录创建 HEARTBEAT.md，写成 checklist：

```markdown
# Heartbeat

## 条件类
- 若 ~/sync/inbox 有新文件，摘要内容并追加到今日笔记；无新文件则不动
- 若 ~/jobs 下任一脚本上次非 0 退出，取日志末尾 20 行通知我

## 定时类
- 每天 09:00 / 18:00，汇总标记为 unread 的 RSS 条目，最多 5 条

## 默认规则
- 以上都不满足时：不产出任何消息
```

2. 配置间隔（默认 30 分钟）：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "interval": "30m" }
    }
  }
}
```

3. 两条关键原则：
- **心跳是触发器，不是执行器。** 重活交给脚本和 MCP 工具，条目只做"检查条件 → 调用 → 汇报"。
- **"无事则沉默"必须显式写。** OpenClaw 约定心跳轮次里无事可做时 Agent 返回空操作，网关不投递这条回复——但这不等于不花 token，写明默认规则能避免 Agent 为了"显得有用"编造汇报。

## 踩坑点

- **间隔太短 = 烧 token。** 每次心跳都是真实的模型调用，哪怕最后沉默。15 分钟起步要慎重，个人场景 30 分钟足够。
- **条目太模糊会失效。**"帮我看看有什么新东西"这类写法，Agent 要么不动，要么臆造工作。每条都要有明确触发条件、动作、和"不满足时不动"的出口。
- **时区。**"早上 8 点"取决于宿主机 TZ，先 `date` 确认再写定时条目。
- **别把长任务塞进心跳。** 心跳会话占用主 Agent 上下文，跑 10 分钟的构建不如让心跳只负责"发现 + 派发"。
- **文件会越长越肥。** 每次心跳都读全文，控制在 20 行以内，定期删掉从未触发过的条目。

## 可复用建议

- 条目按三类维护：**条件类**（有变化才动）、**定时类**（固定时刻汇报）、**巡检类**（周期健康检查）。
- 用 git 管 HEARTBEAT.md，回溯"它半夜为什么给我发消息"时有据可查。
- 数据源优先接 MCP server（邮件、日历、监控），别在条目里硬编码一堆路径。
- 多 Agent 场景按工作区各放一份，避免单个心跳文件承担所有职责。

## 总结

HEARTBEAT.md 的价值不是"自动化"本身——cron 早就有了——而是把触发后那层"该不该做、做到什么程度"的判断交给了模型。写好它只有两条核心：条件明确、默认沉默。先从一两条低风险条目开始（比如监控一个目录），跑一周，删掉没用的，再加新的。
