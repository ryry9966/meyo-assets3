## 背景

用 OpenClaw 跑自动化，几乎所有人都会遇到同一个分叉口：想让 agent「定时干点事」，发现有两套机制——heartbeat 和 cron。表面上都是「每隔一段时间跑一次」，但设计意图完全不同，选错会直接体现在账单和体验上：heartbeat 用多了 token 涨得莫名其妙，cron 用多了收到的消息机械又空泛。这篇帖把两者的差异、选型方法和踩过的坑整理出来。

## 机制差异在哪

**heartbeat 是巡逻模式**：agent 按固定间隔醒来，读取工作区的 HEARTBEAT.md，结合最近上下文判断「有没有值得做的事」。有事就处理并汇报，没事就静默跳过（HEARTBEAT_OK，不投递）。核心是 agent 自己做判断。

**cron 是闹钟模式**：按 cron 表达式精确触发，每次跑在独立会话里，执行 payload 中的固定指令，并把结果投递到指定渠道。核心是确定性交付。

| 维度 | heartbeat | cron |
|---|---|---|
| 触发 | 固定间隔 tick | cron 表达式，精确到分钟 |
| 会话 | 共享主会话上下文 | 独立会话，无对话历史 |
| 决策 | agent 判断做不做 | 无判断，到点就执行 |
| 成本 | 每个 tick 都消耗，静默也花钱 | 只在触发时消耗 |
| 输出 | 有事才打扰 | 到点必投递 |

## 选型做法

1. **先把需求分成两类**：「到点必须做」的（每天早 9 点发摘要、每周固定备份、定点提醒）交给 cron；「隔段时间看看要不要做」的（盯 CI 有没有红、没异常就别烦我）交给 heartbeat。
2. **配 cron 时，payload 必须自包含**：任务背景、数据来源路径、输出格式、投递目标，四样缺一不可。独立会话里 agent 什么都不知道，全靠 payload 兜底。
3. **配 heartbeat 时，把 HEARTBEAT.md 当规则表维护**：每条 = 触发条件 + 动作 + 静默条件。例如「CI 失败时汇总失败项并通知，全绿则静默」。写完先跑几天，再调 interval。
4. **混合使用形成闭环**：heartbeat 观察一段时间后发现某件事其实每天都做，就固化成 cron；再在 heartbeat 里加一条巡检项——检查 cron 最近一次是否成功——互相兜底。

## 踩坑点

1. **heartbeat interval 设太短**。静默跳过不等于不调用模型，每个 tick 都是成本。判断型巡检 30 分钟起步，低优先级事项拉到 1–2 小时。
2. **HEARTBEAT.md 变杂物间**。条目越多，每次醒来读得越久、判断越容易漏。完成即删，控制在三五条以内。
3. **cron prompt 不自包含**。最常见翻车：payload 写「总结昨天的进展」，但独立会话里没有「昨天」的任何上下文，输出全是空话。路径、口径、格式必须写死。
4. **时区**。cron 按主机时区跑，服务器是 UTC 时「早上 9 点」会变成下午 5 点。部署后先手动触发一次核对。
5. **heartbeat 条目太模糊**。「帮我盯着点」这种写法让 agent 无法判断有事没事，要么全静默要么全打扰，触发条件必须可验证。
6. **cron 失败是静默的**。任务挂了没人通知你，要么定期看日志，要么交给 heartbeat 巡检兜底。

## 可复用建议

- 一句话选型：**时间确定、产物确定 → cron；时间不重要、做不做要判断 → heartbeat。**
- 新需求先用 heartbeat 试运行一周，稳定后再决定是否固化为 cron，避免过早硬编码。
- cron payload 和 HEARTBEAT.md 条目都可模板化：背景 / 来源 / 格式 / 投递，四段式。
- 每两周回顾一次 HEARTBEAT.md：删失效条目，迁稳定条目。

## 总结

cron 和 heartbeat 不是竞争关系，而是「闹钟」与「巡逻」的分工：闹钟负责到点交付确定性产物，巡逻负责发现值得注意的事、决定要不要吵你。按「确定 vs 判断」这一标准切分需求，再让两者互相兜底，定时自动化才能既有用又省钱。
