# AI 助手的 USER.md：让 Agent 真正了解你是谁

## 背景：项目上下文解决了一半问题

用 Agent 做开发的人大多已经熟悉 CLAUDE.md / AGENTS.md 这类项目级上下文文件：描述仓库结构、构建命令、代码规范，效果立竿见影。但它描述的是“这个项目是谁”，而不是“我是谁”。每次新开会话，你仍要重复交代：主语言是什么、终端是 zsh 还是 fish、希望回答简短还是详细、哪些做法明确不要。Agent 的内置记忆能记住一部分，但它是黑盒——你不知道它记了什么、何时记错，也无法 diff 和回滚。

## 问题

落到日常，表现为三类：

1. **重复成本**。每个会话开头花两三分钟交代背景，一个月下来是纯损耗。
2. **猜测漂移**。Agent 按统计惯例替你做默认选择：生成 tabs 还是 spaces 全看心情，假设你在 macOS，推荐你早已弃用的包管理器。
3. **记忆不可控**。自动记忆错一次（比如把临时项目当成主栈），后面每轮对话都被带偏，而你连审计入口都没有。

共同根源：缺少一份由用户自己维护、Agent 每次稳定读取的“用户上下文”。

## 做法：一份 40 行以内的 USER.md

我维护一份 `~/.openclaw/USER.md`（如果你的加载链路不同，放在能被稳定注入的位置即可），结构如下：

```markdown
# USER.md

## 身份
- 后端工程师，主要写 Go，偶尔 Python
- 时区 Asia/Shanghai，沟通用中文

## 环境
- macOS 14 + zsh，编辑器 Neovim
- Go 1.22，Node 侧用 pnpm

## 偏好
- 回答直接给结论和代码，不要开场客套
- 代码用 tabs 缩进，错误处理显式返回
- 解释性内容给链接，不要长篇复述

## 明确不要
- 不要主动重构我没让动的代码
- 不要建议迁移新框架
```

三个原则：

- **条目化**。写 bullet 而不是段落，Agent 对短事实的遵循率远高于叙述。
- **短**。控制在 40–60 行。它和项目上下文、系统提示共享 token 预算，越长越稀释。
- **可版本管理**。放进 dotfiles 仓库，改动走 commit，diff 和回滚都有据可查。

加载方式视链路而定：在 OpenClaw 配置里把文件内容拼进 system prompt；或写一个十几行的启动 hook / MCP resource 读取它；最差情况做个模板片段手动粘贴。机制不重要，重要的是“每次会话，同一份内容”。

## 踩坑点

- **写太长**。我第一版写了 120 行，塞满历史背景，结果核心偏好遵循率反而下降——指令密度被稀释了。
- **与项目级文件冲突**。USER.md 写 pnpm，项目 AGENTS.md 写 npm，Agent 会摇摆。建议显式约定优先级：技术选型以项目文件为准，个人风格以 USER.md 为准，并写进两个文件。
- **内容过期**。换机器、升版本、换方向后，旧条目变成误导。环境变更后顺手改，或设月度 review。
- **放敏感信息**。不要写 token、内网地址、客户实名。这份文件大概率进版本库，甚至可能被贴进对话。

## 可复用建议

- 模板固定四段：身份 / 环境 / 偏好 / 明确不要。团队场景另加一份 TEAM.md 描述团队约定，与个人文件分开。
- 每条偏好写成“可判断的事实”（“用 tabs”），而不是态度（“代码要优雅”）。
- 某类错误反复出现时，先加一条到“明确不要”，观察两三个会话，有效保留，无效删除——把 USER.md 当配置调参，而不是一次性文档。

## 总结

USER.md 不玄学：把“用户上下文”从黑盒记忆里拿回来，变成你自己维护、可审计、可版本管理的普通文件。它不替代 Agent 的记忆功能，而是把最稳定、最该由你掌控的部分固化下来。几十行、十分钟成本，换来的收益是：每个新会话，Agent 都已经知道你是谁。
