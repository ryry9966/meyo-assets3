## 背景

OpenClaw 的记忆体系很朴素：memory 目录下的一堆 markdown（长期记忆 + 每日笔记），召回时靠 memory_recall / memory_search 把相关片段捞回上下文。检索默认走全文索引（SQLite FTS 一类），较新版本可以接 embeddings 做语义检索，也有混合模式（具体开关随版本变，以 docs 为准）。社区里经常吵“语义搜索是不是吊打全文”，我拿自己跑了两个月的真实语料做了轮对比，把结论记下来。

## 问题

两种模式在我这里都翻过车：

- 全文搜索：查“上次那个部署脚本”命不中，因为笔记里写的是“上线脚本”。中文分词 + 同义改写是硬伤。
- 语义搜索：查 `ffmpeg 压缩参数`，它返回一堆“视频处理心得”，真正记着参数的那条排在第五开外。专有名词、命令、路径这类强关键词查询，语义模型会“脑补”。

所以真正的问题不是哪个更好，而是：你的查询是什么分布。

## 做法

1. 从两周的会话日志里抽 30 条真实提问（查参数、查结论、查“上周干了啥”各占一部分），人工标注期望命中的 memory 片段。
2. 固定变量：同一份语料、同样的分块方式、同样的 top-k=5，只切换检索模式（全文 / 语义 / 混合）。
3. 统计 recall@5，把所有 miss 的 case 逐条分类。

结果：全文在“带精确关键词”的查询上 recall@5 约八成；语义在自然语言改写类查询上明显更好，但小语料（我不到一千条片段）的优势被弱相关召回吃掉不少；混合模式整体最稳，代价是多一次 embedding 开销。

## 踩坑点

- embedding 模型选型对中文不敏感，语义检索直接废掉一半；换成中文表现好的模型后，漂移 case 明显减少。
- 分块别按固定 token 硬切，按标题/日期切。“上周做了什么”这类时间查询，全靠片段带日期前缀才召得回。
- 全文检索的默认分词对中文不友好，长句查询基本靠整段撞上，关键词得在写入时就有意识地埋。
- 召回质量的上限是写入质量。MEMORY.md 写成流水账，换任何检索模式都救不了。

## 可复用建议

- 语料小、查询偏关键词：全文够了，精力花在写入规范上——每条带日期、带命令原文、带一句话结论。
- 语料大、查询偏口语：上语义或混合，注意 embedding 的成本与隐私（本地模型 vs API 要自己权衡）。
- 别拍脑袋选型，照上面那套 30 条测试集的方法跑一遍，recall@5 半小时能出结果。
- 定期把 miss case 回灌成写入规范，收益比调检索参数大得多。

## 总结

语义搜索不是银弹，全文搜索也不是老古董。memory_recall 的效果 ≈ 写入质量 × 分块策略 × 检索模式，而检索模式恰恰是三者里最不值得先折腾的一环。我的现役配置：混合模式 + 严格的写入规范。先测量，再切换。
