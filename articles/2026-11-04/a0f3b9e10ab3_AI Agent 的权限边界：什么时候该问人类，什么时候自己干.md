## 背景

Agent 接上 MCP 和插件之后，能做的事从"回答问题"变成了"操作世界"：读写文件、调 API、发消息、跑脚本。能力上去了，但"该不该自己做"这个判断，很多团队还停留在两条极端路线上——要么全问（每一步都确认），要么全放（无条件信任模型）。前者把人变成点击机器，后者迟早出事故。

## 问题

权限边界难定，是因为它不是二值问题，至少有四个维度在互相拉扯：

- **可逆性**：改动能不能撤销？git 管得住的写文件，和删数据库行，不是一个量级。
- **影响半径**：只动自己的工作区，还是会波及他人（发通知、改共享配置、对外发布）？
- **资源成本**：调付费 API、跑长任务，花的是真金白银。
- **意图确定性**：动作是用户明确授权过的，还是模型自己"推理"出来的衍生目标？

只靠 system prompt 写"删除前请确认"是不够的。prompt 是建议，不是强制——长上下文里规则会被稀释，复杂任务里模型也会漂移。

## 做法：动作分级，门修在工具层

**第一步：盘点工具，按四个维度打分。** 把 Agent 能调用的每个 MCP 工具列出来，逐个标注可逆性、影响半径、成本。这步枯燥，但做完你会发现 80% 的工具其实可以自动放行。

**第二步：划四档。**

- **自动执行**：只读、本地、无副作用（读文件、查询、搜索）。
- **自动执行 + 留痕**：可逆写操作（git 管理下的代码修改、本地缓存写入），记录参数和结果。
- **需确认**：对外可见、不可逆、花钱（发消息、提 PR、调付费接口）。确认时必须带上下文：改了什么的 diff、发给谁、预计花多少。
- **工具层直接拒绝**：明确禁区（生产库 DDL、支付、rm 类操作），在 MCP server 侧硬编码拦截，连问都不问。

**第三步：设计"有信息量的确认"。** 确认框只有一句"是否继续？"是失败的——看多了人必然无脑点 yes。好的确认应展示关键参数和影响范围，并支持批量：同类型动作在当前任务内授权一次后放行，但逐条记日志。

**第四步：会话级授权 + 超时策略。** 人不在时，Agent 应挂起等待，而不是自作主张重试；授权要有有效期，任务结束自动回收。

## 踩坑点

- **规则只写在 prompt 里**。换个长任务就漂移，工具侧没有兜底等于裸奔。
- **确认疲劳**。50 个文件逐个问，用户从第 10 个开始就是橡皮图章。宁可批量授权 + 事后审计。
- **只读工具也有副作用**。外部搜索 API 会花钱、留访问记录，别默认全放。
- **子 Agent 权限没收紧**。主 Agent 被授权的事，派发出去的子任务不一定该有同等权限。
- **缺 dry-run**。写操作前没有预览环节，出问题只能回滚，无法预防。

## 可复用建议

1. 默认拒绝写操作，白名单放行，方向不要反。
2. 确认必须带 diff / 参数 / 成本，否则等于没问。
3. 高风险动作优先用"托管模式"：Agent 备好一切，人来按执行键。
4. 用红队思路自测：故意给模糊指令，看 Agent 会不会越界自推目标。

## 总结

权限边界不是一次性配置，而是随工具清单持续维护的分类表。核心判据可以压缩成一句话：**可逆且只影响自己 → 自己干；对外可见、不可逆、花钱 → 问人，且问得有信息量；禁区 → 工具层直接拦。** 把门修在工具层，prompt 只做引导，你才敢放心给 Agent 权限，也才敢放心不盯着屏幕。
