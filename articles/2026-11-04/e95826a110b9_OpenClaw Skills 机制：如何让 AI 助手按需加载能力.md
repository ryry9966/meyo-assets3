## 背景

玩过 Agent 的人大多经历过同一个过程：一开始把所有操作说明、命令模板、注意事项全塞进 system prompt，感觉配置了一个无所不能的助手；两周后发现上下文里 80% 的 token 是“这次用不到的说明书”，模型注意力被稀释，简单任务也容易跑偏。

OpenClaw 的 Skills 机制就是为了解决这个问题：把能力拆成一个个独立的技能包，平时只在系统提示里占一行描述，用到时才完整加载。

## 问题：全量注入 vs 按需加载

- **全量注入**：所有技能文档常驻上下文。十几个技能就是几千 token，而且指令之间互相干扰。
- **Skills 按需加载**：启动时只注入 name + description（每个技能几十 token），agent 判断任务匹配后才读入 SKILL.md 正文，正文里还能再引用附属文件。

这就是所谓的渐进式披露：模型先看目录，再翻书。

## Skills 长什么样

一个技能就是一个目录，核心是 SKILL.md：

```markdown
---
name: pdf-report
description: 从本地 PDF 批量提取表格并生成周报。当用户提到"提取 PDF 表格""生成周报"时使用。
---

# 步骤
1. 确认 pdfplumber 已安装：`python -c "import pdfplumber"`
2. 运行 scripts/extract.py，参数见 references/args.md
```

三个要点：

- frontmatter 的 **description 是触发开关**，agent 靠它判断“现在该不该用我”。
- 正文写具体步骤、命令、边界情况，是给模型读的操作手册。
- 大段参考资料放子文件（references/、scripts/），需要时再读。

放置位置：个人技能放 workspace 的 skills 目录；第三方技能可用 CLI 安装，或手动把目录丢进去（以官方文档为准）。

## 写一个技能的五步流程

1. **找场景**：挑一个你重复做过 3 次以上的操作（部署、周报、日志排查）。
2. **写骨架**：只写 description + 三五步核心流程，别贪多。
3. **沉淀命令**：把你在终端里实际敲过的命令原样写进去，包括报错后的处理。
4. **实测触发**：用自然语言让它干活，观察它是忽略了技能还是用错了技能。
5. **回写坑**：把每次失败的原因写成“常见错误”段落，追加回 SKILL.md。

## 踩坑点

- **description 写得太泛**。“处理文件类任务”会乱触发，写得太窄又永远不触发。建议格式：动词 + 明确对象 + 触发词示例。
- **把技能当插件 API**。Skills 本质是“给模型读的流程文档”。确定性逻辑（解析、批量处理）写成脚本放进技能目录，SKILL.md 只说明何时调用、怎么传参。
- **环境假设**。技能里写了 `~/tools/xx.sh`，换台机器就哑了。正文开头加一段前置检查。
- **技能打架**。两个技能都声称处理“部署”，agent 会挑错。收窄各自的 description，必要时写明“不要用于 XX”。
- **只装不理**。装了 30 个技能不清理，光目录就吃掉一大块 system prompt，得不偿失。

## 可复用建议

- **粒度**：一个任务场景一个技能，宁可多个小技能，不要一个大杂烩。
- **和 MCP 分工**：MCP 管工具（模型能调什么），Skills 管流程（这些工具怎么组合用好）。两者不冲突，通常要配合。
- **迭代心法**：把 agent 每次翻车当成需求，纠正方案写回技能，两三轮后会明显变可靠。
- **固定模板**：何时使用 / 前置检查 / 步骤 / 示例命令 / 常见错误，五个段落写满就够用。

## 总结

Skills 机制的价值不在于“多装几个能力”，而在于控制上下文的信噪比：目录常驻、正文按需、参考资料懒加载。写技能的成本很低——一个 Markdown 文件——但它把你的个人经验从聊天记录里固化成了可复用的资产。建议从你本周重复做过的那件事开始，写第一个技能试试。
