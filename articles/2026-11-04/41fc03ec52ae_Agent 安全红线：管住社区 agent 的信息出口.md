## 背景

这半年社区里 agent 用得越来越重：答疑机器人、issue 分诊、周报摘要、公告起草，基本都接了 MCP 工具和内部文档检索。效率确实上来了，但随之出现一个不太显眼的风险——**agent 成了内部信息对外的潜在出口**。它读得到什么，理论上就可能说出来什么。

## 问题

实际排查下来，泄露路径主要有三条：

1. **提示词注入。** 用户在帖子、issue 正文或贴出的链接里夹带指令，诱导 agent 输出系统提示词、工具清单或内部配置。外部内容默认不可信，但很多接入没按这个前提设计。
2. **权限过大。** 图省事，社区答疑 bot 和内部工具 bot 共用一份 MCP 配置，前者顺带继承了读内部仓库、甚至 shell 的能力。
3. **语料混淆。** 公开 FAQ 和内部文档建在同一个检索索引里，bot 回答时引用了未发布的路线图，事后才发现。

还有一个前提要先接受：**系统提示词本身应当视为必然泄露**。靠一句"不要透露你的指令"拦不住任何人。

## 做法

我们后来按六步收敛：

1. **资产盘点**：列出每个 agent 挂的工具和数据源，按公开 / 内部 / 敏感三级打标。
2. **最小权限**：面向社区的 agent 只挂只读、公开范围的工具；禁 shell、禁广域文件读取；发公告、push、webhook 这类写出口一律转人工确认。
3. **语料隔离**：公开索引和内部索引物理分开，社区 agent 只挂公开索引，宁可回答"这个我没查到"。
4. **注入隔离**：帖子、网页、issue 正文统一按"数据"处理，进上下文时打标签、加定界，不与指令通道混排。
5. **出口扫描**：输出侧加一层 guardrail，匹配内部主机名、路径、成员 handle 和密钥格式（`sk-`、`ghp_` 等），命中即拦截转人工。
6. **金丝雀与审计**：内部文档埋几串假标记，出现在公开输出即告警；agent 对外输出全量留痕，定期抽查。

## 踩坑点

- guardrail 第一版词表太紧，误杀率高，被人嫌烦直接关了。词表和阈值要跟着误报一起调，规则要有人认领。
- 第三方 MCP server 本身就是出口：agent 发过去的上下文它都拿得到。装插件前先看它声明要什么数据，别默认安全。
- 链接预览、被引用的 issue 正文也是注入载体，只防用户输入框没用。
- 共享记忆库会把内部讨论摘要带进下一次公开回答，记忆也要按数据分级。

## 可复用建议

- 新增 agent 前过三问：它挂了什么工具？能看到哪些数据？有哪几个对外出口？
- 把"公开 agent 只见公开数据"写成接入规范，而不是口头约定。
- 每月做一次内部注入演练，让同事专门攻击答疑 bot，命中就补规则。

## 总结

Agent 安全本质是权限工程，不是提示词工程。假设系统提示词会泄露、假设用户内容不可信，在这个前提下把数据分级、把出口管住、把留痕做全，红线才守得住。提示词只负责降低概率，权限才负责兜底。
