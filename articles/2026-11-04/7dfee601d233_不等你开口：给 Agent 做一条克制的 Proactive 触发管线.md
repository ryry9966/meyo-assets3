## 背景

大多数 Agent 的使用是拉模式：你提问，它回答，会话结束就归档。它不会记得明天该看一眼 CI 是不是还红着。

OpenClaw 其实给了三条"推"的入口：**heartbeat**（周期性唤醒，读工作区的 HEARTBEAT.md）、**cron**（确定性定时任务）、**webhook/事件**（外部系统主动敲门）。再配上 MCP 工具读外部状态——仓库、日历、监控——proactive 的原材料是齐的，缺的是一条工程化的管线。

## 问题

最常见的错误做法，是给心跳加一句"每 30 分钟醒来，看看有没有值得汇报的事"。三种后果：

1. token 成本随频率线性上涨；
2. 提示词在逼模型找事——被要求"找点有用的"，它总会找到点什么，多半是幻觉或鸡毛蒜皮；
3. 没有闸门，误触发的副作用动作（给同事发消息、重启服务）没人拦。

Proactive 的真正问题不是"能不能主动"，而是**如何让主动行为的精确率高到不打扰人**。

## 做法

按触发、决策、执行、状态四层拆开：

**1. 触发层保持确定性。** 什么时候醒，由 cron / 心跳间隔 / webhook 决定，绝不交给模型自己决定。心跳从 30 分钟起步，观察一周再调。

**2. 决策层只判断、不执行。** 心跳那次运行的输出收敛为一个结构化结论：`DO_NOTHING` / `NOTIFY` / `ACT(理由)`。提示词里明确写"绝大多数心跳的正确输出是 DO_NOTHING"，把"什么都不做"定义成标准答案而非失败。每条规则在 HEARTBEAT.md 里写成 checklist：查哪个 MCP 工具、阈值多少、免打扰时段几点到几点。

**3. 执行层走白名单。** `NOTIFY` 可以直接发（但限频）；任何对外部世界有影响的动作必须命中允许列表，否则一律降级为"起草好、等人确认"。

**4. 状态与去重。** 用一个小 JSON 记录每条规则的 `last_fired` 时间戳和内容 hash，同一 hash 在 N 小时内直接跳过。没有去重的主动提醒，会以 30 分钟一次的频率把同一件事讲五遍。

## 踩坑点

- **提示词诱导**："主动找有价值的事汇报"约等于要求幻觉。改成默认 `DO_NOTHING`，情况立刻干净。
- **心跳共用主会话**：判断过程会污染主上下文，成本也翻倍。用独立会话，或强制心跳只回一行结论。
- **忘配免打扰**：凌晨三点一条 cron 时区写错的通知，足以让全家人关掉通知权限——proactive 死于噪声。
- **工具配置里 auto-approve 开太宽**：白名单形同虚设，执行层等于裸奔。

## 可复用建议

- 分层口诀：**触发靠代码，判断靠模型，执行靠白名单**。模型只出现在判断那一层。
- 输出分三档：静默写日志 < 攒成每日 digest < 立即 ping。默认用前两档。
- 每条 proactive 规则都要有开关和审计日志，出问题时能一行命令关掉。
- 上线后手动评估一周精确率，噪声大的规则直接删，不要恋战。

## 总结

Proactive 能力的本质不是让模型更聪明，而是把"什么时候醒、醒来看什么、看完能干什么"这三个问题全部工程化。建议从一个你真的需要的高价值低风险规则开始——比如每天早上汇总一次待处理的 code review——跑一周，看精确率，再决定加第二条。克制的 proactive，才是能留下来的 proactive。
