## 背景

LLM 本身无状态，会话一关，上下文清零。做 Agent 自动化时，用户提得最多的需求往往不是更强的推理，而是“记住我”：记住代码风格、部署习惯、常用的回复口径。但多数实现停留在把历史聊天塞进 system prompt，要么撑爆上下文，要么第二次会话照样失忆。这篇整理一下我在给 OpenClaw 挂记忆插件时跑通的方案。

## 问题：三种典型失败

1. **全量存储**：什么都记，检索时噪声淹没信号，越用越不准。
2. **一次性固化**：用户随口一句“今天想吃清淡的”，被写成永久设定“饮食偏好：清淡”。
3. **只写不筛**：每次全量注入记忆，占掉大半上下文预算，真正相关的没几条。

## 做法：分层存储 + 写时抽取 + 读时检索

**1. 情景记忆（append-only 日志）**：按时间存会话事件，只追加不修改，是后续抽取的原料，不直接参与注入。

**2. 语义记忆（结构化偏好库）**：会话结束时用结构化输出抽取“可跨会话复用”的事实，每条带 schema：

```json
{ "content": "...", "category": "coding_style", "confidence": 0.8, "source": "session#123", "created_at": "...", "last_hit": "...", "hit_count": 3 }
```

**3. 检索注入**：查询时混合检索（向量 + 关键词），叠加元数据过滤（category、confidence > 0.7），按相关性取 top-5，超出一律不注入。需要更多细节时让 Agent 主动调 recall 工具，而不是全量灌。

同 category 出现冲突时，新事实覆盖旧事实，被覆盖的保留用于回溯；长期未命中的条目按 last_hit 衰减降权。

落地方式：把记忆库封装成一个 MCP server，暴露 `read` / `write` / `delete` 三个 tool，OpenClaw 的任何 Agent 和插件都能复用，不用各自造轮子。

## 踩坑点

- **抽取太激进**：低置信度条目先标 `pending`，Agent 在后续对话里复述确认（“我记得你偏好 X，对吗？"）后才转正，误存率明显下降。
- **向量检索假阳性**：语义相近但主题无关的召回很常见。加 category 元数据过滤，比换 embedding 模型见效快。
- **记忆挤占上下文**：给注入内容设硬上限（条数 + token 双限制），宁可让 Agent 多调一次 recall。
- **黑盒不可改**：一定提供 list 和编辑入口。记忆错了用户删不掉，信任会迅速崩掉。
- **偏好有时效**：用 created_at + last_hit 做衰减，别让两年前的设定一直压着新偏好。

## 可复用建议

1. 先跑通"写时抽取 + 读时检索”的最小闭环，再考虑记忆图谱这类复杂结构。
2. 每条记忆带 provenance（source 字段），排查“它为什么这么理解我”时能定位到原始对话。
3. 遗忘是功能不是缺陷：按 category 删除、TTL、用户手动清除，三选一起码做一个。
4. 评估别只看单轮：准备一组跨会话测试问题，验证第二次会话能否正确应用偏好，这才算闭环。

## 总结

记忆系统的核心不是存多少，而是存什么、何时取、错了怎么改。结构化 schema + 置信度分级 + 用户可见可删，这三点做到位，Agent 才算真正“记住”一个用户。欢迎在社区交流各自的抽取 prompt 和检索策略。
