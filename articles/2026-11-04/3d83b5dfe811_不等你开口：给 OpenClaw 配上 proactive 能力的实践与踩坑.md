## 背景

多数 AI 助手的工作模式是"你问它答"：不问不动。但真正省时间的场景往往反过来——磁盘快满了、PR 挂了两天没人 review、明早要交的周报还差数据。你不想靠自己的记性把这些事想起来，而是希望助手自己发现、自己处理，或者至少自己开口。

OpenClaw 里有三个现成的抓手可以做这件事：heartbeat（定期心跳唤醒）、cron（定时任务）、事件触发（webhook / 文件变化推给 agent）。这篇帖记录我给个人助手配置 proactive 能力的过程和教训。

## 问题

proactive 最大的敌人不是"做不到"，而是"做过头"。三种典型翻车：

- 心跳太频繁，每次空转也在烧 token，月底账单教做人；
- 推送噪音大，一天十条"没什么大事"，最后你把通知一关，proactive 等于死了；
- 最糟的一种：无人监督时执行了写操作，比如 agent"顺手"回复了不该回的消息。

所以核心问题是：怎么让"主动"可控、可审计、不烦人。

## 做法

**1. 心跳巡检：检查 → 判断 → 沉默或行动**

OpenClaw 的 heartbeat 会让 agent 定期醒来。我做了两件事：

- 把间隔从几分钟拉长到 30–60 分钟；
- 在工作区放一个 HEARTBEAT.md，写成检查清单：每次醒来看哪些来源（issue 列表、磁盘水位、日历）、什么条件才"值得打扰用户"。

agent 醒来后走"检查→判断"流程，多数时候无事可报，静默结束，这一轮成本只有一次轻量调用。

**2. Cron：固定节律的事别碰运气**

每天早上的摘要、周五下午的周报草稿，用 cron 定死，而不是指望心跳"恰好"在那时候想到。注意时区，配错了就是凌晨三点给你推送。

**3. 事件触发：时效性强的事走 webhook**

CI 失败、监控告警、特定邮件，通过 webhook 推给 agent：拉日志 → 判断级别 → 立刻通知，或记进"待汇总"池。事件源要打标记，避免 agent 自己产生的消息又触发一轮。

**4. 把"打扰阈值"写进系统提示**

分三档：立即打扰（有可执行动作且有时效）、进 digest（重要但不急）、忽略。规则写成一句话能说清的白名单，比"智能判断"可靠得多。

## 踩坑点

- **重复报警**：同一个问题每半小时报一次，直到你想砸手机。解法：给 agent 一个状态文件，报过的问题记下 ID，下轮跳过，问题解决才清除。
- **会话膨胀**：主动任务全塞进主会话，上下文越滚越大。给 proactive 单开会话，只把最终结论带回主会话。
- **无监督写操作**：proactive 阶段先只读。要写也走"草稿 + 人工确认"，或给这轮调用单独配工具白名单。
- **自触发环**：agent 发出的通知又进了自己的 webhook 队列，自己把自己聊死。事件入口务必过滤 agent 自身的输出。

## 可复用建议

1. 先只读，后放权。第一周只让它"看和报"，观察误报率，再逐步放开动作。
2. 每个主动任务有 ID、有日志，方便审计，也方便一键关停。
3. 非紧急信息攒成一天一条 digest，比十条零散推送有用得多。
4. 主动执行的动作要幂等——重试和重复触发都可能发生，别让重复执行造成重复后果。
5. 定期回头看心跳日志：哪些检查项三个月没触发过一次？删掉，省成本。

## 总结

proactive 不是把定时器打开就完事，本质是给助手设计一套"什么时候值得说话"的制度：心跳负责巡检，cron 负责节律，事件负责时效，HEARTBEAT.md 和状态文件负责克制。把噪音压下去，真正的主动提醒才会被认真对待——这才是"不等你开口"的含金量。
