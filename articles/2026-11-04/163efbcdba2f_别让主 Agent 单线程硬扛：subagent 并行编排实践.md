## 背景

用 agent 做自动化久了，都会撞上同一个瓶颈：主会话是单线程的。让它“把这 8 个仓库最近的改动各总结一段”，它就一个接一个地读和写，十分钟过去了还在第 4 个；每份文件原文还都进了主上下文，跑完之后会话臃肿，后续任务质量肉眼可见地下降。

subagent 编排解决的就是这个问题：主 agent 只负责拆任务、发任务、收结果，执行交给若干个拥有独立上下文的子 agent，能并行的并行，该隔离的隔离。

## 问题：什么任务值得拆

不是所有任务都值得并行。我的判断标准有三条：

- 子任务之间没有共享的可变状态（不会同时写同一个文件或分支）；
- 单个子任务能独立完成、独立校验（不需要中途问用户）；
- 数量 ≥3 且单个耗时明显，否则编排本身的开销大于收益。

典型的可拆任务：批量代码审查、多源资料收集、按模块生成文档、批量数据清洗。

## 做法

OpenClaw 里主 agent 通过 `sessions_spawn` 拉起子 agent：每个子 agent 是一个全新会话，不继承主会话上下文，有自己的工具权限和上下文窗口，跑完后把结果回传给主会话。基于这个机制，我的流程是四步：

1. **拆任务**：把总目标切成若干“输入明确、输出可判”的子块，尽量按资源分片（按仓库、按目录、按时间窗），不要按步骤拆——按步骤拆出来的是依赖链，并行不起来。
2. **写任务说明书**：这是编排里最值钱的部分。子 agent 的 prompt 必须自包含：目标、输入（路径/URL 直接写全，别写“参考上文”）、边界（允许哪些工具、不许动什么）、输出 schema（比如 `status / summary / artifacts` 三个字段）、失败时怎么办（返回 failure 加原因，不许硬编）。
3. **控并发**：一次 spawn 三四个就够，跑完一批再发下一批；给每个子 agent 设最大轮数和超时，防止单点拖死整批。
4. **收结果**：只收结构化摘要，父级检查 status；失败的单独重派一次，仍失败就在最终报告里如实标注。

## 踩坑点

- **prompt 不自治**：任务里写“按刚才说的做”，可子 agent 没有“刚才”，只会自由发挥。所有上下文必须在 spawn 时写死。
- **结果污染主上下文**：早期我让子 agent 回传全文，四个跑完主会话直接撑爆；改成固定 schema 摘要后，主 agent 收到的信息密度高了一个量级。
- **失败静默**：子 agent 半路挂掉返回空结果，父级当成功汇总，报告凭空缺一块。status 字段不是摆设，必须检查。
- **写竞争**：两个子 agent 同时改一个文件，后写的覆盖先写的。原则：子 agent 只读、产出草稿，落盘动作收敛到父级，或按资源严格分片。
- **并发拉满**：八个子 agent 同跑长任务，token 消耗直接乘八，还可能撞 API 限流。分批加上限，是成本和稳定性的共同下界。

## 可复用建议

- 任务说明书沉淀成模板库：批量审查一个模板、资料收集一个模板，下次改改输入就能用。
- 最小工具权限：能只读不给写，能不给浏览器就不给。
- 先用 2~3 个子 agent 小规模验证模板，稳了再放大并发。
- 每次编排留记录：拆分方式、实际耗时、失败率，这些数据会告诉你值不值得继续。

## 总结

subagent 编排的价值不在“快”，而在分治带来的上下文隔离和失败隔离：主会话保持干净，单个子任务挂掉不拖垮整体。判断一个任务该不该并行，就看它有没有独立、可校验、无共享写状态的子块；prompt 合同写清楚、并发留上限、结果带状态位——做到这三点，多 agent 并行才算工程实践，而不是看起来热闹。
