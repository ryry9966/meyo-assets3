## 背景

跑了一段时间 Agent 自动化之后，大多数人都会撞上同一个分叉：权限给得太松，一个不可逆操作（删文件、对外发消息、花钱调 API）直接出事故；收得太紧，Agent 每步都停下来确认，人退化成"批准按钮"，自动化就失去了意义。这篇帖不讲理念，只讲我们落地时用的一套分级方法和踩过的坑。

## 问题

两个典型失败模式：

1. **事事上报**。Agent 每写一个文件都要确认，人开始无脑点"同意"，批准形同虚设——这比不问还危险。
2. **全自主裸奔**。System prompt 里写一句"危险操作请先问我"，看起来有约束，实际长任务跑十几轮后指令被稀释，Agent 在第 20 步"顺手"执行了 `rm -rf`，或者把邮件直接发了出去。

根源在于：权限边界不应该靠措辞，而应该靠工程结构。

## 做法：给每个工具标"副作用等级"

用四个维度给动作分级：**可逆性、影响半径、错误代价、有无天然确认点**。落成四级：

| 等级 | 典型动作 | 策略 |
|---|---|---|
| L0 只读 | 搜索、读文件、查询 API | 自动执行 |
| L1 可逆写 | 工作目录内写文件、新建 git 分支 | 自动执行 + 全量审计日志 |
| L2 外部但可撤 | 提 PR 不 merge、邮件写进草稿箱 | 自动生成，由人在确认点触发 |
| L3 不可逆/高危 | 删除数据、对外发送、支付、动生产环境 | 必须问人，且带完整上下文 |

实施三步：

1. **盘点工具清单**。把 Agent 能碰到的每个工具（shell、MCP server、插件）逐个标注等级，写进配置而不是 prompt。MCP 层做工具白名单，shell 做路径沙箱和命令黑名单，金额/频率类操作设硬上限——这些约束放在网关层，Agent 绕不过去。
2. **把"问人"模板化**。L3 的提问必须包含：目标、当前计划、将要执行的命令或 diff、风险说明、2~3 个选项（执行 / 修改后执行 / 放弃）。禁止"我可以继续吗"这种零信息提问。
3. **借用天然确认点**。能复用的流程就复用：PR review 本身就是批准点，草稿箱本身就是缓冲区，不要另造一套审批 UI。

## 踩坑点

- **只靠 system prompt 约束**。措辞约束在长上下文里必然退化，硬约束必须落在工具层或网关层。
- **批准疲劳**。前两周我们让所有写操作都问一次，第三天人就开始盲点 yes。收紧 L3、放开 L1 之后，每次批准才重新变得"有信息量"。
- **权限粒度太粗**。把整个 `fs` 工具一刀切禁掉，结果连读都读不了。后来按路径和操作类型拆分才解决。
- **没有审计**。Agent 干了什么全靠翻聊天记录。现在每次工具调用都记参数和结果，出事能回放，也能定期分析哪些"反复被批准"的模式可以下沉为自动规则。

## 可复用建议

- 一个快速判断口诀：**可逆吗？影响几个人？错了赔多少？有没有现成的确认点？** 四个答案都是"可逆 / 少 / 低 / 有"，就放手让它干。
- 默认拒绝、显式放行，而不是默认放行再打补丁。
- 批准请求必须自带上下文和选项，否则人批准的只是"未知"。
- 每周回看一次审计日志，权限策略是活的配置，不是一次性工程。

## 总结

权限边界不是"多问"或"少问"的问题，而是把操作按副作用分级、把硬约束放进工程层、把人的注意力只留给真正不可逆的决策。Agent 的自主性是省出来的——L0/L1 跑得越顺畅，L3 的那一次提问才越有分量。
