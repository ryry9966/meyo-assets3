## 背景

最近半年，社区里跑常驻 Agent 的人明显多了。典型形态是：一个 Agent 挂着若干 MCP 工具，能读本地文件、查数据库、调内部 API，顺便帮忙在社区答疑、写帖、生成自动化脚本示例。能力上去了，一个新风险也随之出现——**Agent 知道的比你想象的多，而它并不总能分清哪些能说、哪些不能说。**

## 问题的三种真实形态

1. **上下文携带敏感信息。** Agent 的工作记忆里经常有 `.env` 内容、内部域名、连接串。当它"热心地"给出完整排查过程时，这些内容可能被原样带进公开回复。
2. **工作流本身就是资产。** 一份贴出去的 MCP 工具清单加插件配置，等于把内部系统拓扑画给别人看。工具名、参数结构、路由规则拼起来，信息量远超单条配置。
3. **记忆与日志回灌。** 开了长期记忆的 Agent，可能在回答公开问题时召回几周前的私有会话；读过含 token 的日志后，举例时把真实凭据贴出来。

## 做法：把出站内容当作不可信输入

核心思路一句话：**Agent 生成的对外内容，一律按"可能含敏感信息"处理，出厂前过一道人工闸门。**

分四步：

**第一步，物理隔离敏感面。** Agent 工作目录只挂载需要公开的项目；`.env`、内部文档、日志目录用文件权限挡在可读范围外。别指望提示词里写一句"不要泄露密钥"就万事大吉。

**第二步，拆分"对内 Agent"和"对外 Agent"。** 对内那个保留全量工具；对外只挂最小工具集，系统提示里明确输出边界。两者不共享记忆。

**第三步，出站走人工确认。** 凡是发到社区、issue、群里的内容，先进草稿队列，人扫一眼再放行。重点扫四类：密钥格式、内部主机名、真实文件路径、同事用户名。

**第四步，准备"脱敏分享模板"。** 平时维护一份占位符版本配置（`YOUR_API_KEY`、`example.internal`），分享工作流时只发模板，不发实机配置。

## 踩坑点

- **"我已经让它匿名化了"不可靠。** 模型对"什么是内部信息"没有稳定判断边界，脱敏后残留的路径、时间戳、ID 规律仍可反推。
- **日志是最大的暗雷。** 排障时让 Agent 读日志，请求头里带着真实凭证。出现一次就该立刻轮换密钥，而不是删帖了事。
- **截图比文本更容易泄密。** Agent 生成的界面截图、终端录屏，角落里的主机名和用户名经常被忽略。
- **工具清单本身就是情报。** 被问"你用了什么插件"时逐条罗列配置，等于公开架构图。回答层面给思路就好。

## 可复用建议

- 出站前三问：这内容敢贴到公司大厅吗？里面有可反推的路径吗？删掉一半还能回答问题吗？
- 任何一次出现在提示词或日志里的密钥，视为已泄露，直接轮换。
- 定期用 `key|token|secret|password` 模式扫一遍 Agent 可读目录，把误挂载的文件摘出去。
- 社区答疑给结构和思路，配置只给占位符模板。

## 总结

Agent 安全红线的本质，不是让模型更聪明地保密，而是**用工程手段收窄它的可读面、切断它的直连出站通道**。提示词是软约束，权限和流程才是硬约束。把"对外内容人工过闸"当成默认动作，泄露概率会从"随时可能"降到"需要故意犯错才会发生"——对个人和小团队来说，这就够了。
