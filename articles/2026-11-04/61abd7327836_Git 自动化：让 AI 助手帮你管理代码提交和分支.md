## 背景

接上 MCP 之后，OpenClaw 基本具备了常驻在终端旁边的能力。Git 里有一类活儿特别适合丢给它：写 commit message、合并后清理分支、push 前整理提交。这些事规则明确、重复度高，人做起来容易随情绪波动，agent 做反而稳定。但前提是权限和流程设计得当——否则就是在工作区里养了一只会跑 `git checkout .` 的猫。

## 问题

实际用下来，痛点集中在三处：

1. **commit message 质量不稳定**。赶时间时随手一个 "fix"，三个月后没人看得懂历史。
2. **分支残留**。合并完忘删，一个月后本地躺着二十几个 stale branch，远端还多了一堆 `feature/xxx-backup`。
3. **风险不对称**。直接放开让 agent 跑 git 命令，一次 force push 或者一次误删 stash，代价远大于省下的时间。

## 做法

**第一步：收权限，而不是靠 prompt 求它。** 不要给 agent 完整 shell，用 MCP Git server 只暴露 `status / diff / log / add / commit / branch` 这类安全命令，`push --force`、`reset --hard`、`rebase` 在工具层直接禁用。白名单永远比"我在配置里写了不许做"可靠。

**第二步：写一个 `/commit` skill**，流程固定：

- 先跑 `git status` + `git diff`，理解本次改动；
- 生成一条 Conventional Commits 风格的 message，**打印出来给用户看**；
- 只暂存与本次改动相关的文件，禁止 `git add -A`；
- 确认后提交。

**第三步：加一个 `/branch-cleanup` skill**：列出 `git branch --merged main` 的结果，汇报候选删除列表，等确认再动手；远端分支默认只报告、不动手。

**第四步：hooks 兜底。** `pre-commit` 挂 lint 和 gitleaks，agent 的提交和人的提交走同一道闸门。

## 踩坑点

- **早期图省事开了完整 shell**，agent 处理冲突时跑了一句 `git checkout .`，工作区未提交改动直接没了。这次之后才下决心做工具白名单。
- **大 diff 下 message 会失真**。几百行的改动让它概括，出来的描述往往泛泛而谈。后来限定：单次提交只覆盖一个逻辑变更，diff 太大先分批。
- **`.env` 差点进暂存区**。skill 里写死一条：遇到疑似密钥文件一律停下询问，再靠 gitleaks 双保险。
- **无人审查的提交会漂移**。规定 agent 每次 commit 前必须列出 message 和涉及文件；只有纯格式化改动才允许自动放行。
- **rebase / detached HEAD 状态下什么都不做**。skill 第一步先检查仓库状态，异常直接退出。

## 可复用建议

- 把这套规则写成项目级 skill 文件，随仓库进版本控制，团队共享同一套 agent 行为，而不是各调各的。
- 分层授权：只读操作自动执行，本地写操作自动执行，push 和删远端分支必须人工确认。
- 留操作日志：agent 的每次 git 操作追加写入日志文件，出问题能回溯现场。
- 先在个人仓库跑两周，观察 message 质量和误操作率，再考虑进团队流程。

## 总结

AI 管 Git 的价值不在"全自动"，而在把写 message、清分支这类重复决策标准化。权限收窄加明确的人工确认点，决定这套东西能不能长期用下去。工具越顺手，越要提前想清楚：哪些事它不能自己做主。
