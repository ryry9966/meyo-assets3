### 背景

最近把家里一台配 RTX 4060 Ti 16G 的台式机改成常驻推理机，给 OpenClaw 的几个自动化流程当后端。动机很实际：MCP 工具要读本地文件和聊天记录，全走云端 API 心里不踏实；Agent 循环里大量几百 token 的小请求，账单积少成多；另外内网断网也得能跑。

结论先说：8B～32B 量化模型 + OpenAI 兼容端点，已经能撑起大部分 Agent 日常。瓶颈不在“模型聪不聪明”，而在工具调用稳定性和上下文管理。

### 做法

**1. 选引擎，别折腾。** 起步用 Ollama 就够，一行命令拉模型、自带 OpenAI 兼容 `/v1` 端点。等有并发和前缀缓存需求，再迁到 llama.cpp server 或 vLLM。Agent 框架侧只改 `base_url`：

```bash
OPENAI_BASE_URL=http://127.0.0.1:11434/v1
```

**2. 按显存选模型。** Q4_K_M 量化下大致：8B 占 6~8G，14B 占 10~12G，32B 要 20G 以上（或选 MoE 模型做 CPU offload）。原则是留 2G 余量给 KV cache，上下文越长吃越多。

**3. 单独跑 embedding。** 记忆/RAG 的向量化别和主模型混在一个进程，拉个 bge-m3 级别的小模型分开服务。

**4. 做验收，不迷信榜单。** 攒 15 个真实任务（含 8 个要调 MCP 工具的）当回归集，换模型跑一遍，看工具调用成功率和参数解析错误率。

### 踩坑点

- **上下文被静默截断**：Ollama 老版本默认 `num_ctx` 很小，Agent 的长 system prompt + 工具定义直接被砍头，表现为“模型失忆”。务必显式调大并盯着显存。
- **工具调用格式**：引擎和模型都得声明支持 tools，否则模型输出裸 JSON 文本，框架解析直接失败。选型时优先验证这点。
- **并发打爆显存**：Agent 并行发多个工具调用时容易 OOM。推理侧把并发限到 1，或给 Agent 配请求队列。
- **首 token 越来越慢**：多轮对话每轮全量重算历史。保持 system prompt 前缀稳定，让前缀缓存生效，体感差异明显。
- **散热**：7×24 推理对游戏卡是考验，降功率上限换稳定，值。

### 可复用建议

- **分层路由**：摘要、抽取、格式化交给本地 8B；规划、复杂推理留给 32B 或按需走云端。一个简单的 task router 收益立竿见影。
- **模型当依赖管**：pin 住版本 digest，升级像发版一样先过回归集。
- **托管和健康检查**：systemd 或 Docker 拉起，`/health` 挂进监控，别让 Agent 对着一个死掉的端点反复重试。

### 总结

家用硬件跑本地模型已经从“能跑”到了“能用于生产自动化”。但对 Agent 场景，选型标准要换：工具调用可靠性 > 上下文管理 > 通用智力。本地小模型兜住日常、强模型处理硬骨头，是现阶段最务实的架构。有跑通的组合欢迎在评论区贴配置，一起攒个社区实测清单。
