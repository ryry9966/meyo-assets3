## 背景

目前大多数 Agent 交互仍是“你问它答”：用户不发消息，Agent 就是一段静默的代码。但高频需求里有一大类本质上是被动等来的——每天固定的晨报、CI 挂了要人提醒、某目录出现异常文件要人发现。这些事用户不想“想起来去问”，而是希望系统自己盯着。这就是 proactive 的价值：把触发权从用户手里交给事件和日程。

## 问题

朴素的 proactive 很容易做砸，两种典型失败：

- **太安静**：定时任务跑了，结果全埋在日志里，用户不知道 Agent 干了什么；
- **太吵**：每个事件都触发一次完整推理并推送给用户，三天后用户开始屏蔽它——一个被忽略的 proactive Agent 比没有还糟。

核心矛盾是：什么时候该打断用户，什么时候该自己扛。这是个工程问题，不是模型能力问题。

## 做法

以在 OpenClaw 里搭一个“晨报 + 异常告警”助手为例，我把 proactive 拆成四层：

1. **触发层**。三类来源：cron 定时（固定日程）、webhook / 文件监听插件（外部事件）、阈值轮询（状态监控）。原则：触发层只负责把事带到门口，不做任何判断。
2. **评估层（gatekeeper）**。用一段廉价规则加一次轻量模型调用，把事件分成三档，强制输出 JSON：P0 需立刻处理（主干 CI 失败、报错激增）；P1 值得看但不急（依赖出新版本、某文件被频繁改动）；P2 丢弃但落日志。不要让主模型处理每个原始事件——规则先挡掉 80% 噪音，成本才可控。
3. **行动层**，按档位分级授权：P0 立即推送，附证据链接和建议动作，高风险操作（重启、回滚）只做 dry-run 或草稿，等用户确认；P1 攒进每日 digest，固定时间一次发；P2 只写审计日志。授权级别放配置文件，不要硬编码在 prompt 里。
4. **反馈层**。每次 proactive 推送都记录触发原因、证据、用户是否采纳。每周回看并调整分档判据——这是它唯一“越用越准”的机制。

## 踩坑点

- **自触发死循环**：Agent 自己产生的文件改动又触发了监听器。给所有 self-action 打标记，评估层直接跳过。
- **陈旧状态**：执行动作前必须重新拉实时状态，别用触发时缓存的数据动手，中间状态可能早变了。
- **缺安静时段**：凌晨三点推 P1 是自毁信任。加 quiet hours，非紧急事件一律顺延到下一窗口。
- **只看推送量**：上线后关键指标是中断采纳率（用户点开/回应的比例）和误报率，不是条数。

## 可复用建议

- 先跑两周 **digest-only 模式**：所有事件只进摘要、不允许即时推送，用真实数据校准分档，再放开 P0 直推。
- 评估层输出强制 JSON schema，解析失败一律按 P2 处理——宁可漏报，不可乱报。
- 每条 proactive 行为都带“为什么”：触发源、证据、判据版本，事后可审计。
- 把“什么能直接做、什么只能建议”写成权限清单，随配置发布，不散落在 prompt 里。

## 总结

proactive 的本质不是“更多自动化”，而是“更好的打断判断”。触发层广、评估层省、行动层稳、反馈层闭环——把四层当普通工程组件搭，Agent 才能从“随叫随到”进化到“该出手时才出手”。先保守、后放开，是这个功能唯一靠谱的上线节奏。
