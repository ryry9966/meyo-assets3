## 背景

我们组日常数据源有五六类：Git 提交、CI 流水线结果、服务错误日志、工单系统，再加上群里的临时讨论。日报以前靠人肉拼，格式因人而异，一忙起来就断更。

OpenClaw 体系里现成的积木不少：cron 定时任务、MCP 工具接入、Agent 编排、Skill 做领域封装。上周把日报整条链路搬成了自动化流水线，跑了一周多，记录一下做法和踩的坑。

## 问题

核心矛盾是：原始日志是"给机器看的"，日报是"给人看的"，中间隔着三道坎：

1. 日志量大，直接丢给模型会爆 token，截断后还可能随机丢掉关键报错；
2. 多源数据口径不一致，模型自己猜容易幻觉，比如把测试环境报错当成线上故障；
3. 输出格式不稳定，模型时不时改 Markdown 结构，下游渲染就崩。

## 做法

整条流水线刻意分四层，LLM 只放最后一层：

**1. 采集层（确定性脚本）**
每个数据源一个独立小脚本或 MCP tool：git 拉昨日 commit range、CI 查构建状态、日志服务按 error level 聚合计数。全部只读权限，产出统一 JSON schema，落盘到 `daily/YYYY-MM-DD/` 目录。

**2. 预处理层（纯规则，不进模型）**
用 jq/awk 做聚合：同一错误签名合并成一条带 count 的记录，过滤 DEBUG 噪音，按模块分桶。原则是——凡是规则能确定的，绝不交给模型。

**3. 汇总层（Agent）**
OpenClaw Agent 拿到的是几十 KB 的结构化 JSON，不是几百 MB 的原始日志。Prompt 固定模板 + 固定输出骨架（概览 / 异常 / 变更 / 待办四段），temperature 压到 0.2，每段给一个 few-shot 锁格式。

**4. 分发层**
渲染成 Markdown 后推送到群 webhook，原始 JSON 和报告都留档。cron 每天固定时间跑，失败时发带错误栈的告警——与正常日报用不同标记，一眼能区分。

## 踩坑点

- **别让模型碰原始日志。** 第一版偷懒直接喂日志文件，2 万行被截断后恰好丢了当天唯一的 P2 报错，报告看起来风平浪静。聚合必须放在模型前面。
- **时区。** cron 跑在 UTC，日志时间戳是本地时间，第一天日报少了早上八点前的数据。统一用 UTC 存中间产物，渲染时才转本地时区。
- **空数据要报警，不是发空报告。** 采集脚本挂掉时，LLM 会"礼貌地"编一份看起来正常的日报，连续两天才被发现。现在采集条数为零时直接走失败告警。
- **格式漂移。** 即使锁了骨架，模型偶尔在标题里加修饰词，下游正则匹配失败。后来改成让 Agent 输出 JSON，渲染完全交给模板，彻底解耦。

## 可复用建议

- 中间产物必须有固定 schema 并落盘，随时可离线重跑、复盘"那天模型为什么这么写"；
- 模板和数据分离：改报告样式不动 prompt，改统计口径不动模板；
- 每个数据源独立成 Skill，单独可测，新增一个源只是加一个脚本加一次注册；
- 留一份脱敏样本数据当回归集，改 prompt 后先跑样本对比 diff 再上线。

## 总结

跑下来最大的感受是：自动化日报的价值不在省那十几分钟，而在于数据口径稳定、过程可回溯。LLM 在这条链路里只做"最后一公里的人话翻译"，前面全交给确定性脚本——越克制，越可靠。后续计划把周报、事故复盘初稿也接到同一条流水线上，复用中间产物层。
