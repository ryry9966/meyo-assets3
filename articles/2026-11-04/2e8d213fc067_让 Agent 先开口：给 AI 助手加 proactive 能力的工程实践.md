# 让 Agent 先开口：给 AI 助手加 proactive 能力的工程实践

## 背景

现在大部分 Agent 的交互模型还是“你问它答”：用户不开口，它就永远待机。但真正有用的助手应该是环境驱动的——日历出现冲突、CI 连续三次变红、监控指标越线，这些信号出现时，agent 应该主动站出来，而不是等人去查。OpenClaw 生态里，MCP 已经把工具和数据源的接入标准化了，感知层并不缺，缺的其实是“感知 → 分诊 → 决策 → 行动”这条 proactive 链路的工程设计。

## 问题

主动性最大的坑不是做不出来，而是做出来像骚扰。很多人的第一版是：cron 定时唤醒 LLM，把所有状态一股脑总结后推给用户。三天后用户就把通知关了。核心矛盾在于：agent 没有“值不值得打扰用户”的判断，也没有分级行动机制，于是所有主动性都退化成了刷屏。

## 做法：一条四层流水线

1. **触发层**：cron、webhook、文件监听、状态轮询按需混用。离散的高价值事件走 webhook，连续状态类用低频轮询。触发时只传事件摘要和最小上下文，不要全量拉数据。
2. **分诊层**：用便宜的小模型做第一道判断——“该事件是否值得用户关注”，输出一个分数和理由。低于阈值就落日志，攒进每日摘要。
3. **决策与组装**：过阈值的事件再交给主模型，按需调用 MCP 工具补齐上下文（查日历、看日志、翻历史会话），产出建议动作并标注置信度。
4. **行动分级**：silent（只记录）→ draft（生成草稿等确认）→ notify（推送）→ execute（直接执行，仅限幂等、可回滚操作）。默认权限只放到 draft。
5. **反馈回路**：每条主动消息允许用户反馈“不需要 / 太多 / 刚好”，用于动态调阈值和静默时段。

## 踩坑点

- **自触发循环**：agent 自己发出的消息被自己的 watcher 捕获，形成雪崩。给所有自产事件打标记并在触发层过滤掉。
- **上下文过期**：触发到执行之间状态可能已变，任何 execute 前必须二次校验前置条件。
- **成本失控**：轮询唤醒如果每次都带完整 system prompt，一天几百次调用账单很难看。分诊层必须用小模型，上下文按需加载。
- **权限蔓延**：图省事把 execute 放开，某次误判直接改了线上配置。主动执行的白名单要极小，且每次都留痕。

## 可复用建议

- 先做**日报型 proactive**（低频、汇总、零风险），稳定跑两周再上实时通知。
- 感知、分诊、决策、行动拆成独立模块，别塞进一个大 prompt 里——拆开后每一层都能单独测、单独换模型。
- 所有 proactive 行为写审计日志：什么触发、看了什么数据、做了什么决定。
- 静默时段和每日推送配额是产品体验问题，不是技术细节，第一天就要有。

## 总结

proactive 的本质不是“更聪明”，而是“更克制”。触发器和 MCP 解决的是感知，真正的门槛在打扰控制：分级行动 + 阈值 + 反馈回路三者缺一不可。建议从一个具体场景（比如 CI 失败摘要）把整条链路跑通，再横向复制到其他信号源。主动得恰到好处的助手，才留得住用户。
