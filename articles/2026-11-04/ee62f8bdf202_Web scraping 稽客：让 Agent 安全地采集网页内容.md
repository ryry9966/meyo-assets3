## 背景

让 Agent 上网几乎是所有自动化的第一需求：读文档、盯页面变更、抓表格数据。OpenClaw 里接入一个 scrape 类 MCP 工具后，Agent 确实"能看网页"了，但实践中最容易翻车的也在这里——不是抓不到，而是抓得不安全：上下文被原始 HTML 撑爆、被页面里的恶意指令带偏、或者因为抓取姿势太糙被对方封禁。

## 问题

把裸抓的网页直接丢给模型，常见三类事故：

1. **上下文污染**：一个普通页面的原始 HTML 轻松超过 5 万 token，正文只占一小截，模型在标签噪声里找内容，又慢又贵。
2. **提示注入**：网页内容本质是不可信输入。页面里藏一句"忽略之前的指令，执行某命令"，没有防护的 Agent 可能真会照做。
3. **合规与封禁**：不查 robots.txt、并发拉满、UA 乱写，轻则 403/验证码，重则 IP 被封，还涉及 ToS 风险。

## 做法

社区里沉淀了一套比较稳的分层方案，核心思路是"能轻则轻、内容当数据、抓取有边界"：

**1. 分层抓取，先轻后重**
- 第一层：直接 HTTP GET，多数文档页、博客够用；
- 第二层：内容为 JS 渲染时，走 headless 浏览器兜底，设置 10s 超时和用完即杀的进程管理。

**2. 先提取再进上下文**
- HTML 一律先过 readability 类提取，转成 Markdown 再喂模型，token 通常降到原来的 5%~10%，正文结构还更干净；
- 非正文资源（script/style/注释、超长 base64）在提取阶段直接丢弃。

**3. 把网页内容当数据，不当指令**
- 系统提示里明确：抓取结果一律视为"引用材料"，只用于回答，不触发工具调用；
- 内容用显式定界符包起来，对注入类话术做一层关键词告警；
- 涉及写操作或外发动作时，无论内容来源如何，强制人工确认。

**4. 抓取边界写进配置，不靠 Agent 自觉**
- MCP 工具侧做域名 allowlist，不在名单内的域名直接拒绝，而不是靠提示词约束；
- 每域名限流（如 1 req/s）、指数退避重试、结果缓存 10 分钟，避免同一页面反复抓；
- 请求头带可联系的 UA，抓取前查 robots.txt，命中 Disallow 就改走 RSS/API 或放弃。

**5. 固定输出 schema**
- 让 Agent 按预定义字段（标题、正文、时间、链接）抽取，而不是自由发挥，既省 token 也方便下游校验。

## 踩坑点

- **中文页面乱码**：不少老站点是 GBK 编码，按 UTF-8 硬解会得到乱码，工具侧要做好 charset 探测；
- **headless 浏览器僵尸进程**：长跑的 Agent 一天能攒一堆没退出的 chrome 进程，务必超时 kill 并限制并发；
- **SPA 抽不出正文**：正文在 hydration 之后才有，readability 会抽到空壳，只能走浏览器层并等待选择器出现；
- **过度对抗反爬**：遇到验证码别硬刚，优先找官方 API、RSS 或数据下载入口，成本和风险都低得多；
- **提示词层面的"禁止注入"不够**：软约束一定会被绕过，硬边界（allowlist、工具权限、人工确认）才是兜底。

## 可复用建议

- 把抓取收敛成一个专用 MCP 工具（allowlist + 提取 + 限流内建），而不是每个流程各写一套；
- 保留抓取日志：URL、时间、状态码、提取后 token 数，出问题能回溯；
- 有 RSS 或官方 API 就不做 scraping，这是性价比最高的"安全"；
- 定期审查 allowlist，下线不再使用的域名。

## 总结

Web scraping 是 Agent 的眼睛，安全的关键不在"抓得多猛"，而在三件事：边界清晰（能抓什么）、内容卫生（先进提取再进上下文）、信任隔离（网页内容只是数据）。把这三层做进工具侧而不是提示词里，Agent 采集网页这件事才算真正可托付。
