## 背景

新同事入职第一天的体验，很大程度取决于有没有一份好的 onboarding 文档。OpenClaw 的 agent 每次进入一个工作空间，处境和新同事几乎一样：它能读文件、跑命令、调用 MCP 工具，但它不知道这个空间的“规矩”。AGENTS.md 就是补上这一环的约定——放在工作空间根目录（或子目录）的 Markdown 文件，agent 进入对应目录时会优先读取，作为理解项目、选择工具、约束行为的上下文。

## 问题

没有 AGENTS.md 时的典型表现：

- agent 猜测构建/测试命令，跑错包管理器或用错参数；
- 每个会话都重新踩一遍同样的坑，比如手改了本该由脚本生成的文件；
- 对目录结构的假设是幻觉，反复找不到路径；
- 多 agent、多插件协作时，各自的默认习惯互相冲突。

这些本质上是上下文缺失问题，不是模型能力问题。与其反复在对话里纠正，不如把规矩固化成文件。

## 做法

一份能用的 AGENTS.md，建议按这个顺序写：

1. **项目一句话概述 + 技术栈**：让 agent 快速定位语言和工具链；
2. **常用命令**：构建、测试、lint、本地启动，写成可直接执行的命令，而不是描述性语句；
3. **目录约定**：哪些是生成物不能手改、配置在哪、产物输出到哪；
4. **行为边界**：不要动的文件、不要自动提交、提交信息格式等“不要做”清单；
5. **工具与 MCP 备注**：接了哪些 MCP server、什么场景用哪个、有没有前置条件；
6. **验证方式**：改完代码后 agent 应该自己跑什么来确认。

分层放置：根目录放全局约定，子项目、子目录放更具体的规则，就近覆盖。OpenClaw 的工作空间可以按模块拆分，agent 进入哪一层就读哪一层的文件，避免一份巨型文件管所有事。

篇幅上，目标是 agent 一次能完整读进去，几百行以内。能用链接指到 `docs/` 的内容就别整段复制，减少重复和漂移。

## 踩坑点

- **写成许愿清单**。“代码要优雅”没有信息量，“提交前跑 `pnpm test`”才有。规则必须可执行、可判定。
- **内容过期比没有更糟**。agent 会信以为真地执行过时命令。AGENTS.md 的修改要和代码一起过 review，重构时同步检查。
- **指令互相矛盾**。根目录说用 npm，子目录说用 pnpm，agent 只能猜。出现层级覆盖时，明确写“以本文件为准”。
- **把密钥、内网地址写进去**。AGENTS.md 通常进版本库，也会进 prompt，按公开文档的标准写。
- **从不测试**。写完开一个全新会话，问它“这个项目怎么跑测试”，看它引用的是不是你写的内容，而不是自己的猜测。

## 可复用建议

- 把 AGENTS.md 当 prompt 工程产物维护：每次 agent 犯错，先问“补一条什么具体规则能防住”，然后立刻写进去。
- 排查日志里反复出现的误操作，是文档内容最好的来源，比凭空想规则有效得多。
- 小步迭代，别一次写三百行。先放最痛的十条，观察两三个会话再增删。
- 团队共享同一份文件，保证所有人的 agent 行为一致，而不是每人各养一套私有提示词。

## 总结

AGENTS.md 的本质是把团队的隐性知识显性化，只是读者从人换成了 agent。它不要求文采，要求准确、可执行、持续维护。在 OpenClaw 里把这件事做好，多会话协作的稳定性和一致性会有肉眼可见的提升——而成本只是一个 Markdown 文件，加上一点维护纪律。
