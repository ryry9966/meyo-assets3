## 背景

大多数 Agent 的默认形态是"你问它答"：不提问，它就一直安静待着。但日常里真正有价值的往往是周期性任务——早上汇总日历、定期巡检服务状态、RSS 里出现指定关键词时提醒你。OpenClaw 内置了一个很轻的心跳机制（heartbeat）：Agent 按固定间隔醒来（默认 30 分钟），读取工作区里的 `HEARTBEAT.md`，有活就干，按需推送给你。

## 问题

- 用系统 cron + CLI 也能拼定时任务，但脱离了会话上下文，工具、记忆、聊天渠道都得重接一遍；
- 心跳天然跑在 Agent 会话内，文件工具、MCP、已绑定的渠道直接可用；
- 但很多人把它写成"每 30 分钟总结一次"，很快被消息轰炸和 token 账单劝退。

## 做法

1. **建文件**：`HEARTBEAT.md` 放在 Agent 工作区根目录（默认 `~/.openclaw/workspace/`），没有就新建。
2. **写条件，不写动作**：反例是"总结今天的日历"；正例是"检查今天日历，仅在 15 分钟内有未提醒的会议时通知我；无事可报时只回复 HEARTBEAT，不推送"。
3. **调间隔**：调试期把心跳间隔临时降到 1–2 分钟，跑几轮看日志确认行为，再调回 30 分钟或更长。
4. **接工具**：指令里直接引用 MCP 工具或接口，比如"用 fetch 访问本机 healthz，连续两次非 200 再告诉我"。每次心跳就是一次完整的 Agent 回合，工具照常生效。
5. **拆 Agent**：某类任务复杂到指令写不长，就单开一个专属 Agent，用它自己的工作区和心跳，互不干扰。

## 踩坑点

- **消息轰炸**：指令里没写沉默条件，Agent 每轮都汇报。所有任务应默认静默、异常才说话（report by exception）。
- **重复执行**：心跳是轮询不是精确调度，"每天 9 点发日报"可能一小时内触发多次。要加状态约束"今天已发过则跳过"；精确时刻的任务交给 OpenClaw 的定时任务（cron），心跳只做有状态的条件检查。
- **成本失控**：间隔 × 文件长度 = 每天固定开销。文件控制在十几行内；心跳属于低优先级任务，有条件的话给它单独配个便宜模型。
- **失败行为**：网络抖动、工具报错时要明确写"本轮跳过、下轮重试，不要连发错误消息"。
- **静默时段**：加一条"22:00–08:00 只记录不发消息"，否则半夜挨炸。

## 可复用建议

- 给工作区上 git，`HEARTBEAT.md` 每次改动可回溯，改坏了能 diff 回去。
- 每条指令固定三段式：触发条件 → 动作 → 汇报规则（含静默时段与失败处理）。
- 只读、廉价、可延时的检查留给心跳；需要准点执行的动作交给 cron 或手动触发。
- 单个心跳文件别堆超过 3–5 个任务，一长模型注意力就散，优先级也乱。

## 总结

HEARTBEAT.md 的价值不是"AI 会自己动了"，而是把 Agent 从问答接口变成一个低噪声的值守进程。写好它的原则就一句话：**默认沉默、异常汇报、失败可恢复**。按这个写指令，心跳机制才真正省心，而不是添乱。
