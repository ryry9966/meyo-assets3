# 背景

把 agent 接上 shell 工具后，最大的心理负担不是“它不会做事”，而是“它会不会做错事”。一句含糊的指令，加一条 `rm -rf` 的自动补全，就可能变成一次不可恢复的清理。OpenClaw 的回答不是靠提示词求模型小心，而是把工具执行整体搬进了隔离层。

# 问题：风险被拆成三段

默认配置下，agent 的 exec 工具并不直接跑在你的登录环境里。真正接触宿主机文件的只有 gateway 守护进程；agent 发起的命令先经过 gateway 的策略检查，再落进 sandbox 执行。于是“误删”被拆成三个独立问题：

1. 命令能不能被放行（审批策略）；
2. 进了沙箱能看到什么（文件系统视图）；
3. 看到了能不能写（挂载权限）。

三层任一拦截，破坏都到不了你的数据。

# 做法：最小可复现配置

1. 启用 Docker 沙箱模式（如 `sandbox.mode: "all"`），exec 及多数工具调用落在一次性容器里，会话结束即销毁。
2. 只把 workspace 目录以卷形式挂进容器——这是 agent 唯一“看得见”的持久目录，宿主机其他路径在容器命名空间里默认不存在。
3. 设置分级审批：沙箱内静默执行，宿主机侧命令一律 ask 或 deny，不要把全量放行当默认值。
4. 需要共享资料优先只读挂载；确有写需求再缩到具体子目录。
5. 验证：新会话里让 agent 执行 `ls /`、对工作区外路径建文件、删除一个测试文件，观察哪些被拒、哪些落空。这五分钟能换来对边界的确信。

# 踩坑点

- **把 `$HOME` 整个挂进容器等于没沙箱**。容器隔离了进程，挂载重新打开了门。
- **挂载 Docker socket 等于交出宿主机 root**，容器内可起特权容器，工具类场景基本没有正当理由。
- **符号链接**：容器内建的软链指向宿主路径是无效的，解析发生在容器命名空间内；但挂载源目录若本身含外部软链，行为取决于挂载方式——原则仍是最小挂载。
- **网络隔离与依赖安装的矛盾**：默认断网最安全，但装不了包。折中是构建期联网、运行期断网，或只对特定 registry 开白名单。
- **审批疲劳**：把 ask 配成“总是允许”，几次之后就退化为全放行，审批日志要定期回看。
- **沙箱不是备份**：workspace 卷内的文件 agent 依然删得掉，只是损失被限制在工作区内，定时快照该做还是要做。

# 可复用建议

- 最小挂载、默认拒绝、写权限只给 workspace，三条作为所有 agent 项目的起手配置。
- 固定一套“破坏性回归用例”：删文件、读敏感路径、装包、联网。沙箱配置每次变更后跑一遍。
- 工具能力按读、写、执行、网络四级审视必要性，不整体放行。
- 别用提示词替代权限：模型是概率系统，边界必须是确定性系统。

# 总结

Agent 不会误删你的文件，不是因为模型“懂事”，而是因为它的 `rm` 只能落在一个它看得见、可抛弃的容器里。OpenClaw sandbox 的核心是纵深防御：gateway 收口执行入口，容器圈定文件系统视图，审批策略兜底高危操作。提示词会漂移，配置不会——把安全从“求模型”变成“限环境”，自动化才敢真正上生产。
