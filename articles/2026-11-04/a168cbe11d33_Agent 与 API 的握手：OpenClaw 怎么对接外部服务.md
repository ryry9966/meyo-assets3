## 背景

Agent 本身只会"说"，真正能"做事"，靠的是身后那层工具。在 OpenClaw 里，这层工具主要有三种形态：挂载 MCP server、写插件/skill、或者直接注册一个 HTTP 工具。不管走哪条路，本质是同一件事：把外部服务的 API，翻译成模型能理解、能正确调用的接口。我习惯把这叫"握手"——双方要约定好语言、凭证和容错方式，缺一样都会握手失败。

## 问题

服务接多了之后，故障点其实很集中：

- **凭证管理混乱**：key 硬编码在配置里，日志一打就泄漏；
- **工具描述含糊**：模型靠猜参数，十次里三次传错；
- **返回值不加工**：上游吐几 KB 的 JSON，原样塞进上下文，几轮对话就撑爆；
- **没有超时和重试**：上游一慢，整个会话卡死。

## 做法

我的接入流程固定五步：

1. **选路径**。服务有现成的 MCP server 就直接挂上；没有就写一个薄 skill 封装 HTTP 请求，不要让模型自己拼 URL 和 query string。
2. **管凭证**。API key 全部走环境变量，或权限收紧到 600 的配置文件；读和写拆成不同 token，写操作用最小权限。
3. **收窄接口**。一个工具只做一件事，输入用 schema 约束，描述里写清参数含义、单位和边界。工具描述是写给模型看的文档，值得花时间打磨——这往往是命中率高低的分水岭。
4. **加工返回值**。只挑模型需要的字段，长列表截断或分页，附一句"已省略 N 条"。
5. **加护栏**。设超时；读操作做指数退避重试；写操作带幂等 key，重试才不会重复建单。错误信息返回结构化、模型能读懂的原因，方便它自己纠正参数再来一次。

## 踩坑点

- 上游返回 429 时别原样抛给模型，先退避重试，否则它可能连环重发把配额打穿；
- 非幂等的 POST 直接重试，会多出一堆重复资源，我踩过；
- 长任务（导出、批处理）不要同步等，返回任务 ID 让 agent 轮询，否则会话直接挂起；
- 日志记得脱敏，error message 里带 Authorization header 的情况并不少见；
- 工具越多模型越容易选错，暂时用不到的先关掉。

## 可复用建议

给自己定一份 checklist：单一职责、schema 校验、超时、重试、幂等、日志脱敏、dry-run 开关。灰度顺序固定为：只读 → dry-run → 带确认的写操作。新服务接入先跑一天只读，观察参数命中率和返回截断情况，再放开写。这套流程迁移到任何新服务上，基本只需要换掉薄封装那一层。

## 总结

Agent 对接外部服务，本质上是在为模型写一份"可执行的接口文档"。接口越窄、约定越显式、失败越可观察，握手就越稳。OpenClaw 在工具层给的自由度很足，但稳定性得靠自己把每层护栏补齐——活儿不难，只是琐碎，值得一次性做对。
