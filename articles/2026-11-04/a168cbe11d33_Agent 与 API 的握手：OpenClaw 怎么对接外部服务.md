## 背景

Agent 的价值往往不在对话本身，而在能否替你调外部服务：查工单、发通知、拉报表、操作内部系统。OpenClaw 里常见的对接方式有三种：在 skill/插件里直接发 HTTP、起一个 MCP server 把 API 包成工具、或用内置 HTTP 工具直连。三种都能跑，但选错位置，后期维护成本会翻倍。

## 问题

把原始 API 直接丢给 Agent，典型麻烦是：认证散落各处、容易泄漏；工具描述写不清，模型乱传参或干脆不调用；接口报错是给人看的，Agent 收到 `500` 只会傻 retry；限流和超时没兜底，一轮循环调用就把配额打爆。

本质是：API 的契约面向程序，而 Agent 需要一份**模型读得懂的契约**。握手失败，多数时候不是网络问题，是这一层没做。

## 做法

以对接一个内部工单系统为例，我们的大致步骤：

1. **先定工具边界，再看接口文档。** 不要按 endpoint 一比一暴露，把 `GET /tickets` 和 `GET /tickets/:id` 合并成 `search_tickets(query, status, limit)`，按任务粒度切工具。单个 server 控制在 5–10 个工具。
2. **认证收口。** token 走环境变量或密钥管理，在 MCP server 层统一注入 header，Agent 上下文里永远不出现凭证。
3. **description 写给模型看。** 说清何时该用、何时不该用、参数含义、返回结构示例。这部分是握手的核心，值得花一半的时间。
4. **错误结构化。** 失败时返回错误码、一句话原因、建议下一步（如 `rate_limited, retry after 30s`），让模型有路可走，而不是靠猜。
5. **加兜底。** 统一超时、指数退避、分页强制上限；写操作加幂等键，防止模型重试导致重复建单。
6. **先灰度。** 用测试环境 key 跑通全流程，打开工具调用日志，人工核对参数后再放开。

## 踩坑点

- **工具太碎。** 一次挂 20 个工具后，模型选错率明显上升，表现为"明明有查询工具却先猜答案"。合并成任务级工具后明显好转。
- **布尔参数歧义。** 模型常给 `is_urgent` 传字符串 `"true"`，schema 里要严格限定类型，或在描述里给示例。
- **报错太笼统。** 只返回 `failed` 会引发无限重试；多给一个 `insufficient_permission`，行为就完全不同。
- **慢接口拖死会话。** 超过 30s 的同步调用建议改成异步任务 + 轮询，工具先返回任务 ID。
- **日志带敏感数据。** 工具调用日志默认全量记录请求体，接含个人信息的接口务必脱敏。

## 可复用建议

- 把工具描述、错误结构、超时策略当成独立交付物来 review，与代码同权重。
- 给每个 MCP server 写最小 contract 测试：schema 稳定、错误码稳定，避免上游升级时静默破坏 Agent 行为。
- 记录 request id 串起 Agent 会话与后端日志，排障效率差别巨大。
- 工具超量就按业务域拆 server，而不是往一个 server 里堆。

## 总结

Agent 对接外部服务，难点不在"能不能调通"，而在契约转换：把面向程序的 API，翻译成面向模型的工具。选 skill、插件还是 MCP 并不关键，关键是把工具边界、认证收口、错误语义、兜底策略这四件事做扎实。做完之后你会发现，Agent 的出错点会从"调不到接口"变成"业务判断"——那才是它该出错的地方。
