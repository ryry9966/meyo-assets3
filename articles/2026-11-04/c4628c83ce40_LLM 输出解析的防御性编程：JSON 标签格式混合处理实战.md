## 背景

在 OpenClaw 的插件和 Agent 工作流里，LLM 输出是下游一切动作的起点。我们常在 prompt 里写“请只输出 JSON"，但模型实际返回的往往是代码围栏、XML 风格标签、裸 JSON、甚至散文夹 JSON 的混合体。解析层如果只按理想格式写，坏一次就是整条链路断一次。

## 问题：格式承诺不可信

实测同一模型、同一段 prompt，几天内能出现至少五种格式：

1. ` ```json ` 围栏
2. ` ``` `（无语言标注）或 ` ```JSON `（大写）
3. `<json>...</json>`、`<result>...</result>` 等标签包裹
4. 裸 JSON，但前后有空行或一句解释
5. JSON 字符串里嵌了代码，内部又出现 ` ``` `，导致围栏配对错乱

外加隐性炸弹：尾逗号、中文引号（“”）、`NaN`、控制字符。注意 `json.loads` 对 `NaN/Infinity` 是默认放行的，这不是标准 JSON，序列化回传时才炸。

## 做法：五层降级解析管线

核心思路是逐层降级，每层只解决一类问题，任何一层成功即返回：

```python
# 第一层：直接解析（用 parse_constant 拒掉 NaN/Infinity）
json.loads(s, parse_constant=lambda x: (_ for _ in ()).throw(ValueError))

# 第二层：剥围栏，容忍语言标注大小写和缺失，非贪婪、只剥最外层
^```[a-zA-Z]*\s*\n([\s\S]*?)\n?```\s*$

# 第三层：剥 XML 风格标签，维护一个已知标签集合
# 第四层：括号截取，取第一个 { 到最后一个 }
# 第五层：容错修复（有损，必须放最后）
```

第五层去尾逗号、统一中文引号、剔控制字符，或直接用 `json_repair` 这类库。**修复是有损操作，永远放在兜底位置。**

解析成功不等于结束：上 pydantic / jsonschema 做结构校验，字段类型、枚举值、必填项都要过。校验失败进入重试，把“上次输出在 X 处不合法”拼回 prompt 作为反馈，上限 2 次；超限带原始输出进死信队列并告警，不要静默吞掉。

## 踩坑点

- **贪婪匹配围栏**：用贪婪配对 ` ``` ` 会把 JSON 字符串内部的 ` ``` ` 也吃进去，截取错位。务必非贪婪加首尾锚定。
- **括号截取对多对象输出失效**：模型偶尔一次吐两个 JSON 对象，首尾截取会拼成一个坏串。截取前先用括号计数切分。
- **修复层过激**：盲目把所有 `'` 换成 `"` 会破坏字符串里的撇号，只修已确认的坏模式。
- **别裸吞异常**：每层失败要分类计数（`raw_ok / fence / tag / brace / repaired / failed`），否则你永远不知道模型格式漂移到什么程度。
- **结构化输出 API 也要校验**：`json_schema` / tool call 能大幅降低漂移，但不等于零漂移，校验层保留。

## 可复用建议

- 做成**共享工具函数**，别每个插件复制一份解析逻辑——策略一改就是十处同步。
- 建一个**脏输出语料库**：线上解析失败就把原始输出存档，回归测试直接跑这批语料，比手造 case 真实得多。
- 开发期 fail loudly，生产期带重试上限静默恢复，但失败必须进日志和指标。
- 换模型或升版本时，先跑一遍解析成功率的分层数据——格式漂移往往是最早的回归信号。

## 总结

模型输出就是不可信输入，解析层是边界防御。分层降级 + 结构校验 + 分类观测，三件事做齐，JSON 解析就从“偶尔炸”变成“可度量的常态”。代码量不大，但这层写扎实了，上游所有 Agent 流程都省心。
