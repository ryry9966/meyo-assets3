## 背景

把模型接到真实世界这件事，过去两年大家各干各的：function calling、自研插件体系、手写胶水代码调 API。痛点很具体——每个 Agent 运行时要单独适配每个工具。3 个 Agent 对接 10 个数据源，就是 30 份互不兼容的集成代码。

2024 年底 Anthropic 开源了 Model Context Protocol（MCP），把「模型如何获取工具和数据」标准化了。它本质是一层协议约定，不是框架，也不是产品。

## 它解决的是什么问题

一句话：**把 M×N 的集成问题变成 M+N**。

- 以前：每个 Agent 应用（M）为每个工具/数据源（N）写定制适配；
- 现在：工具方实现一次 MCP Server，Agent 方实现一次 MCP Client，按协议握手即可互通。

核心概念只有三个，先分清：

- **Tool**：模型可调用的动作（查库、发请求、写文件），由模型决定何时调用；
- **Resource**：提供给模型读取的上下文数据，由应用侧控制注入时机；
- **Prompt**：预置提示模板，由用户触发。

传输层主流两种：本地进程用 stdio，远程用 Streamable HTTP；消息格式是 JSON-RPC 2.0，握手时协商能力。理解到这个程度就够动手了。

## 最小实践步骤

以 Python 为例，十行左右跑通一个 Server：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo-tools")

@mcp.tool()
def query_order(order_id: str) -> str:
    """按订单号查询订单状态，返回 JSON 字符串。"""
    return db.get_order(order_id)

mcp.run()  # stdio 模式
```

流程建议：

1. 用官方 SDK 定义 3~5 个工具，写清参数 schema 和 docstring；
2. 用 `npx @modelcontextprotocol/inspector` 起 Inspector，脱离 Agent 单独调试 Server；
3. 调通后把启动命令配置进 Agent 宿主（OpenClaw 的 MCP 接入同理），重启会话验证；
4. 远程部署时再换 Streamable HTTP + 鉴权，别第一天就上远程。

## 踩坑点

1. **stdio 模式的环境问题**。Server 进程是宿主拉起的，工作目录、Python/Node 版本、环境变量都和你的终端不一样。报 command not found 十有八九是路径问题，用绝对路径启动最稳。
2. **工具描述是写给模型看的，不是写给人的**。模型选工具只依赖名称、描述和 schema。`get_data(id)` 这种命名模型基本靠猜，误调用率很高。描述里写清楚：做什么、参数含义、返回什么、什么场景该用。
3. **工具数量爆炸**。几十个工具挂上去，模型选择困难，上下文也被描述占满。按场景拆分 Server，按需挂载。
4. **协议版本与传输方式不匹配**。早期 SSE 传输已被 Streamable HTTP 取代，新旧客户端/服务端混用会握手失败，先核对协议版本日期。
5. **安全别裸奔**。第三方 Server 的工具返回会进入模型上下文，等于多了一条 prompt injection 通道。只装来源可信的 Server；删数据、付款类操作务必加人工确认。

## 可复用建议

- 工具设计尽量**无状态、幂等、快返回**；长任务返回任务 ID，别让模型同步等 60 秒。
- 报错信息也是给模型看的上下文。写清楚「缺什么参数、该怎么改」，模型能自纠错。
- 先在 Inspector 里把异常路径测全，再接 Agent，能省大量联调时间。
- 工具粒度宁粗勿细：一个 `create_issue` 好过 auth + validate + create + confirm 四连调。

## 总结

MCP 本身没有魔法，它只是把 Agent ↔ 工具这层接口标准化了，价值上限取决于你工具设计的质量。实践路径很清晰：SDK 写 Server → Inspector 单测 → 接入 Agent → 再考虑远程化。把工具描述当 prompt 写、把错误信息当上下文写，MCP 的体验会好一个档次。
