## 背景

跑 OpenClaw 这类常驻 Agent 时间长了会发现：工具权限、插件、MCP 都配好了，但 Agent 的"性格"始终不稳定——今天话痨，明天高冷；有时自作主张替你发消息，有时又在该动手时反复确认。这些问题的根源大多不在能力，而在没人告诉它"你是谁、什么能做、什么必须先问"。

OpenClaw 的 workspace 里有个约定文件 SOUL.md，就是干这个的：和管任务的 AGENTS.md、管记忆的 MEMORY.md 分开，专门承载人格与边界。

## 问题

我最初没写 SOUL.md，踩到三类典型问题：

1. **风格漂移**。换模型或开新会话后，语气、详略程度明显变化，像团队里换了人。
2. **边界模糊**。它会直接执行"帮我把这段话发到群里"这类不可逆操作，事后才补一句"已发送"。
3. **规则散落**。早期我把约束写在代码里的 system prompt 和零散提示词里，改一次要动好几处，也没有版本记录。

## 做法

我的 SOUL.md 目前 60 行左右，分四段：

- **身份**：一段话说清它是谁、服务谁、用什么口吻说话。写"直接、简洁、先给结论"，而不是"专业友好"。
- **行为准则**：3–5 条按优先级排序的原则，比如"事实不确定时明说不知道，禁止编造""回复默认 5 句以内"。
- **硬边界**：不可逆操作必须先确认——发消息、删文件、花钱、对外承诺时间。写成可判定的规则："凡向外部发送内容的动作，必须先展示完整内容并等待确认"。
- **失败行为**：拿不准时停下提问，而不是猜。

流程上：文件进 Git，Agent 每出现一次不想要的行为，就补一条针对性规则，跑两个已知触发场景验证后再合并。相当于给人格做 code review。

## 踩坑点

- **写太长**。第一版 200 多行，模型明显抓不住重点，砍到 60 行后遵从率反而上去了。
- **形容词没用**。"谨慎一点""语气专业"基本无效，必须是可执行、可验证的行为规则。
- **和 AGENTS.md 抢地盘**。有段时间两边都写了确认逻辑，规则冲突后行为很怪。现在约定：SOUL.md 只管"是谁和边界"，AGENTS.md 只管"怎么干活"。
- **过度矫正**。一次糟糕回复就加一条重规则，几轮下来互相打架。现在加规则前先判断是不是普遍问题。
- **别拿它当安全屏障**。人格约束挡不住注入和误调用，真正的红线要靠工具权限、白名单这些硬机制兜底，SOUL.md 只是第一层。

## 可复用建议

- 四段模板起步：身份 / 行为准则 / 硬边界 / 失败行为，每段先写 2–3 条。
- 规则用祈使句 + 可判定条件，不写形容词。
- 一次事件加一条规则，小步迭代，Git 管理。
- 换模型后重测一遍触发场景——人格文件应当模型无关，但实际效果不保证。

## 总结

SOUL.md 是个成本极低、杠杆很高的文件：几十行 Markdown，换来的是行为可预期、边界可审计。把它当代码维护——版本化、小步改、有验证——比在对话里反复纠正 Agent 划算得多。
