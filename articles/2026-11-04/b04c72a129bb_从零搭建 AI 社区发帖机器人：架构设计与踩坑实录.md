## 背景

社区每天产生大量讨论，精华内容散落在不同频道里，人工整理每日精选耗时且容易漏。目标很朴素：让一个机器人每天定时拉取讨论、生成摘要草稿、经确认后自动发帖。技术栈基于 OpenClaw 的 Agent 能力，社区 API 和数据库通过 MCP 工具接入。

## 问题

最初的做法是直接让 LLM「每天总结并发帖」，跑了三天就翻车：同一天发帖两次、编造了不存在的讨论、触发平台限流被临时封禁。复盘下来核心矛盾很清楚：**LLM 负责生成，但发布这件事必须确定性、可回滚**。把两件事混在一个提示词里解决，注定不稳。

## 做法

最终架构拆成五层：

1. **采集层**：MCP 工具封装社区 API，拉取近 24 小时讨论原文，落库 SQLite。
2. **处理层**：OpenClaw Agent 分两步——先用小模型对内容做相关性打分和去重，再用大模型基于原文生成摘要草稿，要求每条摘要附带原帖引用。
3. **审核层**：草稿写入待审队列，默认 dry-run 只写日志；自动发布开启前必须人工确认。
4. **发布层**：带幂等键（内容哈希 + 日期）的发布器，失败重试最多 3 次，指数退避。
5. **调度层**：cron 触发，显式声明时区；每次运行记录状态、耗时和 token 消耗。

代码量其实不大。状态表只有一张：`posts(id, idempotency_key, status, created_at)`，状态机为 `draft → approved → published / failed`，全部逻辑围绕这张表展开。

## 踩坑点

- **重复发帖**：重试逻辑和调度器叠加，同一天发了两次。修复：幂等键入库前先查、发布前再校验，数据库唯一索引兜底。
- **幻觉链接**：模型会「补全」看起来合理的帖子 ID。修复：摘要只能引用采集层落库的原文 ID，URL 一律由代码拼接，禁止模型生成。
- **时区坑**：容器内是 UTC，配置里写的「每天 9 点」实际 17 点才跑。修复：调度配置显式声明时区，日志打印本地时间。
- **限流封禁**：重试没有退避，连续打爆接口。修复：指数退避 + 全局速率限制 + 收到 429 时熔断 30 分钟。
- **成本失控**：每轮把全量讨论塞给大模型。修复：小模型先过滤，进入大模型的内容量降了约 80%。

## 可复用建议

1. 先跑一周 dry-run，人工看日志确认质量，再开自动发布。
2. 模型可以生成内容，但不能生成「事实」——链接、ID、时间戳一律由代码负责。
3. 幂等键 + 单张状态表是最小可靠方案，别一上来就引入消息队列。
4. 运行状态和 token 消耗写进日志，出问题时才有据可查。
5. 自动发布范围从小起步：先一个频道、先一种帖子类型，稳定后再扩。

## 总结

整个项目代码不到 500 行，但 90% 的精力花在「让发布变得可信」上：幂等、退避、审核、回滚。LLM 部分反而是最简单的。给想复刻的同学一句建议：先把状态落库、先跑 dry-run，再谈自动化——顺序反了，大概率重走我的踩坑路线。
