2025 年 11 月底，安全圈集体坐直了：Anthropic 披露，一款尚未正式发布的模型，在发布前的内部安全评估里以 agent 形式自主审计代码，结果在 Linux 内核中挖出一个此前无人知晓的漏洞（zero-day），内核社区确认并修复。这不是 AI 第一次找到真实 0-day，但"未发布模型 + 系统级内核"两个关键词叠在一起，基本宣告 AI 漏洞挖掘从实验室 demo 走进了实战期。这篇拆三件事：这类漏洞为什么致命、AI 到底怎么挖、以及"未发布"这个细节意味着什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-04/13beddc1cc3d9392.png)

## 事件回顾：一次发布前的"体检"，跑出了意外结果

- 经过其实很朴素：Anthropic 按惯例对预发布模型做能力与安全评估，其中一项就是让模型以 agent 方式对开源代码做漏洞挖掘。模型在 Linux 内核中报告了一个未知漏洞，维护者确认属实，补丁随后合入。
- 从公开报道看，这是一个典型的内存安全类问题——use-after-free、越界访问这一族。别嫌这个词出现频率高，它们就是历年内核 CVE 里的绝对主力。
- 披露流程也是标准动作：先报给内核社区，补丁落地后再对外说明。厂商不公开全部技术细节属于常规操作，避免给在野攻击者递刀。
- 拉长时间线看更清楚：2024 年 10 月，Google Project Zero 的 agent "Big Sleep" 首次在主流软件 SQLite 中发现 0-day；据公开披露，2025 年它又在 Linux 内核确认了新的内存安全问题；同年 8 月 DARPA 的 AIxCC 决赛上，参赛 AI 系统在真实开源项目里找出了多个此前未知的漏洞并自动生成修复。几个月内连续发生，这是趋势，不是孤例。

## 为什么内核漏洞是"系统级致命"？

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-04/63205efb38a59657.png)

- **权限最高**。内核运行在 CPU 最高特权级，一个内核漏洞一旦可利用，约等于整台机器、整部手机直接沦陷。杀软、沙箱、容器全都建立在"内核可信"这个假设上——内核失守，这些防线一起作废。
- **影响面巨大**。Linux 跑着全球大多数服务器、安卓手机、路由器、车载系统。内核补丁还要经设备厂商层层适配，大量老旧设备可能永远等不到更新。
- **use-after-free 一句话原理**：内核把一块内存释放了，但某个指针没清干净、还在引用它；攻击者趁机"占坑"，用构造好的数据填回那块内存，让旧指针读到攻击者控制的内容，最终劫持执行流。KASLR、CFI 这些缓解措施能抬高攻击成本，但攻防从未停过。
- **攻击面也大**：300 多个系统调用、上千个驱动、超过 3000 万行 C 代码。多项统计口径下，内核 CVE 里七成上下都是内存安全问题。这不是 Linux 写得差，是 C 语言先天缺护栏。

## AI 挖洞和传统 fuzzing，到底差在哪

- 传统方案是 syzkaller 这类内核 fuzzer，打法类似"暴力穷举"：随机变异系统调用序列，靠覆盖率反馈往深处推。优点是全自动，缺点是只能打到浅层 bug，而且报出的 crash 噪音大，人工分诊成本高。
- LLM agent 更像一个不用睡觉的审计员：通读代码建立状态模型 → 提出假设（"这条路径释放了对象，另一条路径在锁外还会引用它"）→ 写触发代码丢进沙箱虚拟机验证 → 按结果迭代。它找的是"推理出来的漏洞"，不是"撞出来的崩溃"，产出少，但信噪比高。
- 成本结构变了：过去审计一个大型 C 项目需要资深研究员几周到几个月；agent 可以 7×24 跑，几小时到几天出一批候选。人负责直觉和验证，机器负责读不完的代码——分工重排了。
- 局限也得说清：模型会"脑补"出不存在的漏洞（幻觉），PoC 必须能实际跑通才算数；对依赖复杂环境交互的逻辑型漏洞，目前仍然吃力。所以它现在更像给人类审计员装了放大镜，而不是替掉人类。

## "未发布模型"这个细节，比漏洞本身更有信息量

- 这不是猎奇，是评估体系的一部分。Anthropic 的 Responsible Scaling Policy 把"模型能否自主发现真实漏洞"列为能力红线之一，触发红线就要上更严格的部署管控。换句话说，这个 0-day 本身就是发布前体检的成绩单。
- 对行业，它给出了一个新的能力刻度：agent 能完成"读几十万行代码 → 形成假设 → 构造 PoC → 独立验证"这种长程工程任务，而不只是答题和写 demo。这对所有做 coding agent 的团队都是一个参考点。
- 双刃剑属性拉满：同样的能力，防御者用来提前修洞，攻击者用来批量挖洞、写 exploit。0-day 正在从"稀缺资源"变成"流水线产能"，攻防双方的成本曲线都在被重写。
- 流程问题随之浮出水面：AI 提交的漏洞报告会越来越多，开源维护者本来就人手紧张，接下来要面对的是"分诊洪峰"——AI 报告怎么验证、怎么披露、责任归谁，社区规范还在草创期。

## 三条实用建议与冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-04/4ccf948cc205ae9b.png)

- **补丁窗口变短了**。0-day 的发现周期从"数月"被压到"数天"，干等就是最大的风险。服务器建议配好自动安全更新（如 unattended-upgrades）和内核 live patch；手机、路由器、NAS 尽量选还在收安全更新的型号，过保设备别再裸奔在公网。
- **开发者的主战场仍是内存安全**。新代码认真考虑 Rust（Linux 内核已正式支持）；CI 里把 KASAN、KFENCE、UBSAN 这类 sanitizer 当默认配置；引用计数和锁的 review 要有固定清单。收到 AI 报的 bug，别当噪音忽略，也别直接当真——只认可复现的 PoC。
- **冷思考：最脆弱的不是技术，是开源生态的人力**。AI 把审计成本打了下来，但如果维护者分诊不过来，漏洞照样躺在代码里没人看。资助关键开源项目（OpenSSF 这类组织）的钱，比以往任何时候都花得值。攻防的胜负手，正在从"谁手里的 0-day 多"，变成"谁的修复流水线跑得快"。
