## 背景

社区里不少人已经把内容生产交给 Agent：读 issue、看代码 diff、产出周报或技术文章。AI 输出 Markdown 几乎是默认能力，但"生成"和"发布"之间隔着一段被低估的距离——公众号、知乎、掘金、博客对 Markdown 的支持各不相同，真正的脏活是格式适配。

## 问题

我们最早的做法是让 Agent 直接生成"公众号版""知乎版"两份文本，结果很难维护：

- 同一篇内容存在多个副本，改一处要同步多处；
- 模型产出的"方言"不稳定：这次写内联 HTML，下次用脚注，随采样参数漂移；
- 各平台差异点（外链、表格、代码高亮、图片防盗链）散落在 prompt 里，没有单一事实来源。

本质上这是工程问题：需要一条以 Markdown 为中间表示（IR）的管线，而不是一堆互相覆盖的 prompt。

## 做法

管线拆成四段，每段职责单一：

1. **归一化**。AI 只产出内容，约定输出 GFM + YAML frontmatter。脚本强制清洗：标题层级统一（正文从 h2 起）、剥离非白名单 HTML、脚注降级为普通引用标记、CJK 与拉丁字符间补空格。产出一个平台无关的标准文档。
2. **元数据驱动**。标题、摘要、tags、cover 以及 `platforms: [wechat, zhihu, blog]` 全部写在 frontmatter，发布脚本据此决定调用哪些适配器。Agent 不再感知平台细节。
3. **平台适配器**。每个平台一个纯函数：标准文档进，平台文档出。公众号适配器把外链转成文末引用列表、代码块转成内联样式 HTML；知乎适配器把表格压到 5 列以内；博客适配器基本直通。适配器互不依赖，可单独测试。
4. **发布**。图片先统一上传，替换为目标平台可访问的 URL，再通过 MCP 工具推送。发布动作做成幂等：同一篇重复执行不会产生重复草稿。

Agent 侧我们不让它"写公众号文章"，只让它调用 `pipeline.publish(source_md, platforms)`，格式转换全部发生在工具内部。模型处理内容，管线处理排版。

## 踩坑点

- **模型爱写 HTML**：prompt 里禁了也偶尔冒出 `<div>`，归一化必须做白名单清洗，不能靠提示词自觉。
- **公众号外链被静默吞掉**：不报错，渲染后直接消失。适配器里显式转成 `[1]` 引用比事后人工检查靠谱。
- **图片防盗链**：GitHub 图床的图在微信里可能裂图，必须二次上传并保留 URL 映射，方便重发。
- **frontmatter 污染**：正文里出现 `---` 会破坏解析，生成阶段要求用 `***` 做分隔线，或归一化时转义。
- **表格移动端溢出**：宽表格在公众号基本不可用，我们的硬规则是超过 4 列转列表。

## 可复用建议

- 平台差异写进适配器，内容规范写进归一化器，两者进版本库、走 code review；prompt 里只留"写什么"，不留"怎么排"。
- 每个适配器配 golden file 测试：固定输入比对输出，平台规则更新时不至于悄悄回归。
- 发布一律走工具/MCP 调用并落日志，不要让 Agent 直接持有账号凭证自由发挥。
- 管线必须幂等，重跑成本低，自动化才敢放开。

## 总结

多平台发布的痛点不在 AI 生成，而在适配。把 Markdown 当 IR、平台当后端、适配规则当代码，内容只写一次，格式问题收敛到几个可测试的纯函数里。Agent 负责内容，管线负责确定性——边界清楚之后，自动化才推得动。
