## 背景

Agent 和传统脚本的区别在于：它不是一次调用，而是一个循环。模型每轮都可能发起工具调用，一次任务跑十几个外部 API 很正常——LLM 提供商、搜索、数据库、各种 MCP 插件。任何一环抖动，整个循环就会出问题。传统服务挂了会返回 500，Agent 挂了往往表现得更糟：模型开始凭记忆编造结果，或者陷入高速重试烧 token。

所以错误恢复不是"加个 try-catch"的事，而是 Agent 工程里的一等公民。

## 问题拆解

外部 API 的故障基本分三类：

1. **瞬时故障**：超时、429 限流、503，大概率重试就好。
2. **持久故障**：401 鉴权过期、配额用完、参数错误，重试一百次也没用。
3. **模糊故障**：请求发出去了，然后超时了。你不知道服务端到底执行没有——这类最危险，直接重试可能造成重复下单、重复发消息。

Agent 场景还多一个问题：**谁来做恢复决策**。把重试逻辑完全交给模型（在 prompt 里说"失败了就重试"），你会看到它在循环里疯狂重试，或者干脆无视失败继续编。

## 做法

我们的原则是把恢复机制全放代码层，模型只拿"诚实的信息"：

**第一步：统一出口。** 所有工具调用走同一个封装：设超时硬顶（如 10s），拿到响应或异常后先按上面三类打标。

**第二步：分类处置。** 瞬时故障走指数退避 + 抖动重试，最多 3 次，429 要读 `Retry-After`；持久故障不重试，直接返回结构化错误；模糊故障只在操作幂等时才重试，写操作必须带幂等键。

**第三步：熔断。** 同一工具连续失败 5 次就熔断一段时间，后续调用直接短路，返回"该工具暂不可用"。比每次都等 10s 超时再重试省得多。

**第四步：给模型结构化错误。** 不要抛裸异常。返回类似 `{retryable: false, reason: "auth expired", suggest: "提示用户更新凭证"}` 的对象。模型拿到明确的分类和建议，决策质量高很多；拿到一堆 stack trace，它只会瞎猜。

**第五步：降级路径。** 关键工具准备备胎：备用 provider、缓存的最近一次成功结果，或者声明"本步跳过、任务降级继续"。任务状态落盘，恢复时从断点续跑，而不是从头来。

## 踩坑点

- **让模型控制重试节奏**是最大的坑。重试必须由代码执行，prompt 里只告诉它"已重试 N 次仍失败"。
- **非幂等操作盲重试**：我们早期重复发过消息。现在所有写操作默认带幂等键。
- **吞掉错误**：工具失败但返回空结果，模型会把空数据当真数据继续推理，产出看起来很合理的假答案。宁可失败得响亮。
- **退避无上限**：退避要受总 deadline 约束，否则任务挂死比失败更难排查。
- **熔断阈值太低**：单次失败就熔断会误伤健康请求，连续失败计数至少从 3 起步。

## 可复用建议

- 把"超时 + 分类 + 重试 + 熔断 + 结构化错误"做成一个通用工具包装器，所有 MCP 工具统一过一遍，别每个插件各写一套。
- 在工具 schema 里就定义好错误返回格式，作为团队约定。
- CI 里做故障注入：mock 一个必挂的 API，验证 Agent 是优雅降级而不是死循环。

## 总结

外部 API 一定会挂，问题只是什么时候。Agent 的错误恢复本质是一道工程题：**重试的机械动作交给代码，判断和决策交给模型，但前提是你给模型的错误信息是诚实且结构化的**。把这条边界划清楚，Agent 在故障面前才像个可靠的系统，而不是一个会编故事的对话者。
