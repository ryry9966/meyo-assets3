## 背景

用 OpenClaw 跑自动化一段时间后，你会发现一个规律：**任何任务迟早会被执行两次以上**。定时任务 overlapping、webhook 重推、网络超时后的自动重试、MCP 工具内部的重试逻辑、用户手动"再跑一遍"——重复不是异常，是常态。写自动化流程时默认"只会跑一次"，是这类系统翻车最常见的根源。

## 问题

幂等性（Idempotency）指同一个操作执行一次和执行 N 次，最终状态相同。不幂等的任务在重复执行时会出现典型症状：

- 通知类插件重复推送消息，用户收到三条一样的告警
- 数据库重复插入，报表数字翻倍
- 产物文件用时间戳命名，跑两次生成两份，下游消费到旧的
- 外部 API 副作用重复发生：重复下单、重复建工单

根源都是同一个：**任务的效果依赖于执行次数**。

## 做法

第一步，给任务分类，不同类别改造成本完全不同：

1. **只读类**（查询、汇总、生成预览）：天然幂等，不用管。
2. **写固定目标类**（更新配置、写报告文件）：用覆盖写代替追加写，用 upsert 代替 insert。
3. **有外部副作用类**（发通知、调第三方 API）：必须引入去重机制。

第二步，针对第 2、3 类做三件事：

- **给"逻辑任务"定义稳定 ID**。ID 从任务定义派生，比如 `daily-report-2025-06-01`，而不是每次执行随机生成 UUID。同一次逻辑执行的多次重试，必须共享同一个 ID。
- **维护一张执行台账**，记录"逻辑任务 ID → 状态"。执行前查台账，已成功则直接跳过；正在执行则等待或放弃。
- **外部调用带幂等键**。支持的 API 直接传 Idempotency-Key；不支持的，在自己这层先过台账再放行。

第三步，验证：写一个双跑测试，同一任务连续执行两次，对比第二次前后的系统状态 diff，为空才算通过。

## 踩坑点

- **先查后写的竞态**。两个 worker 同时查台账、同时通过检查、同时执行。检查逻辑只能做快路径优化，兜底必须靠数据库唯一约束——靠插入冲突来判断，而不是靠"查一下没有"。
- **多层重试叠加**。agent 层重试、MCP 工具内部重试、HTTP 客户端重试可能同时存在。幂等键要从最外层生成并逐层传递，任何一层自己重新生成新 ID，去重就失效了。
- **LLM 输出的不确定性**。agent 每次生成的内容都不完全一样，即使写进同一个文件，"结果相同"也很难严格成立。务实的拆法是：内容生成可以不幂等，**落盘动作必须幂等**（固定路径、覆盖写），产物另做版本管理。
- **时间戳命名是重复的温床**。`report_1717200000.json` 跑两次就是两份。要么固定文件名，要么用内容哈希命名。
- **半成功状态**。任务写到一半挂掉，台账里没记成功，重跑时前一半副作用已经发生。把副作用拆成可重放的小步，或者在执行前先写入"进行中"占位记录。

## 可复用建议

- 设计时默认假设**每个任务都会被执行两次**，按这个前提审查流程。
- 优先选用天然幂等的原语：PUT 覆盖、upsert、删除后重建，天然比 insert + append 安全。
- 台账 + 唯一约束是兜底手段，永远不要只依赖"先查一下"。
- 幂等键从任务定义派生，全链路共用一个。
- 把双跑测试加进自动化流程的上线检查清单，成本很低，收益很高。

## 总结

幂等性不是锦上添花的工程洁癖，而是自动化系统的入场券。重试、超时、人工干预都会制造重复执行，区别只在于你的流程是"重跑无害"还是"重跑出事"。按只读/覆盖写/外部副作用三类拆开处理，用稳定 ID 和台账兜底，再用双跑测试验证——做到这几点，你的 OpenClaw 任务才敢真正放手让它自己跑。
