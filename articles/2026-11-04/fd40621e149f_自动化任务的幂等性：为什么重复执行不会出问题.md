## 背景

写自动化的人迟早会撞上同一个问题：你没法保证"一个操作只执行一次"。

定时任务可能重叠，重试逻辑可能多发一次，Agent 调 MCP 工具超时后会重试，外部 webhook 可能重复推送，人工补跑更是家常便饭。分布式系统里有个共识：重复不是异常，是常态。幂等性（idempotency）就是应对它的基本功——同一个操作执行一次和执行多次，最终状态一致。

## 问题

几个典型翻车场景：

- 定时让 Agent 汇总 issue 写入库，某天进程重启后 cron 补跑，表里出现两份一样的日报；
- Agent 调"创建工单"工具超时，判定失败后重试，结果建了两个工单——第一次其实成功了；
- webhook 消费端没去重，上游重推一次就重复处理一次。

根因都一样：这些操作本身不幂等。"创建""发送""累加"执行两次和一次结果不同。而在有重试、有调度、有并发的自动化链路里，重复执行几乎是必然事件。

## 做法

1. **先盘点**。把任务里的操作分两类：天然幂等的（读取、按 ID 覆盖写、按 ID 删除）和非幂等的（创建、发送、增量修改）。只对后者做处理，别过度设计。
2. **定义稳定的幂等键**。键必须来自任务本身的身份，比如 `来源 + 日期 + 资源 ID`。注意：不能在重试循环里用随机 UUID 或当前时间戳生成——那样每次重试都是新键，等于没做。
3. **落库去重**。把处理过的键持久化：数据库唯一约束、Redis 的 `SET NX` 都行。插入前先查一遍是兜底，唯一约束才是真保险。SQLite/Postgres 里 `INSERT ... ON CONFLICT DO NOTHING` 一条语句解决。
4. **能"设置"就别"累加"**。把"计数 +1"改成"把计数设为 X"，把"追加记录"改成"按键覆盖写"。写绝对状态天然幂等，这一条性价比最高。
5. **外部副作用单独处理**。发消息、调第三方接口做不到严格恰好一次，务实做法是：发送前先落一条"发送中"状态，成功后更新为"已发送"，重试逻辑只捞"发送中"且超时的记录。

## 踩坑点

- **只在内存里去重**：进程一重启集合就空了。去重状态必须持久化。
- **先查后写的竞态**：两个并发执行同时查到"不存在"，然后都写入。应用层 if 判断挡不住并发，得靠唯一约束或原子操作。
- **键里掺了时间**：用 `now()` 拼键，重试晚一秒键就变了。
- **把加锁当幂等**：锁只防并发，不防先后两次执行。定时任务既要有锁防重叠，也要有幂等键防补跑，这是两回事。
- **MCP 工具本身不幂等**：暴露给 Agent 的工具如果是 append 语义，Agent 重试一次就脏一次。工具尽量设计成"同样参数收敛到同一状态"。

## 可复用建议

- 上线前问一句：**这个任务跑两遍会怎样？** 答不上来就先别上线。
- 写个最便宜的回归测试：同样参数连调两次工具，断言第二次状态不变。
- 幂等键带 TTL，别让它无限膨胀；过期窗口覆盖重试加补跑的最大跨度即可。
- 日志里带上幂等键，排查重复问题时能对得上账。

## 总结

幂等性不是什么高级模式，它是让重试和调度变得可信的前提。Agent 自动化里，你控制不了"执行了几次"，能控制的只有"执行多次是否安全"。把重复执行当常态来设计，自动化才敢真正放手跑。
