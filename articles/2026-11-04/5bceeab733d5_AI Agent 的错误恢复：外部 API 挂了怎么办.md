## 背景

社区里跑 Agent 自动化的朋友应该都遇到过：任务跑到一半，MCP 工具背后的某个第三方 API 突然 503 了。轻则任务失败，重则 Agent 陷入重试循环烧 token，或者更糟——模型"脑补"操作成功，整个流程带着错误状态继续跑下去。这篇帖子把我们团队在 OpenClaw 工作流里处理 API 故障的做法整理出来，提供一个可复用的框架。

## 问题出在哪

传统服务端调外部 API，重试、熔断、降级都是成熟工程问题。但 Agent 场景多了几层复杂度：

1. **决策层是模型。** 错误信息一旦以自然语言进入上下文，模型可能误判：把 500 当成参数错误去改参数，把超时当成"没执行"而重复提交。
2. **重试不可控。** Agent 的重试不是代码里的 for 循环，是模型"决定"再试一次，次数、间隔都没有约束。
3. **中间态没人管。** 多步任务里第 3 步挂了，前 2 步的成果如果不落盘，恢复就得从头来。

## 我们的分层做法

核心原则一句话：**重试和恢复放在代码里，不要指望模型自己处理。**

**第一层：工具包装层（必须做）**

在 MCP 工具/插件和外部 API 之间加一个薄网关：

- 统一错误分类：`timeout` / `rate_limited` / `server_error` / `auth_failed` / `bad_request`，每个错误带 `retryable` 布尔值；
- 指数退避 + 抖动，重试上限 3 次，尊重 `Retry-After` 响应头；
- 连续失败 N 次后熔断，短时间内直接拒绝调用，并在工具描述里告知模型"该工具当前不可用"。

**第二层：错误信息契约**

返回给模型的错误要结构化、精简。我们踩过的坑是网关返回了一整页 HTML 错误页，直接污染上下文。现在统一截断成 code + hint，比如 `{"error_code":"rate_limited","retryable":true,"hint":"wait 60s"}`。"可重试"与"不可重试"的语义要写进工具描述里，模型才知道该等、该绕、还是该上报。

**第三层：降级与兜底**

- **备用 provider**：主 API 挂了切备用源（搜索、地图这类有多家可选的服务）；
- **降级模式**：用缓存或本地数据顶上，但必须显式标注"这是降级结果"；
- **部分成功上报**：多步任务允许带缺口完成，明确告知用户哪几步没执行，而不是静默失败。

**第四层：状态落盘与升级**

每步完成即写 checkpoint，恢复时从断点续跑；重试预算耗尽后暂停任务、转人工确认，不要让模型自由发挥。

## 踩坑点

- **401/400 也在重试**：鉴权错误重试一百次也不会好，这种循环最烧 token。`retryable=false` 的错误必须直接终止或升级。
- **非幂等接口的重试**：POST 创建资源时超时，可能是"没到达"也可能是"到达了没回包"。没有幂等键的重试等于双倍下单。能加幂等键的接口一定加。
- **静默降级**：fallback 返回了三天前的数据却不说，模型拿着旧数据继续推理，比直接失败危害更大。
- **多层各自重试**：外层 3 次 × 内层 3 次 = 9 次真实请求，重试放大就是这么来的。重试只做一层，其他层只做分类和传递。

## 可复用建议

1. 把工具网关做成通用组件，所有出网调用走同一套错误契约；
2. 给每个任务设全局预算（时间 + token），防止单个故障 API 拖垮整个任务；
3. 留运行轨迹：哪次调用失败、重试几次、是否走了 fallback，事后排障全靠它；
4. 定期演练：故意对某个 API 注入故障，看 Agent 是优雅降级还是原地崩掉。

## 总结

API 故障不是"会不会遇到"，而是"什么时候遇到"。Agent 的错误恢复本质上仍是系统工程：确定性的部分（重试、熔断、降级、状态管理）交给代码，模型只负责在拿到结构化信息后做合理决策。把这条边界划清楚，Agent 才能在生产环境里站得住。

欢迎大家分享自己的兜底方案，尤其是多 provider 切换和幂等处理这两块的经验。
