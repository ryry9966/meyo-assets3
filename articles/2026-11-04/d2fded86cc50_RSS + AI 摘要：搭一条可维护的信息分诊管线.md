## 背景

信息源越加越多，真正读的没几个。试过各种阅读器的"稍后读"，结局都是未读数破千然后一键已读。RSS 本身仍是目前最稳定、最可控的订阅协议——不依赖推荐算法、可导出、可脚本化。缺的从来不是订阅能力，而是一层自动分诊。

我的场景：OpenClaw 常驻跑在一台小主机上，本来就用它做定时任务和消息推送，于是顺手把 RSS 管线也挂了上去。

## 问题

直接"RSS → LLM 摘要"有两个明显坑：

1. 全量送模型，token 成本高，且大部分条目本来就不相关，摘要出来也是噪音；
2. 很多源只给 summary，不抽全文的话，摘要空洞到没法看。

所以核心不是"加个 AI"，而是设计一条先过滤、后压缩的管线。

## 做法

整体五步，每步独立可调试：

**1. 源收敛。** 订阅控制在 30 个以内，分两档：必读源直接进摘要，低频源先过滤再决定。没有原生 RSS 的站点用 RSSHub 补齐。

**2. 抓取与去重。** 写一个抓取 skill（也可以包成 MCP tool 供 agent 主动调用），由 cron 定时触发，解析后写 SQLite，按 GUID + 归一化标题去重。同一篇文章多源转载很常见，标题去掉空格标点后再比对一遍。

**3. 两级过滤。** 第一级是关键词和来源权重，纯本地正则；第二级用 embedding 算条目与兴趣描述的相似度，低于阈值直接丢弃。实测只有 15%–20% 的条目需要进 LLM。

**4. 结构化摘要。** 过滤后的条目批量送模型，prompt 强制 JSON 输出：一句话摘要、0–10 相关性分、标签。明确要求"仅基于给定文本"抑制幻觉，相关性低于 6 的只留标题。

**5. 推送与回溯。** 每天早上 OpenClaw 把 digest 发到 Telegram，原始条目和摘要都落盘成 Markdown。对某条摘要点踩，就往过滤规则里加一条负样本。

## 踩坑点

- **正文抓不全**：至少三分之一的源 summary 没信息量，需要 readability 类工具抓全文。有的站反爬，抓失败要降级用 summary，而不是报错中断整条管线。
- **成本失控过一次**：第一版全量送 LLM，一天几千条直接烧掉不少 token。加两级过滤后降了一个数量级。
- **幻觉兜底**：即使 prompt 里做了约束，偶尔还是会脑补。除了指令限制，摘要末尾永远附原文链接，一眼可核对。
- **静默失败**：抓取挂了 digest 照样发（空的），看起来一切正常。加了失败计数，连续三次失败就推告警。
- **cron 时区**：容器里默认 UTC，推送时间差了八小时。老问题，但每次都忘。

## 可复用建议

- 各步骤用中间产物（SQLite 表或 JSON 文件）解耦，任何一步可以单独重放，排查问题不用重跑全链路。
- 摘要输出固定 JSON schema，下游不用写解析兼容逻辑。
- 先跑一周"只记录不推送"，人工看相关性分布再定阈值，比拍脑袋准。
- 摘要分诊这类任务用便宜的小模型足够，别把预算花在最简单的环节。

## 总结

这条管线的价值不在"全自动"，而在把 90% 不值得读的东西挡在外面——每天推送的 digest 才是真正需要人看的 10%。RSS 提供稳定输入，embedding 做廉价分诊，LLM 只做最后的压缩，OpenClaw 负责编排和触达。每一层都很简单，组合起来才稳。欢迎大家贴自己的过滤规则和 prompt 写法，这块踩坑经验比架构本身更值钱。
