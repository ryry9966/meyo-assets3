## 背景

跑过稍微长一点的 Agent 任务都知道，最脆的一环往往不是模型，而是模型调的那些外部依赖：LLM 供应商限流、MCP 工具背后的第三方 API 超时、插件连的数据库抖一下。社区里不少自动化流程（定时抓取、消息分发、数据落库）都栽在这上面：模型本身没问题，一次 503 就让整个 run 废掉，或者更糟——Agent 把报错当成了工具返回的数据，一本正经地编了个结果出来。

## 问题：错误的三种糟糕结局

实际观察下来，外部 API 挂掉时通常有三种结局：

1. **静默失败**：工具层把异常直接抛给模型，模型没有“我不知道”的概念，倾向于顺着上下文编一个答案。
2. **重试风暴**：Agent 或外层脚本无脑重试，429 期间继续打请求，token 和配额双输。
3. **全链路阻塞**：某个调用默认 30 秒超时，串行 pipeline 上十几个工具，一个卡住全线等死。

根因基本是同一个：**没有把错误处理放在模型外面的工程层里**。

## 做法：在工具层做四件事

**1. 错误分类，别一视同仁。** 把错误分成三类：可重试（429、502、503、超时）、致命（401、403、参数错）、可降级（能拿到旧数据或备用源）。分类逻辑写在工具封装里，不要指望模型判断。

**2. 指数退避 + 抖动 + 硬上限。** 重试间隔 1s → 2s → 4s，加随机抖动，最多 3 次。上限务必写在代码里，而不是把“你可以重试”写进 system prompt。

**3. 结构化错误回传。** 工具失败时不抛裸异常，而是返回统一结构：

```json
{"status": "error", "retryable": true,
 "reason": "upstream_timeout", "suggestion": "try_later_or_use_cache"}
```

模型拿到这种结构，要么选备用工具，要么如实报告“这步失败了”，而不是幻觉。

**4. 降级与熔断。** 关键工具准备 fallback：缓存快照、备用 API、或明确的“跳过并标记”。同一 session 内连续失败 N 次就熔断，直接走人工兜底。

## 踩坑点

- **重试不幂等**。写操作（发消息、建工单）重试前先确认幂等键，否则一次超时重试 = 两条重复消息。
- **200 不等于成功**。有些 API 返回 200 但 body 里带错误码，解析层必须校验业务字段。
- **把重试交给模型**。模型会原样重发同样的请求，同样的参数同样的失败，纯烧 token。重试必须在代码层做。
- **降级数据不标注**。fallback 返回的旧数据要带时间戳和“降级”标记，否则下游把它当实时数据处理。

## 可复用建议

- 所有工具调用过一层统一的执行器（gateway），超时、重试、熔断、日志集中配置，按工具粒度覆盖默认值。
- 给每个 run 设总时间预算，超了就保存 checkpoint 退出，下次续跑而不是从头来。
- 错误日志记录完整上下文（工具名、参数、错误类型、第几次重试），事后复盘全靠它。

## 总结

Agent 的可靠性不取决于模型多聪明，而取决于模型外面那层工程代码多扎实。API 一定会挂，问题不是“会不会”，而是挂的时候系统是重试、降级还是如实上报——这三条路要在代码里提前写死，而不是临时让模型即兴发挥。欢迎大家把自己踩过的 API 故障案例贴出来，一起攒一份社区的错误分类清单。
