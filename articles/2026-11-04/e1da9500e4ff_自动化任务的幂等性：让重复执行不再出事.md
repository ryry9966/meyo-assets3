## 背景

写自动化的人迟早会撞上这个问题：同一个任务被执行了两次。

在 Agent / MCP 的日常使用里，重复触发几乎是常态：工具调用超时后框架自动重试、定时器在同一分钟触发了两次、人工看日志觉得“好像没跑”又手动重跑了一次、Webhook 因为对端没收到确认而重发。这些都不可控，唯一可控的是任务本身能不能扛住重复执行。

## 问题

举个最常见的场景：你写了一个定时任务，让 Agent 每天把昨日数据汇总写入数据库，并推送一条通知。某天数据库响应慢，调用超时，框架按策略重试了一次——数据库里多了两条一模一样的汇总记录，通知群里发了两条消息。更糟的是付费 API 场景，重复调用就是重复扣费。

根因很简单：任务的每次执行都会产生新的副作用，执行两次就有两份副作用。这就是非幂等。

幂等的定义很朴素：同一个任务执行一次和执行 N 次，最终状态一致。做到这一点，重试、重复触发、人工重跑才不会变成事故。

## 做法

按副作用从弱到强，三步走：

**1. 用确定性 ID 替代随机 ID。** 成本最低、收益最大的一条。任务标识不要用 `uuid()` 或时间戳，而要用“日期 + 目标资源”推导出的确定性值，比如 `hash('2024-06-01' + 'daily-summary')`。这样重试天然指向同一个逻辑任务，而不是每次重试都变成一个新任务。

**2. 写入类操作全部 upsert，文件用固定路径。** 数据库写入配唯一键 + upsert；生成文件用固定命名（如 `summary-2024-06-01.json`）覆盖写，而不是 `summary-2024-06-01-1717200000.json` 这种每次重跑都换名字的写法。文件名里出现秒级时间戳，基本可以断定有幂等性隐患。

**3. 外部副作用先查再动，动前落标记。** 发通知、调第三方 API 这类不可撤销的操作，执行前先检查是否已执行过（当天是否已推送），并在执行前写入“进行中”标记。涉及付费的 API 优先用服务端幂等键（很多云服务支持 `Idempotency-Key` 类机制），让服务端替你兜底。

另外在编排层做一件事：把每个 MCP 工具的幂等语义写进工具描述。“此工具可安全重试”和“此工具每次调用都会产生新记录，请勿在失败后自动重试”——这两句话能让模型在重试决策上少犯很多错。

## 踩坑点

- **文件名 / 记录键里带时间戳或随机数。** 最常见的非幂等写法，重试一次就多一份资源，还很难被测试发现。
- **“先查后写”有竞态。** 两个实例同时检查都发现“不存在”，然后都执行。查询挡不住并发，唯一约束和锁才能。
- **标记和操作不在同一个事务里。** 标记写成功、操作失败，下次直接跳过，出现“假成功”。要么把标记当提示而非保证，要么引入 pending 状态做两阶段确认。
- **给非幂等操作套了自动重试。** 框架默认重试是善意，但叠加在“每次调用都创建新记录”的工具上就是灾难。重试策略和工具语义必须配套。

## 可复用建议

- 团队约定：所有自动化工具默认按幂等设计，做不到的在工具描述里显式标注副作用。
- 统一任务 ID 规则：日期（或业务周期）+ 目标资源的确定性 hash，写进文档。
- 日志里始终带幂等键，排查“为什么没执行 / 为什么执行了两次”时有据可查。
- 不可撤销的操作（付费、删除、群发），宁可加人工确认步骤，也不要裸自动重试。

## 总结

幂等不是什么高级技巧，它是自动化的入场券。重试、重复触发、人工重跑在长期运行的系统里一定会发生，区别只在于你是有备而来还是事后救火。把“执行两次和执行一次结果一样”当作默认设计目标，自动化任务才敢真正放开跑。
