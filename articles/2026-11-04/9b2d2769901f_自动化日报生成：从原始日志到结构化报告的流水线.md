## 背景

我们团队维护十几个服务和若干内部工具，日常信息散落在服务日志、Git 提交、CI 结果和告警群里。日报靠人肉拼凑，经常遗漏，还占掉每天半小时。这篇帖子记录我们用 Agent + 定时任务搭的日报流水线，思路可直接迁移到周报、事故摘要等场景。

## 问题

最初的做法很直接：cron 触发，把当天日志整体塞给模型，让它"写一份日报"。跑了一周暴露出四个问题：

1. 上下文爆炸，成本高，日志被截断后结论失真；
2. 噪声太大（DEBUG、重复心跳），模型开始"脑补"不存在的异常；
3. 输出格式漂移，今天 JSON 明天 Markdown，下游解析天天坏；
4. 静默失败，cron 挂了两天没人发现。

结论：这不是一个 prompt 问题，是一个数据管道问题。

## 做法

流水线分五层，每层产物落盘为中间文件，可重放、可调试：

**1. 采集层**：cron 按时间窗口拉当日切片——服务日志、`git log`、CI 状态、告警事件，统一转成 JSONL，每条带 `source`、`timestamp`、`level`。

**2. 预处理层**：纯脚本，不进模型。规则过滤 DEBUG 和心跳；去重；错误码聚合出 TopN；超长字段截断。这一层通常砍掉 90% 的数据量。

**3. 摘要层**：预处理后的数据分块，逐块送 Agent，输出固定 schema 的 JSON（异常事件、变更、指标摘要）。日志查询封装成 MCP 工具让 Agent 按需调用，而不是全量塞进上下文。

**4. 汇总层**：合并局部摘要，套固定模板生成日报，分四节：服务状态 / 异常事件 / 变更 / 待跟进。用 jsonschema 校验，结论必须引用原始条目 id，保证可追溯。

**5. 投递层**：渲染 Markdown 推送到群和邮件。发送带幂等键（日期+版本），重跑不重复投递；流水线失败时自动发降级版（仅 TopN 统计），让"没有消息"本身就是消息。

## 踩坑点

- **别让模型看原始日志**。预处理没做好，摘要就是幻觉制造机，规则能干的事不要花 token。
- **格式校验 + 带错重试**。模型输出偶发混入代码块围栏、字段名大小写不一。校验失败后把错误信息带回 prompt 重试一次基本能解决，两次不过就走人工告警。
- **时区陷阱**。cron 用本地时区、日志时间戳是 UTC，窗口错位导致漏数据。统一 UTC 存储，窗口计算只放一处。
- **静默失败**。加心跳文件 + 看门狗：超时未产出就往群里发"日报生成失败"。这是整条流水线性价比最高的一行配置。
- **"无异常"也要有据**。早期模型会在没异常时编一条凑数，改成必须引用条目 id 后，空引用即判定为无异常。

## 可复用建议

- 一句话原则：**规则负责过滤与聚合，模型只负责归纳与表达**。
- 每层中间产物落盘，出问题能定位到具体环节重跑，不必从头来。
- 固定 schema + 校验 + 重试，是 Agent 结构化输出稳定性的三件套。
- 先对一个服务跑稳一周再横向扩展，别一上来接全部数据源。

## 总结

流水线上线后，日报从每天半小时人工降到零，准确率反而上升——数据进了管道，"遗漏"变成了可观测的问题。核心体会：日报质量的瓶颈从来不是 prompt 写得多好，而是上游数据有多干净。把工程做在模型前面，Agent 才能稳定发挥。
