## 背景

LLM 本质上是无状态的，每轮对话都是一次失忆重启。上下文窗口再大也只是"当前工作区"，不是记忆。实际用下来最烦的不是能力不行，而是反复交代同样的事：代码风格、回复长度、常用的工具链。这些重复背后，就是记忆系统的缺位。

## 问题：三种常见但不奏效的做法

1. **全量塞 system prompt**——上下文膨胀、注意力稀释、成本直线上升；
2. **"记住这个"追加进历史**——散落在长对话里，没有任何检索机制，等于没记；
3. **每次手动粘贴偏好说明**——人肉记忆，不可持续。

所以真正要解决的不是"存不存"，而是四个问题：**什么时候写、怎么检索、怎么更新、怎么过期**。

## 做法：分层记忆 + 检索注入 + 受控写入

我目前在 OpenClaw 上跑的方案分三层：

- **工作记忆**：当前会话上下文，不做额外处理；
- **偏好库（核心）**：SQLite 一张表，字段大致是 `content / category / embedding / confidence / source / updated_at / hit_count`，category 区分编码风格、沟通偏好、环境信息；
- **情节摘要**：长对话结束后由 LLM 生成一段摘要入库，供跨会话召回。

读写是两条链路：

**读**：每轮请求前，用当前 query 做 embedding + 关键词混合检索，取 top 3~5 条，拼成带标签的结构化区块注入 system prompt，并注明"与当前指令冲突时以当前指令为准"。

**写**：独立的提取步骤（会话结束时或通过 MCP hook 触发），从对话中抽取候选偏好。只有**显式表达**（"以后都用 TypeScript"）或**重复出现 ≥2 次**的模式才入库。写入前做相似度去重，命中就更新 `updated_at` 和 `hit_count`，不新增。

**冲突与遗忘**：同 category 下语义相反时，新的覆盖旧的，旧记录标记 `superseded` 保留审计痕迹；confidence 随时间衰减，命中多的衰减慢，低置信长期未命中的定期归档。

另外给用户一个显式入口：`/memory list` 查看、`/memory forget` 删除。**记忆必须可见可控，否则用户不会信任它。**

## 踩坑点

1. **什么都记等于什么都没记**。早期我把所有"用户似乎喜欢 X"都入库，两周后检索出来一半是噪音，反而带偏回复；
2. **隐式推断要克制**。某次说"别加香菜"不等于永久忌口，先给低置信度，靠重复模式升上去；
3. **注入格式影响很大**。散文本拼接模型经常忽略，改成结构化区块后命中率明显提升；
4. **去重别只靠 embedding 阈值**。"简洁回复"和"回复尽量短"是同一条，但"简洁回复"和"代码要简洁"不是。阈值两头不讨好，加一道 LLM 判断更稳；
5. **记忆是隐私资产**。本地优先存储，导出和清除接口从第一天就要有。

## 可复用建议

- Schema 从小做起：`content + category + confidence + updated_at` 四个字段够用，别一上来就搞知识图谱；
- **写入从严，检索从宽**：宁可少记，靠重复模式补置信度；
- **MCP 化**：把读写封装成 `memory_search / memory_write / memory_forget` 三个 tool，任何 agent 都能挂载，与具体实现解耦；
- **可观测**：每次注入了哪几条偏好都记日志，排查"它怎么又忘了"时最有用。

## 总结

记忆系统不是"把东西存下来"，而是一套关于**何时写、如何检索、怎样更新和过期**的策略。核心原则：受控写入、结构化注入、冲突可裁决、用户可查看可删除。建议先跑通最小闭环——一张表、一次检索、一个提取钩子，再逐步加衰减和审计。记得住的助手，前提是有一套克制的记忆策略。
