## 背景

跑过一段时间 Agent 的人都熟这个场景：每次新会话，助手都是“失忆”的。你得反复说明“部署目标是 arm64”“commit message 写中文”“时区 UTC+8”。这些都能塞进系统提示词或项目配置，但代价是 token 越堆越多、跨项目不通用，而且并非所有偏好都值得常驻上下文。记忆系统真正要解决的是三件事：什么该长期记、偏好变更怎么处理、以及在对的时机以最小代价注入。

## 问题：我的第一版是怎么烂掉的

我最初的方案很典型：会话结束后把摘要扔进向量库，每轮检索 top-k 注入。两周后开始还债：

- 一次性上下文被当成偏好记了下来，“今天网络不稳定”这种也进了库；
- 我把默认分支从 main 改成 trunk，旧条目还在，模型在两条矛盾记忆之间随机摇摆；
- 每轮固定注入近 2k token，上下文预算被打穿；
- 出错时说不清“它为什么这么做”——条目没有来源。

结论：难点不在存储和检索，在写入策略和数据治理。

## 做法

**1. 分层。** 会话内信息归上下文；项目级约定归仓库里的 AGENTS.md 这类文件；长期用户偏好单独一个 profile 目录。三者不要混在一个库里。

**2. 条目结构化。** 每条记忆一个 YAML 文件：type（偏好/事实/流程）、value、confidence、created_at、last_hit、source、superseded_by。自由文本只做补充字段。

**3. 写入走双通道。** 显式：用户说“以后都……”时直接落盘；隐式：会话结束跑一个提炼任务产出候选，低于置信度阈值的丢弃，中间档列出来等人确认。宁缺毋滥。

**4. 写前查重。** 新增前先检索相似条目，命中就更新而非追加；偏好变更用 supersede 逻辑把旧条目标记失效，但保留原文，方便审计。

**5. 注入分级。** 高频核心偏好（语言、时区、代码风格）用模板每会话固定注入，几百 token 搞定；长尾记忆通过 MCP 暴露的 memory_search 工具按需查询，调用留日志。

**6. 遗忘。** confidence 随时间衰减，last_hit 超过 60 天的低置信条目移入回收区，复核后删除或恢复。

## 踩坑点

- **别一上来就上向量库。** 几十条记忆用 grep 足够；短偏好文本在 embedding 空间区分度极差，“用 pnpm”和“用 npm”的距离近得没法用。
- **隐式写入阈值要高。** 被污染的记忆库很难清洗，写入端多花一分力气，删除端少花十倍。
- **冲突必须显式处理。** 注入前做同类型冲突检测，取时间新、置信度高者，其余一律不进上下文。
- **记忆要可解释。** 条目必须带 source，并提供列出/删除命令，否则用户信任建立不起来。

## 可复用建议

- 起步方案：profile 目录 + 结构化文件 + 注入模板，一天能写完，覆盖八成需求。
- 记忆读写做成 MCP 工具，而不是全量塞 system prompt，决策链路可观测。
- 只盯两个指标：记忆条数、每周误注入次数。条数无脑增长，说明写入策略失守了。
- 每月跑一次整理任务：合并近似条目、检测冲突、降权冷数据。

## 总结

记忆系统本质是数据治理问题，不是模型问题。核心就三件事：什么该记（写入门槛）、怎么变（更新与替代）、何时出现（分级注入）。先做小而准，等条目真到几百条，再考虑检索算法不迟。
