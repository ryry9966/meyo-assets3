# OpenClaw 多模型路由实战：什么时候用 GPT，什么时候用本地模型

## 背景

OpenClaw 跑起来之后，token 消耗往往比预想大得多：主 agent 的规划循环、子 agent 的工具调用、定时 heartbeat、消息通道里源源不断的上下文。全走云端旗舰模型，账单不难看；全走本地模型，又会在最需要推理的地方翻车。多模型路由要解决的就是这个分配问题。

## 问题

难的不是"接多个模型"，而是"哪个请求交给谁"。我们最初的做法很粗：全部走云端，再手动把 heartbeat 和摘要改成小模型。结果有两个：一是路由散落在各处配置里，改一次要全仓搜索；二是本地模型在某些任务上悄悄降级，直到某天子 agent 的 JSON 解析连续失败才发现。

## 做法

1. **先给任务分层，再谈模型。** 把流量分成四类：
   - 规划与工具编排（主 agent 循环）——云端旗舰模型，这个钱不省；
   - 日常对话与澄清追问——中档云端模型，或本地 14B 级别；
   - 格式化、摘要、转录清洗、分类打标——本地模型，Ollama 跑量化 Qwen 系列就够；
   - 高频低价值消息（heartbeat、空闲应答）——能多小就多小。
2. **路由规则显式化。** 不要靠感觉，在配置里写清 task_type → model 的映射，路由决策落日志。OpenClaw 的 per-agent model 配置正好承载这件事：主 agent 和各子 agent 各自指定模型，而不是共用一个全局值。
3. **fallback 链只做一层。** 云端主模型失败时落到本地，仅用于保命；本地任务失败可以升级到云端，但必须打点记录，避免静默降级。
4. **用真实流量做评估集。** 从自己的会话日志里抽 30 条典型请求，换模型各跑一遍，对比成功率和耗时——比看任何榜单都准。

## 踩坑点

- **本地模型的 function calling 是重灾区。** 量化模型闲聊没问题，一到结构化输出就开始漏字段、夹注释。工具调用密集的子 agent 别交给它。
- **上下文窗口差异是隐形炸弹。** 会话累积到几万 token 后，本地模型静默截断，agent 开始"失忆"。长会话任务要么固定走云端，要么先做摘要压缩。
- **本地延迟未必更低。** GPU 同时跑转录等负载时，本地推理的排队时间可能超过云端。路由前先压测。
- **fallback 会掩盖故障。** 有次云端配额耗尽，流量全部滑到本地，表面一切正常，质量肉眼可见地掉。fallback 触发必须接告警。

## 可复用建议

- 维护一张自己的"任务-模型能力表"，随版本更新；换模型只改映射，不动代码。
- 每次路由决策记三件事：task_type、实际用的模型、是否触发 fallback。一周后你自然知道钱花在哪。
- 新任务上线默认走云端，观察两周再决定是否下沉到本地——降级容易，升级难。
- 别为省小钱让规划步骤用弱模型：一次失败重试的工具调用，比省下的 token 贵得多。

## 总结

多模型路由本质是把"模型能力"当资源做调度：云端模型留给规划与编排，本地模型吃掉高频低难度的批量活。关键不在选哪个模型，而在路由规则是否显式、日志是否完整、降级是否可控。先跑通全云端的基线，再逐类任务下沉到本地，每一步都有数据兜底。
