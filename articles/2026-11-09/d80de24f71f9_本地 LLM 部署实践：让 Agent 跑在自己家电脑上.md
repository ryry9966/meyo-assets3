## 背景

把模型搬到本地的动机很实际：一是数据不出门——Agent 要读日志、代码库、私人文档，全量送云端心里不踏实；二是成本——自动化流程一晚跑几千次调用，API 账单是真实的；三是离线可用。目前 7B~14B 档位的开源模型（Qwen2.5、Llama-3.1、GLM-4 这一档）在结构化输出和工具调用上已经够用，缺的不是能力，是部署经验。

## 问题

家用机器有三个硬约束：

- 显存/内存上限直接决定能跑的参数量级；
- 上下文长度和 KV cache 会悄悄吃掉权重之外的显存；
- Agent 对模型的要求比聊天高：要稳定吐 JSON、要可靠执行 function calling，小模型最容易在这两点翻车。

## 做法

1. **先盘硬件再选模型。** 经验值：Q4 量化的 7B 约占 5GB，14B 约 9GB，32B 约 20GB，另留 2GB 余量给系统和上下文。12GB 显存跑 14B Q4 + 8K 上下文是比较舒服的组合。
2. **运行时选型。** 想省事用 Ollama，一条命令起服务，自带 OpenAI 兼容接口；想精细控制量化与线程用 llama.cpp；显存充裕且要并发再上 vLLM。建议从 Ollama 起步，别在运行时上过早优化。
3. **显式设置上下文长度**（`num_ctx`），绝不用默认值。
4. **接入 Agent。** base_url 指到本地端点即可，OpenClaw 这类框架不用改代码：

```yaml
model:
  provider: openai-compatible
  base_url: http://127.0.0.1:11434/v1
  model: qwen2.5:14b-instruct-q4_K_M
```

5. **自建迷你评测集。** 写 20~50 条真实任务（含工具调用、JSON 提取、多轮记忆），每次换模型跑一遍。这比看任何榜单都靠谱。

## 踩坑点

- **默认上下文太小。** Ollama 默认 `num_ctx` 很低，Agent 长对话会"失忆"，且报错不直观，这是我遇到频率最高的坑。
- **KV cache 超预算。** KV cache 随上下文线性增长，权重装得下不代表 32K 上下文装得下，直接 OOM。
- **量化后 JSON 漂移。** 字段偶发缺失或格式变形，优先用框架的结构化输出约束（JSON schema / grammar）兜底，别裸奔。
- **工具调用静默降级。** 模型不支持原生 function calling 时，部分框架会退化为纯文本解析，成功率骤降——上线前必须实测一整轮工具链路。
- **"能跑但慢得离谱"。** 显存不足触发部分层卸载到 CPU 时，速度会从 30 tok/s 掉到 2 tok/s。先查 GPU 层数分配，而不是怀疑模型本身。

## 可复用建议

- **混合路由。** 高频低难度调用（分类、抽取、格式化）走本地小模型，规划与复杂推理走云端大模型，综合成本能降一个量级。
- **锁定模型版本号。** 量化版本更新后行为可能变化，Agent 的交付物要可复现。
- **持续记录 tok/s 与任务成功率。** 这两个指标比一切评测分数都真实。

## 总结

本地部署的门槛已经从"能不能跑"变成"跑得好不好"。家用电脑跑 7B~14B 完全能支撑日常 Agent 自动化，省下的不只是 API 费用，还有对数据的掌控感。代价是工程细节要自己补齐：上下文管理、结构化输出、工具链验证。把评测集建好，这些都不是玄学。欢迎在评论区晒你们的硬件配置和实测 tok/s。
