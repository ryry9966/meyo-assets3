## 背景

OpenClaw-CN 的内容散落在群聊、GitHub 仓库和各家博客里，好东西经常沉底。我想要一个机器人，每天聚合一次值得看的条目，自动整理成帖子发到社区板块。整套东西跑在一台最低配 VPS 上：一个 OpenClaw 实例，加一个 SQLite 文件，没有更多了。

## 问题定义

难点从来不是"能不能发出去"，而是四个：**什么该发**（过滤与去重）、**发了什么**（可追溯）、**发错了怎么办**（审核与回滚）、**发失败怎么办**（幂等与重试）。把生成器当核心来设计一定会翻车——真正的核心是状态管理。

## 做法

流水线拆成五层，状态机只有一条主线：`draft → pending → published / failed`。抓取与发布各封装成独立的工具/MCP 接口，便于脱离 agent 单独测试。

1. **触发层**：用系统 cron 定时唤醒 agent 跑一次任务，而不是让 agent 自己维持循环。定时是确定性的，agent 只负责干活。
2. **抓取层**：三个来源各写一个 adapter——RSS、GitHub Releases、群聊置顶消息，统一输出同一 schema 的 JSON 条目。
3. **过滤层**：纯代码规则，不经过模型：按关键词、长度、时间过滤，再和 SQLite 里的已发条目 hash 比对去重。
4. **生成层**：LLM 只做摘要和排版，不做"发不发"的决策。所有链接、标题由代码从原始条目注入模板，模型无权生成 URL。
5. **发布层**：调论坛 API，带幂等 key（条目 hash），失败退避重试三次，仍失败写入死信表并推送告警。

草稿先落到 pending 区发进我的审核群，回一个固定指令才发布；白名单话题走自动发布。

## 踩坑实录

- **重试打出重复帖**。论坛 API 偶尔返回 200 但内部处理超时，一重试就发了两遍。解法：幂等 key 放到服务端可识别的字段，发布前先查"已发表"表——宁可漏发，不可重发。
- **模型编链接**。早期让它"整理并附上来源"，它补了几条看起来合理但 404 的链接。现在 URL 一律由代码注入，模型只碰正文文字。
- **时区错一天**。VPS 是 UTC，"今天"在两个时区差出一天，日报经常把昨天算成今天。统一在抓取层打带时区的时间戳，日期在 prompt 里显式传入，不让模型自己猜。
- **上下文被塞爆**。抓回来 50 条全丢给模型，摘要质量直线下降。规则过滤后控制在 10 条以内，超出的进候选池明天再说。
- **频控与转义**。论坛对连续发帖限流，加了最小间隔和指数退避；帖内下划线和代码块被论坛渲染器吃掉，发布前用论坛自己的渲染做一次 dry-run 校验。

## 可复用建议

1. 让 LLM 只做文本变换，决策和记忆全部放在代码与数据库里。
2. 任何对外写操作必须有幂等 key——重试和去重本质是一件事的两面。
3. 先接人工审核通道，稳定两周后再放自动发布，灰度推进。
4. 来源抽象成 adapter，新增一个数据源的成本应该只是一个函数。

## 总结

整套 MVP 不到三百行，真正的工时都花在可靠性上：去重、幂等、降级、告警。结论也简单——机器人难的不是生成内容，而是**少发错、不重发、发失败有人知道**。先窄后宽，先丑后稳，比一开始追求全自动划算得多。
