## 背景

最近社区里"把 OpenClaw 接进群聊/论坛"的实践越来越多：有人让 Agent 帮忙答疑，有人挂上 MCP 直接查内部 wiki，还有人跑自动化流水线把 Agent 生成的周报推到社区频道。方向没问题，但一个事实常被忽略：**Agent 一旦面向社区，它就是一个对外服务**，得按暴露面来管，而不是当本地玩具。

## 问题：泄漏往往不走"恶意"，走"顺手"

几类真实发生过的路径：

1. **MCP 挂得太宽**。社区答疑用的 Agent 同时挂着内部知识库 MCP，用户一句"总结下最近的项目进展"，它就把内部文档要点搬进了公开频道。
2. **求助贴自带敏感信息**。为了让大家帮忙排查，直接把配置、`.env`、带 Authorization 头的 curl 命令贴出来。
3. **会话记忆串场**。上午在内网任务里让 Agent 读过内部排期，下午同一会话在社区被问"你们在忙什么"，它答得头头是道。
4. **自动发帖无卡点**。流水线从内部系统取数、Agent 汇总、直接推送，中间没有任何人工审核。

系统提示词里写一句"请勿泄露内部信息"挡不住这些——它只是建议，不是边界。

## 做法：四条红线

**红线一：内外两套身份，物理隔离。** 面向社区的 Agent 单独建 profile/工作区，不挂任何内部 MCP，不指向内部文件系统根目录。宁可手动粘贴脱敏后的片段，也不要图方便挂全量知识库。

**红线二：工具最小权限。** MCP server 走白名单，token 只给只读、只给必要 scope；文件系统访问限制在沙箱目录内。每季度清一次"当时图方便加、后来忘了"的工具。

**红线三：出站过滤。** Agent 输出进入社区频道前加一道机器检查：内部域名、密钥前缀（如 `sk-`）、项目代号、客户名的 deny-list 正则扫描，命中即拦截转人工。过滤器放代码库，跟配置一起评审。

**红线四：发布有卡点。** 高风险动作（自动发帖、批量回复）默认关闭，或先发内部预览频道跑一段时间；社区内容至少抽检 session 日志，确认 Agent 没引用不该引用的上下文。

## 踩坑点

- **"本地测过没事"不成立**：会话记忆和挂载的工具是持久的，今天测试用的配置就是明天社区机器人用的配置。
- **deny-list 精确匹配不够**：内部代号换个写法、域名去掉一段就绕过了。按模式匹配，别按字符串匹配。
- **截图也是出口**：半开放的群里有新人，一张带内部路径的调试截图就是一次泄漏。
- **日志即现场**：成员求助前先本地跑一遍脱敏脚本（抹掉 header、token、内部主机名）。养成习惯比事后删帖便宜得多。

## 可复用建议

- 准备一份《社区 Agent 接入 checklist》：挂了哪些 MCP？scope 是什么？出站过滤跑了吗？发布卡点在哪？接入前逐项过。
- 团队维护一份共享脱敏正则库，Agent 输出过滤和人工贴图前检查用同一套规则。
- 每月 dump 一次社区 Agent 的会话日志，用同一套正则反扫，当作例行安全巡检。
- 响应流程提前写好：确认泄漏范围 → 撤换 token → 删帖/联系渠道管理 → 复盘。别等事发当晚才想流程。

## 总结

Agent 泄漏很少来自攻击，多数来自"顺手"和"忘了"。四条红线——身份隔离、最小权限、出站过滤、发布卡点——没有一条需要写多少代码，但每一条都对应一类真实事故。把面向社区的 Agent 当对外服务对待，红线的成本永远低于善后的成本。
