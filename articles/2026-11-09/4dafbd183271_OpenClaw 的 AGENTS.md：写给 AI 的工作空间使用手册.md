在 OpenClaw 的工作空间里，AGENTS.md 是最容易被低估的一个文件。它不定义人格，也不装工具，只做一件事：告诉模型“这个工作空间怎么用”。

## 背景

OpenClaw 每次会话启动都会读取工作空间的固定文件。聊天里说的话随会话消失，AGENTS.md 里的规则却每次都在。你可以把它理解成给新同事的 onboarding 文档——这位同事能力很强，但每天上班都失忆，所以交接文档写得越清楚，返工越少。

## 问题

没有它时的典型症状：模型猜路径，把产物写错地方；每次重新发明你的命名和目录约定；不清楚哪些 MCP 工具已接入、什么场景该用哪个；定时任务跑偏，只能靠在提示词里反复强调。根因一致：你的隐性预期没有被固化成每次都能读到的显式规则。

## 做法

1. 在工作空间根目录建 AGENTS.md，控制在百行以内。
2. 推荐五段骨架：
   - **环境事实**：操作系统、关键路径、常用命令；
   - **约定**：文件命名、目录职责、输出与回复偏好；
   - **工具清单**：已接入的 MCP server、插件、skills，各自适用场景；
   - **自动化**：有哪些定时任务、触发后该做什么；
   - **边界**：禁止操作的目录、需要确认才执行的动作。
3. 规则要具体可执行：

```
反例：请注意文件命名规范。
正例：日报写入 /workspace/daily/YYYY-MM-DD.md，目录不存在先创建。
```

4. 建立迭代机制：模型做错了，先问“这条规则写了吗”——没写就补一条，写了没用就改得更具体。像修 bug 一样维护它，而不是写完就归档。

## 踩坑点

- **写太长**：每个会话都占上下文，关键规则埋在段落里等于没写；
- **与记忆文件、其他配置重复或矛盾**，行为会飘，排障时很难定位是哪份指令生效；
- **放密钥**：它会被整份读进上下文，敏感信息一律走环境变量或独立配置；
- **用形容词下指令**：“尽量”“注意”没用，“失败两次后停下询问”才有用；
- **把它当能力来源**：AGENTS.md 只是指引，能力来自 skills 和 MCP 配置，指引替代不了装好的工具。

## 可复用建议

- 每条规则自测：能否设计一个场景验证模型是否遵守？不能验证就重写。
- 多项目场景，用子目录的局部 AGENTS.md 承载项目级约定，根文件只留全局规则，避免一份文件越养越肥。
- 让模型帮你起草或重构 AGENTS.md 很有效，但合并前必须人工过一遍——它会礼貌地保留废话。
- 每月 review 一次，删掉过期规则。文档腐烂比没有文档更糟。

## 总结

AGENTS.md 的价值在于把“你心里默认的东西”变成“模型每次都会读到的东西”。成本很低，杠杆很高。把它当代码维护：小步修改、定期 review、错一次补一条。写好这一份文件，你在日常自动化里大多数“反复强调”都可以下岗。
