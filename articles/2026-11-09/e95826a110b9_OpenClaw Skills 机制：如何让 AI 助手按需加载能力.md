## 背景

Agent 场景里一个很实际的矛盾：能力越多，上下文越贵。早期我们把所有工具说明、操作手册全塞进 system prompt，四十多个工具描述常驻，光这部分就吃掉大几千 token，而且模型选错工具的频率肉眼可见地上升。OpenClaw 的 Skills 机制解决的正是这个问题：把“知道有这个能力”和“知道具体怎么做”拆开，平时只留一行元数据，命中触发条件才加载完整定义。

## 问题拆解

直接堆能力有三个代价：

1. **上下文膨胀**：不常用的能力描述长期占据窗口，挤压真正重要的对话内容。
2. **注意力稀释**：候选工具越多，模型在相似工具之间的误选率越高。
3. **维护困难**：改一段操作说明要动 system prompt，改完还得重启会话验证。

## 做法

Skills 的加载是分层的：

- **第一层（常驻）**：每个 skill 只注入 name + description，一段话的 token 成本。
- **第二层（按需）**：模型判断当前任务命中某个 skill，才读取对应 SKILL.md 正文。
- **第三层（引用）**：长参考资料、脚本放在 skill 目录里，用 bash 按行读取，不整体进上下文。

实际操作步骤：

1. 在 `skills/` 目录下建一个文件夹，写 SKILL.md，frontmatter 里填 name 和 description。
2. description 是整个机制的开关，写法要覆盖“触发条件 + 适用场景 + 明确不适用的情况”。比如日志分析 skill，要写清“用户要求排查服务报错时使用；闲聊或问代码语法时不使用”。
3. 正文控制在几百行内，按“步骤 → 示例 → 边界情况”组织，写成给模型执行的操作手册，不是给人看的介绍文档。
4. 用会话命令查看当前加载了哪些 skill，跑几个典型问法验证触发是否准确。

skill 和 MCP 是互补关系：MCP 工具是“手”，skill 是“手上的操作规程”。我们最常见的模式，是 skill 正文指导模型何时调用哪个 MCP 工具、按什么顺序、失败后怎么降级。

## 踩坑点

- **description 写成营销文案**。“强大的数据分析助手”这种描述等于没写，模型无法决策，结果就是不触发或乱触发。要写成判断条件，不是形容词。
- **SKILL.md 越写越长**。有人把整个 wiki 搬进去，按需加载变成按需爆炸。长内容一律拆成引用文件。
- **技能职责重叠**。两个 skill 都覆盖“部署”，触发时模型二选一，选哪个都不稳定。重叠的合并，边界写进各自的“不适用”里。
- **脚本环境依赖**。skill 里的脚本在本机跑得通，换台机器 Python 版本不对就挂。SKILL.md 开头加一步环境检查。
- **忘了 skill 是给模型读的**。段落式散文模型执行起来很吃力，要短句、编号步骤、明确输入输出。

## 可复用建议

- 从三个高频重复操作起步，验证触发准确率后再扩，不要一次铺几十个。
- 把 skills 目录纳入 git，description 每次修改都对应一轮典型问法回归——这是这个机制里唯一需要认真维护的地方。
- 每月清一次长期未被触发的 skill，能力库和代码一样会腐化。

## 总结

Skills 本质上是上下文经济学：用一行元数据的成本，换完整能力的按需可得。它不提升模型智力，但显著缓解了“能力多”和“上下文有限”之间的矛盾。对我们团队来说，最大的收益不是省 token，而是工具选择的稳定性——这件事对自动化流程可靠性的影响，远大于成本本身。
