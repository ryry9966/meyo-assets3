## 背景

用 OpenClaw 这类常驻 Agent 有一个绕不开的现实：每次会话的上下文都是新的。模型能力再强，它默认只知道你这一轮说的话。我的 workspace 里最初只有 AGENT.md——告诉 agent "你是谁、该守什么规矩"，却从没有一份文件告诉它"我是谁"。结果就是每天开局都要重新交代：我用的什么栈、机器怎么部署、回复要简洁、别自作主张升级依赖。

## 问题

这些信息每次都占用开场 token，更麻烦的是遗漏。有一次让 agent 写服务重启脚本，它默认我用 systemd，实际机器跑的是 Supervisor，来回折腾三轮才对齐。这类"重新对齐"的隐性成本，比维护一份静态文件高得多。

## 做法

1. **在 workspace 根目录新建 USER.md**，和 AGENT.md 平级。
2. **内容分五段，每段几行**：
   - 身份与角色：我是做什么的，agent 协助哪些场景
   - 技术栈：语言、框架、**具体版本号**（agent 很容易默认最新版）
   - 环境：OS、时区、常用路径、部署方式
   - 偏好：回复语言、详略程度、代码风格
   - 禁区：不要自动 commit、不要碰哪些目录
3. **控制体量在 40 行以内**。USER.md 通常整份注入上下文，写长了既浪费 token，也稀释重点。
4. **在 AGENT.md 加一条规则**：会话开始先读 USER.md；被我纠正时，主动问"要不要把这条写进去"。这一条让文件从静态变成会生长的。
5. **用 git 管 workspace**，改偏好走 diff，能看清 agent 何时、为何更新了这份文件。

## 踩坑点

- **别写成日记**。USER.md 是配置不是日志，"上周做了什么"应该进记忆文件，这里只放稳定事实。
- **别放敏感信息**。USER.md 会被读进上下文，而上下文可能随工具调用、MCP 请求外发。密钥、真实住址一律不写。
- **偏好冲突要及时清理**。我留过"回复要详细"，后来又加"只给结论"，agent 行为开始摇摆。定期 review，删作废条目。
- **别让 agent 无节制地追加**。开闸之后它什么都想写，两周能膨胀一倍。所以 review diff 这步不能省。
- **模糊表述有风险**。"用 Node"不如"Node 20 LTS"，agent 对模糊描述的默认行为经常和你想的不一样。

## 可复用建议

- **三份文件分工**：AGENT.md 管行为准则，USER.md 管关于我的稳定事实，MEMORY.md 管动态记忆。混在一起迟早乱。
- **让 agent 自己维护，你只负责评审**。人肉维护的文档两周就会过期，这条已在我这里验证过。
- **把它当代码评审**：agent 提议写入时看一眼 diff 再合并，保持这份文件小而准。

## 总结

USER.md 解决的不是记忆问题，是对齐问题。它便宜——一个 Markdown 文件、几十行；收益却直接：开场不用重复自我介绍，输出风格趋近你的习惯，环境类错误明显减少。花二十分钟写第一版，之后让 agent 帮你养着它，是低成本高回报的一件事。如果你现在还在每次会话里打字介绍自己，那就是该建这个文件的时候了。
