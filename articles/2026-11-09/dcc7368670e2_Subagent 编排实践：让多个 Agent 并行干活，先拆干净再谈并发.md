## 背景

单 agent 串行执行是最常见的用法：主会话里规划、调工具、写结果，一条线走到底。任务简单时没问题，但遇到"对比四个候选库并给出选型""给五个服务各写一份巡检脚本"这类天然可拆的活，串行的代价就出来了：耗时长，中间过程和最终结论全挤在一个上下文里，越往后越容易"忘事"。

OpenClaw 的 subagent 机制提供了另一条路：主 agent 通过 `sessions_spawn` 派生独立子会话，子 agent 有自己的上下文窗口，干完活把结果汇报回来。子任务互不干扰，可以并行跑。

## 问题

我遇到的典型场景：要验证四个 MCP 工具库的可用性，每个都得装依赖、跑示例、记录坑。串行做下来一轮四十多分钟，且四次实验的中间输出把主上下文撑得很臃肿，后面写总结时质量明显下滑。

## 做法

1. **先判断可拆性**。子任务满足三条才值得并行：彼此无顺序依赖、不写同一份资源、交付物能用"几行结论 + 文件路径"说清。
2. **写自包含的子任务 prompt**。子 agent 看不到主对话，背景、目标、约束、返回格式必须全部写进 prompt。我固定一个模板：目标 / 环境 / 步骤提示 / 返回格式（结论三行以内 + 证据文件路径）。
3. **控制并发**。同时最多 3 个子 agent。再往上 rate limit 和 token 成本先爆，速度反而下降。
4. **失败兜底**。每个子任务设超时；失败不无限重试，超过两次就降级为主 agent 自己串行补做，或标记"未完成"进汇总。
5. **汇总收敛**。子 agent 只回摘要，原始日志落各自的文件，主 agent 合并时去重、对齐格式，最后才进主上下文。

改成并行后，同样一轮验证压缩到十二分钟左右，主上下文只增加了四段摘要。

## 踩坑点

- **共享可变资源**：最早让两个子 agent 同时改同一个配置文件，后写的覆盖先写的。现在并行任务一律各写各的文件，由主 agent 统一合并。
- **返回内容过长**：子 agent 起初把完整执行过程倒回来，两次就把主会话撑爆。必须在 prompt 里硬性限定返回格式。
- **隐含依赖被硬拆并行**：两个"调研"子任务其实都依赖第一次的环境准备，分开跑得到互相矛盾的结论。拆之前先跑通依赖链，确认前序产物已就位。
- **并发过高**：开过 6 个并发，rate limit 排队后总耗时反超串行，纯花钱买堵车。

## 可复用建议

- 把"可并行三条件"做成拆任务前的 checklist，不满足就老实串行，并行不是默认选项。
- 子任务 prompt 模板化，存成固定片段，避免每次手写漏背景。
- 主 agent 保持"路由 + 汇总"角色，不亲自下场干活，上下文才守得住。
- 每次编排留一份记录：拆了几份、几个成功、耗时对比。跑三五次，你就能判断这类任务值不值得并行。

## 总结

subagent 并行的收益来自任务本身的可拆性，不是 agent 数量。先花几分钟把任务拆干净、把子 prompt 写自包含，再谈并发数和超时策略。顺序反了，并行只会更快地制造混乱。
