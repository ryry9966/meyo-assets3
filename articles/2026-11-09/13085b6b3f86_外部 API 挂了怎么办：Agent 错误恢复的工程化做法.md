## 背景

跑 Agent 自动化的人大概率都遇到过：流程平时很稳，某天一个外部 API 突然 503，整条链路就乱了。OpenClaw 的 agent 依赖大量外部服务——MCP 工具、搜索、模型 provider、各类插件——任何一环挂掉，轻则任务中断，重则模型"编"出一个结果继续往下跑。

失败本身不可怕，可怕的是 agent 对失败的默认反应：盲目重试、静默降级成幻觉、或者干脆卡死。这里整理一套实践里验证过的错误恢复做法。

## 问题：三种典型翻车

1. **无限重试**：插件层没设上限，agent 循环里又自己重试，一个挂掉的 API 被打了几十次，token 烧掉，API 更挂。
2. **幻觉兜底**：API 返回报错，但错误信息以纯文本塞回上下文，模型把它当数据"理解"了一下，然后自信地给出一个编造的结果。
3. **无状态中断**：定时任务跑到一半挂了，恢复后从零重跑，已完成的步骤重复执行（重复发消息、重复写库）。

## 做法

核心思路：把"重试"从模型的临场发挥，变成工具层的确定性策略。分五步：

**1. 工具层统一封装，fail fast。** 所有外部调用走同一个 wrapper：超时 15–30 秒，最多重试 2–3 次，指数退避加随机抖动（jitter）。只对可重试错误重试（timeout、429、5xx），401/400 直接失败：

```yaml
timeout_ms: 15000
max_retries: 2
backoff: exponential + jitter
retry_on: [timeout, "429", "5xx"]
```

**2. 结构化错误返回给模型。** 不要把原始报错字符串丢进上下文，返回 `{"ok": false, "error": "upstream_timeout", "retryable": true}` 这类结构。模型拿到明确的 retryable 标记，才会做出正确决策。

**3. 预定义降级策略，禁止静默兜底。** 每个关键工具预先声明失败时的行为：切换备用数据源、用缓存的上次成功值（必须标注数据截止时间）、或明确停下来告诉用户"这个数据现在拿不到"。规则只有一条：宁可说拿不到，不允许编。

**4. 任务状态落盘（checkpoint）。** 多步自动化在每步完成后写入状态，恢复时从断点续跑而不是从头来。非幂等操作加幂等键，重试前先查一下是否已执行。

**5. 熔断 + 恢复探测。** 连续 N 次失败后把该工具标记为 down，冷却期内定时任务跳过它，别去捶一个已经在死的 API。冷却结束不要直接放流量，先用轻量健康检查探测，通过再恢复。降级发生时顺手往消息通道推一条"任务暂停，预计稍后重试"。

## 踩坑点

- **重试只设一层。** MCP server 重试一次、插件重试两次、agent 又重试三次，实际就是乘法。重试收敛在 wrapper 一层，其他层透传。
- **重试必须加 jitter。** 固定间隔重试会让多个任务同步共振，形成重试风暴。
- **缓存数据要带时间戳。** 否则 agent 会把昨天的天气当今天的报出去，比失败更糟。
- **注意超时配置冲突。** MCP client 有自己的默认超时，别让它比 wrapper 的总耗时还短，否则重试没跑完就被外层掐了。
- **失败路径要测。** 开发时 mock 一个一直返回 500 的 endpoint，看 agent 是停下、降级还是幻觉，别等生产环境第一次故障才发现。

## 可复用建议

- 把 wrapper 做成通用工具基座，所有外部调用强制走它，超时/重试/降级配置集中管理。
- 故障期间在 agent 记忆里记一条"事故备注"（时间、哪个服务、怎么处理的），后续对话里模型有上下文，不会重复踩。
- 日志记全：工具名、endpoint、耗时、错误分类。没有日志的恢复策略没法改进。

## 总结

Agent 的错误恢复不是"加重试"三个字，而是一套策略：快速失败、错误分类、诚实降级、状态断点、熔断探测。判断标准也很朴素——API 挂掉时，agent 要么如实报告，要么明确降级，绝不该给出一个看起来正常、实际是编的结果。
