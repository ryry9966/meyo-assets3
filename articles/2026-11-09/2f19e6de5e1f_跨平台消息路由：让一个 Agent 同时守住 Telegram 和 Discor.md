# 跨平台消息路由：让一个 Agent 同时守住 Telegram 和 Discord

## 背景

我们的主 Agent 最初只挂在 Telegram 上，手机上随手问很方便。但团队协作和社区问答都发生在 Discord，于是面临选择：再起一个实例专门服务 Discord，还是让同一个 Agent 同时接两个渠道。

结论先说：单实例双渠道是对的，但前提是把「路由」当成工程问题来设计，而不是在配置里随手加一行。

## 问题

双实例方案很快排除：两份配置必然漂移，技能和 MCP 工具改动要同步两处，会话记忆完全割裂，换端再问一遍还得重新交代背景。

单实例真正要解决的是三件事：

1. **会话路由**：来自不同平台、不同对象的消息，分别进哪个会话；
2. **格式适配**：两个平台的 Markdown 方言、消息长度上限都不一样；
3. **频控与回环**：Discord 限速、bot 之间的自回复环路。

## 做法

**第一步，网关层并行启用两个渠道插件。** Telegram 用 bot token + 长轮询，Discord 用 bot token + gateway websocket。两条链路都是网关主动出站，不需要公网回调地址，部署上没有额外负担。

**第二步，设计会话键。** 默认按 `渠道:对象` 隔离：Telegram 每个白名单用户一个会话，Discord 每个 guild 的指定频道一个会话；而工作区的记忆、技能、MCP 工具全部共享。这是这轮改造里最重要的决定——**上下文隔离，能力共享**。

**第三步，收紧入口。** Telegram 侧用 DM 白名单（按用户 ID）；Discord 侧要求同时满足两个条件才响应：频道在白名单内，且消息 @ 了 bot。群聊环境里少了第二条，Agent 会对每句话插嘴。

**第四步，把适配做薄。** 渠道插件层只负责格式转换与切分，Agent 主逻辑完全不感知平台。内部统一用一份 Markdown 输出，出站时按渠道转译。

## 踩坑点

- **Markdown 方言不一致。** Telegram 的 parse_mode 和 Discord 的渲染规则对代码块、链接处理不同，长代码块常有一边排版崩掉，最后在渠道层各写一个转译函数才稳定。
- **长度上限别用统一阈值。** Telegram 单条 4096 字符，Discord 是 2000。切分逻辑必须按渠道配置，否则 Discord 侧频繁截断报错。
- **bot 回环。** Discord 群里另一个 bot 的回复被我们当作用户消息处理过一次，差点刷屏。之后所有渠道统一过滤：忽略自身消息、忽略其他 bot。
- **会话串味。** 早期图省事把两个渠道指到同一个会话，Discord 群聊上下文很快污染了 Telegram 私聊的体验，改回隔离后才正常。
- **Discord 限速。** 长回复切成多条时容易撞频道级限速，加了一个简单的节流队列解决。

## 可复用建议

1. **渠道当传输层，Agent 当核心。** 平台差异止步于插件层，别让 prompt 里出现「这是 Discord」这类补丁。
2. **新渠道先影子验证。** 用测试 Agent 挂新渠道跑几天，确认路由和格式没问题再切主 Agent。
3. **日志带渠道标签。** 按 channel 维度统计延迟与失败率，双渠道后渠道相关故障占比明显上升，没有标签基本无法定位。
4. **路由表写成文档。** 哪个 guild/频道/用户对应哪个会话、哪个 Agent，别让它只存在于配置的直觉里。

## 总结

跨平台消息路由本质上是两个决定：**哪个消息进哪个会话**，以及**以什么格式出去**。这两个问题想清楚了，接第二个渠道真的只是配置工作；想不清楚，接多少个渠道都会变成事故来源。上下文隔离 + 能力共享，是最值得复用的一条经验。
