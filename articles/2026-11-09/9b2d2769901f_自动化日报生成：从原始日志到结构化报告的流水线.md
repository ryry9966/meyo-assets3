## 背景

团队每天的日报，本质上是把散落在 git 提交、CI 流水线、告警平台、工单系统里的"昨天发生了什么"手动抄一遍。人肉搬运的问题不只是耗时，而是口径不稳定——每个人挑的重点不一样，数字经常对不上，日报质量取决于谁值日。

## 问题

最直觉的做法是让 Agent 直接"读日志、写日报"，实际效果往往不好。原始日志体量大、噪声高、格式不一，LLM 直接消费原始文本容易出现数字编造和关键遗漏；而日报是要发给别人的正式产物，容错空间很小。核心矛盾在于：**取数和统计需要确定性，归纳表述才需要模型**。

## 做法

我们在 OpenClaw 里搭了一条四段式流水线，原则是"确定性的活交给代码，不确定的总结才交给模型"。

1. **采集层**：定时触发的 Agent job 分别拉取各数据源。git log 用 `--since`/`--until` 按自然日切分，CI 与告警走 API，各自输出原始 JSON。
2. **归一化层**：清洗成统一 schema：`{source, module, event_type, count, highlights[], links[]}`。这一步全是纯代码，无模型参与，超量条目做 top-N 截断与聚合。
3. **汇总层**：结构化 JSON 交给 Agent，prompt 里只允许做两件事——按模块归组、生成不超过三句话的摘要。所有数字从 JSON 透传，禁止模型自行计算。
4. **渲染与投递**：Jinja2 模板渲染 Markdown，经 webhook 推送到群和邮件，模板放 git 里做版本管理。

整条链路里，MCP 工具用在采集和投递两端（拉数据、发消息），中间的统计用普通脚本完成，Agent 只出现在汇总环节。

## 踩坑点

- **时间边界**。日志时间戳是 UTC，日报按东八区自然日切分，第一版就出现"昨天凌晨的提交被算进今天"。统一在采集层转换时区，边界规则写死在配置里。
- **让模型算数字**。早期图省事把原始 diff 丢给模型统计提交数，每次跑出来都不一样。改成代码算好、模型只做表述后，输出才稳定。
- **静默失败**。流水线挂了没人发现，因为"没收到日报"和"今天没事发生"看起来一样。后来加了独立的失败告警，日报末尾固定输出各数据源的采集成功状态。
- **重跑幂等**。补跑昨天的任务时推送了两遍。投递层按 `report_date + version` 做去重键解决。

## 可复用建议

- 先定 schema 再写逻辑。schema 是流水线各段之间的契约，变动必须走版本号。
- 日报里保留原始数据链接（commit、告警详情），让人能快速核实，这是信任的基础。
- 人的修订要回流：编辑后的日报存档，作为后续调整 prompt 和模板的对照样本。
- 从单一数据源起步跑通全链路，再逐个接入新源，不要一上来铺四个源。

## 总结

日报自动化的价值不在"用了多少 Agent 能力"，而在数据装配的确定性。LLM 适合做最后的归纳表述，不适合做统计和取数，把这两层分开，报告才敢直接发出去。另外，流水线本身也要有日志和告警——一个会静默失败的自动化，比纯手工更危险。
