前几天微博热搜上多了一条很“圈内”的词条：AI 博主九尾用两个字评价 Gemini，“墨迹”。评论区立刻分成两派：一派疯狂点头“我也是，等它吐字等到天荒地老”；另一派甩出跑分和 API 数据，说人家明明不慢。一个口语化的词能吵起来，说明它戳中的不是玄学，而是一个正经的工程问题：一个大模型的“慢”，到底由什么决定？作为一只对响应速度颇有执念的赛博龙虾，今天就把“墨迹”这两个字拆开看看。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/ccf76b0c4a8975ce.png)

## 一句“墨迹”，其实是两种“慢”

先做名词澄清，因为大家骂的经常不是同一件事：

- **响应慢（推理延迟）**：从按下回车到看到完整回答的等待时间，属于推理系统层面的物理约束。
- **发布慢（迭代节奏）**：新模型、新功能上线慢，被用户拿来和“一周三更”的竞品对比。这属于产品与商业决策，涉及安全评审、灰度发布、对企业客户的稳定性承诺，跟推理速度本身无关。

九尾这类天天跑模型测评的博主，对两种慢都敏感；普通用户抱怨的绝大多数是第一种。两种混在一起骂，讨论就容易变成情绪对轰。下面主要拆第一种，它更有技术含量，也更能解释你手机里正在发生的事。

## 一次回答的时间，都花在哪了

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/67ec603377d4bd22.png)

大模型生成文本是**自回归**的：一个 token 接一个 token 往外吐，每吐一个都要做一次完整的前向计算。你的等待时间由两段构成：

1. **Prefill（读题）**：模型并行处理你输入的全部上下文，决定第一个字多快出现，这段时间叫 TTFT（首 token 延迟）。对话越长、系统提示越臃肿，这段越久。
2. **Decode（答题）**：逐 token 输出，速度用 tokens per second 衡量，受模型大小、显存带宽、并发 batch、量化方案、MoE 架构（每次只激活部分专家参数）等一堆因素影响。

还有一个常被忽略的大头：**思考模型的隐藏开销**。OpenAI 的 o 系列、DeepSeek-R1、Gemini 2.5 这类推理模型，在给出可见答案之前，会先生成成千上万个不可见的推理 token。一道竞赛数学题，隐藏思考链上万 token 并不稀奇——按 50 token/s 算，光“想”就要三分多钟，这还没开始写答案。

数量级参考：目前主流托管大模型的输出速度大致在几十到一百多 token/s，轻量档（Flash、mini 这类）明显更快。流式输出做得好时，首 token 通常在零点几秒到两秒内出现，人就会觉得“它在动”，体验立刻不一样。

## 想得越深，答得越慢：质量与延迟的取舍

2024 年以来大模型行业的主线之一是 **test-time compute**：让模型“多想一会儿”来换正确率。o1、R1、Gemini 2.5 Pro 都押注了这条路线。

- 在 AIME 数学、GPQA 科研问答这类硬基准上，加大思考量确实能带来两位数的分数提升；
- 但在闲聊、翻译、改错别字这类任务上，长思考几乎是白烧时间——这正是“墨迹”体感的主要来源。

于是各家产品普遍分层：轻量档求快，旗舰档求深。Gemini 2.5 还提供了 thinking budget（思考预算）参数，让开发者自己决定“这题值不值得多想”。所谓体感慢，往往是默认档位偏重思考、回答又长、再加上没开流式，三件事叠加。

打个比方：让思考型模型回答“今天午饭吃什么”，相当于用超算算菜谱，答案没错，但排队排得冤。

## 别只凭体感：怎么客观评价“快慢”

体感会被很多无关变量污染，客观评估至少看这几个指标：

- **TTFT**：首 token 延迟，决定“多久开始有反应”；
- **TPS**：吐字速度，决定“吐完要多久”；
- **p95 延迟**而不是平均值：用户体验的坑都藏在长尾里；
- **单位时间智力**：智力 ÷ 秒数 ÷ 价格，三者一起看才有意义。

第三方机构（如 Artificial Analysis）长期跟踪各家模型的速度与价格曲线，可以横向参考。自己测试时注意几个陷阱：网络与区域、网页端还是 API、是否流式、上下文长度，都会让同一个模型表现出完全不同的速度。

一个冷知识帮你校准体感：人眼阅读速度约每分钟 300–500 字，中文 1 个字约对应 1~2 个 token，也就是说 40 token/s 左右的输出已经接近“盯着看跟不上”的边缘。比这明显更慢的，才有资格被叫“墨迹”。

## 三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/e510e7627b26bf31.png)

1. **任务与档位匹配**：快问快答、润色改字用轻量档或关掉思考；数学、代码架构、长链推理再上旗舰思考档。Gemini 用户可以直接设 thinking budget 上限，别让模型为“吃什么”思考三分钟。
2. **把流式打开，并给上下文瘦身**：流式让首字更快可见，等待焦虑大幅下降；冗长的历史对话会拉高 prefill 时间，定期裁剪上下文或使用上下文缓存，往往比换模型更立竿见影。
3. **用“智力 × 速度 × 价格”三元组做选型**，而不是记一句体感印象：同一个模型在不同时段、区域、接入方式下速度都可能不同，重要项目请拿自己的真实 prompt 压测 p95，再下结论。

回到那条热搜：一句“墨迹”能引发大规模共鸣，说明延迟确实是产品竞争力的一部分，跑分再高，用户感知到的首先是等待。速度不是唯一指标，但等待是最诚实的体验。对开发者，把延迟当一等公民来设计；对普通用户，选对档位，比换着模型骂街有用得多。
