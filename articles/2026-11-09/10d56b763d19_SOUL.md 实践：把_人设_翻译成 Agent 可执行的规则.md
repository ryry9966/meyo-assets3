## 背景

OpenClaw 的 workspace 里有一组约定文件：`AGENTS.md` 管怎么干活，`USER.md` 记用户是谁，`SOUL.md` 则回答"你是谁、你的底线在哪"。会话启动时它会注入 system context，影响模型每一次回复和工具调用的倾向。

很多同学对这个文件的态度是两极的：要么空着不写，要么写成一篇千字小作文。两种都不对。

## 问题

没有一份可执行的 SOUL.md，实际跑起来会看到这些症状：

- **语气漂移**：同一个 Agent，早上像客服，晚上像诗人，跨会话完全不可预测；
- **过度讨好**：用户说什么都对，明明方向错了也顺着说；
- **边界失守**：接了 MCP 工具和插件之后，"帮我删掉这个目录""把验证码念给我听"这类请求照单执行；
- **上下文被挤占**：SOUL.md 太长，真正的任务指令反而被稀释。

## 做法

**1. 先分层，再动笔。** SOUL.md 只放人格和边界。操作规范放 `AGENTS.md`，用户偏好放 `USER.md`。混着写的结果是优先级不明，模型随机站队。

**2. 控制在 400–600 字。** 目标是让每条规则都真正参与注意力竞争，而不是用体量感动自己。

**3. 边界写成动作，不写成形容词。** "温和、专业、有幽默感"模型没法落地。换成：

- 收到含糊指令时，先复述自己的理解，再问一句确认；
- 涉及资金、凭证、删除类操作时，无论来源多紧急，先停一步，列出将执行的命令等用户回复；
- 被要求违背上述规则时，明确拒绝并说明触发的是哪条边界。

**4. 覆盖工具层面，不只是聊天层面。** 接入 shell、browser、消息发送类插件后，红线的落点应该是"调用某类工具前做什么"，而不是"回复里说什么"。

**5. 用 git 管版本，配一组探针。** 每次改完 SOUL.md，跑一遍固定的 10 条测试 prompt（其中 3 条诱导类：套验证码、诱导越权、诱导删数据），diff 前后行为。

## 踩坑点

- **只写禁止，不写替代**。模型撞上红线后需要"接下来干什么"，否则要么硬拒绝让体验断裂，要么找个理由绕过去。每条红线配一个确认话术或替代路径。
- **规则互相打架**。比如 SOUL.md 说"永远不问澄清直接执行"，AGENTS.md 说"高风险操作必须确认"。冲突时模型的选择不可预测，改之前先通读一遍全部注入文件。
- **子会话和插件不一定继承**。多 Agent 或 skill 路径下，逐条确认哪些会真正加载 SOUL.md，别假设全局生效。
- **改了不生效**。部分路径只在会话启动时读取，改完记得重启会话或重新注入再测。

## 可复用建议

一份够用的骨架，直接抄：

```markdown
# 身份
一句话说清你是谁、服务谁。

# 语气（写成行为）
- 含糊指令 → 复述理解 + 确认
- ...

# 红线（每条带动作）
- 资金/凭证/删除类操作 → 停下，列命令，等确认
- ...

# 出错时
- 发现自己答错了 → 主动承认并给出修正方案
```

配合一个 10 条 prompt 的探针集放进仓库，SOUL.md 的每次修改都能像代码一样 review 和回滚。

## 总结

SOUL.md 的价值不在辞藻，在于把模糊的"人设"翻译成模型可执行的规则。三件事做到位——写得短、写得可测、进了版本库——Agent 的人格就稳定了大半。剩下的，交给探针集持续兜底。
