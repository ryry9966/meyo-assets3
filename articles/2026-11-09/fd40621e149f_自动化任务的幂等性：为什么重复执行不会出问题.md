## 背景

在 OpenClaw 这类 agent 环境里，"跑一次就结束"的任务其实很少。定时任务可能被调度器重复触发；网络超时后 agent 会重试；MCP 工具调用失败后上层循环会再来一次；人工排查时你也经常手动 re-run。执行两次、三次是常态，不是异常。

## 问题

幂等性的定义很朴素：同一个操作执行一次和执行多次，最终状态一致。问题在于大量常用操作不满足这一点——发送通知消息、往文件里 append、向外部 API 创建资源、数据库 insert、计数器自增。

举个最常见的例子：一个每天早上发群摘要的 cron 任务，第一次请求其实成功了但响应超时，调度器重试，群里出现两份摘要；或者 agent 写日报用的是追加模式，重跑一次后内容全部重复。这类问题单次测试永远发现不了，只在生产环境以"偶尔重复"的形式出现，排查成本很高。

## 做法

1. **先分类。** 读操作、按固定路径覆盖写文件、按 ID 删除、PUT 语义的更新，天然幂等，不用处理。发消息、创建资源、追加内容、自增，属于非幂等，需要设计。

2. **给非幂等操作加幂等键。** 关键是键要由"逻辑身份"决定，而不是执行时刻。推荐组合：任务 ID + 逻辑时间窗（如当天日期）+ 输入摘要哈希。执行前先查键：存在就跳过，不存在就先占位再执行。存储用 SQLite 一张表或 Redis 的 SETNX（带 TTL）都够用，插件里写一个本地状态文件也可以接受——只要占位动作是原子的。

3. **用覆盖代替追加。** 任务产物用确定性命名：日报文件名按日期生成、路径固定，重跑就是覆盖，天然幂等。

4. **调外部 API 优先用对方的幂等支持。** 很多支付、工单类 API 支持幂等键请求头，直接透传；不支持的，退化为"先查再写"，或接受偶尔重复、在下游做去重。

5. **通知类操作单独记"已发送"状态。** 发送成功后立即落状态，下次执行前检查。宁可漏发后补，也别重复发。

## 踩坑点

- **用当前时间戳做幂等键**：每次重试生成新键，等于没做。必须用逻辑时间窗或调度批次 ID。
- **check-then-act 的竞态**：两个并发实例都通过检查、然后都执行。占位动作必须原子（SETNX、唯一约束、文件锁）。
- **TTL 过短**：重试发生在 TTL 之后，重复照样出现。TTL 要大于最大重试窗口。
- **隐性副作用**：有些看起来是"读"的工具其实有副作用（标记已读、更新缓存、触发 webhook），别默认只读就安全。
- **把超时当失败立即重试**：超时可能意味着"已执行但响应丢失"，这是重复的最大来源。先确认再重试，或确保重试本身幂等。

## 可复用建议

- 给每个自动化任务写一行声明：幂等策略是什么、键是什么、存哪里。写不出来，说明没想清楚。
- 能设计成状态机的就设计成状态机：状态外置（pending / running / done），执行过程是状态迁移，迁移天然幂等。
- 把"连续跑两次、对比两次结果一致"作为自动化任务的验收标准之一。
- 封装 MCP 工具时，在文档里明确标注哪些工具可安全重试，让上层 agent 的重试策略有依据。

## 总结

幂等性不是让任务不重复执行，而是让重复执行无害。在 agent 自动化场景里，重试、重复触发、手动重跑是常态——设计时就假设"这个任务一定会被跑第二次"，然后让第二次的结果和第一次一样。做到这一点，你的定时任务和插件才敢真正放手让它跑。
