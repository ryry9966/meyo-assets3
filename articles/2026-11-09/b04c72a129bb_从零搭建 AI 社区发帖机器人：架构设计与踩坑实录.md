## 背景

我们社区每天有大量讨论沉淀在不同板块，运营一直想把这些内容整理成每日精选帖发出来。人工做了一个月，耗时且质量不稳定，于是决定用 OpenClaw 搭一个半自动发帖机器人。目标很明确：定时抓取指定板块的高质量讨论，由 Agent 生成草稿，经校验后发布。

## 问题

最初的想法很简单：写个 cron，调 LLM 生成内容，调发帖 API。跑起来之后问题接连出现：

- Agent 会编造不存在的引用链接和"网友观点"；
- 同一内容隔两天被再发一次；
- 发布接口没有幂等设计，重试导致重复帖；
- 一次塞给 Agent 的任务太重，上下文膨胀后输出格式崩坏。

## 做法

最终架构分五层，每层职责单一：

1. **调度层**：cron 触发，每次运行都是全新短会话，不复用历史上下文。
2. **采集层**：自建一个 MCP server，暴露 `fetch_board_posts`、`fetch_thread_detail` 两个只读工具，返回结构化 JSON。
3. **生成层**：OpenClaw Agent 接收采集结果，按 JSON Schema 输出草稿（标题、摘要、引用列表）。system prompt 中明确约束：引用只能来自工具返回的数据。
4. **校验层**：脚本侧做三件事——引用链接逐条回验、内容哈希与 SQLite 中近 7 天记录比对去重、敏感词过滤。
5. **发布层**：MCP 工具 `publish_post` 前置 dry-run 模式。前两周所有草稿进人工审核队列，确认稳定后才逐步放权。

状态全部落在 SQLite（帖子 ID、内容哈希、发布时间、审核状态），Agent 本身不持有任何长期记忆。

## 踩坑点

- **幻觉引用**：仅靠 prompt 约束不够，必须在代码层回验 URL，验证不过直接打回重写。
- **重复发帖**：只查标题相似度会漏，最后用内容哈希 + 标题分词重合度双条件才堵住。
- **工具权限过大**：最初 `publish_post` 没有 dry-run，Agent 一次格式异常直接发了半成品帖。教训：发布类工具必须先支持草稿态，再开放正式发布。
- **限流**：社区 API 有速率限制，重试要加指数退避，否则一波重试把自己的 IP 打进冷却。
- **长会话**：让一个 Agent 会话从采集做到发布，跑到后面输出质量明显下降。拆成短会话后稳定得多。

## 可复用建议

1. 发布动作一律做幂等：以内容哈希作幂等键，重试安全。
2. 状态外置到数据库，不要指望对话上下文记住"昨天发过什么"。
3. 工具粒度要小且原子，采集、校验、发布分开，方便定位问题。
4. 结构化输出比自由文本可靠，Schema 校验失败自动重试一次再降级为人工。
5. 保留人工开关：任何自动发布系统都该有 dry-run 和一键暂停。

## 总结

这个机器人现在每天稳定产出 1-2 篇精选帖，人工只需要最后扫一眼。整个项目最大的收获不是自动化本身，而是想清楚了"Agent 负责生成，代码负责兜底"这条边界——凡是不可逆的动作（发布、删除），决策权永远不要完全交给模型。核心逻辑五百行左右，MCP 工具复用了社区示例实现，感兴趣的可以照这个分层思路自己搭一个。
