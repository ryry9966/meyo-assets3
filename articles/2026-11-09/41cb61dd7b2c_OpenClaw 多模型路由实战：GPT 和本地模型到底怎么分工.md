## 背景

OpenClaw 的模型层是可插拔的：除了云端 API，任何 OpenAI 兼容端点（Ollama、vLLM、llama.cpp 起的本地服务）都能挂进来，不同 agent、定时任务、MCP 工具调用可以各自指定模型。但实际部署里最常见的两种极端是：全走旗舰云模型，或者全走本地。前者烧钱，后者在硬任务上掉链子。

## 问题

把我自己的部署拆开看，调用其实分三类，痛点各不相同：

- **轻任务**（格式化、分类、短摘要、工具参数补全）占请求量的大头，用旗舰模型纯属浪费；
- **隐私敏感的会话**（本地笔记、消息记录）不应该出网；
- **重任务**（多步规划、跨文件改代码、复杂排障）本地小模型撑不住，工具调用经常格式崩坏。

所以路由要解决的是：让每类调用落到合适的模型上，同时在云服务抖动时有兜底。

## 做法

**第一步：列任务清单，划三档。** 别凭感觉分，把 OpenClaw 日志里实际发生的调用翻一遍。我的划分：轻任务走本地 7B~14B；日常对话和单文件修改走中档；agent 规划和代码重构走旗舰云模型。

**第二步：三层路由落配置。**

1. 默认模型设成本地/便宜档，保证杂活不出网、不烧钱；
2. 按 agent 覆盖：编码 agent、规划 agent 显式指定旗舰模型；
3. 配 fallback 链：可用性优先就"云主本地备"，隐私优先就"本地主云备"——但后者要控制哪些会话允许升级。

**第三步：升级路径做成显式重试。** 本地模型失败两次、或 tool call 的 JSON 解析失败，就换云模型重跑一次，设最大重试次数，不搞无限重试。

**第四步：看日志校准。** 每次调用记录模型、耗时、token 数、是否触发 fallback。跑一周，回头看路由表和直觉是否一致，不一致就调。

## 踩坑点

- 本地模型 context 窗口小，长会话被**静默截断**，表现为"突然失忆"，不是模型笨；
- 小模型 function calling 不稳，MCP 工具参数漏字段是常事。更稳的做法是让本地模型只做参数整理，最终 tool call 由强模型发起；
- 量化太狠的模型写代码明显掉智商，代码任务别省这个钱；
- fallback 别写成环：云→本地→云会放大故障，务必设总超时；
- 隐私优先的部署里，fallback 到云等于绕过了自己的隐私策略，要么禁止升级，要么给会话打标记再放行；
- 本地模型冷启动加载显存的十几秒会吃掉"快"的优势，常驻进程就常驻显存。

## 可复用建议

1. 建一个 20 条左右、来自真实任务的评测集，改路由前后各跑一遍，看通过率而不是看感觉；
2. 模型版本钉死，云模型静默升级会造成行为漂移；
3. 把"快车道/深车道"拆成两个 agent，从配置层面分开，比运行时智能判断更可控；
4. 路由表写进配置文件而不是硬编码，三个月后改起来不痛苦。

## 总结

多模型路由本质是在成本、质量、隐私三个约束之间找平衡。不建议上来就追求智能路由，先用"默认便宜 + 显式升级"这个最笨的方案跑两周，拿日志说话再迭代。OpenClaw 把模型层做成了配置项，恰恰是希望你把精力花在路由策略本身，而不是胶水代码上。
