# 背景

在 OpenClaw 的插件和 Agent 工作流里，让模型输出结构化 JSON 是最常见的集成方式：技能编排要消费它，MCP 工具要回传它，自动化脚本靠它做分支判断。提示词里写一句「只输出 JSON」，听起来像约定，实际只是君子协定——模型可能包一层 ```json 围栏，可能用 `<json>...</json>` 标签，可能先解释两句再贴 JSON，推理型模型还会先带一段思考块。格式漂移不是异常，是常态。

# 问题

最直接的写法是 `json.loads(response)`，一遇围栏就抛异常。常见的脆弱修法是简单 replace 掉反引号，但遇到内容里嵌套围栏、或「标签+围栏」双重包裹照样翻车。更麻烦的还有：多个 JSON 块、尾逗号、全角引号、字符串里未转义的换行。典型症状是测试环境稳、线上挂，换模型好、升级完又挂。这类问题不值得靠提示词措辞去治——你穷举不完所有模型的行为，解析层必须自己扛。

# 做法

我的做法是把解析写成漏斗，把模型原始输出当不可信输入处理：

1. **候选提取**：依次跑三个提取器——剥 markdown 围栏、剥自定义标签（json / output / result / think）、string-aware 括号配对找完整的 `{...}` / `[...]` 块。收集全部候选，不要只取第一个。
2. **按序解析**：对每个候选依次 `json.loads`；多个候选时取解析成功且通过 schema 的那个。
3. **最小修复**：只处理最高频的几类——尾逗号、全角引号、字符串内裸换行。建议直接用成熟的 JSON repair 库，别自己堆正则。
4. **Schema 校验**：JSON 合法后再过一遍 pydantic / jsonschema，`"123"` vs `123` 这类类型漂移在这一步暴露。
5. **有界重试**：全部失败时，把解析错误和原始输出拼回上下文重试一次，硬上限 2 次，避免 Agent 陷进循环。

# 踩坑点

- **用正则找 `{...}`**：字符串里的 `{` 或嵌套对象会让它切错位置，必须用 string-aware 的括号配对。
- **贪婪去围栏**：JSON 字段值本身含代码示例（带围栏）时，粗暴替换会把内容截断。
- **只取第一个块**：模型常「先解释再给 JSON」，第一个 `{` 多半在解释文本里；应取能解析且过 schema 的那个。
- **温度 > 0 时格式是随机的**：贪心解码下测出的稳定不代表线上行为。
- **静默兜底**：失败返回 `{}` 会把上游问题埋掉；应抛错并保留原始输出。
- **层次越权**：解析层只保证「合法 JSON 且结构正确」，枚举值等语义校验留给业务层，别混在一起。

# 可复用建议

- 解析逻辑收敛到一个公共模块，别在每个插件里各抄一份 `json.loads`。
- 把线上真实坏输出存成 fixture 做回归测试，比任何提示词措辞优化都保值。
- 记录每次解析用的策略和成功率，格式漂移在模型升级前就能看到趋势。
- 优先用 API 的结构化输出能力（JSON mode / tool call），但兜底解析照写——模型不总守约。

# 总结

把 LLM 输出当输入看，别当返回值看。解析层做成「提取候选 → 归一化 → 解析 → 校验 → 有界重试」的漏斗，比在提示词里反复叮嘱「请务必只输出 JSON」可靠得多。模型会换、提示词会改，一套防御性解析代码是少数能跨版本活下来的资产。
