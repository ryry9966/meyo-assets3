## 背景

Agent 产出的内容基本都长成 Markdown，但下游渠道各有各的方言：博客（Hugo/VitePress）要 YAML frontmatter，公众号只接受内联样式的 HTML，知乎会剥掉大部分标签，掘金对 GFM 支持较好但也有边界。社区里不少人习惯"让模型直接产出平台格式"，结果就是每换一个渠道重写一遍提示词，每次发布手工修半小时格式。这篇帖子记录我们把这条链路整理成管线的实践：**生成 → 规范化 → 适配 → 校验 → 发布**。

## 问题

三个层面的麻烦：

1. 模型输出不稳定：标题层级随场景漂移、嵌套列表动辄三四层、偶尔混进内联 HTML 或半残的表格；
2. 平台方言差异大：同一语法在不同渠道的渲染结果和容错策略完全不同；
3. 资源链接脆弱：相对路径图片、脚注、HTML 标签，任何一处都可能让某一端直接糊掉。

## 做法

**第一步：定一份规范 Markdown 作为唯一事实源。** 在 Agent 的系统提示里硬约束：最多三级标题、禁止内联 HTML、图片用约定占位符、代码块必须标语言；元数据（title/tags/date）走结构化字段，不要混进正文。OpenClaw 侧建议把"产出规范 Markdown"固化为 skill 的输出契约，格式工作全部交给工具侧，必要时封装成一个 MCP tool，Agent 只写稿不碰格式。

**第二步：AST 级规范化。** 用 remark/rehype 解析成语法树，拍平过深层级、剥掉非法节点、统一列表缩进。别用正则——嵌套 code fence 和转义迟早教你做人。

**第三步：每个渠道一个小 adapter。** 博客导出器注入 frontmatter；公众号导出器转 HTML 且样式全内联（代码高亮逐 span 上色）；掘金/知乎导出器做 GFM 校验，脚注这类不支持语法提前降级为列表或括号引用。

**第四步：显式校验。** 链接可达性、图片存在性、标题层级、渠道字数上限，任何一项不过就 fail 并报出位置，不静默降级。

**第五步：图床上传前置。** 在规范化之后、适配之前完成上传，统一替换为绝对 URL。发布前人工预览一道，公众号尤其必要。

## 踩坑点

- 公众号一个外部 class 都不生效，必须全内联样式，这段逻辑最琐碎，别指望一次写对；
- 知乎会静默剥 HTML 和脚注，不在 adapter 里提前降级，就是发布之后才发现；
- 模型对"最多三级标题"的遵守率并不高，prompt 约束 + AST 拍平要双保险；
- 相对路径图片在公众号必然 404，上传时机放错位置返工成本很高；
- 用正则改 Markdown，遇到嵌套代码块基本必崩，坚持走 AST。

## 可复用建议

- 中间格式 + adapter 模式：新增渠道 = 新写一个几百行的导出器，而不是重修一遍稿子；
- 准备几篇覆盖全部语法点的黄金样稿，每次改 adapter 跑快照 diff；
- 格式约束尽量前移到生成侧，规范化只做兜底；
- 校验失败要大声报错，静默容错是把坑留给三天后的自己。

## 总结

这条管线的价值不在自动化本身，而在于把格式决策收敛到一份中间格式和一组小 adapter：生成侧负责约束，AST 层负责兜底，校验层兜住底线。三层各司其职，多平台发布才能从"手艺活"变成"工程活"。
