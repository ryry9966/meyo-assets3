## 背景

Agent 默认是无状态的。上下文窗口不是记忆，会话结束就清零。对日常写代码、跑自动化的用户来说，每次都要重新交代"用 pnpm、别动我的 lint 配置、部署走 staging"，体验很割裂。OpenClaw 这类常驻 Agent + MCP 的组合，其实很适合把记忆做成一个独立、可审计的模块，而不是堆在 system prompt 里的一坨文本。这里分享一套我自己在跑的方案。

## 问题

常见的三种失败做法：

- **全塞 system prompt**：token 膨胀，噪声淹没真正的指令，偏好之间还会互相冲突。
- **对聊天记录做 RAG**：检索回来的是"当时说了什么"，而不是提炼后的"用户偏好"，噪点多、命中率低。
- **写入太激进**：每轮都存，错误事实和临时上下文（比如"这周在赶版本"）会污染后续所有会话。

## 做法

我用三层结构 + 保守写入策略：

1. **分层存储**
   - 工作记忆：当前会话上下文，不落盘。
   - 情景记忆：会话结束时的摘要，按时间衰减。
   - 偏好记忆（核心）：结构化条目，形如 `{key: "package_manager", value: "pnpm", scope: "global", confidence: 0.9, updated_at, source_session}`。
2. **写入策略**：只在会话结束或用户显式确认时提取；只存稳定、可一句话复述的事实，不存过程性内容。新旧条目 key 冲突时覆盖，但保留 history 字段，可回滚。
3. **读取策略**：每轮注入前先检索，按 scope（project 优先于 global）和相关度取 top-k，硬性预算 500 token 以内。宁缺毋滥。
4. **MCP 暴露三个工具**：`memory_read` / `memory_search` / `memory_write`。Agent 自己能读写，用户也能直接打开存储文件审计、手改。我用 SQLite，单文件，备份方便。

## 踩坑点

- **存成大段散文**：检索和去重都困难，必须结构化。
- **没做冲突处理**：新旧偏好并存，Agent 行为来回摇摆。
- **scope 混淆**：把"这个项目用 v3 接口"写进全局，其他项目全被带偏。
- **静默写入**：用户不知道 Agent 记了什么，信任崩得很快。写入时在回复里带一句"已记住：xxx"。
- **注入过多**：塞 20 条记忆进上下文，模型反而开始机械复述偏好，回答变僵。

## 可复用建议

- **先别上 RAG**。一个 markdown 偏好文件 + 手动维护，能覆盖 80% 的需求，这是最好的 baseline。
- 每条记忆必须带来源和时间戳，出问题能追溯。
- 给用户一条编辑通路（文件、命令或面板都行），记忆系统必须可审计。
- 按置信度衰减：90 天未被检索命中的条目降权或归档。
- 建一个 10 条左右的回归清单，每次改记忆逻辑后跑一遍"它还记得吗"。

## 总结

记忆系统本质是数据工程问题，不是 prompt 技巧。核心就四点：结构化存储、保守写入、带预算的检索、用户可审计。先跑通最简单的偏好文件方案，再逐步加检索和衰减，比一上来就搭向量库靠谱得多。如果你已经在 OpenClaw 里接了 MCP，建议从一个只有三个工具的 memory server 起步，一周内就能验证效果。
