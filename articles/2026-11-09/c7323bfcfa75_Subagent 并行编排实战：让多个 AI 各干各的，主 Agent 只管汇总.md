## 背景

用一个主 agent 串行处理批量任务，是多数人用 OpenClaw 的起点：批量改代码注释、审一批 PR、给多个服务写巡检报告。这类任务的共同点是单个不难、数量多、彼此独立——串行跑一遍，既慢，又会把主会话的上下文撑爆。

OpenClaw 提供了 subagent 机制（当前为 `sessions_spawn` 工具，版本迭代较快，参数以 docs 为准）：主 agent 把任务拆给多个子 agent 并行执行，各自拥有独立会话与上下文，完成后向主会话汇报结论。下面是社区几次实战后的经验总结，重点是"什么时候该拆、怎么拆才不翻车"。

## 问题

直接让主 agent 自己干，有三个典型痛点：

1. **上下文污染**：读 10 个文件的中间输出全堆在主会话，真正需要的只是结论，噪声占大头，后续对话质量明显下降。
2. **串行太慢**：10 个互不依赖的任务排队跑，耗时约是单任务的 10 倍。
3. **一错全停**：某个任务卡住，整条批处理流程跟着中断。

## 做法

我们的编排分四步：

**1. 判断是否值得拆。** 只拆满足两个条件的任务：子任务间无共享可变状态；每个子任务的指令能写成一段自包含 prompt（子 agent 看不到主会话历史）。

**2. 定义输出契约。** 在 spawn 的 task 里明确规定返回格式，例如"只返回：变更文件列表 + 风险点 + 建议动作，不超过 200 字"。汇报精简，是并行编排能成立的前提。

**3. 控制并发。** 别一次 spawn 太多，3–5 个为宜；超量后调度开销和 API 限流会吃掉并行收益。建议先 spawn 一个跑通流程，再放量。

**4. 主 agent 统一汇总。** 子 agent 返回的紧凑结论由主 agent 聚合、去重、排序，形成最终报告。聚合这步不要下放给子 agent。

## 踩坑点

- **两个子 agent 改同一个文件**：后写的覆盖先写的。解法是给每个子 agent 独立工作目录，或让子 agent 只产出 diff/建议，由主 agent 统一落盘。
- **prompt 不自包含**：子 agent 收到"继续刚才的分析"这种指令会直接失败。spawn 的 task 要当成给新同事的交接文档来写，背景、路径、目标全部写清。
- **全量回传输出**：让子 agent 把整个文件内容贴回来，主会话瞬间爆上下文。坚持"只回结论"。
- **忽略失败分支**：子 agent 超时后主 agent 干等。要设定超时预期，失败任务记录在案，别让一个坏任务拖死整批。

## 可复用建议

- 拆分粒度以"单个子任务 5–15 分钟内可完成"为准，太细不值得。
- 子 agent 用更快更便宜的模型即可，强模型留给主 agent 做汇总判断。
- 只读类任务（审查、巡检、总结）最适合并行；写类任务先隔离再并行。
- 把 spawn 的 prompt 模板沉淀成技能或脚本，复用率很高。

## 总结

subagent 编排的价值不在"多开几个 AI"本身，而在于倒逼你把任务拆解清楚、把输入输出契约写明白。边界清晰，并行是自然结果；边界不清，开再多子 agent 只是把混乱放大几倍。建议从一个真实的小批量任务开始，跑通"拆分—隔离—精简汇报—汇总"这条链路，再逐步放大规模。
