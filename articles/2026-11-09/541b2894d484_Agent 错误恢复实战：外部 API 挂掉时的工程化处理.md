## 背景

跑过真实自动化任务的人都有体感：demo 时一帆风顺，放到生产环境，LLM 供应商开始限流，MCP 工具背后的第三方 API 偶发超时，内网服务周期性抖动。Agent 是多步编排，任何一步的依赖挂掉，整条链路都会受影响。所以"外部 API 会失败"不是异常路径，而是需要按一等公民对待的常态。

## 问题

实际观察下来，故障大致有三种表现：

1. **直接崩掉**：异常没被接住，一整批任务中途终止，且没有恢复手段，只能从头重跑。
2. **静默失败**：最危险的一种。工具返回错误信息后，模型自己"脑补"了一个看似合理的结果继续往下执行，下游拿到脏数据却毫无察觉。
3. **重试风暴**：无退避、无上限的重试把瞬时故障放大成雪崩，非幂等操作还会被重复执行。

## 做法

按下面的顺序搭一层恢复机制，成本不高，收益明显：

**1. 先分类错误。** 可重试（429、5xx、超时、网络错误）和不可重试（400、401、403、业务校验失败）分开处理。对 401 重试只是烧配额，正确动作是刷新凭证或终止。

**2. 指数退避 + 随机抖动。** 基础间隔 1s，倍增，最多 3~5 次，加随机抖动避免所有 worker 在同一时刻集中重试。

**3. 处处设超时。** 除了单次请求超时，还要给整步设置预算。没有 deadline 的重试等于无限挂起。

**4. 把错误当数据返回给 Agent。** 不要让异常打断循环，返回结构化错误（错误码、是否可重试、处理建议），并在提示词里明确约束："工具返回错误时，禁止编造结果，必须如实报告或走降级路径。"

**5. 准备降级路径。** 备用 provider、上一轮的缓存快照、跳过非关键步骤并把结果标记为 partial，按业务容忍度选择。

**6. 状态落盘，支持断点续跑。** 每步执行后把状态持久化到 DB 或文件，失败后从断点恢复而不是重跑全链路；写操作务必带幂等键。

**7. 连续失败后升级人工。** 比如重试加降级都失败 3 次，就停止并通知，而不是无限循环。

## 踩坑点

- 重试非幂等的 POST（下单、发消息）导致重复副作用。GET 随便重试，写操作必须幂等键。
- 退避无抖动，多实例同时重试，等于自己对自己发起 DDoS。
- 上层取消了任务，但取消信号没传到下游 HTTP 请求，请求还在后台跑。
- 状态只存内存，进程一重启进度全丢。
- 提示词里没写错误处理约束，模型默认目标是"把流程走完"，于是开始编。

## 可复用建议

- 做一个统一的工具调用封装层：超时、重试、退避、错误归一化都收敛在这一处，插件和业务代码不重复造轮子。
- 每个工具的 description 里写清楚失败语义：是否幂等、可否重试、有没有备用路径，让模型决策时有据可依。
- 定期做故障注入演练：手动断掉某个依赖跑一轮，看 Agent 的表现是否符合预期。

## 总结

错误恢复不是包一层 try/except 就完事。可靠的 Agent 建立在四件事的组合上：**错误分类、超时预算、幂等性、状态持久化**。Agent 自主性越强，越要假设外部世界随时会失败——好的设计不是避免失败，而是失败后能便宜地恢复。
