## 背景

大部分 Agent 的默认形态是"金鱼"：会话一结束，一切归零。你第一次告诉它"commit message 用中文、别加 emoji"，第三次开新会话它又问一遍。Context window 再大也不是记忆——它只解决"这次装得下"，不解决"下次还记得"。

在 OpenClaw 这类长期运行的助手场景里（挂多个 channel、每天被唤起几十次），记忆直接决定体验。这篇帖子记录我给自己助手做记忆系统的第一版设计，思路可以搬到任何 Agent / MCP / 插件体系里。

## 问题

最常见的三种错误做法：

1. **全塞 system prompt**。偏好攒到几十条后 prompt 膨胀，指令互相打架，模型开始选择性失明。
2. **什么都记**。随口一句闲聊也入库，噪声淹没有效偏好，检索回来全是废料。
3. **只写不管**。用户半年前说"用 Python"，现在改用 Go 了，旧记忆还在每次被命中。

本质上是四个工程问题：**记什么、什么时候写、怎么取、怎么更新/遗忘**。

## 做法

我按四层拆，用一个独立 memory 服务承载（在 OpenClaw 里可以做成插件或 MCP server，暴露 `memory_search` / `memory_write` 两个 tool）：

**1. 分层存储**
- 会话内：不落盘，就是上下文本身；
- 情景层：会话结束生成摘要，带 TTL（如 30 天）；
- 语义层：长期偏好与事实，如"喜欢简洁回复""时区 UTC+8"；
- 过程层：固定工作流习惯，如"部署前先跑 lint"。

优先做语义层，收益最大。

**2. 写入：异步 + 结构化**
不在对话主链路里写。会话结束或空闲时跑后台抽取任务，用 LLM 从对话中抽结构化条目：`{category, content, confidence, source_session}`。低于置信度阈值直接丢弃——"今天天气不错"这种根本不该入库。写入前过一遍敏感信息 denylist（密钥、住址类）。

**3. 存储：先简单**
SQLite 一张表加 embedding 列就够：`user_id / category / content / embedding / created_at / updated_at / hit_count / status`。别一上来上图数据库。

**4. 检索：预算内取小集合**
按 embedding 相似度召回，叠加时间衰减和 hit_count 加权，取 top 3–5，压缩成 ≤500 token 的块注入 system prompt。宁少勿多。

**5. 更新与遗忘**
新旧冲突时比较置信度和时间，新覆盖旧、保留版本历史。用户纠正 agent 的那句话按高优先级写入。同时给用户暴露指令："列出你记住的关于我的一切"和"忘掉某条"——没有删除能力的记忆系统不该上线。

## 踩坑点

- **检索马太效应**：旧记忆 hit_count 高一直排前面，新偏好永远上不来。必须加时间衰减。
- **抽取太勤**：两周后库里 80% 是闲聊噪声。置信度阈值宁高勿低。
- **只存自由文本**：不分类不结构化，检索没法按 category 过滤，注入也没法压缩。schema 先行。
- **没有 provenance**：一条奇怪的记忆出现时查不到来源，没法调试。每条记录带 source_session。
- **没评估**：至少记一下每次注入了哪些记忆、用户是否纠正行为，否则不知道它在帮忙还是帮倒忙。

## 可复用建议

- 记忆写入永远是异步后台任务，不阻塞主对话；
- 注入记忆设硬性 token 预算，超了就砍；
- 置信度 + 版本化 + 时间戳是冲突解决的最小配置；
- 用户可见、可删，既是合规底线也是调试工具；
- 从 SQLite + embedding + 三条规则起步，跑两周看日志再加复杂度。

## 总结

Agent 记忆不是一个"功能"，而是一条数据生命周期：写入端过滤、检索端限流、更新端解决冲突。先把语义层做对——记什么、怎么取——再考虑情景层和更复杂的机制。我的经验是：一个 200 行的 SQLite 版本，比一个设计宏大但从不落地的方案有用得多。欢迎在评论区贴你们的 memory schema 一起交流。
