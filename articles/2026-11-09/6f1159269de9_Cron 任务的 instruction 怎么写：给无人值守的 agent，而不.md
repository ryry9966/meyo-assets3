## 背景

OpenClaw 的 cron 任务本质上是"定时唤醒一个没有记忆的同事"：到点触发、执行 instruction、把结果送到指定渠道，然后结束。整个过程没有对话上下文，也没有人在旁边答疑。这意味着聊天里好用的 prompt 风格，直接搬过来大概率翻车。

最近我把几个定时任务（日志巡检、数据汇总、依赖更新提醒）从"聊天式写法"重构成"岗位说明书式写法"，从两周跑偏三次到基本稳定。这篇记录具体做法。

## 问题：聊天式 prompt 在 cron 场景为什么失效

- **无上下文**：你昨天聊过的内容，agent 这次醒来一无所知
- **无人答疑**：instruction 里任何一个模糊点，agent 只能猜，猜错就静默跑偏
- **重复执行**：同一条指令会跑几百次，小概率边界情况迟早必然发生
- **失败不可见**：跑偏了不报错，只是产出一份没用但看起来正常的结果

## 做法：五段式模板

我的 cron instruction 现在固定按五段写：

1. **上下文**：一句话说明这是什么任务、为什么存在，让冷启动的 agent 有全局观
2. **任务**：动词开头、单一目标。"读取 X，计算 Y，写入 Z"，不要堆多个目标
3. **边界**：允许访问的路径、工具或 MCP 能力白名单，时间预算，以及明确的"不要做"清单
4. **产出**：输出格式、落点、字数上限，产出必须可校验
5. **异常分支**：数据缺失怎么办、命令失败怎么办、要不要通知人

示例（日志巡检任务，节选）：

```
你是巡检任务。读取 /data/logs/app-$(date +%F).log，
统计 ERROR 行数并提取最近 5 条样本。
只读该目录，不执行任何修复动作。
产出写入 /data/reports/$(date +%F).md，不超过 15 行。
若日志文件不存在或 ERROR 为 0，仍在报告里注明"无异常"。
仅当 ERROR > 100 时，通过消息渠道推送告警。
```

## 踩坑点

1. **依赖"上次运行的结果"**。agent 每次醒来都是新的，状态要么落在文件里显式读写，要么把任务设计成幂等的
2. **"今天"没定义**。cron 触发时刻和你想的时区可能不一致，instruction 里明确写出日期口径
3. **没有输出契约**。不限定格式和落点，每次报告的样式都会漂移，没法做趋势对比
4. **一条指令塞多个目标**。无人值守时多目标必有取舍，agent 的取舍未必是你的取舍
5. **上线前不手动触发**。先手动跑三五次、覆盖正常和异常分支，再启用定时，能省掉大部分返工

## 可复用建议

- 把 cron instruction 当"给外包的工单"写：假设对方很聪明，但完全不认识你
- 复杂流程别堆在 instruction 里，写成 SOP 文件让 agent 先读，instruction 只做分发和约束，顺便走版本管理
- 报告类任务坚持"无异常也要产出"，用产出物的存在性做健康检查
- 告警设阈值和冷却时间，避免定时任务本身变成噪音源

## 总结

cron 任务的 instruction 不是聊天，是自动化系统的配置项。核心转变就一句话：从"跟 agent 对话"改成"给一个聪明但不了解背景的执行者写岗位说明书"。上下文、边界、产出、异常分支写清楚，定时任务才能从"偶尔能用"变成"可以托付"。
