## 背景

OpenClaw 的 cron 任务本质上是一件事：到点后，框架用一条 instruction 拉起一个**全新的 agent 会话**，跑完、输出、结束。没有你在旁边追问、纠偏、补充上下文。这条 instruction 的质量，直接决定你的定时任务是"自动助手"，还是"定时制造噪音"。

我维护着几条跑了数月的生产定时任务（晨报汇总、仓库巡检、数据对账），踩过不少坑，总结出一套写法。

## 问题：大多数人把 instruction 写成了聊天消息

典型反面例子：

> 每天早上帮我看看 issues，有重要的发到群里。

这条指令在有人的对话里没问题，放到无人值守的 cron 里会炸：

- "重要的"没有定义，agent 自己拍标准，而且每天标准都不一样
- 没说发到哪个通道、发几条、什么格式
- 没说"没有重要事项时怎么办"，agent 为了"完成任务"会硬凑内容
- cron 是全新会话，它不记得昨天发过什么，容易重复播报

## 做法：按交接文档的套路写

我现在的模板固定分六段，可以直接抄：

1. **目标**：一句话说明这次执行要产出什么。
2. **输入与工具**：明确用哪个插件/MCP 工具、拉什么数据、时间范围。
3. **步骤**：编号 3–5 步，每步有可判定的完成条件。
4. **输出契约**：发到哪个通道、条数上限、字段格式、是否带来源链接。
5. **失败兜底**：数据拉不到、工具报错时做什么，通常是"输出一行失败说明，禁止编造"。
6. **空结果约定**：明确"无事发生也是正常结果"，输出一句话即可结束。

举个仓库巡检任务的核心段落：

> 使用 github 工具查询本仓库过去 24 小时新增的 open 状态 issue（时区 Asia/Shanghai，以执行时刻倒推 24h）。若为空，向 #ci-log 发送"今日无新增 issue"后结束。若非空，筛选含 bug 或 crash 标签的条目，按严重度排序，最多 5 条，每条一行：编号、标题、链接。查询失败时发送"数据获取失败：{原因}"，不要猜测内容。

## 踩坑点

- **别依赖记忆**：cron 每次都是新会话。需要跨次对比（比如去重），要么让 agent 先把上次结果写到固定文件、本次先读再比，要么用日期做幂等标记。
- **相对时间必须换算**：instruction 里写"今天"不如让 agent 第一步先算出具体日期再执行，时区写死。
- **一条 cron 只干一件事**："汇总 + 判断 + 提醒"拆成两条任务，用第一条的输出文件作为第二条的输入。范围切小，单次才跑得完、跑得稳。
- **输出必须有上限**：没有"最多 N 条"的约束，遇到上游数据异常就是刷屏事故。
- **上线前把失败路径也跑一遍**：手动触发正常路径之外，故意断网、给错 token 跑一次。兜底逻辑没验证过的 cron 等于裸奔。

## 可复用建议

- 写完自检三问：无人回答追问时它能跑完吗？数据为空时它输出什么？连续跑两天会不会重复？
- 给每条任务配一个日志通道，要求 agent 执行完追加一行摘要（时间、结果、条数）。排查问题全靠它。
- instruction 的改动视为代码改动：先挂到测试任务上跑几天，再替换生产任务。

## 总结

Cron instruction 的本质，是给一个能力很强但毫无上下文的"新同事"写交接单。写得越像聊天，跑得越像抽卡；把目标、输入、步骤、输出、兜底、空结果六段写全，定时任务才会从"定时惊喜"变成真正的自动化。
