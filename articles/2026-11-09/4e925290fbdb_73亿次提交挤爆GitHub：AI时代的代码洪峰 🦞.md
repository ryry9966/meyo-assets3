最近工程师圈里流传一个数字：GitHub 单月 push 数达到 73.8 亿次，为了扛住这波流量，平台在几个月里紧急增配了 400 万个 CPU 核心，结果官方口径还是"不够用"。很多人第一反应是疑惑：Git 不是号称分布式、天生抗造吗，多几个提交能压垮它？这期就把这笔账拆开算——AI 代码洪峰压的到底是哪一层，钱烧在哪儿，普通开发者又该怎么自处。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/f6f070533ad20a29.png)

## 一、先把数字翻译成人话

- **平均每秒约 2800 次 push**：73.8 亿 ÷ 30 天 ≈ 每天 2.46 亿次；再除以 86400 秒，均值约每秒 2847 次。真实流量有早晚高峰，峰值估计是均值的 5~10 倍。
- **换算成人力**：一个勤快的工程师每月 push 大约 100 次，73.8 亿次相当于 7380 万个"全职人类"满负荷提交一整月。GitHub 全球开发者早已过亿，账面上对得上——但分布是长尾的，增量的大头显然不是人。
- **400 万核什么概念**：按单机 64 核算，相当于 6 万多台服务器同时上线，差不多凭空多出几座超大规模数据中心。而且不是一次性买断，是几个月里"边跑边换轮胎"式的紧急扩容。

## 二、Git 不怕提交多，怕的是"事件瀑布"

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/59a02efe572757b5.png)

Git 在 2005 年由 Linus Torvalds 为 Linux 内核设计：分布式、内容寻址（SHA-1 对象）、本地提交几乎零成本。它隐含的设计假设是——提交者是有耐心的人类，一天提交几次顶天了。这个假设在 2025 年正式失效。

真正扛不住的不是 `.git` 目录本身，Git 的 packfile 和对象去重机制其实很能装。贵的是 GitHub 在 Git 之上叠的那一整层平台服务：

1. push 触发 webhook，向下游系统广播事件；
2. 触发 GitHub Actions 流水线，一次 CI 动辄烧几分钟到几十分钟算力；
3. 更新 PR 状态、跑 status checks、代码扫描、依赖图、搜索索引；
4. 给 watcher 扇出通知、邮件和第三方集成。

关键区别在于：一次 push 在人手里是"事件"，在 agent 手里是"循环"。人修 bug 是改完→push→看结果；agent 修 bug 是生成→push→CI 失败→分析→再改→再 push，一个任务循环二三十轮稀松平常。所以算力消耗不是线性涨，而是"提交总数 × 单次提交的级联开销"一起涨。那 400 万核，大部分是在给 Actions、API、事件总线这些层补血，而不是给 Git 存储本身。

## 三、Agent 为什么这么能"生"

- **试错式开发**：LLM agent 的工作方式是"生成→验证→修正"的循环，每轮都留下提交痕迹。人类攒一周的活儿才 push 一次，agent 是想到就 push。
- **天然并行**：现在流行的多 agent 工作流，主 agent 派活，N 个子 agent 各开分支、各跑 CI。被并行的不是代码量，是"提交流"本身。
- **Jevons 悖论**：1865 年经济学家 Jevons 发现，蒸汽机效率越高、煤烧得越多。放到写代码上同理——生成成本趋近于零时，代码产量（包括用完即弃的脚手架、实验分支、一次性 demo 仓库）不是省下来，而是暴涨。
- **噪声再添一把火**：AI 生成的 SEO 仓库、刷星、低质量 PR，不产生价值，但照样消耗存储、索引和审核人力。

一句话总结：提交曾经是稀缺劳动的结晶，现在变成了免费弹药，数量自然奔着物理上限去。

## 四、成本账：谁在为"免费的提交"买单

- **对 agent 用户**：一个自动化任务摊下来几美元，几乎无感。
- **对平台**：每次提交背后是存储、网络、CI 分钟数、GC 重打包、事件队列的真实电费与折旧。提交免费、活动收费——很像自助餐厅的饮料，单杯看着不要钱，店长盯着的是你总共接了几升。
- **商业模式被倒逼重构**，大概率往三个方向走：
  1. agent 身份体系——让 agent 成为有独立鉴权和配额的"一等公民"账号，而不是蹭人类的凭证；
  2. 活动量分级计费——push、Actions 分钟、webhook 调用都可能进入计费维度；
  3. 平台侧自律——僵尸分支自动清理、事件去重，把各家 coding agent 统一接入管理（GitHub 的 Agent HQ 就是这个方向）。

400 万核不是终点。只要"生成代码的成本 < 提交代码的成本"这个不等式还成立，扩容就是一场追着跑的马拉松。

## 五、给普通开发者的三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/beb7e89a03e555d2.png)

1. **把 AI 输出当"初级工程师的 PR"对待**：review 标准不降级——分支保护、必须绿测、code owner 审批一个都不能省。AI 提高的是产量，不是免检资格。
2. **给 CI 装上闸门**：用 path filter 让无关目录不触发流水线；设 concurrency 上限，防止 agent 把 Actions 分钟数烧穿；善用缓存与增量测试。月底看一眼账单，比事后惊讶体面。
3. **仓库卫生定期做**：自动删除合并后的僵尸分支、定期 GC、收紧 fork 策略；开源维护者对来源不明的 PR，要求关联 issue 并说明生成方式。

最后一点冷思考：稀缺资源正在换位置——过去缺"写代码的手"，现在缺"review 代码的眼"。当提交历史混入大量机器痕迹，它作为知识档案的含金量在稀释；而工程判断力——决定写什么、不写什么、什么该扔——反而更值钱。洪峰不会退潮，学会在洪峰里游泳，是这一代工程师的基本功。
