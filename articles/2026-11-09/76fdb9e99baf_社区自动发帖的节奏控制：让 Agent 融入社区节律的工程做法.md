# 背景

用 OpenClaw 挂一个 Agent 加 MCP 工具做社区自动发帖，是很常见的实践：定时发周报摘要、新版本 changelog、聚合答疑。跑起来不难，难的是跑两周之后——固定 cron 每 30 分钟一条、凌晨三点准时出现、同一模板连发三帖，人类一眼看穿，反垃圾系统也一眼看穿。

这篇记录我们把内部几个发帖 Agent 的节奏调“自然”的过程，只讲工程手段，不涉及对抗平台的灰色技巧——目标只是让自动化内容别干扰社区。

# 问题

“不像机器人”拆开看是四个可测量的特征：

1. **时间规律**：发布时刻方差为零，或呈明显周期；
2. **频率规律**：间隔固定，或 burst 式连发；
3. **内容规律**：同模板、同长度、同句式；
4. **无反馈回路**：被删、被踩、没人理，下个周期照发不误。

# 做法

**1. 全局限额 + 抖动间隔。** 每天总量上限写进配置；单次间隔不是 `interval ± random(5)`，而是从对数正态分布采样，中心 45 分钟、偶尔拉到 2 小时。均匀随机本身也是一种特征。

**2. 活跃时段建模。** 拉目标频道历史消息的回复时间分布，按小时加权采样发布窗口；本地时间 1:00–7:30 设为静默区。注意时区：我们的 Agent 跑在 UTC 容器里，第一次上线差点全改成半夜发。

**3. 事件驱动优先于定时。** cron 只负责触发“检查聚合队列”，队列攒够阈值或超时 4 小时才真正发一条。没有值得发的内容就不发——节奏跟着社区走，而不是跟着时钟走。

**4. 内容侧去模板。** 标题句式、开头段、是否带代码块做成变量池，同一模板连续出现两次就强制换。长度方差比措辞更重要。

**5. 反馈回路与熔断。** 记录每条的删除率、回复率；连续 2 次失败或被删就指数退避，连续 5 次直接暂停转人工。发布动作统一带幂等 key，重试不会造成重复帖。

最小配置大概长这样：

```yaml
throttle:
  daily_max: 6
  jitter: lognormal(center=45m)
  quiet_hours: "01:00-07:30"
  burst_cooldown: 90m
  backoff: {fail_threshold: 2, pause_threshold: 5}
```

# 踩坑点

- 把间隔随机成“精确 47 分钟”这种伪随机，比固定值更可疑。分布形状比“加随机数”重要。
- 只随机时间不随机内容，三连发一个模板，前面全白搭。
- 聚合队列没做淘汰，服务重启后凌晨一次性补发 5 条积压，等于自爆。
- 重试逻辑没加幂等 key，同一条内容发了两遍。
- 静默窗口按服务器时区算，而社区在另一个时区。

# 可复用建议

- 把节奏控制做成发布前的统一 gate 模块（或在 MCP 层封装 `schedule_post` 代替裸 `post`），所有 Agent 共用，别散落在各脚本里。
- 所有阈值配置化，宁可保守起步，观察两周再放开。
- 留一条人工草稿通道：低置信内容先进草稿，人确认后才发。
- 每周抽看一次 bot 的发帖串，人眼比指标准。

# 总结

“不像机器人”不是玄学，而是让自动化服从社区自身的节律：事件驱动决定“发不发”，分布采样决定“什么时候发”，内容变量决定“长什么样”，反馈熔断决定“要不要停”。四层都做到，自动化内容就能安静地成为社区的一部分，而不是一个显眼的异常点。
