## 背景

用 OpenClaw 做日常自动化的痛点之一是调用频率：工具选择、文本总结、格式转换、例行分类，一天几百次请求。全走云 API，月底账单不好看，隐私上也别扭——很多任务其实不需要前沿模型的智力。于是我把一部分流量切到了本地模型，跑了一段时间，把过程和教训记录下来。

## 问题

硬件现实：我只有一块 RTX 3060 12GB。在这个前提下要解决三件事：选什么模型、agent 场景下 tool call 是否可靠、长上下文会不会把显存吃穿。

## 做法与步骤

**1. 选运行时。** 主力用 Ollama（省事，自带 OpenAI 兼容端点），调量化参数时换 llama.cpp 的 `llama-server`，可控性更强。

**2. 选模型。** 12GB 显存，主力定为 Qwen2.5-14B-Instruct Q4_K_M，权重约 9GB，给 KV cache 留余量；备用 7B Q4 处理轻活。实测 3060 上 14B 约 15–18 tok/s，7B 约 35 tok/s，agent 循环可接受。

**3. 接入 OpenClaw。** 配置自定义 provider，`base_url` 指向 `http://127.0.0.1:11434/v1`，api key 随便填。关键是分流：轻任务路由到本地，复杂规划和代码生成仍走云端，双模型并存。

**4. 压测再上岗。** 写了个脚本循环跑 50 次工具调用，记录 tokens/s、显存占用和解析失败率，确认达标后才把任务真正切过去。

## 踩坑点

- **KV cache 是隐形杀手。** 32k 上下文的 14B 模型，cache 还要再吃 3–4GB。`num_ctx` 别无脑拉满，按实际对话长度设 8k–16k。
- **小模型 tool call 不稳。** 7B 以下偶尔输出不合规 JSON，工具解析直接失败。解法：系统提示里强制 JSON schema，温度压到 0.1–0.2；关键流程一律用 14B。
- **agent 循环撑爆上下文。** 一次失败重试五六轮，历史不裁剪就 OOM。给 agent 加了历史压缩，超阈值就摘要截断。
- **冷启动延迟。** 模型首次加载 20–40 秒，`keep_alive` 设长一点，别让高频调用反复触发加载。
- **Embedding 单独跑。** 记忆/检索用独立的小 embedding 模型，别占主力模型的窗口和显存。

## 可复用建议

- **显存选型经验**：8GB→7B Q4；12GB→14B Q4；24GB→32B Q4 或 14B 高精度。权重之外务必留 20–30% 余量给 KV cache。
- **分流而不是全本地**：本地做总结、分类、格式转换、routine 工具调用；云端做复杂规划、长代码生成。目前混合路由的性价比最高。
- **监控先行**：`nvidia-smi` 循环记录 + tokens/s 日志，出问题先看曲线，再谈猜测。
- **结构化输出一律加 schema 约束**，不要相信小模型的自觉。

## 总结

本地 LLM 不是前沿模型的替代品，而是给自动化场景提供"调用量无限、数据不出门"的底座。12GB 级显卡跑 14B Q4，配合合理的任务分流，足够承接 OpenClaw 日常六成以上的调用。建议的路径是：先搭监控和压测，跑出真实数据，再决定要不要为本地推理升级硬件。
