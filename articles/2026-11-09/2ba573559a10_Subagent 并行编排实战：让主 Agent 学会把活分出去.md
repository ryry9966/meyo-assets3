## 背景

单 agent 干所有活的模式，任务一旦变大就会撞上两个很具体的瓶颈：一是上下文被工具输出撑爆——读几个大文件、翻一段日志，主会话里堆满中间产物，后面的推理质量明显下滑；二是串行执行慢，十个独立模块的重构只能一个一个排队。Subagent 编排解决的就是这两件事：**上下文隔离**和**并行执行**。

## 问题

举个常见场景：让 agent 批量整理一个多模块仓库。主 agent 串行处理每个模块，每个模块要读十几份文件，跑到第五个模块时，前面的约束已经开始"遗忘"，输出风格漂移；总耗时是所有子任务之和。这类任务的特征很明确——读取量大、写入量小、彼此独立——正适合拆给 subagent。

## 做法

1. **拆任务**。先判断独立性：子任务之间不写同一批文件、没有顺序依赖，才能并行。模块级重构、多目录巡检、批量生成文档都是典型候选。
2. **定契约**。给每个 subagent 的 prompt 固定三段：目标与边界（只处理哪个目录、不许动什么）、可用工具（按需裁剪，别全量继承）、返回格式（status + 变更文件列表 + 200 字以内摘要）。最后一条最关键：**禁止返回原始文件内容**，否则主上下文照样爆。
3. **控并发**。2–4 个起步。并发数上去之后，token 消耗和限流风险增长得比直觉快，别一上来开八个。
4. **收口写入**。要么把写操作统一收口到主 agent，要么按目录分区、每个 subagent 只写自己的地盘。原则一句话：**并行读、串行写**。

## 踩坑点

- **写冲突**：两个 subagent 同时改同一个文件，后写覆盖先写，且很难事后发现。分区或串行化，别赌运气。
- **返回值污染**：subagent 图省事把读到的内容原样贴回来，主上下文被二次撑爆。契约里写死输出上限。
- **权限扩散**：subagent 默认继承全部工具，既贵又危险。按子任务最小需要给。
- **静默失败**：子任务挂了但没上报，主 agent 拿着残缺结果继续合并。强制要求 status 字段，失败也要显式返回。
- **假并行**：看着独立、实际有隐含依赖（比如都依赖一次公共的重命名），并行完集体返工，比串行还慢。

## 可复用建议

- 先跑 2 个 subagent 的最小版本，量出耗时和 token 成本，再决定扩不扩。
- 每个 subagent 用独立 session，出问题能单独回放日志，不用翻主会话。
- spawn prompt 沉淀成模板，只参数化目标和边界，减少每次现编带来的不一致。
- 一个粗略判断标准：读多写少、彼此独立 → 并行；需要互相参考中间结果 → 老实串行。

## 总结

Subagent 编排不是"更多智能"，而是一个工程手段：隔离上下文、并行执行、控制爆炸半径。先把契约和写权限设计清楚，再谈并发数。做对的收益是稳定的——主会话干净、总耗时接近最慢的那个子任务、失败可定位；做错的代价也同样稳定：覆盖、返工、账单翻倍。
