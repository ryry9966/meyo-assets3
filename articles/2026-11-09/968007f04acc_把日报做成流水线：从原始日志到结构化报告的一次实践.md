## 背景

团队每天要发日报，数据散在几个地方：git 提交记录、CI 流水结果、告警日志、工单系统。之前是人工翻日志、复制粘贴、拼措辞，一个人每天稳定消耗 30–40 分钟，还经常漏掉风险项。后来我们用 OpenClaw 的定时任务加几个 MCP 工具，把它改造成了一条无人值守的流水线，稳定跑了一个多月，这篇记录一下做法和踩的坑。

## 问题

核心矛盾在于：**原始日志是半结构化文本，而日报需要的是可信的结构化叙述**。最常见的错误做法是把一整天的原始日志直接丢给 LLM“总结一下”——结果是 token 爆炸、要点遗漏，还会编造出根本不存在的工单号。数据结构化和文字组织必须分开处理，这是整条流水线的设计前提。

## 做法：五步流水线

1. **采集归一化**：定时任务触发，git 和工单系统通过现成的 MCP server 拉取，没有 server 的源用脚本落盘。所有输出统一转成一个中间 JSON schema：`{date, source, items: [{id, type, project, status, summary, ts}]}`。这个 schema 是全流水线的契约。
2. **聚合去重**：纯脚本处理，按 `id + project` 合并——同一条 commit 在 git 和 CI 里各出现一次的情况很常见，必须去重，再按项目分桶。
3. **生成层**：Agent 只拿聚合后的 JSON 和版本化的模板文件，输出限定为固定章节（进展/风险/明日计划），temperature 调低，并明确要求所有 id 只能从输入 JSON 原样复制。
4. **规则校验**：纯代码，不做语义判断——报告里出现的每个工单号必须存在于源 JSON；字数在区间内；必填章节齐全。校验不过重试一次，仍不过就降级为脚本直接拼装的原始版本。
5. **投递归档**：webhook 推送到群，同时按日期把 markdown 归档进仓库，幂等设计，同一天重跑是覆盖而非追加。

## 踩坑点

- **时区**：任务在 00:05 跑，日志时间戳却是 UTC，“昨天”的窗口第一天就算错，报告缺了半天的尾巴。统一在采集层转本地时区，窗口固定为 `[T-1 00:00, T 00:00)`。
- **幻觉 id**：LLM 会“补全”看似合理的编号，肉眼很难发现。改成强制复制 + 校验脚本比对后才根治。
- **静默失败**：流水线挂了比报告难看更糟，群里没人会意识到“今天没日报”是个故障。加了一个看门狗：报告未按时到达就单独告警。
- **单源降级**：某个源拉取超时不应阻塞整条流水线，标记 degraded 并在报告顶部注明“数据不完整”。
- **模板漂移**：有人本地手改 prompt 后输出格式慢慢变形。模板和 prompt 放仓库版本化，改动走 PR。

## 可复用建议

- **最值得坚持的一条：代码负责把世界变成 JSON，LLM 只负责把 JSON 变成人话。** 把不确定性关在生成层这个小盒子里，用规则兜底。
- 中间 schema 尽量稳定，来源可以随时增删替换，上游改动不冲击下游。
- 一切产物按日期做幂等键，可重跑、可回溯。
- 从单一来源先跑通全链路，再接新源，不要五路齐上。
- 给流水线本身做可观测：记录每次运行的耗时、各源条数、校验结果。这些数字反过来又能作为日报里的一小段“流水线健康”。

## 总结

日报自动化的价值不在 LLM 写得多流畅，而在上游数据先被可信地结构化。跑通之后，每天省下的半小时只是副产品，真正的收益是：报告口径一致、数据可验证、出问题能定位到具体环节。剩下的都是老老实实的工程活。
