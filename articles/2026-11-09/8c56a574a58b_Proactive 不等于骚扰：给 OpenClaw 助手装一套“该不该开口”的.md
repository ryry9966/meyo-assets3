## 背景

大多数助手的默认形态是 reactive：用户发消息 → agent 响应 → 结束。但很多有价值的事并不发生在“你问的那一刻”——CI 挂了、磁盘快满了、日历冲突了、订阅的仓库发了新版。这些事的共同点是：等你想起来去问，时机往往已经过了。

OpenClaw 这类常驻 agent 网关天然适合做 proactive：有心跳（cron heartbeat）、有 MCP 工具、有插件系统和消息通道。缺的不是触发能力，而是“什么时候该开口”的判断。

## 问题：naive proactive 的三种死法

直接给 agent 挂个定时任务，结果通常是：

1. **骚扰型**：每次心跳都推一条“一切正常”，三天后被静音。
2. **失控型**：agent 在后台自作主张改文件、发消息，用户从此不敢让它后台跑。
3. **成本型**：每 5 分钟唤醒一次完整 agent，token 账单先爆。

核心矛盾在于：proactive 的价值与推送频率呈倒 U 曲线。工程问题不是“能不能主动”，而是“门槛怎么设计”。

## 做法：触发 → 门槛 → 执行 → 投递，四层分开

我把它拆成四个独立插件，各自可测：

**1. 触发层（trigger）**：只负责产生信号。心跳 cron、webhook、文件 watcher 都算。信号统一写入待检队列，不直接唤醒 agent。

**2. 门槛层（gate）**：决定“要不要说话”。先用纯规则滤掉约 90% 的噪音：

- 静音时段（如 23:00–08:00）
- 最小间隔：同一 dedup key 4 小时内只推一次
- 每日推送上限

剩下模糊的再交给 LLM 判断相关性并输出分数。**规则在前、模型在后**，这是稳定性的关键。

**3. 执行层（act）**：过闸后组装最小上下文包（触发原因 + 相关工具结果），调用 MCP 工具完成动作。第一版只做只读操作 + 推送。

**4. 投递层（deliver）**：按话题路由到对应会话，带 silence key。用户回复“别推 X”就写入 mute 列表——反馈回路必须有。

一个跑了一个月的具体例子：每 30 分钟心跳检查三类信号（服务器磁盘、订阅仓库 release、明日日历冲突），命中规则才组装摘要推到 Telegram。实际日均推送 0.8 条，至今没被静音。

## 踩坑点

- **时区**：cron 默认 UTC，静音时段全体错位。心跳里显式传本地时区。
- **循环触发**：主动推送本身会进会话历史，下次心跳可能把它当新事件再推。给主动消息打标记，gate 里排除自己发的内容。
- **LLM 门槛抖动**：同一信号今天推明天不推。把判定结果和分数落盘，低分连续 N 次才升级为推送，做滞后（hysteresis）。
- **上下文断档**：心跳触发的 agent 没有对话上下文，容易重复问已回答的问题。维护一个小状态文件（最近推送、用户最近指令），每次心跳先读。

## 可复用建议

1. 第一版永远**只读 + 推送**；写文件、发邮件等动作一律 dry-run 或要求确认。
2. gate 每次决策都留日志：触发源、分数、结论。调阈值全靠这份日志，不靠感觉。
3. 把“日推上限”当硬预算写进配置，而不是靠自觉。
4. 用回复率评估：推送后用户有响应才算有效，回复率持续走低就该收窄话题了。

## 总结

proactive 不是“更聪明”，而是“更克制”。触发、判断、执行、投递四层解耦，规则做粗筛、模型做边界判断、日志做反馈闭环，助手才能在你开口之前把事办了——而不是让你想把它静音。先从一条心跳 + 三个只读信号开始，比一上来就全自主靠谱得多。
