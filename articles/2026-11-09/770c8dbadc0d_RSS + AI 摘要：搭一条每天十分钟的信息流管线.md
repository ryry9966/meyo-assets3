## 背景

订阅源越加越多，真正读完的比例越来越低。RSS 重新成为我主动获取信息的主要方式，但"订阅"和"消化"之间一直缺一环。OpenClaw 的定时任务、MCP 工具和 Agent 编排能力，正好可以把"抓取—过滤—摘要—推送"串成一条自动管线。我把关注的三四十个源收敛成一条日更摘要，跑了两三个月，这里记录设计和踩坑。

## 问题

- 全量阅读不现实，信噪比低，标题党占比高；
- 直接把整个 feed 丢给模型总结，成本高、输出无结构，值得深读的条目和灌水混在一起；
- 大量站点不提供全文 RSS，只基于标题摘要容易失真甚至误导。

## 做法：四层管线，逐层可替换

### 1. 抓取层
- 源选择"少而精"，先删后加；没有 RSS 的站点用 RSSHub 路由补齐，建议自建实例，公共实例限流严重。
- 无全文的条目抓原文链接，用 trafilatura / readability-lxml 抽正文；抽取失败降级为"仅标题+原始摘要字段"，不让脏数据进下一层。

### 2. 清洗与过滤层（管线质量的真正决定者）
- URL 归一化 + hash 去重入库，SQLite 足够；
- 标题相似度去重：同一事件多源报道只留一条，简单 shingle 重叠率即可，不必上 embedding；
- 规则过滤：关键词黑名单、来源权重、最小正文长度；
- 启发式打分排序，只有前 N 条送进模型。

### 3. 摘要层
- 廉价模型做初筛分类，强模型只处理高分条目；
- 结构化 JSON 输出：一句话结论 + 三个要点 + "为什么值得看"，下游渲染稳定；
- prompt 明确要求仅基于正文；正文过短直接跳过，宁缺毋滥。

### 4. 推送层
- 聚合成日报，webhook 推到 IM bot / 邮件，或生成 Markdown 提交到仓库；
- cron 触发加文件锁，防止重跑产生重复推送。

在 OpenClaw 里可以把抓取、去重封装成 MCP 工具，由 Agent 负责编排和失败重试；也可以全脚本化，Agent 只做每日总结。两种都成立，关键是层与层之间用落盘数据（SQLite/JSONL）衔接，方便回放和排查。

## 踩坑点

1. 公共 RSSHub 实例频繁限流，部分路由直接 5xx，自建后解决；
2. 编码坑：部分老源是 GBK，入库前统一转 UTF-8，否则摘要层读到乱码开始"自由发挥"；
3. token 成本：最初全量送模型，单日几千条直接爆，加打分门槛后成本降一个数量级；
4. 摘要同质化：prompt 太宽泛时所有条目摘要长得一样，结构化字段 + 强制"为什么值得看"能明显缓解；
5. 短正文幻觉：正文只有两句话的标题党条目，模型会脑补内容，最小长度门槛直接跳过；
6. 时区：cron 按服务器时区跑，日报一度下午才发，统一时区并固定触发时间。

## 可复用建议

- 先跑最小闭环：10 个源、每天一次、纯脚本 + 一次 LLM 调用，验证价值后再加层；
- 原始条目永久入库，prompt 随时可以重跑历史，迭代不心疼；
- 过滤逻辑保持确定性规则，不要把筛选也交给模型——不稳定且贵；
- 按 URL hash 缓存摘要结果，重跑只处理增量；
- 每层打日志和计数（抓取多少、去重掉多少、送模型多少），管线健康度一眼可见。

## 总结

这条管线最大的收益不是"AI 帮我读"，而是过滤层把信噪比提上来之后，摘要才有意义。RSS 解决获取，规则解决筛选，模型只做最后一步的信息压缩。把它当一条有质量门禁的数据管线来做，而不是"一键总结全网"的按钮。整套东西一个 SQLite、一个 cron、几百行脚本就能起步，OpenClaw 用户可以按需把任意一层替换为 MCP 工具或 Agent 节点。
