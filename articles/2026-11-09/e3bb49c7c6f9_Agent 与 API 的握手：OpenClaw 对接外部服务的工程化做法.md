## 背景

OpenClaw 本身并不"认识"任何外部服务，它认识的是工具。天气、日历、内部接口、自建数据库，对 Agent 来说都是一层被注册进来的工具描述，外加一个能实际执行的通道（skill 脚本、自定义插件或 MCP server）。所谓"握手"，就是把这份契约定义清楚：模型知道什么时候调、传什么参数，服务返回什么、失败时如何表达。

## 问题

最常见的翻车方式是"直接把 curl 甩给 Agent"。跑起来通常会遇到四类问题：

1. **认证没地方放**——写进 prompt 等于泄漏，写进命令行会进日志；
2. **返回体太大**——完整 JSON 直接灌进上下文，几轮对话后 token 爆炸；
3. **失败不可读**——HTTP 500 或一坨堆栈丢给模型，它要么反复重试，要么编造结果；
4. **写操作不设防**——对非幂等的 POST 重试一次，就是两条重复工单。

## 做法

我的模板是：每个外部服务配一个"薄适配层"，统一包含五件事。

**1. 选对接通道。** 只读、结构简单的用 skill 包一层脚本；需要标准协议或独立进程的用 MCP server；深度定制再写插件。别一上来就写插件，先跑通最小链路。

**2. 收窄参数 schema。** 工具描述里写清每个参数的含义、单位、可选值。宁可参数少而明确，不要一个大而全的 payload 让模型去猜。

**3. 凭证走环境变量。** 在 OpenClaw 的执行环境里读 env，token 用最小权限 scope，绝不内联进配置或 prompt。

**4. 裁剪返回体。** 适配层只挑业务需要的字段，长列表截断并在输出里注明"还有 N 条，可用 offset 继续"。分页逻辑收敛在工具里，不要让 Agent 自己循环翻页。

**5. 归一化错误与超时。** 设明确的 timeout（我一般 10–15s）；429/5xx 用指数退避重试，上限 2–3 次；最终把错误翻译成一句模型能理解的话，比如"服务限流，请 60 秒后再试"。写操作标记为非幂等，重试前必须过确认门槛。

## 踩坑点

- 工具描述含糊会导致模型"猜参数"，中文接口名配英文 schema 时尤其明显，描述里务必带调用示例；
- 日志打完整请求容易把 Authorization 带出去，只记 status、latency 和参数摘要；
- 中文参数记得 URL encode，否则带签名的接口校验必挂；
- 重试、分页这类控制流必须收敛在适配层，交给 Agent 自己处理一定会失控。

## 可复用建议

- 先只读后写入，写操作一律加确认；
- 用固定 fixture 离线调通工具层，再接真实 key；
- 所有外部调用落一条结构化日志，排障只看这一张表；
- 工具描述当代码维护：改接口必改描述，二者不同步是最隐蔽的 bug 来源。

## 总结

Agent 对接外部服务，本质上不是 prompt 问题，而是契约设计问题。模型负责决策，适配层负责把网络世界的混乱翻译成模型可读的、有限的、安全的输入输出。把超时、重试、裁剪、鉴权这些脏活从 Agent 手里拿走，这次握手才算真正握上。
