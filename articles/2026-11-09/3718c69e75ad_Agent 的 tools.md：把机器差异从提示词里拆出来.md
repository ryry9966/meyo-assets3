## 背景

跑 Agent 的常见场景：同一套提示词和配置，在 MacBook、Linux 开发机、公司内网机上各跑一遍，结果各不相同。Mac 上 agent 顺手 `brew install`，Linux 上没有 brew；脚本里写死 `/Users/xxx/...` 到服务器直接断；ffmpeg、jq、direnv 这类工具有的机器有、有的没有。根因很简单：agent 对环境的全部认知来自上下文，而上下文里没有一份可靠的环境事实。

## 问题

多数人的做法是把环境信息直接塞进系统提示词或项目级的 AGENTS.md。几个后果：

- 项目文件要提交进 git，机器私有信息（本机路径、代理、硬件限制）写进去污染协作者，不写 agent 就靠猜；
- 换一台机器就要改提示词，改完经常忘了同步，配置开始漂移；
- 提示词越堆越长，每轮会话的上下文成本都在涨，而其中大部分内容只对某一台机器有意义。

## 做法

核心思路是拆两层：**项目级指令**（提交、共享、与机器无关）+ **本机事实清单 tools.md**（不提交、可再生成、只描述"这台机器有什么"）。

1. **定模板。** tools.md 固定几节：OS 与 shell、包管理器及安装习惯、语言运行时（版本管理器路径）、常用 CLI 工具及绝对路径、目录约定（临时文件放哪、测试怎么跑）、硬约束（离线、走代理、不能 sudo）。MCP/插件用户可以加一节，列出本机已配置了哪些 server 和插件。
2. **让 agent 自己生成初稿。** 给它一段 bootstrap 指令：依次执行 `uname`、`which`、各工具 `--version` 等探测命令，把结果整理写进 tools.md。比自己手写快且准。
3. **主提示词里只留一句引用**："本机环境细节以 tools.md 为准，与文件冲突时先确认。"不要把内容复制过去，避免双份维护。
4. **gitignore 掉 tools.md**，另提交一份 `tools.md.example` 作模板。新机器上跑一遍 bootstrap 即可，不用迁移。

## 踩坑点

- **密钥别进 tools.md。** 它会被整个读进上下文，也可能被同步工具带走。只写环境变量名，值留给 shell。
- **文件会过时，而 agent 倾向于信任文件胜过现实。** 在文件头部注明生成时间和再生成命令，并要求 agent 使用关键工具前先 `which` 验证。
- **控制篇幅，100 行以内。** 它是每次会话都要付的常驻上下文成本，不是文档。细节宁可指向一条可执行的探测命令，也不要展开写。
- **与系统提示词重复必然漂移。** 一份事实只有一个来源：机器相关的只进 tools.md，团队相关的只进项目文件。

## 可复用建议

- 把 tools.md 当**缓存**而不是资产：丢了能秒级重建，就不会有过时带来的心理负担。
- 写一个十几行的 bootstrap 脚本放进 dotfiles，新机器一条命令出文件。
- 团队场景：共享一份"能力清单"（大家都有什么），个人差异放本机文件，code review 只看前者。
- 排查工具调用失败时，先对照 tools.md 那一节，很多"agent 不会用工具"其实是环境事实没写清。

## 总结

tools.md 的正确姿势不是"多写文档"，而是把机器差异收敛成一个小的、可再生的、与项目配置隔离的事实清单。拆层、最小化、密钥隔离、自动化生成——做到这四点，同一套 agent 配置就能在 N 台机器上稳定跑，而不是每台机器养一套方言提示词。
