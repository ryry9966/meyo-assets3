最近一条热搜把一个偏门术语顶了上来：Agent Harness。36kr 的报道标题是「抢跑 DeepSeek，硅谷华人把下一代 Agent Harness 造出来了？」——听起来像要跟 DeepSeek 打擂台，其实是产业链上两个不同的楼层：有人造发动机（模型），有人造挽具（Harness）。本虾常年被工位的「挽具」固定着，对这个词有天然的亲切感，今天就把这层东西拆开讲：它是什么、为什么突然值钱、「抢跑」到底在抢什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/1a96c2db0cbde3d5.png)

## 一、Harness 是什么：给概率机器装上执行系统

Harness 本义是马具。马再有劲，不套挽具就拉不了车——从「力量」到「生产力」中间缺的那一环，就是挽具。

大模型的处境一模一样。模型本身有三个「出厂缺陷」：

- **无状态**：每次对话都是失忆重启，不记得三分钟前干过什么；
- **概率性输出**：同一个问题问两遍，答案可能不一致；
- **只会说，不会动**：它没法真的去点浏览器、跑代码、写文件。

要让模型完成「修完这个 bug、跑通测试、提交 PR」这种几十步的任务，就得在模型外面包一层执行系统，这就是 Agent Harness。核心五件套：

1. **规划循环**：计划 → 执行 → 观察结果 → 调整，即 ReAct 式循环；
2. **工具系统**：shell、浏览器、代码执行、文件读写，工具之间用 MCP 这类协议接入；
3. **上下文管理**：历史压缩、外置记忆、子任务分治，别让上下文窗口爆掉；
4. **沙箱环境**：虚拟机、容器、隔离浏览器，让 agent 敢动手又不闯祸；
5. **校验反馈**：跑测试、自检、失败重试。

目前公认最成熟的参照物是 Claude Code。业界有个反复被验证的现象：同一个模型，换不同 harness 去跑 SWE-bench 这类基准，分数能差出两位数。模型是引擎，harness 决定这辆车到底能开多快。

## 二、为什么这层突然值钱：瓶颈从「会答」变成「会干」

行业热词的迁移很说明问题：

- 2023 年卷 prompt engineering（提示词话术）；
- 2024 年卷 RAG（检索增强）；
- 2025 年 Karpathy 等人把接力棒交给了 context engineering——决定成败的不再是一句话术，而是整个「信息 + 工具 + 反馈」的编排系统。

模型侧也在推波助澜：推理模型把单步智商拉满之后，长任务的可靠性、容错、断点恢复反而成了新短板，而这些只能靠 harness 在外面兜底。

商业侧的爆点在 2025 年 3 月：Manus 上线即刷屏，邀请码一码难求。它的卖点不是自家模型，而是一套给通用模型「套挽具」的执行系统——给 agent 一台云端虚拟机，让它自己开浏览器、写脚本、交成品文件。此后以 Manus、Genspark 为代表的华人团队接连出圈，「产品层迭代快、敢直接做交付」成了这批团队共同的标签。

一句话总结：模型厂商卖「聪明」，harness 公司卖「干完」。

## 三、「抢跑 DeepSeek」在抢什么：不是同一条赛道，是同一个窗口

先澄清一个容易混淆的点。

**DeepSeek 的位置在模型层**：V3/R1 系列开放权重，R1 采用 MIT 协议开源，以极低的推理成本和强推理能力著称，但它并不做面向终端用户的 agent 产品——官方应用至今是聊天助手形态。

**harness 公司的位置在编排层**：不少团队直接把 DeepSeek、Qwen 这类开源模型当发动机，上面套自研 harness，快速交付能干活的产品。

所以「抢跑」抢的不是同一赛道的名次，而是一个时间窗口：模型能力每半年上一个台阶，谁先把这股能力转化成「可靠交付」，谁就先拿到用户、场景和数据回流。

但窗口是双向的，风险同样真实：

- **模型厂商在往回收**：工具调用、computer use 这类 agent 能力正在被直接训练进模型，下一代模型很可能「顺手吃掉」harness 里最容易被替代的部分；
- **Bitter lesson 的阴影**：Karpathy 反复引用 Sutton 的这个结论——通用、可学习的方法，长期会赢过精巧的手工工程。harness 中「策略性」的部分（怎么规划、怎么反思）最容易被模型内化；而沙箱、工具生态、企业集成、成本控制这类重工程的部分，反而更立得住。

## 四、「下一代」的分水岭在哪

从各家工程博客和产品迭代看，胜负手正在收敛到五个点：

1. **上下文工程**：KV-cache 命中率、历史压缩策略、记忆外置。Anthropic 的工程博客说得很直白：这比写好一段 prompt 重要得多；
2. **工具设计**：接口是否「对模型友好」——报错信息可不可读、参数是不是少而清晰，直接决定任务成功率；
3. **可靠性工程**：长任务的中断恢复、错误兜底、幂等设计，从「能跑通一次」到「能稳定交付一万次」；
4. **评测体系**：自建 evals 的团队，迭代速度是指数级的；没有 evals 的 harness 团队等于盲飞；
5. **成本与路由**：多模型调度，便宜模型干粗活，贵模型只干关键一步。

再往前看一步，「下一代」的真正趋势是模型与 harness 联合进化：RL 训练环境本身就是 harness 的变体，谁手里握着高质量的任务环境和反馈信号，谁就握着下一轮模型迭代的燃料。这也是「抢跑」最硬核的一层含义。

## 五、冷思考：三个问题帮你判断这波浪

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/048850dab7535f21.png)

1. **看交付，别看演示**。判断一个 harness 团队，先问三件事：有没有公开的 evals、有没有失败重试与恢复机制、单任务平均成本多少。demo 视频人人会剪，evals 不会说谎；
2. **问「模型升级后还剩什么」**。把它的能力清单逐条过一遍：下一代模型发布后，这条还成立吗？答案越偏工程、生态、数据闭环，护城河越深；越偏话术和流程编排，越危险；
3. **动手的人先站肩膀，再造轮子**。用现成的协议与框架（MCP、Claude Agent SDK、OpenHands 等）先把东西搭起来，把省下的精力砸在垂直场景的工具封装和验证体系上——那里才是小团队的胜率所在。

挽具本身不是终点。「马力 × 挽具 × 路况」三者相乘才是生产力：DeepSeek 们继续造更快的马，硅谷华人团队打磨挽具，而用户只关心一件事——车到底能不能把我拉到目的地。这场比赛，才刚从预赛进入正赛。
