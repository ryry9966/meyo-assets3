## 背景

OpenClaw 是长跑型 agent，memory 目录跑几个月下来就是几百条笔记：MEMORY.md、daily notes、会话摘录。agent 靠 `memory_recall` 工具找回上下文，检索质量直接决定"它到底记不记得住"。配置里检索方式可以在全文检索（FTS）和语义检索（embedding 向量）之间选，社区里经常争论哪个更好。我们两种都用了一段时间，记录一下实际体验。

## 问题

两边各有翻车现场：

- **全文检索**：精确匹配强，查命令行参数、错误码、文件路径一查一个准；但换个说法就空手而归——笔记里写的是"上线卡住"，查询是"部署超时"，FTS 查不到。
- **语义检索**：口语化查询召回好，但"短查询 + 短笔记"场景下经常返回语义相近、事实无关的条目。查某个配置键名，返回一堆泛泛的架构笔记，agent 拿去当事实用就出事了。

结论先放前面：**单选任何一个都不够，混合检索才是默认答案**。下面是落地做法。

## 做法

1. **先盘数据。** 我们的记忆里七成是短条目、带稳定关键词（命令、路径、报错码），FTS 命中率高；三成是叙述型摘录，语义更稳。
2. **基座用 SQLite FTS5（BM25 排序）**，保证精确词必中；再挂一路 embedding（本地小模型或 API 均可），两路各取 top 8。
3. **用 RRF（倒数排名融合）合并两路结果**，最终取 top 3~5 塞进上下文。别搞复杂加权打分，RRF 一行公式够用。
4. `memory_recall` 参数保留 `mode: auto | fts | vector`，让 agent 在明显是精确查询（路径、命令）时显式走 FTS。
5. **建一个 20~30 条真实查询的小评测集**，每次改配置跑一遍、人工标 hit@3。十分钟的事，比拍脑袋强。

配置示意（简化）：

```toml
[memory]
backend = "sqlite"
retrieval = "hybrid"
fts_tokenizer = "trigram"     # 中文必须
vector_model = "bge-small-zh"
top_k = 5
fuse = "rrf"
```

## 踩坑点

- **FTS5 默认分词器对中文基本不可用。** unicode61 会把整句当一个 token，必须换 trigram 或接 jieba，否则中文全文检索等于摆设。
- **余弦阈值别乱设。** 0.75 以上常见查询全漏；不设阈值则噪声条目稀释 top-k。经验值 0.55~0.65 起步再调。
- **索引滞后。** 记忆刚写入还没进索引，agent 当场 recall 不到。在写路径上挂增量索引 hook（OpenClaw 插件或 MCP 工具都能做）。
- **重复与过期记忆互相稀释。** 定期合并同主题条目，检索前先按时间过滤（比如"最近 30 天"）。
- **query 别只用原文。** 把当前会话近两轮拼进查询再送向量检索，召回明显变准。

## 可复用建议

- 混合检索 + RRF 作为默认，不要二选一。
- 记忆条目原子化：一条一个事实，行首放稳定关键词——两种检索都受益。
- 精确查询（路径、命令、错误码）显式走 FTS，别交给向量。
- 评测集先行，改动前跑一遍，避免"感觉上更好"。

## 总结

语义和全文不是对手，而是分工：FTS 管精确事实，向量管说法变换，RRF 把两者缝起来。真正的大头收益其实在数据侧——记忆写得干净、带关键词、去重及时，比换任何检索算法都管用。顺序建议：先上混合，再做记忆卫生，最后才谈调参。
