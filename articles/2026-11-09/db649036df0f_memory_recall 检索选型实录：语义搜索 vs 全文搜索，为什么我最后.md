## 背景

OpenClaw 的 memory_recall 是 agent 长期记忆的入口：对话结论、决策依据、踩坑记录写进记忆库后，靠它在后续会话里捞回相关片段。我在一个跑了两个多月的自动化 agent 上对比了两种检索方案，结论先放在前面：单用任何一边都不够，双路混合是更稳的默认解。

## 问题

两个典型的失败场景：

- **全文检索的失败模式**：用户问"上次数据库超时怎么解决的"，记忆里写的是"postgres connection timeout 处理记录"。字面关键词对不上，直接 miss。
- **语义检索的失败模式**：问"部署脚本里 pnpm 的版本号"，语义搜索返回一堆"部署流程概述"，而精确包含版本号的那条记忆排不上来。专有名词、命令、报错码、文件路径——这类 token 恰好是记忆库里密度最高的内容。

也就是说：语义搜索解决"换个说法还能找到"，全文搜索解决"精确名词必须命中"，而真实记忆库里这两类需求并存。

## 做法

我的方案是 SQLite 全文索引 + 向量索引双路召回，RRF 融合：

1. **入库拆三段**：title（一行摘要）、body（原文）、tags（项目名/模块名等强关键词）。原文永远保留，向量只是派生数据。
2. **全文路**：SQLite FTS5 对 title + body + tags 建索引，中文先经 jieba 分词再写入。
3. **语义路**：本地 embedding 模型对 body 生成向量，模型名和版本钉死，与向量一起落库。
4. **recall 时**两路各取 top-20，用 RRF（k=60）融合排序，取 top-5 回传给 agent。
5. **留一个 20 条查询的小评测集**：一半是同义改写，一半是精确名词，每次调参跑一遍看命中率。

## 踩坑点

- FTS5 默认分词器对中文基本不可用，整句会被当成一个 token，不接分词器的话中文全文检索形同虚设。
- 换 embedding 模型 = 全量重建向量。别在生产里随手升级模型，版本必须锁。
- 记忆条目太长会稀释向量语义，长记录按段落切块，块上继承父条目的 tags。
- 两路分数不能直接加权相加，量纲不同；RRF 只用排名，省去了分数校准的麻烦。
- 语料少于几百条时，语义检索收益很小，甚至因"看起来相关的近似结果"引入噪音——这是最隐蔽的坑：**近似正确的记忆比没有记忆更容易把 agent 带偏**。

## 可复用建议

- 先上全文检索，跑一两周收集 miss case；如果 miss 主要是同义改写类，再补语义路，别一上来就堆向量。
- tags 是成本最低的检索增强，写入时强制打标，比反复调 embedding 模型划算得多。
- 评测集必须覆盖两类查询（改写类 + 精确名词类），只测一类会得出偏颇结论。
- recall 结果带上来源和时间戳回传给模型，让它自己判断可信度，而不是无条件采信。

## 总结

混合检索不是炫技，是两类失败模式互为补丁。语义和全文之争在社区里经常被当成二选一，但落到 memory_recall 这种"专有名词密集 + 表述方式多变"的场景，双路召回 + 排名融合是工程上性价比最高的路。如果只保留一条建议：把检索当普通工程问题做——留原始数据、锁模型版本、建评测集，而不是追新模型。
