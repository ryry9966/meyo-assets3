## 背景

日常开发里 Git 操作占了相当比例的重复劳动：写 commit message、按规范切分支、清理陈旧分支、补 PR 描述。这些事不难，但琐碎、易漏、风格难统一。有了 OpenClaw 这类常驻 agent，再配上 MCP 的 Git 工具，让助手直接读写仓库已经完全可行——真正的难点不在能不能做，而在边界怎么划。

## 问题

在我们团队接入前的典型痛点：

- commit message 全靠当场发挥，回看历史基本无法检索；
- 分支命名随意，feature、hotfix、实验分支混在一起，几个月后没人敢删；
- agent 一旦拿到 shell 权限，最先闯祸的往往就是 Git：`reset --hard`、force push、直接提交到 main，都属于"一句指令就丢工作"的操作。

## 做法

按四层拆，每层只解决一个问题：

**1. 工具层。** 优先用 MCP Git server，而不是裸 shell。读操作（status、diff、log、branch -a）默认放开，写操作（commit、push、branch -D、reset）逐项授权。这是整个方案可控的前提。

**2. 约定层。** 把 commit 规范（我们用 Conventional Commits）、分支命名模板写进仓库里的一个约定文件，agent 每次操作前先读它。约定进配置文件，不堆在系统提示词里——前者随仓库走、可 review、可版本化。

**3. 流程层。**
- 提交：强制 agent 先跑 `git diff` 和 `git log` 建立上下文，再生成 message，输出给用户确认后才执行 commit。禁止跳过确认直接 push。
- 分支：开工时按模板生成分支名；收尾时对已合并分支只输出报废清单，删不删由人决定。
- PR：diff 过大时分文件分段摘要，最后汇总成描述，避免一次性塞爆上下文。

**4. 审计层。** agent 每次写操作落一条日志（时间、命令、结果），用任务记录或轻量脚本都行，出问题能回放。

## 踩坑点

- **交互式命令跑不了。** `git rebase -i`、`git add -p` 在非交互环境会直接卡死或失败，要么换非交互等价参数，要么在约定文件里明确告诉 agent 别碰。
- **签名环境不一致。** GPG/SSH commit 签名在 agent 的执行环境里经常失败，表现为 commit 莫名报错。先在 agent 环境里手动签一次，确认配置再放手。
- **大 diff 反而降质。** 上下文被撑满后生成的 message 明显变水。按文件或 hunk 分批总结，再汇总。
- **权限白名单要列全。** 只封 force push 不够，`reset --hard`、`clean`、`checkout -- <file>` 都能静默丢内容，漏一个就是事故。
- **凭据别进 prompt。** 走系统 credential helper，不要把 token 写在配置或对话里。

## 可复用建议

1. 默认只读，写操作逐项授权，这是底线不是优化项。
2. 约定写成仓库内的文件让 agent 读，别全塞提示词。
3. push 和一切删除类操作永远留人工确认。
4. 从低风险场景切入：先只做 commit message 起草和每周分支报告，跑稳两周再逐步放开。

## 总结

Git 自动化的价值不在"全自动"，而在把风格统一、高度重复的部分交给 agent，把不可逆的决策留给人。工具权限收敛、约定进配置、操作留痕迹——这三件事做齐，这套流程就能长期稳定地跑下去，而且换一个仓库、换一个 agent 都能直接复用。
