## 背景

Agent 用得深了，配置就是资产。一个跑顺了的 workspace 里，通常有 system prompt、MCP 工具配置、memory 摘要、自动化脚本——这些加起来等于你的工作方法本身。社区里互相分享插件、skill 包、排障日志很正常，但"分享"和"泄露"之间，往往只隔一层没做脱敏的导出。

## 问题

实际见过三类泄露路径：

1. **配置导出带毒**：打包分享插件时，env 变量、内网 endpoint、真实 token 跟着一起进压缩包。
2. **日志即答案**：排障时直接把 session dump 贴进社区，里面除了报错栈，还有 agent 读过的内部文档片段、文件路径、API 返回原文。
3. **自动化回帖**：让 agent 自动整理"本周工作流总结"发到社区频道。它做摘要时不会替你判断哪些是内部信息——它没有这个概念，除非你显式给。

工作流泄露的后果不只是丢 key：内部命名规范、参数组合、工具编排方式被别人拿到，等于把排障经验和权限拓扑一起送出去。

## 做法

按一条"分享前流水线"来做：

1. **分级**：先把 workspace 里的东西分三类——公开（结构、思路、脱敏示例）、内部（工作流参数、prompt 全文）、机密（key、内网地址、客户数据）。分享只允许第一类。
2. **最小权限挂载**：给"社区场景"单独建一个 agent 实例，只挂只读、无敏感 scope 的 MCP 工具，memory 目录与主工作区隔离。别用日常干活的那只 agent 去发社区内容。
3. **导出即扫描**：写个十几行的脚本，对待分享目录跑正则——`sk-`、`Bearer`、内网 IP 段、内部域名特征、`.pem`、`.env`——命中即拦截。跑在打包之前，不靠肉眼。
4. **日志手工摘录**：社区求助只贴最小复现：报错栈加一行配置结构，永远不发原始 transcript。需要上下文就自己转述。
5. **自动化加人工 gate**：agent 自动发帖的流程里，在发布动作前插一个 diff 审查步骤，人确认后才推出去。

## 踩坑点

- **删了 `.env` 不等于干净**：memory 摘要、cache、agent 自己写的 README 示例里经常还留着真实值。扫描要覆盖整个导出目录，包括隐藏文件。
- **占位符陷阱**：配置里写着 `YOUR_API_KEY`，但 git 历史或旧版压缩包里是生效的 key。轮换比删除靠谱。
- **打包工具默认带 cache**：很多打包习惯会把 `__pycache__`、`.openclaw/cache` 一起压进去，里面是运行时数据。
- **prompt 本身是资产**：有人觉得"prompt 不算秘密"，但你的 prompt 里往往编入了内部工具名、团队术语、审批链。分享思路可以，分享全文要过一遍脑子。

## 可复用建议

- 固化一份 pre-share checklist：分级确认 → 全目录扫描 → 隐藏文件检查 → git 历史确认 → 打包后复查压缩包内容。
- 社区分享模板化：只贴结构不贴值——JSON 字段名可以留，值全部换成无害占位符。
- 出现在任何导出文件里的 key，一律视为已泄露，直接轮换，不要赌。
- 每季度做一次 workspace 审计：看看 memory 和日志里积累了多少"当时的内部信息"。

## 总结

Agent 安全红线的本质是一句话：**默认你导出的一切都会被看到**。分级、隔离、扫描、人工 gate，四步不重，固化成流程后每次分享多花两分钟。工作流是你自己的复利资产，泄露一次，补不回来。
