## 背景

跑 Agent 自动化迟早会遇到同一幕：任务跑到一半，某个 MCP 工具背后的外部 API 开始超时或返回 5xx，接下来要么整条流程卡死，要么更糟——模型拿到一个空结果，一本正经地编了个答案继续往下走。依赖越多，故障越必然。问题不是"会不会挂"，而是挂了之后 Agent 的行为是否可控。

## 问题：故障不是一个东西

排障时至少要区分四类：

- **瞬时故障**：超时、偶发 5xx，重试大概率能过；
- **限流**：429 带 Retry-After，硬重试只会更糟；
- **认证失效**：401/403，重试无意义，得刷新凭据；
- **持续性宕机**：重试到天荒地老也没用。

裸的 Agent 看到的往往只是一段报错文本或空返回，它无法区分这些情况，默认行为就两种：盲目重试，或者编造结果。恢复机制的目标就是把这两条路都堵死。

## 做法：四层防线

**1. 统一错误契约。** 工具调用不返回裸异常，收敛成结构化结果，让模型能读懂"发生了什么、该怎么办"：

```json
{ "ok": false, "error_code": "UPSTREAM_TIMEOUT", "retryable": true, "retry_after_ms": 3000 }
```

`retryable` 字段很关键：模型看到 false 就不该死磕，应转向降级或上报。

**2. 重试放代码里，不放 prompt 里。** 指数退避加抖动、尊重 Retry-After、设尝试上限，全部由工具执行层实现。让模型自己决定"再试几次"几乎必然失控——它没有时钟概念，还烧 token。同时给每次任务设时间与费用预算，超了就停。

**3. 降级与断路器。** 每个外部依赖配断路器：连续失败 N 次进入熔断，冷却后半开探测恢复。只读工具做本地缓存并标注数据新鲜度（"这是 2 小时前的缓存"）；关键工具准备备用实现，schema 差异在适配层抹平。

**4. 任务可续跑。** 多步任务做检查点持久化，故障中断后从断点恢复而非从头再来。所有写操作带幂等键，避免重试导致重复下单、重复发消息这类比宕机更尴尬的二次事故。

## 踩坑点

- **空字符串是幻觉之源。** 工具失败返回 `""`，模型大概率脑补数据。宁可显式报错，不要静默。
- **不区分 401 和 500。** 前者是凭据问题，退避重试到额度烧完也治不好，却是最常见的写法。
- **幂等键缺失。** 重试读操作没事，重试写操作没有幂等保障，恢复机制本身就成了事故来源。
- **降级链没测过。** 备用 API 平时不用，真用的时候 schema 对不上、字段缺失，等于没降级。定期演练里真的切一次。
- **熔断器没有半开状态。** 只熔断不探测，上游恢复后服务仍被长期打成"挂了"。

## 可复用建议

- 给所有工具套一层统一 runner：超时、重试、限流、断路、日志全在这里做，模型只接触干净结果；
- 错误契约（error_code + retryable）做成团队约定，新插件直接继承；
- 读多写少的工具上缓存，写操作必须幂等；
- 关键流程支持断点续跑；
- 无法自动恢复时，宁可挂起任务并清楚告诉用户卡在哪，也不要输出似是而非的结论。

## 总结

Agent 的错误恢复，本质是"机制放代码、策略放模型"的分工：重试、熔断、幂等、持久化是纯工程问题，别指望 prompt 解决；模型擅长的是拿到结构化错误后选择降级路径、向用户解释现状。这两层分开做，外部 API 挂掉就不再是事故，而是一次可预期的降级。
