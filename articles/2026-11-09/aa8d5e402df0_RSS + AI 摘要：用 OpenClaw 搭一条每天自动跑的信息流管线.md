## 背景

订阅源越攒越多，真正读完的比例越来越低。RSS 的好处是协议简单、完全可控，但原始 feed 噪音大：全文、摘要、更新、重复混在一起。我的目标很具体：每天早上收到一份结构化摘要，每个源几条一句话概括，想细看再点原文。整条管线由 OpenClaw 的定时任务（cron）驱动，LLM 只负责压缩，抓取和去重都交给确定性脚本。

## 问题拆解

- 抓取必须确定性、可重跑，不能依赖模型行为
- 去重要有持久状态，重跑不能重复推送
- LLM 输入要可控：条目数和 token 上限硬性截断
- 推送复用 OpenClaw 已配置的 channel，不额外造轮子

## 做法

**1. 源清单与状态分离**

用一个 YAML 维护订阅源，每条含 url、分类、是否抓全文。去重状态存 `state.json`，按源记录已处理的 entry id（优先 guid，退化用 link）。脚本本身无状态可重跑，状态文件可备份。

**2. 抓取脚本只做三件事**

Python + feedparser：拉 feed → 过滤已处理 id → 抽正文（摘要型 feed 用 readability 抓原文兜底）→ 写入 `pending/` 目录，每源一个 JSON。单源超过 20 条只留最新，防止任务膨胀。

**3. OpenClaw 定时任务串联**

cron 每天 7:30 触发：先执行抓取脚本，再把 `pending/` 内容作为上下文交给 agent，要求输出固定格式的 markdown——按源分组、每条一句话 + 原文链接、末尾三行“今日重点”。摘要任务用便宜的模型档位即可。也可以把抓取包成 MCP tool 让 agent 按需调用，但定时批量场景直接跑脚本更省事。

**4. 推送与归档**

摘要写进 `digests/日期.md`，同时通过 channel 推到群。归档文件顺便是可检索的历史语料。

## 踩坑点

- **guid 不可靠**：个别源的 guid 会变，导致重复推送。改用 guid + link 双键去重，再对标题做一次 hash 兜底。
- **只给标题就让它摘要**：摘要型 feed 信息太少，模型会硬编。要么抓原文，要么在 prompt 里写死“信息不足时输出标题级摘要，不要扩写”，否则幻觉稳定出现。
- **编码与日期**：不少老源是 GBK，写文件要显式 utf-8；部分源 pubDate 格式怪异，别信它，用抓取时间排序即可。
- **单源失败拖垮全流程**：一个 404 曾中断整次任务。逐源 try/except，失败记日志下次重试，连续失败 3 次自动禁用并通知。
- **token 截断要在进 prompt 之前做**：按条目截断，比靠模型上下文硬扛便宜且稳定得多。

## 可复用建议

- 抓取与摘要分层：确定性的归脚本，模糊的归模型，边界划清管线才可调试。
- 状态文件按源分 key，带上 `last_run` 和 `fail_count`，排障一眼定位。
- prompt 里放 2-3 个 few-shot 样例，输出格式稳定性明显提升。
- 先灰度一周“只写文件不推送”，确认格式和信源质量后再接 channel。

## 总结

整套代码不到 200 行，核心价值是把 RSS 的可控性和 LLM 的压缩能力用一个薄薄的调度层连起来。跑下来每天推送成本可以忽略，信息漏不掉、重复推不了，坏源能自愈。后续可以加关键词打分做粗排序，但目前“按源分组 + 一句话概括”已覆盖八成需求，先不过度设计。
