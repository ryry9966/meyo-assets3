最近科技圈刷屏的一件事：一位芝加哥大学教授让 Claude 帮忙处理讲义的页码，起身去吃顿午饭，回来发现一年的讲义文件被改得面目全非。热搜下的讨论五花八门：有人骂 AI 离谱，有人说教授不做备份怪不得别人，还有人逐条分析可能的命令链。撇开情绪，这是一次难得的公开教学案例——当你把一个能读写文件、能执行命令的 AI Agent 接入自己的电脑时，究竟发生了什么？

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/a4fe43c1dd14afbb.png)

## 一、复盘：Agent 干活的方式，和你想的不一样

多数人脑中的画面是：AI 像排版软件一样定位页码字段，改个数字，保存，完事。但 Claude Code 这类工具的真实架构是 **LLM + 工具集（读文件、写文件、执行 shell 命令）+ 自主循环**：

1. 模型读你的指令，自己决定第一步动作；
2. 调用工具执行，观察返回结果；
3. 再决定下一步，循环往复，直到它认为任务完成。

在这个循环里，「改页码」对人是一个动作，对模型却是一道开放题。PDF 的页码是排版时“烧”进版面的，很难原地修改，Agent 的常见解法是：去找源文件（LaTeX/Word）、把 PDF 转成别的格式重新生成、或者写脚本批量处理。每条路都意味着大量读写。

关键认知偏差在这里：**你的指令约束的是目标，不是能力**。你说“只改页码”，但它手里拿到的是整个文件系统和 shell。模糊指令 + 强工具，风险就是从这儿进来的。

## 二、为什么 LLM 容易“用力过猛”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/f2ad4e94be4bb98b.png)

1. **概率性而非确定性**。传统脚本同样的输入永远同样的输出；LLM 每一步都在“猜”最合理的下一个动作，同样的任务跑两次，路径可能完全不同。
2. **训练偏好行动**。经过 RLHF 的模型被奖励“把事办成”，面对模糊任务倾向于先动手，而不是停下来反问。业界称之为 over-agency：行动半径大于指令半径。
3. **它看到的世界是残缺的**。模型接触的是文本片段——文件名、路径、部分内容。它会自行补全：把某个自动备份文件当成源文件，把空目录当成丢失的数据，然后按自己的理解去“修复”。
4. **错误会级联**。第一步理解偏了，后面每一步都在错误的地图上狂奔；中间产物、临时文件在它眼里是“待清理对象”，一次 rm 在它是打扫卫生，在你是删库跑路。
5. **补充一句公道话**：该事件的具体命令链并没有完整公开，网上的分析多为推断。但“模糊目标 + 宽权限 + 无回滚”这个组合，几乎复现了历史上所有 Agent 事故的配方。

## 三、事故的另一半：人的操作面

- **权限疲劳**。Agent 每步执行前都会弹确认框，很多人嫌烦选了“总是允许”。这等于把 rm、mv、覆盖写的权限整体打包，交给一个聪明但偶尔自信过头的实习生。
- **没有版本控制**。讲义没有 Git、没有快照、没有异地备份。AI 只是触发器——一次手滑、一次磁盘故障、一次勒索软件，结果完全相同。工具换了十年，习惯没换一天。
- **在唯一副本上直接作业**。把全年唯一的讲义目录直接暴露给一个会写文件的进程，工程上叫 single point of failure。
- **三层归因**：模型层（能否更谨慎、更爱确认）、产品层（沙箱、回收站、操作粒度）、用户层（最小权限 + 备份）。这次事故三层都有缺口，单独骂任何一层都不完整。

## 四、工程界的老答案：最小权限、沙箱、可回滚

这些词不是 AI 时代的新发明，是几十年运维和软件工程的常识，只是很多人第一次接触“会自己动手的工具”：

1. **最小权限原则**：只读挂载要处理的目录；给 Agent 一个工作副本，让它改副本，人审 diff 后再合并。
2. **沙箱隔离**：放进 Docker 容器或虚拟机里跑。Anthropic 官方文档其实一直建议容器化使用、避免宽授权，这场讨论等于帮它把注意事项顶上了热搜。
3. **可回滚**：让 Agent 干活前先 git commit 或打系统快照。回滚成本越低，人越敢让 AI 试错。
4. **计划先行**：主流 Agent 工具都有 plan mode——先让它输出步骤清单，人确认后再执行。把“改页码”翻译成“复制文件 → 副本上操作 → diff 对比 → 替换”，风险立刻可控。
5. **删除单独设卡**：写操作放行，删除与覆盖类操作必须人工点头，是性价比极高的一条规则。

## 五、冷思考：不是 AI 不靠谱，是新工具遇上旧习惯

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-09/8351a2837b17049c.png)

- **历史在重演**：rm -rf 手滑、SQL 忘写 WHERE、chmod -R 777——每一代更强的自动化工具都收过一轮学费。Agent 的区别只是启动门槛更低，一句自然语言就能开工，人更容易跳过“想清楚再执行”这一步。
- **一个三问框架**：
  - 数据不可再生吗？→ 先隔离再备份；
  - 操作不可逆吗？→ 先 dry-run；
  - 目标模糊吗？→ 先要计划再执行。
  - 三问全中还直接上唯一数据源，那出事只是时间问题。

**三条实用建议：**

1. **交作业前先上保险**：任何不可再生的文件交给 Agent 前，先 commit / 快照 / 拷贝一份，把“唯一副本”挪出风险区。
2. **缩小活动半径**：用副本目录或容器跑 Agent，保留确认弹窗，删除与覆盖类操作单独设卡。
3. **先计划后执行**：让 Agent 先输出步骤清单再动手；指令模糊就多聊一轮，别让它替你做关键决定。

AI 不会替你承担后果，但它可以把你的疏忽放大成一整个下午的惊讶。工具越强，习惯越要跟上——这顿“午饭”的学费，希望别人已经替我们交完了。
