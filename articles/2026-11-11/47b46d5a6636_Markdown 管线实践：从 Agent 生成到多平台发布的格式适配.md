## 背景

在 OpenClaw 的自动化实践里，让 Agent 直接产出 Markdown 已经是默认动作：周报、技术帖、文档都这么来。但生成只是第一步，真正耗时的是发布——公众号、知乎、掘金、自建站点对 Markdown 的支持各不相同，同一份稿子往往要手工调几轮格式。

## 问题

痛点不在转换本身，而在三件事：一是 AI 生成的内容常混入目标平台不支持的语法（脚注、Mermaid、裸 HTML）；二是转换逻辑散落在各个脚本里，改一处崩一处；三是发布后没人校验，图片挂了、代码块丢高亮，只能靠读者反馈。

## 做法

我们把整条管线拆成四段，段与段之间只传结构化数据。

**第一步，收紧源头。** 给 Agent 的生成 prompt 附一份「允许的语法子集」：只用 GFM 基础语法，禁用裸 HTML 和脚注，图片一律写相对路径，元信息放进 frontmatter（title、tags、cover、target）。写进 prompt 只是软限制，后面还要硬校验。

**第二步，统一中间表示。** 用 unified/remark 解析成 mdast，所有平台相关的处理都基于这棵 AST 做，不再对字符串做正则替换。这里加一个 normalize 阶段：统一标题层级、列表缩进、空行规则，保证后续转换的确定性。

**第三步，平台适配器。** 每个平台一个纯函数：mdast 进，平台载荷出。公众号适配器把代码块转成内联样式的 HTML、图片先上传再替换 URL；知乎适配器把任务列表降级成普通列表；静态站点基本直通，只补 frontmatter。适配器无状态，可以单独做快照测试。

**第四步，发布与校验。** 适配器可包装成 MCP tool 交给 Agent 调度，发布时带去重键保证幂等。发布完成后抓一次渲染结果，与本地期望输出做结构级 diff，顺带检查图片可访问性。

## 踩坑点

- 只靠 prompt 约束不够，脚注和 HTML 标签照样会漏出来，lint 必须兜底：不支持的节点报错或降级，不要静默丢弃。
- 公众号粘贴富文本会丢 `<style>` 块，样式必须全部内联；深色代码主题在白底文章里非常突兀，建议单独配浅色主题。
- 图片外链有防盗链和过期风险，任何平台发布前都先把图片落到自己的存储再替换链接。
- markdown 库升级会改变输出，依赖锁版本，核心转换逻辑配快照测试。
- 宽表格在移动端必然溢出，要么转图片要么拆成纵向列表，别指望平台自己缩放。

## 可复用建议

- 「允许语法子集」做成独立配置文件，生成 prompt 和 lint 共用同一份，避免两边漂移。
- frontmatter 里用 `target: [...]` 声明分发目标，管线按声明执行，同一份稿子天然支持跳过部分平台。
- 适配器保持纯函数 + 快照测试，新增平台就是新增一个文件。
- 发布接口一律带幂等键和重试，Agent 调度下失败重放是常态，不是异常。

## 总结

核心思路一句话：收紧源头、中心化转换、平台只做减法。AI 负责内容，lint 负责合规，适配器负责翻译，校验负责闭环。整套东西不复杂，unified 生态加几百行适配代码就能跑起来，但它把「每次发布手工调格式」变成了 CI 里的一条任务——在 Agent 批量产出内容的场景下，这是刚需。欢迎在评论区补充你们遇到的各平台适配怪癖，一起攒一份中文平台的语法支持矩阵。
