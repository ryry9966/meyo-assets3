## 背景

大多数人用 Agent 仍是"一问一答"：你不发消息，它就永远安静。但 OpenClaw 这类常驻网关型 Agent 有个天然优势——它一直在线。HEARTBEAT.md 就是利用这一点的小机制：系统按固定间隔（默认约半小时，可配置）向 Agent 发送一条心跳提示，Agent 读到你工作区里的 HEARTBEAT.md，自行判断这轮有没有值得做的事，有就做并汇报，没有就静默确认。

## 问题

纯被动模式会漏掉三类事情：基于时间的检查（磁盘水位、证书到期、每日摘要）、基于状态的巡检（MCP 服务是否存活、任务队列是否堆积）、以及需要长期观察才成立的事（"这个目录三天没动静就提醒我"）。而"每分钟跑一遍完整任务清单"的粗暴做法会带来两个新问题：token 成本失控，通知噪音把你训练成习惯性忽略它。

## 做法

1. **建文件**：在工作区根目录建 HEARTBEAT.md。心跳触发时该文件会随提示注入上下文，所以第一原则是短——控制在 30 行以内，细节放到单独文件，让 Agent 按需去读。
2. **三段式写任务**：每项写成"检查条件 + 触发动作 + 静默规则"。例如："检查今日日志中的新增 ERROR；仅当出现昨天没有的同类错误时汇报片段和路径；否则不做任何事。"
3. **约定确认信号**：要求 Agent 无事时回复 HEARTBEAT_OK。这是区分"正常值守"和"没收到心跳/进程挂了"的关键，别省。
4. **控制频率与路由**：心跳间隔不宜低于 15 分钟；把汇报目标路由到独立的低优先级会话，避免刷屏主对话。
5. **落盘状态**：心跳跑在独立会话，与主对话上下文隔离。需要跨轮记住"上次已经提醒过"，就让 Agent 写入一个 state 文件，下一轮先比对再决定。

## 踩坑点

- **抖动**："磁盘超 80% 就提醒"这类检查会每轮触发。务必加 state 文件比对，或写明"同一问题 24 小时内只报一次"。
- **时间感知**：Agent 不一定知道现在几点。涉及时间的检查让它先执行 `date`，别靠猜。
- **成本错配**：心跳只需低成本模型做轻量判断；定时汇总、批量处理这类重活交给 cron 类工具按计划触发，心跳只做巡检。
- **清单膨胀**：一旦超过一屏，Agent 会开始漏项或偷懒。定期删掉从未触发过的检查项。
- **上下文幻觉**：心跳会话看不到你主对话里说过的话，依赖聊天记忆做判断必翻车，重要约定落盘到 MEMORY.md 这类持久文件。

## 可复用建议

把 HEARTBEAT.md 当作"值班的巡检表"，而不是"任务队列"：写规则，不写一次性任务。核心模式是**检查 → 与 state 比对 → 有增量才通知 → 更新 state**，几乎可以套在任何巡检场景。每周翻一次心跳会话日志，你会发现一半检查项从未触发过，直接清掉——巡检表和代码一样需要 review。

## 总结

HEARTBEAT.md 的价值不在于让 AI 更聪明，而在于把触发权从人挪到机制里：文件即策略，心跳即调度，state 文件即记忆。它解决的是值守问题，不是推理问题。建议先从一个低频、低噪音的检查开始（比如每日摘要），验证通知路由和状态记录都稳定后，再逐步加项。
