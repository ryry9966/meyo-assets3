## 背景

OpenClaw 的 agent 本质上是一个能调工具的执行体：shell、MCP 服务、定时任务都能接。而 Git 恰好是"规则明确、操作重复、结果可回滚"的典型场景，很适合交给 agent 做半自动化。我最近在几个个人仓库上跑了一套流程，让助手负责日常提交、分支创建和清理，跑了两三个月，把经验和坑记下来。

## 问题

先说痛点，都是小项目里的真实状态：

- 改动攒一天，一次 `git commit -m "update"` 糊上去，回看历史没法定位；
- 忘了切分支，直接在 main 上改了半小时；
- 已合并的 feature 分支堆了二十多个没人删；
- rebase、cherry-pick 这类机械操作占用不该占的注意力。

这些事不需要判断力，但需要纪律。纪律恰好是 agent 擅长的。

## 做法

**1. 给受限的执行环境。** agent 通过沙箱 shell（或 MCP git server）操作仓库：独立的 deploy key、只授权特定仓库、在 shell 白名单层面直接拦截 `push --force` 和对受保护分支的删除。

**2. 把约定写进 skill 规则。** 在技能定义里固化：Conventional Commits 格式、分支命名 `feat/` `fix/` `chore/`、单次提交只对应一个主题、提交前必须跑 lint。规则写一次，跨会话自动生效，不要靠对话里反复叮嘱。

**3. 授权分级。** 我的分法是三层：`add + commit` 自动执行；`push` 需要人工回一句确认；rebase、删分支、force push 一律禁止，agent 只能给建议命令。这样错误的上限被锁死在本地。

**4. 分支生命周期自动化。** 定时任务每天跑一次：列出已合并分支、生成清理清单、经确认后删除；开工时说一句"开个 XX 的分支"，它自动从最新 main 切出并命名好。

## 踩坑点

- **大 diff 概括失真。** 攒一天的改动让 agent 写 message，它会抓错重点。解法是让它按文件和逻辑分组拆成多个提交，单次 diff 变小，概括就准了。
- **提交物不干净。** 有次差点把本地环境文件提交进去。现在提交前强制过一遍检查：`.gitignore` 有效性 + 敏感信息扫描，命中直接中止并报告。
- **冲突自动处理不可信。** rebase 遇到冲突时 agent 会"猜"一个解法，结果往往能跑但逻辑不对。冲突必须交还给人，这是硬规则。
- **并发写仓库。** 我手动改代码时 agent 同时跑了清理任务，状态错乱过一次。现在 agent 操作前先检查有无未完成的交互会话，同一时刻只允许一个操作方。

## 可复用建议

- 从**单人仓库**开始验证，别直接在团队主仓库开自动化；
- 授权按风险分级，默认最小权限，逐步放权；
- 所有 git 操作留痕：agent 会话日志 + 仓库 reflog 双份，出问题能倒查；
- 凭证走环境变量或 credential helper，绝不写进提示词；
- 规则沉淀在 skill / MCP 配置里，而不是每次会话的上下文里。

## 总结

Agent 管 Git 的价值不在于"全自动无人值守"，而在于把提交、清理、命名这类机械劳动外包出去，把冲突解决、发布决策这些判断留给人。约束先行、授权分级、留痕可查——做到这三点，这套流程在个人项目和小团队里都能直接落地。
