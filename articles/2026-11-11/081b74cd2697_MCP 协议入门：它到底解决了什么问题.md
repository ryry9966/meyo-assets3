## 背景

Agent 要真正干活，就得接外部系统：读本地文件、查数据库、调内部 RPC。早期大家的做法是为「每个客户端 × 每个数据源」写定制适配器。3 个 Agent 框架、10 个内部系统，就是 30 套胶水代码，鉴权、参数格式、错误处理各来一套。

## 问题

本质是 M×N 集成问题：客户端和工具方之间没有统一契约。换个宿主，工具要重写一遍接入；换个工具，客户端要改一遍调用逻辑。对模型也不友好——工具描述写法随意，模型选错工具、传错参数是日常。

## MCP 做了什么

MCP 把 M×N 压成 M+N：一套基于 JSON-RPC 的开放协议，传输层支持本地 stdio 和远程 Streamable HTTP。客户端（Host/Client）负责发现和转发，服务端（Server）暴露三类原语：

- **tools**：模型可调用的动作
- **resources**：可读取的数据
- **prompts**：预置的提示模板

客户端启动时握手、动态拉取能力列表，调用时传结构化参数。可以类比 LSP：编辑器不必为每种语言单独写插件，语言服务器自己实现协议即可。

## 上手步骤

1. 先跑现成的：`npx @modelcontextprotocol/server-filesystem ./` 起一个文件系统 server。
2. 在客户端配置里登记这条 stdio 命令（以 OpenClaw 的 MCP 插件配置为例，填 command/args），重启后确认工具列表被自动发现。
3. 让模型实际调用一次 `read_file`，观察入参校验和返回结构。
4. 自己写一个最小 server：Python SDK 里用 `@mcp.tool()` 装饰一个函数，docstring 写清楚，stdio 跑起来。
5. 接进你的 Agent 循环，跑一个真实任务验证闭环。

## 踩坑点

- **Windows** 下 stdio 注意编码和 shell 包装，`npx` 常需要 `cmd /c` 前缀。
- **工具描述是写给模型看的，不是写给人看的**。参数名含糊、类型太宽（什么都收 string）会显著拉高误调用率。
- 一个 server 塞几十个工具：上下文膨胀，模型选择错误率上升。按业务域拆分。
- 长任务会阻塞 stdio 请求，注意超时设置和异步设计。
- **安全**：本地 server 以你的用户权限运行，装第三方 server 等于给模型开本地权限。先读源码，能沙箱就沙箱。
- 协议在演进（SSE 已被 Streamable HTTP 取代），客户端与服务端版本要配套。

## 可复用建议

- 把存量 CLI、内部 RPC 包成 MCP tool，别重写业务逻辑。
- 只读数据走 resources，有副作用的动作走 tools，命名用动宾结构。
- 每个工具的 description 至少回答三个问题：什么时候用、什么时候不该用、返回什么。
- 本地开发用 stdio，多人共享再上 HTTP + 鉴权。
- 给 server 加日志和进程监控——它就是一个普通子进程，按子进程的标准对待。

## 总结

MCP 不负责让模型变强，它负责把「接入」这件事标准化。价值在于：工具实现一次，任何支持协议的 Agent 都能用。协议本身很薄，真正的工程量仍在工具设计、参数约束和安全边界上。建议从官方 reference server 读起，再包一个自己业务的内部 API，一天内可以跑通完整闭环。
