## 背景

社区内容运营有个现实痛点：好内容散落在 RSS、GitHub Release、群聊讨论里，人工筛选、改写、排版、发布，每天固定吃掉一两个小时。我决定用 OpenClaw 搭一个发帖机器人，目标不是"全自动躺平运营"，而是把人从机械劳动里解放出来，只保留审核环节。

## 问题

动手前先明确了自动化发帖的三个核心风险：**内容不可信**（模型会编链接和结论）、**重复发布**（同一事件换个说法就漏检）、**语气失控**（跑几天就变营销号）。这三个风险直接决定了管道怎么设计。

## 做法：四段式管道

```
cron → 采集agent → SQLite → 起草agent → 待审队列 → 人工放行 → 发布skill → 社区API
```

1. **采集**：cron 触发 OpenClaw agent 会话，通过 MCP fetch 工具拉 RSS 和仓库动态，落本地 SQLite。
2. **起草**：agent 按模板生成草稿，输出结构化 JSON（标题、正文、来源链接、标签）。
3. **审核**：草稿进待审队列，每天批量人工过一遍，通过才放行。
4. **发布**：自定义 skill 调社区 API 发帖，写入已发表记录。

原则是每段独立、可单独重跑、有日志。agent 只负责生成和调工具，状态全部落库，不依赖会话记忆。

## 踩坑实录

**坑一：链接幻觉。** 早期版本 agent 会"编"出看起来很合理的文章 URL，发出去就是死链。修复是硬性约束：草稿里每个 URL 必须先由 fetch 工具验证返回 200 且内容匹配，不通过就丢弃该条目，而不是让模型自己改。

**坑二：重复发帖。** 只按标题去重不够。现在用"URL 精确匹配 + 标题相似度 + 内容 hash"三重检查，上线后重复率归零。

**坑三：重试导致双发。** 发布 API 超时后重试，帖子发了两条。解法是幂等键：发帖前本地生成唯一 post_id 随请求携带，已成功即跳过重试。

**坑四：语气漂移。** 跑几天后草稿全是"重磅""震撼"。把风格约束从一句提示词扩成固定清单：禁用词列表、必须含"来源+一句技术摘要"、正文不超过 300 字，再给两三个合格样本做 few-shot，明显稳定了。

**坑五：长会话超时。** 采集和起草放一个会话里，源一多超时全丢。拆成两次独立触发，中间靠数据库衔接，单次失败只影响一段。

## 可复用建议

- 一定留人工审核，至少冷启动期。自动发出的错误比不发更伤信任。
- 任何事实性内容（链接、版本号、引用）必须经工具验证，别信模型复述。
- 幂等键 + 本地已发表记录，是一切自动发布的标配。
- 风格约束要"可判例化"：禁用词、结构模板、样例，比一句"语气自然"有效得多。
- 频率宁低勿高，先每天一条跑两周，观察失败模式再放量。

## 总结

上线一个月发了 40+ 帖，单条审核耗时从十几分钟降到一分钟以内。技术上没有黑魔法，价值在于把"采集—起草—审核—发布"拆成可观测、可重跑的管道，并在每个环节假设模型会出错。OpenClaw 在这里的角色是 agent 运行时和工具调度，真正的工程质量都在管道设计里。下一步计划把审核接进群聊，回复即触发发布。
