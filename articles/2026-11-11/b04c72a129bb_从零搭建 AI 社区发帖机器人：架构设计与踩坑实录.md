## 背景

我们社区的周更内容一直靠人工：整理仓库动态、筛选本周值得关注的讨论、汇总成帖发布。坚持三个月后盘了下时间，写帖本身只占 30%，剩下 70% 花在收集素材、核对信息、对格式上。于是决定做一个发帖机器人，把「收集 → 摘要 → 成稿」自动化，人只做最后一步审核。

## 问题：自动化发帖难在哪

- **信息源分散**：Git 提交、issue、社区讨论散落在不同地方，人工汇总费时；
- **模型会编造**：让 LLM 直接"总结本周动态"，它会把旧 PR 混进本周更新；
- **发布不可逆**：发出去就是公开内容，出错不是 bug，是事故。

## 架构设计

整体分三层，核心原则是**数据和权限分离**：

1. **触发层**：cron 定时触发 + webhook 手动触发；
2. **Agent 层**：OpenClaw agent 挂载 MCP 工具，负责摘要与成稿；
3. **执行层**：自建 MCP server，只暴露三个工具——`fetch_activity`（拉取仓库与讨论动态）、`save_draft`（写入草稿队列）、`publish_post`（调用论坛 API 发布）。

关键决策：**发布前强制人工审核**。`publish_post` 只允许被"已批准"状态的草稿调用，agent 没有直连发布权限。

## 实施步骤

1. 先写 MCP server，不接 LLM，用 curl 把三个工具单独验证通过；
2. 写 agent 系统提示词，硬约束：内容只允许来自工具返回值，返回值里没有的信息一律不写；
3. 跑 dry-run：agent 只产出草稿入队，不触达论坛；
4. 加最简审核界面（一个状态表 + 批准按钮）；
5. 灰度上线：先发测试板块两周，确认无事故后再放正式板块。

## 踩坑实录

1. **模型编造 changelog**：第一版提示词只说"总结本周"，模型把两个月前的 PR 写成本周更新。解法：提示词明确"工具未返回的内容禁止出现"，并在后处理层抽查关键条目是否来自原始数据。
2. **重试导致重复发帖**：论坛 API 超时后 agent 自动重试，同一内容发了两帖。解法：`publish_post` 加幂等键（内容 hash），发布前先查重。
3. **格式不一致**：论坛只吃 Markdown，模型偶尔输出 HTML 标签。解法：后处理做格式白名单清洗，不要指望提示词解决一切。
4. **上下文爆炸**：某周 issue 突增，一次性返回把上下文撑爆。解法：`fetch_activity` 改为分页返回 + 相关性过滤，token 用量降了一个数量级。
5. **定时任务跑了两次**：容器重启触发 cron 补跑。解法：任务加锁 + 当日已有草稿则直接跳过。

## 可复用建议

- **提示词当代码管理**：进仓库、有版本号、改动走 review，避免"改一句话全盘行为变化"；
- **外呼全留痕**：每次工具调用记日志，出问题能回放现场；
- **权限后置**：自动化先做"只读 + 草稿"，发布权限一定是最后才给；
- **范围收窄**：一个 bot 只做一类帖子。做"万能内容助手"的尝试我们放弃了，维护成本远超收益。

## 总结

机器人现在每周稳定产出一份草稿，人工审核约 10 分钟。最大的心得是：发帖机器人的难点不在"生成"，而在"可信"——**数据有来源、过程可回放、发布可拦截**。这三点做到位，自动化才敢真正放到社区里跑。代码结构不复杂，MCP server 两百来行，感兴趣的同学可以从 dry-run 模式开始复刻。
