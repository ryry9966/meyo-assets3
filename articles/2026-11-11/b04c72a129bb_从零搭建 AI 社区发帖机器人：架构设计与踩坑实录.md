## 背景

社区里每天产生大量值得沉淀的内容：答疑、踩坑、经验帖。人工整理成日报发到精华板块，重复且容易断更。我的目标是做一个发帖机器人：定时抓取站内动态 → 生成草稿 → 人工确认后发布。注意定位：不是全自动，而是「自动草稿 + 人工闸门」。

技术栈：OpenClaw agent 负责生成与编排，MCP 封装社区站点的读写接口，SQLite 存状态，cron 触发。

## 最初的错误认知

第一版我把它写成了一个大 prompt：「抓取今日动态，写一篇日报，然后调用发帖接口发布」。跑了三天暴露三个问题：

- **不可控**：生成和发布耦合，模型「觉得该发」就直接发了；
- **不可重放**：出错后不知道断在哪一步，只能整段重跑；
- **不可审计**：发了什么、为什么发、谁触发的，没有任何记录。

结论：这不该是一个 prompt，而该是一条流水线。

## 实际架构与步骤

1. **状态机拆分**：抓取 → 生成 → 审核 → 发布，四阶段各自落库，每条内容记录 state 和幂等键（源内容 hash）。
2. **MCP 工具层**：三个工具 `fetch_sources` / `create_draft` / `publish_post`。publish 独立鉴权、独立限频，其余只读或写草稿表。
3. **调度**：cron 起 OpenClaw 会话，系统提示词只负责「基于素材生成结构化草稿」，不决定是否发布。
4. **审核闸门**：默认进待审队列；含外链或置信度低的草稿强制人工；dry-run 模式只产草稿不发布。
5. **可观测性**：每次运行记录 prompt、工具调用参数（脱敏）、耗时与结果，失败推告警。

## 踩坑实录

1. **重复发帖**：任务重试导致同一篇日报发了两次。修复：publish 前按幂等键查重，已存在直接跳过。
2. **幻觉链接**：模型会「编造」相关帖子的 URL。修复：prompt 明确只允许引用 fetch 返回的原始 URL，发布前做域名白名单校验，不匹配打回人工。
3. **频率失控**：早期跑得太勤，被社区成员提醒「刷屏」。修复：发布频率成为一等配置（每日上限 + 冷却时间），写进 publish 工具而不是 prompt。
4. **Prompt 漂移**：换模型后输出格式变了，机器人反复重试。修复：草稿强制 JSON schema 校验，失败直接进人工队列，不做无限重试。
5. **凭证泄露**：调试日志把论坛 token 打了进去。修复：MCP 工具层不回传凭证，日志统一脱敏。
6. **时区问题**：cron 按 UTC 跑，日报时间错乱。修复：调度和展示显式指定时区。

## 可复用建议

- 生成与发布物理隔离，发布永远是独立、最小权限、可审计的工具。
- 一切写操作带幂等键——调度系统一定会重试你。
- 上线先 dry-run 一到两周，人工对比草稿质量，再逐步放开。
- 状态落库，不要依赖会话上下文：会话会丢，库不会。
- 每个 MCP 工具定义 schema、超时和失败语义：可重试的失败和必须进人工的失败要分开处理。

## 总结

机器人本身不难，难的是把它当成有状态的流水线来设计。OpenClaw + MCP 适合承担「编排 + 工具」的角色，但幂等、闸门、审计这些关键工程决策应放在工具层而不是 prompt 层，稳定性才立得住。目前它稳定运行数周，人工审核每天只花几分钟，产出质量比早期「一键全自动」版本高出一截——省下的不是人力，是返工。
