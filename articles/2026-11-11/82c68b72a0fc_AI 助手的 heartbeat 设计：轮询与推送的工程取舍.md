## 背景

在 OpenClaw 这类常驻型 agent 框架里，模型本身是“被动”的：没有输入就不产出。要让助手具备主动性——定时提醒、盯文件变化、检查消息箱——就必须引入 heartbeat 机制：周期性唤醒 agent，让它扫一遍状态，决定做什么还是继续睡。

围绕“唤醒的触发方式”，实践里基本两条路：**轮询**（定时醒来自己查）和**推送**（事件发生时被通知）。两条路我都跑过一段时间，把取舍记录一下。

## 问题

轮询的问题很直接：**空转成本**。心跳间隔 5 分钟，一天 288 次唤醒，绝大多数无事可做，但每次都要走一遍模型调用；及时性又被间隔锁死——事件发生后平均要等半个周期才被看到。

推送的问题更隐蔽：

- 事件源碎片化，webhook、文件监听、消息通道各自为政，格式与可靠性不一致；
- agent 会被随时打断，长任务执行中插入的消息会污染上下文；
- 推送通道本身可能失联——你以为“没事发生”，其实是没收到。

## 做法

我的方案是分层混合，步骤如下：

1. **给事件分级。** 列出所有事件源，按“是否值得唤醒 agent”打标：用户消息、报警类走推送；文件变化、日历临近这类低价值事件只写进状态文件，等轮询时聚合处理。
2. **轮询降频、瘦身。** OpenClaw 默认心跳会读 HEARTBEAT.md，无事就回 `HEARTBEAT_OK`。我把间隔从 5 分钟拉到 30 分钟，并把心跳指令精简为“只读状态文件，无事直接返回”，坚决不做全量扫描。
3. **推送统一入口。** 所有 webhook 收敛到一个网关脚本：先去重（相同 key 在静默窗口内只投一次），再判断静默时段（深夜仅报警级可穿透），最后以轻量摘要写进队列文件并触发唤醒。
4. **推送只敲门。** 事件 payload 只带一句话摘要和详情路径，agent 醒来后自己去拉，避免上下文被大块数据撑爆。
5. **加观测。** 每次心跳记录唤醒原因、耗时、token 消耗，每周看一次空转率，再回头调间隔与分级。

## 踩坑点

- **心跳 prompt 写太重**：早期让 agent 每次心跳“检查所有目录”，空转一次也烧几千 token，这是最贵的一课。
- **webhook 直写会话**：推送消息曾直接注入主会话，打断过一次长任务，上下文乱成一团。后来一律走队列，由心跳或空闲时机消费。
- **事件风暴**：监控抖动 3 分钟推了 40 条，去重和静默窗口是事后补的，建议一开始就有。
- **推送通道静默失败**：某天 webhook 配置错了，agent 一整天没动静，我误以为是“没事”。教训是：轮询心跳要保留一个极低频的 liveness 探测——哪怕收不到推送，也要确认链路活着。
- **定时漂移**：提醒类任务若依赖“心跳间隔整除”，会随负载漂移几分钟。时间敏感的用独立 cron 触发，不要蹭心跳。

## 可复用建议

- 心跳保留，但降频，定位为“兜底 + 健康探测”，不要当主力驱动；
- 高价值事件走推送，推送侧必配三件套：去重、静默窗口、轻量 payload；
- 每类事件都要有独立 mute 开关——宁可漏一条低价值事件，也不要让 agent 被噪音唤醒；
- 先上线观测再调参：空转率、唤醒原因分布、单次心跳 token 成本，三个数字够用了。

## 总结

轮询和推送不是二选一。轮询给你确定性、简单性和一个天然的健康探测，代价是空转与延迟下限；推送给你及时性和低空转，代价是链路复杂性与打断风险。对个人 agent 这个规模，我的结论是：**推送管“该醒的时候醒”，轮询管“没消息时确认活着”**，两者叠加比任何单一方案都稳。
