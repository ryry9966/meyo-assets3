## 背景

OpenClaw 的工作区里有一组以 Markdown 组织的"自我描述文件"：AGENTS.md 管行为规则，SOUL.md 管价值取向，USER.md 存用户事实，而 IDENTITY.md 管的是最基础的一层——这个 Agent 是谁：名字、定位、语气、emoji。这些文件在每次会话开始时注入 system prompt，相当于模型每次"睁眼"第一件事就是读一遍自己是谁。

很多人装完就跳过了这一步，用默认占位内容跑几个月。后果不是报错，而是隐性的：Agent 跨会话语气漂移、自我介绍前后不一致、通知和日志里看不出是谁发的。

## 问题

实际用下来，IDENTITY.md 有三类常见毛病：

1. **空置**。默认内容没人改，身份感弱，一致性差。
2. **写飞了**。当成"人设小作文"，几百字性格描写全塞进去。这个文件每轮常驻上下文，写太长不仅费 token，模型还会过度拟合描述，风格反而更不稳。
3. **混放**。把"用户偏好"、"项目背景"这类事实写进身份文件。身份是"我是谁"，记忆是"我经历过什么"，混在一起后每次改记忆都在动身份，行为自然漂。

自动化场景还有个特有问题：多个实例（一个工作 Agent、一个生活管家）共用同一份身份，群聊通知里根本分不清哪条是谁发的。

## 做法

我的实践是把它当配置文件养，四步：

1. **先做减法**。控制在 5–8 行：名字、一句话定位、3–5 个语气关键词、一个 emoji、一条"不做什么"的边界。既然每轮都加载，短就意味着稳。
2. **职责分离**。语气习惯归 SOUL.md，用户事实归 USER.md，事件性内容交给 MEMORY.md。判断标准很简单：这条内容换了用户还成立吗？成立才放这里。
3. **进 git，小步演进**。workspace 整体纳入版本控制，改身份走 commit，一次只动一个维度（比如只调语气关键词），观察一周行为再决定下一步，回滚成本为零。
4. **Agent 起草，人来提交**。让 Agent 在会话里根据近期交互起草修订版，我自己 diff、自己 commit。不要让它自由改写自己的身份文件——自我修改的反馈回路容易越改越偏。

## 踩坑点

- **改太勤**。身份每周一变，等于每周换个搭档，cron 任务的通知语气也跟着变，排查问题时很混乱。建议以月为节奏。
- **与 SOUL.md 冲突**。身份写"简洁克制"，SOUL.md 写"热情外向"，模型会在两者间摇摆。改之前全局搜一遍关键词。
- **多实例没拆身份**。第二个实例上线时记得复制 workspace 并改 IDENTITY.md，名字和 emoji 错开，通知可读性会好很多。
- **忽略了常驻成本**。排查上下文占用时别漏掉这份文件，它和 MEMORY.md 一样是每轮固定开销。

## 可复用建议

- 模板化：`名字 / 一句话定位 / 语气关键词×3 / emoji / 边界一条`，新实例五分钟配好。
- 想验证改动效果，固定一组探针问题（让它自我介绍、处理一个歧义请求），改前改后各跑一遍对比。
- 能力变更与身份变更解耦：接新 MCP 工具、换模型、装插件，都不该和身份改动混进同一个 commit，出问题时好定位。
- 团队场景维护一份基础身份 + 每实例一小段 override，减少重复维护。

## 总结

IDENTITY.md 是 OpenClaw 里最小、却加载频率最高的文件之一。它不值得写长，但值得被认真对待：当配置管、进版本库、小步改、人审提交。身份稳了，跨会话一致性和自动化输出的可辨识度都会跟着稳下来。
