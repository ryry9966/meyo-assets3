## 背景

用 Agent 框架搭过助手的应该都有同感：模型本身无状态，每次新会话都得重新交代一遍——“我用 pnpm 不用 npm”、“提交信息别带 emoji”、“时区是东八区”。塞一次上下文管一次会话，第三次重复时你会开始怀疑这套东西的工程价值。

记忆系统要解决的就是这件事：把“用户是谁、偏好什么”从一次性 prompt 变成持久化、可维护的数据。

## 问题

常见的三种失败做法：

1. **全塞 system prompt**。偏好越攒越多，几百上千 token 的“用户说明书”，模型注意力被稀释，关键项反而被忽略，成本也在涨。
2. **全靠向量检索**。历史对话全量 embedding，用时查相似。偏好类信息会被大量闲聊淹没，检出来的上下文噪声很大。
3. **指望模型自己记**。跨会话它什么都不记，除非你显式设计。

根因是没区分记忆的类型和生命周期，试图用一种机制兜住所有东西。

## 做法：按生命周期拆三层

**1. 用户画像（Profile）**：稳定偏好，低频变更。用一份结构化文件存，比如 `memory/profile.md` 或 JSON，每条带 `updated_at` 和 `source`。这份文件全量注入 system prompt——控制在一两百 token 内，不参与检索。

**2. 任务记忆（Working）**：当前项目状态、进行中的决策。按项目目录存，会话开始时由 Agent 主动读取，任务结束归档。

**3. 情景记忆（Episodic）**：历史对话和结论。进向量库，但只在 Agent 判断需要时通过工具按需检索，不做默认注入。

写入路径分两条：显式写入是用户说“记住我偏好 X”或直接改文件，可靠；隐式写入是会话结束后用 LLM 抽取候选偏好，必须过置信度阈值，先落“待确认区”，用户点头才进 profile。更新时**替换旧值而不是追加**，避免自相矛盾。

暴露成 MCP 工具就三个：`get_profile`（读画像）、`search_memory`（按需检索）、`propose_memory`（写入需确认）。profile 文件保持人类可读可编辑，用 git 管理，改动有据可查。

## 踩坑点

- **append-only 是重灾区**。偏好会变，只增不改，三个月后库里同时存在“深色模式”和“换浅色模式”，模型随机听一个。
- **隐式抽取容易幻觉**。用户随口一句“今天有点冷”不代表“用户讨厌低温环境”。没有阈值和确认环节的自动写入，污染速度远超清理速度。
- **记忆内容要当数据对待**。检索回来的历史文本可能携带注入指令，注入 prompt 时用明确边界包住，别和系统指令混排。
- **不可见就不被信任**。用户看不到也改不了的记忆宁可不做。纯文件方案最大的好处就是随时能 `cat` 出来看、随时能删。

## 可复用建议

- 先从单个扁平文件起步，别一上来上数据库；条目超过 50 条再考虑拆分
- schema 必带 `updated_at` 和 `source`，排查过期偏好时能救命
- 情景检索加时间衰减，按访问频次和年龄降权
- 验收方式很朴素：开新会话，不重申偏好，看 Agent 行为是否兑现

## 总结

记忆不是模型能力，而是存储、读写策略和生命周期管理的工程问题。画像用文件加全量注入，情景用检索加按需拉取，写入走确认，更新走替换。先用最土的方案跑起来，等出现真实痛点再增加复杂度——大多数个人助手，一份维护良好的 profile 文件已经能解决八成问题。
