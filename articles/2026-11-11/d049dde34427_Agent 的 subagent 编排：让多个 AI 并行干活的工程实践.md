## 背景

早期跑 agent 任务大多是"一根筋"模式：主 agent 自己读文件、调工具、写结论，所有中间过程堆在同一个上下文里。任务一长，context 膨胀、响应变慢，中途任何一个工具调用出错，整条链路都得重来。subagent 编排就是把这件事拆开：主 agent 只负责拆解和汇总，具体执行交给若干个子 agent，能并行的并行跑。

## 问题

举个实际例子：要给仓库里 30 个模块的 README 做结构化摘要并汇总成一份报告。单 agent 串行跑，逐个读、逐个总结，要 40 多分钟；主上下文还塞满了 30 份中间输出，最后写总报告时模型等于"带着一肚子杂物"工作，质量明显下滑。

## 做法

1. **先做依赖分析，再决定并行。** 把任务列成清单，标出哪些是纯读、哪些有写冲突。纯读任务才适合并行；两个子 agent 同时改同一个文件，结果就是互相覆盖。
2. **给子 agent 最小上下文。** 不要把主会话历史整个传下去，只传它的目标、所需输入片段和输出格式。建议把子 agent 的 prompt 固定成模板：任务目标 / 输入 / 允许的工具 / 返回格式 / 超时。
3. **收窄工具权限。** 子 agent 只挂完成该任务必需的 MCP 工具，能不给 shell 就不给。权限越小，跑偏概率和爆炸半径都越小。
4. **控制并发。** 从 2~3 个并发起步，观察限流和本机资源（文件锁、端口、API 配额）再往上调。盲目开 10 个并发，往往换来 429 和一堆半成品。
5. **约定结构化返回。** 要求子 agent 只返回结论和关键数据（固定 JSON 或 200 字以内摘要），不返回过程，主 agent 聚合时只吃摘要。
6. **每个子任务设超时和独立重试。** 单个子 agent 卡死不应拖垮全局；失败的重试一两次，仍失败就标记跳过，最后在汇总里如实报告。

## 踩坑点

- **子 agent 返回太长**：不约定返回格式的话，聚合阶段照样把主 context 撑爆，等于把串行的膨胀换了个位置。
- **隐式依赖**：两个任务看起来独立，实际都要"先更新索引再写文件"，并行就出乱序。这类要降级成串行或加锁。
- **无超时**：子 agent 陷入循环调用工具，主 agent 干等。没有 timeout 的编排迟早翻车。
- **过度编排**：任务本身强串行（后一步依赖前一步的完整输出），硬拆成 subagent 只多了调度开销和失败面。并行是手段，不是目的。

## 可复用建议

- 把子 agent prompt 模板沉淀到项目里，下次直接填空。
- 每次编排记录三个数：总耗时、token 消耗、失败率，跑几次就能判断哪些任务值得拆。
- 优先拆"批量同构"任务（N 个同类目标、互不依赖），这类收益最大、风险最小。
- 主 agent 的职责收敛为：拆解、分发、聚合、汇报，不要自己再下场干活。

## 总结

subagent 编排的价值就两点：上下文隔离和并行提速。能不能用好，取决于任务是否真的可拆、结果是否容易聚合。建议先从两三个并发、批量读类任务练手，把模板、超时、返回格式这三件事做扎实，再逐步扩大使用面。编排本身不复杂，复杂的是克制——不为了并行而并行。
