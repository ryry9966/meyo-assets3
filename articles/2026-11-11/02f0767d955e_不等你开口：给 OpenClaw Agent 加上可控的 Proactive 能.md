## 背景

目前大多数助手的交互模型是问答式的：用户开口，agent 响应，结束。但日常里真正高频的需求往往不是"问"，而是"盯"——盯 CI 是否红了、盯某个目录有没有新产物、盯日报今天填没填。等用户记得开口时，事情通常已经晚了。这篇帖记录我在 OpenClaw 上给个人 agent 加 proactive 能力的过程与取舍。

## 问题

"主动"做错比不做更糟。核心矛盾有三个：

1. **触发从哪来**：没有用户输入，agent 靠什么知道自己该动？
2. **说什么**：没有用户问题，上下文得自己拼，拼少了等于没说。
3. **动到哪一步**：只提醒，还是直接替用户执行？

## 做法

我的方案是"三类触发 + 三级升级 + 白名单动作"：

**第一步，接入三类触发源**（挂在 OpenClaw 的 scheduler / hook 插件上）：

- 定时类：cron 触发，适合周期性巡检；
- 事件类：webhook / MCP 事件订阅，如 git push、CI 回调；
- 状态类：对目录、文件、接口做快照比对，diff 非空才触发。

**第二步，便宜过滤器前置**。规则（正则、阈值）在前，LLM 在后。九成轮询事件用规则就能判掉，只有真正值得看的才进模型，token 开销直接降一个数量级。

**第三步，agent 自组上下文**。主动消息必须带三件套：发生了什么（原始证据）、为什么找你（命中原因）、建议动作。不带证据的主动提醒，用户第一反应是"它是不是幻觉了"。

**第四步，三级升级通道**：写入静默日志（可事后查）→ 汇总进每日 digest → 只有高置信度且高时效的事件才走即时推送。默认走低级别，宁可漏报，不可轰炸。

**第五步，动作权限分层**。读操作直接执行；写操作分白名单（如追加到草稿文件）与需确认（如发消息、改配置），确认类只给选项、不代执行。

## 踩坑点

- **自触发循环**：agent 生成的文件又触发了目录 watcher，事件风暴。解决：agent 自产动作统一打 origin 标记，watcher 直接跳过。
- **重复提醒**：同一个失败 CI 连推五次。改成快照 + diff，状态没变不发，变了才发。
- **quiet hours 失效**：凌晨两点收到推送后，我一气之下把整个 proactive 模块关了三天。补上时间窗和每日推送上限，它才活了下来。
- **成本失控**：早期把原始日志整段丢给模型判断，一天烧掉平时一周的量。教训：过滤前置，模型只看摘要。

## 可复用建议

- 触发源配置化，插件只注册"触发器 + 过滤器 + 摘要器"三件套，不写死流程；
- 每条主动消息带幂等键，方便去重与事后审计；
- 度量两个指标就够：行动转化率（用户照做了没）和忽略率。忽略率连续走高，就自动降级该触发器的推送级别。

## 总结

Proactive 不是"多做事"，而是"在对的时刻，用最小成本把正确信息送达"。工程上的关键不在模型，而在触发设计、过滤前置和权限收窄。先用日志级和 digest 级跑两周，攒够置信度再放开即时推送，是最稳妥的路径。欢迎在评论区交流你的触发器设计。
