## 背景

做 Agent / MCP 相关开发有个绕不开的问题：工具调用链路里会塞进大量本地上下文——文件内容、日志、库表结构、MCP 工具的返回结果。这些数据全走云端 API，隐私和成本都是负担。我的诉求很直接：把日常自动化任务（定时抓取、本地文件整理、内网巡检）交给跑在自己机器上的模型，云端只兜底困难任务。

## 问题

动手前先回答三个问题：

1. 这台机器到底能跑多大的模型？
2. 哪个量化档位是速度和质量的平衡点？
3. 本地模型能否稳定完成 Agent 最依赖的能力——工具调用？

## 做法

我的环境：一台 32GB 内存的 Mac，加一台 4060Ti 16GB 的 Windows 台式机。步骤如下：

**1. 先算显存账。** 粗略公式：Q4 量化下模型体积 ≈ 参数量 × 0.6 GB，再预留 20–30% 给 KV cache。16GB 显存跑 14B Q4 从容，32B 勉强；24GB 是 32B 的舒适区。

**2. 选运行时。** 快速验证用 Ollama，一条命令起服务；要吞吐和精细控制用 llama.cpp 或 vLLM（后者需要 Linux + NVIDIA）。它们都暴露 OpenAI 兼容接口，Agent 框架侧改个 base_url 就能切换。

**3. 选模型。** 工具调用能力优先于通用能力。我在自己的 20 条真实 Agent 任务上对比了几轮：14B 级别的 Qwen 系列、DeepSeek 蒸馏版在结构化输出上已经够用；7B 以下在多工具场景参数幻觉明显。

**4. 接进 Agent 循环。** 在 OpenClaw 里注册 MCP 工具，跑通完整链路：模型 → 工具选择 → 执行 → 结果回填 → 二次推理。先跑通，再谈优化。

**5. 压测。** 记录两个数：首 token 延迟和生成速度。14B Q4 在 4060Ti 上约 35–45 tok/s，Agent 循环体感可接受；低于 15 tok/s 就该降档。

## 踩坑点

- **Ollama 默认上下文很小**（2048/4096），Agent 循环几轮就溢出，表现为“模型失忆”。务必显式把 num_ctx 设到 16k 以上，同时注意 KV cache 的额外显存开销。
- **工具调用格式不兼容**。部分模型的自定义 function call 格式框架解析不了。选型时确认运行时已适配该模型的 tool calling 模板，而不是只看榜单分数。
- **上下文截断是静默的**。系统提示 + 工具描述 + 历史轮次叠加很快超限，超了不报错、只是悄悄丢内容。给 Agent 循环加 token 计数日志。
- **别迷信参数量**。我测到过 32B 通用模型在小工具集上输给 14B 工具特调模型的 case。用自己的任务集验证，别只看跑分。

## 可复用建议

- 建 10–20 条真实任务的私有评测集，换模型、换量化档位各跑一遍，十分钟出结论，比任何公开评测都可靠。
- 混合路由：隐私敏感、高频、简单任务走本地；复杂推理和长上下文走云端，在框架里按任务标签分流。
- 上下文开多大不是免费的，KV cache 预算单独列一项。
- Agent 场景温度压到 0.1–0.3，固定 stop 参数，减少工具参数的随机性。

## 总结

家用机器跑本地 LLM 已经是成熟的工程问题，难点不在“跑起来”，而在“稳定地跑 Agent 循环”。先算显存、再选工具调用友好的模型、最后用自己的任务集验收——三步走完，本地模型就能真正接进自动化链路，而不是停留在本地聊天玩具。
