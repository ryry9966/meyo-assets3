# 背景

OpenClaw 的 agent 跑起来之后，一天内的调用差异非常大：主对话是长上下文、多轮、常带 MCP 工具编排；而心跳检查、定时摘要、记忆压缩、消息聚合这类任务，本质是单轮、无状态、格式固定的"粗活"。全部走同一个云端强模型，账单和首 token 延迟都难看；全走本地模型，复杂任务又容易翻车。所以多模型路由的核心不是"能不能配两个模型"，而是分流的判断标准。

# 问题：按"难度"分会失手

我们最早按任务难度分：难的给 GPT，简单的给本地模型。跑两周就发现这个标准不稳——"难度"是主观的，模型版本一换，边界就漂。后来改成按**任务形态**分，稳定性好得多：

- 需要多步工具调用（MCP 编排）→ 云端强模型
- 需要输出结构化 JSON / 代码，下游要解析 → 云端强模型
- 无状态、单轮、批处理、模板化输出 → 本地模型

# 做法

1. **先盘点调用路径。** 从 usage 日志里把主会话、cron 任务、心跳、subagent、记忆整理各自的调用次数和 token 拉出来。不盘点就路由，等于盲调。
2. **分桶后落配置。** 主模型设为云端档作为默认；本地模型走 Ollama 的 OpenAI 兼容端点，作为第二档（配置示意，字段名以你手上版本为准）：
   ```yaml
   primary: cloud-model      # 主对话、工具编排
   secondary: local-endpoint # 粗活与兜底
   ```
3. **路由落地二选一：**
   - 对特定 skill / 定时任务做模型覆盖，指定用本地档；
   - 或者（更推荐）把本地模型包成一个 MCP 工具，比如 `summarize_local`，让主 agent 显式调用。路由决策留在 agent 手里，日志里看得见，出问题好排查。
4. **兜底链：** 云端不可用时降级到本地，保证"能出结果"，但不追求质量。
5. **每周复盘** usage 日志：调用分布、失败率、token 成本，再微调分桶。

# 踩坑点

- **本地模型的 function calling 很不稳。** 小参数量的开源模型在 agent loop 里经常乱传参数或陷入重复调用。结论：让本地模型干"不调工具"的活，工具链全留给云端。
- **上下文静默截断。** 本地档常见 8k/32k 窗口，长会话直接塞进去，摘要会漏后半段。先分段再摘要。
- **中文 token 效率差异。** 部分本地模型中文 tokenizer 不经济，实际省的钱比估算少。先跑一周真实账单对比，再决定要不要迁移。
- **输出风格漂移。** 摘要任务换模型后格式变了，下游解析挂掉。给本地模型固定输出模板，解析端加 schema 校验 + 一次重试。
- **fallback 抖动。** 超时阈值设太紧，两档来回切，会话风格不一致。给 fallback 加粘性：切换后锁定一段时间。

# 可复用建议

- 分桶标准用"任务形态"，别用"难度"。
- 无状态、单轮、可批处理 = 本地模型的最佳场景。
- 本地模型包成 MCP 工具，比到处改路由配置更可控。
- 留一个一键全切云端的环境开关，专供排障时使用。
- 记账先行：没有统一的 usage 日志，路由优化就是玄学。

# 总结

多模型路由不是省钱技巧，而是把算力花在对的地方：工具编排和结构化输出交给云端强模型，模板化的单轮粗活留给本地。先盘点、再分桶、小步切换、每周看数据——这套流程一个月内就能把成本和延迟压下来，而且不牺牲主链路的稳定性。
