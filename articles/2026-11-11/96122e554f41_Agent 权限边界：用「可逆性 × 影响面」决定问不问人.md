## 背景

Agent 接上 MCP 工具和插件之后，第一次「自己把事情办成」很爽，第一次「自己把事情办砸」也很深刻。很多人第一反应是往 system prompt 里加一句「谨慎行事」，但跑几天就会发现：模型对「谨慎」的理解和你不一致。权限边界不是 prompt 问题，是系统设计问题——哪些动作默认放行、哪些必须停下来问人，要在工具层就定清楚。

## 问题：两个方向的失败都常见

- **问太多。** 每写一个文件、每调一个接口都弹确认，人很快退化成「无脑点允许」的橡皮图章，确认机制形同虚设。
- **问太少。** Agent 静默执行了删数据、对外发消息、调付费 API 这类动作，等发现时已经收不回来。

核心矛盾在于：确认本身有成本，成本太高机制就失效；但破坏性动作一旦漏过，代价不可逆。

## 做法：两维度打分，三档划分

先给每个工具按两个维度打分：**可逆性**（能不能撤销）和**影响面**（只动本地沙箱，还是会触达外部系统、别人、钱）。再叠一个辅助判据：结果能否被机器自动验证（测试、lint、diff）。

据此划三档：

1. **自动执行**：可逆 + 影响面小 + 可验证。读文件、跑测试、生成草稿。
2. **必须确认**：不可逆、对外可见、花钱、影响他人。发消息、删数据、付款、发布。
3. **直接禁止**：明确不许 Agent 碰的，比如生产配置、密钥本体。

落地三步：

- **盘点。** 把 OpenClaw 里接的所有 MCP 工具和插件列一张表，逐个标档位。多数人盘完会发现：自动档比想象中多，真正要确认的就那几个。
- **在工具网关 / hook 层强制，而不是只写在 prompt 里。** Prompt 是软约束，模型会漂移；网关层的 allowlist 和 confirm 拦截才是硬边界。
- **确认要带上下文。** 弹给人的不是「Agent 想执行某个操作」，而是具体 diff、完整命令、目标环境、预估成本。人批准的是一次有信息的决策，不是一次仪式。

## 踩坑点

- **只靠 prompt 约束。** 跑一周就会遇到「自作主张」，规则必须落到工具层。
- **确认疲劳。** 弹窗一多，人开始无脑批准，比不弹还危险。解法不是加强提醒，而是把更多动作挪进沙箱，让它够格自动执行。
- **读操作不一定安全。** 带副作用的 GET、触发 webhook、消耗配额的查询都存在，别默认「读 = 无害」。
- **dry-run ≠ 真实执行。** 权限、限流、目标端状态常在真跑时才暴露，保留一份差异清单。
- **等待批准变成死锁。** 人不在，Agent 卡在 pending 直到超时。要有默认降级策略：停下、汇总、留给下次，而不是自己猜一个答案继续跑。
- **档位没带环境。** 同一个工具在 dev 和 prod 风险完全不同，环境标签要进到工具配置里。

## 可复用建议

- 一条经验法则：凡是**发出去了就收不回**的动作（对外发消息、付款、删除、发布），一律问人；其余尽量用沙箱和自动化验证兜住。
- **先收紧再放宽。** 上线时偏保守，靠审计日志（自动执行的部分也要记）逐步放开，而不是先放开再补规则。
- 能让机器验证的，别麻烦人：测试能过的改动，人只看摘要。
- **「始终允许」只给可逆动作。** 不可逆动作不允许存在永久白名单，批准要带过期时间。

## 总结

权限边界不是调 prompt，而是做系统设计：两维度打分、三档划分、工具层强制、带上下文确认、审计日志回灌调参。目标是让 Agent 在沙箱里大胆干、在边界上停下来问、在禁区外进不去——而不是让人变成它的橡皮图章。
