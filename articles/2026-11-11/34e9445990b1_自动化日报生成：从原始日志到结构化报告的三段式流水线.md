# 背景

跑了一段时间 OpenClaw 之后，最直观的感受不是"能力不够"，而是"发生了什么说不清"。Agent 会话日志、cron 任务执行记录、MCP 工具调用输出分散在不同目录，出了问题靠人翻。于是做了一条日报流水线：每天固定时间，把前一天的原始日志压成一份结构化报告，异常时才推送。

# 问题

直接让模型读原始日志，有三个明显问题：

1. **上下文装不下**。一天的日志动辄几万行，模型只能读到片段，摘要天然残缺。
2. **幻觉不可控**。日报里出现过一次"脑补"的错误描述，之后没人再信这份报告。
3. **成本不划算**。每天重复消费同样的噪声，token 花费远超价值。

结论：提取和聚合必须用确定性代码做，模型只放在最后一公里做叙述。

# 做法：三段式流水线

**第一段：采集与归一化（纯脚本）。** 一个 Python 脚本扫指定日志目录，逐行解析出时间戳、来源（agent 名 / cron / MCP 工具）、事件类型（启动、工具调用、错误、结束）、耗时与成败，输出当天一份 JSONL。字段固定、带版本号，这一步不调用任何模型。

**第二段：聚合与指标（纯脚本）。** 对 JSONL 分组统计：各 agent 任务数、失败率、最慢调用、按错误签名去重后的 Top 错误。签名聚类前先把消息里的 UUID、数字、路径归一化，否则同一个错会被算成一百个。产出一份几 KB 的 JSON 摘要。

**第三段：LLM 摘要层。** 把聚合 JSON 交给模型，prompt 固定输出三节：今日概览、异常与建议、明日关注点。用 OpenClaw 的 cron 触发，结果落盘为带日期的 Markdown；只有异常指标超阈值时才推送到消息渠道。

# 踩坑点

- **时区边界**。日志是 UTC 时间戳，日报按本地时区切天，结果跨界事件被算错天，失败率曲线看着莫名其妙。统一时区、显式写死切分时间后才稳定。
- **cron 重入**。某次聚合卡住，下一轮 cron 又跑了一遍，群里收到两份日报。加锁文件 + 超时兜底，日报生成必须幂等。
- **错误签名太粗**。最初按原文聚类，"timeout on task abc123" 和 "timeout on task def456" 被当成两种错。归一化后噪声降了一个量级。
- **日志轮转抢跑**。聚合还没跑，日志先被轮转删了。把聚合挪到轮转之前，JSONL 归档再单独保留 30 天。

# 可复用建议

- **中间产物比最终报告更值钱**。JSONL 留着，周报、趋势图、复盘都能重建，日报只是它的一种视图。
- **指标层与叙述层解耦**。换模型、改 prompt 不影响统计口径；口径要变，历史数据也能对齐迁移。
- **把日报当产品对待**：schema 校验、阈值推送、失败告警一样不能少。否则它会悄悄烂掉——某天你才发现已经三周没出报告了。

# 总结

这条流水线的核心取舍是：**确定性的部分交给代码，模糊的部分才交给模型**。提取、聚合、阈值判断用脚本，模型只负责把几 KB 的结构化摘要讲成人话。上线两个月，日报稳定生成，模型调用量反而降了——因为不再需要为了"总结一下"去喂全量日志。自动化的老道理：先把数据流捋直，智能才有地方安放。
