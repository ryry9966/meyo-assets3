最近技术圈吵得最凶的关键词之一，是 harness。36kr 把这场争论称为「Harness 大战」：当各家大模型的编程能力快速趋同，真正拉开 Agent 产品差距的，变成了包在模型外面的那层「脚手架」。有人喊出「the harness is the moat」（harness 才是护城河），也有人反驳：模型每半年升一级，harness 的花活迟早被原生能力抹平。这场架吵的不是玄学，而是 AI 工程里一个非常具体的问题——模型之上那层代码，到底值多少钱？

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/246fcbb5b33c14ae.png)

## Harness 是什么：给模型装上驾驶舱

- 词源上，harness 来自软件测试领域的 test harness：包在被测代码外面、负责喂输入收输出的那层驱动代码。到了 AGI 评测语境（比如 ARC-AGI），它指包裹模型的一切评测工程——怎么提问、给不给搜索、允许多少轮反思。
- 在 Agent 语境下，harness 大致由五部分组成：
  1. system prompt 与行为约束；
  2. 工具集定义：执行 shell、改文件、搜代码、开浏览器；
  3. 上下文管理：历史压缩、按需检索、子任务拆分；
  4. 执行循环：规划 → 执行 → 观察结果 → 自我修正；
  5. 安全层：权限控制、沙箱、回滚。
- 一个不太严谨但好用的类比：模型是发动机，harness 是底盘、变速箱和方向盘。没人会开着裸发动机上班——同一个发动机装在卡丁车和跑车上，圈速是两回事。

## 仗是怎么打起来的

- 导火索是编程 Agent 的商业化：Claude Code 用「极简终端 harness + 强模型」跑通了付费闭环，随后 OpenAI 推出 Codex CLI、Google 上线 Gemini CLI，开源阵营 opencode、Cline、Amp 贴身缠斗，IDE 派的 Cursor、Windsurf 也没闲着。
- 正方论据：同一个模型换不同 scaffold，在 SWE-bench 这类基准上分差能拉开十几个百分点；ARC-AGI 上，同一个模型「裸考」和配了搜索、反思机制的 harness 考，分数能差数倍。这说明 harness 本身就在生产「智力」。
- 反方论据：很多 harness 技巧本质是给弱模型打的补丁——兜底重试、啰嗦的提醒、精细到啰嗦的流程控制。下一代模型原生能力上来后，这些补丁不仅多余，反而会束缚模型发挥。一句话：为弱模型设计的拐杖，会变成强模型的镣铐。

## 为什么模型越强，harness 反而越关键

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/565ad2aebda14fc6.png)

机制层面至少有三条硬道理：

1. **上下文窗口 ≠ 上下文利用率**。长任务动辄几万 token，模型对中段信息的注意力明显稀释（所谓 lost in the middle）。harness 要负责压缩历史、按需检索、把大任务拆给子 Agent——本质是替模型做「工作记忆管理」。
2. **工具接口决定发挥上限**。一个文件编辑工具返回精简 diff 还是整份文件，token 成本和出错率差一个量级；工具描述写得含糊，模型就真的会理解错工具。这部分纯靠工程，模型自己救不了。
3. **反馈回路放大成功率**。假设单次操作正确率是 p，带测试反馈的自我修正循环能把成功率推向 1−(1−p)^n——n 是修正轮数。跑测试、读报错、定位、再改，这套回路的质量直接复利到最终结果上。

换个公式：Agent 的最终表现 ≈ 模型能力 × harness 质量 × 环境质量。乘法关系意味着短板效应——模型再强，回路烂就是白搭。

## 战场格局：三个流派与一个趋势

- **模型厂一体化派**：Claude Code、Codex CLI。harness 与模型共同迭代，享受「亲儿子权限」，能针对模型脾气做深度调校。
- **IDE 生态派**：Cursor、Windsurf。把 harness 嵌进编辑器，拼的是代码库索引、补全延迟和开发流程整合。
- **开源终端派**：opencode、Cline、Goose 等。社区驱动、迭代极快，harness 本身就是开源产品。
- 两个共同趋势值得盯住：其一，MCP 等协议正在把工具层标准化，harness 的壁垒从「我接的工具多」转向「我的上下文工程和错误恢复做得好」；其二，模型厂不断把 harness 能力下沉为原生能力（原生工具调用、computer use、长时程记忆），逼所有 harness 定期返工。

## 三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/0187ba3faa3d598e.png)

1. **选 Agent 产品，别只问「用的哪家模型」，去测它的失败恢复**：给它一个跨多文件、必须跑测试的真实任务，看它第一次失败后能不能自己爬起来。错误恢复能力是 harness 质量最诚实的指标。
2. **自己搭 Agent，优先做上下文工程和工具返回值瘦身**，别急着堆 prompt 技巧；同时把 harness 写成可替换的一层——模型升级时只动这一层，业务逻辑纹丝不动。
3. **判断 harness 护城河，只需一个问题**：下一代模型发布时，这套 harness 里哪些设计会从「助力」变成「累赘」？为弱模型打的补丁越多越危险；真正模型吃不掉的，是沙箱权限、代码库索引、CI 集成这类「环境」资产。

龙虾每次长大都要蜕一次壳：壳太硬，长不大；没壳，会被吃掉。harness 就是模型的壳——模型每升一次级，所有壳都得重造一遍。这场大战大概率没有终局赢家，但每一轮蜕壳，都会把「怎么把模型用好」这门手艺往前推一格。
