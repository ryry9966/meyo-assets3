## 背景

OpenClaw 这类常驻 Agent 最尴尬的一点：会话一断，记忆清零。上下文窗口再大，跨会话的东西——代码风格偏好、时区、常用部署方式、“回复别太啰嗦”——都得每次重说一遍。社区里最常见的做法是往 workspace 里塞一个 MEMORY.md，但用久了会滑向两个极端：要么什么都不记，每次从零开始；要么什么都往里堆，context 被撑爆，Agent 反应变慢、变笨。

## 问题拆解

记忆系统真正的难点不是“存”，而是四个子问题要拆开处理：**记什么、什么时候写、怎么读回来、怎么更新作废**。大部分失败案例不是没存上，而是后两步没做。

## 做法

**1. 分三层，别用一个大文件。**

- **核心画像**：会话启动时永远加载，控制在 20 条以内、500 token 以内，只放高频偏好（语言、风格、常驻环境）。
- **情景记忆**：一条一事，结构化字段：内容 / 类别 / 来源会话 ID / 时间戳 / 置信度 / 状态。按需检索，不默认进 context。
- **原始日志**：只做回溯和审计，永不注入。

**2. 写入分显式和隐式两条路。** 用户明说“记住这个”的直接写；隐式抽取放在会话结束时跑一次小模型，输出偏好候选，再过规则：带时间限定词的（“今天先用英文写”）、置信度低的，进日志不进画像。

**3. 读取做混合检索。** 关键词命中 + 向量相似度，取 top 3~5 注入当前上下文，并注明“以下为历史偏好，仅供参考”。阈值宁高勿低——检索不到好过检索错。

**4. 更新要有冲突处理。** 新条目写入前先和旧条目做相似度匹配，语义冲突就以新覆旧，旧条目标记 `superseded` 而不是删除；每周跑一次合并去重。

**5. 用 MCP 暴露成工具。** `memory_search / memory_write / memory_update` 三个工具挂到 MCP 上，CLI、web、其他 Agent 走同一套记忆，避免多端各存一份、各说各话。

## 踩坑点

- **全量注入**：三百条记忆塞 system prompt，注意力被稀释，Agent 开始“幻觉”出你从没说过的偏好。核心层必须卡条数。
- **只写不读**：我们早期测试检索命中率只有四成左右，等于白记。上线前先测读路径，别只测写入。
- **临时请求固化为永久偏好**：“今天用英文” ≠ “以后都用英文”。抽取 prompt 里要强制判断时间限定词。
- **缺来源和时间戳**：三个月后你无法判断一条记忆还能不能信。
- **多端并发写**：last-write-wins 会静默丢更新，至少把冲突记进日志。

## 可复用建议

1. **先朴素后高级**：纯文件 + 关键词匹配跑两周，收集 miss 案例再决定要不要上向量库。一千条以内，关键词往往够用。
2. **建 20 条回归用例**：偏好问答对，每次改检索逻辑跑一遍，防止“优化”把老场景改坏。
3. **给用户一个 forget 入口**：既是隐私刚需，也是最好的调试工具。
4. **条目不可变 + 状态机**（active / superseded / expired），比原地改写好排查得多。

## 总结

记忆系统的功夫不在存储而在治理：分层控制 token 预算、写入有门槛、读取有阈值、更新有冲突处理。别一上来就搞向量数据库，先跑通最小闭环——一个核心画像文件、一个检索工具、一套回归用例，两周迭代一轮，比一次性设计大而全的方案靠谱得多。
