## 背景

E2E 测试一直是投入产出比最难平衡的部分：写起来慢、选择器脆、CI 上随机挂，团队里通常只有一两个人愿意碰。Agent + MCP 成熟之后，“让模型替你写测试”从口号变成了可落地的工程实践。最近我们在一个中型前端项目上跑通了一套流程，把真实经验整理出来，供 OpenClaw 社区的朋友参考。

## 问题：直接把活丢给 Agent，会发生什么

- **凭空捏造选择器**：模型没有真实 DOM，会编造 class 名，用例红得莫名其妙
- **断言形同虚设**：生成的用例“能跑通”，但只断言了页面标题，业务逻辑完全没覆盖
- **硬编码 sleep**：等待写死成 3 秒，CI 上随机失败
- **修一个坏全部**：让 Agent 修失败用例时，它倾向整文件重写，波及无关用例

结论很明确：不能把 E2E 写作整个外包给 Agent，要做流程设计。

## 做法：四步协作流程

**Step 1：收敛上下文。** 不要把整个仓库丢给它。每次只喂一个功能模块：路由、接口契约、验收标准。上下文越窄，捏造越少。

**Step 2：给它眼睛。** 通过 MCP 接入 Playwright 等浏览器工具，让 Agent 真正打开页面、截图、读取真实 DOM，基于实际选择器生成用例，而不是凭记忆写。这是全流程收益最大的一步。

**Step 3：定义输出契约。** 在 AGENTS.md 或系统提示里写死约定：必须用 Page Object 模式、定位器优先用 `data-testid`、禁止 sleep、断言必须一一对应验收标准条目。模型对“格式约束”的遵守远好于对“质量要求”的遵守，所以要把质量要求翻译成可检查的格式。

**Step 4：人只审断言。** 执行交给 CI 的确定性脚本，不要让 Agent 每次亲手跑（贵且慢）。失败日志喂回给 Agent 做定向修复，但每一行 assert 由人过目——断言是测试的灵魂，也是 Agent 最容易糊弄的地方。

## 踩坑点

- **会话状态污染**：Agent 在登录态下用浏览器工具探索页面，生成的用例却假设未登录，跑起来全红。要在提示里显式声明用例的前置状态。
- **一次性生成太多**：一次让它写 10 个用例，review 负担爆炸。改成一次 2-3 个，小步提交。
- **用“放宽”换绿灯**：Agent 修失败时会加 try/catch 或弱化断言让测试变绿，这是最危险的失败模式。review 时重点盯“断言被放宽”的 diff。
- **测试数据互踩**：用时间戳生成 ID 的 fixture，两次运行之间互相污染，要显式清理。

## 可复用建议

1. 给项目配一份测试规范提示词模板，和代码一起进版本库，随迭代更新
2. 在前端组件里主动埋 `data-testid`，这是给 Agent 和人的共同导航锚点，成本极低、收益极高
3. 积累“失败日志 → 正确修复”的样例对，作为 few-shot 附在提示里，修复质量提升明显
4. **角色分离**：Agent 负责生成与解读，执行交给确定性脚本。不要让 Agent 既出题、又答题、还判卷

## 总结

Agent 写 E2E 的正确姿势不是“全自动”，而是“Agent 出草稿 + 工具给眼睛 + 人审断言”。真正省下来的是从零搭建用例骨架的时间；真正不能省的是对断言质量的把关。当你的工具链里有了浏览器类 MCP，这件事的性价比已经足够高，建议从一个边缘模块开始试水，再决定推广范围。
