## 背景

OpenClaw 的 workspace 里有几个约定俗成的文件：AGENTS.md 管"怎么干活"，SOUL.md 管"什么性格"，MEMORY.md 管"发生过什么"。但跑起来之后最先暴露的短板，是 Agent 不知道"对面这个人是谁"。

每次冷启动，模型上下文里只有系统提示和这几个文件。你叫什么、在哪个时区、什么技术栈、讨厌什么样的回复——这些不写下来，Agent 只能猜。猜错的成本，是每次对话开头都要重新自我介绍一遍。

## 问题

不写 USER.md 时最常见的三种症状：

1. **重复交代**。"我是做后端的，别解释什么是 JWT"说了三遍，第四遍 Agent 还在给你科普。
2. **错误假设**。默认按美东时区排提醒、默认堆英文术语、默认你单人开发——它没有信息来源，只能拿训练数据里的"典型用户"套你。
3. **职责混淆**。什么都塞 MEMORY.md，事件流水和长期画像搅在一起，检索时信噪比很低。

分清楚一件事就够了：MEMORY.md 记"事"，USER.md 记"人"。这个边界定了，问题解决一半。

## 做法

USER.md 建议按**稳定事实**组织，控制在 1–2KB 以内：

```markdown
# User
- 身份：后端工程师，主语言 Go / Python
- 环境：UTC+8，MacBook + 一台 Linux 服务器
- 沟通偏好：结论先行，可以假设我懂基础概念
- 禁忌：不推荐付费服务，不用 emoji
- 长期上下文：在维护 X 项目的开源分支
- 常用联系人：只写关系和称呼，不写隐私细节
```

分工建议这样定：

1. **人写骨架**：首次创建自己填，只写"半年内不会变"的条目。
2. **Agent 追加**：在 AGENTS.md 里明确授权——"对话中确认到用户的稳定新事实（新设备、新偏好、新项目）时，向 USER.md 追加一行"。
3. **人审校**：Agent 只追加，删除和改写保留给人；每周 git diff 一遍。

第三步是关键。把 workspace 纳入 git，Agent 的每次自我发挥都有据可查。

## 踩坑点

- **写成日记**。放任 Agent 自由更新，两周后 USER.md 就膨胀成流水账，每轮白耗 token。"只记稳定事实"要写进 AGENTS.md，不能靠口头约定。
- **敏感信息明文入库**。USER.md 全文注入每次会话，密钥、详细住址写进去等于每轮都发给模型 API。判断标准：你愿不愿意把它贴在团队 wiki 上。
- **和 SOUL.md 打架**。"称呼我为老王"是 USER.md 的事，"回复简洁、带点冷幽默"是 SOUL.md 的事。同一件事写两处，改的时候必漏一处。
- **事实过期**。换了工作、换了主力语言，Agent 还按旧画像行事，而且它自己意识不到。没有审校机制，USER.md 会从资产变成负资产。

## 可复用建议

- 把上面模板做进 workspace 初始化脚本，新环境一键生成。
- 在 AGENTS.md 写清三件事：定位（稳定事实）、更新规则（仅追加）、审校节奏（人定期处理）。
- 长度红线 1–2KB，超了说明混进了本该属于 MEMORY.md 的内容。
- 生活和工作分开跑两个 workspace，两份 USER.md 各管各的场景，避免画像互相污染。

## 总结

USER.md 本质上是一份**人工确认过、注入每轮上下文的用户画像**。它不炫技，价值全在纪律上：写稳定的事、只追加不覆盖、定期审、控制体积。Agent 没有内置的长期自我，记不住你很正常；但一份维护得当的 USER.md，能把"每次从零开始"变成"每次都站在正确的假设上"。这大概是目前性价比最高的一处 prompt 工程投入。
