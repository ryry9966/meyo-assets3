## 背景：自动化任务一定会被重复执行

跑过一段时间 OpenClaw 自动化的人基本都遇到过：cron 触发器在网关重启后补跑了一次；webhook 因超时被上游重发；agent 执行到一半崩溃，恢复机制把任务重新拉起。这些不是异常路径，而是常态。只要自动化依赖网络和进程存活，执行语义就是"至少一次"（at-least-once），重复执行是设计时就必须假设的前提。

## 问题：副作用不可重复

读取类操作天然幂等，重复执行无害。真正出问题的是带副作用的操作：

- 通知任务重试后，群里发了两条相同的日报；
- 调用 MCP 工具创建工单，超时后 agent 重试，远端出现两个重复资源；
- 向文件或数据库追加数据，崩溃恢复后同一批数据写了两遍。

关键是意识到：**超时不等于失败**。请求可能已经到达远端并生效，只是响应没回来。如果重试逻辑只看"上一次有没有报错"，就会在"已成功但不知情"的状态下再执行一次。

## 做法：让第二次执行天然安全

1. **先分类。** 把任务里的操作分成"读 / 按固定键写入 / 按 ID 删除"这类天然幂等的，和"追加 / 创建 / 发送 / 自增"这类不幂等的，后者单独处理。
2. **用稳定的幂等键。** 键从"触发源 + 计划执行时间 + 任务名"派生，例如 `hash(cron 表达式 + scheduled_time + task_id)`，而不是每次重试随机生成 UUID。核心要求：同一次逻辑执行的所有重试，键必须相同。
3. **先记账，再执行。** 用本地 SQLite 或 JSON 记录幂等键与状态：执行前查记录，已存在且成功则跳过；更稳的做法是用 `INSERT OR IGNORE` 抢占唯一键，天然防并发。
4. **给工具传显式键。** 自己写 MCP server 时，接受客户端传来的 request id 并做去重；调用不支持去重的第三方工具时，在外面套一层"先查远端状态，已存在则跳过"。
5. **写操作尽量用 set 语义。** 固定文件名覆盖写、upsert 替代 insert，把"执行 N 次"变成"确保状态 X"。

## 踩坑点

- **用 now() 当键。** cron 09:00 触发，09:00:03 的重试生成了不同的键，幂等失效。键必须用计划时间，不用当前时间。
- **只在成功后记账。** 副作用已生效、进程在写记录前崩溃，下次照样重复。不确定时应反查远端实际状态作为事实来源。
- **多层重试、键不一致。** 插件内部重试用一套键，agent 层重试又用一套，等于没有幂等。键要在最外层生成并逐层透传。
- **并发窗口。** 两个 agent 实例同时通过"记录不存在"的检查然后都执行。查和写必须原子，靠唯一约束或锁兜底。
- **记录窗口太短。** 去重记录的保留时间要覆盖最大重试跨度，设成几分钟就过期基本没用。

## 可复用建议

- 写一个通用的 `withIdempotency(key, fn)` 包装器，所有带副作用的定时任务走同一入口，日志带上键方便排查。
- 把任务描述成目标状态（"确保每天 9 点群里只有一份日报"）而不是动作（"发日报"），agent 更容易自我校验。
- 主动测幂等：手动连跑两次任务；在副作用生效后人为注入一次超时，验证第二次执行不会产生重复效果。
- 定期审计哪些插件和工具在"无键裸奔"，优先给它们补上。

## 总结

重试不是要消灭的异常，而是自动化的固有属性。幂等性的本质是承认"第二次执行一定会发生"，然后让它变得无害。成本其实很低：一个稳定键、一张本地记录表、一套 set 语义的写习惯，就能把"至少一次"的执行模型变成可以放心依赖的东西。下次写自动化任务时，先问自己一句：这段代码被连续跑两遍，会发生什么？
