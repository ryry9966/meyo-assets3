## 背景

在自动化系统里，重试不是异常，而是常态：调度器超时会重跑任务；Agent 规划失败会重新推理再执行；webhook 送达失败会按退避策略重投；MCP 工具调用超时后，客户端根本无法确定服务端到底执行了没有。这些场景的共同点是：你控制不了"执行几次"，只能控制"执行多次之后，结果是否正确"。这就是幂等性要解决的问题——同一个操作执行一次和执行 N 次，系统终态一致。

## 问题

非幂等的操作平时看不出毛病，故障时才暴露：

- "创建工单"的任务重跑一次，出现两张重复工单；
- 统计脚本用 `INSERT` 写结果表，重跑后数据翻倍；
- 通知插件重试，用户收到两条一样的消息；
- Agent 调用下单类工具，超时重试导致重复下单。

这类 bug 的麻烦在于难以复现：它只在"恰好发生了一次重试"时出现。

## 做法

先把任务分成两类，分别处理。

**天然幂等的操作，尽量改写成这种形式：**

- 按 key 覆盖状态（upsert / set desired state），而不是 append；
- 带唯一约束的插入：`INSERT ... ON CONFLICT DO NOTHING`；
- 条件更新：`UPDATE ... WHERE status = 'pending'`；
- 按条件删除，而不是按计数删除。

**非幂等的外部副作用（发消息、建单、下单），加一层去重：**

1. 生成稳定的幂等键：由任务标识 + 输入规范化哈希 + 时间窗口组成，例如 `daily-report:{date}:{hash(params)}`。关键是稳定——同一逻辑执行必须得到同一个键。
2. 执行前查记录表：键存在且状态为 succeeded，直接返回上次结果；状态为 running，说明有并发在跑，直接退出。
3. 先落记录再执行副作用，成功后更新状态并记录外部 ID（消息 ID、工单号等）。
4. 并发兜底靠存储层的唯一约束，而不是应用层的 if 判断——两个进程同时通过检查是常态。

另一个思路是把任务写成"对账式"：每次执行先读实际状态，与期望状态对比，有差异才动作。收敛型任务天然幂等，Agent 的环境管理、配置下发都适合这个模式。

## 踩坑点

- **幂等键不稳定**：键里混入时间戳、随机 UUID 或未排序的 JSON 字段，每次重试键都不同，去重形同虚设。哈希前先做规范化：字段排序、时间截断到窗口。
- **键的粒度失衡**：粒度太粗，合法的第二次执行（比如修复数据后重跑日报）会被误杀；粒度太细等于没去重。常见解法是在键里加版本号或触发原因。
- **"已执行"不等于"执行成功"**：第一次执行其实失败了，但记录表已标 succeeded，重试被跳过，任务永远停在半成品。状态更新必须紧跟在副作用确认成功之后。
- **并发竞态**：只有应用层 check-then-act、没有存储层唯一约束，两个 worker 同时跑，照样出双份。
- **下游不支持幂等**：有些第三方 API 没有幂等键机制，这层去重必须做在自己这边，且要持久化——内存去重扛不住进程重启。

## 可复用建议

- 给插件和 MCP 工具封装统一的去重中间件：算键、查表、放行或短路，业务代码不感知。
- 每个定时任务写一条 run 记录，状态机至少包含 pending / running / succeeded / failed，排障先看这张表。
- 把幂等键打进日志。排查"为什么执行了两次"或"为什么没执行"时，它是第一线索。
- 写一个回归用例：同一任务连跑两遍，断言第二次被短路且终态不变，放进 CI。幂等性被改坏时能立刻发现。

## 总结

幂等性不是为了让系统不重试，而是让重试变得免费。在自动化和 Agent 场景里，重试由框架、网络、模型共同决定，次数不可控；唯一可控的，是把每一步设计成"再来一次也无妨"。先分类操作、再定稳定的幂等键、最后用存储层约束兜底——这三步做完，大部分重复执行的故障会从"事故"降级成日志里的一行短路记录。
