## 背景

在 OpenClaw 的日常使用里，“同一个任务被执行多次”不是边缘情况，而是常态：

- 定时任务超时后被调度器重跑；
- Agent 规划失败后重新规划，可能再次调用同一个 MCP 工具；
- Webhook 源端按 at-least-once 语义投递，同一事件可能到达两次；
- 用户手动重跑某个流程，而上次其实已经成功了一半。

关键在于：网络超时不代表失败，操作很可能已经生效，只是响应没传回来。只要自动化系统允许重试——而它必须允许——幂等性就不是可选项，而是前提。

## 问题

非幂等操作的典型事故形态：

- 往群里发通知，重试后发了两条；
- 插件往配置文件里 append 一段，重跑后配置重复；
- “创建工单”类工具被 Agent 二次规划又调了一遍，产生重复工单；
- 对接外部系统的扣减类操作，因重试被执行两次。

共同点只有一个：操作的效果和执行次数相关。而自动化的可靠性，恰恰建立在“执行次数不可控”之上。

## 做法

按成本从低到高，几个可落地的层次：

**1. 区分读写。** 纯读取天然幂等，不用处理。重点审查所有写操作：写文件、写库、发消息、调外部 API。

**2. 确定性业务键 + upsert。** 不要用随机 UUID 做主键，用“事件 ID”“任务 ID + 日期”这类跨重试稳定的键，写库时配合唯一约束：

```sql
INSERT INTO task_result (event_id, result)
VALUES (:event_id, :result)
ON CONFLICT (event_id) DO NOTHING;
```

重复执行自动收敛为一次生效。

**3. 先查后做，但要防并发。** 执行前查状态（“这个事件处理过吗”）能挡住大部分重复，但两个并发实例可能同时通过检查。关键路径用唯一索引或原子操作兜底，不要只依赖 check-then-act。

**4. 外部副作用记去重表。** 发消息、调第三方 API 这类数据库约束保护不到的操作，在本地记一条“已处理 ID”，执行前先查。配 TTL 定期清理，否则表只增不减。

**5. 面向状态而非面向动作。** 把“追加一条记录”改成“把状态设置为目标值”。声明式写法天然幂等，重复执行只是重复设置同一个状态。

## 踩坑点

- **键在重试路径上不稳定。** 如果幂等键由 LLM 生成的字段拼接而成，每次重试内容可能不同，去重直接失效。键必须来自确定性输入：事件 ID、任务 ID、业务时间窗。
- **多层重试没对齐。** Agent 层、MCP client 层、调度器层各自重试，幂等键只在某一层生成，其他层感知不到。键要在最外层确定并一路透传。
- **去重记录和业务操作不一致。** 记了“已处理”但操作失败，或反过来。理想是放进同一个事务；做不到就接受“可能重复调用”，把幂等收敛到接收端。
- **只测了单次成功路径。** 幂等必须在测试中显式验证：同一任务连跑两次，断言副作用只有一份。

## 可复用建议

- 新写插件 / skill 时默认 upsert，并在文档里注明幂等策略；
- MCP 工具返回值带上“本次是否新执行”，让 Agent 能区分“我做的”和“已经做好了”；
- 对真实扣款这类难以幂等的操作，不要在 Agent 层解决，收敛到一个幂等的接收端；
- 重试策略和幂等策略一起设计，单独谈重试没有意义。

## 总结

自动化的投递语义通常只能是 at-least-once，幂等性就是把它变成“效果上恰好一次”的那一半工作。它不是工程洁癖，而是你敢让调度器自动重试、敢让 Agent 自主规划的前提。下次写自动化任务时，先问一句：这个操作跑两遍，结果一样吗？
