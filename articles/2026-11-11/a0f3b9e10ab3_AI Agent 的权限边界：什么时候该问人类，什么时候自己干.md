Agent 一旦接上 MCP、插件和 shell，能力上就没有天然上限了。此时真正的工程问题不是"它能不能做"，而是"哪些事该自己做，哪些事必须先问人"。在 OpenClaw 这类常驻 agent 上尤其突出：它跑在你自己的机器上，连着消息渠道和定时任务，一次错误操作的代价是真实的。

实际使用中会碰到两种失败模式：

- **事事都问**。读个文件也要确认，很快产生审批疲劳——人开始无脑点同意，门形同虚设，比不设门还危险。
- **事事自干**。删目录、往群里发消息、调付费 API，这类操作错了没有回滚键，坏的是数据和信任。

## 做法：三个维度，四级分层

判断一个动作该不该自动执行，看三个维度：**可逆性**（能不能撤销）、**影响半径**（只碰本地工作区，还是触达外部世界）、**错误成本**（搞砸了损失多少钱和数据）。据此分成四级：

| 级别 | 动作特征 | 例子 | 策略 |
|---|---|---|---|
| L0 | 只读、本地 | 读文件、搜索、查询 | 自动执行 |
| L1 | 本地写入、可回滚 | 改工作区文件、跑测试 | 自动执行 + 全量留痕 |
| L2 | 有外部副作用 | 发消息、写共享仓库、调付费接口 | 先出计划，批量确认 |
| L3 | 不可逆或高代价 | 删数据、付款、改生产配置 | 硬门禁，必须人工确认 |

关键工程点：**策略落在工具层，不要只写在提示词里**。提示词是软约束，长会话压缩后规则会漂移；工具层的白名单校验是硬约束，模型绕不过去。

落地五步：

1. 给每个工具/技能标注等级，形成权限矩阵，放进仓库跟代码一起 review；
2. 外部副作用默认拒绝，白名单放行；
3. 确认消息必须带预览——完整命令、diff、目标渠道，杜绝盲批；
4. L2 用"先给方案、一次批一批"代替逐条询问；
5. 自动执行的动作全部落日志，出问题能回溯。

## 踩坑点

- **审批疲劳**：问得太碎，人就会闭眼通过，确认机制反而降低了安全性；
- **无上下文确认**："我可以执行吗？"这种不带内容的询问等于盲批；
- **按置信度决定是否提问**不可靠：模型普遍过度自信，错的时候它自己并不知道；
- **临时提权变永久**：调试时开的口子，用完忘了收；
- **演练缺失**：从没测过工具报错时，agent 是停下来上报还是硬着头皮重试。

## 可复用建议

- 新工具上线先按最高级别管两天，观察行为再逐级放开；
- 确认交互固定三选项：确认执行 / 取消 / 让我改方案，别让人只能点头；
- 定期做故障演练：故意让工具返回错误和异常值，验证 agent 的止损行为；
- 权限矩阵随代码演进，新增能力先评审再加白名单。

## 总结

权限边界本质上不是"信不信任模型"的问题，而是**错误成本的分布**问题：可逆且影响小的动作让 agent 自己跑，不可逆或触达外部的动作设硬门禁。判断标准写进配置而不是提示词，审批带上下文，日志全量留痕。这样 agent 才能快得起，也错得起。
