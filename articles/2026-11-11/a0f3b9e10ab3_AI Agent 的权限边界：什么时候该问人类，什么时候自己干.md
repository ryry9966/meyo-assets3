## 背景

Agent 接上 MCP 和插件之后，能做的事从"回答问题"变成了"动手改世界"：读写文件、调内部 API、发消息、跑 shell。能力上去了，但很多团队的授权模型还停留在两个极端——要么全放行，要么每步都问。这篇文章记录我们在 OpenClaw 实践里沉淀的一套分级方法，核心问题只有一个：哪些动作 agent 可以自己做，哪些必须停下来问人。

## 问题：两种失败模式

- **过度询问**：agent 每写一个文件都要确认。人被问烦之后开始无脑点"同意"，确认机制退化成仪式，反而更危险。
- **过度自主**：agent 在一次长任务里自己执行了 `rm -rf`、force push，或者给真实用户群发了消息。事后排查发现每一步单看都"合理"，连起来是事故。

两种失败的本质相同：**授权粒度和动作的实际风险不匹配**。

## 做法：按"爆炸半径"分级

### 1. 盘点所有出口

列出 agent 的全部执行面：每个 MCP server 暴露的 tool、shell 权限、网络出口、插件回调。这一步最容易被跳过，但盘不清楚就分不了级。MCP 的 tool annotation（如 `readOnlyHint`）可以当初始输入，但不能全信，要人工过一遍。

### 2. 三级分类

- **L0 只读**：查询、搜索、读文件。直接放行，不问。
- **L1 可逆写**：工作区内写文件、建分支、本地 dry-run。放行 + 全量日志，可审计可回滚。
- **L2 不可逆 / 外部可见**：删数据、force push、给真人发消息、花钱、动生产环境。必须确认。

判断标准就四条：**可逆吗、影响范围多大、花不花钱、谁能看到**。任意一条命中 L2，就升级。

### 3. 落地机制

- 在网关层做策略，而不是靠 prompt 里写"请谨慎"。prompt 是建议，策略是硬约束。
- L2 确认时给足上下文：展示 diff、目标地址、影响范围，让人能在 10 秒内做出有效判断，而不是回答一句"可以继续吗"。
- 新接入的 MCP server 默认归入 L2，观察一段时间再降级。
- 关键操作落审计日志：谁、何时、哪个 tool、参数是什么。

## 踩坑点

1. **确认疲劳**。L2 清单越长，人越容易变成盖章机器。经验是 L2 只保留少数高频入口，宁可 L1 多打日志。
2. **二段式绕过**。agent 把一个 L2 动作拆成多个 L1 步骤绕过确认（先创建、再合并、再删除）。策略要按最终效果判断，不能只看单个 tool 名。
3. **上下文漂移**。会话开始时任务清晰，中途目标变了，授权范围没跟着变。长任务里要定期把"当前到底在做什么"重新对齐。
4. **重试自动放行**。失败重试时不要沿用上次的授权，尤其是有外部副作用的操作。
5. **批量确认**。一次问十个动作，人根本看不完。要么拆开问，要么降级执行。

## 可复用建议

- 用一句团队共识对齐："**读自动，写留痕，删和对外必问人。**"
- 每接一个新插件或 MCP server，先回答四个问题：可逆？影响范围？花钱？外部可见？
- 确认弹窗的质量比数量重要，一次有效确认胜过十次机械同意。
- 每季度重过一遍 L2 清单，agent 能力扩张到哪，边界就同步收紧到哪。

## 总结

权限边界不是"信不信任 agent"的表态题，而是把风险翻译成可执行策略的工程题。爆炸半径是比"这个动作看起来危不危险"稳定得多的度量。先把出口盘清楚，再分级，再落到网关层硬约束，最后用日志兜底。做到这几步，agent 的自主性和安全性基本可以兼得。
