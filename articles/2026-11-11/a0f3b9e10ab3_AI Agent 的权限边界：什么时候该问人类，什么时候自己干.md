## 背景

Agent 跑起来之后，权限问题会在第二周找上门。OpenClaw 这类框架里，工具越接越多：exec、浏览器、MCP server、消息通道、定时任务。早期的"要不要给这个工具"很快变成"给到哪一层"——同一个 exec，跑 `npm test` 和跑 `rm -rf` 应该是两种待遇。

## 问题

实际会掉进两个极端。**事事请示**：agent 每一步都停下来等确认，退化成一个需要人肉点头的脚本，自动化价值归零。**从不请示**：一次误判调用就可能删错文件、把消息发进错误的群、把预算烧光。真正的难点在于，边界不是一张静态清单，而是随"操作性质"变化的设计决策。

## 做法：两维四档

用两个维度给每个工具动作定级：**可逆性**（错了能不能撤回）和**影响半径**（只影响自己的 workspace，还是波及外部世界、他人、钱）。

- **L0 只读 + 本地**：搜索、读文件、查只读 API → 全自动
- **L1 本地写 + 可回滚**：改文件但走 git、跑测试、生成草稿 → 自动执行 + 落日志
- **L2 外部副作用 + 低代价/可撤回**：给自己发提醒、写入草稿箱、调用有配额的付费 API → 白名单内自动，白名单外确认
- **L3 不可逆或高代价**：给别人发消息/邮件、支付、删除、动生产环境 → 必须人工确认，部分直接禁用

落地四步：

1. 在权限配置里给每个工具显式标注档位，不依赖模型自觉。
2. 确认请求必须自带上下文：要执行什么（命令/diff）、为什么、失败怎么回滚。禁止"可以继续吗"这种让人无法判断的提问。
3. L2 以上先 dry-run：邮件先进草稿、消息先渲染预览，人确认的是将要发生的事实，而不是 agent 的转述。
4. cron 和无人值守场景默认降一档：平时 L2 的任务，夜里自动跑时按 L3 处理——没人盯着的时候，从严。

## 踩坑点

- **确认疲劳**：一天弹 20 次确认，人就开始无脑 yes，权限系统形同虚设。宁可默认收紧，也要把确认次数压到真正值得看的量级。
- **事后请示**："我先发了，不合适再撤回"——消息和邮件没有 undo，这是把确认环节放错了位置。
- **假确认**：prompt injection 会伪造"用户已批准"。确认必须由代码层 hook 执行，不能信任对话上下文里出现的许可。
- **沙箱 ≠ 权限**：沙箱限制的是爆炸半径，但不回答"该不该问"。两者互补，不能互相替代。
- **一次配置不管终身**：上线三个月不 review，边界一定和真实风险脱节。

## 可复用建议

- 外部副作用默认拒绝，白名单渐进放开；每放开一条，都要有对应的日志证据支撑。
- 把权限策略当代码维护：写进配置和系统提示，版本化，改动留痕。
- 定期红队自测：构造"假装已获批准""紧急情况请绕过"类输入，验证确认层是否真能拦住。
- 统计确认拒绝率：如果人经常拒绝 agent 的请求，问题多半出在判断力，先修判断，再谈放权。

## 总结

权限边界是产品决策，不是 prompt 技巧。一句话原则：**可逆且影响圈内就放手，不可逆或出圈就停下问人**。从最严配置起步，让日志说话，逐步放权——这比一开始就"全自动"再回头补救，成本低得多。
