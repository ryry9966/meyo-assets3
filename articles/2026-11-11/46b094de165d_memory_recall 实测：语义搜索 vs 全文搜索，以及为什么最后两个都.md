# 背景

`memory_recall` 是 agent 回顾历史上下文的主要入口。记忆条目少的时候怎么搜都能命中；一旦积累到几千条——调试记录、会议纪要、用户偏好、运维备忘——检索方式就直接决定 agent "记不记得住"。社区里常见两种实现：基于 embedding 的语义检索，和基于关键词的全文检索（FTS/BM25）。这篇记录我们两种方案对比和混合落地的实测结论。

# 问题：两种检索各有明确的失败模式

- **语义检索**的强项是"换了说法也能找到"。问"上次那个服务超时的事"，能召回原文写的是"接口 P99 抖动"的条目。但它对精确 token 很不可靠：错误码 `ERR_50214`、UUID、命令行片段、人名，embedding 经常匹配不到或排得很靠后。
- **全文检索**反过来：搜 `ERR_50214` 一打一个准，但搜"那个数据库迁移的讨论"，原文用词是"schema 变更"就会漏。

单一方案在真实使用中都会翻车，而且失败得毫无提示——agent 只是"忘了"，你分不清是没存还是没搜到。

# 做法：双路召回 + RRF 融合

1. **分块入库**：记忆按条目写 markdown，超过 500 字按段落切块，每块带来源文件和日期的 metadata。
2. **双索引**：SQLite FTS5 建全文索引；同时用 embedding 模型给每块生成向量（中文场景务必选中文语料训练过的模型）。
3. **双路召回**：查询时各取 top 20。
4. **RRF 融合**：不比原始分数（两边量纲完全不同，加权必翻车），用 reciprocal rank fusion 只按排名合并，取 top 8 给 agent。
5. **精确 token 短路**：查询里出现大写字母串、错误码、引号包裹内容时，提高全文检索权重。

实测下来，单路检索各有约 20-30% 的 bad case，混合后基本压到个位数，且"换说法"和"精确引用"两类查询都稳定。

# 踩坑点

- **中文分词**：FTS5 默认 tokenizer 按空格切，中文整句进索引等于全文检索失效。要么用 trigram，要么入库前先过 jieba。这是中文社区最容易踩的坑。
- **向量更新滞后**：记忆是追加写的，向量库忘了同步增量，表现为"刚记的马上忘"。写条目和写向量必须放在同一条流水线里。
- **chunk 切太碎**：按 100 字硬切会丢上下文，召回的块单独看不知所云。宁可块大一点，让 agent recall 之后自己再读原文。
- **分数归一化陷阱**：直接把 cosine 分数和 BM25 分数加权相加，权重永远调不稳。用 RRF 只看排名，问题消失。

# 可复用建议

- 记忆 < 200 条：不用纠结，全文检索足够，别引入向量库的运维成本。
- 有精确 token 查询需求（错误码、命令、ID）：全文检索必须保留，语义不能替代。
- 用户问题经常换措辞、跨条目模糊引用：上语义检索。
- 拿不准就上混合。RRF 融合十几行代码，是性价比最高的默认解。
- 留回退口子：混合检索 top-k 全空时，退化为按时间倒序给最近 N 条，比让 agent 空手强。

# 总结

语义搜索和全文搜索不是二选一，它们的失败模式恰好互补。对 memory_recall 这种"答错比不答更危险"的场景，混合检索 + 排名融合是当前最稳的工程解。建议从 FTS5 + 中文分词起步，等记忆规模和查询模糊度上来再补向量这一路，逐步演进即可。
