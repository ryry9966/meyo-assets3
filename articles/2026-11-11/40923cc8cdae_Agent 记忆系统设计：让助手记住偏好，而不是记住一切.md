## 背景

大模型本身是无状态的。每次会话开始，Agent 对用户一无所知：你用 Go 不用 Python、喜欢先给结论、时区东八区——都得重说一遍。上下文窗口再大也不等于"记得住"。对做 OpenClaw 插件和 MCP 工具的人而言，记忆系统是从"能用的 demo"到"日常依赖的助手"之间绕不开的一环。

## 问题

实践中最常见的三种失败模式：

1. **什么都记**：对话原文和琐碎片段全进向量库，检索回来的全是噪音，反而稀释了关键偏好。
2. **写死在系统提示词里**：用户换语言、换习惯后没人更新，三个月后助手还在推已废弃的方案。
3. **记了不会用**：存了向量但注入策略混乱，要么全量灌入撑爆 token，要么从不触发检索。

## 做法：三层结构 + 读写分离

**第一层：结构化画像（固定注入）。** 一个小的 key-value 文件：编程语言、回复风格、时区、常用工具链。每轮会话固定注入，控制在 200 token 内。这一层覆盖 80% 的个性化需求，成本几乎为零。

**第二层：语义记忆（按需检索）。** 事实和上下文片段进向量库，只对首条用户消息检索一次，注入上限 800 token，每条记忆必须带来源会话 ID。

**第三层：会话摘要（归档）。** 会话结束后由便宜模型异步跑一次抽取："这轮有没有值得长期记住的事？"输出严格 schema：内容、类型、置信度、来源、时间戳，低于阈值不入库。

写路径的关键是**覆盖而非追加**：新记忆与旧条目冲突时（比如从 Python 转向 Go），走 supersede 流程，旧条目标记废弃但保留溯源。读路径上，建议把记忆做成 MCP 显式工具（memory_search / memory_write / memory_forget），让 Agent 自己决定何时调用；用户说"我不用 Python 了"时走显式修正，优先级最高。

## 踩坑点

- **抽取太勤**：默认每轮都写，两周后一半是废话。改成"抽取模型给出明确理由才写"。
- **向量相似 ≠ 相关**："喜欢简洁回复"会召回一堆含"简洁"的无关片段。结构化偏好坚决不进向量库。
- **记忆是注入面**：记忆内容本质是不可信数据，注入时必须包裹边界，防止覆盖系统指令。
- **没有衰减**：加 last_used_at 和时间衰减权重，半年没命中的进冷存储。
- **忘了做遗忘**：memory_forget 必须是真删除，并给用户一个能查看、编辑全部记忆的入口——既是隐私要求，也是调试刚需。

## 可复用建议

1. 先做结构化画像文件，再上向量库。很多团队一上来就做 RAG 式记忆，最缺的反而是画像层。
2. 每条记忆七字段缺一不可：content / type / source / created_at / last_used_at / confidence / status。
3. 注入要有 token 预算，并记录"注入了什么、回复是否用到"，离线评估后再调参。
4. 抽取用便宜模型异步跑，别占主 Agent 循环。

## 总结

记忆系统本质是数据工程问题，不是提示词问题：分层、带元数据、有生命周期、可被用户审计。先让画像层跑起来，再补检索和衰减，比一步到位的大而全方案靠谱得多。欢迎在评论区交流你们社区的实现差异。
