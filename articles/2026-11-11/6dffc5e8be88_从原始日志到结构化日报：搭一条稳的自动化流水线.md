## 背景

我们小组的日常大概长这样：git 提交、CI 流水线、服务器告警，再加上 OpenClaw 的会话日志，散落在四五个地方。以前日报靠人肉翻日志，写出来的东西时好时坏，忙起来直接断更。

这篇帖记录我用 OpenClaw 定时任务 + 一个 Agent 搭的日报流水线：每天早上把前一天的原始日志收敛成结构化报告，推到群里。核心思路一句话：**结构化交给确定性脚本，叙事交给模型**。

## 问题

直接把原始日志丢给模型"总结一下"，有三个硬伤：

1. **上下文撑不住**：一天的 debug 日志轻松几十万行，塞进去要么爆窗口，要么大量 token 花在无关行上。
2. **幻觉不可控**：模型会"脑补"日志里没有的结论，日报一旦出错，别人会当真。
3. **格式漂移**：每次生成的段落结构都不一样，没法对比、没法归档。

## 做法

流水线分四段，每段是独立小脚本，可单独跑、单独测：

**1. 采集**：一个 bash 脚本拉取各来源日志，统一落到 `snapshots/YYYY-MM-DD/`，每类来源一个 JSONL 文件。

**2. 归一化**：纯 Python，不涉及模型。做过滤、去重、聚合计数——错误按类型聚合、提交按仓库分组，只保留 Top N 和异常项，输出一份固定 schema 的 JSON 快照。这一步是整条流水线的地基。

**3. 总结**：OpenClaw 定时任务触发 Agent，通过文件读取工具拿到第 2 步的 JSON 快照（不是原始日志），按严格模板生成 Markdown 叙述：昨天做了什么、哪里出了问题、今天要盯什么。模板里每个 section 都要求有对应的数据字段。

**4. 投递**：Agent 调渠道插件发到群里，成品和快照同时归档。

关键设计：**脚本和 Agent 之间只通过固定 schema 的 JSON 通信**。schema 就是契约，模型只做"把数字讲成人话"这一件事。

## 踩坑点

- **时区坑**：cron 默认 UTC，"今天"的边界和本地差 8 小时，日报会把两个半天拼在一起。后来改成外部显式传日期参数，脚本内部不算时间。
- **静默失败**：最阴险的问题。采集脚本挂了，Agent 拿到空数据，照样生成一份"平安无事"的日报。现在强制：数据为空就发告警而不是日报；流水线自身的运行耗时和失败次数写进日报页脚。
- **格式漂移**：即使给了模板，模型偶尔还是漏 section。加校验步骤：生成后检查必需字段，缺了就带错误信息重试一次，再失败降级为告警。
- **敏感信息**：日志里偶尔混着 token 和内网地址。归一化阶段统一 scrub，别指望模型替你把关。

## 可复用建议

1. 先手动跑通一周再挂定时任务。日报这种东西，错误的自动化比没有自动化更伤信任。
2. 每个阶段的输出都落盘，出问题可以逐段回放，不用重跑全链路。
3. 模板 + 校验 + 重试，三件套缺一不可。
4. 快照至少保留 30 天，报告随时可重新生成或对账。
5. 给流水线本身加监控：它会静默死掉，是常态假设。

## 总结

整条流水线本质是：**采集 → 归一化 → 总结 → 投递**，外加流水线自身的可观测性。经验就两条：确定性的活别交给模型，叙事性的活别交给脚本；任何定时任务都要假设它会静默挂掉，提前装上心跳。搭完之后日报断更次数为零，写日报的时间也省下来了——这才是自动化该有的真实收益。
