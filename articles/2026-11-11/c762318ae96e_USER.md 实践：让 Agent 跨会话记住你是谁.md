## 背景

CLAUDE.md、AGENTS.md 这类项目级上下文文件已经成了标配：告诉 agent 这个仓库怎么跑、有哪些约定。但它们解决的是"这个项目是谁"，没有解决"我是谁"。换个仓库、换个 agent（CLI、IDE 插件、自建的 MCP 服务），你就得重新自我介绍一遍：用什么语言回答、机器什么系统、部署习惯是什么、哪些事不要做。

这些信息其实高度稳定，没必要每次会话靠对话临时输入。USER.md 就是把这部分"关于你个人"的上下文固化成一个 markdown 文件，让 agent 每次启动时自动读取。

## 做法

**1. 建文件。** 放一个稳定路径，比如 `~/.config/agent/USER.md`，跨项目共用。

**2. 分区写内容。** 我的结构大概四块：

- **沟通偏好**：回复语言、称呼、详略倾向（如"默认给结论，细节按需展开"）
- **技术栈与环境**：OS、shell、编辑器、常用目录、云厂商——只写事实，不写敏感值
- **工作习惯与禁忌**：如"不主动升级依赖版本""提交信息用中文""不确定时先问再动手"
- **当前上下文**：近期在推进的两三件事，方便 agent 接话

**3. 注入。** 三种方式任选：

- CLAUDE.md 里用 `@~/.config/agent/USER.md` 做 import
- 自建 agent / MCP：把文件包成 MCP resource，或在组装 system prompt 时拼接
- 简单粗暴：启动脚本里读文件内容塞进 prompt

**4. 控制篇幅。** 目标 100 行以内。它是简历，不是自传。

## 踩坑点

- **写太长。** 我第一版写了 200 多行，结果 agent 对关键规则反而执行变差——长文档稀释了重点，模型注意力被平均分配。砍到 60 行后明显改善。
- **写敏感信息。** API key、真实地址一律不进文件，只写"密钥由 xxx 工具管理"这类路径级引用。
- **过期不更新。** 项目结束后偏好会变。现在的做法是每两周让 agent 对照最近会话里我对它的纠正，主动提议 diff USER.md，我确认后落盘。
- **偏好写成死规则。** "必须""永远不要"用多了，agent 在例外场景下会僵化。改成"倾向……除非有明确理由"效果好得多。
- **多份副本漂移。** 三个 agent 各存一份，两周后就对不上了。坚持单一事实来源 + 软链/脚本分发。

## 可复用建议

- USER.md（跨项目个人上下文）和 CLAUDE.md（项目事实）分开维护，不要合并——职责不同、更新频率不同。
- 每条内容问一句"半年后还成立吗"，成立才写。
- 把"读取并遵循 USER.md"做成启动 hook 或插件默认行为，不靠人肉提醒。
- 用 agent 维护 agent 的上下文：会话结束让它提议 diff，比手动维护省力且更准。

## 总结

USER.md 的本质很小：一份几十行的 markdown，一个注入点。但它把你和 agent 的关系从"每次都要重新培训"变成"有一份稳定交接文档"。当你同时用好几个 agent、跑自动化任务时，省下的重复沟通成本会越来越明显。建议今天就建一个，先写十行，用两周再扩。
