## 背景

本地 Agent 的核心能力之一是调用本地工具：shell 命令、脚本、MCP server、各种 CLI。但系统提示词是通用的，运行环境却千差万别——macOS 和 Linux 路径不同，一台机器装了 ffmpeg 另一台没有，docker socket 挂载位置各异，Python 虚拟环境各有一套。这些"这台机器才知道"的信息，需要一个稳定落点。tools.md 就是这个落点：放在 Agent 工作区里的环境说明，Agent 在规划工具调用时读取它，而不是靠猜。

## 问题

常见的三种错误做法：

1. **让 Agent 自己试**。先试 `apt`，报错，再试 `brew`，来回烧 token，还可能执行有副作用的错误命令。
2. **硬编码在提示词里**。换机器、换部署就失效，多设备同步时互相污染。
3. **散落在 shell alias 和个人笔记里**。Agent 根本看不到，等于没有。

## 做法

建议按三层组织 tools.md：

**第一层：环境概览。** 操作系统、包管理器、路径约定（截图存哪、日志在哪）、网络限制，十几行以内。

**第二层：工具条目。** 每个工具固定四字段：用途 / 调用方式 / 前置条件 / 已知问题。示例：

```markdown
## ffmpeg
- 用途：转码、抽帧
- 调用：输出统一放 /tmp/agent-media
- 前置：本机 6.1 已装；服务器没有，转码走远端机
- 已知问题：服务器加 -threads 4，否则吃满核
```

**第三层：机器差异。** 跨机通用的部分和机器私有的部分（路径、端口、特殊配置）分开，后者放 `tools.local.md` 并加入 .gitignore。

验证很简单：直接问 Agent"你现在有哪些工具、当前是什么环境"，看回答是否来自 tools.md。答不上来，说明你的框架没有注入这份文件，需要显式声明加载。

## 踩坑点

- **写成散文**。tools.md 会整份进上下文，长篇大论稀释关键信息。坚持条目式，百行以内。
- **放密钥**。API key 一律走环境变量，文件里只写名字和获取方式——它会进版本库、会进日志。
- **和 MCP 描述重复**。MCP server 自带的工具说明已经够细，tools.md 只写它覆盖不到的：本机路径、启动命令、注意事项。两边冲突时 Agent 会随机站队。
- **过期不更新**。环境变了不改文件，比没有更糟。条目里加一行"上次验证：日期 + 自检命令"，让 Agent 能自己核实。
- **假设框架自动读取**。OpenClaw 默认加载工作区的 tools.md，自建 pipeline 不一定，先验证再依赖。

## 可复用建议

- 把 tools.md 当代码：改环境必须同步改文件，review 一起过。
- Agent 用错工具，除了当场纠正，把教训写回对应条目——这是一份会自我修复的文档。
- 文件开头放一条环境自检命令（关键工具存在性 + 版本），每次会话先跑。
- 多机部署时，tools.md 的 diff 就是最直观的环境差异清单。

## 总结

tools.md 的本质是把环境知识从模型权重和临时对话里搬出来，变成显式、可版本化、可同步的工程资产。成本极低，见效很快。如果你的 Agent 还在每台新机器上重新摸索环境，值得花半小时把它建起来。
