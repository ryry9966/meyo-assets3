## 背景

OpenClaw 的工具能力来自两层：MCP/插件提供的 schema，以及 workspace 里那份 TOOLS.md（会话启动时注入上下文）。前者告诉模型"这个工具是什么、参数有哪些"，但它不会告诉你：这台机器上 python 在哪个 conda env、包管理器是 brew 还是 apt、某个目录是否可写、代理怎么走。这些恰恰是本地执行最容易翻车的地方。

所以 tools.md 的定位很明确：一份由人维护、agent 每个会话都会读的**环境事实清单**。它不是工具说明书，而是"在你这台机器上怎么把工具用对"。

## 问题

环境差异导致的故障通常很一致：

- 在 Linux 服务器上让 agent 用 brew 装依赖；
- 把项目根目录猜成 `~/projects/xxx`，实际在 `/srv/xxx`；
- 每次换机器都要在对话里口头纠正一遍，下个会话又忘。

这些信息如果散落在系统提示词、聊天记录和 MEMORY.md 里，就会污染上下文、不可复用、换机即失效。tools.md 的价值就是把这些"跑过一次才知道"的事实收口到一个文件里。

## 做法

1. **建文件**：workspace 根目录放 TOOLS.md，按机器分节，一台机器一节。
2. **只写验证过的事实**：OS/包管理器、常用路径、能跑/不能跑的命令、权限边界、网络与代理。每一条都应该是你实际执行过命令确认的，不是"大概如此"。
3. **用祈使句短句**："用 apt，没有 sudo" 比 "这台机器是 Ubuntu 系的所以大概……" 有效得多。
4. **建立反馈闭环**：agent 执行出错并改正后，让它以 diff 形式提议更新 tools.md，人审核后合并。不要放开让它直接重写，否则会漂移。
5. **进 git**：放 dotfiles 仓库，换机或重装时拉下来就是完整环境画像；涉及工作环境的用私有仓库。

## 踩坑点

- **绝不放密钥**。tools.md 会整份进入上下文，写进去等于明文广播，敏感值走环境变量，这里只写变量名。
- **别写太长**。我的经验是单机不超过 60 行，超了就按项目拆分。上下文是稀缺资源，长文档会被稀释。
- **别重复 schema**。MCP schema 说参数，tools.md 说环境，职责别混。
- **过期信息比没信息更糟**。环境变了要删旧条目，否则 agent 会自信地引用一条已经不存在的路径。
- **改完注意会话缓存**。有些会话不会即时重读文件，必要时重开会话验证。

## 可复用建议

一个能直接抄的最小骨架：

```markdown
## <hostname> (<os> <arch>)
- 包管理：apt；没有 sudo
- 项目根：/srv/work/<name>
- Python：conda env "agent"，激活后再跑
- 网络：走 http_proxy=... （值见 env）
- 禁止：修改 /etc 下任何文件
```

原则只有三条：只写验证过的事实、祈使句、一台机器一节。把它当配置代码对待——进版本库、走 diff 审核、定期清理。

## 总结

tools.md 是连接"通用工具 schema"和"你那台并不通用的机器"之间最薄也最有效的一层。它不解决能力问题，解决的是同一套能力在不同环境下如何正确落地。保持短、真、版本化，环境差异就从反复踩坑变成一份可维护的资产。
