## 背景

Agent 的价值不在于会聊天，而在于能动手。要让 OpenClaw 真正干活，就得让它摸到外部世界：查工单、发消息、拉数据、触发构建。但"调 API"这件事直接塞给模型是跑不通的——模型不该碰密钥，不该面对原始错误码，更不该把 200KB 的 JSON 全文吞进上下文。对接外部服务，本质上是设计一次 Agent 与 API 之间的"握手协议"。

## 问题

裸调 API 通常会撞上四类问题：

1. **鉴权混乱**：密钥出现在 prompt 或工具输出里，安全隐患大；
2. **工具描述不清**：模型不知道何时该调、参数填什么，开始幻觉式调用；
3. **返回失控**：大 JSON、深层嵌套、无关字段，白白消耗上下文；
4. **错误不友好**：API 返回 401/429 时模型只会原样复述，不会降级或重试。

## 做法

我在 OpenClaw 里对接过几类外部服务，沉淀出一套通用流程：

**第一步，圈定工具边界。** 不要把整个 API 平面全暴露。一个服务先挑 2~3 个高频操作做成工具，且优先只读。写操作（下单、删除、发送）单独拆分，方便加确认环节。

**第二步，选对接形态。** 标准场景用 MCP server，协议现成、传输和鉴权都规整；轻量需求用插件或 skill 包一层 webhook 也行。原则是：鉴权和重试逻辑放在适配层，绝不下沉给模型。

**第三步，写透工具描述。** 工具描述是给模型看的接口文档：每个参数的含义和单位、返回结构长什么样、什么场景该调、什么场景不该调。描述写细之后，调用准确率的提升非常明显。

**第四步，裁剪返回。** 在适配层做字段筛选、分页上限和截断，只把决策需要的部分吐回去。必要时把原始响应落到本地文件，让模型按需再读。

**第五步，翻译错误。** 把 401、429、超时翻译成模型能理解的话："密钥失效，请检查配置""触发限速，已等待 30 秒重试一次"。反馈可理解，恢复路径才走得对。

## 踩坑点

- **描述含糊**：早期工具描述只有一句话，模型频繁传错参数类型，扩写描述后基本消除；
- **密钥经手模型**：试过让模型读环境变量拼请求，密钥差点被输出日志带出来，改为全部在适配层处理后才收口；
- **非幂等操作没加闸**：一次批量删除被重复触发，之后所有写操作默认 dry-run，预览经人工确认再执行；
- **无超时无重试**：上游偶发慢响应会让整个会话挂住，适配层统一加了超时和指数退避；
- **上游漂移**：第三方改了返回字段导致工具静默失败，后来在适配层加 schema 校验，字段不符直接报结构化错误。

## 可复用建议

1. 一个 API 包一个薄适配层，只做三件事：鉴权、裁剪、翻译错误；
2. 只读先行，写操作必须过确认闸门；
3. 所有工具调用打日志，事后能回放"模型调了什么、传了什么"；
4. 出入参都过 schema 校验，让漂移尽早爆炸而不是静默失败。

## 总结

对接外部服务不是"把 API 丢给 Agent"，而是设计一层克制的握手协议：模型负责决策，适配层负责安全、稳定和可解释。把鉴权、裁剪、重试、确认这些工程细节收进适配层，Agent 的调用准确率和稳定性会同时受益。先小后大、先读后写、处处留日志——这三条做到，OpenClaw 接外部服务就不再是碰运气的事。
