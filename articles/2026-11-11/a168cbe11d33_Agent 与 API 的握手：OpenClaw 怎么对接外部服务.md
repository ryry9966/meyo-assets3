## 背景

OpenClaw 的核心价值在于"让 agent 长在手边"：它不只是一个对话窗口，而是通过工具调用把模型能力接到真实世界——查状态、发通知、操作 CI、调用内部系统。对接外部服务的质量，直接决定这个 agent 是"能聊天的助手"还是"能干活的员工"。

## 问题

第一次对接外部 API，通常会遇到三类典型问题：

1. **鉴权怎么管**：API key 写进代码、漏进日志，或者指望模型自己"记住"——都不行；
2. **响应怎么喂**：接口一次返回 50KB JSON，直接塞进上下文，几轮对话后 token 就爆了；
3. **失败怎么兜**：网络抖动、限流、参数幻觉（模型编出不存在的字段），轻则静默失败，重则死循环重试。

## 做法

推荐路径：把每个外部服务包成一个**薄封装的 skill/工具**，而不是让模型直接拼 curl。五个步骤：

**1. 定义最小工具面。** 只暴露业务真正需要的动作。比如对接工单系统，`create_ticket`、`query_ticket` 两个工具就够了。动作越少，参数幻觉越少。

**2. 鉴权收进配置层。** key 走环境变量或配置文件，工具代码只读引用，执行日志对敏感字段脱敏。原则：模型可见的是工具签名，不是凭据本身。

**3. 控制返回体。** 在封装层做裁剪：只返回决策需要的字段（id、status、关键摘要），大列表分页 + 截断。经验值：单个工具返回控制在 1–2KB。

**4. 显式处理失败。** 超时设短（5–10s），错误文案是写给模型看的，要包含"发生了什么 + 可以怎么做"，比如 `rate_limited: retry after 30s`。不要只抛一个堆栈。

**5. 写操作加确认与幂等。** POST/DELETE 类动作在封装层生成幂等键；高敏感操作在权限配置里设为需人工确认，agent 只负责拟稿，不直接落盘。

## 踩坑点

- **让模型自由拼 URL**：几乎必然幻觉出错误路径。URL 模板写死在工具内部，模型只填参数；
- **返回原始 HTML 或长日志**：上下文消耗巨大且无用，先清洗再返回；
- **静默吞错**：catch 之后返回 "ok"，模型会误以为成功并继续编造后续动作，错误必须显式上抛给 agent；
- **不限流的写接口**：agent 的重试循环能把测试环境配额一小时打光，封装层自己加节流；
- **密钥进了对话历史**：一旦发生，整条会话都可能留存，提醒用户立刻轮换。

## 可复用建议

- 每个外部服务一个 skill 目录：manifest + 工具实现 + 测试用例三件套，方便复用与评审；
- 给每个工具写"黄金样例"测试：给定输入断言返回结构，防止上游 API 变更悄悄破坏 agent 行为；
- 错误信息当 prompt 写：结构化、可操作、带下一步建议；
- 灰度上线：先只挂只读工具跑一周，观察调用日志，再逐步放开写操作。

## 总结

对接外部服务的本质，不是"让模型会调 API"，而是**用工程手段把 API 的复杂性挡在封装层，只给模型一个干净、安全、可失败的工具面**。OpenClaw 提供了 agent 与工具之间的连接骨架，握手质量取决于你怎么设计那份契约：最小工具面、受控返回体、显式错误、幂等与确认。这四件事做扎实，第三方服务才敢真正放手交给 agent。
