## 背景

跑过一阵 Agent 的人都会遇到同一个阶段：模型本身没问题，卡住的是它和外部世界的连接。查天气、提工单、查库存、写数据库，这些动作最终都要落到真实的 API 上。OpenClaw 的工具层——无论是 MCP server 还是原生插件——本质上是给 Agent 装了一双"手"。但手好不好用，取决于你怎么封装对端服务。

## 问题

实践中最常见的失败不是"调不通"，而是"调得不可靠"：

- Agent 选错工具，或该调的时候不调；
- API 超时后原地重试，产生重复写入；
- 返回体太大，几轮对话就把上下文撑爆；
- 报错信息是写给人看的，Agent 读了也不知道下一步该干嘛。

这些问题在 demo 里看不出来，一旦接入真实服务就会集中爆发。

## 做法

把我们踩过坑之后沉淀的对接流程拆成五步：

**1. 先分层再动手。** 每个外部服务单独起一个薄适配层（MCP server 或插件），业务逻辑不进工具层。工具层只做三件事：鉴权、组装请求、把响应裁剪成 Agent 能消化的形状。

**2. 控制工具粒度。** 不要把 REST 的每个 endpoint 都原样暴露成工具。经验值是按"用户意图"合并：`get_order` 加 `cancel_order` 两个工具，远比一堆带十几个查询参数的变体好用。工具数量超过二十个左右，误选率会明显上升。

**3. 描述写给模型看，不是写给人看。** description 里写清楚：这个工具什么时候该用、什么时候不该用、参数的单位与时区。这是成本最低、收益最大的一处优化。

**4. 错误要"可执行"。** 返回给 Agent 的错误带上原因和建议动作，例如 `quota_exceeded, retry_after_60s`，而不是一坨原始堆栈。Agent 拿到结构化错误才有自愈的可能。

**5. 写操作必须防重。** 超时重试是常态，不是异常。所有写接口强制带幂等键，或者提供 dry_run 参数让 Agent 先确认再执行。

## 踩坑点

- **上下文膨胀**：上游返回 50KB 的 JSON 直接塞给模型，几轮就废了。适配层做字段白名单和截断，必要时支持分页参数。
- **长任务阻塞**：导出报表这类接口一跑几分钟，同步等待会卡死会话。拆成"提交任务 + 查询状态"两个工具，或走 webhook 回调。
- **密钥进日志**：调试时把 headers 整个打出来，token 就进了日志文件。日志层加脱敏，密钥一律走环境变量。
- **隐式状态依赖**：模型记住上一轮的 resource_id 就自作主张复用，结果资源早已被删。读接口默认返回新鲜状态，别让 Agent 靠记忆干活。

## 可复用建议

每对接一个服务，先过一遍这张清单：鉴权方式 / 超时与重试策略 / 错误结构 / 返回体裁剪规则 / 分页 / 写操作幂等 / 日志脱敏。七项都答得上来再上线。另外两条原则：工具层保持无状态，把会话上下文留给 Agent 自己管理；每个工具单独可测，替换外部服务时不用动上层逻辑。

## 总结

对接外部服务的核心不是"接上"，而是让 Agent 在不完美的网络里稳定地完成"握手"：少而准的工具、写给模型看的描述、可执行的错误信息、防重的写路径。这四件事做到位，从 demo 到生产之间那段最疼的距离，基本就填平了。欢迎在社区贴出你们的工具封装实践，尤其想看看大家是怎么处理超时与幂等的。
