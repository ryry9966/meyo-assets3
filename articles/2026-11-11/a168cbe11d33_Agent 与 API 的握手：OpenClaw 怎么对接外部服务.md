## 背景

Agent 本身只会推理，真正“做事”靠的是外部 API：查工单、发消息、读写数据库、调内部系统。在 OpenClaw 里，对接外部服务主要有三条路径：在 skill 里直接写 HTTP 调用、封装成插件、或者挂一个现成的 MCP server。选哪条、封装层怎么写，决定了 agent 是“能跑通”还是“用得住”。

## 问题

把 API 原样丢给模型，常见翻车姿势大致五种：

1. 工具描述含糊，模型靠猜传参数；
2. API key 硬编码在代码里，或被完整打进日志；
3. 没有超时和重试，一次网络抖动卡死整个会话；
4. 接口返回几 MB 的 JSON，上下文直接撑爆；
5. 下单、删除这类写操作没有确认机制，被误触发。

## 做法

1. **先定 schema，再写实现。** 每个工具先定义清晰的输入输出结构，描述里写明白“什么时候该用我、什么时候不该用”。这一步比实现本身重要。
2. **薄封装原则。** 包装层只做三件事：鉴权、参数校验、错误翻译。业务逻辑留在对话流程和提示词里，工具层越薄越好维护。
3. **鉴权走环境变量。** key 一律从 env 或 secret 管理读取，封装层发现缺失就返回一句明确错误，而不是抛个 stack trace 让模型自由发挥。
4. **错误信息写给模型看。** 把 4xx/5xx 翻译成可操作的提示，"rate limited, retry after 30s" 远好于一段 HTML。模型拿到可读错误，自己就能判断是重试还是换路径。
5. **限制返回体量。** 列表接口默认分页、截断、只回传必要字段；大 JSON 先做摘要再喂给模型。
6. **写操作加确认。** 副作用类工具拆成 draft + commit 两步，或在对话流里强制二次确认后再真正提交。

MCP 和插件怎么选：目标服务已有标准 MCP server（GitHub、数据库类居多）就直接挂，省掉自己维护的成本；内部系统或小众 API 用 skill/插件封装反而更省事。

## 踩坑点

- 工具描述写了个笼统的"send message"，没说明支持哪些渠道和格式，模型天天传错参数；
- 重试没考虑幂等，一次超时后的重试导致同一条消息发出三遍；
- 排障日志里打印了完整请求头，key 顺手就泄漏了；
- 工具挂到二十个以上后，模型选择工具的准确率肉眼可见地下降——该合并的合并，该下线的下线。

## 可复用建议

- 每个工具的描述里加一行“反例”：什么情况**不要**调用我；
- 封装层统一超时（10–30s 比较稳）加指数退避重试，且只对幂等操作重试；
- 上线前用固定的评测脚本跑 20 个典型请求，核对工具选择和参数是否正确；
- 灰度上线：先让 agent 只读不写，跑一周看调用日志再放开写权限。

## 总结

对接外部服务的本质，是给模型一个干净、可预测的“手感”。schema 清晰、错误可读、副作用可控——这三点做到位，OpenClaw 接什么服务都不难。工具层写得越克制，agent 的表现就越稳定。
