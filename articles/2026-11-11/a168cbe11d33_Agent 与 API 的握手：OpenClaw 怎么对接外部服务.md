## 背景

Agent 从"能聊天"到"能干活"，中间隔的就是工具层。OpenClaw 的实践里，大多数真实任务最终都落在一次对外部服务的 HTTP 调用上：查工单、发通知、拉数据、触发流水线。MCP 和插件机制解决的是"怎么把能力暴露给模型"，但真正决定成败的，是这次握手本身的工程质量。

## 问题

把一个 API 直接包成工具丢给 Agent，通常会撞上三类失败：

1. **参数幻觉**：模型编造枚举值、日期格式、字段名，请求在网关就被 400 打回。
2. **错误语义缺失**：服务端返回 500 加一段 HTML，Agent 看不懂，只能反复重试，形成死循环。
3. **上下文膨胀**：一个列表接口返回 50KB JSON，两三轮就把窗口吃满，后续推理质量骤降。

这三个问题的共性是：我们默认"模型能理解一切"，但工程上恰恰要做的是不让它理解多余的东西。

## 做法

以 OpenClaw 的 MCP server 接入为例，我们内部沉淀了一套固定流程：

**第一步：一个工具对应一个业务意图。** 不要把原始 REST client 暴露出去。不要给 `http_request(url, method, body)`，而是给 `create_refund_ticket(order_id, reason)`。参数越贴近业务语言，幻觉率越低。

**第二步：鉴权留在服务端。** API key、token 由 MCP server 进程从环境变量或密钥服务读取，永远不出现在工具参数里。模型只传业务字段。

**第三步：入参先过校验层。** 用 JSON Schema 做前置校验，枚举、日期格式、ID 规则在这里拦截。校验失败直接返回结构化错误，不打真实请求。

**第四步：错误也按契约返回。** 统一成 `{code, message, hint}` 三段式。`hint` 是写给模型看的："订单不存在，请先用 query_order 确认 ID"。这一行字能把重试循环砍掉大半。

**第五步：出参做裁剪。** 列表截断到前 N 条并注明"已截断"，长文本摘要后再返回。让 Agent 拿到的是"够用的信息"，不是"全部的信息"。

## 踩坑点

- **幂等性**：Agent 超时后倾向重试，非幂等的 POST 会造成重复下单。写操作类工具务必带客户端幂等键，并在描述里写明"可安全重试/不可重试"。
- **限流没有反馈**：触发 429 后如果只返回"请求失败"，Agent 会立刻再打。应返回 `hint: 等待 60 秒后重试`，或在 server 层直接 sleep。
- **工具描述偷懒**：description 是模型唯一的说明书。一句"调用某接口"不如三行说明：什么时候该用、什么时候不该用、失败后怎么办。
- **日志缺失**：每次工具调用都要落 request id、入参摘要、耗时、结果码。排查"Agent 为什么做了那个决定"时，这是唯一线索。

## 可复用建议

- 给每个工具配 `dry_run` 参数，上线前先跑只读模式。
- 工具 schema 变更视为 API 变更，走版本号管理。
- 高频错误码做映射表，把"工程语言"翻译成"模型语言"。
- 对外部依赖加熔断，避免服务抖动被放大成 Agent 的连环误操作。

## 总结

Agent 对接外部服务，本质是给模型修一条"它看得懂、走得稳"的路。OpenClaw 的插件/MCP 层提供了插座，但电压适配、保险丝、说明书仍要工程师来做。经验只有一条：把每个工具当成一个微型产品来设计——清晰的输入契约、诚实的错误反馈、克制的输出体量。握手才握得牢。
