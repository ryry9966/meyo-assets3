# 背景

Agent 类助手最大的落差往往不在模型能力，而在"它不记得我"。每次新会话都要重复交代：时区、代码风格、常用路径、commit message 不要带 emoji。LLM 本身无状态，上下文窗口也有限，所以记忆必须做成显式的系统工程：存什么、怎么写、怎么读、怎么过期。

# 问题：三种常见但跑不通的做法

1. **全塞进 system prompt**：几天后膨胀到几千 token，成本上升，注意力被稀释，模型反而开始忽略关键指令。
2. **直接 RAG 聊天记录**：检索出的是原始对话，噪声大，模型还得自己猜哪些是稳定偏好。
3. **只读不写**：记忆停在初始化那几条，两周后全是过期信息。

核心矛盾是：记忆既要持久，又要可控、可修、可审计。向量库不是银弹。

# 做法：分层记忆 + 显式读写路径

**第一步，分层。** 实践中三类够用：

- 偏好层：稳定、结构化，如"回复用中文""测试框架用 vitest"，几十条以内
- 项目层：当前工作目录的上下文，随项目切换
- 事件层：阶段性事实（"本周在赶 v2 发布"），带 TTL，过期清理

**第二步，写路径。** 会话结束跑一个抽取 prompt，提炼候选记忆，去重、分类后落盘。关键规则：只写"以后还会用到"的事实，单次表态不写，用户纠正时立即写。每条记录带字段：

```json
{
  "content": "commit message 不用 emoji",
  "category": "preference",
  "source": "user_correction",
  "confidence": 0.9,
  "created_at": "2025-01-01",
  "last_used": "2025-01-10",
  "superseded_by": null
}
```

**第三步，读路径。** 会话启动时注入，不要全量：按相关度 × 频率 × 新近度打分取 top-K，预算控制在上下文 10% 以内（几百 token）。

**第四步，冲突与生命周期。** 新旧偏好矛盾时，标记旧条目 `superseded_by`，绝不两条同时注入。定期清理长期未命中的条目。

**第五步，反馈闭环。** 用户说"我说过不用 tabs"，这是最强的写入信号，当场 patch 记忆，比任何自动抽取都可靠。

# 踩坑点

- **过度抽取**：早期我把每条事实都写入，两周后记忆文件变成垃圾场。要设门槛：稳定性 + 可复用性，宁可漏写。
- **矛盾共存**：新旧偏好同时注入，模型行为随机。必须做取代而不是追加。
- **存储过度设计**：偏好就几十条，上向量库纯属自找麻烦——不可读、不可 diff、调试痛苦。一个 markdown/JSON 文件加 git 版本管理足够，用户还能直接审阅编辑。
- **记忆投毒**：agent 会读邮件、网页，如果外部内容被抽进记忆再注入 prompt，等于持久化后门。写入前过滤来源，外部来源降权或隔离。

# 可复用建议

- 从纯文件起步，别急着上数据库。
- 写（抽取）和读（注入）做成 agent loop 里两个显式步骤，分别可测试；也可以封装成两个 MCP 工具（`memory_read` / `memory_write`）让 agent 调用，但写入必须过门槛校验。
- 建一个记忆回归测试：一组"应该记得 / 不该记得"的问答对，改 prompt 后跑一遍。
- 让用户能直接查看和修改记忆文件，这占了产品信任的一半。

# 总结

记忆不是模型问题，是工程问题：存储选型、写入门槛、读取预算、生命周期管理，这四件事做对，助手才会"越来越懂你"。先简单后复杂，文件方案能撑很久。
