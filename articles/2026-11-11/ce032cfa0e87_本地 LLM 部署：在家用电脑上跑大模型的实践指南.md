## 背景

过去半年我把家里的旧台式机（RTX 3070 8G）改成了常开的推理机，跑 Ollama 加几个开源模型，给 OpenClaw 的日常自动化当"廉价劳动力"。动机很朴素：一是聊天记录、日程、本地文件这些数据不想全送云端；二是 Agent 的高频小任务（摘要、分类、定时提醒）用本地模型几乎零边际成本；三是断网也能跑。

## 问题

真把 Agent 接上本地模型，才发现和"能聊天"是两回事：

- 8G 显存对模型尺寸和上下文长度都很苛刻；
- 小模型的工具调用（function calling）成功率明显低于云端大模型，MCP 工具一多就容易乱填参数；
- 一些框架默认按云端 API 的行为设计，直接切本地端点会踩静默截断的坑。

## 做法

1. **按显存定档位**。经验值：Q4 量化下，7B ≈ 5–6GB，14B ≈ 9–10GB，32B 需要 20GB 以上。8G 卡老实从 7B 起步，Apple Silicon 统一内存可以放宽一档。
2. **装 Ollama，走 OpenAI 兼容端点**。`ollama pull` 拉完模型，服务在 `http://127.0.0.1:11434/v1` 暴露 OpenAI 兼容接口，OpenClaw 侧把自定义 provider 的 base URL 指过去、模型名填 tag 即可，改动量很小。
3. **选对模型比选大模型重要**。中文 + 工具调用场景，优先选官方说明支持 function calling 的 instruct 版本（Qwen 系列小尺寸版本是稳妥起点），避开各种激进微调的"特化"权重。
4. **显式设置上下文长度**。Ollama 默认 ctx 很小（常见 2k–4k），Agent 会话一长就被静默截断。务必在参数里把 `num_ctx` 拉到 8k–16k，同时确认显存装得下对应的 KV cache。
5. **给小模型减负**。接入 OpenClaw 的 MCP 工具别一次全挂，按场景只暴露 3–5 个，工具描述把参数含义写清楚；复杂推理仍路由回云端模型，本地负责隐私敏感和高频轻任务。
6. **补齐本地 embedding**。记忆/RAG 功能需要向量化，`bge-m3` 或 `nomic-embed-text` 在 CPU 上跑也够用。

## 踩坑点

- **OOM 多半不是权重而是上下文**：权重装得下不代表 16k ctx 装得下，KV cache 是显存大户。
- **Q4 以下量化慎用于 Agent**：闲聊看不出差别，工具调用参数错误率会明显上升，关键任务建议 Q5/Q6 或 Q8。
- **模型卸载后的首 token 延迟**：Ollama 默认几分钟后卸载模型，自动化场景记得设置 `keep_alive`，否则定时任务每次都冷启动。
- **小模型的循环陷阱**：多步执行时小模型容易重复同一动作，要限制最大迭代次数，并在关键节点落日志、落盘。

## 可复用建议

- 先用 7B Q4 打通全链路，再考虑升档；链路没通之前换大模型只是浪费电。
- 给每个模型建一张"任务卡"：模型、量化、ctx、温度、能胜任的任务清单，换模型时按卡对比。
- 用自己 Agent 的真实任务做基准，别只看榜单——你的工具集和 prompt 风格对结果影响很大。
- `ollama ps` 和 `nvidia-smi` 常驻副屏，观察显存水位比猜测靠谱。

## 总结

本地模型已经能承担 Agent 工作流里相当一部分"体力活"：隐私数据不出门、高频任务零边际成本、断网可用。代价是工具调用可靠性和推理深度。工程上的解法不是追求本地全包，而是分层——本地干粗活、云端干细活。一台 8G 显存的旧电脑，就足以让你的 OpenClaw 自动化先跑起来。
