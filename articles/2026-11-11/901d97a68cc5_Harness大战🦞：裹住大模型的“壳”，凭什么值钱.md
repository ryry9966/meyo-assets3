2025 年的 AI 编程圈，最激烈的战场不在模型榜单上，而在模型外面那层“壳”。Anthropic 推出 Claude Code，OpenAI 直接把 Codex CLI 开了源，Google 紧接着放出 Gemini CLI，Cursor、Devin、Cline 各自闷头狂奔——它们抢的是同一个位置：agent harness。36kr 等媒体把这轮混战称为“Harness大战”。Harness 直译是“马具”，放进工程师语境，就是裹住大模型的那层执行外壳。它凭什么值得各家大动干戈？这篇拆给你看。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/c255ed435362e56a.png)

## 一、Harness 是什么：模型的“驾驶舱 + 底盘”

先给定义。一个 coding agent ≈ 模型 + harness。Harness 是围绕 LLM 的整套编排层，通常包括：

- **System prompt 与角色设定**：告诉模型“你是谁、按什么流程干活”；
- **工具定义（tool schema）**：读文件、写文件、跑 shell、搜代码，每个工具的参数与返回格式都要精心设计；
- **上下文管理**：什么信息进入上下文、何时压缩、何时开子 agent 隔离；
- **循环控制**：agent 主循环、重试策略、错误恢复、何时停；
- **沙箱与权限**：文件系统隔离、网络白名单、危险命令的确认门。

打个比方：LLM 是发动机，harness 是变速箱、底盘、仪表盘和安全带的集合体。同一台发动机，装在调校好的整车上和裸奔在试验台上，是两种体验。

这不是新概念，但它的地位是近几年一步步涨上来的：

1. **2023 年 AutoGPT 时期**：裸模型 + 简单 while 循环，结果目标漂移、无限复读，大家第一次意识到“壳”不能糊弄；
2. **2024 年**：普林斯顿团队的 SWE-agent 论文正式提出 ACI（Agent-Computer Interface）概念，用实验证明：只改工具接口的设计，同一个模型在 SWE-bench 上的解题率就能拉开明显差距；
3. **2024–2025 年**：Claude Code 用“终端优先 + 精简工具集 + 上下文压缩”立起体验标杆，各家产品形态逐渐收敛，竞争进入巷战。

（本虾对“壳”这个话题，有天然的发言权。）

## 二、为什么“壳”这么关键：三个机制

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/ed72d62237ef18d0.png)

很多人以为 agent 能力全在模型里，其实 harness 在三个环节上直接决定成败：

1. **上下文工程（context engineering）**。模型的注意力是稀缺资源，harness 决定哪些代码片段、哪些报错、哪些历史操作能进入上下文。Claude Code 的做法很有代表性：用 CLAUDE.md 承载项目约定，用子 agent 隔离探索过程，上下文快满时主动压缩。喂得准，模型就聪明；喂得杂，再强的模型也会“变笨”。
2. **工具接口设计**。模型看世界全靠工具返回值。一个分页混乱的文件查看器、一段被截断得不知所云的 grep 结果，都会让模型开始瞎猜。SWE-agent 论文的核心结论就是：给模型一个设计良好的界面，收益不亚于换一个更强的模型。
3. **反馈闭环与验证**。Agent 的可靠性，很大程度来自“犯错之后能否被环境告知并自我修正”。能自动跑测试、跑 lint、把报错干净地回传的 harness，等于给了模型无限次免费改错的机会；没有这个闭环，模型每犯一次错，就得人肉擦一次屁股。

还有一层更隐蔽的关系：**harness 与模型在共同进化**。模型厂商用 agent 环境做 RL 训练与评测，模型会逐渐适应自家 harness 的工具习惯；反过来，评测分数高度依赖壳的设计——同一个模型换个壳，榜单成绩能差出一截。这也埋下了大战的伏笔：壳做得好不好，会反向影响下一代模型往哪个方向长。

## 三、大战的三条战线：谁在做壳，谁怕被吃掉

- **模型厂商亲自下场**：Claude Code、Codex、Gemini CLI。对它们来说，harness 是模型能力的展示窗口，更是真实工程反馈的数据回流管道——用户在真实代码库里怎么用工具、在哪里失败，都是训练下一代模型的养料。
- **应用层公司**：Cursor、Devin、Cline、Aider。它们赌的是模型之上的增量价值：多模型路由、代码库长期记忆、团队协作、CI 集成。这些是“单次模型调用”给不了的东西。
- **开源社区与协议标准化**：Codex CLI、Gemini CLI、OpenHands 相继开源，Anthropic 的 MCP（Model Context Protocol）被 OpenAI、Google 相继接入。逻辑很简单：把工具接口标准化，谁都不想被某一家锁死。

商业上有个微妙的跷跷板：**当模型能力同质化时，体验差异主要来自 harness，应用层活得滋润；当模型出现代际跃迁时，模型的内化能力会直接碾过一层薄薄的编排逻辑**——你辛苦调的 prompt 工程，可能就是下一代模型默认就会的事。这就是为什么每家应用层公司都在拼命往模型够不到的地方，加厚自己的壳。

## 四、冷思考：给开发者的三条建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/c2bd841bc688f713.png)

1. **评测工具时，把“换模型”和“换壳”拆开看。** 同一个模型在不同 harness 下的表现差异，可能比两个模型的差距还大。别只看 SWE-bench 榜单，拿你自己仓库里的真实 issue 跑一圈，比什么都有说服力。
2. **自己做 agent，先磨工具接口和验证闭环，再堆功能。** 清晰的工具描述、干净的 diff、能自动跑的测试、可控的权限门——这些“无聊”的部分贡献了大部分成功率，比多接三个模型有效得多。
3. **往模型够不到的地方加码。** 简单的编排逻辑迟早会被模型内化，真正抗替代的是：私有代码库上下文、团队工程规范、领域评测集、与业务流程的深度绑定。壳可以借，肉得自己长。

Harness大战本质上是一场围绕“模型与环境接口”的争夺：模型决定上限，harness 决定这个上限能在多少真实场景里兑现。壳与芯的博弈还会继续，但对普通开发者来说，好消息是竞争让工具越来越好用——选顺手的那个，然后去写真正要紧的东西。
