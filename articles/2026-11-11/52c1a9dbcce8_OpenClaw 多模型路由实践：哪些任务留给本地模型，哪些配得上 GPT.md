## 背景

用 OpenClaw 跑 agent 一段时间后，账单和隐私是两个绕不开的问题。所有请求都打云端强模型，成本随调用量线性上涨；全部换成本地模型，复杂任务的成功率又明显下滑。多模型路由不是“都支持所以都接上”，而是要回答一个问题：**哪一类任务配得上强模型**。

## 问题

以我们团队的实际场景为例，任务大致分三档：

1. **高频轻量**：会话摘要、消息分类、字段抽取，每天几千次调用；
2. **中等**：单次工具调用、短代码补全、格式转换；
3. **重度**：多步规划、跨 MCP 工具编排、复杂调试。

第一档用云模型纯属浪费；第三档换成本地 7B/14B 模型后，工具调用参数经常出现幻觉，agent 卡在重试循环里出不来。

## 做法

核心思路：**按 agent 拆分绑定模型，而不是指望一个 agent 自适应**。

1. **任务分级**。抽样一周的执行日志，按上面三档打标，统计每档的调用量、平均轮数和失败率。
2. **绑定模型**。摘要/分类类轻量 agent 指向本地 Ollama（我们用 qwen2.5:14b），主 agent 保持云模型。在对应 agent 的配置里覆盖 model 字段即可（字段名以你所用版本的文档为准）：
   ```jsonc
   // 主 agent：云端为主，本地兜底
   "model": {
     "primary": "openai/gpt-4.1-mini",
     "fallbacks": ["ollama/qwen2.5:14b"]
   }
   // 轻量 agent 反向：本地为主，更强的本地模型兜底
   ```
3. **升级路径**。在插件层对本地模型输出做 schema 校验：JSON 不合法，或同一个 MCP 工具调用连续失败两次，就把该子任务转给云模型重跑，并记录升级事件。
4. **观测**。每次执行落一条日志，包含实际使用的 model 字段。跑一周后回看，路由分布是否真如预期。

## 踩坑点

- **本地模型的 function calling 不稳定**。尤其 MCP 工具参数较复杂时，小模型会编造参数名。schema 校验 + 失败升级是底线，不能省。
- **上下文长度差异**。本地 14B 常见 32k 上下文，长会话里工具结果堆积后发生截断，表现为“突然忘了前面的约定”。给轻量 agent 单独限制会话轮数。
- **吞吐要实测**。消费级显卡上 14B 量化模型约 20–30 tok/s，agent 一轮五六个工具调用就是分钟级体验。先测速，再决定哪些任务敢下放。
- **静默降级**。fallback 触发时没有任何提示，质量下降却无从排查——路由决策必须落日志，这是排查一切“模型变笨”问题的第一步。
- **别按榜单选型**。用你自己的 20 条真实任务样本测，公开评测分和你的场景经常不相关。

## 可复用建议

- 建 20–50 条小评测集，每次调整路由策略后跑一遍，用数字说话；
- 高频低难度任务本地化收益最大：摘要、分类、embedding 类；
- 隐私敏感数据（内网文档、客户记录）在路由层强制本地，写规则而不是靠自觉；
- 云模型侧设预算上限和告警；
- 路由规则保持简单：按 agent/任务类型静态绑定优先，动态路由等静态方案确实不够用了再上。

## 总结

路由的核心判断只有一句：**把“结果不确定”的任务交给强模型，把“结果可验证”的任务留给本地**。先用自己的日志量化任务分布，再动手分流。我们的最终比例是本地承接约 70% 的调用量，云模型承接 90% 的复杂任务，月成本降了一半以上，复杂任务成功率没有回退。这套分级思路不依赖特定模型，换型号也能沿用。
