## 背景

OpenClaw 的 cron 任务本质很简单：到点之后，把 instruction 当作一条 prompt 发给 agent，跑在一个独立会话里。schedule 决定"什么时候跑"，instruction 决定"跑成什么样"。常见情况是 schedule 调得很精细，instruction 却只有一句"每天帮我看看邮件总结一下"——结果输出格式天天变、有时漏数据、有时根本不知道结果去了哪。

根因在于：cron 会话没有聊天上下文。日常对话里说"照上次那样"，agent 能懂；cron 里这么说，它只能猜。

## 做法：把 instruction 写成独立任务说明书

推荐五段式结构，每段一两句话就够：

1. **触发语境**：交代"这是什么时间的例行任务，以系统当前时间为准"，避免"今天"被算错。
2. **目标与数据来源**：来源写死，不给自由发挥空间。"读取 `~/notes/todo.md` 和最新 RSS 抓取结果"，远比"看看我关注的内容"可靠。
3. **处理规则**：筛选、排序、去重、忽略什么，一条条列清。
4. **输出格式**：固定结构，比如"3 行以内概要 + 一张 Markdown 表格"，人好扫读，下游脚本也好接。
5. **投递与异常**：结果发到哪（Telegram / 微信 / 写入文件），失败怎么办——"来源读不到就注明原因，不要跳过，不要编造"。

骨架模板，改字段就能用：

```
[定时任务] 每天 08:00 例行任务（以系统时间为准）。
目标：汇总过去 24 小时的 <主题>。
来源：1) <路径/URL>；2) <MCP 工具>。
规则：<筛选/排序/忽略项>。
输出：3 行概要 + 明细表格。
投递：通过 Telegram 发给我。
异常：来源失败注明原因，禁止编造。
```

## 踩坑点

- **依赖上下文**："像上次一样"在隔离会话里无效，cron 拿不到历史对话。
- **没写投递渠道**：结果落在你没接管的会话里，跑成功也等于没跑。
- **放任副作用**：让 cron 直接回复消息、删文件、调写接口，出错没有拦截。写操作改成"先草拟，等我确认"。
- **频率 × 成本**：每 15 分钟跑一次的重推理任务，账单会教育你；高频任务换轻量模型，或让 instruction 先做廉价过滤。
- **任务重叠**：单次要跑 10 分钟的任务设了每 5 分钟触发，只会堆积。先估耗时，再定频率。
- **时区**：容器里没配 TZ，cron 表达式按 UTC 触发，任务半夜就跑了。

## 可复用建议

- 挂 cron 前先手动验证：把 instruction 原样贴进对话跑一遍，符合预期再定时。
- 先观察 3 个周期再提频，稳定之后再加密。
- 一个任务只做一件事，加需求就新建任务，别让单条 instruction 越长越脆。
- instruction 是要迭代的：定期翻执行记录，发现格式漂移就回去收紧措辞。

## 总结

写 cron instruction 只需要一个假设：执行那一刻，agent 对你一无所知。把时间、来源、规则、格式、去向、异常这六件事交代清楚，定时任务就能从"偶尔灵"变成"闭眼跑"。
