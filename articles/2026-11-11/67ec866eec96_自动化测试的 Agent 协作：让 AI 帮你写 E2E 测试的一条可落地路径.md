## 背景

E2E 测试大概是全栈团队里最"欠账"的一块：写起来慢、断言繁琐、UI 一改就崩，很多项目最后只剩几条冒烟用例。Agent 出现后，"让 AI 批量生成测试"听起来很诱人，但直接把页面丢给它说"帮我写 Playwright 用例"，产出往往跑不通，或者只是摆设。这篇记录我们在 OpenClaw 工作流里跑通的一条路：让 Agent 在真实浏览器里操作页面、生成用例、自己跑、自己修，人只做最后的审查。

## 问题：一次性生成为什么不行

- 模型没见过真实 DOM，选择器全靠猜，class 名一变就挂；
- 生成物大量依赖 sleep，CI 里 flaky 率极高；
- 断言薄弱，很多用例只验证"页面渲染了"，不验证业务结果；
- Agent 拿不到运行结果，写完即结束，失败也无人修。

根因是缺少真实环境反馈。写测试本质是"运行—观察—修正"的闭环，只给一次生成机会，等于把闭环砍掉了。

## 做法：把闭环还给 Agent

1. **先立约定。** 准备一份测试规范，作为 skill 注入 Agent：统一 `data-testid` 命名、禁止 sleep、每个用例必须有业务断言。再手写 2~3 条"金标准"用例作为 few-shot 示例。
2. **接上浏览器。** 通过 Playwright 相关的 MCP server，让 Agent 能打开页面、点击、读取真实 DOM。这一步之后它写的选择器是从页面里"抄"出来的，不是编的。
3. **小批量生成。** 一次只给一个业务流程（比如"下单—支付—查订单"），产出 3~5 条用例，不要指望整站覆盖。
4. **闭环执行。** 把"运行测试 + 汇总失败"封装成一个工具，Agent 调用后拿到失败步骤、截图和控制台报错，自己修，循环 2~3 轮。
5. **人工审查门。** Agent 声称"全绿"不等于用例有效。抽查断言质量：是否真的验证了订单号、金额、状态流转，而不是只检查某个 div 存在。

## 踩坑点

- **别把整个仓库塞进上下文。** 只给路由表、相关组件和测试规范，token 省一半以上，质量反而更高。
- **flaky 用例会污染闭环。** 第一轮先剔除依赖时序的用例，否则 Agent 会陷入"修一个挂一个"的死循环。
- **别让它碰业务代码。** Agent 的目标是"让测试变绿"，不给边界它就会去改实现。把业务源码设为只读。
- **headless 差异提前踩掉。** 本地有头能跑、CI headless 挂掉的情况不少，把 CI 的截图和 trace 一并喂回给 Agent。
- **成本设上限。** 闭环每轮都在烧 token，我们限制最大 3 轮，超了转人工。

## 可复用建议

- 测试规范文档是整套流程里 ROI 最高的资产，比换更强的模型有用。
- "运行并报告"做成单一工具，返回结构化失败摘要（哪个用例、哪一步、截图路径），Agent 修复命中率明显上升。
- 保持"一条流程一个 PR"的小步提交节奏，方便 review，也方便回滚。

## 总结

Agent 写 E2E 的价值不在"一次生成多少条"，而在于能否进入运行—反馈的闭环。你要做的三件事：给规范、给浏览器、给带边界的执行权。至于断言是否真的在守护业务，这件事目前仍然只能由人来做。
