2025 年，AI 圈把一个原本冷僻的工程词推上了风口浪尖：harness。所谓「Harness大战」，指的不是某一家公司，而是围绕大模型外层那套“驾驶舱系统”的竞争，Claude Code、Codex CLI、Gemini CLI、Cursor、Cline 同台竞技，模型厂商亲自下场做应用层，第三方工具商腹背受敌。这场仗打的不是模型本身，而是模型外面那层“壳”。壳是什么？为什么突然值钱？谁会活下来？这篇掰开说清楚。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/80cd491c02e4b7a2.png)

## 一、Harness 到底是什么：发动机 vs 整车

先给定义。在 AI Agent 语境里，harness（常被译作“脚手架”“线束”）指包裹大模型的整套工程系统：它把用户意图翻译成指令，管理上下文窗口，调用工具，解析模型输出并真正执行，再把结果喂回去循环，直到任务完成。

一个类比：模型是发动机，harness 是整台车。F1 引擎再强，没有底盘、变速箱、遥测和进站策略也上不了赛道。拆开看，一个现代 coding harness 大致有五层：

1. **上下文管理**：对话超长后的截断、压缩、摘要、关键文件检索，上下文窗口是稀缺资源；
2. **工具层**：读写文件、执行 shell、搜索网页、对接 MCP 服务，工具定义写得好不好，直接决定模型用得顺不顺；
3. **编排循环**：主循环、子代理（subagent）、并行任务、失败重试；
4. **沙箱与权限**：让“让 AI 改代码”不至于变成“让 AI 删库”，需要隔离执行环境和审批流；
5. **验证闭环**：跑测试、lint、构建，把失败信息回喂给模型自我修正。

一段历史注脚：2023 年 AutoGPT 火过一阵又哑火，证明“裸模型 + while 循环”远远不够；2024 年底 Anthropic 发表《Building Effective Agents》，把从 workflow 到 agent 的设计谱系讲清楚；2025 年 Claude Code 走红，业界才真正意识到：harness 是一门精细的工程学，不是随手包一层皮。

## 二、为什么“壳”突然值钱：三个拐点

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/d25a2f47885e927b.png)

**第一，模型能力跨过临界点。** 上下文从早期 4K tokens 涨到 128K 乃至百万级，工具调用从“经常调错”变成可靠技能，推理模型能做多步规划。模型一旦强到能“自己干活”，外层系统的设计质量就成了成败变量。

**第二，交互范式转移。** 此前的 AI 编程是 IDE 补全（Copilot 模式）：人写代码，AI 接下一句。Agent 模式反过来了：人给任务，AI 交付改动。任务制意味着中间所有状态——读哪些文件、怎么改、怎么验证，都得由 harness 接管，工程量指数级上升。

**第三，“上下文工程”成为显学。** Anthropic 在 2025 年专门撰文区分 prompt engineering 与 context engineering：决定 agent 上限的往往不是那句提示词，而是每一轮该给模型看什么、裁什么、压缩什么。社区做过不少对比：同一个模型，裸 API 手搓循环跑复杂任务反复翻车，换上打磨过的 harness 后成功率肉眼可见地提升，差距全在壳上。

## 三、战局：三类玩家，三种打法

1. **模型厂商**（Anthropic、OpenAI、Google）：推出官方 CLI（Claude Code、Codex CLI、Gemini CLI）。动机有三：最懂自家模型的脾气；真实任务数据回流形成飞轮；把商业模式从“卖 token”升级为“卖订阅、卖任务”。据公开报道，Claude Code 上线不到一年年化收入已达数亿美元量级，说明这条路确实跑得通。
2. **独立工具商**（Cursor、Cline、Windsurf 等）：差异化在 IDE 体验、多模型中立、团队与企业功能。风险在于：模型厂商“顺手”就能吃掉最通用的场景，第三方被迫向垂直纵深撤退。
3. **开源与协议层**（OpenCode、OpenHands，以及 MCP、A2A 这类协议）：押注 harness 会像 Linux 发行版一样开放，用标准化协议把工具层变成公共地基。

核心争论可以浓缩成一句话：**壳是护城河，还是临时脚手架？**

- 护城河派认为：模型越强，壳的放大效应越大；企业级的权限、审计、集成是脏活累活，模型厂商没动力碰。
- 挤压派则指出：模型每次升级都在吸收壳的功能，原生工具调用、超长上下文、computer use。当年风光的 RAG 中间件，就是这么被逐步“下拉”成模型默认能力的。

## 四、判断框架：什么样的“壳”能活下来

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-11/47515019b4faf8b8.png)

与其站队，不如用“可替代性”给壳分层，自下而上替代难度递增：

1. **会话与编排层**（最易替代）：起循环、管对话、接工具。模型厂商的官方 harness 会默认提供，纯做这一层的项目很难长期独立存在。
2. **领域工程层**（较难替代）：垂直场景的工具集与验证器——CAD 出图、BI 查询、医学影像、工业流程。模型厂商没有这些私有环境和领域 know-how，壁垒在数据与流程，不在模型。
3. **企业信任层**（最难替代）：权限体系、审计日志、合规、私有化部署、与客户内部几百个遗留系统的对接。这是最“脏”的活，但客户恰恰为之付费。

推论有点反直觉：**越通用的场景，竞争越惨烈。** 写代码是模型最擅长、厂商必争之地；而“在银行内部系统里安全地跑 agent”这种事，恰恰是独立厂商的机会。判断一个 harness 项目的前景，就看它的价值有多少落在第一层，有多少落在二、三层。

## 五、冷思考：给开发者的三条建议

1. **学 harness 思维，而不是某个具体工具。** 记住三条底层逻辑：上下文是稀缺资源，要精打细算；工具设计比提示词措辞更重要；验证闭环决定 agent 的上限。Claude Code 的系统提示词曾被完整逆向公开，社区公认是极好的免费教材，值得逐行去读。
2. **做 Agent 应用，把宝押在模型学不到的地方。** 私有数据接口、领域验证器、企业流程编排。动手前先问自己一句：这个能力，下一代模型会开箱即有吗？
3. **定期做“模型升级压力测试”。** 每逢新模型发布，把自己的产品功能清单过一遍：哪些已被模型默认能力覆盖？被覆盖的部分果断放弃，把资源挪向更深的层。

最后一句冷思考收尾：Harness大战的本质，是“智能最后一公里”的争夺。模型每前进一公里，壳就得后退一步，但最后一公里永远存在，只是它的位置在持续向专业、向纵深移动。看清这个移动的方向，比押注任何一个具体玩家都重要。
