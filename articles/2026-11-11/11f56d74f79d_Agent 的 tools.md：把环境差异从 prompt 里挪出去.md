## 背景

跑 Agent 做自动化的人多半遇到过：同一套任务流在自己机器上顺滑通过，换台机器就反复报错。排查下来，九成不是模型问题，而是环境事实没对齐——路径不同、端口被占、某个 CLI 没装、Python 版本差一个大版本、命令别名只在交互式 shell 下生效。

## 问题

两种常见错误姿势：

1. **硬编码进 prompt 或插件配置**：把 `~/projects/xxx`、`8080` 这类事实写死，换环境就得改，团队里人手一份私有补丁，无法共享。
2. **完全靠 agent 自行探测**：每次任务先 `which`、`ls` 一轮猜环境。token 花了不少，结论还不稳定，探测误判后再往下走就是连环错。

环境差异需要一个显式、可版本化、agent 启动即读的事实来源。

## 做法

我们的社区约定是一份 `tools.md`，配合分层覆盖：

**1. 定位**：`tools.md` 是环境事实的唯一来源。项目层放仓库根目录，全局层放 `~/.config/agent/tools.md`，agent 启动时读取并注入上下文。

**2. 分层覆盖**：全局层（机器级事实：OS、shell、包管理器、工具版本）→ 项目层（构建测试命令、端口约定、数据路径）→ 会话层（本次任务的临时约束）。后者覆盖前者，避免多份文件互相打架。

**3. 写法可执行**：不写散文，写条目和代码块——精确命令、绝对路径，最好附一行预期输出：

```markdown
## 测试
- 命令：`make test`（pytest 包装，超时 120s）
- 注意：首次运行自动拉 fixture，需内网
```

**4. 与 MCP 分工**：MCP server 负责"能力"——工具怎么调、参数是什么；`tools.md` 负责"环境事实"——MCP 无法自描述的部分，比如本地服务端口、凭据加载方式、数据目录位置。工具 schema 不要抄进来，两者互补不重叠。

**5. 像代码一样管**：项目层进 git，全局层进 dotfiles，改动走 PR。环境变了改文件，而不是改 prompt。

## 踩坑点

- **事实过期比没有更糟**：工具升级后没更新，agent 会按旧命令反复重试，越错越执迷。给命令条目标注"最后验证日期"，用 CI 定期跑关键命令校验。
- **塞秘密**：token、密码绝不入文件，只写"凭据在哪、如何加载"（环境变量名、密钥管理器条目）。
- **文件过长**：agent 上下文有限，主文件控制在一两屏内，细节拆子文件按需读取。
- **与硬编码并存**：脚本里残留的旧路径会和 tools.md 打架，约定建立后要顺手清理散落的硬编码。

## 可复用建议

- 按"环境 / 工具 / 路径 / 命令 / 已知坑"固定小节组织模板，方便 diff 和评审。
- 写一个自检脚本（或让 agent 先跑一轮检查），输出实际环境与 tools.md 的不一致项，作为更新提醒。
- 新机器 onboarding 固定为：拷模板 → 填空 → 跑自检 → 提交，十分钟内完成。
- 每次人工排障解决的环境问题，顺手沉淀进"已知坑"小节，形成积累飞轮。

## 总结

`tools.md` 本质上不是文档，而是给 agent 的运行时配置界面。它解决的是工程问题而非模型问题：把环境差异显式化、分层化、版本化、可验证化。记住四条原则——单一事实源、分层覆盖、可验证、不含秘密。配好之后，同一套 agent 工作流跨机器、跨团队复用才真正成立。
