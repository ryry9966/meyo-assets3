# 背景

LLM 本身无状态，会话一结束，Agent 对你的认知就清零。对 OpenClaw 这类常驻个人助手来说，这个问题特别明显：你告诉它“十点前别给我安排提醒”，三天后它照样约了九点的闹钟。

常见错误做法有两类：一是把历史对话全塞进 system prompt，上下文膨胀、成本翻倍，旧信息还互相打架；二是指望模型“自己记住”——那只是写进了当轮上下文，下个会话全部蒸发。

# 问题拆解

记忆系统其实是三个独立问题：

- **存什么**：哪些信息值得跨会话保留；
- **怎么取**：新会话如何召回相关记忆；
- **怎么更新**：偏好变化时旧记忆如何失效。

多数失败方案都是把这三件事混在一起做。

# 做法

我目前用的是三层结构，按稳定性递减：

1. **核心档案**：一个固定 JSON，存时区、语言、称呼等几乎不变的字段，每次会话无条件注入，控制在 200 token 以内。
2. **偏好库**：结构化记录，每条含 subject / predicate / object、confidence、updatedAt、source，按需检索注入。
3. **情景摘要**：会话结束后生成摘要做向量索引，解决“上次聊到哪了”。

写入路径比读取路径更重要。我用插件钩子在每轮对话后触发一次抽取调用，让模型输出候选记忆的 JSON，再过一道规则：与已有记忆 embedding 相似度超阈值就更新 updatedAt 而不是新增；与旧记忆冲突则标记 superseded 并保留旧版本，方便回滚，不直接删。

读取用关键词 + 向量混合检索，只取 top-k，注入预算硬限在上下文的 10% 以内。另外把 memory_search / memory_write 注册成 MCP 工具暴露给 Agent，让它自己判断“用户说‘以后都这样’该不该存”——模型带着对话语境，实测比纯后台抽取准得多。

# 踩坑点

- **抽取太激进**是最常见的失败模式。早期我让模型每轮都提取，一周攒了 800 条“记忆”，大量是“用户问了个问题”这种废话。加置信度门槛和显式信号词（“以后”“每次”“记住”）才压下来。
- **过期记忆比没记忆更糟**。半年前的“用户喜欢简洁回复”可能早就不成立了。给偏好记 updatedAt、检索时对旧记录降权，比设计复杂的遗忘曲线管用。
- **冲突记忆同时被召回时，模型会随机站队**。冲突必须在写入端解决，别指望读取端兜底。
- **别信模型说“我记住了”**。没有落库的记忆等于不存在，一定要验证工具真的被调用。

# 可复用建议

- 先从一个 JSON 档案文件起步，别急着上向量库。80% 的偏好场景，200 行 profile 就够了。
- Schema 优先：每条记忆必须有 type、confidence、updatedAt、source 四个字段，否则后期没法治理。
- 合并策略用“新写覆盖 + 保留版本”，比聪明的自动合并可靠。
- 提供一个 /memory 命令让用户随时查看、删除，既解决信任问题，也方便调试。

# 总结

记忆系统的本质不是让模型“更聪明”，而是给它一个可治理的外部状态：结构化存储、写入时处理冲突、读取时控制预算、用 MCP 工具让 Agent 参与决策。从最小方案起步，等真实使用暴露出检索需求再升级，比一上来就搭 RAG + 向量库 + 图数据库务实得多。
