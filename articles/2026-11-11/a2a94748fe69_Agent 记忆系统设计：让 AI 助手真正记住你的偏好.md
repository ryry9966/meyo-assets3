## 背景

用 OpenClaw 这类常驻助手跑了一段时间后，最影响体验的不是模型能力，而是它"记不住事"。时区、代码风格、回复语言、会议习惯——这些偏好我每次都要重新交代一遍。会话上下文解决不了这个问题，它天生就是短命的。

## 问题：三种常见做法的坑

1. **全塞进 system prompt**。最初我把所有偏好写进提示词，两周后膨胀到几千 token，模型顾此失彼，成本也上去了。
2. **上向量库做 RAG**。偏好条目总共就几十条，需要的是"更新"而非"检索"。语义召回还会把相似但过期的条目一起捞出来，制造矛盾。
3. **append-only 日志**。只追加不覆盖，三个月后同一件事有三条互相冲突的记录，行为变得不可预测。

核心矛盾：偏好是**少量、结构化、需要更新**的数据，不是文档检索问题。

## 做法：三层结构 + 显式写入工具

### 1. 分层存储

- **profile.md**：静态档案（时区、称呼、长期偏好），控制在 1–2KB，每次会话注入 system prompt。
- **working/**：按项目/频道分文件的工作记忆，会话中按需读取。
- **journal/**：带时间戳的会话纪要，只在回溯检索时用，不自动注入。

### 2. 写入做成 MCP 工具

与其在 prompt 里写"请帮我记住"，不如注册一个 `memory_update` 工具（MCP server 或插件均可），schema 锁死：

```yaml
id: reply_style
content: 回复保持简短，默认中文
source: user_explicit
confidence: high
updated_at: 2025-01-14
```

三条硬约束：
- `source` 区分"用户明说"和"模型推断"，推断项置信度默认 low；
- 更新走 overwrite + 新时间戳，不做追加；
- 同 id 冲突以时间戳新的为准。

### 3. 清理作为日常任务

用 cron 挂一个每周任务：合并重复条目，把半年未触碰的条目降级并归档到 journal。**遗忘和记忆一样，得是一等公民。**

## 踩坑记录

- **格式让模型自由发挥**：早期允许模型自定义存储结构，一周后 key 命名五花八门，检索没法做。schema 必须锁死。
- **没有 source 字段**：有次助手突然改用英文回复，翻了半天才发现是一条 inferred 记忆导致的。能回溯来源的 memory 才敢自动化。
- **隐式推断太激进**：我说了一次"周四别排会"，它记成"每周四不排会"。写入门槛宁高勿低。
- **敏感信息入库**：记忆会跟着 prompt 流向所有工具。敏感内容要么不写，要么放受限作用域。

## 可复用建议

- 偏好记忆用**纯文本文件**（markdown/YAML）：可 diff、可手改、可版本管理。这个量级上向量库是负资产。
- 条目五件套：`id / content / source / confidence / updated_at`，缺一个都会在排障时付出代价。
- 注入预算固定（profile ≤ 2KB），超了说明该清理，而不是该扩容。
- 每两周人工 review 一次记忆文件，十分钟，能挽回大量信任。

## 总结

记忆系统本质是数据工程问题：分层存储、显式写入、带元数据、定期清理。不需要向量库和复杂框架，一个 schema 严格的工具加几个文件，就能把"每次重新介绍自己"变成"它知道我在说什么"。先让记忆小而准，再谈规模。
