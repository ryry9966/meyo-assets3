## 背景

常驻 agent 有个绕不开的问题：模型平时是“睡着”的，谁来叫醒它？OpenClaw 内置的 heartbeat 是典型的轮询方案——每隔固定时间给 agent 注入一条心跳消息，它借此检查待办、扫一眼状态、决定要不要主动说话。另一条路线是推送：webhook、MCP 通知、文件监听，事件到达才唤醒。两条路线各有代价，这篇记录我在自己实例上做混合设计的取舍过程。

## 问题

纯轮询的痛点很直接：

- 心跳本身消耗 token。默认 30 分钟一次看似不贵，但心跳 prompt 一旦写重（塞满上下文、要求逐项检查），一天的固定开销相当可观。
- 响应时延上限 = 心跳间隔。要“几分钟内反应”的场景，要么调快间隔烧 token，要么接受延迟。

纯推送的问题也不少：

- 本地部署通常没有公网入口，webhook 打不进来，还得维护隧道。
- 事件丢失没有兜底：agent 重启、推送失败，这条事件就没了，除非上游有重试。
- “盯着一个会变的东西”这类状态型任务，推送反而别扭，事件风暴会把 agent 打醒太多次。

## 做法

我的结论是分层：**推送管及时性，心跳管兜底和对账**。

1. **事件通道走推送。** 本地能产生的事件（文件变化、脚本完成、定时任务输出）由一个常驻小进程写入落盘队列，再投递给 agent 会话；外部服务的事件经 webhook + 隧道进来，先落队列再消费。
2. **队列即事实源。** agent 醒来消费队列，处理完打标记；投递失败不丢，只重试。就算推送通道挂了，下一次心跳对账也能补上。
3. **心跳降频、降重。** 我把间隔放宽到 30–60 分钟，心跳 prompt 只保留一件事：对账——比对队列游标、补漏、清理过期任务。约定一个“无事可做”的固定应答，大多数心跳安静返回。
4. **高频轮询下沉到脚本。** 需要密集盯梢的指标交给脚本层，只有越过阈值才作为事件推给 agent。别让模型干轮询的活，它又贵又不擅长。

## 踩坑点

- **心跳 prompt 贪大。** 早期我把完整日历和待办塞进心跳，token 开销翻了三倍，agent 还频繁“没事找事”主动发消息。瘦身到只剩对账指令后才安静下来。
- **推送没做幂等。** webhook 重试导致同一事件被处理两次，重复执行了动作。现在队列键里带事件 ID，消费端去重。
- **隧道单点。** 内网隧道断过一次，推送静默失败了一天，靠心跳对账才补上——反过来证明兜底心跳不能关。
- **静默约定要明确。** 不给 agent 约定“无事”的固定应答，它就会为了回应而编造输出。

## 可复用建议

- 心跳是“对账”，不是“触发器”；及时性交给推送，可靠性交给心跳。
- 任何事件先落队列再进 agent，队列可回放，agent 可随时重启。
- 高频检查下沉到脚本，模型只做决策。
- 心跳间隔宁长勿短，先看日志里的空转率再调。

## 总结

轮询与推送不是二选一。推送解决“快”，心跳解决“不丢”，两者通过一个可回放的队列粘合，才是本地 agent 既省 token 又不失信的唤醒架构。先让心跳变轻，再让推送补位，是我验证过最省心的路径。
