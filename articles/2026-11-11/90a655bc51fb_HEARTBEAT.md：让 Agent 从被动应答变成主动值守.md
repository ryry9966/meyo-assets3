## 背景：Agent 的默认姿态是"被动"

大多数 agent 的使用方式是问答式：你开口，它回答。但对一个常驻的个人助理或运维 agent 来说，"盯着 CI 挂了告诉我""到期事项提醒我""有新邮件简报一下"这类需求，本质上需要它自己发起动作。OpenClaw 为此给了一个非常轻的机制：在 workspace 里放一个 `HEARTBEAT.md`，agent 会按固定间隔（默认约 30 分钟，可通过 `HEARTBEAT_INTERVAL` 调整）醒来一次，读取这个文件并判断要不要做事。文件不存在或为空时心跳直接跳过，所以这是显式 opt-in，不会白白烧 token。

## 问题：主动 ≠ 定时群发

最朴素的实现是 cron + 固定 prompt，结果通常是每半小时收到一句"一切正常"——噪音、费用、上下文污染三连。我们要的形态是：醒来 → 读规则 → 判断 → **要么沉默，要么行动**。沉默必须是默认行为，而不是靠模型自觉。

## 做法：三步接入心跳

1. **在 workspace 根目录新建 `HEARTBEAT.md`**，写检查项，不要写作文。每条一行，格式统一为"条件 + 动作 + 输出要求"：

```markdown
# 心跳检查项
- TODOS.md 中有到期未完成事项时，提醒我一次
- ~/proj 的 git status 有超过 2 天未提交改动时，简报一次
- 每天 9 点后第一次心跳：汇总 RSS 未读，其余心跳跳过
- 无任何条件命中时输出为空，不要汇报"一切正常"
```

2. **依赖"静默默认"控噪**。心跳 prompt 本身已要求无事可报时保持沉默，你的文件里再强调一遍，双保险。
3. **采集交给工具，心跳只负责判断**。git、日历、RSS 这类数据源用 MCP 工具去取，检查项里只写"取到什么算命中、命中了说什么"。

## 踩坑点

- **把文件当日记写**：长状态、大段上下文塞进 HEARTBEAT.md，每次心跳全量注入，纯烧 token。它只放规则，状态外置到 `STATE.md`，让 agent 按需读。
- **重复告警**：条件持续为真（如"有未提交改动"），每个心跳都会报一遍。解法：要求 agent 告警后把时间写进 `ALERTS.log`，下个心跳先读再判断，做去重。
- **心跳会话 ≠ 聊天会话**：别假设它带着你上一轮的对话上下文。跨会话要共享的信息写进 workspace 的 memory 文件。
- **间隔一刀切**：30 分钟对"盯 CI"太粗，对"盯 RSS"太细。能写死时间的任务交给系统 cron 或 OpenClaw 的 cron 工具，心跳留给"需要看情况"的模糊检查。
- **工具失败静默**：心跳里调 IM/API 失败没人看见。让 agent 把每次心跳动作追加写入日志文件，出问题可回溯。

## 可复用建议

- **模板三段式**：检查项 / 静默规则 / 状态文件约定。新需求只加检查行。
- **一条分界原则**：cron 能写死的别用心跳；需要判断的才用心跳。
- **条目上限 5 条**：超过说明该拆成独立 cron 任务或插件了。
- 状态文件（STATE / ALERTS log）放 workspace 根目录并纳入备份，它们是心跳机制能长期稳定运行的底座。

## 总结

HEARTBEAT.md 的价值不在"定时执行"——那是 cron 的活——而在于给 agent 一个低成本的"醒来判断"循环。写好它只需要两条工程习惯：文件保持极简，状态外置可回溯。做到这两点，agent 才真正从问答机器变成值守助理。
