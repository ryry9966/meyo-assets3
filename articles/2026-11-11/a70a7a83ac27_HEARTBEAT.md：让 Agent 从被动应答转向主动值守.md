## 背景

多数人对 Agent 的心智模型是"一问一答"：你发消息，它回消息，中间的时间它在空转。OpenClaw 提供了一个低成本的机制改变这件事——workspace 根目录下的 `HEARTBEAT.md`。网关会按固定间隔（默认 30 分钟）唤醒一次 Agent，Agent 读取这个文件，自行判断"这一轮有没有值得做的事"。有，就主动开口；没有，就静默返回，不打扰你。

## 问题

两个极端都不理想：

- 纯被动模式浪费了常驻 Agent 的价值，大量可预期的例行检查仍要人肉发起；
- 而直接用 cron 硬调 LLM，成本不可控、消息噪音大、行为不可预期。

真正想要的是"有策略的主动"：周期触发、按条件判断、无事则闭嘴。`HEARTBEAT.md` 就是承载这套策略的地方。

## 做法

1. 在 `~/.openclaw/workspace/` 下创建 `HEARTBEAT.md`，写成结构化策略而非流水账。每条任务固定四段：检查什么 / 什么条件才动作 / 动作是什么 / 不满足时保持静默。示例：

```markdown
- 每次心跳检查日历：24 小时内有日程则发一条摘要，否则不发言
- 检查 ~/repos/app 的 CI 状态：出现新失败且上次未报告过才通知
- 每天第一条心跳生成晨报：对比 STATE.md 里的日期，避免重复
```

2. 在 `openclaw.json` 里配置 `heartbeat.interval` 和 `heartbeat.target`（决定心跳消息送到哪个会话）。调试期把间隔调到 2–5 分钟，临时不用的项目可设 `heartbeat.enabled: false`，避免空跑成本。
3. 观察日志确认行为：每次心跳是一次真实的评估，无事时 Agent 返回静默标记，不会给你发消息。行为符合预期后再调回正常间隔。

## 踩坑点

- **指令模糊必然导致噪音。** "帮我看看有什么新东西"这种写法会让 Agent 自由发挥，条件必须可判定。
- **成本会放大。** 每次心跳是一次 LLM 调用，叠加工具调用后翻倍。重逻辑写成脚本让 Agent 调，别全塞进 md。
- **重复通知。** 缺少状态记录时，同一个问题每个周期报一次。加个 `STATE.md` 记录"上次处理到哪"，配合去重。
- **时区问题。** "每天早上 9 点"这类任务要明确让 Agent 先取当前时间再比较，别靠感觉。
- **别做重活。** 心跳里只做轻量检查，长任务转后台执行，否则会拖垮心跳节奏。

## 可复用建议

- 把 `HEARTBEAT.md` 当策略文件维护：条目控制在 3–5 条，每条必须有静默条件，定期删掉从不触发的项。
- 沉淀四段式模板（检查对象 / 触发条件 / 动作 / 静默规则），新任务往里填，保持全文件风格一致。
- 每周翻一次心跳日志，统计各条目触发率，清理噪音来源和僵尸条目。
- 不要拿它当 cron 替代品：纯定时需求交给系统 cron 更便宜可控；心跳的价值在于"Agent 自己判断要不要开口"。

## 总结

`HEARTBEAT.md` 的核心不是定时器，而是把"何时不说话"也写成规则。它便宜、可版本管理、可逐条迭代，是把 Agent 从问答工具升级为值守角色的最低成本路径。建议从一个晨报任务起步，观察两周真实触发情况，再考虑加检查类和汇总类任务——主动能力是迭代出来的，不是一次写全的。
