## 背景

Agent 的价值最终要落在"能做事"上：查工单、发通知、拉报表。这些动作几乎都发生在 Agent 进程之外——某个内部服务或第三方 API。OpenClaw 里这条链路的标准姿势，是把外部 API 包成 MCP 工具（或插件）暴露给模型，而不是让模型直接拼 HTTP。

## 问题

我们早期走过弯路：把接口文档整段塞进 system prompt，让模型自己生成请求。结果三类问题反复出现：

1. **幻觉调用**：编造不存在的路径和参数，测试环境直接 404；
2. **凭据暴露**：token 写在 prompt 里，一次日志导出就泄漏了；
3. **上下文膨胀**：接口返回 8KB 的原始 JSON，几轮对话就把窗口吃满，Agent 开始"失忆"。

结论很明确：握手这件事要在工程层做掉，不能指望模型自觉。

## 做法：四步把 API 包成 MCP 工具

**第一步，圈定最小接口面。** 不要整站包装。对着业务场景问一句：Agent 到底需要哪几个动作？通常 3–5 个工具就够。接口面越小，模型选错的概率越低。

**第二步，写一个薄的适配层。** 用 MCP server 把选定的端点包起来，输入输出都走 JSON Schema 约束。鉴权放在适配层：从环境变量或密钥服务读 token，注入请求头，prompt 和会话记录里永远不出现凭据。

**第三步，描述即契约。** 工具的 description 不是注释，是模型赖以决策的全部依据。写清楚每个参数的含义、单位、必选/可选、典型取值，以及"什么情况下不要调用我"。一句"page 参数从 1 开始"，能省掉一半调试时间。

**第四步，错误要能被推理。** 不要把堆栈原样丢给模型。把上游错误映射成结构化结果：错误码、人话描述、是否可重试。限流返回 `{retryable: true, wait_seconds: 30}`，模型知道等；参数错误返回 `{retryable: false, hint: "日期格式应为 YYYY-MM-DD"}`，模型能自我纠正。

## 踩坑点

- **返回值不做裁剪**：上游 JSON 原样透传，上下文很快被撑爆。在适配层做字段投影，只留业务需要的键。
- **写操作没有幂等键**：模型重试一次，工单创建了两条。所有 POST 类工具强制带幂等 key。
- **超时跟着上游走**：上游 30 秒超时，Agent 循环就卡 30 秒。适配层设更紧的超时，失败走结构化错误路径。
- **限流没有预算**：Agent 一激动并发十个工具调用，直接把配额打穿。适配层做令牌桶，排队而不是硬撞。
- **描述与实现漂移**：接口升级了、描述没改，模型按旧契约调用。把工具描述当成代码 review 的一部分。

## 可复用建议

1. 一个工具 = 一个清晰动作，宁做多不做杂；
2. 响应字段白名单化，默认裁剪；
3. 每次调用打结构化日志（工具名、耗时、状态码、trace id），排障时能对上账；
4. 固定一套黄金用例做回归：三个正常、三个边界、三个恶意输入；
5. 新接口先以 dry-run 模式跑通，再放开写权限。

## 总结

Agent 对接外部服务，本质上不是"教模型调 API"，而是"把 API 翻译成模型能可靠使用的契约"。OpenClaw + MCP 提供了现成的握手协议，真正的工作量在适配层：最小的接口面、干净的凭据管理、可推理的错误语义。把这三件事做扎实，工具调用成功率会有肉眼可见的提升。
