## 背景

OpenClaw 的很多玩法——MCP 工具调用、定时任务、家庭自动化——都绕不开一个现实：聊天记录、日程、家庭设备状态，全都在往云端模型送。对一部分人这无所谓，但对想做家庭自动化、处理私人数据的人来说，把推理搬回本地是迟早的事。再加上 API 成本和断网场景，本地部署的动机其实相当充分。

## 问题

动机充分不等于条件成熟，家用硬件的约束很具体：

1. **显存**。消费级显卡常见 8–24GB，直接决定能装的模型上限。
2. **Agent 对模型的要求比聊天高**。OpenClaw 调 MCP 工具时，模型要稳定输出合法的 function call JSON，还得吃得下冗长的工具 schema 和多轮上下文。不少聊天里表现尚可的模型，一到工具调用就崩。
3. **运行时行为差异**。Ollama、llama.cpp、vLLM 对工具调用的支持程度和实现细节都不一样。

## 做法

我的环境：一台 12GB 显存的 PC，另有一台 32GB 统一内存的 Mac 做对照。步骤如下：

1. **选运行时**。先用 Ollama，省事且自带 OpenAI 兼容接口；对性能有要求再换 llama.cpp server 或 vLLM。OpenClaw 侧只需把 provider 的 base_url 指到 `http://127.0.0.1:11434/v1`。
2. **按显存选模型**。经验公式：Q4 量化下，显存 ≈ 参数量(B) × 0.6，再留 2–4GB 给 KV cache。8GB 卡跑 7–8B，12GB 跑 14B，24GB 才碰 32B；Mac 统一内存按七成估算。中文 + 工具调用场景，Qwen 系列是稳妥选择。
3. **量化选 Q4_K_M**。这是质量与体积的平衡点；Q4 以下的量化在 agent 场景里 JSON 输出明显劣化，别碰。
4. **调大上下文**。默认 num_ctx 往往只有 2048/4096，MCP 工具 schema 一多就被截断，模型会"忘掉"工具。我设到 16K，同时注意 KV cache 会跟着吃显存。
5. **先测工具调用，再接自动化**。挂一个最小的 MCP 工具（读文件、查时间），跑十几次，确认参数 JSON 合法、无死循环，再逐步换真实工具。
6. **做混合路由**。本地模型处理例行动作和高隐私数据，复杂规划回落云端。这条路比死磕本地大模型现实得多。

## 踩坑点

- **上下文默认值是隐形坑**。接上 MCP 后工具"时灵时不灵"，排查半天发现是 num_ctx 太小、schema 被截断，改大后立刻稳定。
- **别只看 tokens/s**。Agent 的调用模式是大量短请求，首 token 延迟比吞吐更重要。模型一旦溢出到 CPU offload，每次调用都慢到没法用——宁可降一档参数量，也要让权重完整留在显存里。
- **更大 ≠ 更好用**。我在 12GB 卡上硬塞过 Q3 量化的 32B，工具调用成功率反而不如稳定的 14B Q4。
- **升级运行时会改变行为**。某次 Ollama 升级后工具调用模板变了，一半自动化直接挂掉。模型和运行时版本要锁死，升级前先跑一遍工具调用回归。

## 可复用建议

- 给每个本地模型建"档案"：运行时版本、量化等级、上下文长度、工具调用测试结果，换机或升级时照单复现。
- 只给本地模型挂当前任务需要的 MCP 工具，schema 越短越稳。
- 8–14B Q4 + 16K 上下文，是家用硬件上 agent 场景的甜点位。
- 本地再跑一个小嵌入模型，RAG 记忆就完全不依赖云端了。

## 总结

本地 LLM 不是云端的替代品，而是 agent 体系里的一个角色：负责例行、高频、隐私敏感的那部分调用。把工具调用稳定性当第一验收标准，把上下文和显存当一等公民来管理，再用混合路由兜底——家用电脑跑本地模型，就能从"能跑"变成"能用"。
