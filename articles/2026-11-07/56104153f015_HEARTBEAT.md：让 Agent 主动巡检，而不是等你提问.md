## 背景

OpenClaw 的 Agent 默认是应答式的：你发消息，它处理；你不发，它静默。但日常自动化里大量需求是周期性、低频、条件触发的——盯一下磁盘、看看仓库有没有新提交、整理收件箱。这类事让用户自己当调度器，迟早会漏。

网关内置了心跳机制：默认约每 30 分钟，向 Agent 所在会话注入一条心跳提示，Agent 会读取 workspace 下的 `HEARTBEAT.md`。文件里没有需要做的事，它按约定返回 `HEARTBEAT_OK`，网关当作空操作丢弃；有任务就执行。换句话说，`HEARTBEAT.md` 是一份用自然语言写的"值班手册"。

## 问题

没有这份文件时，主动性行为散落在聊天记录里："下次记得提醒我""帮我每天看一眼"。上下文一长，模型要么忘，要么自作主张。你需要一个稳定的、每次心跳都会被完整读到的检查清单。

## 做法

1. 在 workspace 根目录建 `HEARTBEAT.md`，用 checklist 形式写，一条任务一行，写成"可判定条件 + 动作"：

```markdown
# 值班清单
- (no reply) 检查 ~/projects/api 的 git status，有未提交改动则整理提交
- / 分区使用率超过 85% 时，清理过期日志并把结果发到主会话
- 收件箱有标记为高优先级的未读项时，摘要后通知我
```

2. 控制回复噪音：不想每跳都说话的任务，标 `(no reply)`，或让 Agent 返回 `HEARTBEAT_OK`。
3. 按场景调间隔：值守类 10–15 分钟，摘要类 6–12 小时，夜间拉长，以你版本网关的 heartbeat 配置为准。
4. 硬定时的任务（如每天 9 点发日报）走 cron 工具。心跳负责"巡检和分诊"，cron 负责准时执行，两者互补而非替代。

## 踩坑点

- **文件体积就是每跳成本。** 整个文件每次注入上下文，写成需求文档等于每半小时烧一次 token，控制在二三十行内。
- **任务写太虚没法执行。** "帮我盯着服务器"模型只能编。必须给判定条件、动作和输出位置。
- **重活别放心跳。** 长任务会占住会话，心跳只做发现，执行交给 cron 或子 Agent。
- **Agent 有写权限。** 这个文件在它自己的 workspace 里，它可能"好心"改你的清单——用 git 管 workspace，diff 一目了然。
- **群聊场景要定向。** 默认心跳走主会话；如果路由到群，每跳都可能打扰，务必确认 target 配置。

## 可复用建议

任务分三档：**必做**（监控告警类）、**可做**（每日摘要类）、**禁做**（花钱、删数据类必须人工确认，心跳只提醒）。冷启动只放 2–3 条，跑一天观察 token 消耗和误报，再逐步加。配合 `MEMORY.md`，让 Agent 每次主动动作后记一笔，避免重复打扰。

## 总结

HEARTBEAT.md 的价值不在配置，而在于把"我希望你主动做什么"从口头约定，固化成一份每次都会被读到的检查清单。工程量很小，一个下午就能跑起来；真正要花时间的是迭代任务措辞——写得越可判定，Agent 的主动性就越可靠。
