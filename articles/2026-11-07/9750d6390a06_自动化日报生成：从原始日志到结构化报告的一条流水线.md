## 背景

我每天要交一份日报，素材来自三处：服务器日志里的异常统计、Git 仓库的提交记录、内部工单的状态变化。过去的方式是手动翻日志、手动抄数字，每天约 20 分钟，还偶尔漏掉关键报错。

于是我用 OpenClaw 搭了一条流水线：定时采集 → 预聚合 → Agent 生成 → 校验 → 推送。目前稳定跑了两周多，本文记录做法和踩过的坑。

## 问题

最初偷懒的做法是直接丢给 agent 一句"读一下今天的日志，写份日报"，结果不稳定：

- 全量日志塞进上下文，token 爆炸，agent 还经常抓错重点；
- 数字偶尔被"重新发明"，报错次数和 `grep` 出来的对不上；
- 输出格式每次略有不同，没法归档对比；
- 失败是静默的，某天没收到日报才发现链路挂了。

结论很明确：**agent 不适合处理海量原始日志，它适合做摘要之后的那一步**。

## 做法

流水线拆成五步，agent 只参与第三步。

1. **采集层**：cron 定时跑三个采集脚本，分别拉取当日日志、git log、工单变更，统一输出 JSONL 到 `/data/daily/YYYY-MM-DD/`。关键是窗口定义：明确用 `[当天00:00, 24:00)` 且固定时区，避免跨午夜的数据漂移。
2. **预聚合**：一个确定性脚本做 agent 做不好的事——错误码分组计数、Top-N 慢请求、提交按仓库归类。输出一份几百行的摘要 digest，agent 看的是这个，不是原始日志。
3. **Agent 生成**：写成固定的 skill/prompt 模板，输入 digest，输出严格按固定章节（异常、变更、风险、待办）。prompt 里明确两条约束：只允许引用 digest 中出现的数字，不得推算；不输出模板以外的寒暄。
4. **校验层**：生成后跑一个校验脚本，做两件事——章节结构完整性检查；digest 与报告之间的数字一致性 diff。校验不过就带错误信息重试一次，再不过就降级为"原始 digest 附件 + 失败标记"。
5. **分发**：通过 webhook 推到 IM。失败时单独发告警，而不是默默重试。

## 踩坑点

- **时区坑**：cron 按服务器时区跑，日志按 UTC 记，第一天日报里两套时间对不上。解决：整条链路统一时区，采集脚本里显式转换。
- **数字幻觉**：即使 prompt 写了"只引用给定数字"，模型偶尔还是把两个数相加给你一个"总计"。校验层的数字 diff 是唯一可靠的兜底，prompt 约束只能降低概率。
- **格式漂移**：不加校验时，每隔几天就会冒出一份带额外段落的报告。结构校验 + 一次重试基本解决。
- **静默失败**：MCP 工具超时导致采集失败，报告直接缺了一天。后来加了两处心跳：采集完成发一条、报告推送成功发一条，两条都没收到就是链路挂了。

## 可复用建议

- 原则一句话：**能用确定性代码做的，不要交给 agent**。agent 只负责把结构化摘要翻译成人话。
- 输入端做减法比 prompt 调优有效：digest 的质量决定报告的上限。
- 任何 LLM 输出如果要落库或对外发送，都要有 schema 校验和数字核验，这两层比换模型管用。
- 自动化任务的失败通知比成功通知更重要，心跳务必做。

## 总结

这条流水线跑了半个多月，日报从每天 20 分钟降到每天扫一眼。真正的经验不是"用 agent 自动写日报"，而是把任务切开：采集、聚合、校验、分发全部交给确定性代码，agent 只站在 digest 和人之间做翻译。这样即使模型偶尔抽风，流水线的下界也不会塌。
