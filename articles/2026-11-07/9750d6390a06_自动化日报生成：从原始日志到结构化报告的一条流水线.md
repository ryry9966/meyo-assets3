## 背景

团队里的自动化任务——定时脚本、数据抓取、Agent 批处理——每天都在产生大量日志，但"今天到底发生了什么"仍然靠人翻日志或凭记忆写日报。日报本身没有太高的技术含量，缺了却影响同步。目标很明确：让这件事完全自动化，并且数字可信。

## 问题

最容易想到的方案是"把日志丢给大模型总结"，实际跑两天就会暴露三个问题：

1. **数字不可信**：模型会漏数、凑数，而日报最忌讳数字出错；
2. **上下文装不下**：一天的原始日志轻松超过窗口限制；
3. **格式漂移**：每天生成的报告结构不一致，下游没法稳定消费。

由此得出本方案的核心原则：**统计归代码，叙述归模型**。

## 做法

流水线分四层，每层一个脚本、一个 MCP 工具，保持松耦合：

**1. 归一化层。** 所有任务写日志时遵守同一份 JSON Lines 约定：`ts`（UTC）、`source`、`event`、`level`、`payload`。这是整条链路的地基，格式不统一，后面全是补丁。

**2. 聚合层。** 一个纯 Python 脚本按天分片统计：成功/失败次数、错误 Top5、任务耗时分布。输出中间 JSON（带 `run_id` 和日期）并落盘留存。这一步**不经过任何模型**。

**3. 叙述层。** 把聚合 JSON 通过 MCP 工具喂给 Agent，强制按固定 schema 输出：`summary`、`highlights`、`risks`、`anomalies`。模型只负责解读和挑重点，不负责算数；prompt 中明确"不得引入输入之外的数字"。

**4. 渲染与分发层。** 模板渲染成 Markdown，经 Webhook 推送到群里；模型环节失败时降级为只推聚合原始 JSON，保证"至少有数"。

调度上由 cron 触发统一入口，脚本带 `--dry-run` 和幂等保护：相同 `run_id` 重复执行直接跳过。

## 踩坑点

- **时区**：日志用 UTC，日报按本地时区切天。最初没处理，凌晨 0–8 点的任务全被算进前一天。切天逻辑抽成独立函数并补了单测。
- **重复报告**：cron 与手动重跑撞车，群里一天发了三份。加 `run_id` + 状态文件后解决。
- **模型输出不稳定**：早期让模型自由发挥，字段时有时无。改为强制 JSON schema，校验失败重试一次，仍失败走降级路径。
- **异常静默**：聚合脚本挂了但 cron 不报错，连续两天推的是旧数据。补了哨兵检查——聚合产物的 mtime 必须晚于当天零点，否则告警。

## 可复用建议

- 把"日志格式约定"和"聚合 JSON schema"当成接口维护，加版本号；
- 每天的聚合中间产物落盘保留，报告有误可回溯，也能离线重跑；
- 各层封装成独立 MCP 工具，周报、告警摘要可以直接复用聚合层；
- 上线前先 dry-run 一周，人工比对模型叙述与真实数据，确认无误再放开自动推送。

## 总结

这套流水线的价值不在于"让模型写日报"，而在于划清边界：确定性的事交给代码，模型只做它擅长的解读。稳定运行一个月以来，零漏发、数字零错误，维护成本接近于零。有类似需求的建议从归一化格式做起，逐层搭建，而不是先写 prompt。
