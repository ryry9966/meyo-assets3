## 背景

跑常驻 Agent 的第一个工程问题不是"它多聪明"，而是"它什么时候该醒"。目前主流就两条路：**heartbeat 轮询**——定时醒来，检查有没有待办；**推送**——外部事件直接触发一轮运行。很多插件和自动化的第一版只做了其中一种，然后在真实使用里撞墙。

## 问题

轮询的问题很直接：间隔太密，token 和 API 配额白白烧掉，绝大多数醒来发现无事可做；间隔太疏，提醒类任务错过时间窗。

推送的问题更隐蔽：需要暴露 webhook 端点，涉及鉴权、去重、断线重连；本地跑的 Agent 在 NAT 后面，稳定收推送本身就是个工程活。

## 做法

我们的结论是分层触发：**轮询当兜底，推送当加速器**。

1. **按延迟容忍度给任务分类**：硬截止（日历提醒、定时触发）和软任务（摘要、巡检、清理）分开处理。
2. **软任务走 heartbeat**：基础间隔 15–30 分钟，叠加随机抖动，避免多个 Agent 同时醒来挤爆配额。
3. **硬任务走推送**：webhook 收到事件立即触发运行，事件带幂等键。
4. **heartbeat 兼做推送的补偿**：每轮顺便检查"错过的推送队列"，整体做到 at-least-once。
5. **把空转做便宜**：heartbeat 醒来先读一个几行的待办清单文件，无事直接早退，不加载完整上下文、不调用任何工具。这一步做完，轮询的边际成本基本归零。

## 踩坑点

- **推送重试没有幂等键**：同一条事件触发两次运行，用户收到重复通知。加 `event_id` + 去重窗口解决。
- **heartbeat 每轮都带完整 system prompt**：空转成本比干活还高，空闲路径必须最早退。
- **webhook 裸奔**：公网端点一天被扫几百次，触发一堆垃圾运行。至少上 token 校验。
- **SSE / 长连接静默断开**：以为在推送，其实连接早死了。连接层自己也要心跳，且轮询兜底不能删。
- **时区坑**：定时逻辑用了本地时区，DST 切换那天任务整体漂移一小时。存储统一 UTC，展示层再转本地。

## 可复用建议

- 有推送通道时，轮询间隔可以放宽，但**不要取消**——它是可靠性下限。
- 给每次触发记录来源（push / poll），跑一两周拿真实数据调间隔，别拍脑袋。
- 事件幂等键是推送侧性价比最高的一笔投入，第一天就该有。

## 总结

轮询和推送不是二选一：轮询是正确性地板，推送是延迟与成本优化。建议的落地顺序是——先用最笨的轮询跑通全流程，再对高价值路径加推送，最后让 heartbeat 降级成补偿机制。顺序反过来做，大概率返工。
