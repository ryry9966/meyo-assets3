## 背景

在 OpenClaw 上跑内容自动化，最容易低估的是"最后一公里"：AI 生成 Markdown 很容易，但从生成到真正发到公众号、知乎、掘金和自建博客之间，隔着一大段格式适配的脏活。直接复制粘贴，格式基本必掉。

## 问题

问题分两层。

第一层是生成物本身不规范：标题层级跳跃、混入内联 HTML、图片用相对路径、代码围栏不标语言、偶尔编造链接。单篇人肉修一下可以，规模化就不行。

第二层是平台差异：公众号不支持 Markdown，渲染时剥掉 class 和 `<style>`，正文外链不可点，图片必须走微信 CDN；知乎对 HTML 是白名单制；博客自由度最高，但代码高亮、图表要自己处理。同一篇内容，五种目的地就是五套约束。

## 做法

整条管线分五步，核心原则：agent 只碰源头和修复，格式转换全部交给确定性代码。

**1. 约束生成。** 在 agent 的 skill 提示里固化一份产出规范：全文只允许一个 H1；图片一律相对路径占位；代码围栏必须标语言；禁止内联 HTML 和裸链接，引用统一收进文末。这份规范不是散文，是下一步能机器校验的规则。

**2. lint 校验环。** 用 remark/mdast 写十几条自定义规则做结构校验，不通过就把错误清单回喂给 agent 修复，循环两三轮。失败信息要具体到行，否则修复效率很低。

**3. 规范化为中间表示。** lint 通过后做一次 normalize：统一标题层级、压平三层以上的嵌套列表、收敛 frontmatter 字段。得到唯一事实源，之后所有平台从它派生，而不是从原始生成物派生。

**4. 平台适配器。** 每个平台一个纯函数：中间表示 → 平台 HTML。公众号渲染器把样式全部内联，代码块用 shiki 预渲染成内联样式的 HTML；图片在这一步上传 CDN 并改写 URL；Mermaid、KaTeX 统一预渲染成静态图。知乎、掘金走各自支持的子集，复用同一份 normalize 产物。

**5. 预览卡点。** 每步产物落盘归档，生成静态预览页，人工确认后再由脚本调 API 发布或落到剪贴板。发布可以自动化，确认这一步不建议省。

## 踩坑点

- 公众号会剥 class 和 `<style>`，必须全内联；表格在移动端容易溢出，控制在 3–4 列并固定宽度。
- 相对路径图片直接发必裂；微信图片有防盗链，产物被外站复用时还要处理 referer。
- 最想省的一步最不能省：让 LLM 直接"转成公众号 HTML"看着省事，实际不可测——同一输入两次输出不同、样式漂移、没法做回归。转换必须走代码。
- AI 爱写深层级列表和滥用加粗，各平台渲染差异大，normalize 阶段就压掉。

## 可复用建议

- 规范做成可执行的 lint 规则，别只写在文档里。
- 规范化与适配分离，平台差异全部收敛在适配器；新增平台只是加一个纯函数。
- 保留每步产物（原始生成、修复后、normalize 后、各平台产物），出问题能回放定位。
- 图片上传这类副作用动作封装成脚本或 MCP 工具，管线里只调用不实现。

## 总结

这条管线的精神是"一次规范化，多次渲染"。全部成本大约两三百行代码加十几条 lint 规则，换来的是多平台发布从手工搬运变成一条命令。真正值钱的不是转换器本身，而是"AI 产出必须先过机器校验"这个约束——它让整条链路从碰运气变成了可回归的工程。
