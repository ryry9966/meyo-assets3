## 背景

写 commit message、起分支名、清理废弃分支，这些活不难，但琐碎。真正的痛点是：写代码的人不愿在这上面花心思，一个月后回看提交历史一团糟。让 AI 助手接入 Git 是个自然的选择——diff 解读和 commit message 生成恰好是它擅长的。但在 OpenClaw 里给 agent 开 git 权限之前，有几个问题必须先想清楚。

## 问题

我们仓库里常见的三类失控：

1. 提交信息随意，`fix`、`update`、`wip` 占一半，出问题时 git log 没有检索价值；
2. 一次提交塞多个不相关改动，回滚粒度粗；
3. `feat/*` 分支越积越多，没人敢删。

这些本质是纪律问题，靠自觉不可持续，适合交给自动化。

## 做法

核心思路：**给 agent 最小够用的 Git 工具集，约定写进仓库，破坏性操作加确认门槛。**

**第一步：收敛工具面。** 不给完整 shell。封装成窄接口：只读的 `diff`、`log`、`status`、`branch -vv`；写操作只留 `commit`、`branch create/delete`、`switch`。rebase、reset、push 一律不开放，由人执行。

**第二步：把团队约定写成 agent 可读的规范文件**（如 AGENTS.md）。内容包括 Conventional Commits 格式、scope 枚举、分支命名 `feat/xxx` `fix/xxx`、单次提交 diff 上限。agent 生成 message 前先读这份文件，风格就稳定了。

**第三步：定义工作流。**
- 提交流程：agent 读 status + diff → 判断是否需要拆分 → 逐块暂存 → 按 diff 实际内容拟 message（要求引用 diff 中的证据，禁止脑补）→ 输出待确认 → 人工点头后才 commit。
- 分支流程：从 main 拉任务分支；每周跑一次清理任务，只删「已合并且超过 7 天」的本地分支，远程操作必须显式授权。

**第四步：加护栏。** pre-commit hook 保持不变，agent 不得带 `--no-verify`；所有写操作记日志；先跑两天 dry-run，只输出"它会做什么"，确认无异常再放开执行。

## 踩坑点

- **agent 倾向一把梭**：把改动一次全 add，message 写得四平八稳但混了无关改动。必须在指令里强制"先分类再暂存"，review 时检查 diff 范围。
- **message 润色过度**：diff 只改了一行配置，agent 能写出三行"架构级"描述。要求 message 每句话对应 diff 里的具体行，能压掉大部分幻觉。
- **权限给太宽**：早期图省事开放了 `git reset`，agent 处理冲突时直接 reset 掉了半天的手工调整。写操作白名单要抠得死。
- **分支清理误删**：别只看分支名，必须用 merge-base 判断是否已合并，保留宽限期，删除前列清单人工过目。

## 可复用建议

1. 约定写在仓库里而不是 agent 配置里——任何人、任何 agent 进来都遵守同一套规范；
2. 只读全放开，写操作按命令白名单，破坏性命令永远不开放；
3. agent 的输出是"提案"，commit 留给人确认，直到你对它的质量建立信任；
4. 先自动化最痛的部分（commit message），分支清理这类低频操作放后面。

## 总结

这套流程上线后，提交历史可读性明显好转，废分支不再堆积。但要说清楚：AI 助手的角色是"执行纪律的助手"，不是"替你做决定的人"。约定是人定的，白名单是人抠的，最后的确认也是人按的。把它当成一个不知疲倦、偶尔犯傻的初级同事来管理，就对了。
