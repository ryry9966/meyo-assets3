## 背景

Agent 的价值不在于会聊天，而在于能动手。OpenClaw 里跑一个 Agent，最终都要落到“调外部服务”这件事上：查库存、发工单、读数据库。模型本身只会生成一段结构化的调用意图，真正把意图变成一次成功的请求，中间隔着鉴权、超时、错误语义、返回值裁剪这一整套工程活。我们把这中间的过程叫“握手”——握手不通，Agent 再聪明也只能停留在嘴上。

## 问题

新手最常见的失败模式不是“调不通”，而是“调通了但没用好”：

1. 工具描述含糊，Agent 猜参数，传了个格式错误的日期字符串；
2. 上游 API 返回 20KB 的 JSON，原样塞进上下文，两轮对话 token 就烧光了；
3. 请求失败后没有明确的错误语义，Agent 陷入无限重试；
4. 密钥写在 prompt 或调试日志里，截图一贴，Key 就泄了。

这些都不是模型的问题，是适配层没做好。

## 做法

我们的经验是把对接拆成五步：

**第一步：收敛工具面。** 不要把上游 API 的十几个端点原样暴露给 Agent。一个工具对应一个业务能力，比如 `create_ticket` 而不是 `post_api_v3_tickets`。工具越少、语义越清晰，调用准确率越高。

**第二步：写好 schema 和描述。** 参数描述按“给新来的实习生写文档”的标准写：类型、格式、示例值、什么场景该用这个工具。这段描述会直接进入模型上下文，值得花时间打磨。

**第三步：鉴权放配置层。** API Key 走环境变量或配置文件，插件初始化时注入，绝不出现在对话里。MCP server 的思路值得参考——凭据在 server 侧持有，模型只看到工具能力。

**第四步：设计返回值。** 返回给模型的结果要“瘦身”：只留关键字段；出错时返回结构化的 `error_code` 加一句人话提示（比如“日期格式应为 YYYY-MM-DD”），让模型有能力自我纠正。

**第五步：加固边界。** 客户端设超时（建议 10–30 秒）、限制重试次数、对上游做基本限流。每次调用记录 in/out 日志，排障时这就是现场的全部证据。

## 踩坑点

- **别让 Agent 拼完整 URL。** 路径参数让它拼极易出错，全部收进适配层的函数签名里。
- **错误别只返回 `{"success": false}`。** 模型拿到这种信息只能瞎猜，错误信息要指向“怎么改”。
- **警惕上游 API 变更。** 适配层加版本号和冒烟测试，上游一改字段你至少能第一时间发现。
- **流式接口慎接。** SSE/WebSocket 对多数 Agent 场景意义不大，能轮询就轮询，简单可靠。

## 可复用建议

把每个工具适配器当成独立小项目维护：独立目录、独立测试、README 写清“这个工具解决什么问题”。团队内沉淀一个适配器模板，把鉴权、超时、日志、错误包装四件套预置好，新对接服务时只填业务逻辑，能省一半时间。

## 总结

Agent 对接外部服务，本质是给模型一双可靠的手。OpenClaw 的插件/MCP 机制解决了“怎么接”，但“接得稳不稳”取决于适配层的工程质量：收敛工具面、写清描述、管好凭据、裁剪返回、加固边界。这五件事做到位，握手才算真正握上。
