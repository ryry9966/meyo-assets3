## 背景

社区里跑 Agent 定时任务的人不少：MCP 工具调用、插件巡检、数据抓取，每天产生大量零散日志。这些日志散落在 cron 输出、MCP server 的 stderr、插件自己的文件里，出了问题只能人工翻。我给自己搭了一条「原始日志 → 结构化日报」的流水线，跑了近一个月，稳定性和成本都可控，把做法沉淀下来。

## 问题

核心矛盾有三个：

1. **格式不统一**。自研脚本输出 JSON，MCP 日志是带时间戳的文本行，插件可能只有一个退出码。
2. **噪声掩盖信号**。一天几千行 INFO，真正需要人看的失败可能只有十几条。
3. **摘要环节要可靠**。用 LLM 写日报很方便，但统计数字不能让它编。

## 做法

流水线四步，每步落盘中间产物，按「日期/版本」命名，任何一步失败可单独重跑。

**第一步：统一采集。** 写了个 wrapper 包住所有定时任务，输出 JSONL 追加到按日期分片的目录。约定公共字段：`ts`（UTC）、`task_id`、`level`、`status`、`duration_ms`、`summary`。新任务接入只改 wrapper 参数，不动流水线。

**第二步：归一化。** 对存量日志（如 MCP server 日志）写适配器，逐行解析进同一 schema。解析失败的行不硬扛——丢弃并累加计数器，计数器本身进日报，避免静默吞数据。

**第三步：规则聚合 + LLM 摘要。** 先用代码算硬事实：错误总数、各任务成功率、耗时 Top 5、失败明细，这些数字直接写进模板，不经过模型。再把「失败明细 + 异常时段日志片段」（限制在 3–5KB）交给 LLM 做归因摘要和措辞整理。LLM 只解释，不产生任何统计数字。

**第四步：渲染与投递。** 模板渲染成 Markdown，两层结构：开头 TL;DR（状态灯、错误数、三句话总结），后附明细表格。投递走 Webhook，失败重试一次，仍失败则落盘到待发目录，次日补发并标注。

## 踩坑点

- **别把全量日志喂给模型。** 早期直接丢一天日志让它总结，token 开销大，还会「脑补」不存在的故障原因。规则先过滤，上下文卡在几 KB 内，效果反而更好。
- **时区。** 多台机器的日志混着本地时区和 UTC，按天切分会漏数据。统一 UTC 存储，只在展示层转本地时区。
- **LLM 的「温和偏差」。** 模型倾向于把事故写得不痛不痒。能算的指标全部代码生成；模型输出只允许出现在归因段落，且要求引用给定的日志行号。
- **流水线自身要可观测。** 日报任务挂了没人知道最尴尬。wrapper 写心跳文件，超过 24 小时未更新由独立的轻量告警戳一下。
- **格式漂移。** MCP 升级后日志格式变过一次，适配器解析成功率掉了 30% 才被发现。现在解析成功率本身就是日报里的一个指标。

## 可复用建议

1. **Schema 先行。** 统一日志 schema 是整条流水线最值钱的部分，比摘要模型重要得多，新工具接入前先对齐字段。
2. **事实与解释分离。** 代码算数字，模型管措辞和归因，责任边界清楚。
3. **中间产物全落盘。** 排障能定位到具体哪一步坏了，重跑不必从头来。
4. **报告分层。** 一屏 TL;DR + 可选明细，让日报同时支持「扫一眼」和「深挖」两种读法。

## 总结

日报的价值不在文字漂亮，而在稳定、可信、可追责。结构化做扎实了，LLM 只是最后润色的那 10%。这套方案没有引入重型组件：一个 wrapper、几个适配器、一段聚合脚本加一次 LLM 调用就能跑起来，小团队可以直接照搬起步。
