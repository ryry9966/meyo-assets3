## 背景

团队里每天发日报的人大概都经历过：早上打开七八个面板，把昨天的构建结果、agent 任务执行情况、服务日志里的报错复制进一个模板，再补两句"今日小结"。单次只要二十分钟，但它每天都发生，而且每个人汇总的口径都不一样。

我们的做法是把这件事做成流水线：定时拉取原始日志 → 结构化 → 聚合 → 生成报告 → 推送。LLM/agent 只出现在最后一步，负责"叙述"，不负责"算数"。

## 问题

直接让 agent 读原始日志写日报，我们试过，主要有三个问题：

1. **数字不可信**。让模型从几千行日志里数"昨天失败了几个任务"，数错是常态，而且错得很自信。
2. **上下文装不下**。多来源日志塞进 prompt，要么截断漏项，要么 token 成本失控。
3. **不可复现**。同样的日志跑两次，得到两份不一样的日报，没法审计。

结论很明确：数值必须由确定性代码算出来，LLM 只处理模糊的部分。

## 做法

流水线分四步，每步是独立脚本，可单独重跑：

**1. 采集与规范化。** 定时任务（cron 或 OpenClaw 的定时触发）拉取各来源：CI 结果走 API，服务日志走日志平台查询，agent 执行记录从任务库导出。统一转成 JSONL，每行带 `source`、`timestamp`、`level`、`payload`。这一步纯代码，无 AI。

**2. 结构化与校验。** 每个来源一个解析器，输出对齐到固定的中间 schema（比如"构建记录"必须有 `status`、`duration`、`branch`）。解析失败或字段缺失直接进错误队列，不静默丢弃。这一步是整条流水线的地基。

**3. 聚合计算。** 脚本对中间 JSON 做统计：成功/失败计数、耗时分布、错误信息按错误码+首行归并取 Top。产出一份"日报中间产物" JSON，所有数字都在这里，可 diff、可审计。

**4. 报告生成与推送。** 模板引擎把中间产物渲染成固定结构的 Markdown；然后调 agent，让它只读这份 JSON，写"异常解读"和"今日小结"两段——输入受限，输出就只能围绕事实展开。最后经 webhook 推送到群/邮件，同时归档到 Git 仓库留痕。

## 踩坑点

- **时区。** "昨天"的定义必须显式声明。我们按业务时区切天，日志统一存 UTC，查询时转换；跨天任务（23:50 开始、00:10 结束）的归属规则写进 schema，否则周五和周一的日报永远对不上。
- **格式漂移。** 上游服务升级后悄悄改了日志格式，流水线不报错，只是日报里那块变成零。对策：schema 校验失败即告警；关键指标设"非零预期"，连续为零也告警。
- **失败静默。** 流水线挂了比报告难看更糟。现在任何一步失败都发独立告警，且与日报走不同通道。
- **agent 输出越界。** 早期模型会在小结里"补充"数据（其实是编的）。改成 prompt 里明确"只能引用输入 JSON 中的数值，缺失就写'无数据'"，生成后定期抽查。
- **报告膨胀。** 模板固定八个区块，异常置顶，正常项折叠成一行。长度稳定后，阅读率才回升。

## 可复用建议

- **中间产物 JSON 是核心资产**。schema 稳定后，下游换模板、换推送渠道都不用动上游。
- **确定性优先**。能用代码算的绝不交给模型，LLM 只做归因和叙述。
- **每步幂等**。带日期参数，任何一天都能重跑，方便回溯和补报。
- **留原始快照**。除中间产物外，保留当日原始日志的压缩归档，出争议时有据可查。

## 总结

流水线上线后，日报从"每天二十分钟的手工活"变成"早上九点自动出现在群里的一条消息"，信任度反而比手写时期更高——因为每个数字都能溯源到中间产物，每句话都锚定在真实数据上。经验浓缩成一句：先让数据结构化，再让 AI 说话。
