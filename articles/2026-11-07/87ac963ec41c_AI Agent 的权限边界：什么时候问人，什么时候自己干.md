## 背景

Agent 接上 MCP 和插件之后就有了手：写文件、跑命令、调外部 API、发消息。于是问题来了——哪些动作它自己干，哪些必须停下来问人。

实践中常见两个极端：要么每次工具调用都弹确认框，用户麻木之后一路点"允许"，确认形同虚设；要么什么都不问，直到某天 agent 把清理脚本跑上了生产库。这是设计问题，不是模型问题。

## 问题本质：三个维度

拆开看，"要不要问人"只取决于三件事：

- **可逆性**：能否撤销？工作区写文件、开分支提交是可逆的；发出去的邮件、扣掉的钱、删掉的数据不可逆或撤销成本极高。
- **影响范围**：只碰沙箱/工作区，还是会触达生产环境、真实用户、外部系统？
- **意图明确度**：用户是否明确要求了这个动作和参数？"改掉 config 里的超时"是明确的；agent 自己推理出"顺便重启服务"是推断的，推断的动作要多一道确认。

三个维度可以压成四级：

- **T0 自动执行**：只读操作、沙箱内写入，零确认。
- **T1 自动 + 留痕**：工作区写文件、分支上 commit、无副作用的内部调用。不问，但每步记日志、可回滚。
- **T2 单次确认**：部署、对外发消息、花钱的调用、带 force 的操作。先展示"执行什么 + diff + 影响"，批准后再跑。
- **T3 永远人工**：删生产数据、改凭证、动权限体系。agent 只负责准备方案和材料。

## 做法：闸门做在工具层，不写在 prompt 里

最容易踩的坑是把这些规则写进系统提示词（"删除前必须询问用户"）。长上下文、prompt 注入、模型波动都会让它失效。正确的位置是 MCP server / 工具适配层：

1. **注册时给每个工具打级**。按工具 + 关键参数共同决定，而不是只看工具名——同一个 `exec`，目标是本地容器和目标是跳板机，级别不同。
2. **T2 工具默认 dry-run**。第一次调用只返回将要执行的命令和 diff，不落地；用户批准后发放一个绑定该动作签名的 approval token 才真正执行，token 设 TTL，防止旧批准被复用。
3. **确认内容要具体**。不是"是否允许执行？"，而是"将在 staging 重启 deploy/api，影响 3 个副本"。人审批的是 diff，不是 yes/no。
4. **计划批准与执行闸门分离**。批准一份计划相当于预授权清单，但执行时每个 T2 动作仍要核对是否在清单内、参数是否被动过。

## 踩坑点

- **确认疲劳**：问得越多，用户越容易盲批。降低提问率的正确方式是提高可逆性（把更多操作挪进 T1），不是把确认框做得更容易点掉。
- **环境漂移**："这只是 staging"，直到某天环境变量指到了生产。分级依据必须是目标标识本身（host、集群 ID、账号），不是 agent 自认为的环境。
- **批量确认**：agent 把 50 步打包成"可以开始吗？"问一次。批准一旦被泛化，后面 49 步就脱离了监督，批准必须绑定具体动作。
- **危险默认值**：`rm -rf`、`--force`、`drop table` 这类参数值得在适配层单独拦截，哪怕工具本身是 T1。

## 可复用建议

- 默认可逆，让"问人"成为低频且有信息量的事件：每次提问都带上动作、目标、diff、后果。
- 没有回滚路径的动作，不配自动执行。
- 分级一次做在适配层，团队共享同一份策略配置，不要每次写 prompt 重新辩论一遍。
- 出一次事故，回头调一次分级。这张表是活的，不是评审一次就归档的文档。

## 总结

权限边界不是价值观问题，是系统设计问题：可逆性 × 影响范围 × 意图明确度，三个轴一量，绝大多数动作该不该问人是显然的。工程落点就三句话：闸门做在工具层，确认绑定具体动作，人审 diff 而不是点按钮。Agent 的自主性不是靠少问挣来的，是靠把更多事情变得可逆挣来的。
