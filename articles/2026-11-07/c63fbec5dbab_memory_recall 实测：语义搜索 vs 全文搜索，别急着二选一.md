## 背景

给 Agent 加持久记忆，绕不开 memory_recall 这一层：用户发消息，先从历史记忆里捞几条相关条目注入上下文。我的记忆库约两千条，来源是对话摘要、操作日志和手工笔记。最初直接上向量检索（语义搜索），效果时好时坏；换成全文检索（BM25）又遇到另一个方向的问题。最终落地的是混合方案，这里把对比结论和踩坑记录下来，希望帮你少走弯路。

## 问题：两种检索各自会在哪里翻车

语义搜索的优势是同义改写：用户问"之前那个部署报错"，能召回措辞完全不同的故障记录。但短板也明显：

- **精确 token 召不回**：文件路径、变量名、错误码、日期这类强标识，embedding 经常给出"语义相近但不对"的结果；
- **领域偏移**：通用 embedding 模型对"中文口语 + 代码"混合文本的表征不稳定，同一句话换个说法，相似度分数波动很大。

全文检索则相反：关键词命中就是命中，可解释性强；但用户不会用你入库时的原词，"那次故障"和"上个问题"指同一件事，原文没这个词就漏召回。

方向结论：这不是二选一，是互补。

## 做法：混合召回 + 时间衰减

1. **入库结构统一**：正文 + 元数据（时间戳、来源、标签、会话 ID），存 JSONL，原始文本永远保留，方便日后换索引方案重建；
2. **双路检索**：一路本地 embedding 算余弦相似度，一路 jieba 分词后跑 BM25。两千条规模内存里暴力算就行，没上向量数据库；
3. **融合排序**：用 RRF（倒数排名融合），两路各取 top 20 合并，比手调融合权重省事得多；
4. **过滤与重排**：按标签硬过滤（如只查"部署"类），加时间衰减因子给近期记忆轻微加权；
5. **组装上下文**：最终取 top 5，附来源和时间戳，让模型自己判断可信度。

如果你是通过 MCP 暴露 memory_recall 工具，这套管线直接塞进 tool 的 handler 里即可，接口不用动。

## 踩坑点

- **中文 BM25 别按空格切分**，必须先分词，否则召回率惨不忍睹；
- **切块别贪大**：最初按整段对话存，一条几百字，召回后塞爆上下文且相关内容只占一角。改成"一事一条"重写入库后效果立竿见影；
- **相似度分数没有跨库意义**：阈值不能复用，换 embedding 模型就失效，得重新标定；
- **时间指代查询**（"上周那个问题"）纯靠相似度必挂，必须靠元数据过滤兜底。

## 可复用建议

- 默认上混合检索，RRF 起步，别一上来调融合权重；
- **一万条以下不需要向量库**：一个数组 + 暴力余弦足够，部署简单、零额外依赖；
- 攒一个 20~30 条的小评测集（真实查询 + 期望命中的记忆 ID），每次改检索策略跑一遍，比凭感觉靠谱；
- **入库质量 > 检索算法**：原子化的记忆条目，比任何花哨的召回策略提升都明显。

## 总结

语义搜索解决"换了说法也能找到"，全文搜索解决"精确命中"，混合方案加元数据过滤基本覆盖了日常场景。真正决定 memory_recall 上限的，不是选哪个检索器，而是记忆怎么切、怎么存、带不带结构化元数据。推荐路径：先保证入库质量 → 上混合检索 → 用评测集持续迭代。这条路线性价比最高，也最容易在你们自己的 Agent 里复现。
