过去几个月，“Agent 正在重做数据库”从一句营销口号，变成了基础设施圈认真讨论的命题。逻辑其实很直接：数据库四十多年来的几乎所有设计——索引、优化器、权限模型、接口协议——都建立在“使用者是受过训练的工程师，写的查询精准且量少”这个前提上。而当 Agent 成为数据的第一调用方，这个前提塌了，塌了的地方就要重修。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-07/d5d5079932b23000.png)

## 四十多年的前提：数据库是给“人”用的

- 1970 年 Codd 提出关系模型，SQL 在七十年代中期成型。从 IBM 的 System R 到 Oracle，这条技术路线服务的对象非常明确：会写 SQL 的人。
- 围绕“人写查询”演化出一整套经典技术：B+ 树索引加速点查，查询优化器重写执行计划，物化视图预计算，连接池控制并发——所有权衡都默认查询是稀缺、昂贵、深思熟虑的。
- OLTP 和 OLAP 在九十年代分家，也是同一逻辑的延伸：人写分析报表太重，所以拆出专门的分析型引擎。

一句话概括：过去数据库优化的对象是“查询”本身，而“谁在问、为什么问、怎么问”从来不是变量。这些设计极其成功，SQL 至今是数据领域的通用语——问题不在技术不好，而在前提变了。

## Agent 拆掉了哪三条假设

1. **用户从人变成机器。** 一个 Agent 工作流一晚上发起的查询，可能超过一个工程师一年手写的 SQL 量。连接数的含义从“多少个开发”变成“多少个正在跑的任务”。
2. **查询从“一次写对”变成“试探式探索”。** 人的模式是先想清楚再执行；Agent 的典型行为是查一次、看结果、改条件再查——短平快、高并发、大量冗余，`SELECT *` 几乎是它的口头禅。
3. **数据从“行列”变成“语义”。** Agent 要回答“上季度活跃用户为什么下降”，光有表结构没用：它需要知道“活跃”的口径定义、哪些表可信、join 键是什么。这些信息在传统数据库里没有位置。

## 三条改造路线，改的不是同一个东西

- **语义层**：把指标口径、业务术语、表间关系沉淀成 Agent 能读的中间层。dbt 的 metrics、Cube 这类产品在抢这个位置。它改的是“理解”，不动存储。
- **检索混合化**：向量数据库（Milvus、Qdrant、pgvector）负责非结构化数据，与关键词倒排、结构化过滤做混合检索，充当 Agent 的“感觉器官”。Postgres 靠 pgvector 一步到位，也是它近年稳居 Stack Overflow 年度调查榜首的注脚之一。
- **Agent 原生工作流**：MCP 这类协议把“数据库接入 Agent”标准化成即插即用；Supabase、Neon 被 AI 编程工具带火，Neon 甚至被 Databricks 收购——“对 Agent 友好”已经涨到并购级估值。

## Text-to-SQL 的真实水位：演示惊艳，落地骨感

- 学术基准上，头部模型在 Spider 这类经典评测里执行准确率早已冲到八成以上；但换到模拟企业真实环境的 Spider 2.0，公开论文里最强系统也只有两三成。
- 差距来自哪？多表 join、方言差异、脏 schema、没写进文档的业务规则——这些恰恰是企业数据库的日常。
- 更危险的是另一类失败：SQL 语法正确、能跑、但语义错了，返回一份看似合理的错误报表。报错会被人发现，错误的结果不会。
- 所以结论是：瓶颈不在“生成 SQL”这一步，而在数据库端缺少让 Agent 理解业务的基础设施。这才是“重做”二字的真实所指。

## 真正会被重做的四个部件

1. **接口层**：从驱动和 CLI，走向 MCP、语义 API，工具调用成为一等公民。
2. **优化器**：Agent 写出的查询模式（海量短查询、宽 SELECT、嵌套子查询）会倒逼引擎内置查询预算、自动改写和语义缓存——相似问题直接命中缓存，不再重跑。
3. **权限与审计**：Agent 拿着高权限账号跑任务的场景下，行级权限、只读副本、逐条可回溯的审计日志，从“最佳实践”变成“生存必需”。
4. **记忆**：Agent 的长期记忆与会话上下文存储，会从外挂组件逐步长进内核。

## 收尾的三条冷思考

1. **先补语义层，别急着换引擎。** Postgres + pgvector + 一个 MCP 服务能覆盖大多数团队的场景；指标口径混乱的组织，换什么数据库都白搭。
2. **护栏先行。** 给 Agent 单独账号、行级权限、查询预算和超时熔断，再谈智能化。一条失控的笛卡尔积查询就能把生产库打挂，这和 Agent 聪不聪明无关。
3. **让日志说话。** 先让 Agent 在只读环境跑两周，分析真实查询分布、失败率和成本曲线，再决定是加向量检索、上语义缓存还是换引擎。“重做”应该由工作负载驱动，而不是由发布会驱动。

四十年来数据库行业换过无数引擎，但从没换过调用方。这次来了一个不睡觉、不摸鱼、也不读文档的新用户——引擎们确实该重修了。
