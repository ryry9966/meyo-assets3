## 背景

MCP（Model Context Protocol）是 Anthropic 在 2024 年底开源的协议，目标是把「大模型应用 ↔ 外部工具/数据」的连接方式标准化。基于 JSON-RPC 2.0，支持 stdio 和 HTTP 两种传输。一年多下来，它基本成了 Agent 生态里事实上的工具接入标准：Claude Desktop、各类 IDE、自研 Agent 框架都在往 MCP 上靠。

## 它到底解决了什么

核心是 **M×N 集成问题**。假设有 M 个 AI 应用（桌面助手、IDE、你自己的 Agent），N 个工具/数据源（GitHub、数据库、文件系统、内部 API）。没有统一协议时，每一对组合都要单独写适配代码，M×N 份胶水，且互不通用。MCP 把它降成 M+N：应用实现一次 MCP Client，工具方实现一次 MCP Server，两边按统一协议握手。

第二个是**上下文孤岛**。模型要用你的本地文件、数据库、内部系统，过去要么靠复制粘贴，要么写一次性函数。MCP 提供三类标准原语：

- **Tools**：模型可主动调用的动作（查库、发请求）
- **Resources**：可读取的上下文数据（文件、文档）
- **Prompts**：预置的提示模板

还有一个容易被忽略的价值：**解耦**。工具层和应用层可以分开迭代，工具升级不动 Agent 代码。

## 最小上手路径

以 Python SDK 写一个最小 Server：

1. `pip install "mcp[cli]"`
2. 用 FastMCP 定义两三个工具，docstring 写清楚（模型靠它选工具）
3. `mcp dev server.py` 起 Inspector，确认工具能列出、能调用
4. 在宿主侧注册 stdio 命令（Claude Desktop 的 config，或自研 Agent 的 MCP Client）

应用方则反过来：选一个带 MCP Client 能力的框架，先挂 filesystem、fetch 这类社区 Server 跑通链路，再决定自己包什么。

## 踩坑点

1. **stdio 下 stdout 是协议通道**。任何 `print` 调试输出都会污染 JSON-RPC 流，表现为「Server 起不来/握手失败」。日志一律走 stderr。
2. **工具描述决定模型行为**。描述含糊，模型就会选错工具、传错参。把它当成写给新同事的接口文档来写。
3. **工具数量失控**。一个 Server 塞几十个工具，上下文膨胀、选择准确率下降。按域拆分。
4. **权限想清楚再开**。挂了 filesystem Server，Agent 就能读写整个目录树。先只读，写操作逐步放开并加确认。
5. **版本兼容**。HTTP 传输相关规范仍在演进，Client/Server 的 SDK 版本差太远会出现能力协商失败，先锁版本。

## 可复用建议

- 一个 Server 只管一个领域，别做全家桶
- 工具参数保持扁平的标量结构，复杂嵌套 schema 会显著提高传参出错率
- 写操作默认带确认或 dry-run
- 排协议问题用 Inspector，别靠裸日志猜
- 包内部系统前先问一句：它真需要被 Agent 频繁调用吗？有些场景一个定时脚本更省事

## 总结

MCP 没有让 Agent 变聪明，它只是把「接入」这件脏活标准化了：工具方一次实现处处可用，应用方生态拿来即用，团队获得工具层与应用层的解耦。它不解决安全、鉴权和工具质量这些真正难的问题——那些仍然要你自己把关。理解了这一点，就知道什么时候该上 MCP，什么时候不该。
