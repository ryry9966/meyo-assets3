## 背景

我们社区每天有几个固定的内容动作：晨报汇总、周度精选、新教程转发。之前全靠人肉——找素材、写摘要、排版、发帖，单次约 40 分钟，还经常因为忙而断更。于是决定用 OpenClaw 搭一个发帖机器人，把这条流水线自动化。目标定得很克制：不是“全自动无人值守生产内容”，而是“机器出草稿，人做最后把关，发布环节零手工”。

## 问题

拆下来是四个工程问题：

1. **素材从哪来**：RSS、GitHub Trending、站内精华帖，来源分散且格式不一；
2. **内容怎么保证可信**：LLM 写摘要时容易编造标题、链接甚至数据；
3. **怎么保证不重复发、不错发**：定时任务重试、网络抖动都可能导致重复发布；
4. **凭据怎么管**：论坛 token 不能进 prompt，也不能落日志。

## 做法

最终架构分三层：

**调度层**：cron 触发一个 OpenClaw 任务，附带上下文（本期主题、来源列表、去重键）。

**Agent 层**：一个 agent 负责编排，通过三个 MCP 工具干活：

- `fetch_sources`：拉取各来源，统一成 `{title, url, summary_source}` 结构；
- `generate_draft`：只允许基于 fetch 结果生成，prompt 里明确“禁止使用未出现在输入中的 URL”；
- `submit_post`：全系统唯一有写权限的工具，只接受 draft_id，不接受自由文本。

**状态层**：SQLite 存三张表——`sources`（已抓取）、`drafts`(草稿及状态）、`posts`（发布记录，URL 做唯一索引）。

完整流程：cron → fetch → generate → 写入 drafts → **人工审核**（可选跳过）→ submit → 回写 posts。dry_run 模式下 submit 只打印不发。

## 踩坑点

1. **重复发布**：首次上线遇到网络超时，重试逻辑直接重跑整个任务，同一内容发了两遍。修复：把去重键（来源内容 hash）的检查前置到 generate 之前，且 submit 内部先查 `posts` 表，幂等通过后才调发帖 API。
2. **幻觉链接**：模型“补全”过一个不存在的教程链接，格式完全正确，肉眼难辨。修复：submit 校验阶段对每条 URL 发 HEAD 请求，404 即整单打回，并把失败样例回灌进 prompt。
3. **触发论坛风控**：发帖间隔写死 1 秒，连发 5 条后被限流。修复：加随机抖动（5–15 秒）+ 失败退避，单次任务发帖上限设为 3。
4. **Markdown 被吞**：正文里的下划线和尖括号被论坛渲染器吃掉。修复：在 submit 前做一轮转义白名单处理——别指望模型自己转义对。
5. **时区坑**：cron 按 UTC 跑，晨报晚发八小时。修复：调度层显式指定时区，并在任务上下文里注入“今天”的日期，不要让模型自己猜。

## 可复用建议

- **写权限收敛到一个工具**：agent 能调的写操作越少，事故半径越小；
- **幂等键贯穿全链路**：fetch、draft、post 用同一个 hash 串起来；
- **先 dry-run 一周**：把草稿输出当日报看，稳定后再放开真实发布；
- **工具调用日志全量落盘**：每次 MCP 调用的入参出参都留档，排障全靠它；
- **模型只做生成，不做决策**：发不发、发几条、什么顺序，全部由代码和状态表决定。

## 总结

这个机器人目前稳定跑了六周，人工介入从每天 40 分钟降到约 3 分钟（审一眼草稿）。最大的心得是：发帖机器人的难点不在“让 AI 写内容”，而在发布环节的工程可靠性——幂等、校验、限流、凭据隔离，这四件事做扎实了，Agent 编排反而是最简单的部分。MCP 的价值也正在于此：把每个有副作用的动作封装成小而明确的工具，Agent 的自由度被约束住了，自动化才敢真正上线。
