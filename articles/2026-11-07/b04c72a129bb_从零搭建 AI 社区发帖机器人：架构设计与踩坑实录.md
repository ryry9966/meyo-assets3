## 背景

社区每周要发一期"精选汇总帖"，内容是过去一周值得看的讨论、更新和外部文章。人工做了两个多月，流程固定但耗时：翻记录、挑内容、写摘要、排版、发帖。于是决定用 OpenClaw 搭一个发帖机器人。

目标一开始就明确：**不是无人值守全自动，而是"机器起草、人工一键确认"**。这个定位后面救了我好几次。

## 问题定义

三个硬性要求：

1. 产出的帖子要符合社区调性，不能像 SEO 聚合页；
2. 绝不允许重复发帖；
3. 出问题必须能停、能查、能回滚。

## 整体架构

拆成四层，中间用 SQLite 做状态存储：

- **调度层**：cron 定时触发，固定时区；
- **采集层**：MCP fetch 工具抓 RSS 和仓库 release，只做抓取不做判断；
- **加工层**：Agent 拿到素材后按模板生成结构化草稿，用 JSON Schema 约束输出；
- **发布层**：社区 API 封装成 MCP 工具，带 `dry_run` 开关，默认为 true。

采集和发布严格分离，Agent 只能调用"发帖"这一个写操作工具，删帖、改帖不挂在 Agent 上。

## 实施步骤

1. **最小闭环**：手动触发，草稿写到本地 Markdown 文件，完全不碰发帖接口。先跑通内容质量。
2. **Schema 约束**：输出固定为 `title / tags / body / source_links` 四个字段，校验失败重试一次，再失败就中断告警。
3. **接发布 API**：`dry_run` 模式下只打印请求体不实际发送，人工核对一周后才切正式。
4. **幂等设计**：以 `hash(素材链接集合 + 日期)` 作为幂等键，发帖前先查库里是否存在，存在直接跳过。
5. **调度上线**：失败重试两次，仍失败则推送告警消息，不做静默降级。

## 踩坑实录

**幻觉链接。** 第一周就有：Agent 生成的摘要里出现了一条素材列表里不存在的 URL，编造得有模有样。解法是发布前校验 `source_links` 必须是采集层出现过的链接，白名单外一律拒绝。

**重试导致重复帖。** 发帖接口超时后重试，实际第一次已成功，结果同一内容发了两遍。教训：重试必须带幂等键，且"查询是否已发"要在重试路径上再次执行，而不是只在首次发布前查一次。

**API 限流。** 社区接口有频率限制，客户端加了固定间隔和指数退避，429 一律退避重试，不硬刚。

**时区问题。** cron 默认 UTC，帖子半夜就发了。显式指定时区后解决，这种问题测试环境根本暴露不出来。

**权限过大。** 早期图省事把整套社区 API 都暴露给了 Agent，某次 prompt 异常导致它尝试"编辑"刚发的帖子。之后坚持最小权限：Agent 手里只有一个发布工具。

**调性难固化。** 聚合式写法没人看。后来维护了三篇人工精选帖作为 few-shot 样例，并要求每条素材必须有编辑视角的一句点评，篇幅控制在固定区间。调性是靠样例和约束喂出来的，不是靠一句"写得自然点"。

## 可复用建议

- 永远先 dry-run，人工开关不可省；
- 幂等键设计放在第一天，不要等出事再补；
- 采集、加工、发布拆开，每步独立可测；
- 日志里保存完整 prompt 和原始输出，复盘 badcase 全靠它；
- 给 Agent 的写权限越少越好，危险操作走人工。

## 总结

这个机器人技术上没有难点，真正的成本都在稳定性设计上：幂等、权限、限流、回滚。发帖只是最后一行代码，前面九成工作量是让它在第 50 次运行时和第 1 次一样可靠。目前它稳定运行数周，人工确认只需一分钟，这个投入产出比是划算的。
