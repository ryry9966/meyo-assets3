## 背景

大部分 Agent 交互是“拉”模式：你问，它答。但真正省时间的事往往在“推”这一侧——CI 挂了、日历冲突、数据源水位异常，这些你不需要每天记得去问一遍。OpenClaw 的 heartbeat 机制给了 Agent 一个周期性醒来的钩子，理论上它可以在你不看手机的时候把事办了、把话带到。但我在实际调这套东西的过程中发现，默认配置离“可信的值班员”差得远，更像一个定时找话说的实习生。

## 问题

naive 的 proactive 有三种典型失败：

1. **贵**：每 5 分钟醒一次，一天 288 次调用，哪怕每拍只是“看一眼没什么事”，token 账单也不好看。
2. **烦**：同一件事每拍报一遍，三天之后你把它静音，这个功能就死了。
3. **越权**：主动给第三方发消息、主动改仓库状态，出一次事故，信任清零。

核心工程问题不是“怎么让它更自主”，而是“怎么把周期唤醒收敛成有依据、有节制、有分寸的动作”。

## 做法

1. **把 HEARTBEAT.md 当规则表，不是日记**。每条规则固定三段：条件（尽量可脚本判断）、动作（只读检查还是通知）、通道（静默日志 / 每日摘要 / 立即 ping）。
2. **检测前置到脚本**。CI 状态、磁盘水位、日历冲突这类条件判断，用 cron + 脚本预筛，结果写状态文件；数据源走 MCP 工具直接拿事实，别让 LLM 自己猜。只有条件触发时才叫醒模型做判断和措辞。这一步把日调用量从几百降到个位数。
3. **去重和冷却**。维护一个 last-reported 状态文件（issue key + 时间戳），同一问题 N 小时内不重复报；问题消失后复现才算新事件。
4. **分层上报**。默认进每日摘要；只有“失败持续超过 10 分钟”"main 分支受影响”这类硬条件才立即 ping。所有写操作加确认门，主动模式只读 + 通知。
5. **静音时段**。凌晨只记日志，攒进早上摘要。时区要显式配置，别信默认值。

## 踩坑点

- **规则表只增不减**：一个月后每拍读的上下文越来越长，成本悄悄上涨。定期清理是必须动作。
- **LLM 在没事可报时会硬找事报**：检查项要写成可验证的事实判断（“main 的 CI 是否失败超过 10 分钟”），别写开放题（“今天有什么值得注意的”）。
- **心跳任务没设超时**：一次卡住的 MCP 调用堵住队列，后续心跳全部排队。每拍必须有 timeout。
- **去重 key 不规范**：直接拿消息文本做哈希，同一问题换个措辞就重报。key 应该是 repo + 分支 + 错误类型这种结构化字段。

## 可复用建议

- 一个门槛：这条主动消息发出来，你会说“谢了”还是“别烦我”？说不清就进摘要。
- 三层分开：触发用确定性脚本，判断用模型，动作用门禁。
- 先只开 2–3 个高价值触发，跑一周，统计“被处理率”（你真的因此采取了行动的比例）。低于三成说明阈值或方向不对，先调再加。
- 每周看一眼主动 ping 次数曲线，突然上涨基本都是规则写错了，或者外部环境变了。

## 总结

Proactive 能力的难点不在让 Agent 更自主，而在让它更会过滤：便宜的检测、可靠的去重、分层的上报、写操作的门禁。OpenClaw 的 heartbeat + 规则表 + 状态文件这套组合，工程量不大，但每一步都在决定这个功能最终是被感谢，还是被静音。
