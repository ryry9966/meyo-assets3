## 背景

大多数 Agent 的交互模型是"你问它答"：不发消息，它就是一块石头。但自动化场景里真正需要的是巡检型行为——定期看一眼日志、仓库状态、收件箱，有事才开口。OpenClaw 提供了一个很轻的机制：**HEARTBEAT.md**。它只是一个放在工作区的 Markdown 文件，Agent 每次心跳（默认约 30 分钟）醒来时读一遍，按内容决定做事还是沉默；无事可做就返回 `NO_REPLY`，完全不打扰你。

## 问题

难点不在"定时"，在"克制"。直接写"帮我盯着点项目动态"，结果要么每半小时骚扰你一次，要么因为指令模糊而什么都不做。心跳本质是低信息量的唤醒：每次醒来都要烧 token 判断"要不要汇报"，如果条目写得含糊，成本和噪音会同时失控。

## 做法

1. **结构化条目**：在 HEARTBEAT.md 里，每个任务写成"触发条件 + 动作 + 汇报策略"三段式：

```markdown
- 检查 app 容器日志新增 ERROR：
  超过 5 条且与上次不同 → 即时汇报；否则静默。
- 每天 21:00 汇总今日完成的任务 → 摘要档发送。
```

2. **汇报分三档**：静默（`NO_REPLY`）、摘要（攒一天一报）、即时（超阈值立刻推）。
3. **工具承接动作**：心跳只负责"发现"，实际动作交给 MCP 工具或脚本——查日志、调 API、写文件。
4. **状态去重**：让 Agent 把"上次处理到哪"写进一个 state 文件（如 `heartbeat-state.md`），下次心跳先对比，避免重复报警。
5. **频率分层**：默认 30 分钟适合巡检；需要精确定时的（每天 9:00 的日报），交给系统 cron 触发一条消息更可靠，心跳只做兜底。

## 踩坑点

- **指令模糊是噪音之源**。"看看有什么新鲜的"会诱导 Agent 为了"有产出"硬找事汇报。每条任务必须有可判定的阈值。
- **心跳每次都消耗 token**，即使最终回复 `NO_REPLY`。文件保持精炼，条目控制在个位数，别把大段上下文塞进去。
- **非幂等动作会重复执行**。发通知、调写接口这类动作一定要有 state 去重，否则一次重试就是三连击。
- **别把心跳当精确调度器**。它是"醒来时顺路检查"，间隔有抖动，分钟级定时需求用 cron。
- **汇报渠道要分流**。静默、摘要、即时的去向不同，全部推到私聊很快就会被你静音。

## 可复用建议

- 把 HEARTBEAT.md 当 **runbook** 写，不是愿望清单：每条 = 条件 + 动作 + 汇报档位。
- 新任务先跑"摘要档"观察两三天，确认误报率再升级到"即时档"。
- state 文件与 HEARTBEAT.md 放同一目录并纳入版本管理，改动可回溯。
- 若心跳检查支持换更便宜的模型，把"是否需要汇报"这类轻决策降级处理，重活留给主对话。

## 总结

HEARTBEAT.md 的价值在于它足够笨：一个纯文本文件加一个固定节奏的唤醒，没有新概念要学。真正决定体验的是你写进去的条目质量——阈值是否可判定、动作是否幂等、汇报是否克制。把它当 runbook 认真维护，Agent 就能从"问答机器"变成一个不吵人的巡检员。
