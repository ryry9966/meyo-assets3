# 背景

过去一年在社区里做了不少 Agent 自动化的小项目，工具调用、定时任务、MCP 服务接了一大堆，慢慢遇到一个现实问题：高频、低价值的模型调用（分类、摘要、格式化、路由判断）全走云 API，账单和限流都难受；而部分数据出于隐私又不想出本地。于是开始认真折腾本地 LLM。这篇记录我在一台普通家用机上跑通并接入 Agent 工作流的过程。

# 问题

先澄清两个误区。其一，"本地跑大模型必须堆卡"——实际上 8B~14B 级别的量化模型，消费级显卡甚至纯 CPU 都能跑，关键看够不够你的任务用。其二，"能聊天就等于能用"——本地模型最大的坑不在对话，而在 Agent 场景下的工具调用稳定性和长上下文表现，这两点不开真实任务根本测不出来。

# 做法

1. **算清显存账。** 经验值：Q4_K_M 量化下，7B~8B 约需 6GB 显存，14B 约 10~12GB，32B 约 20~24GB。注意这只是权重开销，KV cache 随上下文线性增长，Agent 的长 transcript 会把它吃掉，预留 20%~30% 余量。
2. **选运行时。** 我最终用 Ollama：一条命令拉模型，自带 OpenAI 兼容接口（`localhost:11434/v1`），Agent 框架和 MCP 客户端改个 `base_url` 就能接。追求极限性能可上 llama.cpp 的 `llama-server` 或 vLLM，但对多数人 Ollama 的工程性价比最高。
3. **选模型。** 中文 + 工具调用优先看 Qwen 系列，8B 的 Q4_K_M 是入门甜点；显存富余再上 14B。别碰 Q2/Q3——聊天看着还行，输出 JSON 时崩得很难看。
4. **显式设置上下文长度。** 这是最重要的一步，踩坑部分细说。
5. **用真实任务压测。** 别拿"你好"测，把 Agent 一轮完整的工具调用 transcript 灌进去，看 tokens/s、首 token 延迟、JSON 解析成功率。

# 踩坑点

- **上下文默认值陷阱：** Ollama 早期版本默认 ctx 只有 2048，超了静默截断，Agent 表现为"突然失忆"，极难排查。务必显式设 `num_ctx`，并按 KV cache 的显存开销算好。
- **工具调用不是白送的：** 模型卡片写了 function calling，不代表你的运行时聊天模板支持。接入后先连跑 10 次工具调用验证，统计成功率再上生产。
- **温度与长循环：** 小模型在多轮 Agent 循环里容易复读、退化。把 temperature 压到 0.2~0.4，必要时加重复惩罚。
- **别只看生成速度：** Agent 场景里，首 token 延迟和长输入的 prefill 时间对体验影响更大，测的时候分开记录。

# 可复用建议

- **混合路由最划算：** 规划和复杂工具链交给云端大模型，本地 8B 承接高频子任务（分类、摘要、格式转换），按任务分级路由，成本和隐私都照顾到。
- **配置进版本管理：** 模型名、量化版本、ctx、温度全部写进配置文件，复现问题时有据可查。
- **一张最小评估 checklist：** 显存余量够 → ctx 显式设置 → 工具调用 10 连测通过 → 真实 transcript 下 tok/s 达标。四条都过再接入正式工作流。

# 总结

本地 LLM 不是"替代云 API"，而是在 Agent 工作流里多一层可自主掌控的算力。8B~14B 量化模型 + OpenAI 兼容运行时 + 显式上下文配置，家用电脑完全跑得动；剩下的和所有工程问题一样——度量、压测、记录。欢迎在评论区贴你的机型和实测数据，攒一份社区自己的适配表。
