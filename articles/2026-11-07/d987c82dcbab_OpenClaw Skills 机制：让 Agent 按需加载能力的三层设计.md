## 背景

Agent 跑得久了一个很典型的问题：能力越堆越多，提示词越来越胖。早期做法是把操作手册、工具说明、业务规则全塞进 system prompt，结果上下文里八成内容和当前任务无关——token 成本上去了，模型反而容易"分心"，关键步骤被淹没在噪音里。

Skills 机制就是针对这个问题的：把"能力"拆成独立的技能包，平时只加载一行描述，命中任务时才展开完整内容。

## 问题：全量加载 vs 按需加载

Skills 的核心是三层渐进披露：

1. **扫描阶段**：启动时遍历技能目录，只把每个技能的 `name` + `description` 注入上下文，单个技能几十 token；
2. **命中阶段**：当任务匹配某个技能的描述，Agent 才去读取对应的 SKILL.md 正文；
3. **展开阶段**：正文里可以再引用脚本、参考文档，执行时按需读取。

上下文里始终只有"目录"，不是"全书"。而且实现上很克制——加载技能本质上就是读一个文件，没有特殊运行时，全靠约定加元数据注入。

## 做法

以"周报导出 PDF"为例：

```
skills/
  pdf-report/
    SKILL.md           # frontmatter + 操作步骤
    scripts/render.py  # 确定性逻辑放脚本
```

SKILL.md 的 frontmatter：

```yaml
---
name: pdf-report
description: 将周报 Markdown 渲染为 PDF。当用户要求导出、生成或发送 PDF 报告时使用。
---
```

步骤：

1. 在工作区 skills 目录下建文件夹，放入 SKILL.md；
2. `name` 用小写连字符；`description` 是触发关键，写清"做什么 + 什么时候用"，而不是功能罗列；
3. 正文放操作步骤、约束、输出格式。确定性部分（格式转换、批量处理）写成脚本，正文里只给路径，让 Agent 去执行而不是自己"演"一遍；
4. 重启重扫后做双向验证：问一个应该触发的请求，确认它读了 SKILL.md；再问一个无关请求，确认没有误触发。

## Skills 和 MCP 的分工

常见困惑：有了 MCP 还要 Skills 吗？我的理解是——**MCP 管连接**（接外部服务的工具），**Skills 管流程**（怎么组合这些工具完成任务的知识）。二者互补：一个技能的正文里完全可以指挥 Agent 调用某个 MCP 工具。

## 踩坑点

1. **description 写得太泛**。比如只写"处理文件"，结果所有涉及文件的任务都触发，等于退化回全量加载。要写触发条件，不写能力清单。
2. **正文太长**。SKILL.md 展开后占半个上下文，渐进披露就失去意义。单技能正文控制在一屏内，细节拆到引用文件。
3. **把密钥写进技能**。技能目录通常在 git 里，密钥放环境变量，正文只写"读取环境变量 X"。
4. **技能描述互相覆盖**。两个技能描述相近时触发不可预测，命名和描述要有区分度。
5. **写完不验证**。必须用正反两个用例各测一次，触发行为才算闭环。

## 可复用建议

- 把技能当代码管理：进 git、写变更说明、review 后合并；
- description 公式：**动作 + 对象 + 触发场景**；
- 团队里反复口头交代的流程（发版步骤、故障排查手册）最适合先做成技能；
- 不确定的环节别写死步骤，写清决策原则，让 Agent 自己判断。

## 总结

Skills 的本质是把提示词从"堆料"变成"索引"。它不炫技，但解决的是 Agent 工程里最实在的约束：上下文预算有限，而能力会持续增长。建议从把一段你反复口头交代给 Agent 的流程提炼成第一个技能开始，比一次性设计完整技能体系现实得多。
