## 背景

在 Agent / MCP 场景下，AI 产出的第一格式几乎都是 Markdown。但发布端各不相同：公众号编辑器会吞掉大部分样式和部分语法，知乎不支持完整 GFM，静态站点需要 frontmatter 和相对链接，走 API 的平台又各有块结构。常见做法是让模型“再生成一版”，结果往往是内容漂移——同一篇文章在不同平台细节不一致，每次改稿都要重复劳动。

## 问题

核心矛盾是：**单一信源，多目标格式**。要避免两个极端：一是人肉逐平台改格式；二是把适配交还给模型，让它直接输出“公众号版 Markdown”这种本质上不存在的东西。正确的插入点在模型输出之后、发布之前——一个确定性的转换层。

## 做法

我的管线分四步，核心栈是 unified / remark：

1. **固定规范源**。仓库里只维护一份 canonical 文档，限制语法子集：标准 GFM + 脚注，禁用内联 HTML。用 remark-lint 写成配置，作为“家规”。
2. **解析与校验**。remark-parse 转 MDAST 后跑 lint 和自检：标题层级不跳级、外链可达、图片必须是白名单图床的绝对 URL。AI 输出不直接进管线，先过这关。
3. **目标转换器**。每个平台一个纯函数模块（AST → AST 或 AST → string）。公众号版：代码块转预样式段落、表格降级为列表、脚注内联；静态站版：注入 frontmatter、重写相对链接。转换器互相独立，可单独测试。
4. **发布与回滚**。优先走平台 API，没有 API 的走富文本粘贴兜底。每次发布记录版本 hash，改稿后 diff 再发。

在 Agent 里，我把整套管线封装成一个 MCP tool：模型只负责产出符合规范的 canonical Markdown，格式适配全部在工具侧完成。

## 踩坑点

- **表格是重灾区**。公众号会把宽表格压坏，列数超过 4 就降级为列表，收益立竿见影。
- **代码块语言标签**。模型爱写 `text` 或干脆不写，导致高亮丢失，lint 里加一条强制规则。
- **嵌套列表缩进**。2 空格和 4 空格混用，部分渲染器直接解析错位，统一 2 空格并固化到 lint。
- **图片本地路径**。转换层里做一步“上传 + 改写 URL”，别指望平台帮你处理相对路径。
- **别让模型直接生成目标格式**。见过让模型输出带内联样式的 HTML，一次幻觉就毁掉整条管线的确定性。

## 可复用建议

- 信源唯一，目标派生，一切派生物可随时重建。
- 适配器写成无副作用的纯函数 + 快照测试，平台改版时只改一个文件。
- 校验规则前置：宁可拒绝 AI 输出，也不带病转换。
- 职责边界要清晰：模型管内容，管线管格式。

## 总结

这套管线没有黑科技，价值在于把“格式适配”从模型的不确定输出变成确定性的代码。AI 负责写，管线负责形，各司其职之后，多平台发布从一件烦心事变成 CI 里的一行命令。
