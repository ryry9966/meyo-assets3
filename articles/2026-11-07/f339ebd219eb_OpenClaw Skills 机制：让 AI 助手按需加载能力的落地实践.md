## 背景

用 OpenClaw 做自托管助手一段时间后，我发现上下文是最先撑不住的资源。早期我把所有操作流程都写进 AGENTS.md：消息模板、截图整理规则、服务器巡检步骤……系统提示词膨胀到四百多行，模型开始漏指令、串流程。MCP 解决了工具接入问题，但它的工具定义是常驻的，挂上十几个 server 后光 schema 就占掉一大块，而多数工具在一次会话里根本用不到。

Skills 是 OpenClaw 的解法：**渐进式披露**。每个技能是一个目录，核心是一个 SKILL.md。会话启动时只把 `name` + `description` 注入系统提示，正文在模型判断"这次用得上"时才读入。常驻成本从"全部能力"降为"一张索引"。

## 做法

**1. 建目录，写最小 SKILL.md**

放在工作区 `skills/<name>/SKILL.md`，个人通用的放 `~/.openclaw/skills`。以我实际在用的一个为例：

```markdown
---
name: screenshot-tidy
description: 当用户要求整理、归档或重命名截图目录时使用。批量按日期归组并生成命名规则。
---

# 截图整理
1. 先列出目录规模，超过 500 个文件先向用户确认。
2. 运行 scripts/tidy.sh --dry-run 预览改动。
3. 用户确认后去掉 --dry-run 正式执行。
```

**2. 把 description 当路由写**。它决定了技能会不会被触发，写"何时使用"，不是功能简介。对比："用于整理文件"（弱）vs "当用户要求归档或重命名截图目录时使用"（能用）。

**3. 正文只写步骤骨架**，长参考拆到 `references/`，确定性操作写成脚本放 `scripts/` 让模型去调。正文控制在一两百行内。

**4. 验证与分发**：`openclaw skills list` 看加载状态，`skills info` 查详情；不重复造轮子可以先用 ClawHub 装现成的；整个 skills 目录进 git，多台机器同步。

## 踩坑点

- **description 写不好是第一大坑**。太泛会乱触发，太窄则永远不触发。我的做法是用一段真实对话去测：开新会话只给原始需求，看它会不会选中这个技能。
- **正文塞太满**，等于把 AGENTS.md 的问题换个目录重演。原则：常驻的是索引，按需的是细节。
- **脚本没加执行权限**，模型反复尝试后放弃并开始用自然语言"重演"步骤，结果不可控。写完顺手 `chmod +x`，Windows 下注意路径分隔符。
- **技能数量失控**。超过三四十个后命中率明显下降，按场景合并成工作流技能比堆细粒度更有效。
- **密钥别写进 SKILL.md**，它会随正文被读进上下文。用环境变量，需要时在 frontmatter 声明依赖。
- 破坏性操作（删除、批量改名）必须在正文里写明确认步骤，别信模型自觉。

## 可复用建议

- 一个技能一件事，宁可多建也不做万能技能。
- 判断用 Skill 还是 MCP 的标准：**有状态、需长连接、要鉴权的服务用 MCP；流程知识、个人自动化用 Skill**。"怎么发一条消息"写成 Skill 比 MCP server 划算得多。
- 能用脚本表达的就别用自然语言描述，脚本可测、可复现。
- 定期跑一遍冷启动测试：新会话 + 原始需求，检验路由是否准确。

## 总结

Skills 机制的本质是把提示词工程变成索引工程：常驻的只是描述，正文和脚本按需加载。对我来说最直接的收益是 AGENTS.md 从四百多行瘦回八十行，指令遵循明显变好，token 账单也顺眼了。它不是 MCP 的替代品，而是同一套自动化体系里更轻的那一层——先把流程知识装进 Skills，真有常驻服务需求再上 MCP，这个顺序在个人自托管场景下基本不会错。
