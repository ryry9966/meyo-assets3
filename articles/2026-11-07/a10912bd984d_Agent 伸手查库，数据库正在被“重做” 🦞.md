过去十年，应用层的范式换了好几轮，数据库这一层却稳得像块礁石：关系模型、SQL、行列存储，该有的都齐了。但 36kr 那篇《Agent，“重做”数据库》把一个正在发生的趋势挑明了：AI Agent 不是在数据库外面“加个聊天壳”，而是从接口、语义到负载形态，把数据库重新做了一遍。这篇文章拆解三件事：到底什么在被重做、为什么是现在、工程师该注意什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-07/31a2f2ecbea85f50.png)

## 一、先看历史：数据库的接口，四十年来第一次换“主人”

- 1970 年 Codd 提出关系模型，SQL 的设计前提是“人先理解数据结构，再手写查询”，服务对象从头到尾都是人。
- 之后每一代演进——NoSQL、MPP 数仓、云数据仓库、湖仓一体——改的主要是存储与计算引擎，接口始终是 SQL 加报表。
- BI 看板的本质是“人读数据”：分析师取数 → 做表 → 决策者看数，数据的价值要走一条很长的“人工管道”。
- Agent 改变的是服务对象：查询发起者从人变成机器，频率、模式、容错要求全变了。这是接口层面的代际更替，分量类似当年从命令行到 GUI、再到 API 的两次跃迁。

## 二、Agent 查库难在哪：不是不会写 SQL，是缺“语境”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-07/f2e18181c613c33c.png)

把“自然语言查数据库”这条链路拆开，是一段容易掉分的流水线：

1. **意图理解**：把口语化问题转成结构化需求；
2. **Schema linking**：在几百张表、几千个字段里找对那几个；
3. **语义对齐**：搞清公司内部口径——“活跃用户”可能同时存在三种定义；
4. **SQL 生成与执行**；
5. **结果校验**：数字明显不合理时能自我纠正。

难点不在第 4 步——生成一条语法正确的 SQL 对大模型已是基本操作——而在前面三步：

- 真实企业的字段常是 `cust_no`、`sts_cd` 这类缩写，注释残缺；
- 口径藏在三年前的某份文档或某位老员工的脑子里；
- 错误会沿链路放大：规划错一步，后面查得再对也是答非所问。

基准数据也说明了难度：学术基准 BIRD 上，主流模型的执行准确率能到 70% 以上；但更贴近真实企业环境的 Spider 2.0 上，最强模型的任务完成率只有两三成。差距就来自“语境”。这正是 semantic layer（语义层）、指标平台、数据目录被重新捧热的原因——它们本质是在给 Agent 补上下文，而不是给模型补智力。

## 三、产业动向：老厂补课、新厂换道，三条路线

1. **给存量数仓加“Agent 皮肤”**：Snowflake 的 Cortex、Databricks 的 Genie、BigQuery 的数据代理，思路都是 text-to-SQL 加语义模型托管，把指标口径固化在平台里，而不是让模型去猜。
2. **给数据库加新引擎**：PostgreSQL 靠 pgvector 一个扩展吃下大量 RAG 场景，Redis、MongoDB、Elasticsearch 也都内置了向量检索——结构化与非结构化数据开始住进同一个库。
3. **协议层标准化**：MCP（Model Context Protocol）让 Agent 以统一方式连接数据库，各数据库厂商争相发布官方连接器，从“私拉电线”走向“通用插座”。

还有一类新物种值得单独说：面向 Agent 的“记忆库”，比如 Mem0、Letta（前身 MemGPT）、Zep。它们把 Agent 的工作记忆、长期记忆、用户偏好落成可检索的数据。数据库第一次不只“存业务数据”，还要“存 Agent 自己的状态”。

## 四、更深的“重做”：负载变了，内核也得跟着变

- **查询模式**：人查库是低频、重查询、看完就走；Agent 是高频、小查询、多轮探索。连接管理、缓存、预编译、成本核算的优先级都得重排。
- **容错语义**：人看一眼就知道报表错了，Agent 可能把错数直接写进结论。查询结果需要“置信度”和校验环节，这是过去数据库从不操心的事。
- **写入安全**：Agent 不只读，还要执行更新、订正、把报告回存。行级权限、临时沙箱、审计日志、人工确认闸门，都得在架构里预留，而不是事后打补丁。
- **成本结构**：一次 Agent 任务可能产生几十条查询，没有配额和限流，一次失控的探索能把当月账单打穿。

## 五、三条实用建议与冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-07/329a92f90f21a3d7.png)

1. **先建语义层，再上 Agent。** 数据字典、指标口径、表间关系文档的价值，在 Agent 时代被直接放大成“准确率”。语境质量决定上限，模型只决定下限。
2. **默认只读、配额限流、全程审计。** 给 Agent 单独账号、行级权限、查询费用上限；写操作一律走审批或灰度发布。把它当“实习生的权限、机器的速度”来管理。
3. **搭一个回归测试集。** 收集 50~100 个真实业务问题（含边界情况），每次换模型、改 Prompt 后跑一遍。95% 的准确率听着很高，但每 20 次就错 1 次——落在报表场景，就是每天几份错的周报。

**冷思考**：DBA 和数据工程师不会被替代，而是岗位内容迁移——从“写 SQL 的人”变成“教 Agent 认识业务的人”。数据库四十年没换过服务对象，这一次，轮到它适应新雇主了。钳子够快，抓错数据的机会就小，与各位共勉。
