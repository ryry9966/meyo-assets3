## 背景

OpenClaw 的 cron 任务用起来很方便：写一个调度表达式，配一段 instruction（也就是任务 prompt），到点 agent 醒来执行，再把结果发到你的消息通道。但社区里常见的情况是：交互式聊天里调得挺好的提示词，搬进 cron 就开始翻车——输出时长时短、偶尔编链接、数据源挂了还硬凑内容。

原因不复杂：**cron 运行是一次无人值守的单轮会话**。没有你在场追问，没有上文的对话记忆，跑错了也没人立刻纠正。instruction 的质量，直接决定这次"盲跑"的成败。

## 三个约束决定写法

写 cron instruction 之前先认清三件事：

1. **无上下文**：agent 醒来时接近"失忆"，别指望它记得昨晚聊过什么；
2. **无追问**：instruction 里没写清楚的地方，它只能猜，猜错就直接进你的群；
3. **不可即时纠偏**：发出去就是发出去了，最多事后修 prompt。

所以好的 cron instruction 更像一份给外包的作业说明书，而不是聊天提示词。

## 做法：六条原则

**1. 调度归 cron，动作归 prompt。** instruction 里不要出现"每天早上"，时间逻辑全部交给 cron 表达式（并确认时区，很多宿主机默认是 UTC）。prompt 里统一用"现在"："汇总过去 24 小时的……"。

**2. 自包含。** 需要的背景直接写进 instruction；较长的上下文（比如关注的仓库列表）放到 workspace 里的一个文件，instruction 第一句让它先读这个文件。

**3. 明确数据源和工具。** 写清楚用哪个 skill/工具取数，并明确禁止凭训练记忆作答。这是防幻觉最有效的一行。

**4. 定义输出契约。** 发到哪个通道、几条、每条什么结构、字数上限、语言。没有契约，模型每次自由发挥，格式必然漂移。

**5. 定义失败语义。** 数据取不到怎么办？要么"静默跳过"，要么"发一句不超过 20 字的失败通知"。关键是一定要写"禁止编造或凑数"。

**6. 需要记忆就落文件。** 比如新闻去重：先读 `workspace/cron/xxx-seen.json`，跳过已推送条目，完成后写回。这个文件就是任务之间的"记忆"。

一个对比例子，感受一下密度差异：

> ❌ 每天早上给我推送 AI 新闻。
>
> ✅ 使用 web_search 检索过去 24 小时 AI 领域新闻（关键词：LLM、agent、开源模型）。发到 Telegram「日报」：不超过 8 条，每条 = 中文标题 + 一句话摘要 + 原文链接。结果少于 3 条时只回"今日共 N 条"，禁止编造。先读 workspace/cron/news-seen.json 去重，完成后写回。

## 踩坑点

- **时区**：上线前先确认 cron 表达式跟谁走，别让"早 9 点"变成"下午 5 点"；
- **一件事一个 job**：新闻 + 天气 + 日程塞一个 prompt，一处失败污染全部，拆开各自独立；
- **先手动触发**：新任务先手动跑一次、当普通 prompt 调，稳定了再上调度，能省一半排障时间；
- **别写"工具不可用就换别的方式"**：agent 会自由发挥到你想不到的地方，降级路径要么写死，要么明确禁止；
- **上下文别贪多**：塞一大段无关背景，token 翻倍，判断反而变差。

## 可复用模板

```
【目标】一句话说清做什么
【数据源】用哪个工具/skill，从哪取数，禁止凭记忆
【输出】通道 / 格式 / 条数或字数上限 / 语言
【失败处理】取不到数据时的行为；禁止编造
【状态】如需跨次记忆，读写哪个文件
```

## 总结

Cron instruction 的本质，是把一次可以来回澄清的对话，压缩成一份无人值守的作业说明书：所有本来可以追问的问题，都必须提前写死在指令里。调度交给 cron，内容契约、工具约束、失败语义写进 prompt，跨次状态落到 workspace 文件。按这个结构写，定时任务的稳定性会有肉眼可见的提升。欢迎在社区帖子里贴出你的 cron instruction，一起迭代模板。
