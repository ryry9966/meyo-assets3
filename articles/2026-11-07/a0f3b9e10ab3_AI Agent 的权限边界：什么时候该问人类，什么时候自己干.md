## 背景

Agent 能做的事越来越多：调 MCP 工具读写文件、执行 shell、发消息、操作数据库。框架层面的问题基本解决了——工具能调通、循环能跑通。真正悬着的是另一个问题：每次调用工具前，agent 应该自己决定，还是先问人？

这个问题没有标准答案，但大多数团队最后会在两种失败形态之间来回摇摆。

## 问题

- **全都要问**：每次工具调用都弹确认，人很快退化成"无脑点确认"的机器。这时确认机制形同虚设——人不再阅读内容，只负责点击。
- **全都不问**：平时很爽，直到某天 agent 把测试库的 drop 跑在了生产库上，或者把一封没核对的邮件发给了客户。

所以权限边界不是"问 / 不问"的二选一，而是一个决策函数：输入是这次操作本身，输出是"直接干"或"停下来问"。

## 做法：两轴四象限

我们用的是最简单的二维分类，够用：

**轴一：可逆性**。操作能否撤销？读文件可逆，删文件不可逆，发出去的消息不可逆，转出去的钱基本不可逆。

**轴二：影响范围**。只影响 agent 自己的工作目录，还是波及生产环境、他人数据、外部系统？

组合成四象限：

1. 可逆 + 小范围（读文件、写草稿、查数据）→ 直接干，留日志。
2. 可逆 + 大范围（批量改配置、重启服务）→ 用可回滚的方式干：dry-run、先备份、灰度执行。
3. 不可逆 + 小范围（清理自己的临时文件）→ 可以干，但记确认日志。
4. 不可逆 + 大范围（发外部消息、动钱、删生产数据）→ 必须问人，没有例外。

落地步骤：

1. 把 agent 能调的所有工具列成清单，逐个标注可逆性和影响范围。
2. 在 MCP 工具配置或网关层做分级：read / write / dangerous 三档，dangerous 档强制人工确认。
3. 危险工具提供 dry-run 参数，确认时把将要执行的内容以 diff 或预览形式展示。
4. 确认结果落审计日志：谁批的、批了什么、什么时候。

## 踩坑点

- **确认疲劳**：问得太频繁，人就开始盲批。宁可调高"问"的门槛，也要保住每次确认的严肃性。
- **无效提问**："我可以删除吗？"却不展示删什么、影响多大。人无法决策的提问等于没问，确认请求必须带上下文。
- **粒度太粗**：一刀切禁用整个工具，而不是约束参数。比如 shell 不该全禁，而是限定工作目录、拦截特定模式。
- **批准被永久缓存**：人批准了一次删除，agent 记住了，下次直接删。批准应绑定到具体操作，而不是升级 agent 的全局权限。
- **措辞带节奏**：agent 提问时偏向"建议同意"，人容易被带着走。确认界面尽量只展示事实，不展示 agent 的倾向。

## 可复用建议

- 把权限策略写成配置或代码，不要散落在 system prompt 里靠模型自觉。
- 一条底线：不可逆、且影响超出 agent 自身工作区的操作，永远问人。
- 每次事故后回头修订象限划分，把它当代码一样迭代。
- 定期审计：连续自动执行且从没出问题的操作可降级为直接干；出过一次问题的，升回确认档。

## 总结

权限边界本质上不是技术问题，而是产品决策：你愿意用多少效率换多少可控性。两轴四象限不是为了精确，而是给团队一个可以讨论、可以修订的共同语言。边界划清楚之后，agent 该自己干的时候痛快干，该问的时候问得让人能决策——这才是自动化跑得快的前提。
