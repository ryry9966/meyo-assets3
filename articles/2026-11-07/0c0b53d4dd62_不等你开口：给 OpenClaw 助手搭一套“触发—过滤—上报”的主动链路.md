## 背景

大多数 agent 的默认形态是“一问一答”：用户发消息、模型响应、结束。但真正省时间的场景往往反过来——磁盘快满了、CI 挂了、半小时后有会，这些事不该等人去问。OpenClaw 这类常驻网关型助手天然具备主动性的基础设施：常驻进程、heartbeat/cron 定时器、消息通道、可挂 MCP 工具的 skill 体系。所以问题从来不是“能不能主动”，而是“主动到什么程度不算骚扰”。

## 问题

把主动能力直接放开，通常一周内翻车，常见三种：

1. **通知疲劳**：每次心跳都汇报“一切正常”，三天后用户开始忽略所有推送；
2. **幻觉事件**：模型把“可能发生”当“已经发生”，比如把一行 WARN 日志解读成服务宕机；
3. **越权动作**：主动场景下没人确认，agent 自作主张改配置、发消息。

本质是缺一个工程化的闸门：什么事件、什么阈值、发给谁、允不允许执行写操作。

## 做法

社区里跑得比较稳的一套链路分四步：

1. **触发层分离**。低频心跳（30–60 分钟一次）只做“巡检 + 状态落盘”，结果写进状态文件；时间敏感事件用 cron 或 webhook 触发独立任务。别让心跳承担全部主动性，成本和噪声都会失控。

```yaml
heartbeat:
  interval: 30m
  quiet_hours: "23:00-08:00"
  allow_write: false
```

2. **事件结构化**。巡检结果不直接发消息，先整理成固定 schema：`{事件类型, 严重级别, 证据, 建议动作}`。证据字段强制要求来自工具调用的真实输出，不允许模型凭记忆编写。

3. **上报闸门**。在 skill 里加规则过滤：
   - P0（服务不可用、数据丢失风险）→ 立即推送；
   - P1（阈值接近、连续异常）→ 每天固定时间汇总推送；
   - P2 及以下 → 只写状态文件，用户主动问才说。
   同时配静默时段和去重（同一事件 4 小时内不重复报）。

4. **写操作默认禁用**。主动链路里 agent 只有“读 + 报告”权限；需要执行动作时生成一条待确认项，等人回复再走正常交互流程。

核心提示词其实只有一句：**“如果这次心跳没有值得打扰用户的事，回复 NOOP，不要输出任何汇报。”** 配合结构化输出，NOOP 就静默。

## 踩坑点

- **心跳间隔太短**（<15 分钟）：token 成本翻倍，产出没变化。30 分钟起步，按事件频率调。
- **自激循环**：agent 对自己发出的消息做出反应，反复触发。给通道消息加来源标记，来自 agent 自身的消息不进触发队列。
- **时区混乱**：cron 用 UTC、静默时段用本地时间，混着配必出事故，统一到一种。
- **“连续 N 次异常”的 N 太小**：一次网络抖动就报警，我们用 3 次窗口 + 指数退避。
- **状态文件不设过期**：三周前的 P1 还在每日汇总里反复出现，记得加 TTL。

## 可复用建议

- 严重级别定义和静默规则写成独立配置文件，不要散在提示词里，换模型时不用重调。
- 所有主动推送留痕（时间、事件、级别、是否被点开），一个月后你就有数据决定收紧还是放宽。
- 灰度上线：先只开 P0，跑两周再加 P1。
- 判断标准很简单：开始想关通知，说明闸门太松；错过过一次该知道的事，说明太紧。

## 总结

Proactive 不是让 agent 更“聪明”，而是给它一套和人类同事一样的汇报纪律：有事说事、有证据、分级别、不越权。触发层、结构化、闸门、只读默认——四件事搭起来，主动助手才能从演示品变成每天真的在用的东西。欢迎在社区帖里贴你自己的阈值配置，这套东西非常吃实际负载的反馈。
