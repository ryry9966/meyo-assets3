## 背景

模型本身无状态。每次会话结束，“你上次说要用 pnpm 而不是 npm”这类信息就丢了。上下文窗口再大也只是短期工作台，不是记忆。在 OpenClaw 这类长期运行的 Agent 环境里，记忆是和技能、插件、MCP 平级的基础设施——没有它，每个任务都要重新自我介绍一遍。

## 问题

常见的两种失败做法：

1. **全量塞进 system prompt**：偏好、历史、项目背景全堆进去。Token 成本线性上涨，关键信息被稀释，注意力反而下降。
2. **把聊天记录当记忆**：对话里九成是过程噪音，检索召回一堆无关内容，旧结论和新偏好混在一起没人清理。

核心矛盾是：写入太多是污染，写入太少没用处。记忆系统真正要设计的是**写入标准、读取时机、更新策略**这三件事。

## 做法

以下分层方案在一个日常自动化 Agent 上稳定跑了两个月：

**第一层：结构化偏好档案（Profile）**
一个约 60 行的 YAML 文件，常驻 system prompt。只放稳定事实：语言偏好、代码风格、常用工具链、部署习惯，控制在 500 token 以内。用户可以直接手改——记忆不该是黑盒。

**第二层：情景记忆（Episodes）**
任务结束时的会话摘要、失败原因、关键决策，存 SQLite 并加 embedding 列做向量检索。不追求全量，只在会话收尾时用一次 LLM 调用提炼 3～5 条。

**第三层：写入触发器**
只有三种情况才写：
- 用户显式说“记住……"
- 用户纠正了 Agent 的行为（最强的偏好信号）
- 会话摘要时发现的重复模式

**读取**：Profile 常驻注入；情景记忆通过 MCP 工具 `memory_search` 按需检索。注意检索 query 要用“任务重述”而不是用户原话。

**更新**：每条记忆带 `source`（explicit/inferred）、`confidence`、`last_used_at`。冲突时新记忆覆盖旧记忆而非追加；inferred 来源置信度低于阈值时先向用户确认；90 天未命中自动降级归档。

## 踩坑点

- **只写不读**：最早只做了写入，Agent 根本不会主动调 `memory_search`。后来在技能描述里明确写“执行任务前先检索相关偏好”，命中率才上来。
- **隐式推断翻车**：用户某次用了一个库，Agent 推断成“偏好此库”并写死。教训：inferred 记忆必须标低置信度，重复出现两次以上才固化。
- **检索 query 直接用原话**：“再改一下那个脚本”这种口语输入基本召不回东西。先用一次轻量调用把原话重写成语义完整的任务描述，再检索。
- **Token 预算失控**：Profile 三个月没人清理，膨胀到 2000 token。加了一条规则：每次更新 Profile 时顺带检查并合并冗余项。

## 可复用建议

1. 从一个手写 YAML Profile 起步，覆盖 80% 的价值，先别急着上向量库。
2. 把记忆做成 MCP 工具而不是硬编码注入，让 Agent 自己决定何时检索——把工具描述写清楚，比在 prompt 里喊话有效。
3. 区分三种记忆：用户是谁（profile）、发生了什么（episode）、怎么做（procedure），别混在一张表里。
4. 记忆文件保持人类可读可编辑，定期人工 review 一次，比任何自动清理都可靠。
5. 记录 `memory_search` 的命中/未命中日志，用真实数据决定要不要扩容，而不是靠感觉。

## 总结

Agent 记忆本质是数据工程问题，不是模型问题：写入标准、冲突处理、过期策略才是难点。从最小可用的结构化档案开始，把记忆做成可检查、可编辑的一等公民，再根据命中日志逐步演进检索层。两个月实践下来最大的感受是一句话：**宁可少记，不可记错。**
