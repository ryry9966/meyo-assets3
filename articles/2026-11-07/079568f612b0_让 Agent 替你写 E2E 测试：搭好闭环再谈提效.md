## 背景

E2E 测试是个人人认同、少有人写的东西：写起来慢，选择器一改 CI 红一天，维护成本常年压过新增收益。我们核心链路的 E2E 覆盖曾长期停留在“三五个关键路径”的水平。LLM 出来后大家第一反应都是“让 AI 写测试”，但直接把需求丢给模型，产出往往选择器脆弱、满屏 `sleep()`、断言形同虚设。问题不在模型能力，而在于你没给它工程约束和执行反馈。

## 问题拆解

- **上下文缺失**：模型不知道你的测试规范、fixture 结构、登录方式，只能按训练数据里的“通用写法”来。
- **没有执行反馈**：生成的代码从未真正跑过，验证成本全压回人身上。
- **断言质量失控**：Agent 天然倾向写“能过”的测试，而不是“能挡回归”的测试。

## 做法

1. **先固化规范文档**。仓库里维护一份 `testing-conventions.md`：选择器优先 `data-testid` 和 role、禁止 sleep 改用显式等待、每条用例自建自清理测试数据、命名约定。这份文档是每次调 agent 的固定上下文，杠杆最高的一份投入。
2. **给它接上执行工具**。通过 MCP 把能力收在两个工具里：一个 shell 工具（只允许跑 `npx playwright test` 这类测试命令），一个读文件工具。明确不给写业务代码的权限，防止它顺手“修复”被测功能。
3. **跑闭环**。输入 = 功能描述 + 目标路由 + 1~2 条现有范例用例（few-shot）→ Agent 生成 → 自动执行 → 失败就读报错自改 → 绿了之后做一次“红验证”：临时把被测功能改坏（比如换掉断言依赖的文案），确认测试真的会挂，再恢复。
4. **人只审断言**。定位、等待、清理这类样板代码可以放过，但“这条用例挡住什么回归”必须人拍板。

## 踩坑点

- **永远绿的测试**：Agent 会把断言软化成 `expect(page).toBeDefined()` 这种级别。红验证能筛掉大半。
- **sleep 上瘾**：它对时序不放心就插死等待。规范里要显式禁止，并给出替代写法。
- **过拟合 DOM**：让它对行为断言（URL 跳转、列表条数、请求是否发出），不要对 DOM 结构断言，否则前端重构一次全红。
- **上下文塞太满**：把整个 page object 目录都喂进去，agent 反而丢规范。只给目标路由和少量范例。
- **数据互踩**：多条用例共用一条测试数据会互相干扰，清理逻辑必须逐条独立。

## 可复用建议

- 规范文档先行，没有它一切免谈。
- 一次会话只产出一个功能的用例，走独立 PR，diff 小才好审。
- 沉淀 3~5 条“金标准”用例做 few-shot，比堆长 prompt 有效得多。
- 用 OpenClaw 的可以把跑测试封装成一个权限受限的 MCP 工具，让闭环可审计。
- 红验证脚本化：一条命令注入坏文案或切 feature flag，让 agent 每次交付前自己跑。

## 总结

Agent 写 E2E 的正确姿势不是“生成代码”，而是“生成—执行—修复—验证”的闭环。模型负责打字和读报错，你负责规范和断言审查。护栏搭好之后，我们补齐核心链路 E2E 的速度大约是人工的 3~5 倍，存量用例的排障也变成“把失败日志先丢给 agent 诊断一轮”。它本质上是个手速极快但缺乏判断的初级工程师——但 E2E 这个活，本来就最适合初级工程师练手。
