## 背景

Agent 跑得越久，依赖的外部 API 就越多：搜索、数据库、第三方 SaaS、内部服务。这些依赖没有一个承诺 100% 可用。我在 OpenClaw 上跑的几个自动化流程里，一周内真实遇到过的失败包括：上游 429 限流、请求超时、凭证过期、接口悄悄改了返回结构。对 Agent 来说，API 挂掉不是异常路径，而是常态路径。

## 问题在哪

天真的处理方式有三种，代价都见过：

1. 直接崩掉，整个任务作废；
2. 无限重试，token 烧穿，还可能触发对方更严的限流甚至封禁；
3. 最危险的一种：工具调用失败后，模型基于上下文"脑补"一个结果继续往下走。流程看起来正常，产出是错的。

第三种最棘手，因为它不报错，往往到事后对账才暴露。

## 我的做法

给所有工具调用加一层统一的执行器，大致五步：

**1. 错误分类。** 429、503、超时、网络抖动归为可重试；401/403、400、404 归为不可重试——重试只会浪费时间和配额。

**2. 有限重试 + 指数退避 + 抖动。** 最多 3 次，间隔约 1s/2s/4s 再加随机量，避免重试风暴。写操作必须确认幂等（带请求 ID），否则宁可停下来等人工介入。

**3. 硬超时。** 每个工具调用设独立预算（比如 30 秒），不能让一次慢查询卡死整个 agent 循环。

**4. 结构化地把失败交还给模型。** 不要抛异常了事，把错误作为一等结果返回：状态码、是否可重试、建议动作（换工具 / 跳过该步 / 询问用户）。模型拿到可判断的信息，才会做出合理的降级决策，而不是瞎猜。

**5. 熔断与降级。** 同一工具连续失败 N 次后暂停调用一段时间，期间走降级路径：备用 API、本地缓存（明确标注数据是旧的）、或把该步骤标记为"未完成"并通知人。

## 踩过的坑

- **把重试规则写进提示词，靠模型自觉。** 不行，模型会陷入循环。重试次数必须由 harness 硬性封顶，提示词只负责决策框架。
- **错误信息太模糊。** 只返回"调用失败"，模型无从判断该重试还是绕路，等于把垃圾丢给它。
- **降级不声明。** 用缓存兜底时没告诉模型和用户，产出看似新鲜实为过期——比直接失败更糟。
- **熔断太激进。** 上游只是部分节点抖动，熔断把完全正常的其他工具也停了。计数要按"工具 + 错误类型"分开。

## 可复用的建议

- 每个 MCP 工具 / 插件接入前先问三个问题：可重试吗？幂等吗？挂了之后的降级路径是什么？答不上来就别上生产。
- 定期做故障演练：手动断掉某个 API，观察 agent 实际行为，比任何文档都真实。
- 日志里记录结构化失败信息（工具名、状态码、耗时、重试次数），复盘全靠它。

## 总结

错误恢复的目标不是"永不失败"，而是失败可预期、恢复成本低、全程诚实——对模型诚实，也对用户诚实。执行层兜住重试、超时和熔断，提示词层给出决策框架，两层配合，Agent 才能在外部世界不稳定时依然可靠地跑完任务。
