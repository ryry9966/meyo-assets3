## 背景

跑 Agent 自动化越久，越会碰到同一个问题：流程本身没改，外部 API 却在某天开始 502。搜索接口超时、模型供应商限流、内部服务重启，对 Agent 来说，这些不是"代码 bug"，而是运行时的常态。如果工具层没有错误恢复设计，一次普通的接口抖动就足以让任务链条卡死，或者更糟：让模型在拿不到数据时自己编一个。

## 问题在哪

直接把原始异常抛给 Agent，通常出现三种坏结果：

1. **无限重试**：模型看到失败就反复调用同一工具，token 烧完任务也没推进；
2. **上下文污染**：几 KB 的堆栈信息塞进对话，把真正有用的上下文挤掉；
3. **幻觉兜底**：拿不到数据，模型转而"推测"一个看起来合理的答案交给用户。

## 做法

与其指望模型自己处理，不如在 MCP 工具封装层做四件事：

**1. 错误分类先行。** 只有三类错误值得重试：超时、429、5xx。4xx（尤其 401/403）重试没有意义，应直接失败。分类逻辑写在封装层，别让模型判断。

**2. 统一错误信封。** 所有工具失败时返回结构一致的 JSON：

```json
{
  "ok": false,
  "error_type": "upstream_timeout",
  "retryable": true,
  "hint": "service may recover in minutes"
}
```

模型拿到的是可决策的信息，而不是一行 traceback。

**3. 指数退避 + 抖动。** 封装层先自己重试 2~3 次（1s / 2s / 4s，加随机抖动），把瞬时抖动消化掉。注意：只有幂等调用才允许自动重试，创建订单这类 POST 不能盲目重试，否则会产生重复数据。

**4. 熔断与降级。** 连续失败达到阈值（比如 5 次），标记该工具"不可用"并冷却 5 分钟，期间调用快速失败。同时准备降级路径：备用 API、本地缓存，或如实告知用户"该数据源暂时不可用"。最后一种是合法且往往最优的选择。

## 踩坑点

- **退避不加抖动**：多个 Agent 实例同步重试，服务恢复瞬间被打出第二波雪崩；
- **熔断状态存进程内存**：Agent 一重启状态就丢，等于没熔断，至少落盘或放共享存储；
- **重试没有上限**：必须设最大次数和总时间预算，超了就交还上层决策；
- **错误信封太啰嗦**：hint 一句话就够，别制造新的上下文污染。

## 可复用建议

- 每个工具调用都包一层：timeout → 分类 → 重试 → 熔断 → 信封输出；
- 设计时就问一句："这个 API 挂了，Agent 该说什么？"降级不是事后补丁；
- 日志里统计 error_type 分布，跑一段时间后你会知道哪些上游最不稳定，值得加备用源。

## 总结

Agent 的健壮性下限由工具封装层决定，而不是靠 prompt 祈祷。把重试、熔断、降级做进封装层，给模型一个干净、可决策的错误信封，它才能在外部 API 挂掉时做出正确反应，要么等，要么绕，要么如实说。这三个选项，都比编一个答案强。
