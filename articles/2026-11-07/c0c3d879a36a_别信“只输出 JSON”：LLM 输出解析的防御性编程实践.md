## 背景

在 OpenClaw 的插件和 MCP 工具链里，让模型返回 JSON 是常态：工具参数、路由决策、批处理任务的中间结果。提示词里写一句“只输出 JSON，不要多余解释”，测试时也确实如此。但一旦进入自动化流水线——跑得多、模型杂、温度不为零——输出格式就会开始漂移。

我的态度逐渐变成：**把 LLM 输出当成不可信的外部输入**，和解析第三方 API 一样做防御。

## 问题：格式漂移的真实形态

跑了几天定时任务后，我从失败日志里收集到的变体大致有：

- 标准 JSON（反而是少数派）
- ```json 围栏包裹
- 无语言标注的 ``` 围栏
- `<json>...</json>` 这类 XML 风格标签（某些模型的训练偏好）
- JSON 前后带一句“好的，以下是结果：”，有时还夹着 markdown 列表
- 字段值里嵌套代码块，导致内层又出现 ```
- 尾逗号、单引号、中文引号 ""、未转义换行
- max_tokens 截断导致的半截 JSON

任何一个变体都能让 `json.loads` 直接抛异常，让整条任务链中断。

## 做法：分层解析 + 强校验 + 受控重试

我把解析器抽成独立纯函数模块，步骤固定：

1. **直读**：原样 `json.loads`，成功且通过 schema 校验即返回。
2. **提取围栏**：正则抓 ``` 围栏，兼容语言标注；注意不能只取第一段——字段里嵌代码块时会有多段，优先取最长那段再解析。
3. **提取标签**：抓 `<json>` 等已知标签块。
4. **括号配平提取**：字符串感知扫描（记录 `in_string` 和转义态），抓第一个配平的 `{...}`。裸括号计数会把字符串里的 `{` 算进去，这是经典错误。
5. **轻量修复**：以上全部失败后才修复——去尾逗号、删 `//` 注释、全角引号转半角。只修已确认的模式，不做激进全局替换。
6. **校验**：解析成功只是第一步，必须过 pydantic / jsonschema。“结构对了但字段类型不对”的情况并不少。
7. **受控重试**：仍失败则把错误信息和原文回喂模型，最多一次；超限落库告警。有条件时优先用 provider 原生 structured output / tool schema，解析器只做兜底。

## 踩坑点

- 非贪婪正则 ```` ```json(.*?)``` ```` 遇到嵌套围栏会在内层 ``` 处截断，拿到残片。
- 修复“单引号→双引号”时会把 `it's` 这类字符串内部的单引号一起换掉，必须只在解析失败后、且逐模式确认才修。
- 截断 JSON 不要盲目补 `]}`了事，先校验字段完整性，缺关键数据宁可重试。
- 别忽略 BOM 和零宽字符，少数模型的输出头部会带。
- “测试通过”不等于“线上稳”：温度、模型版本、上下文长度都会改变漂移概率。

## 可复用建议

- 解析器保持纯函数，配一组 fixture——把线上失败原文脱敏后收进来，每次换模型跑一遍回归。
- 失败时务必记录 raw 原文和命中的变体类型，这是后续改进提示词最有价值的素材。
- 解析预算封顶：fallback 层数和重试次数都是常量，防止自动化任务里死循环烧 token。

## 总结

提示词约束是概率性的，代码处理是确定性的。工程上的正确姿势是：提示词尽力约束，代码假设它一定失守——分层解析、强校验、受控重试、持续观测。四件事都不复杂，但能把“偶尔挂掉”的流水线变成“偶尔降级”的流水线。
