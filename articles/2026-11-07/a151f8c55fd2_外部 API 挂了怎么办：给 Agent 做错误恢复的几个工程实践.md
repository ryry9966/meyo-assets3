## 背景

跑 Agent 的同学大概都遇到过：流程设计得挺好，一上线就撞上第三方接口抖动——LLM 供应商返回 429、MCP 工具背后的 SaaS 服务 503、webhook 目标超时。Agent 和传统脚本的区别在于，失败之后它不会安静退出，而是拿着错误上下文继续"思考"。轻则烧 token 空转，重则幻觉出一个根本没执行成功的操作结果。所以错误恢复不是可选项，是 Agent 工程的标配。

## 问题

实际观察到的故障大多落在三类：

1. **重试风暴**：收到 429 后立刻原样重发，越限流越重试，把配额彻底打穿。
2. **副作用重复**：写操作（发消息、建工单、下单）在超时后被重试，用户收到三条一模一样的通知。
3. **错误被吞**：插件 catch 掉异常返回空字符串，模型以为调用成功，基于假结果继续走流程。

## 做法

我们的原则是把恢复逻辑放在工具层，而不是写进提示词。分五步：

1. **错误分类**。把失败分成四类：可重试（429/5xx/超时）、不可重试（4xx 参数错）、需降级、需人工。分类决定后续动作，不要一上来就重试。
2. **指数退避重试**。基础 1 秒，倍增间隔，加随机抖动，上限 3~5 次，严格尊重 `Retry-After` 响应头。
3. **熔断**。同一上游连续失败 N 次后短路一段时间，直接走降级路径，避免雪崩把故障放大。
4. **降级路径**。每个关键工具准备 Plan B：读操作回退到缓存或备用 provider，写操作挂起进入待办队列，绝不静默丢弃。
5. **幂等与恢复点**。所有写操作带幂等键（比如任务 ID + 步骤序号），Agent 状态定期落盘，故障恢复后从检查点续跑，而不是从头来过。

工具层返回给模型的结构化错误大致长这样：

```json
{ "ok": false, "error": "rate_limited", "retryable": true, "retry_after_ms": 2000 }
```

模型拿到的是语义化信号，而不是一段裸 stack trace 让它自己猜。

## 踩坑点

- **把所有错误都当可重试**：参数错误重试一百次也是失败，先分类再动手。
- **把重试逻辑写进提示词**："如果失败了再试一次"这种指令不可控，模型可能重试二十次，且每轮上下文都在膨胀。
- **只重试不熔断**：上游已经挂了还在排队重试，只是把故障时间拉长。
- **无限循环 Agent + 无上限重试 = token 火灾**：务必给整条链路设总预算（次数 + 时长 + 成本）。
- **吞异常返回空结果**：等于亲手给模型喂幻觉素材，这是最隐蔽的一类事故。

## 可复用建议

- 错误处理下沉到插件 / MCP 工具层，向上只暴露结构化错误码，让模型做决策而不是让它猜。
- 每个对外写操作生成幂等键，配合服务端去重。
- 用故障注入做测试：mock 一个永远返回 503 的工具，看你的 Agent 是优雅降级还是当场崩掉。
- 留人工兜底通道：连续失败的任务进死信队列，带上完整上下文等人工介入，不要让 Agent 悄悄放弃。

## 总结

外部 API 一定会挂，问题只是什么时候。Agent 的错误恢复核心就三件事：**先分类、再退避、留退路**。重试是手段不是目的——把失败变成显式、可观察、可恢复的状态，而不是一次静默的幻觉，这才是 Agent 生产化的分水岭。
