## 背景

跑自动化时常见一个诉求：让模型去干一件"过程很脏"的活——翻几百条日志、批量核对文档、逐个验证配置。这类任务的中间产物可能有几十万 token，谁也不想让它们全灌进主会话。OpenClaw 的思路是子 Agent：主会话派生一个独立 session 去干脏活，干完只交回一份结论。听起来简单，实际用下来有几个坑值得记一笔。

## 问题：隔离没做对时的三种典型污染

1. **上下文暴涨**：子过程逐条回流主会话，几轮之后主会话被压缩，最早下的关键指令被挤掉。
2. **记忆互相覆盖**：子 Agent 和主会话写同一份 `MEMORY.md` 或共享笔记，后写的赢，先前的记忆丢了。
3. **状态串台**：两个并发子 Agent 写同一个工作文件互相覆盖；或者子 Agent 继承了主会话残留历史，基于过时上下文"自作主张"。

## 做法

以下以常见用法为例，具体工具名以你部署的版本为准。

1. **派生独立 session，不要复用主会话。** 用类似 `sessions_spawn` 的方式派生时，确认子 Agent 拿到的是全新 session，不带主会话历史。任务所需的最小上下文显式写进任务 prompt，不要靠"它应该能看到"。
2. **约定结果契约。** spawn 时在 prompt 里明确返回格式，比如固定三段：结论 / 证据路径 / 未解决项。禁止复述过程。主会话只消费这份结构化结论。
3. **文件系统隔离。** 每个子 Agent 一个独立工作目录（如 `workspace/subtasks/<task-id>/`），主 workspace 对它只读。需要改共享状态时，让子 Agent 把补丁写进自己目录，由主会话统一合并。
4. **写操作收口。** 子 Agent 工具权限按需裁剪：能读主 workspace，不能直接改 `MEMORY.md`；涉及共享文件的写动作全部回到主会话侧执行。
5. **清理与观测。** 子任务结束后确认子 session 已归档或可清理；子 Agent 日志落盘到独立路径，事后排障不占主会话上下文。

## 踩坑点

- **回传即污染。** 子 Agent 的最后一条消息本身就是主会话上下文的一部分。让它"顺便总结一下过程"，三千字流水账照样把主会话撑爆。回传内容要当正式产物来审。
- **隐性共享。** 有些插件 / MCP server 是全局单例，子 Agent 调用时改了全局状态——浏览器 profile、临时目录、登录态——主会话再用就翻车。并发子任务要么给独立实例，要么加锁排队。
- **继承幻觉。** 子 Agent 一旦继承主会话历史，就会基于可能已过时的上下文行动。宁可多打几行事实进任务 prompt，也别赌上下文新鲜度。
- **残留 session。** 子 Agent 超时被杀后，session 可能还挂在列表里，日积月累一串尸体，还有被误投递的风险。定期清一次 `sessions_list`。

## 可复用建议

- **结果契约模板化**：每次 spawn 复制同一段返回格式说明，减少口头发散。
- **目录即边界**：一个子任务一个目录，这是成本最低的隔离手段。
- **主会话保持"只读协调者"角色**：所有写共享状态的动作，收口到主会话或专门的后处理步骤。
- **大结果先落盘再传路径**：详细结果写文件，回传只带路径和摘要，上下文成本几乎归零。

## 总结

session 隔离的本质不是"开个子会话"这个动作，而是控制信息流向：**过程往下沉，结论往上收，写权限往回收**。把这三条当成默认值，子 Agent 才是主会话的放大器，而不是污染源。
