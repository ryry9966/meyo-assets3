## 背景

用 agent 干活久了，最烦的不是模型不够聪明，而是它每次都像失忆：你说过十遍“用 pnpm、别加多余注释、commit message 写英文”，下次会话照样给你 npm 命令。上下文窗口再大，默认也不会跨会话保留“你是谁、你怎么干活”。OpenClaw 这类可挂 MCP 工具的 agent 框架，把记忆留给了用户自己设计——既是自由度，也是坑。

## 问题

三种常见做法都有硬伤：

1. **全塞 system prompt**：偏好一多就膨胀，token 成本上升，条目之间还会互相冲突；
2. **靠聊天历史做 RAG**：召回的是对话原文，噪声大，一句玩笑可能被当成指令；
3. **无门槛自动记忆**：什么都记，一个月后记忆库变垃圾场，关键偏好被淹没。

核心矛盾是：记忆不仅要“记得住”，更要“记得对、用得上”。

## 做法

我在自己项目里落地了一套三层记忆，一个小 JSON 存储加一个轻量 MCP server 就能跑：

**1. 分层。** 偏好层（稳定的个人习惯：语言、工具链、代码风格）、事实层（项目事实：部署路径、分支约定）、会话层（临时上下文，不持久化）。重点经营偏好层。

**2. 结构化存储。** 不存整段话，存条目：`{key, value, scope, confidence, updated_at}`。scope 分 `global` 和 `project:<path>`，防止项目偏好泄漏到全局。

**3. 写入有门槛。** 让 agent 在对话中判断“这是可复用偏好，还是一次性指令”，只有前者才写入；密钥、token 等敏感内容先过正则过滤。

**4. 读取有预算。** 会话开始时按 scope 过滤，按 confidence 排序取 top 20，注入 system prompt 尾部，统一写成祈使句（“输出使用英文”，而不是“他喜欢英文输出”）。也可以封装成 `recall` 工具让 agent 按需查询。

**5. 可审计、可衰减。** 条目带来源会话 ID；新旧偏好冲突时提示覆盖；长期未命中自动降权。给用户一个 review 入口，能直接增删改。

## 踩坑点

- **召回了 ≠ 被遵守**。注入位置和措辞影响很大：祈使句、集中放 prompt 尾部，效果明显好于散落各处。
- **记忆污染**。一次“先别用 TypeScript”被永久记住，我花了一下午排查为什么它一直生成 JS。所以必须有更新和删除机制，不能只增不减。
- **scope 混淆**。早期没做 scope 过滤，把 A 项目的“端口固定 3000”带进了 B 项目。
- **一上来就上向量库**。偏好记忆多是短句，关键词 + scope 过滤基本够用，向量检索反而引入不相关召回。先跑通，再优化。

## 可复用建议

- **手写种子记忆**：冷启动时手动写 20 条自己的核心偏好，比全自动抽取靠谱得多；
- **记忆做成独立 MCP server**：暴露 `remember / recall / list / forget` 四个工具，任何 agent 都能挂；
- **记录注入日志**：每次会话注入了哪些条目、agent 是否遵循，攒两周数据再调置信度权重，别拍脑袋。

## 总结

Agent 记忆的本质不是“更大的上下文”，而是**结构化、有写入门槛、可审计的持久化偏好**。从一个小 JSON 加两个工具函数开始，先让它稳定记住 5 条偏好，比直接搭一套向量记忆系统价值更高。记忆系统首先是个运维问题，其次才是算法问题——先保证可控，再谈聪明。
