## 背景

过去一年我把大部分自动化流程挂在云端 API 上，直到某天翻账单：一个每天只做摘要、分类和轻量工具调用的后台 Agent，月消耗抵得上一块二手显卡的月供。另一个动机是隐私——MCP 工具链里经常带本地文件路径、内网地址和运行日志，这些内容发给第三方 API 总归不踏实。于是有了这次把模型搬回家的实验。

## 问题

家用环境有三个硬约束：

1. **显存**：主流消费卡 8–24GB，Mac 靠统一内存但带宽有限，70B 级别基本不用想。
2. **速度**：Agent 循环里模型要反复"思考—调工具—读结果"，首 token 延迟和生成速度直接决定体验。
3. **可靠性**：小模型的工具调用明显不如旗舰模型稳，JSON 出错、参数幻觉都会让整条自动化链断掉。

所以这次的目标不是"跑起来"，而是"跑到能稳定干活"。

## 做法

**1. 盘硬件，定上限。** 12GB 显存 / 16GB 内存是分水岭：以下选 7B–8B，以上可以上 14B。32GB 统一内存的 Mac 可以考虑 MoE 结构的 Qwen3-30B-A3B，激活参数少，速度依然能打。

**2. 选量化档位。** 实测 Q4_K_M 是工具调用场景的底线，再压质量塌得很快；显存富余就上 Q5/Q6。

**3. 装运行时。** Ollama 上手最快，llama.cpp 更可控，两者都暴露 OpenAI 兼容接口，Agent 侧几乎零改造：

```bash
OLLAMA_CONTEXT_LENGTH=8192 ollama serve
ollama pull qwen3:14b
```

**4. 接 OpenClaw。** base_url 指到 `http://localhost:11434/v1`，上下文压到实际需要的值（摘要类任务 8k 足够），注册给模型的 MCP 工具从 20 个砍到 5 个以内。

**5. 建基准。** 从真实任务里抽 20 条，固定 prompt 跑一遍，记录成功率、tokens/s 和首 token 延迟。以后换模型只看这张表。

## 踩坑点

- **KV cache 吃显存比想象狠。** 14B 模型开 32k 上下文，光缓存就多占好几 GB，直接 OOM。上下文按需给，别无脑拉满。
- **小模型函数调用爱"自由发挥"。** 两个解法：开 structured output / grammar 约束；或在 Agent 侧加一层 schema 校验加重试。后者通用性更好，我最终用的是后者。
- **GPU offload 层数默认保守。** llama.cpp 记得手动调 `-ngl`，我的卡从默认值调到 33 层后速度翻倍。
- **量化包下载损坏不报错。** 表现为输出乱码，校验 hash 能省两小时排障。
- **Mac 注意内存压力。** 统一内存别让系统吃满，留 20% 余量，否则瞬间 swap、速度跳水。

## 可复用建议

- **分层路由，别二选一。** 现在的架构：本地模型处理高频低难度的活（分类、摘要、格式转换、简单 MCP 调用），拿不准的升级云端。成本降了七成，隐私数据不出门。
- **基准集是资产。** 那张 20 条的评测表现在是换模型的唯一依据——感觉不可信，数据可信。
- **锁定模型版本。** 用 tag + hash 固定，别用 latest，一次静默更新就可能让自动化链悄悄变脆。
- **工具定义少即是多。** 给小模型的工具列表越短，调用越稳。

## 总结

本地部署的门槛比两年前低很多，但"能跑"和"能干活"之间隔着量化、上下文、工具调用可靠性这几道坎。我的结论：8B Q4 起步验证链路，14B 是目前家用环境的甜点位，MoE 适合大内存 Mac。别追参数量，先建基准集，让数据决定哪个模型上岗。
