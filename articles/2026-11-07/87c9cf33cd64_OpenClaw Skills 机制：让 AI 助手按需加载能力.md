## 背景

OpenClaw 的 agent 默认只有裸模型加几个基础工具。Skills 是它的能力扩展机制：每个 skill 就是一个文件夹加一份 SKILL.md，用自然语言描述"什么情况下做、具体怎么做"。它不是传统插件——不注册回调、不注入代码，本质上是一份模型会按需读取的操作手册。

## 问题

把能力说明塞进上下文的两条老路都走不通：

- **全量注入**：十几个技能几千 token 的说明常驻 system prompt，贵且稀释注意力，模型反而容易漏看关键约束。
- **手动粘贴**：每次会话人工贴文档，等于没有自动化。

核心矛盾是：能力清单必须常驻（模型得知道"有什么"），但细节应该按需（用到才读）。Skills 用**两段式加载**解决这个问题——会话启动时只注入每技能两三行的名称和描述，模型判定相关后才通过 read 工具加载全文。

## 做法与步骤

1. **建目录**：`~/.openclaw/skills/pdf-report/`，内放 `SKILL.md`。
2. **写 frontmatter**：`name` + `description`。description 是路由信号，模型靠它决定是否读取，要写成"触发条件 + 一句话能力"，例如：`当用户要求把对话整理成 PDF 报告时使用，依赖 weasyprint CLI`。
3. **写正文**：固定骨架——适用场景 → 前置检查（依赖是否存在）→ 操作步骤（给可直接执行的命令）→ 失败兜底。
4. **细节外置**：长参数表、示例放 `references/` 子目录，SKILL.md 里写"详见 references/api.md"，让模型第二步再读。
5. **验证**：重启 gateway，开新会话问一个踩边界的触发问题，查日志确认两件事——技能出现在索引里；触发时发生了 read 动作。

## 踩坑点

- **description 含糊 = 永不触发**。我写过"处理 PDF"，三个月没人调用；改成"用户要求生成或合并 PDF 时使用"后触发率才正常。
- **YAML 格式错误导致静默失败**。缩进错、冒号后没空格，整个 skill 不会被索引，报错很安静，改完务必看启动日志。
- **正文里放完整可执行脚本，模型会"手痒"直接跑**。给片段，或明确标注仅供阅读参考。
- **技能描述了但依赖没装**。Skill 不能替你装环境，前置检查必须写成正文第一步："检查 xxx 是否存在，不存在则提示用户安装"。
- **改完不生效**。索引在会话启动时构建，修改后要新开会话，老会话读的是旧索引。
- **别和 MCP 抢活**。MCP 负责接服务、暴露工具；skill 沉淀"怎么组合这些工具"的流程知识。两者是互补不是替代。

## 可复用建议

- 把 description 当**函数签名**写：输入是触发条件，输出是能力描述，控制在 20–50 字。
- 一个 skill 只做一件事。"报告生成"和"报告发送"拆成两个，触发边界更干净。
- 易变的路径、版本号、密钥引用写正文，不写 description，降低索引维护成本。
- skills 目录进 git，改动走 PR。团队共享时，review 的重点就是 description 质量。
- 累积到 30+ 个技能时索引本身开始占上下文，定期清理从未触发的技能。

## 总结

Skills 机制的价值不在"插件多强"，而在**渐进式披露**：索引常驻、细节按需，用几百 token 的固定开销换一整套可复用的操作流程。它把 agent 的能力管理从 prompt 工程降级成文件管理——可版本化、可 review、可共享。建议从沉淀一个你反复手把手教模型的流程开始，比一次写十个泛用技能有效得多。
