## 背景

OpenClaw 里有两条让 agent「定时干活」的路径：

- **cron**：显式排程。用 cron 表达式定义「几点跑、跑什么 prompt」，到点触发，支持把结果投递到指定频道。
- **heartbeat**：周期性唤醒。agent 每隔一段间隔（默认 30 分钟）自己醒来，读工作区的 `HEARTBEAT.md`，自行判断「现在有没有值得做的事」，没事就安静回去。

两条路都能实现「每天发日报」，所以新装的同学经常纠结。我把自己踩过的坑整理一下。

## 问题：混用的代价

我最早的用法很粗糙——所有周期需求全塞进 `HEARTBEAT.md`，包括「每天早上 9 点发工作日报」。结果：

1. **时间漂移**。心跳醒来时刻受上一轮会话耗时和排队影响，日报经常 9:10、9:25 才出来，对准点有要求的场景不可接受。
2. **token 放大**。每次心跳都是一轮真实会话（读文件、推理、可能调工具）。检查项写得太泛，等于每半小时烧一次全量上下文。
3. **不可审计**。heartbeat 的行为依赖模型当时的判断，同一检查项今天做明天不做；而排程类需求本质是要确定性。

反方向也有人踩坑：把「每 5 分钟盯一次某个状态」拆成 288 条 cron 任务，管理成本爆炸。核心矛盾是：**你要的是确定性调度，还是自主巡检？**

## 做法

我的选型原则一句话：**时间驱动用 cron，状态驱动用 heartbeat。**

### 该用 cron 的场景

触发时间明确、对外有约定的事：早报/晚报、每周复盘、到点提醒、备份提示。配置大致是：

```json
{
  "cron": {
    "jobs": [
      {
        "name": "morning-digest",
        "schedule": "0 9 * * *",
        "payload": "汇总昨日会话摘要，发到日报频道",
        "deliver": true,
        "channel": "daily"
      }
    ]
  }
}
```

也可以用 `openclaw cron add` 命令行建任务，`openclaw cron list` 看清单。字段名以你装的版本为准。

### 该用 heartbeat 的场景

没有固定触发时间、需要「持续留意」的事：盯目录有没有新文件、检查长任务跑完没有、发现异常主动汇报。做法是把 `HEARTBEAT.md` 写成**可快速判定的 checklist**：

```markdown
- inbox/ 有新文件？→ 有则摘要并通知我，无则跳过
- longrun.log 末尾出现 ERROR？→ 有则贴出上下文并告警
```

每条写清「什么条件算有事、有事做什么」，让模型醒来只做判断，不做闲聊。

### 混合：两者配合

我目前稳态运行的结构：cron 负责三班准点交付（早报、周报、备份提醒），heartbeat 每 30 分钟巡检一次目录和日志，发现异常才主动插话。各干各的，互不抢戏。

## 踩坑点

- **时区**。容器里没配 TZ，cron 的 9 点按 UTC 算，直接变成下午 5 点触发。部署后先跑一条每分钟任务验证时间。
- **会话隔离**。cron 任务默认跑在隔离会话里，与 heartbeat/主会话上下文不互通。别指望它「记得」你昨天聊天里说的偏好，prompt 里写全。
- **心跳频率**。30 分钟对巡检够用，改成 5 分钟前先算 token 账；高频需求更可能该用 cron 表达式，而不是心跳硬扛。
- **HEARTBEAT.md 膨胀**。检查项超过 5 条，单次心跳的判断质量明显下降，还容易漏。定期清理、合并同类项。
- **一次性任务**。别放心跳里靠模型「记住明天提醒我」，交给 cron 的单次触发，到期自动干净。

## 可复用建议

1. 新需求先问一句：**这事有确定的钟点吗？** 有 → cron；没有、只是「要留意」 → heartbeat。
2. `HEARTBEAT.md` 控制在 3–5 条，全部是可判定条件，不写叙事性描述。
3. cron 任务统一命名（`daily-xxx`、`weekly-xxx`），每月 `cron list` 清理一次僵尸任务。
4. 交付目标分开：例行报告进固定频道，异常告警走私聊，避免互相淹没。
5. 改完频率观察一两周 token 消耗和触发记录再定稿，别拍脑袋。

## 总结

cron 和 heartbeat 不是二选一的竞争关系，而是分工：**cron 负责「准时」，heartbeat 负责「在线」**。确定性排程交给 cron，开放式巡检留给 heartbeat，`HEARTBEAT.md` 保持精简，token 和可靠性就都稳得住。如果你场景里两者总在打架，大概率说明需求本身该拆开。
