## 背景

跑过几轮 Agent 任务后会发现一个规律：**大部分 token 花在低难度步骤上**——清理工具输出、抽取字段、格式化、总结。这些活全压在 GPT 上，又贵又不一定快。而 OpenClaw 支持全局默认 / Agent / 节点三级模型配置，天然适合做「按步骤路由」：规划类、不可逆操作留给 GPT，高频低风险步骤切到本地模型。

## 问题

三个现实压力：

- **成本**：一个 Agent 循环跑十几步，工具输出全部回灌上下文，单任务在 GPT 上轻松烧掉几万 token；
- **隐私**：本地文件、内部文档的摘要走本地不留痕，走 GPT 就要上传；
- **延迟**：简单步骤上本地 7B/14B 反而更快。

但「全切本地」会翻车：规划跑偏、工具参数幻觉、JSON 不守 schema，返工排查的成本比省下的 API 费更高。

## 做法

1. **先全量跑 GPT，拿到基线**。开启 OpenClaw 的 trace 日志，给每个节点标注任务类型和失败率。没基线就降级，等于盲切。
2. **按风险分三档**：
   - 高风险：任务拆解、决定调用哪个 MCP 工具、一切写操作（发消息、写库）→ GPT；
   - 中风险：代码生成、多条件抽取 → 14B 级本地模型，跑 eval 后再定；
   - 低风险：总结、格式转换、字段抽取 → 本地 7B-14B。
3. **配置路由**：全局默认保持 GPT，只在具体节点类型上切本地。路由边界尽量按 MCP server / 工具命名空间划分，比按 prompt 内容匹配更稳。
4. **加 fallback 链**：降级节点本地优先，置信度不足（如结构化输出解析失败）时回落 GPT，并设重试上限。
5. **建小型 eval 集**：每类节点 20–50 个用例，任何切换前后各跑一遍。用数据说话，别凭感觉。

## 踩坑点

- **本地上下文撑爆**：OpenClaw 挂的 MCP 工具描述全塞进 prompt，小窗口模型直接溢出。本地节点要精简工具列表。
- **通用跑分 ≠ 工具调用可靠性**：基准测试高分不代表函数参数不幻觉，必须在真实任务上 eval。
- **本地不一定快**：消费级 GPU 跑长输出可能比 GPT 还慢，切换前先压测。
- **fallback 死循环**：本地失败→GPT 兜底→再失败→回本地，重试成本反超全量 GPT。重试上限必须配。
- **模型被静默升级**：本地模型 pull 更新后行为漂移，pin 住版本。

## 可复用建议

- 按「出错的代价」路由，而不是按 prompt 长度：不可逆操作用强模型，可逆的只读操作本地够用。
- 监控「单次成功任务的成本」，而不是每千 token 成本——前者才反映真实收益。
- 把节点级 eval 挂进 CI，换模型、改配置都必须过 eval。
- 本地节点用压缩版工具描述，GPT 节点保留完整版。

## 总结

多模型路由不是二选一，而是**用证据逐步降级质量的工程过程**。稳妥路径：全量 GPT → 建基线和 eval → 逐节点下切本地 → eval 守住就留，守不住就回滚。省下的钱要能对账，才是真的省了。
