## 背景

用 OpenClaw 跑常驻 Agent 的同学应该都见过 workspace 里的 SOUL.md。它不是 system prompt 的替代品，而是一份跨会话持久生效的人格与边界声明：每次对话、每次心跳，Agent 都会重新读取。它决定的是“这个助手长期是什么样”，而不是“这一轮怎么答”。

## 问题

我最初没把它当回事，结果踩了两类典型的失控：

一是**人格漂移**。日常闲聊没问题，跑两三天后称呼、语气、做事风格开始变，时而过度热情刷存在感，时而把确认流程忘光。

二是**边界模糊**。最惊险的一次，它在心跳任务里“顺手”整理了我的联系人列表，并尝试给对方发消息。当时约束散落在各个会话的临时 prompt 里，改动成本高，行为完全不可预测。

## 做法

后来我把 SOUL.md 当代码治理，几个步骤：

1. **先分层**。IDENTITY.md 管“我是谁”（名字、称呼），SOUL.md 管“我怎么做事”（价值观、禁区、默认行为），AGENTS.md 管“流程怎么走”。三份文件职责不重叠。
2. **SOUL.md 只写三段**：我是谁（5 行以内）；我不做什么（明确禁区）；拿不准时怎么办（比如“先问再动手”）。
3. **每条边界写成可判定的句子**。“语气克制、专业”这种形容词没有约束力，改成“回复默认不超过 5 句；涉及花钱、对外发消息、删改文件，必须先确认”。
4. **小步迭代**。一次只改一条，观察几天再改下一条，文件尾部留一行变更注释，方便回滚。
5. **交叉引用**。SOUL.md 声明原则，AGENTS.md 把原则落到具体工具调用流程，两边用一句话互相指向。

## 踩坑点

- **写太长**。一度膨胀到几百行，关键约束被稀释，注意力覆盖不到。现在控制在 60 行以内，短而硬。
- **禁区太抽象**。“不要做危险操作”等于没写，必须具体到动作 + 对象：不主动给联系人发消息；单次任务工具调用超过阈值先汇报。
- **把流程塞进 SOUL.md**。部署步骤、定时任务逻辑属于 AGENTS.md，混写后两边改动互相污染。
- **边界一刀切**。写过“未经确认不得使用工具”，结果 Agent 遇到该动手的场景反复请示，日常任务全卡住。禁区要分级：可自动 / 需确认 / 禁止。
- **和 USER.md 打架**。个人偏好放 USER.md，SOUL.md 里明确冲突时谁优先，否则换个场景行为就不一致。

## 可复用建议

- 用“三段式”模板起步：我是谁 / 我不做什么 / 拿不准时怎么办。
- 每条边界按“触发条件 + 允许或禁止的动作”写，写完自问：这条能被判定违反吗？
- 准备 3~5 个固定测试对话做回归：诱导它越界（比如让它替你给朋友发消息），观察是否守住。每次改完 SOUL.md 跑一遍，相当于单元测试。

## 总结

SOUL.md 的价值不在“人格感”这种玄学，而在于把散落的隐性约束收敛成一份可版本管理、可回归验证的行为契约。短、硬、可判定，永远比长而全有效。人格是产品决策，边界是工程问题——后者才是这份文件真正的杠杆。
