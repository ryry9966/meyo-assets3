## 背景

OpenClaw 常驻助手默认带一种 heartbeat 机制：每隔 N 分钟唤醒一次 agent，检查有没有待处理的事——未读消息、定时任务、需要巡检的状态。另一条路线是“推送”：由外部事件（webhook、MCP 通知、插件回调）主动触发 agent。两条路我们都跑过一段时间，这里把取舍记录下来。

## 问题

纯轮询的问题很直观：

- 大部分唤醒是空转，白烧 token；
- 间隔短了费钱，间隔长了响应延迟明显；
- 多实例部署时，容易重复响应同一条消息。

纯推送的问题更隐蔽：

- 需要维护常驻接收端（webhook 服务或消息队列），部署成本上来了；
- 事件源一多，每个插件都得自己实现推送；
- 推送丢失、重复、乱序没有天然兜底——agent 掉线，消息就没了。

## 做法：低频心跳 + 事件推送

我们最终落在“事件优先、心跳兜底”的混合结构上：

1. **能推送的一律推送。** 凡是能拿到 webhook / MCP 通知的事件源，注册推送，不做轮询，延迟控制在秒级。
2. **心跳只做巡检。** interval 拉到 30 分钟，heartbeat prompt 里明确只允许做三类事：检查推送队列是否积压、执行定时任务（如日报）、确认订阅源还活着。其余情况一律返回 `HEARTBEAT_OK` 空响应，不产出内容。
3. **唤醒侧做去重。** 用 Redis（本地部署用文件锁也行）记一个 processed key，多实例下只有一个实例真正执行。
4. **推送侧加重试与幂等。** webhook 先落库再异步投递，消息带唯一 ID，agent 处理前先查重。

## 踩坑点

- **心跳里塞太多逻辑。** 最初我们把“未读消息汇总”也放进 heartbeat prompt，结果每 30 分钟必产生一轮实打实的模型调用；改回推送后，这块 token 消耗降了约 80%。
- **空心跳也花钱。** 哪怕返回“无事可做”，一次唤醒就是一次完整调用。interval 不是越保险越好。
- **推送乱序。** 两个事件先后到达但被并发处理，agent 拿着旧状态回复了新问题。后来按会话加了个简单的串行化队列才解决。
- **心跳掩盖故障。** 推送链路断了，要等下一次心跳巡检才发现。这个发现延迟本身就是设计的一部分，应该写进预期文档，而不是当成 bug 追。

## 可复用建议

- 一句话判断标准：**有事件源就推送，没有才轮询；轮询间隔按“可接受的故障发现延迟”倒推，而不是按“多快能响应”倒推。**
- heartbeat prompt 要写得像运维巡检脚本：限定检查项、限定输出格式、无事可做就明确空返回。
- 任何唤醒路径都做幂等：消息带 ID，处理前查重。

## 总结

轮询和推送不是二选一。推送负责延迟，心跳负责兜底，职责分开之后，token 成本和故障发现时间都变成了可调参数，而不是玄学。
