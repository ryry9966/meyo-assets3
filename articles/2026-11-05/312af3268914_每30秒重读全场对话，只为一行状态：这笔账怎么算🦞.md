最近开发者圈刷屏的一条技术新闻：Claude Code 的状态栏（status line）被实测发现，每 30 秒就把整段对话历史重新发送一遍给模型，只为了更新终端底部的一行小字。Claude Code 负责人 Boris Cherny 随后回应，确认机制确实如此，而且是有意的设计。「Token 浪费」的批评和「这是设计哲学」的辩护在社区里吵成一团。这事表面看像一则工程八卦，拆开看，其实是大模型应用开发里非常典型的一堂成本课。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-05/896d5dcc0eef2671.png)

## 先看机制：状态栏为什么要把对话「重读」一遍

- Claude Code 是 Anthropic 的命令行编程 agent。它提供一个自定义状态栏功能：你配置一条 shell 命令，系统把当前会话的上下文（完整对话 transcript、模型名、工作目录、git 分支等）以 JSON 形式喂给这条命令，命令输出的第一行显示在终端底部。
- 关键在于：这条命令里**可以调用模型**。如果状态栏脚本写成「把 transcript 塞给 `claude -p`，让模型用自然语言总结当前状态」，那么每次刷新就是一次完整的 LLM 调用。
- 而 LLM API 是**无状态的**：服务端不会替你记住之前的对话，每次请求都必须把全部上下文重新传输、重新计费。这是 Transformer 推理服务的通用工作方式——即便服务端有 KV cache，那也只是复用计算结果，输入 token 该收的钱一分不少。
- 于是出现了那个荒诞画面：对话越长，刷新一次状态栏越贵。为了底部那约 20 个字符的输出，输入端可能扛着几万甚至几十万 token 跑一趟。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-05/85cdf195acbe6862.png)

## 一笔细账：这行字到底烧多少钱

用一组保守的估算把账摆到桌面上：

1. 假设一场编码会话累积到 8 万 token 上下文（重度用户很常见）；
2. 每 30 秒刷新一次 = 每小时 120 次调用；
3. 每次输入 8 万 token → 每小时约 **960 万 input token**；
4. 按 Claude Sonnet 档位约 $3/百万 token 的输入价，全价计算约 **$29/小时**——比模型本体干正事的开销还高。

当然，实际账单没这么吓人，因为有两个折扣机制兜着：

- **Prompt caching**：Anthropic API 支持前缀缓存，命中缓存的输入按约 1/10 价格结算。30 秒的刷新间隔落在缓存 TTL（默认 5 分钟）之内，所以大部分刷新能吃到折扣价；
- **输出极小**：状态栏每次只吐一行，几十个 token，基本可以忽略。

即便如此，按缓存价算一小时也要约 $3，挂机一晚就是一杯咖啡钱——花在一行「当前分支：main」上。这就是社区炸锅的原因：逻辑上站不住，工程上有兜底，两边都有道理。

## 设计哲学：官方为什么觉得「这很合理」

Boris Cherny 的回应大意是：让状态栏能拿到完整对话，它就能展示任何「模型知道的事」，灵活度拉满。背后其实是一条清晰的产品路线：

- **用最聪明的组件干所有事**：代码量最小、可组合性最强。状态栏想显示「是否在跑测试」「距上次提交改了几个文件」？不用写解析器，一句话让模型自己判断。
- 这和机器学习圈常说的 **bitter lesson** 一脉相承：与其手工设计精巧规则，不如把算力怼上去，让通用能力碾压特化方案。
- 反方观点同样成立：状态栏是纯展示型任务，确定性极强。git 分支名、todo 数量、耗时，shell 脚本零 token 就能拿到；让旗舰模型干这个，属于「开卡车送明信片」。
- 工程界的惯例是 **model routing**：按任务难度分配资源——开场白用大模型，意图分类用小模型，格式校验用正则。Claude Code 在这里选择了「不分档」，把成本转嫁给用户。真正的争议点在这：不是技术做不到分级，而是产品暂时不打算做。

## 业界常规操作：同样的活，能省多少

把「一行状态」这类需求放进通用工程视角，至少有五档省钱方案，按实施难度从低到高排：

1. **规则优先**：分支名、文件数、计时这类确定性信息，用脚本直接读，成本为零。能用代码算的，永远别用模型猜；
2. **模型降级**：确实需要语义理解时，用 Haiku 这类小模型，输入单价约为旗舰的 1/3，质量对一行状态绰绰有余；
3. **降频**：状态栏不需要秒级智能。把 30 秒改成 5 分钟，调用量直降 90%，肉眼几乎无感；
4. **增量输入**：只发送「自上次刷新以来的 diff」，或定期压缩的摘要，而不是全量 transcript；
5. **Prompt caching**：退一万步必须全量重读，也要把长上下文挂进缓存，让重复部分按 1/10 价格结算——Claude Code 自己就是这么兜底的。

这五档不是理论假设，而是各家 agent 框架的标配动作。差异只在于：有的产品帮你做了，有的把选择权（和账单）一起留给你。

## 三条冷思考

1. **「浪费」要算总账再看。** Token 成本 = 频次 × 上下文长度 × 单价 − 缓存折扣。任何一项单独拿出来骂都可能冤枉人。Claude Code 这事就是典型：绝对量惊人，但边际成本被缓存压低了一个数量级。看账单，别看截图。
2. **成本结构正在成为 agent 产品的核心竞争力。** 功能相似的两个 agent，单位任务成本差 10 倍，商业上就是生死线。判断一个 agent 产品是否成熟，看它怎么给「贵模型」和「便宜手段」分工，比看 demo 炫技有用得多。
3. **给开发者三条可执行的动作**：自定义状态栏优先写 shell 脚本读本地状态；确实要调模型，就选小模型并拉长刷新间隔；用 API key 计费的重度用户，打开 prompt caching、定期用 /compact 压缩上下文，并在控制台里单独盯住这类「隐形调用」的用量——它烧起钱来，安静得很。
