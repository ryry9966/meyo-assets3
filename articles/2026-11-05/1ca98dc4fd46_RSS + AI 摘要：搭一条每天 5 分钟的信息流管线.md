## 背景

RSS 没死，只是被推荐算法挤到了角落。对我这类需要持续跟进 Agent / MCP 生态的人来说，RSS 仍是唯一完全可控的信息源：结构化、无算法干预、可程序化处理。但问题不在订阅，而在订阅之后——几十个源每天产出几百条更新，逐条读不现实。

## 问题

原始痛点有三个：

1. 噪声高：真正值得读的可能不到 10%
2. 时间碎片：没有整块时间逐篇判断值不值得点开
3. 上下文丢失：隔几天再看，早忘了当初为什么订阅这个源

目标很朴素：每天早上收到一份按相关度排序的摘要简报，5 分钟内完成分诊——读、稍后读、丢弃。

## 做法

管线分四层，用 OpenClaw 的定时任务驱动，跑在一台小 VPS 上：

**1. 采集层**
- 源清单用 OPML 维护，方便迁移
- 没有 RSS 的站点走 RSSHub 路由补齐
- 每次运行记录已处理的 entry GUID（SQLite 一张表），避免重复

**2. 预处理层**
- 按 `published` 时间过滤，只取上次运行后的新增条目
- 关键词白/黑名单先粗筛，能砍掉一半流量
- 抽取 title + description；description 过短的尝试抓原文正文

**3. 摘要层**
- 批量喂给 LLM，要求输出结构化 JSON：`{summary, relevance_score, tags, action}`
- prompt 里明确"仅基于给定内容，信息不足则标注 insufficient"，压幻觉
- 按相关度阈值过滤，超量则截断保 Top K

**4. 分发层**
- 拼装 Markdown 简报：按 tag 分组，每条附原文链接
- webhook 推到 IM，同时落一份本地文件归档

## 踩坑点

- **description 不等于正文**。很多源的 description 只有前两句，直接摘要会产生大量 insufficient。后来改成三级策略：短摘要 → 抓原文 → 失败则降级为仅按标题分类
- **GUID 不稳定**。个别源每次刷新 GUID 都变，去重失效。兜底用 link + title 的哈希做二级去重
- **时区坑**。published 字段有的 UTC 有的本地时区，直接比较会漏抓或重抓，统一转 UTC 再过滤
- **成本失控**。初期所有条目无差别过 LLM，token 消耗很难看。加关键词预筛 + 低相关直接跳过后降了 70% 以上
- **RSSHub 路由会失效**。某条路由突然 404 是常态，单源失败只记日志发告警，不阻塞整条管线

## 可复用建议

- 状态持久化（已处理 ID、上次运行时间）是一切前提，别放内存
- 采集、摘要、分发三层解耦，任何一层挂了其余还能跑
- LLM 输出强制结构化，下游的排序过滤才好做
- prompt 做版本管理，效果回退时有据可查
- 简报宁短勿长，超过 20 条就砍——简报的目标是分诊，不是替代阅读

## 总结

整套管线写完大约一个周末，日常维护成本很低，偶尔处理失效源。它最大的价值不是"自动读了文章"，而是把每天的判断成本从半小时压到 5 分钟。RSS 的开放性 + LLM 的压缩能力，是当前信息过载环境下性价比很高的一组组合。下一步计划把分诊结果（哪些被丢弃）回灌进 prompt，做最简单的偏好修正。
