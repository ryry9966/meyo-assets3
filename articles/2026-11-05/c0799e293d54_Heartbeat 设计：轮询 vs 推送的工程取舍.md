## 背景

OpenClaw 的 agent 默认是被动响应式的：有消息进来才干活。但自动化场景经常要求 agent 具备“主动巡检”能力——盯一个数据源、定时汇总、发现异常主动提醒。heartbeat（心跳）就是为此设计的：每隔一段时间唤醒一次 agent，让它自己判断有没有需要主动处理的事。

社区里反复出现一个问题：既然有 webhook，为什么不全部改成事件推送？事件来了直接触发，省掉空转不好吗？

## 问题

两种机制的核心矛盾不在性能，而在**判断逻辑放在哪**：

- **轮询**：判断逻辑在 agent 内部，每次醒来由 LLM 综合上下文判断。灵活，能发现“没预料到的事”，但每次唤醒都有 token 成本，时效受间隔限制。
- **推送**：判断逻辑前置到 agent 之外，由事件源决定“这事值得打扰 agent”。时效好、平时零开销，但触发规则要自己写全，漏写的事件永远不会被处理。

一句话：轮询是持续付费买兜底，推送是提前把所有情况枚举清楚。

## 做法：分层混合

我的实践是分层，不二选一：

1. **推送层管高时效事件**。可控、结构化的事件源（CI 结果、监控告警、邮件到达）一律走 webhook → gateway → 注入 agent 会话。延迟秒级，不占心跳预算。
2. **心跳层管兜底巡检**。间隔放宽到 30–60 分钟，prompt 里明确收口：
   ```
   [HEARTBEAT] 检查当前状态。若无需要主动上报的事项，
   仅输出 NO_REPLY，不要执行任何工具调用。
   ```
   gateway 捕获 `NO_REPLY` 后静默丢弃，不打扰用户。
3. **精确时刻任务走 cron，不走心跳**。心跳是“间隔”不是“时刻”，每天早八点的日报交给 cron 调度，别指望 30 分钟间隔的心跳撞准时间。

## 踩坑点

- **心跳响应刷屏**：早期没做空响应约定，agent 每次心跳都汇报一句“暂无异常”，把聊天窗口刷掉。prompt 约定 + gateway 过滤必须成对出现。
- **推送重试导致重复触发**：webhook 服务端重试让同一事件触发了两次执行。加一个事件 ID 去重窗口（5 分钟内相同 ID 只投递一次）。
- **推送撞上会话锁**：agent 在处理长任务时推送进来会排队。接受排队，不要强行并发——两个任务同时改同一份工作区文件才是真灾难。
- **心跳间隔的隐性成本**：5 分钟一次看着不多，乘上系统提示词的固定 token，一个月是一笔可观的账。间隔宁长勿短，时效靠推送补。

## 可复用建议

用一个简单矩阵决定某件事交给哪一层：

- 事件源可控、触发条件可枚举 → **推送**
- 需要精确时刻 → **cron**
- 事件源不可控，或你根本想不到要监控什么（长尾异常、状态漂移）→ **心跳兜底**
- 心跳永远保持低频，只做最后防线，别拿它当主触发器

## 总结

轮询和推送不是对手，是分工。推送解决“已知事件要快”，心跳解决“未知事件要有人看着”，cron 解决“固定时刻要准”。把判断逻辑放在最便宜、最确定的那一层，agent 的主动能力才既灵敏又不烧钱。我目前的稳定配置是：心跳 45 分钟 + `NO_REPLY` 静默 + webhook 去重，跑了两个月没再出过刷屏和重复执行的问题。欢迎在评论区交换你们的心跳间隔和踩坑记录。
