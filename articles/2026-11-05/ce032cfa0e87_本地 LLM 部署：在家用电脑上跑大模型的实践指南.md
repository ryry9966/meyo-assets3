## 背景

过去一年我把自己的一批自动化流程逐步迁到了本地模型上：笔记摘要、邮件分类、家庭相册整理、一些敏感数据的初步处理。动机很实际——高频低难度的任务走 API，一个月烧掉的费用不小；而涉及私人数据的任务，走云端心里总不踏实。这篇帖记录从选型到接入 Agent 的完整路径，供社区参考。

## 真正的问题是什么

对做 Agent 的同学来说，问题从来不是"模型能不能跑起来"，而是**能不能稳定跑完一个 Agent 循环**。循环意味着：系统提示 + 工具描述 + 多轮上下文反复进模型，token 消耗是单轮对话的 10 倍以上；同时要求模型可靠地产出工具调用 JSON。很多模型聊天像模像样，一当 Agent 大脑就开始幻觉参数、漏调用、格式崩。先把这条预期立住，再谈部署。

## 硬件与选型

按我实际测过的三档：

| 配置 | 可跑模型（Q4 量化） | 体验 |
|---|---|---|
| 16GB 内存、无独显 | 7B~8B | CPU 推理 5~10 tok/s，能跑但慢 |
| 8~12GB 显存 | 7B~14B | 30~60 tok/s，日常够用 |
| 16~24GB 显存 | 14B~32B | 当前家用甜点位 |

运行时推荐 Ollama 起步：一行装好，自带 OpenAI 兼容端点，接 OpenClaw 最省事。要精细控制再上 llama.cpp；vLLM 只在显存充裕、需要并发时考虑。

## 部署步骤

1. 安装 Ollama，`pull` 一个量化模型（Qwen3-14B Q4 是我目前的默认款）。
2. **改上下文长度**。Ollama 默认上下文很小，Agent 场景必改：建 Modelfile 设 `num_ctx 8192` 起步。
3. 在 OpenClaw 的模型配置里指向 `http://localhost:11434/v1`，走 OpenAI 兼容协议。
4. 先接**一个最简单的 MCP 工具**（比如查时间）验证工具调用链路，再逐步加复杂工具。
5. 用真实任务跑基准：记 tokens/sec 和任务成功率，别只看 benchmark 分数。

## 踩坑点

- **上下文截断是头号杀手**。默认 ctx 下，工具描述一多，历史轮次被悄悄裁掉，Agent 表现"时好时坏"——90% 的诡异行为源于此。
- **量化别低于 Q4**。Q3 以下工具调用 JSON 可靠性明显劣化，省的那点显存不值得。
- **KV cache 吃显存**。上下文拉到 16K 后，实际显存占用远超模型体积标称值，规划时留一半余量。
- **工具数量克制**。小模型挂 10 个以上工具，参数幻觉率飙升。每个 Agent 只挂它真正需要的，描述写短。
- **结构化输出把 temperature 压到 0~0.3**，否则 JSON 偶发畸形。
- CPU 推理时并发请求会排队，Agent 里并行调多个工具反而串行变慢，注意。

## 可复用建议

- **分层路由**：本地模型承担高频低难度任务（摘要、分类、格式化），难推理任务回退云端 API。这不是妥协，是工程上的正确分层。
- **维护一份模型档案**：记录量化版本、ctx、temperature、实测成功率，换模型时对照回滚，别凭记忆。
- 日志里固定记录 tokens/sec 和失败样本，这是调优的唯一依据。

## 总结

2025 年在家用电脑上跑 LLM 做自动化已经完全可行，但它替代不了旗舰模型——正确姿势是把它作为路由体系中的一层。先立预期，再控上下文，最后用真实任务验收。有具体硬件配置想讨论的，欢迎跟帖。
