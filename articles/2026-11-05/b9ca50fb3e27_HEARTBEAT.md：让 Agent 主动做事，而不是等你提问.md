## 背景

大多数人用 Agent 的方式仍然是"问答式"：想起来一个需求，发一条消息，等结果。但部署在 OpenClaw 上的常驻 Agent 有更好的工作模式——心跳机制。网关会按固定间隔（默认约 30 分钟）自动唤醒 Agent，让它读取工作区里的 `HEARTBEAT.md`，逐条检查有没有需要处理的事项。文件不存在或为空，心跳就等于关闭。

也就是说，Agent 的"主动性"不靠模型自觉，而是靠一份你亲手维护的清单。

## 问题

我最初的痛点很典型：想让 Agent 每天看一眼日志里的报错、汇报一下仓库状态，但每次都得自己记得去问。用 cron 调 Agent 又太重——要管调度、管会话、管输出往哪发。心跳机制正好填这个空档：调度由网关负责，我只负责写清楚"什么情况算有事"。

## 做法

**1. 在 Agent 工作区根目录创建 HEARTBEAT.md**（如 `~/openclaw/workspace/HEARTBEAT.md`）：

```markdown
# 心跳任务

## 规则
- 逐条检查，没有到期或触发的事项时，只回复 HEARTBEAT_OK
- 需要人处理才发消息，单条不超过三句话

## 任务
- ~/logs/error.log 今天有新增 ERROR 时，汇总次数和首条堆栈
- 工作目录磁盘占用超过 80% 时提醒
- 每天 09:00 后的第一次心跳：汇报 git 未提交变更列表
```

**2. 调整间隔**。默认间隔在网关配置里改（不同版本字段名略有差异，以你手上版本的文档为准）。巡检类任务 30–60 分钟足够，没必要压到几分钟。

**3. 验证**。人为制造一条触发条件（往 error.log 写一行 ERROR），等下一轮心跳，确认 Agent 真的发来了消息；再清掉条件，确认它安静地只回 HEARTBEAT_OK、没有打扰你。

## 踩坑点

- **每次心跳都是一次完整的模型调用**。30 分钟一次就是一天 48 次，token 费用实打实。清单务必精简，能拉长间隔就拉长。
- **任务写得模糊，心跳就会变成刷屏机器**。"帮我盯着服务器"这种描述，Agent 每次都能找出点事汇报。必须写可判定条件：具体阈值、具体路径、具体时间窗。
- **污染主会话上下文**。心跳跑在 Agent 会话里，长清单和啰嗦输出会挤占正常对话的空间。规则区里限定"无事只回 HEARTBEAT_OK"很关键。
- **别把高风险动作写进心跳**。自动重启、自动 push 放在无人值守的心跳里，出事时你大概率在睡觉。心跳只做"检查 + 汇报"，动作留给确认之后。
- **HEARTBEAT.md 会整体进 prompt**，别把密钥、token 写进去。

## 可复用建议

- 模板固定两段：**规则区**（如何判定"没事"、输出格式限制）+ **任务区**（每条 = 触发条件 + 判定依据 + 动作）。
- 分工原则：**"大约每隔一段时间看一眼"用心跳，"必须准点的定时任务"用 cron**。整点日报交给 cron，日志巡检交给心跳。
- 把 HEARTBEAT.md 纳入 git 管理，巡检规则变更可追溯，也方便多机同步。

## 总结

HEARTBEAT.md 的价值在于把"你记得去问 Agent"变成"Agent 定期自查"。它不神秘，本质是一份随 prompt 周期执行的检查清单——写得好不好，取决于条件是否可判定、输出是否克制。建议先用两三条低风险巡检任务跑起来，观察一周成本和信噪比，再逐步加码。
