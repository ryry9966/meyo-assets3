## 背景：被动应答的天花板

现在绝大多数 AI 助手的交互模型还是“你问它答”：用户发起 prompt，agent 响应，会话结束。这个模型跑通容易，但天花板明显——大量真正有价值的任务（盯一个价格、检查 CI 是否变红、提醒合同到期）本质上是“条件满足就该发生”，而不是“用户想起来才发生”。

OpenClaw 的架构天然支持往 proactive 方向走：cron 触发、webhook 事件、channel 消息、MCP 工具调用都是现成的积木。问题在于，这些积木怎么拼，决定了助手是“顺手”还是“烦人”。

## 问题：为什么大多数 proactive 尝试最后被静音

我见过不少 proactive 尝试以用户关通知告终，模式很像：agent 定时跑，每次调大模型总结一堆“没什么可说的”，然后照样推一条消息。三天后 proactive 能力事实上死亡。背后是三个工程问题：

1. 没有拦截层，噪音直达用户；
2. 没有成本意识，轮询型触发全量走 LLM；
3. 读写动作不分级，出一次事故就整体回退。

## 做法：拆成 trigger → gate → act → report 四段

**1. Trigger（触发源）**：cron 表达式、webhook、事件监听都行。原则是触发越靠近事件本身越好，能用 webhook 就别用高频轮询。

**2. Gate（判断门）**：触发后先别叫大模型。用规则或便宜的小模型先判断“是否值得打扰用户 / 是否值得执行”——状态有无变化？是否越过阈值？判断为否就直接结束，不产生任何用户可见输出。这一层是噪音和成本的主要阀门。

**3. Act（执行）**：过门之后才进完整 agent 流程，挂载 MCP 工具取数、计算、执行。写操作默认走审批，用 OpenClaw 的 exec approval 机制把“发邮件、调外部 API”这类动作排进待确认队列；只读操作可放行。

**4. Report（汇报）**：每条主动消息必须带一句“为什么现在报给你”，即触发源 + 判断依据。能聚合的进日报，单条只留真正紧急的。

## 踩坑点

- **时区**：cron 默认吃服务器时区，“每天早 8 点”实际跑在 UTC。显式指定时区。
- **幂等**：webhook 重试会让同一事件触发两次，轻则重复推送，重则重复执行写操作。给事件加去重键，执行前先查是否处理过。
- **上下文真空**：proactive 运行时没有当前会话上下文，用户在意什么、上次聊到哪，都得自己从 memory 拉，而且这份状态会漂移，需要定期让用户校正。
- **权限收敛**：别给常驻的 proactive agent 挂全量 shell 工具，按场景挂最小 MCP 工具集，出问题时爆炸半径完全不同。
- **反馈回路**：用户回复“这类别再报”必须真的生效——写进过滤规则或 memory，否则等于没听。

## 可复用建议

- 把噪音预算显式化：每天主动消息上限 N 条，超了自动合并进下一次日报。
- 新的主动行为先只读跑一周，统计误报率，降到可接受再放开写操作。
- 每次执行落一条结构化日志：trigger 来源、gate 判断、调用了哪些工具。没有这个，线上排障基本靠猜。
- 主动消息里永远解释自己。用户一眼能判断“该不该报”，这些反馈是调 gate 规则最好的数据。

## 总结

Proactive 的本质不是“更多自动化”，而是“更会判断什么时候该打扰你”。工程上真正值得花时间的就两块：够狠的 gate，和能自我修正的反馈回路。触发源和工具执行都是现成积木，拼装顺序和边界设计才决定成败。建议从“一条每天一次的只读日报”起步，跑顺了再逐个加触发源和写动作。
