## 背景

OpenClaw 的日常任务里，Agent 大量依赖外部 API：LLM 供应商、搜索、天气、家庭自动化，以及各种 MCP 工具。这些调用发生在长任务链的中间环节，任何一处抖动都可能导致整条链失败。更麻烦的是，Agent 不像普通程序那样“崩了就崩了”——它会把错误读进上下文，然后试图“想办法完成任务”，典型结果就是编一个答案出来。

## 问题

实际踩过三类坑：

1. **硬失败**：超时、5xx、限流，工具调用直接抛错，任务中断，或陷入无意义的循环重试。
2. **软失败**：API 返回 200 但数据为空或降级（比如搜索服务限流后返回空列表），Agent 把空结果当真，得出错误结论。
3. **最糟的情况**：错误以纯文本堆栈进入上下文，模型不是慌乱重试，就是自行脑补结果交付。

## 做法

我们的处理原则：**重试是工程层的事，决策是 Agent 层的事**。分四步：

**1. 工具层重试，不要让模型重试。** 在插件/工具包装器里做指数退避加抖动，只对瞬态错误（超时、429、5xx）重试，并设总预算（如最多 3 次、累计 30 秒内）。4xx 一律不重试。

**2. 失败要结构化返回。** 工具不要抛异常，而是返回结构化错误：

```json
{"status": "error", "error_type": "transient", "retryable": false, "reason": "upstream timeout after 3 retries"}
```

模型能读懂这种格式，才能做出“放弃/降级/问用户”的正确决策。

**3. 预设降级路径。** 每个关键工具提前定义失败时的行为：回退到缓存（必须带上数据时间戳）、切换备用供应商，或明确告知用户任务失败。同时在系统提示里写死一条：工具返回错误时，禁止编造结果，必须如实报告。

**4. 加熔断和计数。** 同一供应商连续失败 N 次就熔断 5–10 分钟，期间调用直接走降级路径。用日志统计每个工具的成功率；定时任务失败时要在会话里留痕，而不是静默跳过。

## 踩坑点

- **让 LLM 自己重试**：它不会退避，会立刻连打三次，还可能对 401 这类永久错误反复重试，纯烧 token。
- **把 200 当成功**：务必在工具层做 schema 校验，空数据也算失败。
- **堆栈直接进上下文**：既污染上下文又诱导编造，永远在工具层截住。
- **重试没考虑幂等**：POST 类操作（发消息、下单）盲重试会重复执行，先查幂等键或改用查询确认。
- **静默降级**：拿昨天的缓存顶上却不告诉用户，比直接失败更危险。

## 可复用建议

- 写一个统一的工具包装器：超时、重试、熔断、结构化错误、日志，所有插件复用，别每个插件各造一套。
- 系统提示里固定一句失败处理规范，团队所有 Agent 共用。
- 上线前做故障演练：用 mock 让上游返回超时和空数据，观察 Agent 的实际表现。

## 总结

错误恢复的核心不是“多重试几次”，而是把失败变成 Agent 可理解的结构化信息，并提前铺好降级路径。工程层负责扛住抖动，Agent 层负责诚实地决策和报告。做到这两点，外部 API 挂了只是一次降级运行，而不是一次幻觉交付。
