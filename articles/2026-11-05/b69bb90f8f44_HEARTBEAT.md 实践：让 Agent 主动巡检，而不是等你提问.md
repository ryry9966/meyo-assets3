## 背景

绝大多数 Agent 交互是被动式的：你提问，它回答，然后归于沉默。但 OpenClaw 的 Agent 是常驻进程，挂在你自己的机器上，手里有 shell、浏览器和各类 MCP 工具——让它一直待机其实很浪费。OpenClaw 提供了心跳机制：Agent 按固定间隔（默认 30 分钟）自动醒来，读取工作区里的 HEARTBEAT.md，判断有没有需要处理的事。这个文件，就是你交给它的巡检清单。

## 问题

主动不等于瞎忙，两种失败模式都很常见：

- **太吵**：文件空着或全是空话，Agent 每次心跳都汇报"心跳正常"，半小时一条，很快被你屏蔽。
- **太忙**：把能想到的任务全塞进去，每轮心跳跑一遍完整检查，token 消耗翻倍，还产生大量低价值打扰。

更隐蔽的是判断权问题。"这件事值不值得叫你"默认由 Agent 自己衡量，指令含糊它就用随机标准。"帮我盯着服务器"和"ERROR 超过 3 条时发到 #ops"，是两种完全不同的体验。

## 做法

1. **建文件**：在工作区根目录（通常是 `~/.openclaw/workspace/`）创建 HEARTBEAT.md。
2. **定频率**：在 openclaw.json 里调整心跳间隔，字段形如 `agents.defaults.heartbeat.every`（OpenClaw 迭代快，字段名以你版本文档为准）。从默认 30m 起步，别一上来就调到 5m。
3. **写条目**：每条按"触发条件 + 检查动作 + 通知策略"三段式写：

```markdown
# Heartbeat
- 检查 ~/logs/agent-error.log 最后 50 行，出现新增 ERROR 时摘要发到 #ops；
  同一错误连续两次出现才 @我
- 每天 08:00 后的第一次心跳：汇总昨日 git 提交数发到 #daily，其余时段跳过
- 没有条目命中时，只回复 HEARTBEAT_OK
```

4. **用 HEARTBEAT_OK 约定**：无事可做时让 Agent 只回这个标记，再配合心跳目标渠道的配置，让"正常"类消息别刷进主对话。

跑一两周，看哪些条目真有价值，再决定增删。

## 踩坑点

- **频率 × 清单长度 = 成本**。心跳是乘法关系，5 分钟间隔配 20 条检查就是烧钱，先估算再调。
- **文件越长越容易被略读**。保持在一屏以内，Agent 对清单的执行力随长度衰减，过期条目及时删。
- **别把危险操作直接写进去**。心跳是无人值守触发的，先写"检查并报告"，稳定一两周后再逐步放权到"自动重启某服务"，且必须带明确前置条件。
- **指令必须可判定**。"磁盘快满了就告诉我"不行，"使用率 > 90%" 才行。阈值、渠道、频率都要落到字面。
- **注意上下文污染**。心跳默认跑在主会话里，长任务和大段输出会挤占正常对话的上下文。重活拆给定时任务，心跳只做"看一眼"级别的轻量检查。

## 可复用建议

- **三级通知模板**：静默记录（只写日志）→ 频道消息（发群）→ 直接提醒（@你），每个条目明确落在哪一级。
- **把它当极简 runbook**：写完自问"另一个 Agent 拿到这条能执行吗"，能，就是合格条目。
- **能力上限取决于工具**：心跳能查什么取决于你接了哪些 MCP 工具和插件。装了 fetch 才能盯 RSS，装了日历工具才能做日程提醒。
- **每月复盘**：删掉从未触发的，收敛触发过频的。清单要像代码一样维护。

## 总结

HEARTBEAT.md 的本质，是把"什么时候该打扰你"的判断标准显式写成文件。写得好，Agent 就从问答终端变成一只安静的看门狗；写得差，它就是个半小时响一次的噪音源。克制地写，逐步放权，定期修剪——给 Agent 立规矩，要领也就这些。
