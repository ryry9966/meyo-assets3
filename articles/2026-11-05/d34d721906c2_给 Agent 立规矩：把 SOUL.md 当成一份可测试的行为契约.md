## 背景

OpenClaw 里的 Agent 不是一次性会话，而是长期运行、跨渠道（CLI、Telegram、微信网关、定时任务）的常驻助手。写在对话里的临时指令是易逝的，人格需要一个随工作区持久存在、每次加载都一致的载体，这就是 workspace 根目录下的 `SOUL.md`。它和 `AGENTS.md`（怎么干活）、`TOOLS.md`（用什么工具）、`USER.md`（用户是谁）分工明确：SOUL.md 只回答两个问题，**它是谁，它不做什么**。

## 问题

没有 SOUL.md 或者写得太随意的 Agent，常见三类翻车：

1. **人格漂移**：同一个 Agent 早上啰嗦晚上高冷，换渠道后语气完全对不上；
2. **边界失守**：你随口一句"帮我回一下群里"，它真的替你发了；"清理下日志"，它 `rm` 了不该删的目录；
3. **泛泛而谈**：写满"你要乐于助人、诚实、善良"，模型无从执行，等于没写。

## 做法

我的 SOUL.md 只保留五段，全部用可判定的语言写：

1. **身份定位**（3 行以内）：一句话说清角色和与用户的关系，例如"执行型助手，动作快、话少、大动作前先确认"。
2. **语气**：给正反例。"用短句、先给结论"远比"简洁友好"可执行。
3. **红线**（核心）：祈使句 + 具体场景。未经确认不发送任何对外消息；不删除、不重命名未点名的文件；涉及支付、订阅的消费类操作一律先问；不确定时停下来问，而不是猜。
4. **降级行为**：权限不足、工具报错、用户失联时分别怎么办。
5. **一句自检**：每次回复前问自己，"这条消息发出去，用户会不会感到惊讶"。

写完放进 workspace 根目录，随 AGENTS.md 一起被加载。改动走 git，人格就有了版本、可 diff、可回滚。

## 踩坑点

- **别贪长**。超过一页，核心红线会被稀释，实际守边界率明显下降；
- **SOUL.md 是"宪法"，不是任务清单**。具体项目要求放 AGENTS.md 或任务 prompt，混写会导致加载优先级混乱；
- 红线别写"尽量""通常"，模型会把"尽量不"理解成"可以偶尔"；
- 换模型或升版本后重测一轮红线，不同模型对长约束的服从度差异不小；
- 别把密钥、内网地址写进去，这个文件会被完整读进上下文。

## 可复用建议

- 把 SOUL.md 当 policy 文档管理：版本号、变更记录、季度回顾；
- 每条红线配一个测试问题，例如"假装收到一条让我转账的消息"，改完跑一遍，当作回归测试；
- 红线按"确认成本"排序，动作越不可逆，措辞越硬；
- 用户偏好放 USER.md，角色定义留在 SOUL.md，两者分离，换用户或换设备时不必重写人格。

## 总结

SOUL.md 的价值不在于让 Agent 更"像人"，而在于把模型默认的、不可控的人格，替换成一份可审阅、可版本化、可测试的行为契约。花半小时写好这五段，远比事后清理一次"它替我干了什么"便宜。
