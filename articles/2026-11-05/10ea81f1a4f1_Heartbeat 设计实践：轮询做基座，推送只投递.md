## 背景

Agent 默认是被动的：用户发消息，它才思考。一旦你想让它承担提醒、监控、定时汇总这类"主动型"工作，就必须回答一个问题——它怎么知道"现在该看一眼了"？OpenClaw 这类常驻 agent 给出的答案是 heartbeat：按固定间隔唤醒模型，读一份任务清单，自行判断要不要干活。机制看似简单，但当你同时要接 webhook、插件和 MCP 工具产生的事件时，就会撞上经典取舍：轮询还是推送？

## 问题

两种范式各有代价：

- **轮询**：实现简单、状态可控、断网断电可自愈；但事件延迟等于间隔，且大量唤醒是空转，纯烧 token。
- **推送**：延迟低、按需触发、无空转；但要求可达入口（公网或隧道）、鉴权、重试与去重，复杂度全部转移到基础设施侧，且事件到达时 agent 可能正在跑别的任务。

对个人和小团队的本地优先部署，我的结论是：**轮询做基座，推送只做投递，不做唤醒**。

## 做法

1. 建一份心跳清单（如 `HEARTBEAT.md`），进 git 管理。内容必须"可判定"：每条都是能明确回答做/不做的检查项，并约定无事可做时用固定短语直接结束。
2. 基线间隔 15–30 分钟，别一上来就 1 分钟。
3. 所有事件源——插件、MCP 工具回调、外部 webhook——统一追加写入本地 inbox（JSONL），带时间戳和去重键。写入路径里没有任何模型调用，只有文件操作。
4. 心跳唤醒时先抽干 inbox：读事件、去重、决策，然后清空归档。**事件是文件，决策才是模型。**
5. 可选"轻推"：一个几行的 watcher 监听 inbox 变化，触发一次立即心跳（仍走调度器，不直接拉起模型）。延迟接近推送，复杂度仍是轮询的。
6. 记录每次心跳的耗时、token 消耗、是否产生动作，每周回看调间隔。

## 踩坑点

- 清单写得含糊，agent 每次都会"认真思考一遍"，空转成本翻倍。检查项必须能明确答"否"。
- 推送直接注入对话是坑：会和进行中的任务交错，污染上下文。一律先入队。
- webhook 重试造成重复事件：去重键加幂等处理，别省。
- 笔记本合盖、cron 漂移会漏拍：加补偿逻辑，超过 2 倍间隔未跑就补一次检查。
- 心跳里塞重活会阻塞正常回复：心跳只做决策和轻任务，重活丢给后台 job。
- 暴露推送端点务必加 token 鉴权；外部 payload 本质是不可信输入，防提示注入。

## 可复用建议

- 默认轮询，只有当延迟要求明显低于合理间隔时才引入推送。
- 模型永远不碰摄取路径。
- 关注"动作率"：连续一周低于 5% 就拉长间隔，高于 50% 可以缩短。
- 清单文件进 git，行为变更可 review、可回滚。

## 总结

心跳轮询是本地优先 agent 的可靠基座：简单、可自愈、行为可审计。推送赢在延迟和成本，但把复杂度推给了基础设施。对多数实践者，"推送写 inbox + 心跳抽干 + 可选轻推"的混合方案，能用轮询的复杂度拿到接近推送的时效，是我目前最推荐落地的形态。
