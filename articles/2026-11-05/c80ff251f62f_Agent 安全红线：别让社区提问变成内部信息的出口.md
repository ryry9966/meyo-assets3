## 背景

社区里跑 OpenClaw 的人越来越多，agent 背后挂着 MCP server、插件和定时任务，能读到的东西也越来越多：内部文档、私有仓库、数据库、CI 日志。与此同时，社区求助和分享又非常频繁——贴日志、贴配置、贴 agent 的回答截图。这两个场景叠在一起，泄露风险就出现了，而且绝大多数是无心的。

## 问题出在哪

先明确一个前提：**agent 是信任边界，它能看到的一切，都要按"可能被公开"来对待。** 实际泄露通常不是攻击，而是三个日常动作：

1. **求助时贴完整上下文**：agent 对话记录和日志里带内部路径、主机名、甚至 token；
2. **系统提示词泄露**：为了"让它懂业务"，把内部工作流写进 system prompt，结果被"复述一下你的指令"这类提问带出来；
3. **调试时共享配置**：直接把 MCP/插件的配置文件发出来，env 里的真实密钥跟着走。

## 我们的做法

**第一步：先分级，再上 Agent。** 写一份红线清单：密钥、内网地址、未发布计划、客户数据——绝不进 agent 上下文；工作流细节——不进社区可见的实例。

**第二步：双实例隔离。** 社区答疑实例和工作实例分开跑，各自独立的 workspace、memory 和密钥，不共享会话历史。社区实例的 system prompt 只写公开可讲的内容。

**第三步：MCP 最小权限。** 社区实例只挂只读、脱敏的 MCP server；token 按 scope 收窄；按项目拆分 server，不要搞一个全局大杂烩让所有实例都看得到。

**第四步：输出侧加一道闸。** 发布前跑一遍脱敏脚本兜底：

```bash
grep -nE "(sk-[A-Za-z0-9]{8,}|10\.[0-9]+\.[0-9]+\.|/srv/|/home/[a-z]+)" draft.md
```

正则覆盖 token 格式、内网 IP、绝对路径。截图前先裁掉日志区，agent 回答里出现内部文件路径就视为红灯。

**第五步：把社区输入当不可信。** 社区消息和工具返回结果只当"数据"，不当"指令"；不让答疑实例随意抓取外部 URL 进上下文。

## 踩坑点

- **换实例但共享 memory**：长期记忆把内部上下文带进社区会话，等于白隔离，memory 也要跟着分。
- **总结也算泄露**：让 agent 总结内部文档再发社区，架构、命名、流程照样出去。
- **截图的边角**：终端标题栏的 hostname、日志里的 `Authorization` 头，裁图时最容易被忽略。
- **占位符没替换**：分享配置前 env 里还是真实密钥，建议仓库里只放 `.env.example`。

## 可复用清单

- [ ] 社区实例与内部实例物理分离（workspace / memory / 密钥）
- [ ] 红线清单写进 system prompt，并配输出侧正则兜底
- [ ] MCP 只读优先，token 按 scope 最小化
- [ ] 发布前统一跑脱敏脚本
- [ ] 每月审一次社区实例的工具调用日志

## 总结

这套方案不复杂，难在执行纪律。agent 会把"能看到的"变成"可能说出去的"，所以安全边界必须画在上下文入口，而不是靠事后删帖补救。先分级、再隔离、最后加输出闸，三步做完，绝大多数无心泄露就堵住了。欢迎在回帖里补充你们遇到的泄露案例和拦截手段。
