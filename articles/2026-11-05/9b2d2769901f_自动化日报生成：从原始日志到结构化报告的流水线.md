## 背景

团队每天要交日报，但信息来源很散：git 提交、CI 结果、错误日志、工单系统。人肉汇总费时、易漏，且每个人的颗粒度不一致。我们的做法是用 Agent + MCP 工具搭一条流水线，把日报变成每天定时跑的任务，人只做最后确认。

## 问题

最省事的思路是直接把原始日志丢给 LLM 摘要，实测踩了三个坑：上下文经常爆（一天几万行日志）；输出格式每天漂移；真正的 P0 异常被"平均化"掉，不如人眼。所以核心原则定为：**能写代码确定的，绝不交给模型**。

## 做法

流水线分四层：

1. **采集层**：每个来源一个小脚本（git log、CI API、日志 grep、工单查询），统一输出 JSONL 到当日目录，每条带 `source / ts / severity` 字段。用水位线（上次采集时间戳）做增量，保证可重跑。
2. **清洗层**：纯脚本，无模型参与。去重、按关键词和路径粗分类（部署 / 告警 / 需求进展）、丢弃噪声。
3. **摘要层**：把结构化后的 JSONL（通常几百行以内）交给 Agent，prompt 强制 JSON schema：`{deploy, incidents, progress, risks}`，附 few-shot。输出先过 schema 校验，失败重试一次，再失败就降级为"数据附件 + 生成失败标记"，而不是憋出一个看似正常的报告。
4. **渲染分发层**：模板渲染成 Markdown，推送群 webhook，同时归档到 git 仓库，中间数据和最终产出都保留，方便回溯。

采集和校验各封装成一个 MCP tool，由定时触发器串起整条链路，任何一步失败都会发显式告警。

## 踩坑点

- **别让模型读原始日志**。哪怕截断，也容易漏掉真正的关键异常。先结构化，模型只负责归纳优先级和组织语言。
- **时区问题**。增量采集没对齐时区，导致某天日报重复了一半内容。统一 UTC 存储，渲染时再转本地时区。
- **schema 漂移**。prompt 不锁字段，模型隔三差五自由发挥。锁字段 + 校验 + 重试是底线，不能省。
- **静默失败最危险**。流水线挂了没有任何报错，只是日报没来，第一天大家还以为"今天没事"。失败必须有显式信号。
- **日报太长没人看**。正文控制在一屏内，细节放附录链接。

## 可复用建议

- 分层原则：确定性逻辑用脚本，模型只做归纳与措辞，顺序不能反。
- 中间产物落盘（JSONL），任何时候可以离线重跑摘要层调试 prompt，不必重新采集。
- schema 校验和降级路径值得多花半小时，这是流水线可靠性的下限。
- 换一份 prompt 和模板，同一套采集层可直接复用到周报、发布纪要、值班交接。

## 总结

日报本身价值有限，真正值钱的是"从噪声到结构"这条路径跑通之后的能力：同样的采集层可以直接喂给周报、异常复盘和值守看板。先让数据可靠，再让模型发挥——顺序反了，得到的只是一份每天格式都不一样的漂亮废话。
