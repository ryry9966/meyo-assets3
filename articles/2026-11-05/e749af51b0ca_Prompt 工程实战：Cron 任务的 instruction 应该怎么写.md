## 背景

OpenClaw 的 cron 任务本质上是**无人值守的 prompt**：到点之后，agent 在一个全新会话里拿到你的 instruction，独立执行，全程没有你在场。这和聊天场景最大的区别是——没有上下文、没有追问的机会、跑错了你也不会立刻知道。

很多人把 cron instruction 写成一句日常聊天（"帮我看下今天有啥日程"），结果往往是沉默失败，或者模型自由发挥。

## 问题

我踩过的三类典型失败：

1. **时间语义模糊**：schedule 按 `0 8 * * *` 触发，但 instruction 里写"今天"，而服务器是 UTC、你在东八区，agent 理解的"今天"可能整体错位。
2. **输出没有落点**：agent 认真生成了完整报告，但 instruction 没说发到哪里，结果只留在会话记录里，等于白跑。
3. **失败静默**：数据源抓取失败后，agent 要么编数据，要么什么都不发，一周后你才发现任务在空转。

## 做法

我现在把 cron instruction 当成一个微型 spec 来写，固定五段结构：

```text
【时间基准】以 Asia/Shanghai 时区的当前日期为准，先执行 date 命令确认。
【数据源】仅使用 rss-reader MCP 抓取 <指定 URL>，不要使用其他来源。
【处理】筛出过去 24 小时内的条目，按相关度取前 3 条，每条一句话摘要。
【输出】通过消息工具发送给用户，格式：标题 + 摘要 + 原文链接，总长不超过 150 字。
【异常】抓取失败重试一次；仍失败则发送"今日抓取失败：<原因>"，禁止编造内容。
```

四个关键点：

- **显式注入时间**，不要依赖模型对"今天"的理解；
- **枚举允许的工具**，写明"仅用 X"，否则模型会自选工具，行为不可复现；
- **输出绑定具体通道 + 固定模板**，好处是每天的产出可以直接 diff；
- **失败路径必须写**，并且明确"禁止编造"。

## 踩坑点

- **一步做五件事**。抓取、汇总、分析、发送挤在一条 instruction 里，模型会跳步。拆成两个 cron 任务，中间用文件传递结果，各自独立调试。
- **双重重试**。cron 层自带重试，instruction 里又写"失败再试一次"，结果收到三条重复消息。重试只保留一层，我建议放在 instruction 层，因为模型能区分"值得重试的错误"。
- **没手动跑通就启用**。写完先手动触发两三次，确认输出符合模板，再开 schedule。
- **引用不存在的历史**。"接着昨天的整理"——cron 会话里没有昨天。所有依赖要么重新获取，要么先落盘成文件再读。

## 可复用建议

- 把 cron instruction 存进 git，每次修改单独提交，出问题可回滚；
- 每次运行的输出追加写入日志文件，用极低成本实现事后审计；
- 新任务先跑低风险场景（比如每日摘要），稳定观察一周，再交给它做对外发送类动作。

## 总结

Cron instruction 的写法核心一句话：**假设 agent 醒来时失忆**。时间要显式、数据源要锁死、输出要有落点和模板、失败要发出声音。它不是一句提示词，而是一段用自然语言写成的定时脚本——用写代码的严谨程度去对待它，定时自动化才真正可靠。
