## 背景

E2E 测试大概是自动化里"最该写又最难坚持"的一层：写起来慢、selector 脆、环境一抖就红，团队通常只维护得了核心路径。而 Agent + MCP（比如 Playwright MCP）让模型能直接操作浏览器、读 DOM 和网络请求，这件事的性价比开始变了——不是 AI 比人更懂测试，而是"从零搭出一批可跑用例"这个体力活，现在可以外包出去。

## 直接让 AI 写会怎样

对着模型说"给这个页面写 E2E"，产出通常有三个毛病：

1. selector 用动态 class 或深层 `nth-child`，跑两天就挂；
2. 断言极弱，只判 `isVisible()`，通过率 100% 但什么都没测；
3. 生成"看起来对"的代码，本地没跑过，进 CI 一片红。

本质是模型缺两样东西：**上下文**（不懂你的规范）和**反馈**（没跑过）。做法就围绕这两点补。

## 我们的流程

**1. 备好上下文。** 给 agent 三样东西：测试环境地址和专用账号；一份核心路径清单（登录后做什么、下单走哪几步，十行以内）；一份测试规范文档（selector 一律 `data-testid`、禁止硬等待、断言必须基于用户可见结果、登录统一复用 `storageState`）。这份规范是全流程投入产出比最高的东西，写一次，之后每次生成都复用。

**2. 探索先行。** 让 agent 通过 Playwright MCP 先自己把核心路径走一遍，观察真实 DOM 和网络响应，再基于看到的东西写用例，而不是凭想象编。

**3. 生成 + 本地闭环。** 要求生成后必须本地跑通，失败就读报错和 trace 自修。设两个硬约束：最多自修三轮，超过就停、输出失败报告，不许无限烧 token。

**4. 人工抽查。** 人只做一件事：挑三五条用例，问"这断言测的是业务结果还是实现细节"。把 `expect(page.url())` 该不该换成订单状态文本，一眼能看出来。

**5. 进 CI。** 新用例先非阻塞跑一周，收 flaky 率，稳定后再入门禁。

## 踩坑点

- **把"修测试"当"修问题"**：跑挂了 agent 可能直接放宽断言让测试变绿。规范里必须写明：怀疑产品 bug 时停下报告，禁止为通过而改断言语义。
- **测试数据不确定**：共享测试账号的数据被人一改就 flaky，核心路径要固定种子数据或跑前重置。
- **探索不等于覆盖**：agent 只走"顺"的路径，异常分支（校验失败、超时）基本不会主动碰，异常用例目前仍要人给清单。
- **登录态各自处理**：每条用例登一次又慢又易被风控卡，统一注入 `storageState`。

## 可复用建议

- 把"测试规范 + 核心路径清单"做成仓库常驻文档，作为 agent 固定上下文——这比换更强的模型有用。
- 用 MCP 浏览器工具跑"探索 → 生成 → 执行 → 自修"闭环，缺了执行环节的生成基本是废纸。
- 把 agent 当成不熟业务但手很快的初级测试：它铺量，人定规范、做抽检。
- 从 5–10 条核心冒烟路径起步，别一上来就追覆盖率。

## 总结

Agent 写 E2E 的真实价值不是替代测试工程师，而是把"从零到一批可运行用例"的成本压到原来的零头。效果好坏几乎取决于你给的约束与反馈闭环：规范越死、本地执行越严、人工抽查越认真，产出越可用。反过来，只丢一个 URL 就想要全套回归覆盖，目前还不现实。
