## 背景

OpenClaw 的 workspace 里有个容易被忽视的文件：`~/.openclaw/workspace/SOUL.md`。很多人装完直接跑，默认人格能用就不再碰它。但当你的 Agent 接上 MCP 工具、跑起定时任务、能碰 shell 和消息通道之后，“它是谁、它什么不做”就不再是情趣问题，而是工程问题。

SOUL.md 会注入 system prompt，是控制 Agent 长期行为最便宜的杠杆：不改代码、不写插件，改完下一个 session 生效。

## 问题

没认真写过 SOUL.md 的团队，通常会撞上三件事：

1. **人格漂移**。长会话、多轮压缩之后语气慢慢变形——昨天还克制，今天满屏 emoji 抢答。
2. **边界失守**。它“热心”地自动执行了没批准的操作，或在你深夜调试时往群里发了不该发的总结。
3. **文件打架**。SOUL.md 说轻松一点，AGENTS.md 要求正式输出，USER.md 又塞一堆偏好，冲突时行为不可预测，排查起来比 bug 还烦。

## 做法

我把它当配置代码管理，分四步：

**1. 分层归位。** 明确职责：SOUL.md 管“我是谁、我的底线”；AGENTS.md 管“怎么干活”；USER.md 管“用户是谁”。人格和流程分开放，冲突自然减少。

**2. 写行为，不写形容词。** “专业、有趣、有分寸”没有操作意义，换成可判定的句子：

- 不在 23:00–8:00 发送非紧急消息
- 涉及删文件、对外发消息时，先列计划等我确认
- 被质疑时先复述我的问题，不急着道歉或反驳

**3. 控制篇幅，给硬边界留位置。** 全文 500 字以内效果最好。结尾固定一段“绝对不做”清单（3–5 条），每条绑定具体工具或场景，比如“不主动执行 rm / 格式化类命令”。

**4. 进 git，按行为修。** 每次发现越界行为，加一行对应约束，像修 bug 一样提 commit，不要心血来潮整篇重写。

## 踩坑点

- **别指望人格文件当安全边界。** SOUL.md 是软引导，模型状态差时会被忽略。硬限制要靠工具白名单、沙箱和确认门禁兜底，两层都得有。
- **改完没生效不是玄学。** 正在跑的会话不会热加载，reset 或开新 session 再验证。
- **别整篇抄别人的。** 人格和你的真实使用场景错位，效果比默认还差。参考结构可以，句子要自己写。
- **换模型后做回归。** 不同模型对 persona 的服从度差异明显，升级后拿两三个典型场景各跑一遍。

## 可复用建议

- 骨架固定五段：身份与语气 / 价值观 / 硬边界 / 与用户的关系 / 2–3 个风格示例（场景 → 期望回复）。
- 硬边界永远绑定工具名和具体场景，不写抽象原则。
- 风格示例是性价比最高的部分：两条真实的“这种情况该怎么回”，胜过十句形容词。
- 每月重读一遍，删掉已经内化到 AGENTS.md 或工具权限里的重复项。

## 总结

SOUL.md 的本质，是把你对 Agent 的期望从“聊出来的默契”变成“可版本化、可回归的配置”。写它只要半小时，省下的是无数次“它怎么又这样”的排查。人格不是玄学，是配置文件——认真写，进 git，按行为迭代。
