## 背景

绝大多数助手默认是"被动应答机"：你问一句，它答一句。但真正省时间的场景往往不是问答，而是"它先发现、先行动"——日历冲突提前提醒、监控指标越界时主动汇总、每天固定时间推一份待办摘要。

OpenClaw 在架构上已经给了主动性足够的基础设施：heartbeat 定时唤醒、cron 作业、webhook 事件，以及通过 MCP 接入的各类工具。问题是，这些能力拼起来之后，很多人的第一版"主动助手"都变成了定时骚扰器。

## 问题

把 proactive 做稳，本质是回答三个工程问题：

1. **何时触发**：时间驱动、事件驱动还是状态驱动；
2. **触发后做什么**：判断"值不值得打断用户"；
3. **如何收敛成本与噪音**：token 开销、消息频率、误报率。

模型能力反而不是瓶颈，瓶颈在触发器设计和打断策略。

## 做法

**第一步：把触发源分类。** 时间型用 heartbeat/cron（每日摘要、周报）；事件型用 webhook/MCP 通知（新邮件、CI 失败）；状态型靠轮询外部状态（域名到期、库存水位）。先只做时间型，最可控。

**第二步：精简 heartbeat 清单。** heartbeat 会周期性唤醒 agent 并读取任务清单，清单务必短、可判定，例如"检查今日日历是否有冲突，有则提醒，无则不回复"。每条都要能被一句话判定为"有事/没事"，否则 agent 会自由发挥。

**第三步：静默累积 + 定时汇报。** 非紧急发现不直接发消息，写入工作区的"待汇报"文件，由每日一次的 cron 汇总成 digest。打断用户的机会要留给真正值得的事。

**第四步：给不可逆操作加闸门。** 主动"读"随便做，主动"写"必须过确认：agent 先把拟执行动作写成计划，等你回复"执行"再调用工具，这条规则直接写进系统提示。

## 踩坑点

- **heartbeat 间隔拍脑袋定。** 每 15 分钟醒一次，单次 2–3k token，一个月就是几十万的固定开销。从每天 2–4 次起步，按漏报率往上调。
- **自触发循环。** agent 主动发的消息又触发事件监听，再唤醒自己。给每类事件加来源过滤和冷却时间。
- **通知疲劳。** 主动消息每天超过三五条，用户就开始无脑忽略，系统等于失效。宁可憋着进 digest。
- **时区与静默时段。** cron 按 UTC 配置、半夜推送，是最常见的事故，配置里要显式写 quiet hours。
- **清单一长就漂移。** 任务清单塞了二十条后，agent 经常漏做或串做，超过五条就拆成多个不同频率的作业。

## 可复用建议

1. 冷启动路径固定为：单工具、只读、单渠道、每日一条 digest，稳定两周再加能力。
2. 检测、决策、执行三段分离：轮询只产生"事件"，决策层对照规则决定打断还是入队，执行层才持有工具权限。
3. 把主动行为日志留下来：每日触发次数、打断式发送几条、进 digest 几条、你实际回复几条。没有这份数据，调参全靠感觉。
4. 规则写在配置里，不要靠提示词祈祷。

## 总结

proactive 不是"让模型更聪明"，而是一套触发器 + 打断策略 + 权限边界的工程设计。先用最笨的时间触发跑通"发现—决策—汇报"闭环，再逐步引入事件与状态触发。判断你的主动助手是否合格，标准只有一个：它发来的每条消息，你都愿意看。
