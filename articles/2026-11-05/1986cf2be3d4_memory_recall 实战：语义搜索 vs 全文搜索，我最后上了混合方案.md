## 背景

给 Agent 做长期记忆，绕不开 `memory_recall` 这一步：用户问“我之前怎么配置的部署脚本”，助手得先从记忆库里捞出相关条目，再组织回答。常见的两条实现路线：

- **全文检索**：BM25 / SQLite FTS5，按关键词匹配；
- **语义检索**：文本 embedding 后算余弦相似度，按“意思相近”匹配。

社区里常见论调是“向量检索更高级”。我们在给 OpenClaw 自建 memory_recall 插件（走 MCP 接记忆库）时，最初也直接上了 embedding 方案，跑了两周发现召回质量参差，才回头认真做了对比。

## 问题：两类 query，两种死法

拿真实的记忆库（几百条事实卡片 + 会话摘要）测试，很快发现两类典型失败：

1. **专有名词类 query 挂在语义检索上**。比如“那个走 9092 端口的服务叫什么”，embedding 会把 "9092" 揉成模糊向量，目标条目排不进 top-5；全文检索一击即中。
2. **措辞漂移类 query 挂在全文检索上**。记忆里写“偏好小步灰度发布”，用户问“上线策略”，关键词零交集，全文检索空手而归。

结论：没有谁全面胜出，取决于记忆内容的形态。

## 做法与步骤

最终方案四步，可直接复用：

1. **记忆分层入库。** 事实卡片（短、含名词）、会话摘要、原始日志分开存，检索优先前两层。
2. **双路索引。** 全文路用 SQLite FTS5 + BM25；语义路整条向量化，不做激进切分——记忆条目本来就短，切太碎反而丢上下文。
3. **RRF 融合。** 两路各取 top-10，用 Reciprocal Rank Fusion 合并：`score = Σ 1/(60 + rank)`，十行代码，比手调加权稳得多。
4. **评测集回归。** 人工整理 40 条 query，标注应召回的记忆 ID，每次改动跑一遍 recall@5。专有名词类和措辞漂移类各占一半。

## 踩坑点

- **FTS5 中文分词是第一坑**。默认 unicode61 把中文整句当一个 token，基本啥也搜不到。要么用 trigram，要么入库前过一遍 jieba 再存，我们选了后者，可控。
- **embedding 对短代号不敏感**。“v2-beta 集群”这类 token 在向量空间里没有区分度，别指望语义路兜底。
- **top-k 别贪大**。早期返回 top-15，无关记忆塞满上下文，模型反而开始幻觉，收敛到 top-5 后明显改善。
- **加时间衰减**。三个月前的过时配置和新配置同分返回，模型会混淆。按 `updated_at` 做指数衰减折分，一行公式的事。
- **评测集要覆盖“空召回”场景**。有些 query 本来就无答案，要确认检索返回空而不是硬凑，否则模型会拿无关记忆编答案。

## 可复用建议

- 记忆内容专有名词多（配置、服务名、命令）→ 全文权重该高；抽象偏好、经验总结多 → 语义价值大；拿不准就上 RRF，别手调权重。
- 落地顺序：先全文兜底（一天能上线），再逐步加语义路和融合，每步用评测集验证。
- 把 recall@5 写进 CI，记忆库 schema 或 embedding 模型一变就跑，检索退化当场抓到。

## 总结

语义 vs 全文不是二选一，而是互补：全文检索守住精确字符串和专有名词的底线，语义检索补上措辞漂移的召回。memory_recall 的质量上限，往往不取决于检索算法多先进，而取决于你有没有一个能持续跑的评测闭环。先让召回可度量，再谈优化。
