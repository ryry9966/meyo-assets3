## 背景

用 Agent 写技术帖的流程已经跑通大半：模型产初稿，人工补细节，定稿。真正卡人的往往不是写，而是发——同一篇内容要投公众号、知乎、掘金和自己的博客，四个地方的格式约束完全不同。我们把这个过程抽成了一条 Markdown 管线，跑了几个月，把做法沉淀下来。

## 问题

两层问题叠在一起。

第一层是 AI 产出的 Markdown 本身不“干净”：一级标题满天飞、加粗滥用、代码块不带语言标记、偶尔夹带 HTML 和 emoji。人眼看没问题，机器处理到处炸。

第二层是平台方言：

- 公众号只认内联样式的 HTML，外链图片直接被吞；
- 知乎、掘金吃 Markdown 但支持面不同（脚注、公式、alerts 各有取舍）；
- 博客要 front matter 和特定的图片路径。

不抽管线的话，每个平台等于手工维护一份副本，改一处漏三处。

## 做法

核心思路：规范化与平台适配拆成两段，规范源只留一份。

1. **规范源**。内容以严格 GFM 存在一个仓库，front matter 声明 title、tags 和目标平台矩阵。AI 初稿落盘先过 `prettier` + `markdownlint`（自定义规则：标题从 H2 开始、禁止行内 HTML、代码块必须带语言标记），不合格打回。
2. **AST 层转换**。所有自动改写走 remark/unified 的 mdast 插件，不写正则。“全文标题降一级”“剥离 HTML 节点”“中英文之间补空格”这类规则，在 AST 上跳过 code 节点即可。
3. **平台适配器**。每个平台一个小模块：公众号走 MD→HTML 再注入内联样式模板；知乎直接出 Markdown 但图片重传；博客补 front matter。产物统一进 `dist/`，当构建产物管理。
4. **图示处理**。Mermaid 多数平台不渲染，管线统一转 SVG 上传；公众号单独调素材接口换 `media_id`。
5. **发布校验**。dry-run 渲染一遍，检查死链、图片数、标题层级，机器过了再进人工终审。

## 踩坑点

- **正则改写是大坑**。全角标点替换、补空格这类规则，遇到代码块里的字符串就出事故，务必走 AST。
- **别只靠 prompt 约束格式**。prompt 能减少问题但保证不了下限，lint 兜底，两者都要有。
- **公众号图片**必须走 API 上传换占位链接，且有频控，批量发要节流。
- **复杂表格**在知乎会被截断，能用列表就不用表格。
- **HTML 注释当私有指令**要小心，个别平台会渲染出来。

## 可复用建议

把 normalize 做成独立 CLI 或 MCP tool，Agent 写完稿自己调用一次再交人工，流程里就少一轮“格式打回”。适配器保持无状态、可单独测试，新平台接入只需加一个 adapter。发布版本打 git tag，出问题可精确回滚。

## 总结

多平台发布本质是构建问题，不是编辑问题：源文件一份、转换走 AST、适配器独立、发布前机器校验。这套结构跑下来，从定稿到全平台发布压在十分钟以内，格式事故趋近于零。管线不难，难的是忍住不在中间手改。
