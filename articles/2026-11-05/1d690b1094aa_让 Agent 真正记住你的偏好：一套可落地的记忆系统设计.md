## 背景

用 OpenClaw 这类 Agent 框架跑日常自动化时，最常见的抱怨不是能力不够，而是"不记事"。每次新会话都要重说一遍部署路径、代码风格偏好、常用服务器列表。Agent 本身无状态，上下文窗口再大也只是短期工作台。记忆不是一个功能开关，而是一套需要认真设计的子系统。

## 问题

大多数实现停留在两个极端：要么把全部历史塞进 system prompt（很快爆上下文、成本失控），要么完全不管（体验退化为复读机）。核心难点有三个：

1. **写什么**：对话里 90% 是噪音，稳定偏好只占少数；
2. **何时读**：检索时机和注入预算都直接影响效果；
3. **如何更新**：偏好会变，三个月前的"永远用 pnpm"今天可能已经错了。

## 做法

我在自己的 Agent 里按五步落地，全部能力通过 MCP 工具暴露：

1. **定义条目结构**。每条记忆是结构化记录：`type`（preference / fact / workflow）、`content`、`source`、`confidence`、`updated_at`。不存大段原文，只存一句话级别的原子事实。
2. **写入策略**。会话结束（或每 N 轮）跑一次抽取调用，用廉价模型从对话中提取候选偏好，打分后入库。同时支持显式指令："记住我喜欢 X"直接走 `memory_store` 工具，绕过抽取，置信度置 1。
3. **存储选型**。起步阶段 SQLite + FTS5 全文检索完全够用；条目过千再考虑向量库。别一上来就堆 embedding 基建。
4. **读取策略**。每轮对话前检索：语义/关键词召回 top-k，按 `updated_at` 加权，去重后控制在 300 token 以内注入 system prompt。预算是硬约束，宁可少注入。
5. **冲突与遗忘**。写入时对同 type、内容相似的旧条目做更新而非追加；长期不被命中的条目降权或归档。

## 踩坑点

- **记忆污染**：用户随口一句"这次先用 npm 吧"被固化为永久偏好。对策：抽取 prompt 里明确区分一次性指令和稳定偏好，一次性行为不入库。
- **静默失败**：检索没命中时 Agent 不吭声，用户误以为它记得。对策：命中分数低于阈值时明确说"我没查到相关记忆"，并提示可用指令显式写入。
- **注入越多越差**：塞 20 条记忆后模型反而抓不住重点。实测 5~8 条、按相关性排序效果最好。
- **黑盒记忆**：用户无法查看和删除记忆，信任崩得很快。做一个 `memory_list` / `memory_delete` 工具，把记忆暴露给用户是必须项，不是可选项。

## 可复用建议

- 顺序别反：先做"显式写入 + 结构化存储"，再做自动抽取，最后才上向量库。
- 每条记忆必须带来源和时间戳，这是冲突处理的全部依据。
- 准备一个 20 条左右的评测集（历史偏好问答），每次调整检索策略后跑一遍，别靠手感调参。
- 分工清晰：抽取用便宜模型，检索用规则兜底，主对话模型只负责消费记忆。

## 总结

记忆系统的本质是"写什么、何时读、怎么更新"三个策略问题，而不是选哪个数据库。从最小闭环做起：结构化条目 + 显式写入 + 带预算的检索注入，跑稳后再逐步加自动抽取和遗忘机制。能被用户查看、纠正和删除的记忆，才算真正可用的记忆。
