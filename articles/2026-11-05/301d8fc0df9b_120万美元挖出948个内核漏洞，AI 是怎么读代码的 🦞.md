最近一条技术新闻刷了屏：OpenAI 与 Linux 基金会合作，用自家 AI 模型把 Linux 内核的源码整个扫了一遍，挖出 948 个此前未知的漏洞，成本约 120 万美元。消息一出，社区两边吵翻：一边问"三十年、全球上万工程师盯着，怎么还能漏这么多？"，另一边问"AI 挖洞已经便宜到可以按斤称了？"。这篇就把三个问题拆开讲清楚：这些洞为什么存在，AI 靠什么找到它们，以及这 120 万美元到底买到了什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-05/e2fa713dde08423f.png)

## 一、"全球审得最严的代码"，为什么还藏着 948 个洞

先补个背景：Linux 内核不是"一个服务器软件"，它是世界上部署量最大的单体软件之一——全球 Top500 超算全在跑，安卓手机、路由器、智能电视、车机底层也都是它。它的审查强度堪称地狱级：

- 规模：约 4000 万行 C 代码，每个版本周期上万次 commit，数千名开发者、数百家公司参与提交
- 流程：任何 patch 都要经过子系统维护者 review、多层合并、持续测试才进主线

那为什么还有洞？四个结构性原因：

1. **C 语言的内存模型天生危险**：内存手动申请释放，use-after-free、double free、越界访问这三类问题占了内核历史漏洞的大头
2. **错误路径没人走**：测试和 fuzzing 大多打 happy path，"第 38 层嵌套里 `return -ENOMEM` 之后调用方忘了释放"这种分支，常规测试几乎覆盖不到
3. **并发问题难以复现**：锁顺序错误、竞态条件，跑一千次可能只崩一次
4. **长尾代码缺人看**：大量十几年前的驱动只有一两位兼职维护者

换句话说，不是维护者不努力，而是人工 review 的速度跟不上代码膨胀和路径组合爆炸的速度。4000 万行，就算一人每天读 1000 行不睡觉，也要一百多年——人类的脑内 cache 没这么大。

## 二、AI 靠什么找到它们：不是 fuzzing，是"语义级审阅"

很多人第一反应是"AI 是不是跑了高级版 fuzzing？"——不是。三种技术路线得分清楚：

- **动态 fuzzing**（内核多年在用的 syzkaller/syzbot）：变异输入砸系统调用，看崩不崩。优点是真，缺点是只能覆盖输入能到达的路径
- **传统静态分析**（Coverity、CodeQL 这类）：按人写好的规则和数据流模式扫，误报率高，新模式得靠人写规则
- **LLM agent 审阅**：把代码当"语言"读，做跨函数、跨文件推理——"这条路径上分配失败提前返回了，上游的锁解了吗？buffer free 了吗？"

这次 948 个漏洞的产出流程大致三步：

1. AI 扫全库，输出疑似问题清单
2. 人工（内核维护者）逐条验证、定级
3. 确认的写成 patch，走正常 upstream 流程合入

注意第二步：AI 只负责提名，定罪的还是人。再算笔账：120 万美元 ÷ 948 ≈ 每个漏洞约 1300 美元，且大头是 GPU 算力，边际成本还会随模型迭代继续降。对比人工审计和漏洞市场的报价，这是数量级的差距。

## 三、不是孤例：两年时间线看 AI 挖洞的工程化

- **2024 年底**：Google Project Zero 的 Big Sleep agent 首次用 LLM 挖到真实开源软件（SQLite）的 0-day，当时还被当作"炫技样本"
- **2025 年**：Big Sleep 又在 Linux 内核里找到真实的内存安全漏洞；同年的 DARPA AIxCC 决赛上，多支 AI 系统自动挖出并修复了真实开源项目中的漏洞
- **2025 年底**：OpenAI × Linux 基金会这次，规模直接上到"全内核扫描、948 个漏洞"

两年时间，AI 挖洞从实验室演示变成了可以工程化采购的能力。当然社区也有争论：有人指出其中不少属于低危或理论性问题，传统工具这些年也一直在持续产出；AI 的独特增量在于把"跨函数语义类漏洞"这个长尾也扫了出来。这些声音并存，但不影响大方向。

## 四、120 万美元真正买到的：三个经济学信号

1. **挖洞的边际成本塌方**：过去挖内核高危漏洞是重人力活动，漏洞市场上五位数起步的报价很常见；现在接近"算力批发价"。攻防双方拿到的是同一把铲子
2. **竞争焦点转移**：胜负取决于谁先把"发现 → 验证 → 修复 → 分发"的循环跑完。防御方有个天然优势——这 948 个 patch 是公开发到 upstream 的，全行业共享
3. **新瓶颈暴露**：找洞便宜了，修和发没便宜。patch 要穿过几十个发行版、无数嵌入式设备；大量路由器和 IoT 设备出厂后永不再更新，漏洞"被发现"与"被修复"之间隔着数年

所以这次事件真正的信息量不是"AI 好强"，而是：**安全的瓶颈从挖洞搬到了分发**。

## 五、落到自己身上：三条可执行的动作

- **开发者**：把 AI 审查塞进 CI，当成新的 lint 层；重点让它盯错误处理分支、并发路径和资源释放；所有 AI 报告必须人工复核，否则你会先被误报淹没，产生"漏洞疲劳"
- **企业/团队**：建立 SBOM、盯上游 LTS 补丁节奏。你的真实风险 = 上游修复时间到你实际部署时间的差值，把这个差值量化出来，比多买一台扫描器有用得多
- **采购/评估**：问供应商三句话——内核版本多新？多久同步 upstream 安全 patch？有没有自动化回归验证？

## 冷思考：三条留给你

1. **挖洞变便宜 ≠ 更安全**。真正的护城河是"修复分发速度"——这条对内核社区成立，对你们自己的系统同样成立
2. **警惕同源盲区**。现在普遍是"AI 写代码 + AI 审代码"，同一代模型可能有同一类思维盲点。关键路径保留人工 review，并用 fuzzing、静态分析等异构工具交叉验证
3. **结构性解药仍是内存安全**。Rust 从 6.1 起进内核，冲的就是这一类问题。AI 是很好的止痛药，语言级安全才是根治手术

说到底，948 个洞不是 AI 的胜利，也不是人类的失败——它只是把一个老事实摆上台面：复杂系统的安全从来不是"一次审完"，而是持续追赶。这一次，终于出现了一个不知疲倦的追赶者。
