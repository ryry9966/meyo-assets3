## 背景

用 Agent 生成技术内容之后，真正耗时的不是写作，是发布。同一篇 Markdown 要发公众号、知乎、掘金和 RSS，各平台渲染器能力差异很大：有的支持 GFM 表格，有的只认内联样式的 HTML，有的把脚注语法原样吐出来。手工逐平台调整，一篇稿子轻松吃掉半小时。这篇帖子记录我把这条链路跑通的做法：一条规范化管线，加上一份平台能力矩阵，让 Agent 在发布前自动完成格式适配。

## 问题拆解

核心是三件事：

1. **源不干净**。LLM 输出的 Markdown 常带冗余嵌套列表、未闭合代码围栏、中英文间距不一致、随机的行内 HTML，直接喂给转换器只会放大问题。
2. **目标方言多**。公众号基本只接受内联样式 HTML；知乎会剥离大部分标签和 class；掘金接近标准 GFM；RSS 和静态站又是另一套。
3. **资源依赖**。图片外链有防盗链和失效风险，脚注、锚点等特性各平台表现不一。

## 做法

我把管线拆成五个幂等步骤，每步一个独立脚本，也可以注册成 MCP tool 让 Agent 按需调用：

1. **Normalize**：用 remark 加自定义规则清洗源文——展开深层嵌套、强制代码块闭合、统一中英文空格、把行内 HTML 抽出并标记为“降级候选”。
2. **Lint**：跑规则检查，输出一份 JSON 报告，列出将被丢弃或需转换的特性。Agent 拿到报告后决定改写内容还是接受降级。
3. **能力矩阵**：一个 YAML 配置，按平台声明每个特性的策略。例如公众号：`table: image`、`footnote: drop`；掘金：全部保留。这是整套方案里复用价值最高的部分。
4. **Transform**：按矩阵执行。表格转图用 headless 渲染截图；脚注降级为文末参考列表；公众号走 Markdown 到内联样式 HTML 的模板映射；图片统一走“下载 → 传图床 → 替换链接”。
5. **Render + 校验**：目标渲染器出预览，锚点做最后一遍校验，快照对比后交人工确认。

在 OpenClaw 里整条链路表现为一个 workflow：源文件进，按平台分目录出成品，附一份差异报告。

## 踩坑点

- **表格转图要控宽度**，默认渲染在手机上必然溢出，后来加了最大列宽和字号缩放才稳。
- **图床上传的幂等性**是重灾区，管线重跑会重复上传，改成按内容 hash 做本地缓存解决。
- **内联样式模板别手写**，手写 CSS 满屏 `!important`，最后是基于现成主题导出的样式做映射。
- **Lint 阶段改标题会破坏锚点**，目录链接全体失效，所以锚点校验必须放在最后一步。
- **降级策略要定优先级**。同一特性在矩阵里配了多个策略时，Agent 每次选择可能不同，产物不可复现——明确顺序后问题消失。

## 可复用建议

- 每步产物落盘（`normalize.md` / `lint.json` / `platform/*.html`），失败可单步重放，不用整条重跑。
- 能力矩阵单独进版本库，平台规则变化时改配置，不改代码。
- 给 Agent 的提示词里写死“只改格式，不改语义”，lint 报告是它的输入，不是让它自由发挥的依据。
- 快照测试兜底：渲染产物差异超阈值就告警，防止上游依赖悄悄变了没人知道。

## 总结

这条管线把“多平台发布”从手工劳动变成配置问题：一份干净的规范源、一份能力矩阵、五个幂等步骤。Agent 在其中的价值不是替代转换工具，而是读懂 lint 报告后在内容层面做取舍。代码量不大，难的是把矩阵维护和快照测试这两件枯燥的事坚持下去——而它们恰恰是产物可复现的底线。
