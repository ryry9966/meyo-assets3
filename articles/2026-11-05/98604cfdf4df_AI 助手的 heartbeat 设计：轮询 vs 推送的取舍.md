# 背景

做 Agent 自动化久了，基本都会撞上同一类需求：让助手定时巡检数据源、处理积压任务、或者在外部事件发生后自动行动。剥掉业务外壳，核心问题只有一个——**助手什么时候"醒来"**。

目前两条主流路线：轮询（定时心跳）和推送（事件驱动触发）。OpenClaw 里常见做法是 cron + heartbeat 插件 + MCP 工具的组合。两条路我都在生产里跑过一段时间，聊点真实的取舍。

# 问题

**轮询的坑**：间隔短了，token 烧得快，还容易撞 API 限流；间隔长了，响应滞后，时效性任务直接过期。更隐蔽的成本在心跳本身——如果每次 tick 都完整调用一次模型，哪怕无事发生，也在持续付费。

**推送的坑**：看似精准，但要求助手运行时可达。本地跑的 agent 进程通常没有公网入口，沙箱环境收 webhook 更麻烦。而且推送直接触发 LLM 调用，遇到事件风暴成本失控，重试机制还会造成重复执行。

# 做法：混合架构

我的方案是两者拼起来，核心原则：**推送只入队，心跳负责执行**。

1. **先分类任务**。时间驱动类（日报、巡检、备份）走心跳；事件驱动类（收到消息、文件变更、上游任务完成）走推送。
2. **心跳做轻**。每次 tick 只做三件事：读队列长度、扫标记文件或资源 mtime、判断是否升级为完整模型调用。无事则静默退出，不进模型。
3. **推送降级为入队器**。webhook 收到事件后写入 inbox（文件、SQLite、消息队列都行），带幂等键去重。真正的执行留给下一次心跳统一 drain。
4. **心跳跑独立会话**，输出不污染主对话历史；设超时，防止一次卡死的心跳阻塞主循环。
5. **每个 tick 记日志**：耗时、是否升级、队列水位。间隔调优靠数据，不靠感觉。

# 踩坑点

- 心跳消息写进主会话，几天后上下文被巡检记录塞满，主任务质量肉眼可见地下降。务必分离会话。
- webhook 重试没做幂等，服务重启时同一事件触发了两次完整任务。
- cron 用了 UTC，和本地时间差 8 小时，日报半夜发出去了。
- inbox 没设上限，一次事件风暴后 drain 十几个任务，token 直接翻倍。现在每个 tick 加了处理上限。

# 可复用建议

- 默认架构就用"**轮询心跳 + 收件箱**"，推送降级为入队器。这是最容易运维、成本最可控的形态。
- 心跳默认便宜，按需变贵。目标是 90% 的 tick 不调用模型。
- 间隔自适应：队列有积压自动缩短，连续空闲自动拉长。

# 总结

轮询和推送不是二选一。轮询解决**可达性**，推送解决**及时性**，用 inbox 把两者拼起来：推送负责把事件可靠送达，心跳负责在合适的时机廉价地醒来。先把心跳做便宜，再谈提速。
