## 背景

单个 Agent 跑长任务有两个老问题：一是 context 很快被工具输出撑满——grep 结果、大文件内容、日志片段全堆在主对话里，越往后越"失忆"；二是所有步骤串行执行，一个依赖多个独立子任务的活儿，明明可以同时做，却在排队。

OpenClaw 这类 Agent 框架普遍支持主 agent 派生 subagent：每个 subagent 拥有独立 context，干完活返回一份摘要，主 agent 负责汇总决策。机制不难，难的是怎么用得稳。

## 问题

举个我实际跑过的场景：让 Agent 排查一个中型仓库里所有废弃 API 的用法。主 agent 需要 grep 定位、逐个读十几处调用点、最后汇总成报告。串行跑到第五个文件，context 一半是中间产物；全部读完接近二十分钟。这种"扇出—汇总"结构的任务，正是 subagent 编排的主战场。

## 做法

1. **先判断任务形态**。只读、可切分、结果能压缩成摘要的，适合派发；需要全局状态或步骤间强依赖的，留在主 agent。
2. **主 agent 只当调度器**。为每个 subagent 写一份自包含的任务书：目标、涉及文件路径、约束条件、返回格式。不要指望子 agent"自己去了解背景"。
3. **控制并发**。2–3 个起步，跑稳后再提到 4–5 个。并发一高，API 限流和 MCP 工具的竞争会先找上门。
4. **写死返回格式**。要求子 agent 只回"文件路径 + 行号 + 结论"这类结构化摘要，明确禁止返回过程叙述。
5. **写入收口**。读操作可以并行，写操作要么收回主 agent 统一执行，要么按文件路径严格分区。

## 踩坑点

- **子 agent 返回太长**，主 context 照样爆。返回格式不约束，编排等于白做。
- **并行写同一文件**，后写的覆盖先写的，且很难发现。我吃过一次亏，之后强制读写分离。
- **任务书不自包含**，子 agent 凭猜测行事，返回结果看起来像模像样但不可信。
- **一次性开满并发**，限流报错加上排障成本，反而比串行慢。
- **单个子 agent 失败拖垮整批**。主 agent 要具备重试或降级逻辑，失败的那份任务单独补跑。

## 可复用建议

- 固化一份任务书模板：目标 / 范围 / 约束 / 返回格式 / 步数预算。五项缺一不可。
- 记住"只读并行、写入串行"这条底线，能避开大部分冲突。
- 每次编排把子 agent 的任务书和返回结果落日志，复盘和调试全靠它。
- 明确禁止子 agent 再派生子 agent，递归编排的排障成本远大于收益。
- 子 agent 的 prompt 是代码资产，值得进版本库维护，而不是每次现编。

## 总结

Subagent 编排的本质是两件事：**context 隔离**和**受控并行**。收益最大的场景是读多写少的扇出型任务——全库扫描、多文件审查、多数据源调研。不要追求"开得越多越好"，先把任务书写扎实、把返回格式约束住，再逐步放大并发。编排质量的上限，取决于你任务书的质量。
