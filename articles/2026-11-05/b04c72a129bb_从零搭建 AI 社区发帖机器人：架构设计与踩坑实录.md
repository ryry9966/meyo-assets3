## 背景

社区日常有一类重复劳动：定期从 GitHub issues、论坛热帖、RSS 订阅里筛素材，整理成精选帖或周报发出来。人做这件事又慢又容易漏。我试着用 OpenClaw 的 Agent + MCP 工具链搭了一个发帖机器人，跑了两周，稳定每天产出一条审核后的帖子。这篇记录架构和踩过的坑。

## 目标与约束

先定三条硬约束，后面所有设计都围绕它们：

1. **宁缺毋滥**：每天最多一条，草稿必须过人工审核才能发。
2. **幂等可重试**：任何一步失败重跑，不能产生重复内容。
3. **全程留痕**：素材、草稿、发布结果都可回溯。

## 架构：四层流水线

```
采集层 ──→ 生成层 ──→ 审核层 ──→ 发布层
(定时抓取)  (Agent起草)  (人工闸门)  (API发帖)
                        ↓
                    状态库(SQLite)
```

- **采集层**：cron 插件每天 09:00 触发，调用 MCP 工具抓 GitHub issues、RSS、论坛 API，落成结构化素材。
- **生成层**：Agent 读取素材 + 社区风格指南（few-shot 用了 10 篇历史优质帖），产出草稿和标签。
- **审核层**：草稿写入状态库，通过 webhook 推给管理员，approve 后进入发布队列。这是唯一的人工介入点。
- **发布层**：调用论坛发帖 API，记录返回的 `post_id`，回写状态库。

核心思路是**生成与发布解耦**：Agent 只负责起草，永远摸不到发布权限，审核闸门物理隔离。

## 实施步骤

1. 在 OpenClaw 里建 Agent，注册三个 MCP 工具：`fetch_sources`、`save_draft`、`publish_post`。
2. 整理社区风格 prompt：语气、禁用词、Markdown 规范，配上 few-shot 示例。
3. cron 插件定时触发采集 + 起草，产出待审草稿。
4. 审核通过后命令行触发发布，回写 `post_id`。

最小闭环先跑通「一个素材源 → 起草 → 审核 → 发布」，再横向加源。

## 踩坑实录

**1. 重复发帖。** 发布 API 超时后自动重试，结果同一天发了两条一样的帖子。根因是重试没有幂等键。修复：以「日期 + 素材内容 hash」作为 idempotency key，发布前先查状态库，命中即跳过。

**2. MCP 工具超时污染上下文。** GitHub 列表接口偶尔 30 秒以上，超时后 Agent 上下文里残留半个 JSON，后续生成质量明显下降。修复：fetch 工具内部自己做超时、截断、重试，超时返回结构化错误对象而不是抛异常，让 Agent 拿到的是干净的可判断信号。

**3. Markdown 渲染炸了。** Agent 生成的草稿混入了 HTML 标签，论坛端渲染错乱。修复：发布前加一层 sanitizer，只放行白名单标签；同时在 prompt 里明确「仅使用纯 Markdown 语法」。

**4. 内容幻觉。** Agent 有一次给不存在的 issue 编了编号。修复是双保险：要求所有引用附原始 URL，发布前脚本校验 URL 可达性，不可达直接打回。

**5. 触发频控。** 重试撞上论坛 API 的 429。修复：指数退避 + 队列串行发布，一天一条的量级下完全够用。

## 可复用建议

- 所有外部调用统一包一层：超时、重试、结构化错误返回，别让原始异常进 Agent 上下文。
- 状态库哪怕一个 SQLite 文件也行，千万别放内存——进程重启等于失忆。
- 约束要「prompt 硬规则 + 事后校验」双保险，只靠 prompt 一定会漏。
- 先把最小闭环压稳，再扩素材源；一次加三个源，出问题分不清是谁的锅。

## 总结

发帖机器人技术上并不复杂，难在「不丢人」：不重发、不乱发、不编造。审核闸门、幂等键、全程留痕，是自动化内容输出的三条底线。相关代码和配置已整理进社区仓库，欢迎提 PR 一起完善。
