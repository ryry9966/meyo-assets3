## 背景

Agent 能干的事越来越多：读写文件、执行命令、调 MCP 工具、发消息、碰生产环境。权限边界的问题也随之从"要不要给权限"变成了"给到哪一层"。这道线画得好，agent 是可靠的自动化工具；画不好，要么是逐句请示的陪跑，要么是没人看管的定时炸弹。

## 问题

实践中通常会滑向两个极端：

- **什么都问**：每一步都等人确认，人成了流水线上的审批机器，最后条件反射地点"同意"，自动化名存实亡。
- **什么都不问**：agent 自主执行 `git push --force`、删数据、往外部渠道发消息、一晚上烧掉几百块 API 额度，出事之后才发现根本没有闸门。

核心矛盾在于：问得太多，人会疲劳；问得太少，错误不可逆。这需要一套可工程化的分级规则，而不是在 system prompt 里写一句"请谨慎操作"。

## 做法：按"可逆性 × 影响半径"分级

不要按工具名分级，要按操作的**实际后果**分四档：

| 档位 | 特征 | 策略 |
|---|---|---|
| Tier 0 | 只读、沙箱内 | 自动执行 |
| Tier 1 | 可逆、不出工作区 | 自动执行 + 记日志 |
| Tier 2 | 不可逆或出边界 | 必须问人 |
| Tier 3 | 破坏性/公开性 | 默认拒绝，人来做 |

读文件、grep、查 API 归 Tier 0；有 git 兜底的文件编辑、跑测试归 Tier 1；对外发邮件、删数据、花钱、push 到共享分支归 Tier 2；`rm -rf`、生产变更、对外发布归 Tier 3。

落地三步：

1. **工具层设闸。** 在 MCP server / gateway 配置里给每个工具标注风险级，写操作默认 Tier 2，逐个评估后降级。命令用 allowlist 管理，路径锁在 OpenClaw 的 workspace 内，凭证目录显式 deny。示意：

```yaml
tools:
  fs.read:     { tier: 0 }
  fs.write:    { tier: 1, scope: "~/workspace/**" }
  shell:       { tier: 1, allow: [ls, cat, grep, pytest], ask: [git push, rm, curl] }
  mail.send:   { tier: 2 }
  prod.deploy: { tier: 3, human_only: true }
```

2. **确认消息带上下文。** 问人时必须给出完整命令或 diff、影响对象、原因。"可以执行吗？"和"我要把 main 重置到 origin/main，丢弃 3 个本地提交，确认？"是两回事。前者只会训练人无脑点同意。

3. **全量审计日志。** 自动放行的操作也要记录，每周回看一次，据此调整分级——这是唯一客观的校准依据，别靠感觉。

## 踩坑点

- **确认疲劳**：ask 次数失控后，人会比机器先失控。控制 ask 频率，提高单次 ask 的信息量。
- **只在 prompt 里约束**：模型对风险的自我评估不可靠，边界必须编码在工具和配置层，prompt 只是补充。
- **按工具名而非效果拦截**：agent 可以不直接跑 `rm`，但可以跑一个会删文件的脚本。要拦的是效果，不是工具名。
- **批准被复用**：一次批准不等于永久授权。授权范围应限定在单个动作，跨会话重置。
- **无人值守任务**：定时任务和后台 agent 执行时没有人在回路里，边界要比交互模式更严，或者只允许 Tier 0/1。

## 可复用建议

- 分级配置进版本库，像 review 代码一样 review 权限变更。
- 新接入的工具默认 deny，观察一段时间再放行。
- 一句话判断法：**可逆且不出圈 → 自己干；不可逆或出圈 → 问人；拿不准 → 问人。**"拿不准就问"要写进默认行为，而不是留给模型现场发挥。
- 从严格开始、根据日志逐步放宽，永远不要反过来。

## 总结

权限边界不是 prompt 问题，是架构问题。把分级规则做进工具层，用审计日志持续校准，让"问人"变成低频但高信息量的动作——agent 才能做到该干就干，该停就停，而你晚上能睡得着。
