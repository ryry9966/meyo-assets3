## 背景

OpenClaw 的 agent 有一个容易被低估的机制：heartbeat。默认按固定间隔醒来，读一遍 `HEARTBEAT.md`，判断有没有事做，没事就静默返回。不少刚上手的人（包括我）第一反应是"这不就是轮询吗，太原始了，改成 webhook 推送不香吗"。

折腾了两周、重构过一版纯事件驱动方案之后，我的结论是：轮询不是没设计，而是刻意保守。它和推送各自覆盖一类任务，真正的问题是你的自动化任务属于哪一类。

## 问题

把任务拆开看，基本是三种形态：

1. **周期巡检**：每小时查日志、每天整理待办。天然适合轮询，推送反而没有"事件源"。
2. **外部事件驱动**：CI 失败、新邮件、监控告警。事件发生时间与 agent 无关，靠轮询等就是浪费。
3. **条件触发但无事件源**："数据波动超过阈值就提醒我"。能推送的是被监控系统，不能推送的就只剩轮询。

纯轮询的代价很直白：**延迟**（最坏一个周期）和**空转成本**（每次醒来都烧一次 token）。纯推送的代价更隐蔽，见踩坑部分。

## 我的做法

**第一步：任务分类，别在机制上争输赢。** 我把 `HEARTBEAT.md` 里的条目全部打标签：`routine`（可容忍延迟）、`event`（必须推送）、`hybrid`。只有 `event` 类才值得为它建推送通道。

**第二步：轮询分级。** 不再全局一个 interval。routine 类降到低频心跳（如 6 小时一次），需要更快反馈的改成 hybrid：15 分钟轮询 + 关键事件另配 webhook。心跳提示词里写死一条规则："无事可做时只回复确认，禁止向任何渠道发消息。"这一条杜绝了 agent 深夜在群里汇报"一切正常"。

**第三步：推送走统一入口。** 外部系统（CI、监控、脚本）不直接操作会话，而是打到一个自建的 webhook 收集器插件，校验签名、去重、限流后，再以工具调用注入 agent。入口统一的好处是：新增事件源不用改 agent 配置。

**第四步：轮询兜底。** 每条推送通道旁边保留一个低频对账轮询（每天一次），核对事件是否丢失。推送是提速，轮询是保底，二者不互斥。

## 踩坑点

- **空转刷屏**：最初规则写得含糊（"看看有什么能帮忙的"），agent 每次心跳都往渠道发消息。沉默条件必须显式写明。
- **webhook 并发竞态**：三条告警同时到达，agent 被并发唤醒，写同一个会话文件差点互相覆盖。现在收集器强制串行排队。
- **重复执行**：上游重试导致同一事件触发两次定时任务。加了幂等键（事件 ID + 时间窗去重）才解决。
- **interval 拍脑袋**：5 分钟心跳一天烧掉的 token 远超预期，且绝大多数是"无事发生"。先算账，再定频率。

## 可复用建议

- 决策口诀：**有事件源用推送，没事件源用轮询，两者都有用混合**。
- 推送入口必做三件事：鉴权、幂等去重、串行化（或显式并发控制）。
- 心跳提示词要可"沉默"：无事时不产出任何面向用户的内容。
- 心跳频率按任务 SLA 反推，不要为了"感觉快"设小值。

## 总结

轮询 vs 推送不是新旧之争，而是成本模型之争：轮询用可预测的成本换简单和可靠，推送用额外的基础设施换低延迟。OpenClaw 的 heartbeat 给了你轮询的底座，推送则需要自己搭一层入口。我的最终形态是"低频轮询保底 + webhook 收集器提速"：上线一个月，token 消耗降了一半以上，告警延迟从最坏 30 分钟降到秒级。先给任务分类，再选机制，比急着推翻默认设计划算得多。
