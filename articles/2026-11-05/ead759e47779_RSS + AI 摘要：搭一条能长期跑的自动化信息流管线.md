## 背景

订阅源多了之后，人工筛不动是迟早的事。RSS 至今仍是最干净的分发协议：结构化、无算法干预、可自托管，问题是量大、质量参差。LLM 出现后，“先聚合、再摘要、按相关性分发”这件事终于有了合理的成本结构。这篇文章记录我用 OpenClaw 搭的一条管线：定时抓取 → 清洗去重 → Agent 摘要打分 → 日报推送，全部跑在自己机器上，稳定运行一个多月。

## 问题

原始需求很朴素：

- 订阅 40+ 个源，日均新增几百条，逐条读不现实；
- 部分源只给摘要不给全文，部分源全文里塞满 HTML 噪音；
- 需要分级：重要的推到 IM，一般的进本地归档；
- 成本可控，不能每天把全部条目无脑塞给模型。

## 做法

整体分四层，层与层之间靠文件和 SQLite 衔接，互相不感知：

1. **采集层**：crontab 定时跑脚本，逐源拉取 RSS；没有源的站点先用 RSSHub 转一层。原始 XML 落盘，方便出问题时重放。
2. **清洗层**：解析出 title / link / guid / published，按 guid + 规范化 link 的哈希去重，已见条目记入 SQLite。同时剥 HTML、做可读性提取、截断到合理长度。这层完全不碰模型。
3. **摘要层**：用 OpenClaw 的 cron 任务定时拉起 agent 会话，每批 10–20 条、按源分组喂入，要求输出结构化 JSON：一行摘要、三个要点、相关性分数（0–10）、标签。低于阈值直接归档，高于阈值进待推送池。采集和清洗也可以包成一个 MCP tool 由 agent 按需调用，顺便能被其他客户端复用。
4. **分发层**：把待推送池合成一份 Markdown 日报，经 IM 通道发出，同时写入本地 notes 目录，供 agent 后续检索。

Prompt 上两条硬约束：内容不足以判断时必须返回 `insufficient_content`，禁止编造；输出必须能被 json 解析，失败重试一次。

## 踩坑点

- **guid 不可信**：有源每次刷新都换 guid，去重直接失效。改成 link 规范化 + 标题相似度兜底，重复率才降下来。
- **截断摘要诱发幻觉**：只喂摘要让模型总结，它会脑补细节。解法是允许“信息不足”输出——宁可少一条，不要错的。
- **HTML 污染上下文**：某些源全文内嵌大量标签和实体，过一遍可读性提取后，token 消耗降了约一半。
- **日期与时区**：RFC822 格式五花八门，按天聚合时踩过时区坑，统一转 UTC 再处理。
- **静默失败**：cron 跑挂了没人知道。给分发层加了心跳，连续两轮无产出就告警——这条比管线本身还重要。

## 可复用建议

- 采集与摘要解耦，状态全放外部存储，agent 保持无状态，任何一步失败都可重跑；
- 结构化输出是下游一切自动化的前提，别让日报格式依赖解析自然语言；
- 相关性打分 + 推送/归档双通道，体验远好于单一信息流，阈值先粗后调；
- 源列表做成配置文件，增删源不碰代码；新源先观察几天噪音水平，再放开推送；
- 记录每轮 token 消耗，成本异常往往先于质量异常出现。

## 总结

管线跑了一个多月，日均处理几百条，实际推给我的不到 20 条，阅读负担明显下降。核心体会：AI 摘要只是管线中的一环，采集的稳定性、去重的准确性和失败告警才决定它能不能长期活着。OpenClaw 在这里的角色，是把调度、agent 调用和工具接入收拢到同一个运行时里，让每一层都能独立替换和测试——这才是“自动化”能持续下去的前提。
