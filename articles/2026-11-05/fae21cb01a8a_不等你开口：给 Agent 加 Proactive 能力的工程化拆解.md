# 背景

绝大多数 Agent 的交互模型是"你问我答"：用户发消息 → 模型处理 → 返回结果。跑了一段时间 MCP 和自动化任务之后会发现，真正有价值的场景往往不在这个循环里——磁盘快满了、CI 连续失败、某个数据源昨天就断了更新。这些问题不需要你提问才存在，但当前架构决定了它们只能等你撞上。

Proactive（主动式）能力，本质上是把 Agent 从"被调用的函数"变成"常驻的服务"：它有自己的触发器、自己的判断门槛、自己的输出通道。

# 问题

做主动式 Agent，核心难点不在模型，而在三个工程问题：

1. **什么时候开口？** 触发太频繁就是骚扰，太保守等于没做。
2. **用什么判断？** 不能每次心跳都调一次大模型，成本和延迟都扛不住。
3. **怎么输出？** push、摘要、静默记录混在一起，用户两周内就会关掉通知。

# 做法

我们在实践中拆成了四层，可以直接套用：

**1. 触发层。** 三类来源足够起步：cron 定时任务、文件/数据变更监听、webhook 事件。MCP 侧如果 server 支持 `resources/subscribe` 或类似通知机制，优先用现成的，别自己造轮子。

**2. 感知与判断分离。** 触发后先跑一段廉价逻辑（规则或小模型）做"值不值得打断用户"的评分，分数过了才进入主模型的完整推理。这一步是成本控制的核心。

**3. 输出分通道。**
- Push：只留给高置信度、有时效性的事件（比如服务挂了）；
- Digest：低优先级信息攒着，每天固定时间合并成一份摘要；
- Journal：所有判断过程写入本地日志，用户想查随时能看。

**4. 幂等与状态。** 每个主动任务带一个去重 key，执行前先查"这件事我是不是已经说过了"。定时任务失败重试时尤其重要。

# 踩坑点

- **心跳直接调大模型**：一个每 5 分钟跑一次的 watcher，一晚上烧掉的 token 比白天所有对话都多。门槛判断必须是规则或小模型。
- **重复触发**：cron 超时后重试，同一条告警推送了三遍。去重 key + 状态存储（哪怕是个 SQLite 表）必须从第一天就有。
- **过期上下文**：主动任务常拿着上次会话的快照就动手，应该先重新读取最新状态再决策。
- **通知疲劳**：日均主动消息超过 2 条，用户就会静音整个通道。拿不准就攒进 digest。
- **后台执行危险操作**：proactive 模式下没人确认，写操作、删除、对外请求必须仍然走确认流程，或者一开始就只做只读任务。

# 可复用建议

1. 架构上记住三段式：**sense**（常驻、廉价）→ **think**（昂贵、有门槛）→ **act**（有权限边界）。
2. 每个主动任务出厂自带两样东西：静音开关和审计日志。
3. 冷启动只做只读主动任务（摘要、提醒、巡检报告），用几周积累信任后再放开写操作。
4. 把每次触发和判断落成结构化记录，阈值不是拍脑袋定的，是拿数据调出来的。

# 总结

Proactive 能力 = 触发基础设施 + 打断策略 + 通道纪律。模型在这里反而是最不重要的部分，管道和策略才是工作量所在。建议从一个"每天早上自动汇总昨日异常"的最小场景跑起，两周内就能验证你的门槛和通道设计是否成立。
