## 背景

在 OpenClaw 这类 agent 环境里，“同一个任务被执行两次以上”几乎是常态，而不是异常：

- 定时任务超时后触发器重试；
- MCP 工具调用遇到网络抖动，agent 重新发起请求；
- 用户没看到反馈，手动点了“再跑一次”；
- webhook 上游重复投递。

写自动化时如果默认“只会跑一次”，这些问题迟早会找上门。

## 问题

几个我实际踩过的场景：

- 定时摘要任务重试后，群里推送了两条一模一样的消息；
- “帮我建一个 issue”在重试后，开出了两个内容相同的 issue；
- 追加写日志的脚本，重跑后同一行出现了三遍。

根因都一样：操作被写成了“每执行一次就追加一次结果”的形式。只要执行次数不可控，结果就不可控。

## 做法

**1. 优先改写成天然幂等的形式。** 读操作、按固定 key 覆盖写（类似 PUT）、“把状态设为 X”都是天然幂等的。尽量把任务从“做一件事”改写成“让世界达到某个状态”：不是“发一条消息”，而是“确保今天的摘要已发送”。

**2. 改不了的，加幂等键。** 键必须跨重试稳定：用 `任务ID + 业务窗口`（如当天日期），或任务定义内容的 hash。千万不要用 `uuid4()` 或 `now()`——重试时键变了，去重等于没做。

**3. 执行前查、执行后记。** SQLite 一张表就够：

```python
key = f"digest:{chat_id}:{today}"
if store.seen(key):
    return  # 已执行过，跳过
do_work()
store.mark(key, ttl="48h")
```

**4. 外部副作用单独封一层。** 发消息、调第三方 API 这类动作不可回滚，把去重下沉到“动作层”，封装成 `ensure_send(...)`、`ensure_issue(...)`，任务层随便重试。

## 踩坑点

- **check-then-act 竞态**：两个实例同时查表都没命中，然后都执行。查和写必须原子（唯一索引 + `INSERT OR IGNORE`），或对 key 加锁。
- **键的来源错了**：agent 两次执行的输出可能不同，拿原始 prompt 做 hash 会得到两个不同的键。键要锚定在任务定义层面，不要锚定在 LLM 输出层面。
- **TTL 与重试时长不匹配**：设 10 分钟，结果 20 分钟后的重试照样重复；设太长，本该每天跑的任务被误判为重复。窗口要覆盖最大重试周期。
- **外部系统幂等能力不一致**：有些 API 原生支持 Idempotency-Key 之类的 header，优先用它，比自己维护状态可靠。

## 可复用建议

- 写每个任务前问一句：**“这个任务连跑三遍，最终状态和跑一遍一样吗？”** 答不上来就是没设计好。
- 动词升级：把“发送 / 创建 / 追加”改成“确保 / 同步 / 覆盖”。
- 去重逻辑统一成一个公共模块，别每个脚本各造一套轮子。
- 保留执行日志：`task_id + run_id + 幂等键`，出问题时能回放和审计。

## 总结

幂等性不是什么高级技巧，而是自动化的底线设计。重试、重复触发、人工重跑在 agent 系统里无法避免，与其祈祷它们不发生，不如默认它们一定会发生。把“只执行一次”的假设换成“执行多次结果不变”，你的自动化才敢真正放着手跑。
