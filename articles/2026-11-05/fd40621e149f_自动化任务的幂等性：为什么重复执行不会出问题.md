## 背景

写自动化的人迟早会撞上同一类事故：cron 任务被调度器重试跑了两次；webhook 被上游重复投递；Agent 调用 MCP 工具时超时，框架自动重试，结果工单系统里出现两条一模一样的记录。这些事故的共同点是：任务本身没有 bug，只是被重复执行了。

在真实环境里，"至少一次投递"（at-least-once）是常态——重试、断点续跑、事件重复分发，都是可靠性的代价。所以问题从来不是"会不会重复执行"，而是"重复执行了会不会出事"。

## 问题所在

把操作按副作用分成两类，问题就清楚了：

- **天然幂等**：设置某个值、按 ID 覆盖写入、按 ID 删除、UPSERT。执行一次和执行一百次，最终状态一样。
- **非幂等**：追加写入（append）、无主键的 create、计数器自增、发消息。多执行一次，状态就多偏一点。

非幂等操作叠加不可控的重复触发，就是深夜告警的典型来源。而且这类 bug 在开发环境很难暴露——你手动跑一遍，永远是干净的。

## 怎么做

1. **先分类，再动手。** 写任何自动化步骤前，先判断它属于哪一类。非幂等的操作要么改写成幂等形式（append 改 replace，create 改 upsert），要么加防护。
2. **定义稳定的幂等键。** 键必须来自业务上下文，比如 `source_id + 日期 + 动作名`，而不是每次生成的随机 UUID。同一件事无论重试多少次，键不变。
3. **让存储层兜底，而不是靠"先查再写"。** 给幂等键加唯一约束，用 `INSERT ... ON CONFLICT DO NOTHING` 或 UPSERT。数据库的原子性比应用层的 if 判断可靠得多。
4. **外部副作用单独处理。** 发通知、建工单这类落不到数据库约束的操作，维护一张执行记录表：执行前先查键，键存在就跳过；对支持的服务（工单 API、支付网关等）尽量传上客户端生成的请求 ID。
5. **重试时复用同一个键。** 这是最容易被忽略的一步——如果重试逻辑里重新生成 ID，前面的功夫全白费。

## 踩坑点

- 幂等键里混了时间戳或随机数，每次重试键都变，等于没做幂等。
- "先查后写"有并发窗口：两个 worker 同时检查、同时通过、同时创建。查询只能用于快速跳过，真正的保证必须靠唯一约束。
- 超时 ≠ 失败。第一次调用可能已经成功，只是响应没回来。重试前先查远端状态，别盲目再执行一次。
- 多步流程只记整体状态、不记分步状态，断点重跑时前几步会被重复执行。
- "已执行"标记只存在内存里，进程一重启，它就忘了自己干过什么。

## 可复用的建议

- 给 Agent / MCP 设计工具接口时，把幂等做成默认语义：写操作一律 upsert，幂等键作为工具契约里的必填参数，而不是可选项。
- 能 replace 就别 append，能整写就别增量。
- 给每个自动化任务写一个"跑两遍"的回归用例：连续执行两次，断言结果和执行一次完全相同。这比任何 code review 都有效。
- 放弃对"恰好一次"（exactly-once）投递的执念，把消费端设计成幂等，比追求投递端的完美更务实。

## 总结

重复执行不是异常路径，而是自动化的默认环境。幂等性不是锦上添花的优化，而是你敢开重试、敢做无人值守、敢让 Agent 自主调用工具的前提。下次写自动化任务时，先问自己一句：这段逻辑连续跑十遍，结果会不会和跑一遍不一样？
