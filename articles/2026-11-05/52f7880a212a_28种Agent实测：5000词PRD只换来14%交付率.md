最近开发者圈流传一份相当扎心的实测成绩单：一份约 5000 词的 PRD（产品需求文档），28 种不同的 Agent 组合轮番上阵——单次直出、任务清单循环、planner/executor 编排、多智能体协作、自我反思重试，基本把社区主流玩法试了个遍，成绩最好的配置也只交付了约 14% 的需求，主角还是编程能力第一梯队的 Claude。“一句话做出一个产品”的叙事被泼了冷水？先别急着下结论，这份成绩单的信息量比结论本身大得多。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-05/2a4d0fc1deea9a04.png)

## 实验怎么做的：拿规格说明书当考卷

- **考卷够硬**：不是“做个 Todo 应用”这种一句话需求，而是一份数据模型、权限体系、边界条件、异常处理俱全的完整 PRD，信息密度接近真实产品的立项文档。
- **选手够全**：28 种组合覆盖了不同提示词策略、不同任务拆解方式、单 Agent 与多 Agent 分工、有无自我检查与重试循环等变量，堪称一次“编排全家桶”横评。
- **评分够严**：逐条对照 PRD 计算需求覆盖率，结果中位数低得感人，最高约 14%。
- **失败模式最有意思**：产物往往“看起来像个应用”——界面能点、主流程能跑，但大量白纸黑字写明的需求被静默丢弃。注意，是“没做”，不是“做错了”：逐条核对时，缺失远多于错误。

这种“静默漏需求”是典型的长上下文 + 长任务病征，不是某个环节的偶发 bug。下面拆原因。

## 为什么只有 14%：一条长任务的衰减链

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-05/940442c1437c82ac.png)

1. **上下文窗口 ≠ 有效注意力**。200K token 的窗口不代表模型对每个 token 一视同仁。"Lost in the Middle" 系列研究早已指出，模型对长文本中段和尾部的注意力密度明显下降——藏在 PRD 第 37 页的那条边界条件，大概率被悄悄跳过，而且遗漏是系统性的，不是随机的。
2. **误差按复利结算**。假设单步子任务成功率 95%，连续 50 步就是 0.95⁵⁰ ≈ 7.7%。Agent 的交付是几百个小决策的串联：读需求、定架构、写模块、连接口，单步都挺准，链起来就崩。这和传统工程里“每个环节 99% 可靠、系统整体照样不可靠”是同一道数学题。
3. **PRD 天然带歧义**。人类工程师接到含糊需求会找 PM 对齐、会反问、会用团队惯例填补空白；Agent 通常选择自行脑补，且脑补方向无人校准。5000 词文档里的歧义点散落各处，每处都是一个分叉路口，走错一条，后面一串需求跟着塌。
4. **验证闭环缺失**。没有可执行的验收测试，Agent 就没有反馈信号，错了不知道错，更谈不上回头修。编程任务的上限很大程度由可验证性决定——这也是为什么模型做 LeetCode 类题目远好于开放性工程。
5. **多 Agent 有协调税**。planner 和 executor 之间传话会丢信息，状态会不一致，工作会重复。这次实测里，不少“高级编排”的表现并不比一个朴素循环好多少——分工的收益，常常被协调的成本吃掉。

## 28 种组合给出的共同答案：花活救不了基本功

把 28 份成绩放在一起看，规律相当一致：

- 提示词优化、任务清单、自我反思，带来的是个位数百分比的改善，边际收益递减得很快。
- 多智能体框架的平均表现不占优，某些组合反而更差——更多角色 ≠ 更多产出，还会放大上下文碎片化。
- 真正拉开差距的变量只有两个：**任务切分粒度**和**反馈信号强度**。能把大需求切成小块、每块带明确验收条件的配置，成绩明显更好。

打个比方：给同一位初级工程师配 28 种项目管理方法论，交付率不会有本质变化——瓶颈从来不在“管理花活”，在“干活的人 + 验收机制”。这也和 METR 的研究相互印证：AI 能稳定完成的任务时长（time horizon）大约每 7 个月翻一倍，目前处在“人类数小时级任务”的区间；而一份 5000 词 PRD 对应的是人类数周到数月的工程量，确实超纲了。

## 14% 的正确读法：体检报告，不是判决书

- **它不说明 AI 编程没用**。在边界清晰的小任务上——写函数、补测试、做 CRUD、迁移老代码——生产力提升是真实且被大量团队反复验证的。
- **它说明委托粒度选错了**。“从 PRD 交付一个产品”是巨型任务，“实现这个接口并通过这组测试”是可解任务。人对 AI 的失望，多半来自把后者当前者用。
- **也要承认评分的严格性**。如果按“逐条字面满足需求”计分，让人类工程师只读一遍 PRD 就盲写，得分同样难看——人类的真实流程是几周的反问、评审与迭代。AI 与人的差距不在单点智商，而在**主动对齐**和**长程迭代**这两个人类习以为常、Agent 还很陌生的机制。

所以这个 14% 不是“AI 不行”的判决书，而是一张精确的体检报告：病灶在长程规划、上下文管理和验证闭环，不在代码风格。

## 收尾三条：把失望换成方法论

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-05/a95090f557893e4c.png)

1. **切，而不是喂**。别把 5000 词 PRD 整个扔给 Agent。按“可验收单元”切片，每个切片配一组测试，人只在切片边界做 review。合理的分工是：人做架构、切分和验收，AI 做切片内的实现。
2. **先建反馈，再谈编排**。在引入任何多 Agent 框架之前，先补齐测试、类型检查和 lint。Agent 的表现上限，基本由“错误多快被发现”决定——可验证性比提示词技巧值钱得多。
3. **把 Agent 当新同事，别当许愿机**。新同事需要 onboarding 文档、明确的边界和参考示例，Agent 一样。单次会话给窄范围、给足上下文，默认假设它会漏需求，用逐条核对兜底——这不是不信任，这是工程。

一句话总结：14% 量出的是当前 Agent 与“独立交付”之间的真实距离，而缩短这段距离的杠杆，一半在模型侧；另一半，其实一直在我们自己的工程实践里。
