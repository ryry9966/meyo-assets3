## 背景

大多数 AI 助手是纯被动的：你发消息，它应答，会话之外什么都不发生。Proactive 能力指另一类行为——agent 自带触发器，条件满足时先出手：CI 挂了先拉日志给摘要，日历上半小时后有会先整理材料，监控越界先做一轮初判。在 OpenClaw 生态里零件其实都齐了：cron/心跳触发、MCP 事件源、插件动作通道，缺的只是把它们串起来的架构。

## 问题：难点不在"能动"，在"何时动"

定时唤醒 agent 并不难，真正要解的是三件事：

1. **触发后该不该说话？** 每次心跳都汇报等于通知轰炸，三天后你就会把 bot 静音。
2. **成本谁付？** 每分钟一次 LLM 调用的心跳，跑一周 token 账单不好看。
3. **权限边界在哪？** 主动执行写操作，判断错一次就是事故。

## 做法：三层结构

我把自己跑通的配置收敛成三层，可以直接照搬。

**第一层：触发器。** cron 低频心跳做兜底（比如每 30 分钟一次巡检）；确定性事件走 MCP server 或插件订阅——文件变更、CI webhook、监控告警。原则：能用确定性事件，就不用 LLM 去轮询判断。

**第二层：分诊。** 事件先过代码规则：关键词、阈值、去重（同一告警 10 分钟内只进一次）。规则判不了的才丢给便宜模型做三级分类：

```yaml
triage:
  L0_silent:    # 只写事件日志，不打扰
  L1_digest:    # 攒着，随下次心跳打包推送
  L2_interrupt: # 立刻推送，附建议动作
```

关键点：频率和成本护栏写在代码里，prompt 只负责语义理解。全塞进 prompt，模型输出一波动，推送频率就失控。

**第三层：动作与权限。** 只读动作（拉日志、生成摘要）全自动；写操作走白名单 + 影子模式——先推"我打算执行 X"，确认后才真跑。每次主动行为落一条结构化日志，方便复盘它到底该不该动。

一个实际例子：CI 失败接 webhook → 规则匹配 "failed" → agent 拉失败日志生成摘要 → L2 推送。从"挂了"到"看到带原因的通知"，间隔从十几分钟缩到一分钟内，而且全程不用我盯着。

## 踩坑点

- **通知疲劳是第一堵墙。** 早期我把 L1 也做成实时推，一天二十多条，第三天就被静音。改成摘要打包后，消息留存率才回来。
- **心跳污染主会话。** 巡检的中间输出别写进主上下文，用独立 session 跑，只把结论注入。
- **cron 时区与重复触发。** 容器重启后 cron 重挂，同一巡检跑了两份。加个去抖锁解决。
- **LLM 分诊不稳定。** 同一条告警这次 L0 下次 L2。后来把"是否打断"改成硬规则（来源+级别决定），模型只负责写摘要，立刻稳定。
- **权限漂移。** agent 某次"顺手"清了构建缓存，没出事但吓人。写操作白名单必须显式枚举，不给"类似操作也行"的自由度。

## 可复用建议

1. 从一个高价值场景切入（CI 失败 / 日历 / 监控三选一），闭环跑通再横向加事件源。
2. 三级响应（静默/摘要/打断）是通用骨架，L2 打断控制在每天个位数。
3. 让用户行为参与调参：某类推送被静音就自动降级到 L1，比在 prompt 里求模型"别太吵"有效得多。
4. 成本护栏放代码里：心跳频率、分诊模型每日调用上限、单事件 token 预算。
5. 把 proactive 行为当生产变更管理：有日志、可回滚、可审计。

## 总结

Proactive 不是 prompt 问题，是架构问题：触发器解决"何时醒"，分诊解决"说多少"，权限解决"敢不敢做"。OpenClaw 生态里零件都是现成的，真正的工作量在于给主动性装上刹车和仪表盘——先让它做对一小件事，再谈做得更多。
