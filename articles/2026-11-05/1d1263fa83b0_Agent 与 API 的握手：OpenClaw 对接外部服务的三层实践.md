## 背景

Agent 的价值不在会聊，而在能动手。在 OpenClaw 这类框架里，模型负责决策，真正干活的是背后的工具层：调 HTTP 接口、查数据、触发自动化。对接外部服务是每个实践者迟早要过的一关，也是翻车最集中的一关。

## 问题：直接把 API 塞给 Agent 会怎样

最朴素的做法是把 curl 命令或 OpenAPI 文档原样丢进工具描述，让 Agent 自己“看着办”。跑起来通常出现三类问题：

1. **参数幻觉**。模型会自信地编造可选字段，尤其是分页、时间格式这类约定不显式的地方。
2. **失败不可控**。超时、限流、鉴权过期没有统一处理，一次 429 就能把整个推理循环卡死。
3. **状态污染**。写操作没有幂等保护，重试一次就产生两条订单、两条通知。

根源在于：Agent 与 API 之间缺少一层“握手协议”——明确谁能调、怎么调、失败了怎么办。

## 做法：三层握手

以 OpenClaw 的插件 / MCP 机制为例，建议按三层组织：

**第一层：契约层。** 不透传原始 OpenAPI 文档，而是手写精简的工具 schema。每个工具只暴露 Agent 真正需要的字段，required 列表宁严勿松。用 Pydantic / Zod 在入口做强校验，非法参数直接拒绝并返回结构化错误，让模型下一轮自我修正。

**第二层：通道层。** 鉴权、重试、超时、限流全部收在这一层，Agent 永远不直接碰原始 HTTP 客户端。超时建议 10–15 秒即熔断；429 / 5xx 用指数退避，最多重试 2 次；写操作强制携带幂等键（可由任务 ID 派生 UUID）。

**第三层：观测层。** 每次工具调用记录：工具名、脱敏后参数、上游状态码、耗时、trace ID。没有这层，线上排障基本靠猜。

如果外部服务已有现成的 MCP server，优先复用；自定义逻辑放在 MCP 之外的包装插件里，避免 fork 后长期维护的负担。

## 踩坑点

- **Schema 与实际行为漂移**。上游悄悄改了字段，Agent 会按旧理解硬填参数。契约层校验要放在入口而非出口，才能第一时间拦住。
- **Secrets 进日志**。观测层不脱敏，API key 会跟着参数落盘。维护一份敏感字段名单，序列化前统一打码。
- **读写不区分**。读工具可放开自动重试；写工具必须在 Agent 循环外加人工确认或白名单，否则循环里一次重复调用就是生产事故。
- **超时被吞掉**。部分 HTTP 客户端默认无限等待，模型会一直干等。显式设置 connect / read 两级超时，超时后返回明确的错误结构而不是抛裸异常。

## 可复用建议

1. 新接服务先做“空转模式”：请求打到 echo 端点或本地 mock，先验证 Agent 的参数生成，再切真实上游。
2. 工具描述里写清“什么时候不该用我”，能显著减少误调用。
3. GET 结果做 60 秒内存缓存，同一轮对话里的重复查询不重复打上游。

## 总结

Agent 对接外部服务的本质，不是把 API 搬进上下文，而是为每次握手定义好契约、通道与观测。把不确定性拦在工具层内部，让 Agent 只面对结构化的成功与失败，它才能表现得像一个可靠的执行者，而不是一个爱猜的调用方。
