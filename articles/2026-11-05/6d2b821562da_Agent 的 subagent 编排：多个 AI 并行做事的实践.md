## 背景

单个 Agent 跑长任务的瓶颈很早就会暴露：上下文被工具输出塞满、每一步串行等待、一个环节出错整条链重来。我们在自动化工作流（代码审查、批量文档处理、多数据源检索）里把一部分工作拆给 subagent 并行执行之后，整体耗时和主上下文压力都明显下降。这篇帖记录一套跑了一段时间、踩过坑的编排方式。

## 问题

让主 Agent 亲自干所有事，常见三类麻烦：

1. **上下文污染**。长文件、日志、网页内容等原始输出直接进入主对话，几轮之后模型开始“忘事”，指令遵循质量下滑。
2. **串行太慢**。十个相互独立的子任务排队执行，墙钟时间就是十倍。
3. **失败粒度太粗**。一个子任务失败，主 Agent 带着中间状态继续走，错误被后续步骤放大。

## 做法

编排原则一句话：主 Agent 只做拆解、分发、汇总、验收；每个 subagent 只做一件有明确完成标准的事。

1. **任务拆分**。先把任务切成相互独立（或依赖可排序）的子任务，每个写清：输入、预期产出、完成标准。
2. **上下文隔离**。subagent 拿到独立上下文，只注入与它相关的信息，不是主对话全量历史。
3. **并行派发**。独立子任务同时 spawn；有依赖的按层派发，上一层产出作为下一层输入。
4. **结果收敛**。subagent 返回结构化摘要（结论 + 关键数据 + 产物路径），原始产物写盘，主 Agent 引用路径而不是全文。
5. **验收与重试**。逐个核对完成标准，不合格的带失败原因重新派发，最多重试一次，仍失败就转人工。

## 踩坑点

- **摘要不收口**。早期让 subagent “描述你做了什么”，每个返回几百行，主上下文照样爆。后来强制 JSON 结构加字数上限才稳住。
- **并发写同一文件**。两个 subagent 同时改一份配置，后写覆盖先写。现在按资源划所有权，一个文件只归一个 subagent。
- **工具权限没下放**。subagent 默认继承不到部分 MCP 工具权限，跑到中途才报错。派发前先核对工具清单。
- **该串行的强行并行**。比如“先定接口、再各自实现”，拆太早会导致实现方向漂移。有依赖就分层，别迷信并行。
- **并发无上限**。一次 spawn 十几个，外部 API 限流直接把整批打挂。我们收敛到 3~5 个并发。

## 可复用建议

- subagent 返回永远是三样：结论、关键数据、产物路径，且结构化。
- 大产物落盘、传路径不传内容，这是控制主上下文的根本手段。
- 每个子任务必须有可机器判断的完成标准，否则验收形同虚设。
- 重试必须携带上次失败原因，裸重试基本是浪费配额。
- 记录每次派发的输入、输出、耗时，离线复盘和回放都靠它。

## 总结

subagent 编排的价值不在“多个 AI 显得厉害”，而在两点：上下文隔离让主 Agent 保持清醒，并行派发让墙钟时间可控。它不是免费的，拆分、验收、限流、权限都要工程化管起来。建议从“两个独立子任务并行”这种最小场景开始验证，跑稳后再逐步扩大拆分粒度。
