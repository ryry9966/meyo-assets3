## 背景

订阅源多到看不完，是老问题了。社交平台时间线噪音越来越大，RSS 反而是少数还坚持"订什么看什么、不带算法加戏"的协议。过去 RSS 解决不了"读不完"——但现在 LLM 批量处理文本的成本已经低到可以当耗材用，这件事终于可以工程化。

我的目标很朴素：每天早上在群里收到一条可扫读的摘要日报，抓取、过滤、摘要、推送全流程本地跑，不依赖任何第三方聚合服务。

## 问题

动手前先想清楚三个坑：

- 直接把所有 RSS entry 扔给模型，token 全浪费在噪音上，且重要信息会被平均掉；
- RSS 源质量参差：有的只有标题、有的给全文、有的更新频率完全不可预测；
- 去重、失败重试、成本控制，都得自己管。

## 做法

整条管线分四段：**抓取 → 过滤 → 摘要 → 推送**，每段独立落盘、可重放。

1. **抓取**：cron 每 2 小时触发，拉取 feed 列表并解析 entry 的 guid / link / pubDate，写入 SQLite。以 guid 为主键去重，guid 缺失时退回 link 的 hash。
2. **过滤**：纯规则层——关键词黑名单、来源权重、标题正则。这一层把约 70% 的噪音挡在模型外面，是成本控制的基石。
3. **摘要**：agent 批量处理，每次把 8–10 条打包进同一个 prompt，要求输出固定 schema 的 JSON：一句话摘要、2–3 个要点、"是否值得进日报"的判断。只有判定通过的条目进入日报渲染。
4. **推送**：每天早上把前一天通过过滤的条目渲染成 Markdown 日报，推到 Telegram 群。

摘要 prompt 的硬约束只有两条：只基于给定文本作答；不确定就写"原文未说明"。

## 踩坑点

- **guid 不靠谱**：有的源 guid 就是 URL 且会变化，导致重复入库。兜底方案是 link + title 的 hash 做二次校验。
- **pubDate 不可信**：时区混乱，甚至有源发未来时间。后来统一按本地入库时间轮转，不再依赖 feed 的时间戳。
- **摘要是负资产的情况**：只有 summary 的 feed，摘要质量太差，"摘要的摘要"没有意义。这类源现在只保留标题直接进日报，不浪费 token。
- **摘要幻觉**：早期模型会给要点"补充背景知识"，加上"不得引入给定文本之外的信息"的约束后才稳定下来。
- **并发与重试**：一次拉 30 个 feed 串行太慢，改成并发 5 + 失败重试一次，失败的记到单独的表，第二天补抓。
- **成本**：规则过滤 + 批量打包之后，日报的每日 token 成本降到了几毛钱级别。

## 可复用建议

- 每个 stage 的中间结果都落盘，SQLite 足够。管线任何一环出问题，可以从任意一步重放，不必重抓。
- 分级推送：高权重来源即时推，普通来源进日报。否则即时推送很快会"狼来了"。
- 摘要永远附带原文链接。摘要是索引，不是替代。
- 监控最简版：日报末尾固定一行"本次处理 N 条，失败 M 条"，异常一眼可见，不需要专门的看板。

## 总结

整条管线没有引入任何重型组件：cron、解析器、SQLite、一个 agent，加起来不到三百行。真正的难点不在代码量，而在过滤规则和摘要 prompt 的持续调优——这两件事没有一次到位的方案，只能跑起来慢慢改。

跑了一个多月，最大的收益其实不是省时间，而是重新掌握了信息入口：摘要质量不满意可以随时换模型、调规则，但订阅什么、以什么节奏看，始终在自己手里。
