## 背景

社区里不少人在用 Agent 批量产出内容：技术周报、教程、文档翻译。生成环节已经很成熟，真正的摩擦在发布端——同一篇 Markdown 要同时投到公众号、知乎、GitHub 仓库或静态博客，而每个平台对 Markdown 的支持子集都不一样。我们的做法是：把 Markdown 当作中间表示（IR），把发布当作编译，搭一条固定的转换管线。

## 问题

直接把模型输出贴到各平台，典型故障包括：

- 公众号编辑器不认 GFM 表格、不支持代码高亮，贴进去样式全丢；
- 知乎会吞掉部分 HTML，脚注语法 `[^1]` 原样显示；
- AI 产出的标题层级混乱（多个 H1、H2 直接跳 H4），frontmatter 偶尔被当成正文渲染；
- 图片用相对路径或占位链接，发布后全部裂图。

单看每个问题都不难修，但它们每天出现、每个平台各出现一次，这就是流水线问题，不是编辑问题。

## 做法

管线分四步，每步独立可调用。我们封装成 MCP 工具，Agent 生成完草稿后自己在工作流里调用，不需要人肉搬运。

1. **规范化**：用 remark 解析成 AST，压平标题保证唯一 H1、清理多余转义、统一列表符号、把 frontmatter 剥离进元数据。这一步与目标平台无关。
2. **校验**：跑一个自写 linter，检查图片链接可达性、代码块语言标签、表格列数一致性。报错即中断，不做静默修复——宁可让 Agent 重写，也不发布带病文档。
3. **平台适配**：每个目标一个 renderer：
   - 公众号：remark 转 rehype 后把所有样式内联进 style 属性，代码块转成带背景色的 HTML 片段；表格超过 4 列直接转图片；
   - 知乎：只保留白名单标签，脚注转成文末普通列表；
   - GitHub / 静态博客：保留 GFM，图片路径重写到仓库或 CDN。
4. **图片落位**：发布前统一上传图床、重写链接，alt 文本由 Agent 根据上下文补齐。

## 踩坑点

- **代码块语言标签**：模型爱写 ` ```text ` 或干脆不写，渲染器必须做兜底映射；
- **转义污染**：模型偶尔输出 `\*` 和 HTML 实体，规范化阶段要专门清一遍；
- **样式内联不彻底**：公众号只认 style 属性，外部 class 一律被剥离，自动内联后仍建议抽查一篇；
- **格式漂移**：Agent 多轮生成的结构每次略有差异，靠 prompt 约束不可靠，最终靠 lint 强制收敛；
- **图片重复上传**：先算哈希查重，否则多平台发布一次就多一份冗余资源。

## 可复用建议

- 永远不要把模型原始输出直接发布，中间至少过一次 AST 规范化；
- 单一源文件 + frontmatter 驱动，所有平台产物都是派生物，改内容只改一处；
- 每个 renderer 配 snapshot 测试：固定几篇金标文档，改渲染逻辑时 diff 一目了然；
- 把四个步骤暴露成 MCP tools，让 Agent 在工作流里自己走完整条管线，而不是人复制粘贴到一半漏一步。

## 总结

这条管线跑下来，多平台发布的边际成本基本只剩"点一下发布"。核心思路并不新：Markdown 是 IR，平台是编译目标，linter 是卡点。工具链基于 remark/rehype 一两百行就能搭起来，比每次手动修格式划算得多。有类似场景的可以直接从"规范化 + 校验"这两步起步，适配层按需补。
