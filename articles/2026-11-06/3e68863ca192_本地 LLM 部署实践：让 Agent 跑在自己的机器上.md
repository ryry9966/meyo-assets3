## 背景

做 Agent / MCP 自动化这两年，我的工作流里模型调用越来越频繁：一条自动化链路动辄几十轮工具调用，API 账单和「数据出网」成了两个现实约束。把一部分负载挪到本地，成了顺理成章的尝试。本文记录我在一台 24GB 显存的 Windows 主机 + 一台 32GB 统一内存的 Mac 上跑本地模型的完整过程，重点是 Agent 场景，不是聊天场景。

## 问题

本地部署的难点和多数人想的不一样，真正的瓶颈有三个：

1. **显存/内存预算**。模型权重只占一部分，KV cache 会随上下文长度线性增长，长上下文才是爆显存的主力。
2. **工具调用稳定性**。跑分高不等于会调工具。Agent 要求模型严格输出 JSON、正确填参数，小模型在这里崩得最多。
3. **吞吐速度**。聊天等 3 秒无所谓；Agent 一条链路 50 次调用，每次 8 秒就是 7 分钟，速度直接决定自动化能不能用。

## 做法

**第一步：盘点硬件，确定档位。** Q4 量化下的粗略经验：7B 约需 6GB 显存，14B 约 10GB，32B 约 20GB（含少量上下文余量）。先确定能跑的最大档位，再往下留一档做兜底。

**第二步：选运行时。** 我的选择：Ollama 做日常（省心、模型管理方便）；要并发和高吞吐时上 vLLM；llama.cpp 适合精细调参。三者都暴露 OpenAI 兼容接口，迁移成本几乎为零。

**第三步：选模型。** 别只看榜单，重点测工具调用。我的做法是拿 15 个真实任务（读邮件、调 MCP 工具、生成结构化日报）组成小型评测集。Qwen 系列 14B/32B 在我的测试里，工具调用成功率明显高于同体积其他模型。

**第四步：接入 OpenClaw。** 把 base_url 指向本地服务即可，MCP 工具的 schema 会原样传给模型。建议把工具描述写得比调用云端时更短——小模型上下文利用效率低，冗长描述反而降低成功率。

**第五步：压测。** 记录三个数：首 token 延迟、tokens/sec、长上下文下的显存峰值。这三个数决定自动化链路能否上生产。

## 踩坑点

- **`n_ctx` 默认值太小**。很多运行时默认 2k~4k 上下文，Agent 跑到一半工具结果塞满就截断。改大之前先算 KV cache 的显存占用。
- **量化别贪低**。Q2 版本指令遵循明显劣化，工具调用基本不可用。Agent 场景 Q4 是底线，关键任务用 Q5/Q6。
- **结构化输出要靠约束**。与其在 prompt 里求模型输出 JSON，不如开启运行时的 grammar / structured output 功能，在解码层直接约束格式，成功率从「碰运气」变成「稳定」。
- **别让小模型做规划**。多步推理会让它陷入循环调用。我的解法是分级路由：规划用云端大模型，工具执行用本地模型。

## 可复用建议

1. 先用 7B~14B Q4 验证整条自动化流程，确认架构可行后再考虑升级硬件，顺序别反。
2. 维护一份自己的评测集和配置表（模型 / 量化 / 上下文 / tokens/sec / 成功率），比任何榜单都可信。
3. 工具描述和系统提示词做版本管理，换模型之后回归跑一遍，防止隐性退化。

## 总结

本地部署不是设备竞赛，而是一组工程取舍：显存换上下文，量化换速度，模型体积换工具调用稳定性。对 OpenClaw / MCP 用户来说，结论很朴素——先用最小可行配置把链路跑通，让数据告诉你该在哪里加钱。
