## 背景

Agent 大部分时间是"睡着"的。但只要它要主动做事——定时提醒、盯一个抓取任务、检查 MCP 工具的健康状态——就必须有被唤醒的机制。OpenClaw 里的 heartbeat 就是干这个的：每隔一段时间唤醒 agent，看有没有该做的事。听起来简单，但轮询间隔设多少、要不要换成推送，是我们内部争论最久的问题之一。

## 问题

轮询的代价很直观：间隔 1 分钟，一个 agent 一天醒来 1440 次，每次唤醒都要加载上下文、跑一次推理，token 成本线性上涨；间隔拉到 30 分钟，又满足不了"5 分钟内响应"这类时效需求。

推送看起来更优雅——事件来了才醒——但它把复杂度转移到基础设施：webhook 丢了怎么办？事件重复投递怎么办？服务重启期间积压的事件要不要补？

单选任何一边都有明显短板。

## 做法：混合，但以轮询为底座

我们的结论是分层：

1. **按延迟要求给事件分类。** 秒级响应的（用户消息、即时告警）走推送通道；分钟级可接受的（定时任务、状态巡检）全部走 heartbeat。
2. **heartbeat 做两级频率。** 默认 10 分钟一个 coarse beat，只做轻量检查：有没有到期任务、上次会话是否留了未完成标记。发现线索才展开细粒度动作。安静时一次 beat 控制在几百 token。
3. **加 jitter。** 多个 agent 不要对齐同一时刻醒来，在间隔上叠加 ±20% 随机偏移，避免同时打满 API 限流。
4. **推送通道必须幂等。** 每个事件带 dedup key，agent 处理前先查重；失败进重试队列，超限进死信，绝不静默丢弃。
5. **heartbeat 兼任 watchdog。** 每次心跳写 last_beat 时间戳，外部监控发现超过 2 个周期没心跳就告警。轮询不只唤醒 agent，也在证明 agent 活着。
6. **配额降级。** 每个 agent 设每日唤醒预算，超了自动把 coarse beat 间隔翻倍——宁可慢一点，不能烧穿配额。

## 踩坑点

- **每次唤醒都加载完整上下文**，早期一晚上烧掉大半配额。后来做了"最小唤醒载荷"：beat 默认只带摘要和任务队列，不拉历史消息。
- **心跳任务里塞了长耗时动作**（比如直接跑抓取），一次 beat 卡了 8 分钟，后续 beat 全部堆积。现在 beat 只做决策，重活交给异步任务。
- **推送事件没做幂等**，同一条 webhook 重试三次，agent 发了三条重复通知。dedup key 是后补的——教训是推送通道上线第一天就该有。
- **离线补齐没设计**：agent 重启后，宕机期间的定时任务直接消失。现在 beat 时对比 last_beat 和当前时间，把错过的任务按"过期即放弃 / 立即补跑"两类处理。
- **时区问题**：用 UTC 存调度时间，展示才转本地，避免夏令时调出 bug。

## 可复用建议

- 把 heartbeat 当 watchdog 和调度兜底，不要当唯一的实时通道；实时性交给推送，可靠性交给轮询。
- beat 的原则是"便宜、快、可跳过"，单次成本要有硬上限。
- 监控三个指标就够：beat 间隔 p95、missed beats 数、单次 beat 的 token 均值。最后一个涨了，通常是有人在 beat 里塞了私活。

## 总结

轮询和推送不是二选一。轮询给你可预测的底座和存活性证明，推送给你时效性，混合架构里两者各司其职。设计时真正要盯住的不是"选哪个"，而是每次唤醒的成本、幂等性和错过事件后的补齐策略——这三件事决定了 heartbeat 是一个安静的守护进程，还是一个安静的账单生成器。
