# AI Agent 的错误恢复：当外部 API 挂了怎么办

## 背景

Agent 跑久之后你会发现：demo 里最稳的部分是模型，最脆的部分是外部依赖。MCP 工具、第三方 API、内部服务……任何一个 5xx 或超时，都可能让一次自动化任务从"顺利执行"变成"模型开始编故事"。

传统服务挂了返回错误码，调用方处理即可。Agent 不一样：**错误信息会进入上下文，成为模型推理的一部分**。模型看到一堆报错文本，可能重试、可能放弃，也可能脑补出一个看起来合理的结果。所以错误恢复不只是工程问题，也是提示词问题。

## 三类典型故障

实践中大概率遇到这三种：

1. **瞬时故障**：超时、502/503、网络抖动，过几秒重试大概率成功。
2. **限流与配额**：429，硬重试只会更糟。
3. **结构性故障**：上游改了返回字段、部分成功、返回半截数据。最危险，因为 HTTP 层是 200，模型拿到残缺数据会自行填补空白——幻觉往往从这里产生。

## 我目前的做法

**第一步：错误在工具层拦截，不进模型。** 给所有工具套统一 wrapper，把异常归一化成结构化对象：

```json
{ "ok": false, "error_code": "UPSTREAM_TIMEOUT", "retryable": true, "hint": "wait 5s then retry" }
```

关键是 `retryable` 字段——重试与否是工程决策，不该交给 LLM 现场判断。

**第二步：重试放在工具层，带退避和上限。** 指数退避加随机抖动，最多 3 次。绝不把"重试"作为能力暴露给模型，否则它没有退避概念，会以最快速度在同一个接口上撞墙烧 token。

**第三步：重试耗尽走降级，而不是抛错。** 优先级：本地缓存（附数据时间戳）→ 备用 API → 明确返回"该数据当前不可用"。降级结果必须结构化标注，如 `"degraded": true, "stale_at": "..."`，让模型知道自己在用过期数据，而不是把缓存当实时值。

**第四步：不可恢复时，让 Agent 汇报而不是硬编。** 系统提示里明确要求：工具不可用时跳过该步骤并在最终输出注明，禁止用推测值填充。

## 踩过的坑

- **让模型自己重试**：没有退避概念，限流越打越死。
- **原始堆栈进上下文**：一大段 stack trace 会让模型注意力跑偏，甚至开始"分析"堆栈而不是完成任务。错误要压缩成一两句话。
- **重试没做幂等**：POST 类操作超时后重试，结果是重复下单、重复发通知。写操作必须带幂等键。
- **缓存降级没标时间**：模型拿着三天前的数据一本正经输出结论。
- **熔断后没有恢复探测**：一旦熔断永远走降级。记得做半开探测，隔段时间放一个请求试水。

## 可复用的建议

- 统一错误协议 + `retryable` 字段，做成公共 wrapper，所有 MCP 工具复用。
- 所有外部状态引用都带时间戳，宁可让模型说"数据可能过期"，不要让它假装新鲜。
- 做故障注入测试：写一个假工具，固定返回超时 / 429 / 坏 JSON，观察 Agent 的行为路径。这一步能提前暴露大部分问题。
- 监控里把"降级触发次数"单独埋点，降级率突增往往是上游故障的第一信号。

## 总结

Agent 的错误恢复，核心不是"让模型更聪明地处理错误"，而是把错误挡在模型外面：能重试的在工具层重试，重试不了的走结构化降级，最后才把一句干净、诚实的"这条路走不通"交给模型。让工程负责韧性，让模型负责表达——这个分工想清楚了，上游 API 挂掉就只是弹一条告警的事，而不是一场幻觉事故。
