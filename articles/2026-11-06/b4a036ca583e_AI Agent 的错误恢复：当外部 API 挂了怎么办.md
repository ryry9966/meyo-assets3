## 背景

Agent 的能力边界基本取决于它能调多少外部接口：LLM provider、搜索、天气、支付、企业内部 MCP 工具……这些依赖任何一个都可能超时、限流或直接 503。单次脚本调用挂了重跑一遍就行，但 Agent 是多步、有状态的流程，一次工具失败处理不好，代价会被放大：重试烧 token、上下文被垃圾填满、模型开始"脑补"结果，最终用户拿到一个看起来合理、实际基于假数据的答案。

## 问题拆解

实践中外部 API 失败通常暴露三类问题：

1. **重试策略缺失或过激**——不区分错误类型，4xx 也无脑重试，或者瞬间打满重试次数。
2. **失败信息污染上下文**——原始 stack trace、HTML 错误页直接进对话历史，模型被误导。
3. **没有降级路径**——唯一工具挂了，整个任务卡死或静默失败。

## 做法

**第 1 步：给错误分类。** 在工具封装层（比如统一包一层 MCP tool wrapper）把错误归为三类：可重试（timeout、429、5xx）、不可重试（4xx、鉴权失败）、结果为空。返回结构化的 `{code, retriable, message}`，不要把原始异常直接抛给模型。

**第 2 步：指数退避 + 抖动。** 重试间隔 1s → 2s → 4s，加随机抖动避免重试风暴。设置硬上限（比如 3 次）和整个任务的 deadline 预算，防止一个工具把整个 Agent 卡住。

**第 3 步：幂等保护。** 凡是 POST 类操作（下单、发消息），重试前必须带幂等键或在工具层做去重。这条不做，重试机制本身会成为新的事故源。

**第 4 步：准备降级路径。** 为关键工具准备备选方案：备用 API、本地缓存数据（明确标注数据时间戳）、或如实告知用户"这一步失败了，已跳过"。宁可诚实报错，也不要让模型用上下文里的旧信息填空。

**第 5 步：状态检查点。** 长任务在每个成功步骤后落盘中间状态，恢复时从断点继续而不是从头跑，既省 token，也避免重复副作用。

## 踩坑点

- **让 LLM 在对话循环里自己"决定重试"**：每次重试都是一轮完整的模型调用，token 成本翻倍，而且模型重试两三次后经常开始编造成功结果。重试应该放在代码层，模型只负责决策。
- **把"工具返回空"当成"工具失败"**：空结果是有效信息，混为一谈会导致无意义的重试。
- **错误信息不过滤就进上下文**：一页 HTML 错误日志能顶掉几千 token 的有效上下文。
- **熔断状态不跨轮次共享**：多轮会话中每个 turn 都重新去连一个明知已挂的服务，等于没有熔断。

## 可复用建议

- **统一错误契约**：所有工具返回相同结构，Agent 主循环按 `retriable` 字段统一分流，不为每个工具写一套特判。
- **策略配置化**：重试次数、超时、降级选项放配置文件，不同工具不同预算，别写死在代码里。
- **结构化工具调用日志**：记录入参、耗时、错误码，事后复盘故障时这是唯一可靠的证据来源。

## 总结

外部 API 挂掉不是异常路径，而是 Agent 的日常。好的错误恢复不是"永不失败"，而是失败可控、信息不失真、有退路、可恢复。核心原则就一条：重试和退避放在代码层做，模型只处理策略层面的决策；同时永远给用户一个诚实的失败报告，而不是一个基于幻觉的漂亮答案。这套封装做好之后，接新工具时套同一个模板，Agent 的稳定性会有质的提升。
