## 背景

用 OpenClaw 跑了一段时间自动化后会形成一个直观感受：主 agent 的上下文是稀缺资源。让它一次性完成“调研 10 个仓库的 changelog 并汇总”这类任务，通常表现为前半程正常、后半程开始丢信息、工具调用变慢、token 消耗直线上升。subagent 的价值就在这里——把独立子任务分出去，每个子任务一个干净的上下文，主 agent 只负责拆分和聚合。

## 问题

单上下文串行执行有三个典型痛点：

1. **慢**。十个子任务串行跑，总时长是累加的。
2. **上下文污染**。子任务的中间过程全堆在主对话里，真正重要的结论被稀释。
3. **脆弱**。一个子任务失败，整个流程跟着卡住，前面的产出也难以复用。

## 做法

我的编排结构不复杂，分四步：

**1. 拆任务，先验证独立性。** 列出子任务，确认彼此没有共享可变状态。要写同一批文件的任务不并行，只读类任务（调研、校验、抓取）才适合并行。

**2. 给 subagent 定输出契约。** 每个 subagent 的 prompt 末尾强制约定返回格式，比如固定字段的 JSON：`status`、`summary`（限 200 字内）、`artifacts` 路径。主 agent 收到的不是聊天记录，而是结构化结果。

**3. 控并发。** 并发数按上游 API 的限流来定，我一般设 3。宁可靠排队，不要靠重试风暴。

**4. 主 agent 只做聚合。** 汇总阶段把各路 summary 合成一份报告，附上失败清单，必要时单独起一个收尾 subagent 处理。

## 踩坑点

- **subagent 输出太长。** 最初没限制返回篇幅，五个 subagent 各回两千字，主上下文照样爆炸。加上 summary 字数上限后才解决。
- **工具权限没收紧。** 一个“只读调研”的 subagent 拿到了写权限，自作主张改了配置文件。此后每个 subagent 只挂必需的最小工具集。
- **共享状态冲突。** 两个 subagent 同时往同一个文件追加，内容互相覆盖。结论：可变资源要么加锁，要么干脆串行。
- **无超时。** 一个抓取任务挂住，整批并行被拖死。现在每个 subagent 都带超时和单次重试，失败走降级路径。

## 可复用建议

- 把 subagent 的 prompt 做成模板文件，参数化目标和输出契约，新任务只改变量。
- 先用单个 subagent 干跑一次，确认输出契约可靠，再放量并行。
- 每次运行落一条日志（任务、耗时、token、结果状态），编排调优全靠这份数据。
- 失败任务单独排队重跑，不让一个失败拖累整批。

## 总结

subagent 编排的本质不是“多开几个 AI"，而是上下文管理：隔离执行、约束输出、控制并发、明确聚合。把它当成一个带并发限制的任务队列来设计，主 agent 保持轻，整个系统才稳。如果你的自动化流程已经出现“越跑越糊涂”的迹象，值得从最小的两个并行子任务开始试起。
