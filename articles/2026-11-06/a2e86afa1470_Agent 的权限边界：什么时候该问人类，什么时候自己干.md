## 背景

跑 OpenClaw 这类常驻 Agent，手里很快会攒出一堆高权限能力：exec 执行、浏览器控制、消息外发、cron 定时任务，MCP 又在持续往里挂新工具。权限边界不是配置一次就完的事——它决定了这个 Agent 是"省心的助理"还是"定时炸弹"。

## 问题：两个极端都跑不通

实践里大多数人从两个极端起步：

- **全放手**：一次误删目录、一条发错群的消息、一笔不该下的单，信任直接清零，之后再也不敢开自动化。
- **全问**：Agent 变成人肉确认机，问十次你可能只认真看第三次，剩下秒点"同意"——确认机制名存实亡，比不问还危险。

核心矛盾是**确认疲劳 vs 事故风险**。真正要回答的不是"问不问"，而是"哪类事必须问"。

## 做法：一条四象限的判断线

用两个维度切分所有工具调用：**可逆性**（能否撤销）× **影响范围**（只动本机，还是触及外部世界）。

| | 可逆 | 不可逆 |
|---|---|---|
| 本机 | 自己干 | 干，但先备份/快照 |
| 外部 | 自己干，留审计日志 | **必须问** |

读文件、写草稿、跑测试、重命名：直接干。发消息、建工单：可干但全量记录。删除生产数据、付款、对外发布、群发：停下来问。

落地时把边界**压在工具层，而不是提示词层**：

1. exec 收敛为白名单 + 沙箱执行（容器、受限用户、目录挂载范围）；
2. MCP 按需挂载，不常用的 server 平时不连，少一个高危工具少一条事故路径；
3. 外发通道设硬阈值：金额上限、收件人白名单，超限强制走人工确认；
4. cron 等无人值守任务权限单独收敛为"只读 + 白名单"——没人盯着的时候，权限应该更小而不是更大；
5. Agent 干完要**自验证**：拿退出码、文件 diff、回读消息做证据，模型说"完成了"不算完成。

另外，"问人类"要做成结构化确认：一条摘要包含操作内容、影响范围、回滚方式，人 3 秒能看完，而不是一句含糊的"可以吗"。

## 踩坑点

- 只在 system prompt 写"不要删库"。提示词是建议，工具层才是法律，模型终会有一天不遵守。
- 图省事关掉沙箱，某天一个 `curl | sh` 直接打穿。
- MCP server 升级后悄悄多了几个高危工具，边界被静默放宽，没人注意到。
- 确认弹窗写得太长，用户被训练成秒点确认，机制等于没有。
- 不留审计日志，出了事查不清 Agent 到底执行过什么。

## 可复用建议

- **默认最小权限，按报错扩权**，而不是按想象扩权——跑不动再放，别提前放。
- 每接入一个新工具/新 MCP，先问一句：它落在哪个象限？
- 所有不可逆操作先落"暂存区"：草稿、dry-run、预览，确认后才真正落地。
- 给自主执行设预算：次数、token、花费上限，超限自动降级为询问模式。
- 定期翻审计日志，把"其实不用问"和"其实必须问"的各挪一次象限，让边界跟着真实使用走。

## 总结

权限边界不是一堵墙，而是一条随信任缓慢外扩的线。判断标准就两个词：**可逆性、影响范围**。强制手段放在工具层，提示词只做补充；问人类的次数要少而重，让每一次确认都真正被读到——这才是自动化能长期跑下去的前提。
