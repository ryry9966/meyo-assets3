最近 36kr 一篇讲 Agent 基础设施的文章把一个问题顶上了热榜：各家 harness 在公开基准上的任务完成率，已经从 2023 年的个位数一路爬到 70% 上下——“手已经够稳了”，为什么还要专门造一个 Agent Native Database？这问题听着反常识，其实是计算机体系结构里反复上演的老剧本：CPU 越快，memory wall 越显眼；模型越准，瓶颈越往后挪。这篇就把两层各自的职责拆开，讲清楚“准了”为什么还不等于“能用”。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-06/4333a6ac04444737.png)

## 先分清两层：Harness 管这一步，数据库管每一步

先把名词摆正：

- **Harness（脚手架）**：包在模型外面的执行层——system prompt 拼装、tool schema 注册、plan→act→observe 循环、重试与终止条件。Claude Code、各家 Agent SDK、LangGraph 都属于这一层。
- **Agent Native Database**：为 agent 的读写模式设计的数据层，核心能力通常是语义检索、会话状态、分层记忆、并发控制和全程留痕。

两者的关系一句话说清：harness 解决“下一步怎么走”，数据库解决“走过的路、看过的风景存在哪、怎么取回来”。这不是替代关系，是上下两层。harness 再准，它默认也是围绕单次会话优化的——会话一结束，状态要么丢，要么散落在几个临时 JSON 文件里，像用保鲜盒建银行。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-06/daced5b06b8ff249.png)

## 准确率的天花板，往往卡在上下文而不是推理

复盘 agent 的失败案例，会发现一个高频模式：不是模型“不会想”，而是“没看见”——关键文件没进 context，历史决策被截断，检索回来的是相似但不对的段落。几条公认的研究结论可以佐证：

- **Lost in the Middle**（Liu et al., 2023）：长上下文的中间部分召回率明显低于头尾，信息放哪本身就影响质量。
- **NoLiMa 类基准**：一旦任务需要语义匹配而非字面匹配，许多模型的有效上下文长度会掉到标称值的一小部分。窗口大 ≠ 装得多。

换算成工程语言：**agent 准确率 ≈ 推理能力 × 上下文质量**。前者由模型厂商去卷，后者是你自己的数据问题。所以社区这两年把 prompt engineering 的说法逐步换成了 context engineering——问题从“怎么问”变成了“给模型看什么”。数据库在这层的价值很具体：用 hybrid retrieval（向量 + 全文 + 结构化过滤）把该进 context window 的那 1% 数据精准挑出来。上下文窗口不是钱包，不是塞得越满越好花。

## Agent 的读写模式，和人类应用是两个物种

传统数据库的默认用户是人写的应用：低频交互、SQL/ORM 查询、事务由程序员提前设计。agent 全反着来：

1. **查询形态**：主查询不是精确匹配，而是自然语言 + embedding 的语义检索，还要混结构化过滤——这正是 hybrid retrieval 兴起的原因。
2. **记忆分层**：认知科学的分类被直接搬进架构——working memory（本次会话）、episodic（做过什么）、semantic（沉淀的事实）、procedural（可复用技能）。MemGPT（后来的 Letta）最早把这套系统化。
3. **并发主体**：几十个 agent 同时读写同一个 workspace，没有事务和隔离级别，就是一场分布式覆盖写的车祸现场。
4. **生命周期混搭**：秒级会话状态和月级长期记忆共存，需要 TTL、摘要压缩和遗忘策略。
5. **可回放**：每一步 tool call 和观察都要留痕（event sourcing 思路），否则 eval、回归测试、事故复盘都无从谈起。

举两个例子就明白：coding agent 需要符号索引、历史 diff 和失败尝试记录；research agent 需要每个结论的来源溯源。这些靠“一个 context 塞到底”都撑不住。

## 为什么不能让 Harness 顺手全包？算三笔账

- **成本账**：把历史全塞进 context，token 费用线性涨，attention 开销按平方涨，还触发上面说的质量劣化。一次精准检索的成本，远低于每一步都背全量记忆。
- **工程账**：每个团队自己用 JSON 文件造记忆，最后得到 N 套互不兼容、无事务、无并发控制的“文件系统玩具”。数据库六十多年攒下的索引、事务、并发控制，没有理由重写一遍。
- **组织账**：agent 一旦规模化运行，trace、记忆、用户反馈每天都在沉淀，这就是数据引力——它天然流向一个统一、可查询的存储。散落的状态没法做分析，更没法迭代。换句话说：harness 做个无状态或轻状态的好公民就好，重状态本来就不该由它背着。

## 落地不必激进：一条务实的选型光谱

实际落地是连续光谱，不是非黑即白：

- **起步**：Postgres/SQLite + pgvector + 全文索引，多数团队够用；LangGraph 的 checkpoint 默认也就落在 Postgres/SQLite 上。
- **进阶**：召回规模上去后换专精向量库（Qdrant、Milvus）；需要分层记忆策略时，引入 memory 中间层（Mem0、Zep、Letta 这类）。
- **判断三问**：①数据要不要跨会话、跨 agent 共享？②要不要按语义查？③要不要可回放审计？“是”越多，越需要一个真正的数据层；全“否”，harness 里的临时状态就够。
- **避坑**：市面上一些“agent native”产品，目前更多是对访问模式的封装，底座仍是成熟数据库。别为名词重构系统，别为概念交税。

## 写在最后：三条冷思考

1. **先归因，再买基建**：把失败案例标注成“推理错”和“没看见”两类，只有后者堆数据层才有效；前者换再多数据库也没用。
2. **记忆策略是要迭代的产品**：写什么、忘什么、何时摘要，需要像调 prompt 一样建 eval 集反复调，不是一次性配置完拉倒。
3. **警惕过早专门化**：先用 pgvector 打补丁，等规模和访问模式真正长出来，再换专门引擎——选型是工程问题，不是信仰问题。

龙虾的壳再硬，也得有个地方存放蜕下来的每一层壳。agent 的 harness 再准，也一样。
