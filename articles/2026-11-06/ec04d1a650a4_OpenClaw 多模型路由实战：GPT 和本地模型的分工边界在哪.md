## 背景

OpenClaw 的典型用法是挂一堆 MCP 工具加一个常驻 Agent，让它处理消息、定时任务、文件整理这些活。跑久了都会遇到同一个问题：所有请求打在一个模型上，要么账单难看，要么本地小模型在复杂任务上反复失败。多模型路由解决的就是“哪个活给谁干”。

## 问题

我最早全走 GPT，一个月下来发现 70% 的 token 花在低价值调用上：消息分类、格式转换、简单摘要。后来切成全本地（Ollama + Qwen 系），又在多步工具调用上频繁翻车——参数漏填、类型乱给、长上下文直接截断。结论是两类模型各有明确边界，需要显式分工，而不是靠运气。

## 做法

1. **先给任务分桶。** 我按三个维度打标：敏感度（是否含私钥、聊天记录、内网信息）、复杂度（单轮分类 vs 多步规划）、频率（每分钟几十次 vs 一天几次）。
2. **建配置驱动的路由表**，别把规则写死在代码里。大致分法：
   - 高频 + 低复杂度 + 可能含敏感数据 → 本地模型（消息分类、本地文件整理、脱敏前的预处理）
   - 多步工具调用、代码生成、跨文档推理 → GPT
   - 拿不准的走默认档（GPT），别为了省钱去赌
3. **两级路由。** 第一级是规则（任务类型、来源渠道、正则命中），第二级才用一个小模型做分类。90% 的请求应该在第一级就被分发掉，别让路由本身变成新的延迟源。
4. **每条路由配 fallback。** GPT 超时降级到本地兜底（提示里明确“只做摘要、不做决策”），本地 OOM 降级到云端。降级链写进配置，不要散落在各处代码里。

## 踩坑点

- **本地模型的 tool calling 是重灾区。** 同一份 JSON Schema，GPT 稳定，本地模型可能漏字段、类型乱填。对策是给本地档精简工具数量，能用 Structured Output 就别依赖 function call。
- **上下文长度不匹配。** 本地 8k 塞不进 GPT 习惯了的长 prompt，切路由等于换了内存条，投喂和分块逻辑要跟着调整。
- **GPU 冷启动。** Ollama 空闲卸载后首次调用十几秒，定时任务场景要么保活，要么接受首包慢。
- **Embedding 别跟着切。** 检索库用一个 embedding 模型建索引，查询时换了模型，召回质量会悄悄崩掉，而且很难第一时间发现。

## 可复用建议

- 路由表进版本控制，每次改规则留 commit，出问题能回滚。
- 日志强制带 model 字段和任务类型标签，跑两周后拉张表，哪些桶该挪一挪会非常直观。
- 从两档开始（本地 + GPT），不要一上来搞三四层，路由复杂度本身就是成本。
- 给每个桶设预算上限，超了自动降档，而不是月底看账单叹气。

## 总结

多模型路由不是炫技，是对任务做诚实的分级。原则就三条：敏感和高频交给本地，复杂和低频交给云端；规则优先于“智能路由”；fallback 永远要有。先把两档跑稳，再谈更细的调度。
