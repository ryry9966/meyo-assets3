## 背景

OpenClaw 的 cron 任务本质上是**无人值守的 prompt**：到点触发，agent 独立跑完，你看不到过程，只能看结果。它和聊天里随手一句话完全不同——聊天时你可以追问、纠偏，cron 跑飞了只有日志知道。我这边稳定挂着十来个定时任务（巡检、摘要、备份提醒），前期的失败几乎都出在 instruction 写法上，而不是调度本身。

## 问题

几种典型的翻车姿势：

- 写得太随意：“每天帮我看看仓库有没有问题” → agent 自由发挥，推一堆没人看的信息；
- 依赖会话记忆：cron 运行是独立会话，上次聊过的上下文根本不在场；
- 没定义“没事怎么办”：于是每天收到一条“一切正常”，第三天就把它静音了；
- 没写幂等：服务重启补跑，同一条告警推了两遍。

## 做法

我的做法是把 instruction 当成交接文档写，固定五段：**目标与触发、数据来源、步骤、输出与投递、边界与失败处理**。给个真实例子（每日 CI 巡检）：

```text
任务：每日 CI 巡检（每天 09:00，Asia/Shanghai）
目标：检查工作区三个仓库昨夜的 CI 状态，异常时提醒我。
数据来源：只用 github MCP 的 workflow runs 查询，不要猜、不要网页搜索。
步骤：
1. 逐个仓库取最近 10 条 run；
2. 过滤出 failed / cancelled；
3. 与昨日 09:00 之后的记录比对，避免重复上报。
输出：仅当存在新失败时发到 #ci-alert，格式：仓库 / 分支 / 失败步骤 / run 链接，一行一条；
没有新失败则不发任何消息，只在本地日志写一行 ok。
禁止：不要重试 CI、不要 @ 全体、不要汇报通过列表。
失败处理：数据源调不通时，写日志 source unavailable 并跳过本次，不要编造结论。
```

上线前用 run now 手动跑一次，对照日志逐条确认行为，再启用调度。

## 踩坑点

- “帮我看看 / 整理一下”这类动词太软，换成可判定的动作和阈值；
- 频率语义要写死：本地时间还是 UTC、错过的任务补不补跑；
- 结果要被脚本消费时，强制结构化输出并给字段名，自由文本没法解析；
- 别在 instruction 里塞背景故事，叙述越多，真正的约束越被稀释。

## 可复用建议

- 一个 cron 只做一件事，想做两件事就拆成两个；
- cron prompt 进版本库，改动写清楚原因，方便回溯某次行为变化来自哪次修改；
- 每周扫一遍运行记录，把每条噪音转化为一条新约束写回 instruction；
- 把“没有新情况则不发消息”这类静默条款当成默认项。

## 总结

Cron instruction 的质量，决定了自动化是省心还是添堵。核心一条：**把它写给一个不了解上下文、不会提问、只按字面执行的新值班同事看**。写完自问三个问题——它知道去哪拿数据吗？知道什么时候闭嘴吗？拿不到数据会干什么？三个都有答案，这个任务才值得挂上调度器。
