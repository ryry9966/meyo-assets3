## 背景：cron 任务是"没有追问机会的 prompt"

不少人第一次用 OpenClaw 的定时任务，都是把聊天里的一句话直接粘进去："每天早上帮我看一下仓库的 CI"。这在对话里能跑，是因为你可以追问、可以纠偏；挂上 cron 之后，它是独立会话里的唯一一条输入，跑完即止。所以 cron instruction 更像一份给值班同事的交接文档，而不是一句聊天。写它的心态要换。

## 问题：五个高频现象

实际用下来，翻车基本集中在这几类：

- 输出不稳定，有时刷屏有时沉默；
- 同一条告警每天重复推；
- 每次报告口径不一样，没法横向比较；
- 时间差八小时，或跑在错误的日期上；
- 任务失败但没有任何通知，你以为它没事。

根因是同一个：instruction 只写了"做什么"，没写"做到什么程度、怎么输出、失败怎么办"。

## 做法：七段结构 + 一个示例

我现在的模板固定七段，每条 cron instruction 照着填：

1. **场景锚点**：第一行说明这是定时任务、无人值守、无上下文可追问；
2. **目标**：一句话，只做一件事；
3. **数据来源与工具边界**：只用哪些命令、只读还是可写；
4. **判定标准**：什么情况才算"有事要报"，必须给可执行阈值；
5. **输出**：发到哪里、几行以内、什么格式；
6. **去重与状态**：读上次的状态文件，跳过已报告项，报完更新；
7. **异常路径**：来源不可用时静默结束还是发一行错误，禁止自行重试。

以"每日 CI 检查"为例：

```text
这是定时任务，无人值守运行，无上下文可追问。
目标：检查 {org}/{repo} 过去 24 小时新增的失败 CI run。
数据来源：只用 gh 命令行，全部只读。
判定：仅当失败 run 涉及 main 分支时才报告。
输出：一条不超过 5 行的消息，逐条列分支和链接。
去重：先读 {workspace}/ci-state.json，已报告的 run id 跳过，报告后更新该文件。
异常：命令失败或超时则直接结束，不重试、不发消息。
禁止：不要 re-run、不要修复、不要改动任何文件。
```

## 踩坑点

- **不要引用历史会话**。"像上次说的那样"在 cron 会话里是空引用，agent 只能瞎猜；
- **输出上限必须写死**，否则 token 成本和推送噪音都会缓慢失控；
- **状态文件要"先读后写"**，路径给绝对值，去重逻辑写进 instruction，别指望 agent 自己想到；
- **一任务一职责**。"汇总新闻顺便查磁盘"这种复合指令，挂了之后你不知道哪部分出的问题；
- **上线前手动跑一遍**：先用交互会话执行同样的 instruction，把不符合预期的输出回写成规则，再挂 cron；
- **阈值要可执行**："有重要的新闻"不可执行，"star 增长大于 10"可以。

## 可复用建议

- 建一个模板文件，新任务从模板改，不从零写；
- 高频任务（比如每 15 分钟）先降频观察两天，稳定后再调回目标频率；
- 每周 review 一次 cron 输出：连续一周没产出有价值消息的任务，删掉或降频——定时任务的维护成本经常被低估；
- 每条 instruction 至少写一句"禁止"事项，权限最小化是无人值守场景的底线。

## 总结

cron instruction 的质量，直接决定定时任务是助手还是噪音源。核心原则一句话：把每次运行当成一次没有你参与的交接班，把输入来源、判定标准、输出形式和失败路径全部写进 instruction。写的时候多花五分钟，之后省掉的是每天早上的意外。
