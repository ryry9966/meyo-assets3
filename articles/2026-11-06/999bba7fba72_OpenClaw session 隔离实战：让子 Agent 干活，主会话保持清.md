## 背景

OpenClaw 由 gateway 进程统一管理会话，每个 session 是一份独立的对话上下文：独立的 transcript、独立的上下文窗口、独立的自动压缩。主会话通常绑定聊天频道长期存活，而日常使用中大量工具调用——读文件、抓网页、翻日志——如果全发生在主会话里，上下文很快被中间过程填满：轻则频繁触发压缩丢细节，重则模型开始"失忆"，忘掉最初的约定。

子 Agent 就是为这件事设计的：通过内置的 `sessions_spawn` 起一个子会话，子 Agent 在自己的上下文里跑完整的工具循环，结束后只把最终结果写回主会话。

## 问题

主会话被污染的本质是：**过程性 token 挤占了决策性 token**。几十轮工具调用的中间输出留在上下文里，直接后果是压缩更频繁、指令遵循变差、长会话后半段质量下滑。session 隔离要解决的就是这个：过程留在子会话，主会话只收结论。

## 做法

1. **判断哪些活该下放。** 经验规则：预计超过五六轮工具调用、要读大文件、结果能压成一段话的任务，都适合 spawn。主会话只做决策和编排。
2. **任务 prompt 必须自包含。** 子 Agent 看不到主会话历史——这正是隔离的本意。目标、输入路径、约束、输出格式都要显式写进 task，例如：「读取 auth 模块近三天的报错日志，定位失败根因，输出不超过 200 字的结论和涉及文件列表，不要修改任何文件。」
3. **限制回传体积。** 明确要求"结论先行、限定长度"，否则子 Agent 一篇长文回来，主会话照样被撑爆，只是撑爆得慢一点。
4. **审计子会话。** 用 `sessions_list` / `sessions_history` 查看子会话轨迹。子 Agent 跑偏时主会话是感知不到的，长任务结束后主动查一眼。

## 踩坑点

- **隔离的是上下文，不是文件系统。** 子 Agent 与主 Agent 共享 workspace，子 Agent 改了文件，主会话后续读到的就是改过的；并发多个子 Agent 写同一文件会互相覆盖。
- **共享记忆是双刃剑。** `AGENTS.md` 和 memory 目录对所有会话可见：子 Agent 有背景常识是好事，但主会话刚纠正过的错误结论若已写入 memory，子 Agent 仍会拿到。
- **嵌套 spawn 要克制。** 子 Agent 再开子 Agent，成本与失控风险翻倍，排障时也难还原现场。
- **别假设子 Agent 一定成功。** 长任务可能超时或被截断，拿到空结果先查子会话状态，再决定重试还是下结论。

## 可复用建议

- 把下放规则写进 `AGENTS.md`，例如「探索类任务超过 N 轮工具调用必须 spawn 子 Agent，回传不超过 X 字」。模型对成文规则的遵守远好于口头提醒。
- 沉淀四段式任务模板：目标 / 输入 / 约束 / 输出格式，spawn 前填空。
- 重要结论落盘到 memory 或文件，而不是依赖主会话上下文存活；主会话该 `/reset` 就 reset，干净状态比"连续剧式"长上下文更可控。
- 用多个 agent 分职责（不同 workspace、不同模型），agent 之间 session 天然隔离，比在单 agent 里手动管理省心。

## 总结

一句话：**session 隔离隔离的是上下文，不是世界。** 子 Agent 让主会话从"干活的"退回"管事的"——只保留决策、结论和状态，把过程性脏活连同它的 token 一起关进子会话。规则写清楚、回传限长度、文件改动心里有数，这套模式足以覆盖日常自动化里的大部分污染场景。
