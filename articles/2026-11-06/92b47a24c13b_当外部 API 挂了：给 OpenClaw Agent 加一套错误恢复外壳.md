## 背景

OpenClaw 的日常自动化里，Agent 的绝大部分"能力"其实来自外部 API：搜索、模型 provider、天气、Home Assistant、自建 MCP 工具。这些依赖任何一个抖动，任务链就断。传统后端挂了可以返回 502 完事，但 Agent 的处境更尴尬——它正处在多步推理的中间，工具调用失败后模型要"决定下一步说什么"。这一步处理不好，比直接报错更糟。

## 问题

实际踩过的三类典型故障：

1. **模型编造答案**。工具抛异常后，模型有时不承认失败，而是凭记忆"补"一个结果，用户拿到的是幻觉数据。
2. **重试发生在错误的层**。靠 system prompt 让模型"再试一次"，结果是烧 token、行为不可控，还可能在 4xx 上无限循环。
3. **级联阻塞 + 哑失败**。一个慢 API 把整个 session 拖到超时，后面的步骤全部陪葬；cron 任务里这种失败往往没人知道，只会发现"这次没跑成"。

## 做法

给插件和 MCP 工具统一加一层恢复外壳，四步：

**1. 重试放在代码层，不交给模型。** 封装一个 `safeCall` 包装器：只对可重试错误（超时、429、5xx、网络错误）做指数退避加随机抖动，最多 3 次；认证/参数类 4xx 直接失败，绝不重试。

**2. 错误结构化后再进上下文。** 不要把原始堆栈扔给模型——它会把堆栈当素材，甚至复述给用户。统一返回 `{"ok": false, "error_code": "upstream_timeout", "retryable": true, "hint": "建议告知用户稍后重试"}`，模型拿到这种信息才会做出正确决策：告知用户、换工具、或终止任务。

**3. 每个关键工具准备降级路径。** 本地缓存（必须带时间戳）、备用 API、或明确的降级模式输出。失败时返回缓存并附 `cached_at`，让模型知道这是旧数据，输出时主动声明。

**4. 高频工具加熔断。** 连续 N 次失败进入冷却期（比如 60 秒），期间直接走降级路径，恢复后半开试探再放量，避免在上游雪崩时火上浇油。

## 踩坑点

- **退避不加 jitter**：多个 cron 任务同一时刻触发，同步重试会形成重试风暴，上游本来半死被你彻底打死。
- **把 4xx 也当可重试**：API key 过期，Agent 能原地重试到天荒地老。
- **降级数据不标注新鲜度**：模型拿着两小时前的缓存一本正经地回答，比报错更坑。
- **失败只打 stdout 不落盘**：cron 任务的 API 失败要写日志并通过 OpenClaw 消息通道通知，否则连"挂过"都无从追溯。

## 可复用建议

- 所有插件接入同一个 `safeCall`，错误码枚举统一，别各造轮子。
- timeout、重试次数、熔断阈值全部配置化，按工具粒度调，不要硬编码。
- 工具失败时向会话写一条可见状态消息："正在重试 / 已降级"。用户知道发生了什么，信任感完全不同。
- 监控各工具成功率，失败率突增先查上游，再怀疑自己。

## 总结

Agent 的错误恢复，核心不是让模型"更聪明"，而是把工程纪律放在工具层：重试、熔断、降级由代码保证；把决策信息（能否重试、数据多旧）诚实交给模型；把运行状态透明交给用户。三层各司其职，外部 API 挂掉时才不至于演变成一场幻觉事故。
