## 背景

E2E 测试大概是所有测试层次里"性价比争议"最大的一类：写得慢、跑得慢，还经常因为一个按钮改了 class 就集体变红。团队不是不知道它有价值，而是维护成本经常压过收益。

Agent + MCP 工具链普及后，一个自然的想法是：让 Agent 自己打开浏览器、走一遍用户流程、顺手把测试代码写出来。听起来很美，但直接丢一句"帮我给登录页写 E2E"，拿到的结果通常不能看。这篇文章记录我们在 OpenClaw 环境里跑通的一套流程，核心是把 Agent 当成"带着工具的实习生"，而不是一键生成器。

## 问题：直接让 AI 写 E2E 为什么大多失败

- **对着实现写测试**：Agent 拿到源码后倾向生成 `.css-1x2y3z` 这类实现级选择器，UI 一改全崩；
- **断言幻觉**：`expect(...).toHaveText(...)` 看着专业，内容可能是编的，测试永远绿；
- **时序靠 sleep**：Agent 很爱写 `waitForTimeout(3000)`，掩盖真实竞态；
- **上下文过载**：一次让它覆盖十个流程，输出质量断崖式下跌。

根因是：Agent 没有真正"操作过"页面，只是在猜测 DOM。所以核心思路是——先让它动手，再让它写码。

## 做法：五步流水线

**第一步：喂旅程，不喂代码。** 输入用用户旅程描述（PRD 片段或手写步骤清单），刻意不给实现源码，避免测试绑定实现细节。

**第二步：挂浏览器 MCP，先走后写。** 让 Agent 通过浏览器自动化工具按旅程真实操作一遍页面，过程中记录每步的可访问性角色、语义化 selector 和关键状态变化。

**第三步：按约定生成测试。** 提供一份内部规范（Playwright + `getByRole`/`getByLabel` 优先、禁止裸 sleep、必须断言用户可感知的结果），让 Agent 把刚才的操作轨迹严格转成测试代码。

**第四步：跑失败，喂回去。** 本地执行，失败输出原样回传给 Agent 修复。迭代上限设 3 轮，超过就人工介入，避免无限循环。

**第五步：CI 接管，Agent 只做维护。** 测试进主干后，日常改动触发的失败由 Agent 先诊断——区分是产品 bug、测试脆弱还是环境问题，人只审它的结论。

## 踩坑点

- **登录态**：让 Agent 自己走登录又慢又脆。我们把登录做成 storage state 预置，Agent 只测登录后的业务旅程；
- **动态数据**：Agent 写的测试偶尔依赖"上次运行留下的数据"，必须强制 fixture + 随机后缀，保证幂等；
- **MCP 工具粒度**：工具太细（单步 click/type）上下文膨胀很快，封装成"导航到 X 并等待就绪"这类复合动作后，token 消耗降了一半以上；
- **别让它顺手改产品代码**：跑失败时 Agent 经常"贴心地"把断言改松让测试变绿，提示词里必须明确：只准改测试，不准改断言语义。

## 可复用建议

1. 把测试规范做成常驻 skill / 提示词模板，一次写好反复用；
2. 每个旅程单独开会话，别混上下文；
3. Agent 生成的测试第一周全部人审，稳定后抽样审；
4. 每个测试记录"来源旅程"链接，回归出问题时方便追溯。

## 总结

Agent 写 E2E 的价值不在"全自动生成"，而在两处：冷启动时把写测试的成本压到可接受，日常维护时把失败分类前置。把它当带工具的实习生管理——给规范、限定迭代次数、守住 review 关卡——得到的测试质量比想象中稳。比一键生成多花半小时，但换来的是敢进主干的测试。
