## 背景

做 Agent 开发，我的信源基本靠 RSS：项目博客、release note、几份技术 newsletter。RSS 结构稳定、没有算法推荐，但量一上来根本读不完。诉求很朴素：每天固定时间拉取新文章，AI 摘成几句话，按主题归档进笔记库，值得精读的单独标出来。

## 问题

直接把 feed 丢给 LLM 有三个坑：很多源只给摘要不给全文，摘要的摘要没有价值；每天几十上百条，全量过模型成本不可接受；同一篇会在多个源重复出现，不去重输出很脏。

## 做法

管线拆成五步，由 OpenClaw 定时 Agent 驱动，每步一个独立 MCP tool，方便单独替换：

1. **拉取**：cron 触发，读配置文件里的 feed 列表，解析出条目；
2. **清洗**：HTML 转纯文本，去掉导航和广告残留；只有 link 的条目再做正文提取，这一步决定摘要质量的下限；
3. **去重**：URL 归一化（去 utm 参数、统一协议）后取 hash，与近 30 天历史比对，命中直接跳过；
4. **摘要**：分层处理。小模型按条目打分，低分合并成一行“今日其他更新”；高分的用大模型按固定 JSON schema 输出一句话结论、三个要点、是否值得精读及理由；
5. **分发**：按主题写入本地 Markdown 目录，精读项推送到 IM webhook；摘要与原文 URL、清洗后全文一起存档，方便回溯。

## 踩坑点

- **正文提取不万能**：SPA 站点用 readability 拿到的是空壳。低于 200 字就走无头浏览器兜底，仍失败就标记“仅标题”，不硬编摘要——宁可少一条，不要一条幻觉。
- **长文截断失真**：release note 动辄上万 token，头部截断会丢关键变更。超长条目改为分段摘要再合并。
- **去重必须归一化 URL**：早期只比原始 URL，同一篇换追踪参数就被当成新文章，重复推了一周才发现。
- **模型会自由发挥**：prompt 不约束时，摘要里出现原文没有的结论。后来要求每个要点附原文片段作依据，生成后做包含性校验，不合格丢弃重试。
- **feed 会挂**：某源证书过期让整条管线崩过。现在单源失败只记日志、不影响其他源，连续失败 3 天进“待清理”清单提醒人工处理。

## 可复用建议

- 配置驱动：feed 列表、阈值、模型选择都在配置里，换信源不动代码；
- 结构化输出 + 校验，比自由文本可靠得多，也方便下游归档和检索；
- 粗筛 + 精读的分层摘要是这个场景性价比最高的成本优化，粗筛模型可以很便宜；
- 保留原文和中间产物——AI 摘要一定会出错，回溯成本决定了这条管线敢不敢长期用；
- 每步做成独立工具/插件，任何环节都能单独升级。

## 总结

跑了一个多月，日均处理 60~80 条，实际推给我的精读项约 5 条，token 成本可忽略。它没有让我“了解更多”，反而让我敢退订更多低质量源——因为验证过覆盖率。对 OpenClaw 用户来说，这是个练手价值很高的场景：调度、工具调用、结构化输出、容错，Agent 开发的核心动作它全占了，而且反馈真实、立竿见影。
