## 背景

用 Agent 产出技术内容后，发布是第二段工程。同一篇 Markdown 要去静态博客、公众号、知乎/掘金、GitHub README，而各平台方言不同：公众号只收内联样式的 HTML 且外链会被吞，Hugo 要 frontmatter，知乎对表格和脚注支持有限。每发一篇手改一遍不现实，需要一条管线。

## 问题

实际是两类问题叠加：

1. **平台方言**：标题、代码块、表格、图片、脚注、公式的支持程度各家不一。
2. **AI 输出漂移**：模型不会稳定遵守“只用 GFM”这类约束，会混入行内 HTML、自造 frontmatter、写相对路径图片、塞进幻觉链接。

如果直接把模型输出喂给各平台适配器，错误会逐层放大。

## 做法

核心思路：先把生成收敛到一种受限方言，再做 AST 级适配；禁止用正则对原文做全局替换。

1. **约束生成**。在 Agent 的系统提示里限定方言：只用 ATX 标题、GFM 表格、fenced code、绝对 URL 图片。生成后立刻跑 markdownlint 加自定义规则（比如禁行内 HTML），不过就触发修复重试，别让脏数据进管线。
2. **规范化**。用 remark 把文本 parse 成 mdast，统一标题层级、脚注转文末列表、图片路径补全为绝对地址。所有变换都作用在 AST 上。
3. **平台适配器**。每个目标平台一个纯函数：
   - 博客（Hugo）：注入/校验 frontmatter；
   - 公众号：mdast 转带内联样式的 HTML，链接降级为文末引用，代码块用预着色 span；
   - 掘金/知乎：保留 Markdown，但替换不支持语法，表格降级为列表。
   
   适配器只读 AST、只输出字符串，方便写单测和快照。
4. **校验与预览**。发布前跑链接检查和图片可达性检查；公众号走草稿箱接口先传草稿，人工确认排版再发。CI 里对所有目标平台做 dry-run。

在 OpenClaw 里，建议把“规范化 + lint + 修复”包成一个 skill，把“传草稿/发布”做成 MCP 工具：Agent 只负责内容与编排，格式细节交给确定性代码。

## 踩坑点

- **正则处理嵌套代码块**：删行内 HTML 时一遇到嵌套 fence 就误伤，必须走 AST。
- **公众号外链静默丢失**：平台不会报错，链接就是没了；脚注化必须在适配器里做。
- **图片托管**：公众号编辑器抓不到部分外链图，要么走素材接口上传，要么用稳定图床并保留 alt 兜底。
- **frontmatter 漏进正文**：模型有时自己写 `---` 块，parse 前先剥一遍。
- **数学公式**：KaTeX、MathJax、平台渲染各说各话，非必要不用，必要就单独映射。

## 可复用建议

- 维护一张**平台能力矩阵**（表格/脚注/HTML/公式/图片），适配器行为按矩阵对齐。
- 方言约束写成**可执行的 lint 配置**，不要只躺在 prompt 里。
- 适配器保持**纯函数 + 快照测试**，新增平台不动存量逻辑。
- 图片从生成阶段就用绝对 URL 和稳定图床，这是多平台复用的前提。

## 总结

这条管线的关键不是“格式转换”本身，而是把格式约束**前置到生成阶段**、把转换**下沉到 AST 层**。Agent 负责内容与编排，格式适配交给可测试的纯函数，多平台发布就从体力活变成一个普通的工程问题——有 lint、有测试、有 dry-run，坏了也知道坏在哪一层。
