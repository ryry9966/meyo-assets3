## 背景

订阅源越加越多，真正读进去的时间越来越少。RSS 看似老旧，却是少数完全可控的协议：格式标准、无算法干预、随时增删。我用 OpenClaw 的定时 Agent 加 MCP 工具搭了一条管线：每天早上抓取过去 24 小时的订阅内容，过滤、去重、生成摘要，推进自己的聊天频道。跑了三周多基本稳定，把做法和坑记录一下。

## 问题

直接做会遇到三个现实问题：

1. 原始 RSS 噪音大，有的源一天几十条，全喂给模型既贵又没重点；
2. 大量 feed 只有截断的 summary 字段，直接摘要会丢关键信息；
3. 摘要质量依赖提示词，输出格式不稳，下游解析容易崩。

## 做法

整条管线拆成五步，每步独立、可重跑：

1. **源管理**：源列表放 YAML，不写死在代码里，每个源标注类别和权重，方便后续过滤。
2. **抓取与清洗**：定时任务触发 Agent，用 MCP 的 fetch 工具拉 feed，解析标题、链接、时间。对只有摘要的源，再抓原文页做正文提取，限制 4000 字以内。
3. **过滤与去重**：本地 SQLite 存 URL 哈希做跨天去重；先用便宜模型按"相关性 0–10"批量打分，低于阈值的直接丢弃。这一步是成本的关键。
4. **摘要生成**：过滤后的条目按类别分组，每组一次调用，强制 JSON 输出：一句话摘要 + 值得关注的理由 + 原文链接。提示词里明确"只基于给定内容，不要补充外部信息"，压住幻觉。
5. **推送**：拼装成日报格式走 webhook 推到频道，中间结果同时落盘，方便回溯。

## 踩坑点

- **幻觉主要来自输入不足**：只给标题就让模型总结，它会自己编。要么喂正文，要么允许它输出"信息不足，仅列标题"。
- **结构化输出要上硬约束**：早期靠提示词求模型输出 JSON，偶尔带 markdown 围栏导致解析失败。改用支持 JSON schema 的接口参数后才彻底稳定。
- **去重前先规范化 URL**：同一链接带不同 utm 参数会出现两次，先剥跟踪参数、统一小写再算哈希。
- **成本失控点在摘要阶段**：一上来就用主模型写所有摘要，一天 token 量很可观。改成"便宜模型打分 → 高分才精读"后，成本降到原来两成。
- **feed 的边角料**：GBK 编码的老源、XML 里混非法字符的源会让解析器直接抛异常，进管线前统一做一次编码探测和字符清洗。

## 可复用建议

- **每个阶段幂等**：任何一步失败重跑，不会产生重复推送或重复摘要。
- **中间状态全部落盘**：原始条目、打分结果、摘要各存一份，出问题能定位到具体环节，换模型后也能重跑对比。
- **提示词当配置管理**：版本化存放、改动留 diff，否则调一次 prompt 等于全管线重测。
- **源配置即数据**：加源只改 YAML 不碰代码；愿意的话可以封装成插件，让社区直接复用整套配置结构。

## 总结

这条管线没有用到什么高深技术，核心就三条：分阶段、可重跑、中间落盘。AI 只负责打分和摘要两个环节，其余都是传统工程。这样拆的额外好处是任何环节都能单独替换——换模型、换推送渠道、换存储，互不影响。如果你也想收一张干净的每日简报，从三五个高质量源起步就够了，先跑通再扩源。
