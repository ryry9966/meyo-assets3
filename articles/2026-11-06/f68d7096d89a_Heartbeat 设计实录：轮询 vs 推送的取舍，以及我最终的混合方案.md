## 背景

OpenClaw 的 agent 有两条被唤醒的路径：一是 **heartbeat**——按固定间隔（默认 30 分钟）自检一轮，看 HEARTBEAT.md 里有没有待办；二是**消息推送**——聊天平台的消息、外部脚本写入的事件会立即进入会话。这正对应自动化系统的经典分野：轮询（pull）与推送（push）。最近我把自己的 agent 从纯心跳轮询改成"低频心跳 + 关键事件推送"，记录一下取舍过程。

## 问题

轮询的代价很直接：

- **延迟不可控**：30 分钟心跳意味着事件最坏要等 30 分钟才被发现；改小间隔，成本又上去了。
- **token 线性增长**：每次心跳都是一次完整推理，即使无事发生也烧 token、写会话记录。5 分钟间隔一天能烧掉几十万 token，大部分花在"确认无事"上。
- **会话污染**：空转记录塞满 session history，长会话检索质量下降。

推送的代价在工程侧：需要一个能到达 agent 的通道（端口、鉴权）；每个事件源都要自己写 glue code；可靠性自负，丢了没有兜底。

## 做法

我的结论不是二选一，而是按事件性质分流。

**1. 给任务分类。** 有明确外部触发、时效强的（CI 失败、告警、日历提醒）走推送；没有触发源、本质是"检查漂移"的（磁盘水位、项目进度、RSS 摘要）走轮询。

**2. 把心跳做轻。** 间隔保持 30 分钟甚至放宽到 1 小时，用 active hours 掐掉深夜空转：

```json
"heartbeat": {
  "every": "30m",
  "activeHours": { "start": "08:00", "end": "23:00" }
}
```

关键是让每次心跳便宜：HEARTBEAT.md 只放 3–5 条真正的检查项；无事发生时返回轻量确认（OpenClaw 的惯例是 HEARTBEAT_OK，不会投递给用户），避免每次都生成大段输出。

**3. 时效事件接推送。** 我用系统 cron + CLI 做折中：监控脚本发现异常时，直接调 openclaw CLI 向会话注入一条消息，agent 立即醒来处理。本质是"条件触发的推送"，比搭一套事件总线简单得多，也够用。

**4. 保留兜底心跳。** 推送链路可能挂——脚本崩了、网络断了。心跳 prompt 里加一条：检查最近一次成功推送的时间戳，超过阈值就告警。这样故障最多潜伏一个心跳周期。

## 踩坑点

- **按"想多勤快"而非"能容忍多大延迟"定间隔**。前者会一路调小，后者才逼你想清真实需求。
- **推送没做去重节流**。接 GitHub webhook 后遭遇 event storm，一个 PR 的一串 action 轰炸了几十条消息；后来在脚本里做 coalesce，同类事件按 5 分钟窗口合并。
- **HEARTBEAT.md 写太重**。十几条任务全塞进去，每次心跳逐条推理，token 翻了三倍。检查项要像 cron 一样克制。
- **只盯心跳不看推送日志**。推送脚本静默失败两天，靠兜底心跳才兜住；务必打点"上次成功推送时间"。

## 可复用建议

1. 经验公式：心跳间隔 ≈ 可接受的最大发现延迟，不是越小越好。
2. 已知来源走推送，未知风险用心跳兜底，二者不互斥。
3. 给每次心跳记账（做没做事、烧多少 token），一周数据自然告诉你该调大还是调小。
4. 推送入口必须鉴权 + 限流，别把 agent 会话当裸奔的 webhook 接收器。

## 总结

轮询用简单性换延迟和 token，推送用工程复杂度换实时和精准，单独用哪边都不舒服。实际部署几乎都会收敛到"低频心跳兜底 + 高价值事件推送"的混合形态。设计 heartbeat 前先问一句：这个事件的触发源在哪里？答案往往就决定了它该走哪条路。
