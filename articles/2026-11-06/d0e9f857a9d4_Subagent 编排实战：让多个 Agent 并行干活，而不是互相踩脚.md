## 背景

跑过一段时间单 Agent 循环的人，大概率遇到过这几个瓶颈：任务一多，上下文很快塞满；工具调用全程串行，一轮跑十几分钟；中途一步失败，整条链路重来。Subagent 编排就是为了解决“一个脑子干所有事”的问题——把大任务拆成若干独立子任务，交给多个子 Agent 并行执行，主 Agent 只负责拆解、分发、验收。

## 问题

举个典型场景：调研 20 个候选 MCP server 并输出对比报告。单 Agent 的做法是逐个抓文档、逐个总结，串行跑完上下文早已爆炸，后半程产出质量明显下滑。并行做法是每个子 Agent 只认领一个候选，各自在干净上下文里工作，最后由主 Agent 合并。听起来简单，实际跑起来细节一堆，很容易翻车。

## 做法

我们用的结构是“编排者 + 工人池”，与具体框架解耦，在 OpenClaw 这类支持自定义工具与子任务的 Agent 环境里都能落地：

1. **任务卡模板**。每个子任务定义成一张卡：目标、输入材料、允许调用的工具、输出 JSON schema、token 与时间预算。子 Agent 只看任务卡，不继承主对话历史。
2. **工具隔离**。通过 MCP 按任务授最小工具集：只读调研类任务不给写权限；涉及文件操作的子 Agent 绑定独立工作目录。
3. **受控并发**。用信号量把并发压在 4–8 之间（视上游限流而定），每个子任务带 run_id，日志单独落盘。
4. **契约化回收**。子 Agent 必须返回结构化结果 + 置信度 + 来源引用；编排者先做 schema 校验，再做抽样交叉验证，不合格的叶子任务单独重试。
5. **合并**由主 Agent 完成，但它只读摘要和校验结果，不碰原始过程数据。

## 踩坑点

- **把父级全量历史塞给子 Agent**：token 成本翻几倍，子任务反而被无关上下文带偏。传任务卡，别传聊天记录。
- **工具权限一刀切**：所有子 Agent 共享全量 MCP 工具，出现过子 Agent“顺手”改了共享配置的事故。权限必须按卡分配。
- **并发不设上限**：一口气拉满，撞限流 429，重试风暴叠加，成本失控。
- **合并当甩手掌柜**：子 Agent 的幻觉直接进了最终报告。结构化输出 + 抽查这道工序不能省。
- **共享状态竞争**：多个子 Agent 写同一文件互相覆盖。改成每人独立目录，最后由编排者统一落盘。
- **重试不幂等**：有副作用的任务重试会重复执行。副作用类子任务要么幂等化，要么失败即上报人工处理。

## 可复用建议

- **先串行跑通单个子任务，再并行化**。并行只是加速器，不是正确性的来源。
- **并发数取三者最小值**：任务数、限流允许值、预算允许值。
- 让每个子 Agent 自报置信度和来源，合并时对低置信度结果降权或显式标记。
- **预算前置**：单任务 token 上限、整轮 run 总上限，超限熔断，不要硬扛。
- run_id + 结构化日志留档，复盘时能还原每个叶子任务的全过程。

## 总结

Subagent 并行编排的核心不是“Agent 越多越好”，而是三件事：**上下文隔离**（子任务干净启动）、**契约化交接**（结构化输入输出）、**资源限流**（并发、token、权限都装闸门）。做到这三点，同样 20 个任务的调研，从 40 分钟串行压到 6 分钟左右，质量不降反升；做不到，并行只会更快地放大错误。
