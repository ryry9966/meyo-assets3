## 背景：能力多了之后，提示词先撑不住

用 Agent 做自动化一段时间后都会遇到同一个瓶颈：能力不是不够，而是太多。MCP server 挂上十几个、工具定义写满系统提示词、各种操作手册全量塞进上下文——结果模型每次推理都要“读完”所有内容。直接后果有三个：token 成本线性上涨；无关工具描述干扰选择，调用准确率反而下降；上下文一长，长任务中途被压缩，关键说明丢失。

OpenClaw 的 Skills 机制针对的就是这个问题。核心思路是“渐进式披露”：启动时只加载技能的元数据，正文按需读取，正文里引用的脚本和资料再按需执行。三层结构，每层只在模型确实需要时才进上下文。

## Skills 的三层结构

一个 Skill 就是一个目录，核心是一个 `SKILL.md`：

- **第一层：元数据。** 头部的 `name` 和 `description` 会被注入系统提示词，通常几十个 token。所有技能的这一层加起来，才是常驻成本。
- **第二层：技能正文。** 当模型判断当前任务与某个 description 匹配时，才用文件读取工具加载完整 `SKILL.md`。操作步骤、判断分支写在这里。
- **第三层：引用资源。** 正文可以指向同目录下的脚本、模板、参考文档，执行到相关步骤时才读取或运行。

我目前的组织方式：

```
~/.openclaw/skills/
  weekly-report/
    SKILL.md          # 元数据 + 核心流程，控制在 300 行内
    template.md       # 报告模板，正文引用
    fetch_stats.sh    # 取数脚本，正文说明依赖和用法
```

## 落地步骤

1. 在 skills 目录下建子目录，写 `SKILL.md`，frontmatter 里填 `name` 和 `description`。
2. description 从模型视角写，写清触发条件：“当用户要求生成周报或汇总 git 提交记录时使用”。这是整个机制里性价比最高的一行字。
3. 正文只写流程主干和判断分支，细节拆到引用文件。
4. 重启会话后用一个真实任务验证：观察模型是否读了正文、读取时机对不对。
5. 技能目录进 git，改 description 就像改路由规则一样对待。

## 踩坑点

- **description 写成功能介绍而不是触发条件。** 写“这是一个周报工具”，模型永远不知道什么时候该用。要写“何时使用”。
- **触发条件太宽或太窄。** “处理文本时使用”会让它抢所有任务的戏；太窄则永不触发。上线后看调用日志调两轮基本能收敛。
- **把所有内容堆进正文。** 一个 2000 行的技能文件一旦被触发，等于把成本问题原样搬回来。超过 500 行就该拆。
- **假设模型“自然会”执行脚本。** 脚本依赖什么环境变量、需要什么权限，必须在正文写清，否则模型要么不敢跑，要么跑挂。
- **同名技能的优先级问题。** 工作区技能和全局技能重名时存在覆盖关系，排查过一次才发现。命名加前缀可以避开。

## 可复用的建议

把 Skill 当“值班手册”来写：封面上只有一句“什么情况翻这本册子”，第一页是决策树，附录才是细节。另外，为每个技能维护一条最小复现的验证任务，每次改完 description 跑一遍，比肉眼审查可靠得多。

## 总结

Skills 机制的本质是把“能力描述”和“能力实现”分离成三级缓存：元数据常驻、正文按需、资源懒加载。它不增加模型能力，但决定了已有能力能不能被稳定、低成本地用上。对维护多个自动化流程的团队来说，这是少数投入一两天、长期回报明确的工程化改造。
