## 背景

AGENTS.md 是放在工作空间根目录的 Markdown 约定文件，形式上像 README，但读者不是人，而是 Agent。OpenClaw 的 Agent 每次进入一个工作空间执行任务时，会先读取这份文件，把它当作"入职手册"来理解项目。README 解释项目是什么，AGENTS.md 解释在这个项目里该怎么干活。

## 问题

没有这份文件时，常见循环是：Agent 用错包管理器、跑错测试命令、命名风格和仓库不一致、动了不该动的生成文件；你纠正一次，下次会话它又忘。把所有规矩塞进系统提示词也不合适——那是全局的，跨项目复用时会互相污染。这些信息本质上是"项目级、可版本化"的知识，应该落在仓库里，而不是对话里。

## 做法

1. 在工作空间根目录建 AGENTS.md，控制在 30–60 行。
2. 按 Agent 视角写四个块：
   - 项目一句话概览（让它先判断自己在哪）；
   - 常用命令：build / test / lint 的原样命令，可直接复制执行；
   - 代码约定：命名、错误处理、提交信息格式等硬性规则；
   - 边界：明确禁止触碰的目录（迁移文件、生成产物、密钥相关路径）。
3. 用嵌套做局部覆盖：`frontend/`、`server/` 各放一份自己的 AGENTS.md，子目录规则优先生效。前端用 pnpm、后端用 cargo 这类差异就靠它隔离。
4. 持续迭代：Agent 每犯一次错，就往文件里加一条对应规则；每月回看一次，删掉过期的。

## 踩坑点

- **写成了 README**：大段历史和背景故事对 Agent 无用，它要的是可执行的事实，不是叙事。
- **太长**：超过百行后中间内容容易被忽略。规则排优先级，宁可短。
- **指令冲突**：根文件说 pnpm、子目录说 npm，Agent 行为会变得随机。同一作用域只留一个事实来源。
- **过期规则比没有更糟**：重构后命令变了没更新，Agent 会照着旧命令跑。把 AGENTS.md 的 diff 纳入 code review，当代码对待。
- **别写密钥**：这份文件会被读进上下文，token、内网地址一律不放。

## 可复用建议

- 当配置即代码维护：进 git、走 PR、写变更说明。
- 规则必须有事故事件支撑：用"错一次加一条"的节奏补内容，不预写空话。
- 新会话做验收：让 Agent 只凭 AGENTS.md 跑通一次 lint 和 test；如果还需要你口头补充，说明手册没写完。
- 从最小集起步：命令 + 边界先落文件，风格类规则等真出错再补。

## 总结

AGENTS.md 是杠杆极高的低成本实践：把你每次重复的口头纠正，固化成持久、可版本化、可评审的指令。保持短、保持真实、保持更新，Agent 在这个工作空间里的表现会稳定得多。
