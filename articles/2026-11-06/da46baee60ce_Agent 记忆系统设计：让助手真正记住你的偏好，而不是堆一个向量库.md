## 背景

大模型本身是无状态的：每次新会话，上下文从零开始。做 Agent 自动化的人都会遇到同一个尴尬——昨天刚纠正过"测试用 pytest，别用 unittest"，今天它又默默写回 unittest。MCP 和插件生态让接入外部存储变得很容易，但"接了存储"不等于"记住了"，真正难的是记忆的写入、检索和淘汰这套工程逻辑。

## 问题：三种常见做法为什么不行

1. **全塞 system prompt**：偏好一多，token 预算爆炸，而且所有会话都背着全量记忆，无关噪声反而拉低表现。
2. **聊天记录整段进向量库**：检索回来的是对话碎片，一堆"嗯""好的"和半截句子，有效信息密度极低。
3. **"记住这个"式单条写入**：没有作用域、没有版本、没有淘汰机制，三个月后记忆库自己打架。

核心矛盾是：记忆系统必须同时回答**写什么、怎么查、什么时候删**，缺任何一环都会退化成垃圾堆。

## 做法：分层记忆 + 明确生命周期

我的方案分三层，全部落成带 frontmatter 的 Markdown/JSON 文件（便于 diff、备份、迁移），通过一个自写的小 MCP server 暴露 `write / search / forget` 三个工具。

1. **Profile 层（稳定偏好）**：语言、代码风格、常用技术栈、沟通语气。结构化 key-value，每条不超过 50 字，会话启动时全量注入，预算 500 token。
2. **Episodic 层（项目事实）**：带 scope（全局 / 项目路径）、时间戳、置信度。按"相关性 × 时间衰减"检索，预算 1500 token。
3. **Working 层**：当前会话草稿，不落盘。

写入分两条路径：用户显式说"记住 X"时直接写入；隐式路径在任务收尾时跑一次抽取，把可能长期有效的事实（如"该项目用 pnpm"）写入 episodic。同一 key 新旧冲突时按版本号覆盖；隐式事实被命中 3 次以上，提示用户确认后晋升进 profile。

## 踩坑点

- **不抽取直接入库**：对话碎片检索命中率看着高，实际全是噪声。先抽成事实句再存。
- **缺 scope 字段**：项目 A 的偏好污染项目 B，当时排查了半天。
- **只写不删**：库越大精度越差。episodic 设 90 天 TTL，`last_hit_at` 超期即归档。
- **隐式推断置信度过高**：模型从一次对话推断"用户喜欢行内注释"，错一次就固化。低置信度一律降权。
- **注入预算失控**：记忆挤占任务上下文后，助手反而变笨。预算写死在配置里，不许超。
- **没有评测**：靠感觉判断"它记住了"不可靠。我建了 20 条跨会话问答题，每次改检索逻辑都跑一遍。

## 可复用建议

- 先只做 Profile 层，结构化偏好能覆盖 80% 场景，别一上来就上向量库。
- 记忆文件保持可导出的纯文本，别锁进黑盒数据库。
- 检索先用"关键词 + 时间衰减"这种确定性打分，不够再上 embedding——先量化，再升级。
- `write` 和 `forget` 拆成两个 MCP 工具，权限可以分开控制。
- 晋升 Profile 必须有人工确认环节，别让模型替你决定"你是谁"。

## 总结

记忆系统的本质是数据生命周期管理，不是玄学：小 schema、明确的写入路径、token 预算、淘汰机制，比一个大号向量库可靠得多。先让助手稳定记住 10 条核心偏好，比试图记住一切更有价值。
