## 背景

OpenClaw 的 cron 任务本质上很简单：到点触发，把 instruction 原样交给 agent，跑完把结果发到指定位置。整个过程无人值守——没有上下文，没有人在线，也没有人回答 agent 的追问。

但我们写交互式 prompt 写惯了，很容易把 cron instruction 当成“给助手留的一句话提醒”。这在交互场景里问题不大，用户在场，缺什么可以补；但在定时任务里，instruction 就是全部。我前前后后跑了十几个 cron 任务（日报、监控摘要、数据巡检），踩过的坑几乎都源于这个认知差。

## 问题：无人值守放大了 instruction 的一切模糊之处

典型翻车现场：

- instruction 写“总结昨天的群聊消息”，agent 按自己的理解算日期，时区一偏，“昨天”就不是你想要的昨天；
- 没写输出去哪，结果默认回了主会话，凌晨三点一条长文糊脸；
- 数据源拉取失败，agent 没有失败路径可走，直接编了一份“看起来合理”的总结；
- 一条 instruction 塞了三个任务，中间一步工具调用失败，后面全断。

共同点：这些在交互式测试时都暴露不出来——因为你在场，你补足了所有缺失信息。

## 做法：按“交接单”结构写

我现在的 cron instruction 固定分五段，直接写进 instruction：

1. **时间锚点**。明确时区和相对日期的计算规则，例如“以 Asia/Shanghai 为准，‘昨天’指执行时刻往前一个自然日”。
2. **数据来源与步骤**。写清用哪个工具/MCP 调用、取多少条、什么时间范围。步骤按序号列，不要让 agent 自己编排流程。
3. **输出格式模板**。给固定骨架（概览一行 / 要点 / 异常项 / 来源），字段缺失就写“无数据”，禁止扩写和客套话。
4. **输出路由**。明确发到哪个会话/频道，或写入哪个文件。不写这条，行为取决于 gateway 的默认配置，往往不是你想要的。
5. **失败路径**。“如果数据源不可用，只输出一条包含失败原因的短消息，不要猜测内容，不要重试超过 N 次。”

另外在开头加一句通用约束：“这是一次无人值守的定时执行，没有人会回答你的问题，无法继续时按失败路径处理，不要等待。”这一句能解决 agent 试图追问导致的挂起。

一个日报任务的骨架大致是：

> 无人值守任务，时区 Asia/Shanghai。步骤：1) 调用 xxx 拉取过去 24 小时数据，上限 100 条；2) 按模板输出：概览一行 / 三个要点 / 异常项 / 数据来源；3) 若拉取失败或为空，只输出失败原因，不编造。结果发送到 #daily 频道。

## 踩坑点

- **相对时间不锚定**。“今天”“本周”都要给出计算规则，否则 agent 自由发挥。
- **没定输出上限**。“总结一下消息”不限条数和时间范围，高峰期一次跑掉大量 token。
- **任务粘连**。一条 instruction 干多件事，拆成多个 cron 更稳，单点失败不影响全局。
- **静默失败**。必须给失败路径，且让失败消息本身可识别（固定格式），方便回头排查。
- **频率与产出不匹配**。每 15 分钟跑一次的宽泛摘要，产出没人读，纯属噪音。先低频跑稳再提频。

## 可复用建议

- 写完做一次“空降测试”：假装第一次看到这条 instruction，不加任何解释能不能一次跑对。
- 把高频任务抽象成模板：时间锚点 + 步骤 + 输出模板 + 路由 + 失败路径，五个字段填空即可。
- 上线前手动触发一次，看日志确认工具调用和路由符合预期，不要只看最终输出“像不像样”。
- instruction 改动保留版本意识，出问题时你能对比“上次到底改了哪句话”。

## 总结

Cron instruction 的本质，是给一位不能提问的同事写交接单：时间、来源、步骤、格式、出路、失败怎么办，一个都不能少。交互式 prompt 可以靠对话兜底，定时任务只能靠 instruction 自身的完备性。写之前先想清楚一件事——agent 拿到这句话之后没有任何外援。做到这一点，你的 cron 稳定性会上一个台阶。
