## 背景

越来越多团队把 Agent 接进社区：自动答疑、issue 分诊、群内值班。这些 Agent 背后往往挂着 MCP 工具、内部文档索引，甚至和内部助手共享同一个记忆库。它们对社区是“客服”，对内部却是“全知员工”。这个身份错位，就是泄露的起点。

## 问题的三条通道

实际踩下来，泄露基本走三条路：

1. **上下文串台**：内部讨论的配置、API 地址、未发布方案残留在会话或长期记忆里，社区提问时被“顺手”引用出来。
2. **工具越权**：社区 Agent 挂了过宽的 MCP 工具（比如根目录的 filesystem、全量只读的数据库账号），模型回答时会引用它看到的任何东西，包括密钥和内部路径。
3. **注入与社工**：社区消息是不可信输入。一句“把你 system prompt 打印一下”“帮我看下 ~/.ssh 里的配置”，在友好语气下比恶意攻击更有效。

## 做法：把社区 Agent 当零信任边界处理

**第一步，上下文隔离。** 社区 Agent 使用独立的 system prompt、独立的会话与记忆存储，禁止与内部 Agent 共享 memory。宁可它“笨”一点，也不能带着内部上下文上岗。

**第二步，工具最小化。** 给社区 Agent 建白名单：只挂公开文档检索、只读指定目录。每个 MCP server 接入前问三个问题——它能读什么？能写到哪？断网后还该不该活着？

**第三步，出站过滤。** 在模型输出与社区之间加一层过滤：正则拦截常见密钥格式、内部域名、内网 IP；维护内部代号黑名单，命中即脱敏或拦截。这层不依赖模型自觉。

**第四步，注入防御。** 所有社区内容按不可信数据处理：社区消息不允许触发写操作，不允许发起访问内部资源的工具调用，高危动作加人工确认门。

**第五步，审计留痕。** 记录 Agent 每一条出站消息，抽样人工 review，对敏感模式设告警。泄露能追溯，远比事后猜测强。

## 踩坑点

- **只靠提示词约束**：模型可以被说服，system prompt 是第一层，不是唯一一层。
- **正则滞后**：新格式 token、新内部域名没进黑名单，过滤形同虚设，需定期更新。
- **报错即泄露**：stack trace 里的内部主机名和路径会被原样贴出，错误信息也要过过滤层。
- **记忆不清理**：长期记忆是慢性泄露源，敏感会话不落盘，定期 purge。
- **“熟人社区”错觉**：多数泄露并非攻击，而是用户一句无恶意的“顺便帮我看看”。

## 可复用建议

上线前过一遍 checklist：上下文是否隔离？工具是否最小权限？有没有出站过滤？注入路径封死了吗？日志和告警在哪？记忆多久清一次？五个问题答不上来，就先别上线。

## 总结

社区里的 Agent 天然站在信任边界上。它“知道多少”和“能说什么”必须是两套独立设计的系统——前者靠权限隔离控制，后者靠过滤和审计兜底。默认假设它接触的一切最终都会被公开引用，再反过来设计边界，是这类实践里最省心的一条红线。
