# AI Agent 的错误恢复：外部 API 挂了怎么办

## 背景

跑过自动化 Agent 的人都有体感：你自己的 prompt 和编排写得再好，挂的往往是别人。LLM 供应商、搜索、天气、数据库、第三方 MCP 工具——任何一个 5xx 或超时，都可能让一个跑了十几分钟的长任务直接报废。在 OpenClaw 里，工具调用大多经过 MCP / 插件层，这层有没有恢复策略，决定了你的 Agent 是「偶尔抽风」还是「基本可靠」。

## 问题

没有恢复策略时，常见四种翻车姿势：

1. **原地硬重试**：同一秒连打 20 次同一个挂掉的接口，把限流打成封禁；
2. **幻觉补全**：工具返回一段报错文本，模型把报错当数据，编出一个「看起来成功」的结果继续往下跑；
3. **无限循环**：失败 → 重试 → 失败，token 和钱一直在烧；
4. **状态丢失**：任务跑到第 7 步挂了，重跑从第 1 步开始，前面写了一半的数据变脏。

## 做法

我们的核心原则：**把错误当输入，而不是当异常**。具体分五步：

**1. 先分类，再行动。** 错误分三类：瞬时（超时、429、5xx）、永久（401、404、参数错）、语义（返回 200 但内容不对）。第一类可重试，后两类重试没有意义，只会烧钱。

**2. 指数退避 + 抖动。** 间隔 1s → 2s → 4s，上限 30s，加随机抖动，最多 3~5 次。关键是设**重试预算**：整个任务最多重试 N 次，超了就停，不允许模型自己决定「再试一次」。

**3. 熔断。** 同一个工具连续失败 K 次就熔断，直接走降级路径，冷却期后半开探测。别让 Agent 每一轮都去撞一个已知挂掉的接口。

**4. 给模型返回结构化错误。** 工具层不要抛裸异常，返回固定 JSON，例如 `{"ok":false,"error":"timeout","retryable":true}`。模型看到 `retryable` 为 true 才允许发起重试，否则必须向用户如实报告失败，而不是自由发挥。

**5. 检查点 + 幂等。** 长任务每完成一步就落盘 checkpoint，恢复时从断点续跑；所有写操作带 idempotency key，重试不会造成重复下单、重复发消息。

## 踩坑点

- **非幂等操作千万别自动重试。** POST 下单超时，你不知道服务端到底成没成功，盲目重试就是双倍扣款。先查单，或带幂等键。
- **只退避不抖动。** 多实例同时重试会形成惊群，把正在恢复的服务再次打挂。
- **报错文本被模型当数据。** 这是最常见的幻觉来源：工具返回一段带数字的错误页，模型直接引用了里面的「金额」。结构化错误返回是解药。
- **熔断粒度太粗。** 按「整个供应商」熔断和按「某个具体工具」熔断是两回事，粒度错了会把没坏的也一起降级。
- **超时比报错更危险。** 不设超时的调用会永远挂着，Agent 假死。每个工具调用必须有显式超时。

## 可复用建议

- 在工具 / MCP 封装层**统一**处理错误，别散落在各处 prompt 里；
- 给每次任务设**错误预算**：失败次数、重试次数、token 上限，超了就转人工；
- 至少准备一条降级路径：备用供应商、缓存结果，或者干脆明确告诉用户「我失败了」；
- 定期回看线上错误日志，你会发现 80% 的故障来自同一个接口——优先治它。

## 总结

Agent 的可靠性不在 prompt 写得多漂亮，而在它失败时的行为：能不能快速识别、能不能不烧钱地重试、能不能诚实地说「我做不到」。把错误恢复当成产品能力来设计，而不是事后补丁，Agent 才敢被放进无人值守的自动化里。
