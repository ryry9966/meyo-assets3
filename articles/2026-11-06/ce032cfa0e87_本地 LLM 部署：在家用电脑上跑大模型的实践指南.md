## 背景

玩 Agent 和自动化的人迟早会撞上这个问题：MCP 工具编排、日志摘要、批量结构化抽取，这些流程一天要打几千次模型调用。走云端 API，一是账单难看，二是不少场景数据根本不适合出网。本地部署不是要替代云端，而是补上"高频、私密、离线"这三块短板。

## 问题

实际动手前，我遇到的三个核心疑问：

1. 家用显卡到底能跑多大的模型、什么量化档位？
2. 模型本地跑通了，接进 Agent 后 tool calling 频繁掉链子怎么办？
3. Agent 的 prompt 天生就长，上下文一拉大显存就爆。

## 做法

**第一步：摸清硬件底数。** 显存是硬约束，经验值大致是：7B 模型 Q4_K_M 量化约 5-6GB，14B 约 10-12GB，32B 要 20GB 以上。对应关系很简单——8GB 卡选 7B，16GB 卡选 14B，24GB 卡可以碰 32B 但上下文要省着用。

**第二步：选运行时。** 求快用 Ollama，一条命令拉模型就能跑；想精细控制参数和性能，用 llama.cpp 直接编译。两者都提供 OpenAI 兼容端点，这一点很关键——OpenClaw 的模型配置里把 base_url 指到本地端口，随时可以和云端配置互换。

**第三步：选模型。** 中文任务优先 Qwen 系列、GLM、DeepSeek 蒸馏版，社区量化包齐全。起步统一 Q4_K_M，够用再升级。

**第四步：接入 Agent 并压测。** 先用简单问答冒烟测试，确认 API 格式没问题；然后把真实 MCP 工具链挂上，用自己业务的真实 trace 跑一遍，记录 tokens/sec 和任务成功率，而不是看跑分榜单。

## 踩坑点

- **上下文默认值是个陷阱。** Ollama 默认 num_ctx 很小，Agent 一挂长 system prompt 就静默截断，表现为"模型好像忘了工具列表"。调大之后 KV cache 显存翻倍涨，14B + 16K ctx 在 16GB 卡上直接 OOM。
- **小模型的 tool calling 是重灾区。** 7B 级别常见参数格式错、漏字段、幻觉出不存在的工具名。对策：一次只暴露 3-5 个工具，打开结构化输出约束，工具描述写短写死。
- **量化的损失因任务而异。** 闲聊几乎无感，但代码生成和 JSON 输出对精度敏感，Agent 场景建议至少 Q6。
- **别信榜单。** 同一模型在你自己的任务分布上表现可能天差地别，唯一可信的是自己那套测试集。

## 可复用建议

1. **路由模式。** 本地模型承接高频低成本任务（分类、摘要、格式转换），复杂推理回落云端。Agent 框架里配两个模型名，按任务类型路由即可。
2. **配置版本化。** 模型名、量化版本、num_ctx 全写进配置文件进 git，别在 UI 里手点，不然换台机器全部重来。
3. **固化冒烟测试集。** 攒 10 条真实任务 trace，每次换模型跑一遍，五分钟内判断"能不能上岗"。

## 总结

家用电脑跑 7B-14B 是完全现实的，但要摆正定位：本地模型是 Agent 流水线里一个便宜、私密、离线的执行单元，不是前沿模型的替代品。把简单的活留给它，把难的活路由出去，这套混合架构才是可持续的。先跑起来，再逐步把更多环节从云端迁回本地，是最稳的路径。
