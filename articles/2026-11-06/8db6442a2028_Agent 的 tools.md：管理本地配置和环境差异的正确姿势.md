## 背景

跑 OpenClaw 这类本地 Agent 有个常见现象：同一个任务，在这台机器上顺顺当当，换一台就翻车。原因不难猜——system prompt 只有一份，环境却各有各的样子。macOS 上 `sed -i` 要带参数，Linux 上不用；`python` 有的机器指向 3，有的还挂着 2；包管理器 brew、apt、pnpm 各管一摊。Agent 每次都靠"试探"搞清楚环境，费 token，还容易试错。

## 问题

更麻烦的是这些环境知识散落在各处：有的写在 system prompt 里，有的留在聊天记录里，有的依赖 agent 自己的"记忆"。结果是：

- 换机器、重装系统、清理 workspace 之后，积累的环境认知清零；
- 配置无法版本管理，也没法在多台机器间同步；
- 信息过期没人发现，agent 拿着半年前的路径继续自信输出。

## 做法

我的方案是把环境知识收敛到 workspace 根目录的 tools.md，让 agent 每次启动都能读到。核心思路只有一条：**机器级"事实"用脚本生成，个人"约定"手写维护**。

具体分四步：

1. **分层**。全局 tools.md 只放机器级事实：OS、shell、包管理器、常用 CLI 及版本、默认工作目录、环境变量命名约定。项目级差异（依赖、命令、端口）放到各项目自己的 README，不往全局塞。
2. **生成事实段**。写一个几十行的 shell 脚本，用 `which`、`--version` 之类把当前环境扫一遍，输出到 tools.md 里标记为 generated 的段落。文件头部明确写"此段由脚本生成，请勿手改"。
3. **手写约定段**。在生成段之上手写少量内容：这台机器的怪癖（比如 WSL 下 Docker 的路径映射）、命名约定、明确禁止的操作。控制在几十行以内。
4. **纳入版本管理**。tools.md 和生成脚本一起放进 dotfiles 仓库，新机器 clone 下来跑一遍脚本，几分钟重建全部环境事实。

一个让这件事持续生效的细节：把"发现新工具或环境变化时，先提议更新 tools.md 再使用"写进 agent 的系统规则。agent 自己参与维护，文档才不会烂掉。

## 踩坑点

- **写太长等于没写**。tools.md 超过两三百行，agent 检索质量会明显下降。细节下放到项目级文档，全局只留事实和约定。
- **过期比缺失更危险**。agent 对文档是无条件信任的，旧路径比没有路径更容易引发连环错误。生成段靠脚本兜底，手写段建议每次改完环境顺手 review。
- **别把密钥写进去**。tools.md 会进 git，也会被模型完整读进上下文。密钥走环境变量，文件里只写变量名约定。
- **生成脚本不要覆盖手写段**。我的做法是脚本只写生成段，两种段落之间用固定标记隔开，脚本按标记定位，避免误删手写内容。
- **多机同步先跑脚本再合并**。直接 `git pull` 可能造成"文档描述的是另一台机器的事实"的错位。

## 可复用建议

- 一条判断标准：能在终端用命令查到的，都交给脚本生成；只能靠人决定的，才手写。
- 全局文件保持精简（我的一直在 80 行以内），宁可少而准。
- 如果跑的 MCP 服务多，可以在 tools.md 里附带一份"已装服务及启动方式"清单，排查 MCP 连接问题时省很多事。

## 总结

tools.md 本质上不是文档，而是 agent 与本机环境之间的契约：事实部分由脚本保证与真实环境一致，约定部分由人负责决策。成本是一次性的脚本加几十行手写，换来的是 agent 在任何一台机器上都能低成本拿到准确的环境上下文。比起把所有东西塞进 prompt，这种方式可版本管理、可同步、可审计，也更符合"让 agent 读文件而不是猜环境"的工程习惯。
