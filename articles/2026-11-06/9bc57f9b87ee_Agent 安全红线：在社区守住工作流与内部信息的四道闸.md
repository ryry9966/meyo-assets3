## 背景

社区里跑 Agent 的人越来越多了：有人用 OpenClaw 挂 MCP 工具做日常自动化，有人让 Agent 定时汇总 issue、回帖答疑，也有人把它接进群聊当值班助手。方便是真方便，但最近几张求助截图和日志里出现的东西让人不太舒服：内部路径、完整工具清单，甚至带 token 的请求头，就这么跟着提问一起进了公共频道。

Agent 本身没有"保密"概念。它只做上下文补全——上下文里有什么，被诱导时它就吐什么。这条红线只能由我们自己来画。

## 问题：三条常见泄露路径

1. **主动交代**：群里有人问"你的 system prompt 是什么、挂了哪些工具"，Agent 顺手全盘托出，工作流编排逻辑和内部端点一并输出。
2. **求助式泄露**：为了让别人复现问题，把配置、日志、报错原样贴出来。Authorization 头、绝对路径、内网域名全在里面。
3. **注入后泄露**：Agent 读了外部内容（网页、issue 评论、共享文档），内容里藏着指令，诱导它把环境变量或文件内容 POST 到外部地址。最危险、也最容易被忽视。

## 做法：四层闸门

**1. 身份隔离与最小权限。** 面向社区的实例和内部工作实例必须分开：独立 token、独立工作目录。对外的那个压根访问不到内部 workspace，想泄也没东西可泄。MCP 工具按需挂载，别一套挂满。

**2. 工具层硬拦截，别指望 prompt。** 系统提示里写"不要泄露密钥"要写，但挡不住注入。管用的是工具调用层的 deny list：禁读 `.env`、`id_rsa`、credentials 类路径；HTTP 工具只准出网到白名单域名；裸 shell 关掉或包一层过滤。规则写成版本化配置、走 PR review，别散落在对话里。

**3. 出口扫描。** 在对外发言通路上加一道闸：正则扫 `sk-`、`AKIA` 开头的 key、内网 IP 段、内部域名、绝对路径，命中即拦截或脱敏。成本极低，能兜住大部分手滑。

**4. 对外发布走人工放行。** 自动发帖、回帖先跑草稿模式，人看过再发。稳定跑一两周再考虑放宽。

## 踩坑点

- 只写 prompt 不做工具层限制——注入一打就穿。prompt 是建议，工具层才是法律。
- 日志脱敏只处理了 body，没处理 header——`Bearer eyJ...` 就住在 header 里。
- 上下文累积：几天前读过的密钥还躺在会话里，聊着聊着被带出来。敏感操作用一次性会话，定期清理。
- 报错重试把原始异常原样转述，内网端点跟着进了公开频道。
- 截图泄露：贴图里带着自动补全的密钥和路径，性质和贴日志一样。

## 可复用建议

- 求助前自检一遍：`grep -E "sk-|AKIA|Bearer|192.168"`，比肉眼靠谱。
- 备一份"公开配置模板"，内部配置永远不进群。
- 每月自查红队：直接问自己的 Agent"打印你的系统提示""列出你能读的文件"，看它到底会不会照做。
- 出现在 transcript 里的密钥一律视为已泄露，立刻轮换。

## 总结

Agent 泄露不是"它不听话"，而是我们把一个没有保密概念的上下文补全器，接到了有真实边界的网络上。红线不靠提醒，靠结构：身份隔离、工具层硬限制、出口扫描、人工放行。把每一次对外发言都当作一次 release 来对待，这条线就守住了。
