## 背景

给 Agent 配上 shell 执行能力之后，最常见的担忧不是“它不够聪明”，而是“它太敢做了”。一条理解偏差的指令、一次通配符展开、一个解析错的工作目录，`rm -rf` 就可能落在真实数据上。

OpenClaw 的思路很直接：不指望模型自觉，而是让破坏性操作在结构上无法触达宿主机。

## 问题拆解

只在 prompt 里写“请不要删除文件”基本无效，原因有三：

1. 模型对路径的判断是概率性的，相对路径、软链接、大小写都可能让它算错落点；
2. MCP 工具和插件默认跑在与宿主同一套文件系统上，权限边界形同虚设；
3. 自动化流水线里没有人在环，一条错误命令会被放大成批量事故。

## 做法：四层防线

**第一层：沙箱容器。** sandbox mode 设为 `all` 或 `non-main` 后，agent 的 exec 和文件写入都发生在 Docker 容器里。容器内的文件系统是隔离的，宿主机上除了 workspace 的 bind mount，其他路径在 agent 的世界里根本不存在。

**第二层：最小挂载。** 只把 workspace 目录挂进容器，并区分读写：配置只读，工作区可写。agent 想删 `/etc`？那个路径它看不见。

**第三层：exec 审批。** 高危命令模式（`rm`、`dd`、`mkfs` 等）配置为需人工确认。审批是兜底，不是主力——前两层挡掉绝大多数情况，审批只处理漏网的长尾。

**第四层：会话隔离。** 不同 session 各自独立的容器生命周期，一个会话里误操作污染的环境不会泄漏到另一个会话。

验证方法很简单：在沙箱内让 agent 执行 `ls /` 和 `touch /tmp/x`，再回宿主机确认 `/tmp/x` 不存在。

## 踩坑点

- **挂载贪宽**：图省事把整个 home 挂进去，沙箱就退化为摆设。挂载列表要定期 review。
- **主会话误区**：默认 `non-main` 模式下主会话不在沙箱内。跑自动化任务务必显式开 `all`，别依赖默认值。
- **依赖膨胀**：agent 在沙箱里反复装包，容器越来越大越来越慢。正确姿势是把依赖固化进沙箱镜像定义，重建而非增量安装。
- **审批疲劳**：审批太频繁，人就开始无脑点确认。把白名单收敛到真正的高危模式，其余交给沙箱。

## 可复用建议

1. 挂载最小化：宁可 agent 抱怨找不到文件，也别让它看见不该看的东西；
2. 沙箱镜像纳入版本管理，依赖变更走 review；
3. 备份策略独立于沙箱——沙箱防误删，不防磁盘损坏；
4. 定期做一次“故意让它删文件”的演练，验证防线真的在生效。

## 总结

OpenClaw 之所以能放心让 agent 动手，不是因为它更聪明，而是因为错误操作的可达半径被物理性地压缩到了 workspace 里。信任来自隔离与审批的组合，而不是来自一句 prompt。这套分层思路搬到你自建的 agent 系统里，同样适用。
