## 背景

我长期订阅 60 多个 RSS 源：技术博客、安全公告、几个常用项目的 release notes。RSS 的好处是源可控、没有算法推荐，坏处是量上来之后根本读不完。两个月前我把「读 feed」拆成了两层：**定时管线**负责抓取、清洗、生成摘要；**OpenClaw Agent** 负责在我提问时基于摘要做检索和追问。跑下来日均 40~80 条输入，成本稳定，效果可用。这里记录一下做法和踩过的坑。

## 问题

直接「拿 RSS 喂给 LLM」有三个硬伤：

1. 多数源只给 summary 或前几百字，摘要等于二次转述；
2. 全文塞进去 token 成本不可控，且大量重复话题；
3. feed 内容是外部不可信输入，直接拼进 prompt 有注入风险。

## 做法

整体分四步，脚本 + cron 即可，不需要常驻服务。

**1. 抓取与归一化。** 用 Miniflux 或自建脚本定时拉 feed，每条保留 guid、链接、发布时间、原始 XML。落库用 SQLite 就够，按 `hash(url + title)` 建唯一索引，天然去重。只输出摘要的源，用 readability 类库抓正文兜底。

**2. 清洗与分批。** 过滤超短条目（通常是广告占位）、按 URL 去掉转载、按主题分组打包。每批控制在 6~10 条、总 token 设明确上限，超出就拆批。这一步是成本的关键，比换模型有效得多。

**3. 摘要生成。** 强制结构化输出 JSON：`{title, one_line, key_points[], category, confidence}`。prompt 里明确要求「正文为空时输出 insufficient_content，不要编造」。低置信度条目只保留原始链接，不生成摘要。

**4. 分发与交互。** 摘要落库后有两个出口：一是 cron 每天汇总成 digest 推给自己（邮件/TG 均可）；二是把摘要库封装成一个 MCP tool 挂给 OpenClaw Agent，日常直接问「今天某方向有什么值得看的」，Agent 调 tool 检索、给引用链接，需要细节时再回到原文。

## 踩坑点

- **注入问题最容易被忽略。** 两道防线：正文统一包在明确标记的数据段里；输出前校验 JSON schema，出现「忽略之前指令」类异常字段直接丢弃该条。
- **release notes 类源更新少但价值高**，按天聚合会被淹没，我单独按仓库分组、按周输出。
- **中文源全文抓取经常失败**，readability 对部分站点抽出的是空正文。必须对「抓取成功但正文 < 200 字」的条目降级处理，而不是照常送摘要——这是早期幻觉的主要来源。
- **guid 不总稳定**，个别源同一文章换 guid 重发。除了 URL hash，再加一层标题相似度去重，简单编辑距离就够。

## 可复用建议

- 把「抓取、清洗、摘要、分发」做成四个独立步骤，中间产物全部落库。任何一步挂了都能重跑，不要写成一个巨型脚本。
- 成本控制优先级：**减少输入 > 缓存 > 换便宜模型**。摘要任务对模型要求不高，别在这上面花冤枉钱。
- 所有摘要保留原文链接和抓取时间戳。AI 摘要只用来排「阅读优先级」，不做事实来源。
- 如果接 OpenClaw，MCP tool 的返回结构务必带 `source_url`，让 Agent 能给出可核对的引用，而不是空口转述。

## 总结

这套管线没有引入新框架，核心就是 cron + SQLite + 结构化输出，外加一个 MCP tool 把结果接回 Agent。它解决的不是「读得更多」，而是「把有限的阅读时间花在值得的条目上」。两周迭代下来，真正点开原文的比例从约 15% 降到 6%，但留下来的几乎都会读完——对我来说，这就是管线在干活的信号。
