## 背景

单 Agent 串行跑长任务的老问题：让它"调研这 10 个模块的鉴权实现并给出对比"，它会一个个读文件、调 MCP 工具、把中间结果贴进上下文。跑到最后，窗口里塞满了原始代码和搜索输出，早期信息被稀释，总结质量肉眼可见地下降，墙钟时间还长。

Subagent 编排是针对这个问题的结构化解法：主 Agent 只做拆解、调度和汇总，把每个有边界的子任务交给一个拥有独立上下文的 subagent 去跑，跑完只回传压缩后的结论。

## 问题

实际落地时会撞上三堵墙：

1. **上下文污染**：中间产物堆在主上下文里，真正重要的约束被挤出窗口；
2. **串行等待**：明明互不依赖的子任务在排队；
3. **故障耦合**：一个子任务抛异常，整条链路报废。

## 做法

**第一步：判定可并行性。** 只有互不依赖的子任务才值得 fan-out。一个土办法：交换两个子任务的执行顺序，如果结果不受影响，才能并行；否则那是 pipeline，老老实实串行。

**第二步：给每个 subagent 定契约。** 五个要素写进 prompt：角色、输入（明确的文件路径/数据）、输出 schema（比如 JSON：`findings`、`artifacts`、`open_questions` 三个字段）、预算（最大步数 / token 上限）、禁止动作（不许 commit、不许对外发消息）。

**第三步：用确定性代码做调度。** 模型负责"怎么切"，代码负责"怎么跑"：并发度限 3–5，每个子任务设超时，失败重试一次，仍失败就打上显式标记返回部分结果，绝不静默吞掉。这段调度逻辑在 OpenClaw 里可以直接做成一个 skill 或插件，再作为工具暴露给编排 Agent 调用。

**第四步：压缩回传。** Subagent 把完整产物落盘，回传的只有摘要和产物路径。编排器基于摘要做汇总。任何时候都不要把完整 transcript 塞回主上下文。

## 踩坑点

- **回传不设上限**：subagent 回来一篇 3000 字的"摘要"，主上下文照样爆炸。schema 校验里加长度上限，超了打回重压。
- **并行写冲突**：两个 subagent 改同一个文件必然出事。要么按目录分区，要么只读并行、写入串行。
- **假独立**：两个"互不依赖"的任务都要先读同一份全局配置——把公共读取上提到编排器，作为输入下发。
- **重试风暴**：无预算的重试会让 token 账单起飞，按 run 设总预算。
- **编排开销反噬**：子任务少于 3 个就别拆了，spawn 和汇总的开销可能比省下的时间还多。

## 可复用建议

- Subagent prompt 套上面那个五要素模板，别让它自由发挥；
- 编排器保持"笨"：切分靠模型，并发/超时/重试靠代码；
- 传引用不传正文：产物落盘、路径回传；
- 每次运行记 `run_id`，每个子任务的输入输出单独落盘，事后 diff 排查非常省事；
- 上线前后盯三个指标：墙钟时间、token 消耗、失败率。没有改善就回退串行，不丢人。

## 总结

Subagent 编排的本质是**上下文隔离 + 有界并发**，不是"Agent 越多越快"。真正的收益来自干净的任务边界和压缩的结果回传。建议从两个真正独立的子任务开始试，把调度写成确定性代码，验证指标有改善后再逐步提高并发度。
