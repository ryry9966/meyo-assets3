## 背景

OpenClaw 默认用一个主模型跑所有会话，大多数人起步都是这么配的。跑了几个月后两个问题会同时出现：一是批量摘要、会话打标这类“体力活”烧 token，账单涨得比预期快；二是一些内网日志、客户数据，从安全角度根本不该往云端送。

OpenClaw 的模型引用（model ref）和 fallback 机制正好支持把任务拆到不同模型上，但官方没告诉你边界画在哪，只能自己试。

## 问题

路由的核心不是“哪个模型更强”，而是分类边界。两种典型的错误姿势：

- **全云端**：账单翻倍，敏感数据外流风险，且云端限流一抖整个 agent 瘫掉；
- **全本地**：多步工具调用频繁失败，本地小模型推理能力撑不起编排，agent 表现明显“变笨”。

## 做法

**第一步：任务分三类**

- A 类：面向用户的最终输出、多步工具编排、复杂推理 → 云端强模型（GPT / Claude）
- B 类：中间结果——摘要、打标、去重、格式转换 → 本地 7B–14B 模型
- C 类：隐私敏感数据（内网日志、客户信息）→ 本地，宁可接受质量略降

**第二步：配双 provider**

云端接 openai/anthropic，本地用 Ollama 跑（同机或内网 GPU 机器均可）。主链让云端做 primary，本地挂进 fallbacks，云不可用或限流时不至于全瘫：

```jsonc
// ~/.openclaw/openclaw.json（字段名以所用版本为准）
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4.1",
        "fallbacks": ["anthropic/claude-sonnet-4-5", "ollama/qwen3:14b"]
      }
    }
  }
}
```

**第三步：B/C 类任务别走主会话**

拆成独立 agent 并覆盖模型配置（比如摘要 agent 固定用 `ollama/qwen3:8b`），或者让主 agent 通过插件 / HTTP 调本地推理服务。关键是路由决策写在配置里，而不是靠主模型自己“临场发挥”。

**第四步：观测两周再调边界**

统计 token 消耗、fallback 触发率、本地任务重试率。数据会告诉你分类画错在哪。

## 踩坑点

- **上下文窗口**：本地模型 context 小，长会话直接截断，表现为“突然失忆”。B 类任务喂数据块，别把整段会话塞过去。
- **工具调用稳定性**：本地小模型输出的 JSON 参数常带杂质，MCP 工具调用频繁报错。要么在插件层做容错解析，要么给 C 类任务换 function calling 更稳的本地模型。
- **静默降级**：fallback 切到本地后没人发现质量掉了。务必给 fallback 触发加日志或告警，否则排查“最近回答怎么变差了”会非常痛苦。
- **资源抢占**：OpenClaw 和本地模型同机部署时，定时任务高峰容易 OOM。分开部署，或限制本地推理并发。

## 可复用建议

- 一条经验法则：**面向用户的输出走云端，中间结果和隐私数据走本地**。先按这条切，再根据观测微调。
- 维护三条链：主链（质量优先）、便宜链（B 类批量）、隐私链（C 类强制本地），别混用。
- 给云端链配成本上限和限流策略，账单应该在配置里被控制，而不是月底看邮件才知道。

## 总结

多模型路由不是省钱开关，而是质量、成本、隐私三者的工程权衡。正确的顺序是：先分类任务、再配路由、最后靠观测数据收敛边界。OpenClaw 的模型引用 + fallback 已经把机制给足了，剩下的活是把“什么任务给什么模型”这条边界用数据画清楚。

欢迎在评论里贴你们的路由配置和 fallback 触发率，边界这东西，样本越多画得越准。
