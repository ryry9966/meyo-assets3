# 从零搭建 AI 社区发帖机器人：架构设计与踩坑实录

## 背景

OpenClaw-CN 社区每周有几个固定动作：整理 GitHub Releases、精选本周讨论、汇总新上架的插件。这些事不难，但全是重复劳动，而且是“人肉搬运”。我的目标很克制：让一个常驻 Agent 每周自动产出一份“社区周报”草稿，人工审核后一键发布。注意，第一版只做草稿生成，不做全自动发帖。

## 问题：不是“接个模型”那么简单

直接把任务丢给模型，会出三类事故：

1. **内容失真**：模型会编造版本号、张冠李戴地摘要；
2. **格式不兼容**：LLM 爱输出的 Markdown 方言，社区渲染器未必支持；
3. **重复或漏发**：重试机制和调度不当，导致同一篇帖子发两次。

所以这个项目的架构要解决的核心问题是**可靠性**，而不是“能不能生成”。

## 架构与步骤

结合 OpenClaw 的 agent / skill / 定时任务能力，我按五层来拆：

1. **采集层**：两个 skill。一个走 MCP 拉 GitHub Releases 和带特定标签的 Issues，一个解析社区相关 RSS。输出统一为 JSON：标题、链接、日期、原文关键段落。
2. **加工层**：一个 agent。输入是上一步的结构化 JSON——**不是让模型自己上网找资料**。prompt 模板固定三段：先逐条摘要，再生成社区格式的 Markdown，最后跑一遍自检（链接是否来自输入、有无虚构数字）。
3. **发布层**：一个薄适配器插件，只负责调社区 API。v1 只写进草稿箱，人工点发布。
4. **调度层**：cron 触发，显式指定时区。
5. **审计层**：每次运行落一条记录：输入源 hash、prompt 版本号、输出长度、token 消耗、成功或失败原因。

## 踩坑实录

- **坑 1：版本号幻觉**。早期让模型“读 changelog 写摘要”，它会把 v0.3.2 写成 v0.3.3，人眼很难发现。改法：版本号、日期、链接这些事实字段**不经过模型转述**，模板里直接注入结构化变量，模型只写描述性文字。
- **坑 2：Markdown 方言**。模型喜欢输出脚注和复杂表格，社区渲染器直接糊掉。加了一步后处理：只保留白名单语法（标题、列表、链接、代码块），其余降级成普通列表。
- **坑 3：重复发帖**。一次发布接口超时后自动重试，同内容发了两遍。加幂等键：`源内容 hash + 日期`，发布前先查重，命中就跳过。
- **坑 4：时区**。cron 默认 UTC，周报定在周五发，结果总在周六早上冒出来。调度器显式声明 `Asia/Shanghai` 解决。
- **坑 5：prompt 无版本**。改了 prompt 之后效果变差，想回滚却发现旧版没存。现在 prompt 按文件进 git，审计记录里带上版本号，出问题可以定位到“哪次改动引入的”。

## 可复用建议

1. **先草稿后自动**：至少人工确认两周，再逐步放开自动发布白名单；
2. **事实字段绕过模型**：数字、版本号、链接用结构化注入，别让模型转述；
3. **一切写入操作都要幂等**，网络重试是常态不是异常；
4. **prompt 当代码管理**，进 git、带版本；
5. **失败必须留痕**，否则排障全靠猜。

## 总结

这个机器人的代码量不大，核心工作量全在边界处理上：格式、幂等、时区、版本管理。一个朴素的经验是——Agent 负责生成，工程负责让它可预期。AI 发帖机器人的价值不在“全自动”，而在于把每周两小时的重复劳动，压缩成五分钟的审核。
