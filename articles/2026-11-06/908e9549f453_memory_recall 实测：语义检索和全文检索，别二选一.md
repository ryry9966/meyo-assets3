## 背景

在 OpenClaw 这类 agent 工作流里，`memory_recall` 是最容易被低估的工具。会话结束后把记忆写进去不难，难的是几天后 agent 能不能把对的那条捞回来。捞错、捞漏，比不记还糟——agent 会拿着半相关的内容自信输出。

目前常见两条路线：语义检索（embedding + 向量相似度）和全文检索（BM25 / FTS）。社区里经常吵哪个“更先进”，我把两套都在自己的 memory MCP 插件里跑了一个多月，说点实测结论。

## 问题：各自的死穴

语义检索擅长“意思对但字面不同”的召回：问“上次部署翻车的事”，能命中一段讲 k8s rollout 回滚的记录。但它对精确 token 很不敏感——错误码、配置键、commit hash、包名，embedding 之后在语义空间里几乎糊成一团，查 `ERR_CONN_TIMEOUT` 经常召回一堆泛泛的网络话题。

全文检索正好相反：精确匹配极强、实现便宜、结果可解释。但召回依赖字面重叠，换了说法就抓瞎；中文分词没做对时更是基本不可用。

## 做法：直接上混合，别纠结

我的落地步骤：

1. **存储层**：每条记忆一个 chunk（一个话题/一次会话），存原文 + 时间戳 + tags。原文永远保留，这是兜底。
2. **基线索引**：SQLite FTS5 建全文索引。中文注意用 trigram tokenizer（或外挂分词），默认 unicode61 对中文几乎无效。
3. **向量层**：写入时同步 embed，读取时 cosine 取 top-20。写入和读取必须用同一个模型。
4. **融合**：两路各取 top-20，用 RRF（倒数排名融合）合成 top-5 喂给 agent。RRF 只看排名不看分值，天然绕开两路分数不可比的问题。
5. **评测**：从自己的会话日志里捞 30~50 条真实 recall 查询，人工标注相关文档，量 hit@5。没这个集合，调参全靠玄学。

实测混合后 hit@5 从纯向量的约 68% 提到 85% 以上，主要增益来自 identifier 类查询。

## 踩坑点

- **换了 embedding 模型没重建索引**：写读不一致，召回质量悄悄劣化，且没有任何报错。升级模型必须全量 re-embed。
- **chunk 切太大**：相似度被稀释；切太小：上下文丢失。我的经验是按话题切，recall 时把命中 chunk 的相邻块一起带回。
- **向量 top-k 取太小**：memory_recall 是“召回”不是“排序”，宁可多捞让模型自己筛，top-5 起步经常漏。
- **分数直接加权求和**：BM25 分数无上界，cosine 在 0~1，先归一化，或干脆用 RRF。
- **过期记忆不处理**：三个月前的旧方案和新方案都在库里，recall 会一起捞出来。至少加时间衰减权重，重要事实更新时对旧条目做软删除。

## 可复用建议

- 先跑通全文基线再加向量层，成本几乎为零，还能当 fallback。
- 召回查询和命中结果落日志，攒出评测集，这是唯一能支撑客观迭代的资产。
- 写入时把 tags、时间、来源记全。“只查上周”这类元数据过滤，收益经常比换检索算法更大。
- 别为“更先进”买单，为 hit@5 买单。

## 总结

语义检索和全文检索不是对立选项，而是互补的两路信号：一个管“意思”，一个管“字面”。agent 记忆这种查询形态多变、又常含精确标识符的场景，混合检索 + RRF 是当前性价比最高的解。真正决定上限的不是算法，而是 chunk 粒度、元数据质量，和一个属于自己的评测集。
