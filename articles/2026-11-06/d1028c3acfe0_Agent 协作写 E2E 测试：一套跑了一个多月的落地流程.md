## 背景

E2E 测试一直是“该写但没人爱写”的部分：业务迭代快，页面一改版，用例成片飘红，维护成本常常超过编写成本。Agent 加上浏览器自动化工具（Playwright 这类通过 MCP 或插件接入）成熟之后，“让 agent 起草、维护、修复 E2E 测试”从想法变成了可落地的工作流。最近在内部项目跑了一个多月，把流程和踩坑记录一下。

## 直接让 AI 写测试，问题在哪

把需求丢给 agent 说“帮我写 E2E 测试”，效果通常不好，主要三个坑：

1. **弱断言**：生成的用例“能通过”而不是“能验证”。点一下按钮、等两秒、不校验任何业务结果，跑绿但没有价值。
2. **选择器脆弱**：agent 拿不到真实 DOM 时会编造选择器，或倾向于用文案定位，一改版就挂。
3. **越改越错**：让它自主“跑-改-跑”，它会为了让测试变绿而改测试，把产品 bug 修成“符合 bug 的断言”。

## 我们的流程：四步

**第一步：准备环境上下文。** 给 agent 两样东西：一份测试编写规范（放仓库里，含断言要求、选择器约定、禁止事项），一个能真实操作页面的工具入口（MCP 接浏览器能力）。规范里明确：每个用例至少一个业务断言；优先 `data-testid`，禁止纯文案定位。

**第二步：录制轨迹，起草用例。** 让 agent 沿着真实用户路径操作页面（而不是看截图猜），输出 Playwright 用例草稿。因为拿到的是真实 accessibility tree / DOM，选择器质量明显比“凭描述生成”高一档。

**第三步：人工只审断言。** review 时重点看两件事：断言是不是业务断言（订单状态变了、列表多了一条）；等待是不是显式条件而不是 sleep。其他细节让 agent 自己迭代。

**第四步：失败驱动的修复循环。** CI 挂了之后，把 trace、截图、失败日志喂给 agent，先做分类：产品 bug / 测试问题 / 环境抖动。前两类才允许出修复 PR；环境抖动走重试策略，不许 agent 碰。修复 PR 照常走人工 review。

## 踩坑点

- **权限要收敛**：不要给 agent 同时放开“改断言”和“改业务代码”。定位产品 bug 时先只读，结论清楚了再允许动测试代码。
- **别让它自己当裁判**：跑-改-跑循环设次数上限（我们设 3 次），超了停下来交给人，否则它会一直把测试改松。
- **flaky 别交给它**：agent 对 flaky 的第一反应是加重试、加超时，短期变绿，长期把真问题埋掉。flaky 先人肉定位根因。
- **快照要喂够**：上下文里页面快照一截断，agent 就开始编选择器。宁可分段喂，不要截断。

## 可复用建议

- 把测试规范写成仓库文件，作为 agent 的常驻上下文，比每次对话口头强调稳定得多。
- 给失败打标签（test-bug / product-bug / flaky），积累一两个月就能看清 agent 修复的可靠率，再决定放开多少权限。
- agent 性价比最高的不是从零生成，而是**改版后的批量修复**和**新页面的草稿起草**这两类活。

## 总结

这套流程里，agent 承担起草、维护、初筛定位这些高重复劳动；断言质量、验收标准、最终裁决留给人。一个多月下来，E2E 用例数翻倍，维护耗时明显下降。结论不新鲜但有效：把 agent 当高强度初级工程师用，先把 review 制度立好，再谈提效。
