## 背景

OpenClaw 的 agent 工作区里，有一组 Markdown 文件实际承担着 system prompt 的角色：`IDENTITY.md` 管名字和形象，`USER.md` 记用户事实，`SOUL.md` 管行为方式——语气、价值观、做事边界。很多人的工作区建完就跑默认模板，SOUL.md 里还是示例文案，agent 的表现全靠模型底子撑，结果就是不可预测。

## 问题

我在自己的实例和帮别人排查的过程中，反复遇到三类问题：

1. **过度顺从**：说"清理一下目录"它就真删，没有确认环节；
2. **人格漂移**：长会话后半段语气和原则全变了，像换了个人；
3. **边界缺失**："帮我处理邮件"被理解成"直接替我回复发出"。

这些不是模型能力问题，而是行为约束没写清楚，或者写了但不可执行。

## 做法

我的 SOUL.md 现在控制在 60 行以内，分四段：

1. **语气与风格**：只写可判定的规则，比如"回复尽量不超过 300 字""不确定就直说不确定"，不写"专业、友善"这类空话。
2. **行为边界**：明确禁止项。例如：删除、对外发送、支付类操作一律先输出计划等确认；不代签任何内容。
3. **工具使用原则**：和 MCP/插件的 allowlist 配合。SOUL.md 写"发消息前先给我看草稿"，插件层再做权限限制——两层都要有，缺一层都不可靠。
4. **冲突升级**：当任务和边界冲突时，先说明冲突点、给替代方案，而不是硬执行或硬拒绝。

改完后用三个固定场景做回归：总结一篇长文（风格）、请求一个敏感操作（边界）、问一个它不知道的问题（诚实度），逐条对照预期。

## 踩坑点

- **写太长**：SOUL.md 全量注入上下文，200 行规则的实际遵从率反而下降，模型会"平均用力"。规则越少越硬，控制在几十行。
- **形容词式规则**："保持谨慎"无法执行；"超过 100 元的操作需确认"可以执行。
- **生效时机**：改完 SOUL.md 在旧会话里可能不生效，测试前先确认已加载，新开会话最稳妥。
- **单次坏体验过拟合**：某次回复太啰嗦就加一条"永远简洁"，三个月后规则互相打架。改动要走版本控制，像改代码一样 review。
- **和插件权限脱节**：SOUL.md 写了"不许自动发邮件"，但 allowlist 没限，模型偶尔还是调得动。文件约束是软的，权限配置是硬的，两边必须同步改。

## 可复用建议

- 分工清晰：SOUL.md 管风格和边界，IDENTITY.md 管身份，USER.md 管用户事实，别混着写。
- 每条规则尽量是**可判定的否定式**：不做什么、超过什么阈值要确认。
- 进 git 管理，agent 行为异常时可以回溯是哪次改动引入的。
- 每月用固定的三五个测试场景跑一遍回归，规则改动和场景更新同步提交。

## 总结

SOUL.md 不是给 agent 写人设文案，而是把"你希望它怎么做事"翻译成模型能稳定执行的短规则清单。人格部分决定它像不像你想要的助手，边界部分决定它敢不敢乱来——工程上更重要的一直是后者：可判定、可回归、和权限配置对齐。它是一份跟着使用习惯持续演进的配置，当作代码维护就够了。
