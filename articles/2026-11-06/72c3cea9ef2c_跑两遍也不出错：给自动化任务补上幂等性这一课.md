## 背景

在 OpenClaw 的日常使用里，自动化任务几乎无处不在：定时触发的 cron 任务、Agent 自主决定调用的 MCP 工具、插件里的 webhook 回调。这些任务有一个共同特征——**都可能被重复执行**。网络超时后的自动重试、Agent 判断"上一步可能没成功"而再次调用、调度器重启后补跑错过的任务，都是常态。

问题在于，我们写任务时往往默认"只跑一次"。

## 问题

一个典型翻车现场：让 Agent 每天整理日报发到群里。某天网络抖动，发送超时，框架重试了一次——群里出现两条一模一样的日报。更隐蔽的是调用外部 API 创建工单：第一次请求其实已经成功，只是响应没送达，重试后又建了一张重复工单。

读操作重复执行无所谓，写操作天然不满足"执行多次等于执行一次"，必须额外设计。

## 做法

我的实践分四步：

1. **先分类**。把任务里的动作分成读、幂等写、非幂等写三类，只有最后一类需要重点处理。
2. **用确定性 ID**。不要在执行时才生成随机 UUID，而是从触发源推导：`trigger_id + 调度槽位 + payload 哈希`。同一次触发无论重试多少次，算出来的 key 一样。
3. **落一个执行账本**。一张表或一个状态文件即可：key、状态（pending/done/failed）、时间戳。执行前先查账本，是 done 就直接跳过。这是最朴素的 check-then-act。
4. **给非幂等操作套壳**。外部 API 支持幂等键就传；不支持就先查后建；数据库操作尽量用 upsert（`INSERT ... ON CONFLICT DO UPDATE`），并给业务键加唯一约束，让数据库做最后防线。

## 踩坑点

- **每次重试生成新 ID**。幂等键在重试之间必须稳定，否则等于没做。Agent 重试时如果重新走一遍 LLM 生成参数，参数微变、哈希就对不上了——正确做法是首次执行就把参数固化，重试复用同一份。
- **并发下的 check-then-act 竞态**。两个实例同时查账本都发现"没做过"，然后都执行。查和写要原子化：靠唯一约束冲突兜底，或加锁/租约。
- **副作用成功、记账失败**。动作做完了，标记 done 那一步挂了，下次又会重跑。要么"先记账再执行"（可能漏做），要么容忍重跑但让动作本身幂等（推荐后者）。能用查询验证结果的操作（文件是否存在、记录是否已建），优先验证而不是信本地状态。
- **时间粒度问题**。用日期做 key 时，先想清楚：任务一天内被手动补跑，是允许的还是该拒绝的。

## 可复用建议

- 给自己写的 MCP 工具/插件加一条默认约定：**所有写接口默认按幂等设计**，接受调用方传入的 client_id。Agent 一定会重试，你拦不住，只能接住。
- 工具命名向 ensure 语义靠：`ensure_file_exists`、`upsert_record` 比 `create_xxx` 更不容易被误用。
- 上线前手动跑两遍：任何自动化任务，重复执行一次不出问题才算过关，这条可以进验收清单。

## 总结

幂等性不是什么高级技巧，本质是一个约定：**同一次业务操作，无论执行多少次，结果一致**。在 Agent 时代它比以前更重要——因为重试不只来自网络，还来自一个会"自我怀疑"的 LLM。把确定性 ID、执行账本、唯一约束这三件套装进你的自动化任务里，大多数重复执行问题就消失了。
