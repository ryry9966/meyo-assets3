## 背景

大模型无状态，会话结束即归零。做 Agent 迟早撞上同一个需求：助手第二次对话就该知道我用 pnpm、注释偏简洁、部署走 Compose 而不是 K8s。这个"记住"不是把聊天记录塞回上下文，而是一个需要独立设计的子系统。

## 问题：三种常见做法为什么撑不久

- **全量塞上下文**：token 成本线性上涨，无关记忆稀释注意力，答错率反而升高。
- **每轮都抽取**：跑一周后库里全是"用户问过天气"级别的噪音，检索质量崩掉。
- **只加不改**：偏好会变（"我改用 React 了"），append-only 会同时召回新旧两条，行为漂移。

本质：记忆是数据工程，写入端、存储结构、读取端要分开设计。

## 做法：三层存储 + 受控写入

**存储分层**

- **L1 结构化画像**：固定 schema 的 JSON——语言、框架、代码风格、部署方式等十来个字段，几百 token，每轮固定注入 system prompt。字段级更新，新值覆盖旧值并带时间戳。
- **L2 情景记忆**：向量库 + 命名空间（按项目/主题隔离），按需检索，不默认注入。每条带 confidence、last_hit、来源会话 ID。
- **L3 原始会话索引**：不做抽取，只存可回溯引用。

**写入闸门（最关键的一步）**

只在三类信号触发抽取：显式指令（"记住/以后都/别再"）、纠正行为（模型做错、用户改口）、重复模式（同类偏好出现 ≥2 次才落库）。落库前做冲突消解：与 L1 字段冲突时 upsert 字段并作废旧条目，而不是追加。

**读取路径**

L1 每轮注入；L2 只在命中且分数过阈值时拼入上下文，并附一句"以下为历史偏好，可能与当前指令冲突"——这句话能明显减少旧偏好压过新指令的情况。

**用 MCP 暴露成工具**

把 memory_write / memory_search / memory_update 做成 MCP 工具让 Agent 主动调用。模型自己判断"该记什么"时，写入质量比 harness 层无差别抽取高得多，且行为可审计。

## 踩坑点

- **相似度 ≠ 相关性**：embedding 会捞回话题相近但语义无关的条目，加 namespace + 标签过滤，别裸跑 top-k。
- **schema 别晚定**：早期用自由文本笔记，攒到几百条后没法清理，第一天就定 schema。
- **删除路径必须有**：记忆含用户隐私，做用户可见、可编辑的记忆列表——不是合规洁癖，是调试刚需。
- **别信模型的"我记得"**：它会编造，所有偏好引用必须能回查到存储记录和来源会话。
- **衰减要做**：last_hit 超期且低分的条目降权，否则半年后检索全是陈年旧事。

## 可复用建议

1. 从固定 schema 的 profile 起步，别一上来就上向量库，80% 的个性化需求一个 JSON 就够。
2. 写入从严、读取从宽：宁可少记，不要脏记。
3. 建 20 条回放评测集：旧会话重放，检查第 N 次会话是否无提示就遵循偏好。没有 eval 的记忆系统不可维护。
4. 每条记忆带 provenance（来源、时间、触发原因），排查"它为什么这么干"全靠这个。

## 总结

让 Agent 记住偏好，核心不是"多记"，而是**分层存储 + 受控写入 + 可评测**。先做一个 200 token 的结构化画像跑起来，再逐步加情景记忆和 MCP 工具化。记忆会随使用变脏，衰减与冲突消解不是优化项，是第一天就要设计进去的东西。
