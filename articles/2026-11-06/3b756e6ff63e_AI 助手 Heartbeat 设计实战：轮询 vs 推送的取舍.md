## 背景

OpenClaw 这类常驻型 Agent 有个共同特征：绝大多数时间在"睡觉"，被唤醒才干活。唤醒来源就两种——定时心跳主动醒来巡查，或者外部事件推它一把。最近在给自己的助手做"定时检查 GitHub 通知 + 及时响应 webhook 触发"时，两条路径都踩了一遍，记录一下取舍。

## 问题：两种模式各自的坑

**纯轮询**：简单、可靠、不依赖入站网络，但延迟取决于间隔，且每次唤醒都要加载上下文、跑一轮推理。心跳设 5 分钟一次，即使无事可做，token 成本也线性上涨；设 1 小时一次，又丢掉了及时性。

**纯推送**：延迟最低、按需唤醒最省 token，但要求 Agent 侧有可入站访问的接收端（公网地址、内网穿透或消息队列消费者），还要处理推送方重试、鉴权，以及"Agent 正忙时事件怎么办"。

## 做法：推送做触发，轮询做兜底

1. **低频心跳做扫尾**。心跳间隔放到 30 分钟，唤醒后只做一件便宜的事：读 HEARTBEAT.md 任务清单，为空就直接返回，不进入完整推理流程。它不再是"及时响应者"，而是"对账员"。
2. **高时效事件走推送**。webhook 接收插件校验签名后，把事件写入本地队列（SQLite 或 JSONL 均可），并立刻触发一次 Agent 唤醒。若事件源是支持变更通知的 MCP server，直接订阅其通知通道，思路相同。
3. **队列是唯一事实源**。推送触发的唤醒和心跳唤醒走同一入口：先消费队列，再处理定时任务。事件带幂等键，重复投递直接丢弃。
4. **心跳里做对账**。每轮心跳对比"队列已处理 / 上游状态"，比如拉一次最新通知列表，补上推送丢失的窗口。兜底频率低，成本可忽略。

## 踩坑点

- **心跳唤醒≠免费**。哪怕"看一眼就睡"，上下文加载和推理照样花钱。早期把心跳设成 5 分钟，一天白烧不少 token，后来加了"清单为空即退出"才压下来。
- **推送没有幂等就是事故**。webhook 方重试很正常，同一事件触发两次"发消息"就很尴尬。幂等键必须落在队列层，不能靠 Agent 自己"记得"。
- **正忙时事件会丢**。Agent 跑长任务时，同步处理推送必然阻塞或丢失，所以事件必须先落盘，绝不在唤醒路径里直接干活。
- **静默时段要两头都管**。只管推送不管心跳，凌晨的对账任务照样把你吵醒。quiet hours 应该是队列消费前的统一闸门。

## 可复用建议

判断标准其实很简单：事件源能主动调你、且你能保证接收端在线，就推送；事件源只能被查询、且延迟容忍大于一个轮询周期，就轮询；生产环境两者都要——推送管延迟，轮询管可靠性。另外三条通用经验：事件先入队再处理、所有动作带幂等键、心跳加随机抖动，避免和别人整点齐刷刷醒来。

## 总结

轮询和推送不是二选一，而是分工：推送解决"快"，轮询解决"稳"。OpenClaw 的心跳机制天然适合做那个"稳"的角色——把心跳从主响应通道降级为兜底对账，让事件推送负责及时性，token 成本和响应延迟才能同时压住。
