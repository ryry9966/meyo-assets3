## 背景

LLM 本身无状态，每次会话都是"失忆"重启。上下文窗口再大，也装不下长期积累的用户偏好；而把历史记录全塞进 prompt，既贵又不稳定。做 OpenClaw 插件和 MCP 工具时，记忆系统是绕不开的一层，但大多数人第一步就走歪了。

## 问题

两种常见失败做法：

1. **全量注入 system prompt**：几轮之后 prompt 膨胀，关键偏好被无关内容淹没，token 成本直线上升。
2. **直接对聊天记录做向量检索**：检回来的全是对话碎片，"用户喜欢简洁回复"这种偏好混在闲聊里，信噪比很低。

核心矛盾是：**记忆的价值在检索，不在存储**。

## 做法

我的方案是分层设计，各层用不同的读写策略：

**第一层：稳定偏好走配置，不走记忆。** 语言、时区、代码风格这类几乎不变的偏好，放进用户配置文件（YAML 即可），会话启动时注入。别让模型"猜"这些。

**第二层：结构化事实记忆。** 自己写了个轻量 MCP memory 工具，SQLite 存储，每条记忆是结构化记录：

```json
{
  "type": "preference | fact | decision | feedback",
  "key": "reply_style",
  "value": "偏好简洁，先给结论",
  "confidence": 0.8,
  "updated_at": "...",
  "source": "session_id"
}
```

**写入**：两条路径——用户显式说"记住这个"时直接写；会话结束后跑一次轻量提取，只抽取符合 schema 的事实，宁缺毋滥。

**读取**：会话开始按 key 精确匹配拉核心偏好，再对当前任务做一次语义检索补充上下文。检索结果限 5 条，避免撑爆窗口。

**更新**：同 key 新值覆盖旧值，confidence 随时间衰减，低于阈值进待清理队列。给 agent 提供 remember / forget / correct 三个工具，而不是只能记。

## 踩坑点

1. **记忆膨胀**：早期版本啥都存，两周后检索质量崩了。解决：写入前过一道"值得记吗"的判断，琐碎对话一律不存。
2. **过期记忆打架**：用户从 Python 转了 Go，旧记忆还在推荐 Python 写法。解决：同 key 覆盖 + 定期跑记忆复核，让用户确认或自动清理。
3. **隐私泄漏**：记忆文件里出现过密钥片段。解决：写入前做敏感信息过滤，记忆按 workspace 隔离，提供一键清空。
4. **检索质量优先于存储量**：1000 条乱序记忆不如 100 条干净记录。

## 可复用建议

- 先用 SQLite/JSONL + 标签跑通全流程，再考虑向量库，别一上来就过度设计
- "稳定偏好"和"情景事实"严格分开：前者是配置，后者才是记忆
- schema 里必须有 `updated_at` 和 `source`，排查问题时能救命
- 维护一个 10 题左右的评测集（"助手应该记得 X"），每次改动后跑一遍，防止回归
- 记忆粒度要小：一条记忆一个事实，别存大段文本

## 总结

记忆系统的核心不是"存得多"，而是"取得准"。分层设计 + 结构化存储 + 主动清理，比直接堆一个向量数据库实用得多。建议从最小 schema 起步，用评测驱动迭代，两周内就能跑出一个可用的 v1。
