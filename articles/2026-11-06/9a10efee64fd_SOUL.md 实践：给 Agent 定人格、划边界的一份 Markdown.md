## 背景

跑 OpenClaw 一段时间后你会遇到一个尴尬的事实：模型本身没有稳定的"身份"。今天它自称贴心助手，明天在群里发言又变得过分热情；接入 MCP 工具后更明显——它会把"能调用工具"理解成"应该主动调用工具"，替你发消息、做承诺、自作主张地执行。

系统提示词写在配置里通常只有一两句，塞不下也不适合维护长篇人格描述。SOUL.md 就是为此存在的：一份放在 workspace 里的 Markdown，每次会话被注入上下文，让 Agent 知道"我是谁、我为谁服务、什么不能做"。

## 问题拆开是三件事

1. **人格漂移**：跨会话、跨渠道语气不一致，群聊像客服，私聊像陌生人。
2. **边界缺失**：模型默认讨好，对模糊指令倾向于直接执行而不是先确认。
3. **维护困难**：人格规则散落在插件描述、渠道配置里，改一次要翻三处。

## 做法

以默认 workspace（`~/.openclaw/workspace/`）为例：

1. 新建或编辑 `SOUL.md`，按四个区块写：**身份**（我是谁、服务谁）、**语气**（语言偏好、正式度、emoji 政策）、**边界**（禁止项 + 遇到时的替代动作）、**升级规则**（什么情况必须停下来问你）。
2. 边界别只写"禁止"。写成"当 X 发生时，先向用户确认再执行"这类正向规则，比一长串"不要做 Y"可靠得多。
3. 控制篇幅，1–2 KB 足够。SOUL.md 每轮都占上下文，长篇大论只会稀释重点。
4. 用 git 管起来，像改代码一样小步迭代。
5. 每次改动后跑一组固定探针：让它转账、向群里发未确认消息、替你答应别人，看它是否按升级规则停下来。

## 踩坑点

- **写太长**：见过 8 KB 的版本，后半段基本被模型忽略，前半段语气反而被过度强化。
- **纯负面清单**："永远不要……"式规则随会话变长衰减，必须配"遇到时怎么办"。
- **和工具描述打架**：MCP 工具的 description 鼓励主动调用，SOUL.md 要求先确认，行为就会随机。边界放 SOUL，机制说明放工具。
- **改完没生效**：长会话里旧上下文还在，重开会话再验证。
- **写入敏感信息**：SOUL.md 进每一次 prompt，密钥、住址都别放。
- **人格写过头**：角色扮演浓度太高，它会开始拒绝正经干活。

## 可复用建议

- 固定骨架：身份 / 语气 / 边界 / 升级规则 / 变更记录，五段足够。
- SOUL 管"我是谁、什么不做"，memory 文件管"发生过什么"，不要混。
- 维护一份 5–10 条的探针清单，改版必跑。
- 各渠道语气差异大时，考虑按渠道覆盖，而不是把所有规则堆进一个文件。

## 总结

SOUL.md 不是魔法，只是一份被持久注入的提示词工程产物。它的价值在于把人格和边界从"散落在配置里的一句话"，变成可版本化、可测试、可回滚的工程资产。写短、写正向、写清升级规则，然后像对待代码一样对待它——这是让 Agent 长期稳定服役里性价比最高的一步。
