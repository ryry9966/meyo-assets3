## 背景

OpenClaw 的 agent 默认是被动响应的：收到消息才动。但自动化场景很快会要求它主动干活——定时巡检、汇总、提醒。heartbeat（心跳轮询）就是为此设计的：每隔 N 分钟把 agent 唤醒一次，读一份任务清单（比如 HEARTBEAT.md），有事就处理，没事就沉默。

另一条路是推送：外部系统通过 webhook 或 MCP 工具回调直接把事件塞给 agent。两条路都能实现"主动性"，但取舍点完全不同。

## 问题

轮询的代价是成本与延迟。唤醒一次就是一次 LLM 调用，间隔太密烧 token，太疏则事件延迟可达一个完整周期。更隐蔽的是"空转"——大多数心跳周期里其实无事可做，钱花了但零产出。

推送的代价是复杂度。你需要一个可达的接收端点、鉴权、幂等处理；而且推送链路本身会挂（网络抖动、服务重启、URL 失效），挂了之后 agent 就"聋"了，而你还不知道。

## 做法：分层混合

我目前的方案是把两者叠加，各干各的：

1. **低频心跳做兜底。** 间隔 20–30 分钟，心跳清单只放两类事：周期性任务（日报、巡检）和"对账"逻辑——检查推送队列有没有积压、上次任务是否跑完。
2. **推送做即时事件。** 时效性强的东西（监控告警、CI 结果、邮件到达）走 webhook/MCP 回调。推送处理器只做一件事：把事件写入状态文件/队列，立刻返回 200。重活留给下一次心跳或即时触发的会话去消化。
3. **心跳兼任 watchdog。** 每次心跳检查推送端点的"最后成功接收时间"，超过阈值就在会话里提醒自己：推送链路可能挂了。这一步补上推送最大的盲区。

判断标准可以简化成两问：事件要求秒级响应吗？是 → 推送。事件每分钟可能来很多次吗？是 → 心跳里批处理，别逐条推。

## 踩坑点

- **心跳间隔拍脑袋定。** 先统计一周内"有事心跳 / 总心跳"的比例，低于 10% 就该拉长间隔或改事件触发。
- **推送处理器里干重活。** LLM 调用一耗时，对端超时重试，事件重复投递。接收端必须幂等：事件带唯一 ID，写入前查重。
- **心跳清单越写越长。** 任务文件变成垃圾桶后，每次唤醒的 token 消耗线性上涨。定期清理，低频任务挪给 cron。
- **忘了静默时段。** 凌晨三点的心跳日报没人看，但每次都花钱。加时间窗判断。
- **重启后状态丢失。** "上次执行时间"和"队列游标"必须落盘，不要只放内存。

## 可复用建议

- 一句话原则：**推送负责事件，心跳负责状态收敛。** 别用推送做对账，也别用心跳追实时。
- 心跳唤醒前先跑一个廉价判断（读状态文件、查队列长度），无事直接跳过 LLM 调用——这是省 token 最有效的一刀。
- 事件统一落一个 JSONL 队列文件，推送写入、心跳消费。schema 稳定后，整个"主动性"子系统就一个文件可查，排障极快。
- 每类事件记一个"最后处理时间戳"，既是幂等依据，也是 watchdog 的数据源。

## 总结

轮询和推送不是二选一，而是互补的原语：推送管即时性，心跳管可靠性和对账。OpenClaw 场景下，建议先从最简单的心跳起步，等"空转率高"或"延迟不够"这两个信号出现，再引入推送，并用心跳反向监控推送链路。保持心跳清单小、事件落盘、接收端幂等，这套结构跑半年基本不用动。
