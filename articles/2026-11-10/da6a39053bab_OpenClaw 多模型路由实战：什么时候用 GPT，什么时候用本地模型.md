## 背景

跑 OpenClaw 的 agent 时，很多人默认全程走 GPT 级别的云模型——规划、工具调用、摘要、格式清洗全打同一个 endpoint，月底一看，80% 的 token 花在"把这段 JSON 里的字段抽出来"这类粗活上。另一部分人为了省钱全切本地模型（Ollama / vLLM 跑 Qwen、Llama 系），结果复杂规划任务翻车率明显上升。两个方向都有真实成本：一个是钱和延迟，一个是任务成功率。

## 问题

多模型路由的本质不是"选哪个模型更好"，而是**给任务分类，再把任务类型映射到性价比合理的模型上**。难点在于 agent 链路里任务类型很多，且同一轮对话里混合出现，静态配置很容易失效。

## 做法与步骤

1. **先做任务盘点，再谈路由。** 把 agent 链路里的调用拆开记录一周，通常会归出几类：复杂规划/多步推理、工具调用参数生成、结构化抽取、摘要改写、分类与 embedding。
2. **建立映射表。** 我的默认配置：
   - 规划、代码修改、跨工具编排 → 云端旗舰模型（GPT 级）；
   - 短摘要、格式清洗、字段抽取 → 本地 7B~14B；
   - 分类、embedding、去重 → 本地小模型，永远不上云。
3. **在 OpenClaw 配置里按 plugin / agent 粒度指定模型**，而不是全局一个 model 字段。让"做粗活的插件"显式声明走本地，主 agent 保持云端。
4. **加升级链路。** 本地模型输出先过 schema 校验，失败重试一次，再失败升级到云端重跑。这一条比任何"智能路由算法"都管用。
5. **按 (任务类型, 模型) 维度记日志**：token 数、延迟、失败率。路由策略应由这份数据驱动迭代，而不是拍脑袋。

## 踩坑点

- **本地模型的 JSON schema 遵循度是最大的坑。** 工具调用参数交给弱本地模型后，坏 JSON 率明显上升。要么用支持 grammar 约束的推理后端，要么这个环节留在云端。
- **上下文静默截断。** 本地模型 context 窗口小，agent 记忆一长就悄悄丢内容，表现为"模型变笨"，很难排查。给本地路由加输入长度守卫。
- **延迟反直觉。** 没有像样 GPU 的机器上，本地推理可能比云 API 还慢。路由前先实测单请求延迟，别只看参数表。
- **别用关键词做路由判断。** 靠 prompt 里有没有"分析""规划"这类词分流非常脆。任务类型应该在调度层打标签，而不是让模型自己猜。
- **混用模型导致风格漂移。** 同一条 trace 里两个模型轮流输出，格式会不一致，下游若有解析逻辑要额外兜底。

## 可复用建议

- 起步用 80/20：一个云端 + 一个本地，别一上来就上路由框架。
- 维护一个"难任务白名单"显式走云，比动态识别难任务可靠得多。
- 所有模型调用统一包一层 wrapper：校验 → 重试 → 升级。这是路由系统的地基。
- 每月复盘一次 (任务类型, 模型) 的成本/成功率表，规则跟着数据走。

## 总结

多模型路由不是模型选型问题，是 ops 问题。先把任务分清楚，便宜的活给本地、难的活给云端，配上校验和升级链路，最后用日志迭代。做到这一步，大多数团队的账单能降一半以上，而任务成功率不受影响——这才是 OpenClaw 多模型配置的正确打开方式。
