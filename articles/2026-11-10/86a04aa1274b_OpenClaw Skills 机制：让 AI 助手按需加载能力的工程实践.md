## 背景

最近半年社区里出现频率最高的调试场景之一：Agent 的 system prompt 越写越长。MCP 工具几十个、各业务 SOP、领域话术全塞进上下文，一次请求光提示就上万 token。结果是模型注意力被稀释——该用的工具没选中，不该触发的流程反而被带出来。

OpenClaw 的 Skills 机制针对的就是这个问题：把「能力」从「常驻上下文」改成「按需加载」。

## 问题：全量注入的三个代价

1. **成本线性增长**：无关内容每请求都在烧 token；
2. **选择准确率下降**：工具和指令越多，模型越容易混淆相似能力；
3. **维护困难**：所有改动挤在一个大 prompt 里，回归基本靠运气。

## 做法：三层结构

Skills 的核心是渐进式披露：

- **索引层（常驻）**：每个 skill 只注册名称 + 一句话描述，全部加起来几百 token；
- **正文层（按需）**：任务匹配到某个 skill 时，才加载完整指令、模板、脚本；
- **资源层（引用）**：正文里可以再挂文件、示例，真正用到才读。

一个最小化的注册示例：

```yaml
name: data-export
description: 当用户要求导出报表或查询历史数据时使用。输入为时间范围与维度，输出为 CSV 文件路径。
body: skills/data-export/SKILL.md
```

落地步骤：

1. 盘点现有 prompt，区分「全局必带」和「场景化内容」；
2. 场景化内容拆成 skill，description 写清三件事：做什么、何时触发、输入输出形态；
3. 注册到 skills 目录，配置按匹配加载；
4. 准备一组固定触发语句做回归：该触发的触发，不该触发的保持静默；
5. 根据误触发/漏触发的日志迭代 description。

## 踩坑点

- **description 太模糊** → 永远不触发；**太宽泛** → 每次都命中，等于没拆；
- **skill 之间隐式依赖**：加载了 A，但 A 默认 B 已在上下文里，链路直接断掉。要么显式声明依赖，要么把关键前提内联进正文；
- **拆得太碎**：按「函数」拆而不是按「任务」拆，选择开销反而上升；
- **只门控了指令，没门控工具**：MCP 工具 schema 仍全量注册时，瘦身效果有限，需配合工具过滤；
- **旁路修改**：有人图省事直接改运行时 prompt，两三天就版本漂移，skill 仓库形同虚设。

## 可复用建议

- 命名统一「动词-名词」或「领域-动作」，人和模型双向检索都省力；
- 单个 skill 正文控制在 2k token 内，超了就继续拆；
- 留默认兜底：没有 skill 匹配时明确走通用路径，而不是硬凑触发；
- 把 skill 当代码管理：进仓库、走 review、随版本带触发用例；
- description 是靠数据迭代出来的，不是一次写对的——命中日志比直觉可靠。

## 总结

Skills 机制的本质，是把 prompt 工程从「一次性写全」改成「索引常驻、正文按需」。真正的工作量不在拆分动作本身，而在 description 的打磨和触发链路的回归验证。我们某条业务线拆完之后，单次请求提示体积降了约 70%，工具误选率也明显下降。收益是实打实的，但前提是把它当工程做，而不是当配置项改。
