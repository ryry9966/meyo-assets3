## 背景

在 OpenClaw 这类 agent 自动化体系里，“一个任务只跑一次”是稀缺事件。定时任务因网络抖动被重试、webhook 因对端超时被重新投递、agent 规划到一半报错后重新规划、网关重启后消息按 at-least-once 再送一遍、用户看没反应手动再点一次——这些都是日常。现实是：exactly-once 很难免费拿到，at-least-once 才是常态。

## 问题

任务不幂等，重复执行就会产生重复副作用：工单建了两张、通知发两遍、文件被追加两份内容、数据库多出重复行、外部 API 被调两次。更隐蔽的是多步 agent 任务：第一步写库成功，第二步发通知超时，agent 重试时从第一步重来——如果写库是幂等的，库没坏，但通知发了两次。问题通常不在“重试”这个机制，而在任务的写操作没按“会被重跑”来设计。

## 做法

我的习惯是按下面几步把幂等性做进任务：

1. **定义稳定的业务幂等键**。键由任务语义决定，不是执行时机。比如“每天汇总周报”的键是 `报告名+业务日期`，补跑和首跑是同一个键。时间戳、随机 UUID 不适合重试场景——每次重试键都变，等于没做。
2. **写操作优先 upsert / 覆盖语义**。数据库用 `INSERT ... ON CONFLICT DO UPDATE`，文件写入用“临时文件 + 原子 rename”整份替换，能 PUT 就不用 POST。
3. **状态记录 + 先查再跑**。任务入口把幂等键和状态（pending/running/done）落库，重试进来先查状态，done 直接跳过。
4. **键透传全链路**。agent 调 MCP 工具、工具调外部 API，同一个键带下去。外部 API 支持 Idempotency-Key 就用上，不支持就在自己这层挡住。
5. **并发兜底靠约束不靠判断**。check-then-act 有竞态，两个实例可能同时查到“没做过”。唯一索引、唯一约束、分布式锁，至少留一样。
6. **外部副作用放最后**。拆成“可重复的准备阶段 + 一次性的提交阶段”，提交失败重试时只重复最后一步。

## 踩坑点

- 只在入口去重：链路中段失败后重试，中段的写操作没保护，照样重复。
- 用“当前时间”生成键：重试时键变了，去重形同虚设。
- 超时立刻当失败重试：请求可能已在上游成功，只是响应丢了。先查询确认再重试。
- 部分幂等：读操作幂等、写操作不幂等，多步任务里混着又没标注，排查全靠猜。
- 删除本身幂等，但“删除并通知”不幂等——补偿类任务同样要按幂等设计。

## 可复用建议

- 给每个 skill / 插件的写操作标注幂等性（yes/no + 依赖的键），像标注参数一样写进文档。
- 设计 MCP tool 时默认提供 upsert 语义，POST 类操作强制要求幂等键参数。
- 定时任务统一用“窗口 + 业务日期”做键，补跑、回填历史数据都是安全的。
- 上线前演练一次：同一任务手动连跑两遍，diff 结果，不变才算过。

## 总结

幂等不是锦上添花的优化，而是自动化系统的默认假设。把“这个任务一定会被重复执行”当作设计前提，重试、补跑、并发才不会变成事故现场。下次写自动化任务时先问一句：这个键，重跑一次还认得吗？
