## 背景

我订阅的 RSS 源常年维持在 60 多个，每天新增文章 100 篇上下。之前靠阅读器的未读列表硬刷，实际打开率不到两成——大部分内容价值密度低，但逐条筛选成本高。于是想到用 OpenClaw 的定时任务和 Agent 能力，把「筛选」和「摘要」这两个环节自动化。

## 问题

手工处理有四个核心痛点：

1. 逐条打开成本高，很多文章看完才知道不值得看；
2. 直接把全文丢给模型，token 消耗大、上下文容易超限；
3. 摘要容易幻觉，比如补全不存在的结论、甚至还原出错误的链接；
4. 多次运行之间会重复推送已处理过的条目。

## 做法

管线分四层，全部跑在一台 VPS 上：

1. **采集层**：没有 RSS 的站点用 RSSHub 转换，所有源统一汇入 Miniflux，靠它处理编码和已读状态。
2. **触发层**：OpenClaw cron 任务，早晚各跑一次，拉起 Agent。
3. **处理层**：Agent 分两步——先读取上次运行时间之后的未读条目（游标存在一个 JSON 状态文件里），用「关键词规则 + 轻量模型」做双重过滤；对通过的部分分批摘要，最后合并成一份 digest。
4. **输出层**：digest 写入 Markdown 笔记库，同时推送 Telegram。标题、链接、GUID 全部由代码模板拼接，模型只负责填摘要正文。

Prompt 里的硬约束：只允许基于给出的条目总结；每条输出「一句话概括 + 关键点 + 是否值得深读」；信息不足时标注出来，禁止自行补全。

## 踩坑点

- **幻觉链接**：早期让模型直接输出 Markdown 列表，它偶尔会「还原」一个相似但错误的 URL。改成模型只输出内容、链接由代码生成后，问题消失。
- **token 超支**：全量摘要一天消耗可观。改为「轻量模型做初筛，主力模型只处理通过的 10%~20%」后，成本降了一个量级。
- **GUID 不稳定**：个别源每次抓取 GUID 都变，导致重复推送。改用 `hash(link + title)` 作为去重键。
- **正文脏数据**：部分源的 description 里全是 HTML 标签和追踪参数，直接喂模型既浪费又干扰判断。加了一步 strip HTML + 域名白名单清洗。
- **cron 时区**：容器默认 UTC，推送时间比预期晚 8 小时，记得显式设置。

## 可复用建议

- 摘要只做「索引」，不替代原文。digest 里保留全部原始链接，深读决策留给人。
- 状态文件比数据库够用：`{feed_url: last_run_ts}` 加一个已读 hash 集合即可。
- 过滤和摘要拆成两次独立调用，方便分别调优和降级。
- 新增源先观察三天日志再上量，低质源及时砍掉——管线再自动化，源头质量决定上限。

## 总结

这条管线跑了两周，日均产出 1 份 digest，深度阅读比例比之前翻了一倍。它没有让我「读得更少」，而是把筛选成本压到了每天几分钟。下一步打算把「是否值得深读」的判定封装成独立的 MCP 工具，让订阅源画像可以跨管线复用。核心思路一句话：让模型做它擅长的压缩和判断，把事实和链接留给确定性代码。
