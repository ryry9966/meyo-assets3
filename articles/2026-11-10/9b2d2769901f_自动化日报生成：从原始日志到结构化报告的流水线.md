# 从原始日志到结构化日报：搭一条可维护的自动化流水线

## 背景

团队每天要交一份服务运行日报：异常统计、发布记录、关键指标波动、待跟进事项。过去的流程是各自翻日志、群里催数据、最后由一个人手工拼 Markdown。信息缺失、口径不一、耗时半小时起步。这篇帖子记录我们用 OpenClaw 定时任务 + Agent + MCP 工具把这条链路自动化的过程，重点不在具体脚本，而在**哪些环节交给代码、哪些才交给模型**的划分。

## 问题

第一版做法很直接：脚本把当天日志原样扔给模型，让它"总结成日报"。跑了三天暴露三个问题：

1. 全量日志动辄几十万 token，费用高，且模型经常漏掉关键报错；
2. 输出格式每次微变，下游渲染脚本天天崩；
3. 偶发幻觉：把一条 debug 日志总结成了线上事故。

根因是让模型干了它不擅长的事——在噪声里做精确的数据提取。

## 做法

流水线拆成四段，核心原则：**提取用代码，模型只做归纳与措辞**。

**1. 采集层（代码）**。cron 定时触发，从四个来源拉数据：应用日志、CI/CD 记录、git log、监控告警回调。每个来源一个独立采集函数，单点失败不影响整体。

**2. 预处理层（代码）**。过滤 DEBUG、去重、按服务聚合、统计频次、脱敏 token 和内网 IP，产出固定 schema 的中间 JSON：`{ incidents, deploys, metrics_deltas, top_errors }`。这一层完全确定性，可单测。

**3. 生成层（Agent）**。把中间 JSON 喂给 Agent，通过 MCP 工具获取写死的日报模板。Prompt 明确约束：只允许基于输入 JSON 陈述事实，不允许推测。输出走 schema 校验，不合法就带校验错误重试一次，再失败则降级为纯模板填充（只有数据，没有总结）。

**4. 渲染与分发（代码）**。渲染两个版本：完整版归档到知识库，摘要版推送 IM 群 webhook。归档按 `YYYY-MM-DD` 命名，重跑即覆盖。

## 踩坑点

- **时区与时间窗口**。任务设在 00:05 跑，最初按"当天"取数，漏掉了前一天 23:50 之后的日志。改为在预处理层显式传入 `[前一日 00:00, 24:00)` 的本地时间窗口，采集函数只吃窗口参数。
- **模型输出不稳**。解法不是堆 prompt，而是收窄任务：模型面对的是已聚合的小 JSON，校验失败率从三成降到偶发，加上降级兜底后基本无感。
- **静默失败**。流水线挂了比日报写得差严重得多。加了一个心跳 URL，最后一步成功才上报；群里的隐含约定是：早上八点半没收到日报，本身就是一条告警。
- **敏感信息外泄**。第一版脱敏做在生成层之后，模型日志里已经带上了内网地址。脱敏必须前置到预处理层。

## 可复用建议

1. **中间 JSON 落盘**：任何一天可离线重跑生成层，调 prompt 不再依赖真实日志；
2. **采集与生成解耦调度**：改 prompt 不触发重新采集；
3. **先跑通单一数据源的最小闭环**：我们第一周只有日志一个源，先让模板和校验稳定，再加来源；
4. **保留人工修改的 diff**：两周后把同事手改的措辞归纳进 prompt，报告的人工修改率降到接近零。

## 总结

这条流水线的价值不在"省半小时"，而在日报变得可信且稳定：格式恒定、数据可回溯、失败可见。LLM 在其中的角色被压到最小——归纳与措辞——这正是它能稳定发挥的位置。同一套架构后来直接复用到周报和告警摘要，几乎只改模板和时间窗口。建议有类似需求的：从一个源、一个模板、一个心跳开始。
