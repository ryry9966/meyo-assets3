# 自动化日报生成：从原始日志到结构化报告的流水线

## 背景

我们组的日报，内容其实早就散落在各处：git 提交、终端历史、任务系统的状态流转、告警记录。手写日报的成本不在“写”，而在回忆和汇总。OpenClaw 自带定时任务和插件机制，正好能把这件事固化成一条无人值守的流水线：每天 18 点自动采集、清洗、生成、投递，人只做最后确认。

## 问题

动手前先明确了三个障碍：

1. 数据源分散且格式不一，raw log 没法直接用；
2. 把原始日志整包丢给模型，上下文放不下，而且模型会“补写”日志里不存在的内容；
3. 日报格式靠 prompt 硬撑，时间一长就漂移，没法横向对比。

## 做法

按四层拆开，每层独立可测：

**采集层**：cron 触发几个小采集器，各拉各的一亩三分地——`git log --since`、shell history、任务系统 API、告警系统。采集器写成独立插件或 MCP 工具，谁的数据谁实现，接口只约定统一输出 JSON Lines，每条带 `source`、`ts`、`id`。

**清洗层**：纯脚本，不经过模型。按时间窗过滤、去重、按项目分组，控制条目规模（每人每天 top 20），对 token、内网地址做脱敏。产出“当日结构化摘要”，体量控制在几千 token 以内。

**生成层**：Agent 读清洗后的 JSON，prompt 里两条硬约束：只允许引用输入条目，每条结论必须标注来源 `id`；输出走固定 JSON Schema，校验不过直接重试。渲染由模板完成，模型不碰排版。

**投递层**：webhook 推到群，同时把输入摘要和最终报告按日期归档。

```yaml
schedule: "0 18 * * 1-5"
collectors: [git, todo, alerts]
schema: report.v1.json
deliver: [webhook, archive]
```

## 踩坑点

- **时区错位**：cron 用机器本地时区，git 日志是 UTC，傍晚跑一次会把当天早上和前一天下午混在一起。统一在清洗层转本地时区再切窗口。
- **幻觉条目**：早期让模型自由总结，出现过日志里完全没有的“成果”。改成来源标注 + 校验器逐条核对 `id`，对不上的直接拒绝输出。
- **上下文爆炸**：一天几十万行日志直接塞给模型，必然截断且截断点随机。教训是聚合必须发生在模型之前。
- **静默失败**：任务挂了两周才被发现。现在报告没按时到达本身就是一次告警，失败通知和成功投递走同一条通道。
- **敏感信息**：脱敏必须放在采集层做，别指望模型帮你过滤。

## 可复用建议

- 采集和生成分离：清洗后的 JSON 是资产，报告只是视图，换模板不用动数据。
- Schema 版本化，格式漂移在校验层拦住，而不是靠 prompt 措辞。
- 先跑两周“草稿模式”，推给自己人工确认，稳定后再切自动投递。
- 每次运行的输入输出都落盘，方便回放、diff 和评估提示词改动的影响。

## 总结

日报自动化的关键不在模型，而在数据管线。先解决“给模型一份干净、够用的结构化输入”，模型只负责最后一公里的措辞。一句话概括分工：脚本负责别让它说错话，模型负责让它说得像人话。
