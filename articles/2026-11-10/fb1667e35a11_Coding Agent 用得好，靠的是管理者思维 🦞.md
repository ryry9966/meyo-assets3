最近，Anthropic 一位工程师的长文被 36kr 等媒体广泛转发，核心论点有点反直觉：很多人用不好 Coding Agent，缺的不是 prompt 技巧，而是「带人」的管理能力。作者把 agent 比作能力极强但毫无上下文的新员工——你愿意给真人同事什么，就该给 agent 什么。下面结合 Anthropic 公开的工程实践，把这套「管理者思维」拆成几块能直接上手的东西。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-10/7c7ed074f563c249.png)

## Agent 是「零上下文的资深新员工」

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-10/a368b80d1c156d10.png)

单点能力已经不是瓶颈。从 SWE-bench Verified 这类「修复真实 GitHub issue」的基准看，主流模型的成绩已站上七成：写代码、跑测试、读报错，动作一气呵成。但多数人忽略了另一半事实——agent 缺三样东西：

- **项目历史**：这个模块当年为什么绕开某个库？哪些文件是雷区？它一概不知；
- **团队约定**：命名风格、错误处理惯例、没写进文档的「老规矩」，对它是无效信息；
- **业务直觉**：什么需求重要、什么方案够用，它只能靠你喂的上下文去猜。

于是同一款工具在不同人手里表现天差地别：一句「帮我修下这个 bug」，模型再强也只能瞎猜；换成一份带复现步骤、期望行为、相关文件和回归测试要求的工单，产出立刻不同。差距不在模型，在输入。

## 工作流要重排：从「动手写」到「带人写」

传统 solo 开发是「想清楚→自己写→自己测」一条龙；接入 agent 后，流程更像带人：

1. **写 spec**：把模糊需求翻译成目标、非目标、约束和验收标准；
2. **拆任务**：按模块边界切成 agent 一次能独立完成的小块；
3. **下发**：附上文件路径、参考实现和注意事项；
4. **验收**：跑测试、读 diff、对照原始目标逐条核对；
5. **反馈**：不满意就带着具体理由打回，而不是自己上手重写。

一个直观对比：让 agent「加个登录功能」，多半得到一个跑不通的半成品；而「参考 auth/legacy.py 的旧流程，用 OAuth2 重写，保留现有 session 结构，先补集成测试」才是合格工单。本质上，你的产出从代码变成了 spec 和 review，工作量从打字迁移到「想清楚」和「看仔细」。

## 上下文工程：Spec 写作是新的核心竞争力

Anthropic 官方的 Claude Code 最佳实践反复强调一件事：维护好 CLAUDE.md 这类项目说明文件——常用命令、代码风格、测试习惯、仓库潜规则都写进去；会话中临时纠正 agent 的经验，也可以顺手沉淀成长期记忆。说白了，这就是给新员工的 onboarding 文档。

一份合格的 spec 至少包含六要素：

- **背景**：问题为什么存在；
- **目标**：做成什么样；
- **非目标**：明确不做什么，防止 agent 自作主张发散；
- **约束**：能用什么库、不能动哪些文件；
- **验收标准**：测试怎么跑、什么算完成；
- **参考资料**：仓库里现有的类似实现。

有意思的是，写 spec 的过程会倒逼你把需求想清楚。很多「agent 产出不行」的问题，换个问法就露了原形——其实是你自己也还没想明白。

## 反馈回路：给 agent 一个客观裁判

管理的核心不是盯人，而是设计反馈系统。agent 最大的优势是「跑验证几乎零成本」：单元测试、类型检查、lint、CI，它都能自己执行、自己读报错、自己修。会用这一点的人，等于给 agent 装上自动纠偏的陀螺仪——它加班不领工资，但会理直气壮地把 bug 改到天亮，前提是你给了它裁判。

- **TDD 天然适配**：先写测试，让 agent 想办法把红变绿，目标客观、路径自主；
- **Plan 先行**：复杂任务先让它出方案，确认方向再放手，避免跑出 800 行代码才发现理解偏了；
- **中途抽查**：长任务定期看进度，早失败、小失败，别攒成大返工。

这和带真人团队完全同构：好的管理者不救火，而是让系统自己暴露问题、自己修正。

## 并行杠杆：一个人也能带一支 AI 小队

单个 agent 的协作模型跑顺之后，下一步是并行。Anthropic 的实践里有现成玩法：用 git worktree 给每个 agent 隔离出独立工作区，互不踩脚；官方还演示过用「子 agent」分头调研、再汇总结果的模式。

但并行立刻暴露管理带宽问题：agent 从 1 个变 5 个，任务怎么切、依赖怎么排、谁的产出先合并，全由你决定。低耦合、边界清晰的任务适合并行；强耦合任务并行只会制造冲突。这与「一个人能同时带好几个下属」的团队规模问题一模一样——管理带宽，成了新的生产力上限。

## 三条建议与一点冷思考

1. **把每条指令当 onboarding 文档写**：背景、约束、验收标准三件套齐全，再按回车；
2. **先搭裁判，再放 agent 上场**：没有测试和 CI 的仓库，先补基础设施，否则你是在盲管理；
3. **复盘沉淀，形成飞轮**：反复纠正 agent 的点随手写进项目说明文件，三个月后新人（和 agent）的上手速度会明显不同。

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-10/c4e150318a8fc9ca.png)

最后一点冷思考：agent 不会淘汰工程师，但会重新分配权重——写代码的边际价值在降，「定义问题、讲清目标、立好验收标准」的能力在涨。过去这叫管理，现在它直接决定你的 agent 生产力。工具面前人人平等，管理能力面前，差距才刚刚开始显形。
