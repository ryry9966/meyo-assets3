## 背景

跑 OpenClaw 自动化任务久了你会发现，"重复执行"不是异常而是常态：调度器超时后重发、Agent 某一步失败后从断点重跑、MCP 客户端对同一个 tool call 重试、手动补跑昨天的任务。如果代码没为此设计过，结果往往是通知发两遍、表格多出重复行、目录里出现 `report_final_2.md`。

幂等性（Idempotency）就是针对这件事的：**同一操作执行一次和执行 N 次，系统的最终状态一致**。它是自动化系统"敢重试"的前提。

## 问题：哪些操作天然不幂等

先把常见写操作分两类：

- **天然幂等**：覆盖写文件、`mkdir -p`、upsert 数据库记录、按固定 key 写缓存。执行多少遍结果一样。
- **天然不幂等**：追加写、insert 新记录、计数器自增、发消息、调用创建型第三方 API。

多数事故来自第二类。典型链路：Agent 执行"抓数 → 生成报告 → 追加到汇总表 → 发群通知"，第 3 步超时，框架重试整条链，第 3、4 步就各执行了两次。

## 做法：四步把任务改造成幂等的

**1. 盘点写操作。** 把任务里每个"会改变外部状态"的动作列出来，标注幂等/不幂等。读操作跳过。

**2. 给非幂等操作确定幂等键。** 幂等键要能唯一标识"这次业务动作"，且重试时保持不变。推荐从任务元数据派生：`task_id + step_name + 业务主键`。不要用时间戳或随机 UUID——那样每次重试 key 都不同，机制直接失效。

**3. 在存储端落地。** 数据库用唯一约束 + upsert，让重复插入被直接拒绝；文件场景优先覆盖写，必须追加时先检查末尾内容是否已存在。不要只依赖"先查再写"，并发下两个请求可能都查不到，唯一约束才是兜底。

**4. 外部副作用单独处理。** 发消息、调第三方 API 无法靠存储约束兜底，需要一张"已执行"记录表：执行前写入意图（带唯一约束），成功后更新状态；重跑时看到 done 就跳过；停在 pending 且超过阈值的，视为失败允许重执行。下游原生支持幂等键的（不少支付、消息类 API 都有），优先用对方的。

一段最小示意：

```python
key = f"{task_id}:{step}:{record_id}"
try:
    journal.insert(key, status="pending")   # 唯一约束，重复则抛异常
except DuplicateKey:
    return  # 已执行过或正在执行，跳过
do_side_effect()
journal.update(key, status="done")
```

Agent 环节补一句：LLM 生成结果建议按"输入内容哈希"缓存，重跑时不重复消耗 token，也避免同一输入产出不同文本、导致后续派生的 key 漂移。

## 踩坑点

- **幂等键不稳定**：key 里混入时间戳、随机数，或派生自 LLM 输出，重试时 key 变了，等于没做。
- **check-then-act 竞态**：先查"是否存在"再写，两次重试间隔很短时会双双通过检查。用唯一约束兜底。
- **记录表与业务操作不一致**：先执行后记录，中间挂掉状态永远是"未执行"；先记录后执行可能卡在 pending，需要超时判定。
- **第三方幂等键有有效期**：超出窗口后重复请求照样生效，文档要看清。
- **过度设计**：纯读、覆盖写任务不需要这套机制，加了反而增加排查成本。

## 可复用建议

- 把 `run_id` / `task_id` 放进任务元数据，所有插件和 MCP 工具共享，幂等键从这派生。
- 在插件文档里把"是否幂等"当作和错误码同级的约定写清楚。
- 缺省策略排序：覆盖写 / upsert > 幂等键 + 记录表 > 分布式锁（锁只解决并发，不解决重放）。
- 每次改完任务，手动连续跑两遍，diff 一下产物——这是最便宜的幂等性测试。

## 总结

在自动化系统里，重试、重放、并发是常态而不是故障。幂等性不是锦上添花的架构优化，而是让"失败了就再来一次"这句话成立的地基。先盘点、定键、用约束兜底，大多数 OpenClaw 任务不需要分布式锁，就能做到安全重跑。
