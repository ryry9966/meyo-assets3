## 背景

E2E 测试是回归保障里最贵的一层：写起来慢，坏了更难修。团队常见的现状是——覆盖靠自觉，新人不敢动测试代码，页面一改版选择器全体阵亡。

Agent + MCP 出现后有了新解法：模型不再只是"生成测试代码的文本机器"，而是可以直接驱动浏览器工具（比如 Playwright MCP），先真实操作一遍页面，再落代码。这篇记录我们在 OpenClaw 里搭的协作流程，目标朴素：AI 产出的用例要**能跑、能过、能进主干**。

## 问题：直接"让 AI 写测试"为什么不行

把 PRD 丢给模型让它输出 Playwright 用例，多半会遇到三类问题：

1. **选择器靠猜**。模型没见过你的 DOM，写出来的 `.btn-primary:nth-child(3)` 要么跑不通，要么脆弱至极。
2. **断言拍脑袋**。只断言"元素存在"，用例永远绿但什么也没验证。
3. **无法自证**。生成的代码没人跑过，"看起来对"和"跑得通"之间隔着整个调试过程。

根因是：写 E2E 的前提是知道页面长什么样、行为是什么，纯文本生成恰好缺这一环。所以核心思路是让 Agent **先做，再写**。

## 做法：五步闭环

**1. 固定工具与上下文。** 在 OpenClaw 接入 Playwright MCP，配置固定 baseURL、测试账号和环境变量。目的是让 Agent 每次拿到同一套环境，避免"上次能跑这次不能"。

**2. 喂好例子而不是长指令。** 挑 2~3 个团队公认质量最高的现有用例放进上下文，外加一份简短测试规范（见下文"可复用建议"）。经验上，三个好例子比三段 verbose prompt 有效得多。

**3. 一个用例一个任务。** 不要说"把这个页面所有功能都测了"。按场景拆：单任务 = 单入口 + 单断言链。Agent 先用 MCP 打开页面、实际点一遍，把真实选择器和交互路径记录下来，再生成代码。

**4. 让它自己跑绿。** 生成后在沙箱执行测试，把失败输出（超时、元素未找到、断言差异）原样回传给 Agent 修复，循环直到通过。这一步价值最大——模型读报错改代码的能力远强于盲写。

**5. 人审断言语义。** 跑通 ≠ 测对了。最终 PR 重点看两件事：断言是否验证了业务语义（而不只是元素可见），边界与失败路径是否覆盖。

## 踩坑点

- **选择器退化**：修复循环里 Agent 会偷懒降级到 `nth()` 或文本匹配。要求 `data-testid` 优先、语义角色其次，写进规范强制读取。
- **等待逻辑混乱**：要么 `sleep(3000)` 死等，要么漏等。统一封装 wait 谓词，禁止裸 sleep。
- **一次给十个用例必塌方**：上下文一长，规范遵守率明显下降。串行小任务 + 每任务独立验证。
- **测试数据污染**：Agent 不会主动清理它创建的订单/草稿。要么给它隔离账号池，要么把清理做成固定 fixture。
- **"全绿"假象**：它可能把断言改松让用例通过。人审时先看 diff 再看结果。

## 可复用建议

1. **测试规范落成 repo 内文档**（选择器优先级、命名、断言模板、禁止事项），Agent 每个任务开头先读。这是所有约束里 ROI 最高的一条。
2. 写一个**选择器体检脚本**（校验唯一性、可见性），暴露成 MCP 工具让 Agent 生成后自查，比事后人肉 review 便宜。
3. 高频页面沉淀为 fixture/工具，别让 Agent 每次从零摸索登录流程。
4. 把"跑绿"授权给 Agent，把"合入"留给人——这条边界想清楚，协作才可持续。

## 总结

这套流程跑下来，单条 E2E 用例的成本降了一半以上，更值钱的是臆造代码几乎消失——Agent 先操作再写，选择器全部来自真实 DOM。经验概括成一句：**Agent 写测试的质量，上限取决于你给的约束和反馈闭环，下限取决于你敢不敢让它自己跑报错。** 它不替代测试设计，只是把"从想到跑"之间最枯燥的搬运工作接走了。
