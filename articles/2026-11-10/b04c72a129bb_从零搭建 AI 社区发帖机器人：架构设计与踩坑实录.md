## 背景

社区有几类固定产出：每周精选帖汇总、版本更新速览、活动预告。人工写了三个月后，节奏开始不稳——忙起来就断更，断更后再补，质量参差。于是决定做一个发帖机器人，目标是**半自动**：机器生成草稿，人工确认后发布。技术栈直接基于 OpenClaw 的 Agent + MCP 工具体系，没有自研框架。

## 问题

发帖机器人表面上是"调个 API 加个 cron"，实际难点不在生成，而在工程侧：重复发布、编造链接、频控超限、转义丢失、时区漂移。任何一项翻车都是社区可见的事故，撤帖比不发更难看。

## 架构与做法

整体分四层：

1. **调度层**：cron 触发，落一条任务记录，状态机为 `pending → generating → review → published / failed`，每步流转写库。
2. **生成层**：Agent 挂三个 MCP 工具——抓取器（拉取素材源）、检索器（查历史帖避免重复选题）、格式化器（Markdown 校验 + 链接可达性检查）。生成层只负责组织内容，不负责提供事实。
3. **发布层**：队列 + 指数退避重试 + 幂等键（发布窗口日期 + 素材内容 hash）。发布前支持 dry-run 输出预览。
4. **观测层**：prompt 进版本库带版本号，每次运行的输入输出落库，失败进人工队列。

关键决策：先以"草稿模式"跑两周，每篇人工点确认才发布，积累 30+ 篇样本后再逐步放开全自动。这个决定后来救了至少五次事故。

## 踩坑点

1. **重复发帖**。调度器超时重试，叠加"发布成功但回调丢失"，同一帖发了两次。修复：幂等检查上移到发布动作之前，不依赖回调状态。
2. **链接幻觉**。模型会编出格式完美但 404 的链接。修复：所有 URL 必须来自抓取器返回，格式化器对每条链接做 HEAD 校验，生成层禁止自由书写链接。
3. **时区**。cron 按 UTC 跑，发帖时间整体漂了 8 小时。修复：调度层显式声明时区，任务记录同时存 UTC 与本地时间戳。
4. **转义**。正文里的代码块含反引号和特殊字符，平台 API 吃掉部分转义导致排版崩坏。修复：格式化工具统一做白名单转义，不指望模型"记得转义"。
5. **Prompt 漂移**。每次改提示词，输出风格就变。修复：prompt 走版本库 + PR 流程，每次渲染结果截图存档，改前改后可对比。

## 可复用建议

- 幂等键 = 内容 hash + 发布窗口日期，发布前查重，别信任回调。
- 一切外部断言（链接、数字、版本号）必须来自工具返回值，模型只做组织，不做提供。
- 半自动起步，人工审满一个月样本再谈全自动。
- 失败默认不发：漏发一期周报无伤大雅，发错内容才是事故。
- 每步落库 + prompt 版本化，保证任何一篇已发布内容都能回放当时的生成链路。

## 总结

这个项目真正的工作量在发布链路的可靠性，不在内容生成。把 Agent 当成一个"会犯错的初级同事"来设计流程——给它工具、给它校验、给它复核环节——比把它当万能 API 靠谱得多。目前机器人稳定运行，全自动发布只对低风险内容开放，高风险内容仍保留人工确认。后续计划把选题检索和去重逻辑抽成独立 MCP 工具，供社区复用。
