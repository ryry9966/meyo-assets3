# 让 Agent 帮你写 E2E 测试：一套可复现的协作流程

## 背景

E2E 测试是全栈项目里最贵的一层：写起来慢，选择器脆弱，UI 改一版就要修一轮。多数团队实际只覆盖登录和核心下单链路，其余靠手工回归。MCP 浏览器工具普及后，“让 Agent 真实操作页面、顺手产出测试”变得可行。但直接丢一个 URL 给它，得到的往往是一堆断言薄弱、睡满 wait 的脆测试——工具能用了，工程方法没跟上。

## 问题

我们实际跑下来，Agent 裸写 E2E 有三个典型毛病：

1. **选择器靠猜**：生成 `class` 名和 `nth-child` 定位，UI 一动全崩。
2. **断言无效**：断“页面包含‘成功’”，却不校验业务结果（订单号、状态流转），测试永远绿，但不证明任何事。
3. **不稳定**：用 sleep 硬等动画和接口，CI 上随机挂，还把排障时间翻倍。

## 做法

我们收敛出一套流程：**先定契约 → Agent 探索 → 小批量生成 → 失败回灌 → 人工把关**。

1. **先定契约，再生成。** 仓库里放一份测试约定文档：命名规范、page object 结构、断言原则（必须断业务结果，禁止只断 DOM）、定位器只允许 `data-testid` 和无障碍 role。给 Agent 读约定文档，比喂全量代码有效得多。
2. **接 MCP 浏览器工具**（如 Playwright MCP），让 Agent 真实走一遍流程：点击、填写、抓网络请求。它输出的不再是想象中的流程，而是实际操作记录和验证过的定位器。
3. **按链路小批量生成**：一次一条用户流程，产出 page object + 用例。明确要求断言落在业务结果上——接口返回值、列表新增行、状态字段，而不是按钮文案。
4. **失败回灌**：trace、截图、报错栈直接喂回去让它自修。限制轮次（我们设 3 轮），修不好转人工，并且明令禁止用加重试和 sleep 来“修好”。
5. **人工 review 只看两样**：断言是否验了正确的事；数据准备是否确定（固定种子、独立测试账号）。选择器细节不用逐行看。

## 踩坑点

- **Agent 会顺着现有行为写测试**：页面本身有 bug，它照样断这个错误结果。给每条用例附一句业务预期，review 时对照。
- **自证循环**：它自己生成的随机订单号自己去查，永远通过。数据要么固定种子，要么等后端接口返回后再断言。
- **上下文别塞满**：整个 repo 喂进去，生成质量反而下降。约定文档 + 相关 page object + 单条流程描述，足够了。
- **会话状态污染**：MCP 浏览器里的登录态和脏数据，与干净 CI 环境不一致。生成的用例必须在 CI 重跑验证，不能只信 Agent 本地那轮全绿。

## 可复用建议

- 把“测试约定”当成 prompt 工程的一部分持续维护，收益比换模型大。
- 选择器契约（`data-testid`）先落地，再谈生成，顺序不能反。
- 失败回灌值得做成 CI 步骤：挂了自动产出 trace 包，Agent 提 patch，人只审断言改动。
- 优先覆盖稳定的核心链路，别指望 Agent 一口气铺满全站。

## 总结

Agent 确实把写 E2E 的边际成本压下来了，但测试质量的决定因素没变：选择器策略、断言设计、数据确定性。合理的分工是——人定义“什么是对的”，Agent 负责起草、探路和修葺。契约写得越清楚，这套协作跑得越久。
