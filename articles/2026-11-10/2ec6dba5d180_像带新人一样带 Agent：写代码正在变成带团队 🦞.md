最近 36kr 报道了 Anthropic 工程师的一篇长文，核心观点有点反直觉：想把 Coding Agent 用好，光会写 prompt 远远不够，你还得会「带人」——定目标、拆任务、给上下文、盯结果、做复盘。听起来像在招人，其实说的是你终端里那个会自己读代码、改文件、跑测试的智能体。这篇文章把这套逻辑拆开看看：为什么「管理能力」忽然成了工程能力的一部分，以及具体怎么练。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-10/637609c8229382d9.png)

## 从自动补全到「数字下属」：角色正在位移

先看背景。2021 年前后 Copilot 把 AI 带进编辑器，但那时它只是「副驾驶」：你敲键盘，它补全下一行，方向盘始终在你手里。2024 年之后，Claude Code、Cursor Agent 这类 agentic coding 工具把交互单元从「一行代码」换成了「一个任务」：你描述目标，Agent 自己规划、连续执行几十分钟、跑测试、提交 PR。

- **SWE-bench Verified** 是业内常用的「真实仓库修 bug」基准。2023 年主流模型的成绩还在个位数徘徊，到 2025 年，前沿模型已普遍超过 70%——两年涨了一个数量级。
- 能力上去了，多数人的用法却没变：还在用「聊天」的方式使唤一个执行者。
- 于是角色位移：你的产出不再按「写了几行代码」计算，而是按「派了几个任务、验收了几份结果」计算。打字员下岗，reviewer 上岗。

Anthropic 工程师的论断就来自这里：当 AI 从工具变成执行者，你和它的关系不再是「人用软件」，而是「人带新人」。

## 为什么「不会管理」就发挥不出 Agent

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-10/7600f353401890e8.png)

把 Agent 想成一个特殊的下属：速度极快、不用睡觉、知识面极宽，但没有任何隐性上下文，还有点过度自信。它有四个典型的「性格缺陷」：

1. **缺隐性知识。** 团队里「这个模块别动」「那段老逻辑是历史包袱」这类信息全在人脑里，不在代码里。Agent 读得到代码，读不到潜规则。
2. **过度自信。** 模型会一本正经地调用不存在的 API、编造配置项，在不熟的框架里尤其严重。它不是故意骗你，而是分不清「合理」和「真实」。
3. **长任务漂移。** 上下文窗口有限，任务一长，Agent 会渐渐忘掉最初目标，方向悄悄跑偏。
4. **输出质量正比于输入质量。** 你只给一句「把这个功能做了」，它就靠脑补补齐所有你没说的约束——补出来的东西往往「看起来对」。

这四条恰好是管理学教科书里的经典命题：目标设定、任务分解、上下文传递、过程检查、验收标准。所以那位工程师的判断并不玄：带过团队的人，把经验平移到 Agent 上就是降维打击；没带过的人，正好借 Agent 把这门课补上。

## 管理四件套：上下文、任务书、验证回路、检查点

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-10/7fb7e55eb8daf77e.png)

具体怎么落地？归纳成四件事，每一件都有管理学对应物。

**1. 上下文工程 = 新人入职培训。** Claude Code 有 CLAUDE.md，其他工具也有 AGENTS.md 之类的规则文件，相当于 Agent 的「员工手册」：构建命令、测试怎么跑、代码规范、目录结构、哪些地方是雷区。手册写得越好，每次派活的沟通成本越低——和给新人写 onboarding 文档是同一个道理。

**2. 任务书 = 需求文档。** 派活说清四要素：目标（做成什么样）、边界（不许动什么）、验收标准（怎么算完成）、已知坑（注意什么）。高手会先让 Agent 进 plan 模式出一份计划，确认后再放手让它写——先对齐方案再执行，返工率显著下降。

**3. 验证回路 = 让下属能自查。** 有测试、lint、type check、CI 的仓库，Agent 表现会明显更好：每改一步都能立刻知道对错，不用等人纠偏。反过来，零测试的老仓库里，它写完只能「自我感觉良好」。Agent 时代写测试的 ROI 直接翻倍：既是质量保障，也是导航仪。

**4. 检查点 = 带小组，而非盯个人。** 任务足够独立时可以并行开多个 Agent，像管几条产品线；但必须设检查点，每到一个里程碑就看一次 diff，而不是等 5000 行攒完再看——漂移发现越晚，返工越贵。同时，中途打断也有代价：上下文要重建，干预时机本身就是一门手艺。

## 四种典型的「管理失败」

对照四件套，反面教材很好认：

- **微观管理型：** 一句一句指挥，Agent 刚起手就被打断。你成了瓶颈，它永远没机会做整体规划，速度优势全浪费。
- **甩手掌柜型：** 一句「把这个功能做上线」就去喝咖啡，回来收获一个方向跑偏、自己发明了三套工具函数的巨型 PR。
- **中途换靶型：** 边做边改需求、随时插新想法，Agent 的上下文被反复冲刷，最后交出一个缝合怪。
- **只听汇报型：** 只信最后那句「一切正常，测试全部通过」，不亲自看 diff。Agent 的自我汇报永远偏乐观，验收责任始终在你。

这四种失败的共同点：都不是模型的错，而是管理动作缺位。

## 写在最后：三条建议

1. **像带新人一样建立信任。** 从有测试覆盖、边界清晰的小任务开始派活，观察它哪里翻车，再逐步放权；别一上来就把核心模块交给它。
2. **把「管理基建」当正经投入。** CLAUDE.md、测试、CI、文档，以前是锦上添花，现在是 Agent 的生产力放大器；补齐这些，等于给未来所有任务提速。
3. **保持手感，坚持读 diff。** 你能 review 的，才是你真正管的；如果连自己都看不懂 Agent 交了什么，那不叫管理，叫开盲盒。架构判断力和代码品味，比以前更值钱。
