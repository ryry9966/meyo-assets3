## 背景

OpenClaw 的主会话（main session）是一个长期上下文：聊天记录、系统提示、工具调用结果全都堆在这里。跑自动化任务、深度研究、批量处理时，很多人图省事直接在主会话里让模型连调几十次工具——上下文迅速膨胀、触发压缩（compaction），真正重要的用户偏好和历史决策被压没了。子 Agent（sub-agent）机制就是为此准备的：把重活分给一个独立 session，主会话只收结果。

## 问题：污染是怎么发生的

实践中常见的两条污染路径：

1. **上下文污染**：重任务在主会话内执行，海量工具输出挤占窗口，触发压缩，长对话的记忆质量直线下降。
2. **状态污染**：子 Agent 与主会话共享同一个 workspace，跑完顺手覆盖了 MEMORY.md 或配置文件，主 Agent 之后的行为被"改记忆"式地扭转，而且很难排查。

## 做法：三步隔离

**1. 独立 session 生成。** 用 `sessions_spawn` 派生子 Agent，它拿到全新的 session id 和干净上下文，与主会话互不共享历史。派生时把任务描述、输入材料、输出契约一次性写全，不要指望子 Agent"自己去翻主会话"。

**2. 工作区隔离。** 给子 Agent 单独的 workspace 目录，或在任务提示里明确"只允许读写 `/runs/xxx`，禁止触碰共享记忆文件"。注意：OpenClaw 的隔离默认是上下文级的，不是文件系统级的——文件边界要自己圈。

**3. 只回传摘要。** 约定子 Agent 的最终消息是一段结构化摘要（结论 + 关键数据 + 产物文件路径），完整输出落在它自己的 workspace 里，主会话拿路径不拿全文。验证方法：sessions 列表里能看到两个独立 session，主会话的 token 增长只有摘要那一段。

## 踩坑点

- **子 Agent 继承了共享 workspace**，跑完发现 MEMORY.md 被改了。第一次跑隔离任务，务必显式指定工作目录。
- **回传内容没约束**，子 Agent 把原始搜索结果整段塞进最终消息，主会话照样爆窗口。输出契约必须写进任务提示。
- **以为隔离等于安全**。上下文隔离不挡误操作：给子 Agent 的工具权限做收敛，删除、外发这类危险操作不放开。
- **并行子 Agent 写同一个文件**，产出互相覆盖。并行任务各自独立目录，最后由主会话合并。
- **没设超时**。子 Agent 卡住，主会话干等。派生时带上超时和失败兜底。

## 可复用建议

- 一句话判断要不要隔离：任务 token 消耗大、工具调用多、结果不确定——三者中一条，就考虑隔离。
- 主会话只保留"摘要 + 指针"，全文落盘到文件。
- 把子 Agent 任务提示做成模板，固定包含五项：任务、输入、工作目录约束、输出格式、超时。
- 定期 review sessions 列表，清掉僵尸 session。

## 总结

session 隔离的本质是控制信息流入：子 Agent 用干净上下文换执行深度，用输出契约换主会话的轻量。OpenClaw 提供了机制，但文件边界、工具权限、超时兜底这些"墙"，还是要靠使用者在派生时显式划清。建议先跑通一个最小隔离任务验证链路，再逐步推广到你的自动化流水线。
