## 背景

OpenClaw 这类常驻 Agent 和一次性对话机器人的最大区别，是它有持续的工作区和记忆。每次会话启动时，工作区里的几个 Markdown 文件会被注入上下文：`AGENTS.md` 管工作方式，`USER.md` 记用户偏好，而 `SOUL.md` 承担的是"这个人是谁"——身份、语气、价值排序和行为边界。

很多人初始化后直接用默认模板，跑几周开始出问题，才回头补这份文件。这篇帖子记录我重写 SOUL.md 的过程和结论。

## 问题

没有认真定义人格与边界的 Agent，常见症状有三类：

1. **风格漂移**。今天简洁明天啰嗦，中英文混用，称呼忽冷忽热。底模没变，但上下文里缺少稳定的人格锚点，行为就跟着最近几轮对话走。
2. **过度顺从**。随口一句"帮我把这个目录清一下"，它真的执行了删除类操作。提示词层面没有任何"什么不该做"的约束。
3. **人格与流程混写**。我最初把语气规则、工具规范、任务流程全塞进 SOUL.md，文件膨胀到几百行，每条规则都被稀释。

## 做法

我把 SOUL.md 控制在一屏以内，按六个段落写：

1. **身份一句话**：你是谁、为谁服务、服务范围。例："你是我的常驻助手，处理开发与日常事务，不提供医疗、法律类建议。"
2. **语气与语言**：用可验证的行为描述，不堆形容词。"默认中文，先结论后依据，回复尽量短"远比"简洁友好"有效。
3. **价值排序**：规则冲突时听谁的，例如"准确性 > 用户情绪 > 速度"。
4. **硬边界**：明确列出不做的事——不改系统配置、不主动私聊联系人、涉及资金的操作先确认。这几条是底线，措辞要绝对。
5. **失败时的行为**：不确定就说不确定，不编造；拒绝任务时给替代方案，不硬顶。
6. **与用户的关系**：协作定位，明确"不要谄媚、不要过度道歉"。

配套原则：SOUL.md 只写"是谁、不做什么"，`AGENTS.md` 写"怎么干活"（工具约定、流程细节）。职责分清后，两边的冲突少了很多。

## 踩坑点

- **写成散文**。早期我写了一堆"做一个温暖的存在"，模型不知道怎么执行。人格文件本质是行为规范，不是文学创作。
- **太长**。超过一两百行后，单条规则的遵守率明显下降。上下文是稀缺资源，这份文件每次会话都要重新付费。
- **靠提示词做安全**。SOUL.md 写了"不要删文件"，但真正的防线是工具权限和审批门。提示词是软约束，注入和绕过是常态。边界分两层：行为边界写 SOUL.md，权限边界交给权限系统。
- **频繁重写**。OpenClaw 默认允许 Agent 自己编辑这份文件，不加约束的自改会让它越写越"讨好"。我的做法是 git 管理：小改动放过，大改动人工 review，随时可回滚。

## 可复用建议

- 用"不满意的回复 → 转成一条具体规则"的迭代循环，比闭门写一份完美人格有效得多。
- 每条规则写成"场景 + 行为"，可执行、可验证。
- 硬边界用绝对措辞，软偏好用默认措辞（"默认……，除非用户明确要求"）。
- 定期 diff 一次，删掉被其他规则覆盖或从未触发过的条目。

## 总结

SOUL.md 不是给 Agent 的性格美化包，而是一份工程化的行为契约：身份、语气、价值排序、硬边界、失败行为，写清楚、一屏以内、版本管理、持续迭代。人格让它稳定，边界让它可控——而真正的安全，仍然要靠权限系统兜底。建议每个跑了一段时间的 OpenClaw 实例，都回头把这份文件认真重写一遍。
