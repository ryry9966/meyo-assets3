## 背景

内容生产交给 Agent 之后，真正花时间的环节往往变成了分发。AI 产出的是“标准 Markdown"，但公众号、知乎、掘金、静态站消费的却是各自的方言：front matter 字段、代码高亮方式、图片外链策略、表格与公式的支持度全都不一样。手工适配等于把自动化的最后几百米用人肉补齐，而且每次改稿都要重做一遍。

## 问题拆成三层

1. **结构漂移**：Agent 输出的 front matter 不稳定，字段缺失、类型漂移、多写少写都常见；
2. **元素支持差异**：表格、脚注、任务列表、数学公式在不同平台的命运完全不同；
3. **资产处理**：图片防盗链、平台图床、内联样式白名单，每个平台一套规则。

## 做法：单一事实源 + 适配器

- **约束生成**：system prompt 里固化 front matter 契约，或让 Agent 直接输出 JSON，再渲染成 canonical Markdown；
- **解析与校验**：gray-matter + remark-parse 解析，front matter 用 zod 校验；不通过就把校验错误喂回去让 Agent 自修复，而不是人手改；
- **AST 级适配**：不要用正则。每个平台写一个 remark transformer——标题层级重排、表格降级为列表、代码块按目标平台主题预渲染成带内联样式的片段；
- **资产归一**：图片统一下载、按内容哈希命名，公众号走上传接口把外链替换成平台 URL；
- **渲染报告 + 人工闸口**：每次转换输出一份“哪些元素被降级/丢弃”的清单，diff 预览确认后再发布。

这套东西可以封装成一个 MCP 工具（比如 `md_pipeline.render(target)`），Agent 侧一次调用产出多端格式；平台上传逻辑放进插件，主流程保持纯函数。

## 踩坑点

- 公众号对 HTML 白名单极严，剪贴板方案下内联样式会被裁掉，代码块要么预渲染成 `<section>`，要么直接转图片；
- 表格和脚注是重灾区：知乎侧基本要兜底，方案是降级为列表或截图；
- 数学公式别指望统一语法，KaTeX 渲染成图片是最稳的通用兜底；
- GitHub raw 图有防盗链，公众号外链图会裂，必须中转上传；
- 幂等性：管线重跑要能覆盖而非重复上传，用内容哈希做键；
- HTML 实体会二次转义：`&amp;` 套娃通常出在“先 escape 再渲染”的顺序上。

## 可复用建议

- canonical Markdown 进 git，adapter 视为纯函数（Markdown 进、平台 payload 出），天然适合快照测试；
- 每个 adapter 准备一份 fixture 文档，升级依赖或改插件时全量跑一遍；
- 保留渲染报告日志，上线后排查“这段怎么没了”能省一半时间；
- 校验失败优先走 Agent 自修复回路，比人工改 front matter 可靠。

## 总结

多平台发布的本质是个编译问题：canonical Markdown 是源码，各平台是目标架构，adapter 是后端。把格式适配从“复制粘贴手调”变成“管线自动转换 + 人工闸口”，AI 生成的内容才算真正具备分发能力。建议先拿最麻烦的平台（通常是公众号）跑通闭环，再横向铺 adapter。
