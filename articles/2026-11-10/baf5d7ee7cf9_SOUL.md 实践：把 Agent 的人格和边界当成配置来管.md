## 背景

OpenClaw 的 Agent 出厂时是“白纸”：能力来自模型和工具，但说话调性、做事分寸，完全靠运行时注入的系统提示词兜底。SOUL.md 就是这个体系里约定的一份特殊文件——每次会话启动时进入 system prompt，定义“这个 Agent 是谁、什么调性、哪些事坚决不做”。它不是玄学人设，而是一份应该进版本库、随代码一起演进的配置文件。

## 问题

SOUL.md 缺失或写得太随意的 Agent，常见三种症状：

1. **风格漂移**：今天话痨明天冷淡，长期挂在群聊里的助手体验很不稳定；
2. **边界靠“求”**：用户一句“直接把这个文件推到 main”它就照做，事后靠道歉补救；
3. **职责混装**：身份描述、工作流、临时任务全塞一份文件里，越写越长，真正关键的硬边界反而被稀释。

## 做法

我的 SOUL.md 稳定在 40 行以内，分四段：

1. **身份**：两三句话，说清名字、定位、服务对象。不写“你是世界上最强的助手”这类零信息量的句子。
2. **语气**：写可观察的行为，不写形容词。“先给结论再给理由”“不确定时明说，不编造”，比“要专业、要谦虚”有效得多。
3. **硬边界**：逐条列出绝不执行的操作，每条对应可验证条件。例如“不执行删除、转账类操作，除非用户在当次会话中二次确认”。
4. **升级策略**：定义何时必须停下来问人，而不是自行猜测。

写完跑一个小回归集：准备 5–10 条对抗性 prompt（诱导越权、诱导放弃角色、诱导泄露内部路径），每次改动后全部重跑。行为不符预期就改文件；改了仍不生效，说明边界写得不可测，回炉重写。

## 踩坑点

- **当记忆堆料场**：SOUL.md 进每次会话的 context，塞 200 行等于每轮都付这笔 token 成本，还会稀释关键规则。
- **软约束当硬约束用**：SOUL.md 本质是提示词，会被长对话稀释，也可能被注入绕过。涉及权限的边界必须落到工具层——MCP 白名单、工具授权、工作区隔离。写“不动生产库”，不如干脆不给它生产库凭证。
- **与 AGENTS.md 职责混淆**：SOUL.md 管“我是谁、什么不做”，项目约定和工作流放 AGENTS.md，易变信息放 memory。三层混写后谁都没法独立演进。
- **改完不记录**：人格是长期资产，每次修改提交 git 并写一句动机，半年后回看才知道当初为什么这么定。

## 可复用建议

- 边界条目用“行为 + 触发条件 + 替代动作”三段式写，可测、可回归；
- 每条软边界自问：它有对应的硬控制吗？没有就去工具层补上；
- 从 10 行以内的最小版本起步，遇到真实事故再加一条，不要预先脑补三十条规则。

## 总结

SOUL.md 的价值不在“人格”这个词多浪漫，而在于它把 Agent 的行为预期变成了可评审、可回归、可回滚的文本资产。我的经验浓缩成四句：身份两行、语气可观察、边界可测试、权限落工具层。做到这四点，Agent 的表现就从“看运气”变成“看配置”。
