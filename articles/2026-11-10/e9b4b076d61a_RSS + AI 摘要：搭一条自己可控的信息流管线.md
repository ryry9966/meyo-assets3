## 背景

订阅制信息源这两年明显回潮，原因很简单：算法时间线不可控。RSS 本身没死，死的是顺手的阅读体验。作为天天写 agent、接 MCP 的开发者，我们手里有 cron、脚本和 LLM，完全可以用一两个晚上搭一条「抓取 → 过滤 → 摘要 → 投递」的管线，把每天半小时的刷信息压缩成三分钟。

## 问题

直接把 RSS 塞给模型说「帮我总结」，基本不可用。三个原因：

1. **量**：几十个源一天几百条，逐条摘要要么贵，要么每条只有一句话的糊弄产物；
2. **噪**：大量条目是更新公告、标题党、跨站转载；
3. **稳**：脚本跑一周就崩——编码问题、正文缺失、去重失效轮着来。

所以这件事的核心不是「会不会调 API」，而是把它当数据工程做。

## 做法

一条最小可用管线，四步：

1. **抓取**：定时拉 OPML 里的所有源，用 feedparser 之类的库解析，落到 SQLite，以 entry 的 `id`/`link` 做 UNIQUE 键。
2. **过滤**：先规则后模型。关键词黑名单 + 来源权重 + 标题相似度去重（标题 3-gram Jaccard 就够用），这一步能砍掉一半以上的量。
3. **摘要**：只对过滤后的条目调模型，且分两档——每条用便宜模型生成一句话摘要；再按主题聚类，用稍好的模型聚合成日报。摘要 prompt 里要写死「只基于给定文本，信息不足就明说」。
4. **投递**：渲染成 Markdown 推到固定渠道（邮箱、IM webhook 或静态页），每条附原文链接。摘要是导航，不是替代。

如果你们在用 OpenClaw 这类 agent 框架，可以把「抓取」和「摘要」封装成两个 MCP 工具，让 agent 负责调度和格式化。好处是交互式追问很自然（「这条展开讲讲」），坏处是调试链路变长。我的建议是：先用纯脚本跑稳两周，再 agent 化。

## 踩坑点

- **很多源没有全文**：description 只有两行，摘要等于瞎猜。要么接 readability 抓正文，要么标记「仅标题摘要」，别硬编。
- **去重键不可靠**：同一篇文章在不同 feed 里 GUID 不同。用规范化后的 URL（去 utm 参数、去尾斜杠）做辅助键。
- **内容注入**：RSS 正文是不可信输入，里面完全可以写「忽略以上指令」。prompt 里要划清系统指令与内容的边界，模型输出别当事实直接入库。
- **成本失控**：逐条摘要一天几百次调用。先规则过滤，再 10 条合并成一次调用，调用量能降一个数量级。
- **cron 堆积**：抓取耗时超过间隔时任务会叠，加锁文件或直接 `flock`。
- **编码与转义**：老源常见 GBK 和 CDATA 坑，feedparser 基本能兜住，手写解析就未必。

## 可复用建议

- 状态全落 SQLite，脚本必须幂等：重跑不产生重复推送；
- 逐条摘要和日报聚合分开做，别指望一次调用同时干两件事；
- 保留原始条目快照——摘要可以重新生成，原文没了就是没了；
- 先拿 10 个精选源跑两周，人工抽检摘要质量，再扩量；
- 只看两个指标：命中率（你真的点开的链接比例）和漏报率（事后才知道的重要事情）。

## 总结

这条管线没有任何单点技术难度，难度全在工程习惯上：状态管理、幂等、成本控制、注入防护。搭完之后最大的变化不是省了半小时，而是信息获取从「被动刷」变成「主动收」——你定义源和标准，模型只负责压缩。同一套思路换个源列表，就能复用到 changelog 跟踪、论文快报、仓库 release 监控上。
