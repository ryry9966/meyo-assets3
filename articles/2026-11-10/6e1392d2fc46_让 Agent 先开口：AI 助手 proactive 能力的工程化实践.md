## 背景

多数助手仍是被动的：你提问，它回答。但对盯 CI、追 issue、出日报这类事，被动模式价值有限——真正需要的是“事件发生时它主动来找我”。随着 MCP 把外部系统（仓库、监控、日历、邮件）标准化成工具和事件源，proactive 不再是产品概念，而是一套可以动手搭的管道。

## 问题

主动 ≠ 定时跑一个 prompt。实践中真正难的是三件事：

1. 触发源怎么接、怎么防重复；
2. 触发后如何判断“要不要打扰人”；
3. 判断完能不能直接动手。

没有这三道闸门，proactive 会在一周内退化成噪音机器，然后被用户整个关掉。

## 做法

以我最近搭的一个“值守 Agent”为例：目标是在 CI 失败、重要 issue 有回复、每日站会前这三类时机主动介入。

**第一步：接事件源。** 用两个 MCP server：一个提供 webhook 订阅，一个提供 cron 调度。事件到达先写入去重表，key 用 `事件类型 + 资源 ID + 时间窗口`，挡住 webhook 重试带来的重复运行。

**第二步：先规则，后模型。** 事件进来先过确定性过滤器：标签、分支名、作者白名单，能直接淘汰的不进 LLM；剩下的边界样本（比如“这次失败算不算阻塞发布”）才交给模型裁决。实测调用量降到原来的十分之一，且规则部分行为可复现。

**第三步：三级响应。** 让模型只输出固定三选一：

```yaml
triage:
  output: ignore | notify | act
  act_allowlist: [label_issue, draft_reply]
  quiet_hours: "23:00-08:00"
  dedup_window: 24h
```

`ignore` 记日志不发消息；`notify` 发一条带上下文的消息（日志摘要、相关 diff）；`act` 只允许白名单动作，且一律落草稿或打标签，人确认后才生效——绝不直接对外写。

**第四步：限流。** 夜间只攒不发，早上合并成 digest；同一资源 24 小时内最多提醒一次；设每日预算上限。

## 踩坑点

- **触发风暴**：上游一次事故触发 40 个 webhook，直接打爆预算。解法：按资源聚合，窗口内合并成一次运行。
- **判断抖动**：同一事件今天 notify 明天 ignore，用户会觉得不稳定。结论是：凡能写成规则的别交给模型，模型只裁决边界样本。
- **上下文缺失**：proactive 运行没有对话上下文，容易答非所问。需要为每个触发源维护独立运行状态（上次处理结果），拼进 prompt。
- **权限过大**：一开始图省事给了写权限，它某次“顺手”关了个不该关的 issue。之后所有写操作一律走草稿 + 确认。

## 可复用建议

1. 先做 digest 再做 action：每日摘要先跑两周，看打开率，再逐步放开主动动作。
2. 响应阶梯固化成协议：ignore → notify → act，不允许模型自由发挥第四种。
3. 每个主动动作必须留痕：消息里带触发源、判断依据、动作链接，方便回溯。
4. 把“忽略”当一等公民：triage 的主要产出是 ignore，不是 notify。
5. 度量三个数——误触发率、通知采纳率、动作确认率，低于阈值就回退该触发源。

## 总结

Proactive 的核心不是更聪明的 prompt，而是触发设计、分级裁决、权限收口这三件工程活。先让 Agent 安静地帮你筛选信息，用数据决定给它多大动作权限——这样搭出来的主动性才留得住。
