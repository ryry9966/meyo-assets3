## 背景

用 Agent 做自动化，绕不开一个问题：模型本身只会"说"，真正落地的动作全部来自外部 API——查工单、发消息、读写数据库、触发 CI。对接质量直接决定了 Agent 是"能聊的 demo"还是"能干活的工具"。在 OpenClaw 这类框架里，这条链路通常由 skill/tool 和 MCP 承担，但实践下来发现，多数坑不在框架层，而在我们怎么"包"API。

## 问题

常见的失败模式有三类：

1. **认证裸奔**：把 API key 写进 prompt 或让模型可见的配置里，既容易泄露，也会污染上下文。
2. **描述失真**：工具 schema 写得太含糊，模型开始猜参数——数字传成字符串、时区搞错、枚举值自由发挥。
3. **边界缺失**：没设超时、没处理 429、非幂等接口盲重试，轻则卡死会话，重则重复下单。

本质是同一件事：把"人调用 API"的心智直接套到了"模型调用 API"上。但模型不会读文档，也不会主动来找你确认。

## 做法

我的做法是把对接拆成五步，核心原则一句话：**模型只做决策，wrapper 承担全部工程细节**。

**第一步：手动跑通。** 先用 curl 或 HTTP 客户端把接口调通，搞清鉴权方式、必填参数、分页规则和错误码。这步不能省，否则后面排查时分不清是 API 的问题还是封装的问题。

**第二步：选对接形态。** 简单的只读接口，直接包成 OpenClaw 的工具；接口多、需要跨场景复用、或社区已有现成实现的，优先接 MCP server。别为了一个接口专门起一个服务。

**第三步：写严格 schema。** 每个参数写清类型、单位、示例值和取值范围。时间统一要求 ISO 8601 或显式时区，金额写明币种，枚举值全部列出。工具描述是写给模型看的文档，写得越"笨"越不容易出错。

**第四步：认证隔离。** key 放环境变量或凭据存储，由 wrapper 在运行时注入，模型全程只见引用、不见明文。日志同样注意脱敏。

**第五步：wrapper 兜底。** 超时（一般 10–30 秒）、指数退避重试、限流处理都写在这一层；非幂等接口必须带幂等键，或者干脆不重试。返回体大的接口，在 wrapper 里先裁剪或摘要，再回给模型，别让一次查询塞爆上下文。

## 踩坑点

- **万能网关陷阱**：做一个"接受任意路径和参数"的工具看似省事，实际模型会频繁传错。一个工具做一件事，粒度小反而稳。
- **错误信息不可操作**：只返回 `error: 500`，模型没法自救。错误要结构化，最好附上"下一步该干什么"，比如提示补传分页游标。
- **分页当单次调用**：只取第一页就开始总结，结论以偏概全。要么在 wrapper 内聚合成完整结果，要么把游标显式暴露给模型。
- **缺 dry-run**：写操作类接口上线前没有预览模式，出问题只能靠回滚数据。凡是可以先"看一眼再执行"的，都值得加。

## 可复用建议

- 封装前先问三个问题：**谁鉴权？怎么失败？返回多大？** 答案基本决定了 wrapper 怎么写。
- 工具描述当代码维护：进版本库、走 review。它的每次改动都会直接影响模型行为。
- 上线先小流量：固定几个真实 case 做回归，比"看起来能跑"可靠得多。
- 记录工具调用的入参摘要和耗时，这是排查"模型为什么这么做"时唯一的线索。

## 总结

Agent 与 API 的握手，技术上是 schema、认证、wrapper 三件事；工程上，是把"模型的不确定性"关进确定性代码的笼子里。模型负责理解意图和选择工具，其余的可靠性细节都应该由你的代码保证，而不是指望模型的临场发挥。把这个边界画清楚，对接外部服务就从碰运气变成了可复现的工程活。
