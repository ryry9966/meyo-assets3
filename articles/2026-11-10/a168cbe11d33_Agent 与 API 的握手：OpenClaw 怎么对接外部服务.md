## 背景

OpenClaw 的核心循环是「模型推理 → 工具调用 → 结果回灌」。Agent 的能力上限，很大程度上取决于它能稳定调用哪些外部服务。MCP 把工具接入标准化了，但真正落地时，从选型到 schema 设计、再到超时重试，每一步都有坑。这篇帖记录我们把 OpenClaw 接到几个内部 REST 服务和第三方 API 的过程，沉淀一套可复用的做法。

## 问题

对接外部服务时我们遇到过几类典型故障：

- 模型选错工具或传错参数，调用成功率低；
- 第三方接口偶发超时，整个会话被卡住；
- 对非幂等接口重试，造成重复下单、重复建单；
- 接口返回大段 JSON，直接回灌撑爆上下文；
- 调试时密钥被打进日志。

这些都是工程问题，不是模型问题，解法也都在工程侧。

## 做法

**1. 选对接方式。** 三条路：MCP server（标准化、可跨项目复用，优先考虑）、OpenClaw 插件内定义 tool（需要精细控制参数校验和私有逻辑时用）、直接暴露 HTTP 调用工具（内网简单接口、一次性场景）。原则：服务会被多个 agent 复用就走 MCP，单一场景用插件 tool 就够。

**2. 写好 schema，尤其是 description。** 工具名用动词+宾语（如 `create_ticket`、`query_order_by_id`），description 写清「什么时候该用、什么时候不该用」，参数逐个标注类型、单位、必填性。我们踩过最大的坑就是一个描述太泛的 `search` 工具，模型什么都往里塞；把 description 从一句话扩成三行说明后，参数错误率明显下降。

**3. 认证放环境变量，不进对话。** 密钥通过配置/环境变量注入工具运行时，绝不写进 system prompt，也不在工具返回里回显。不同服务用不同凭证，方便单独吊销。

**4. 超时、重试、幂等三件套。** 每个工具显式设超时（我们默认 10s，长任务走异步）。重试只对幂等操作开启，指数退避；写操作一律带幂等键（用任务 ID 派生），服务端不支持就先查后写。

**5. 裁剪返回值。** 工具层做字段筛选和截断，返回给模型的是「做决策需要的最小信息」。错误也返回结构化文本（错误码 + 一句人话），让模型能自己判断该重试还是换路。

**6. 留观测。** 记录每次工具调用的入参摘要、耗时、结果状态，出问题时能回放，比翻聊天记录高效得多。

## 踩坑点

- **工具不是越多越好。** 挂到 20 个时模型开始选错，把同类接口合并成带 `action` 参数的单一工具后恢复。经验值：单 agent 10 个以内。
- **大响应是隐形炸弹。** 一个列表接口默认返回 200 条，第一次跑就吃掉大半上下文。工具层强制分页，默认 `limit=10`。
- **长任务别同步等。** 有个部署接口要跑 3 分钟，同步调用必然超时。改成「提交任务返回 ID + 轮询状态工具」的两段式。
- **日志脱敏要在工具层做**，别指望事后清洗。

## 可复用建议

- 上线前用固定 badcase 回归工具调用：错误参数、超时、权限不足各来一条；
- 每个工具配一个最小示例调用，放进 description 或 few-shot；
- 写操作工具单独加开关，默认只读；
- schema 版本化，改动时同步更新回归用例。

## 总结

Agent 对接外部服务，本质是把一次不可控的网络调用，包装成模型可理解、可重试、可观测的稳定原语。OpenClaw 与 MCP 提供了标准插座，但熔断、幂等、裁剪这些「电工活」仍要自己做。先把 schema 和错误路径打磨好，成功率提升比换模型明显得多。
