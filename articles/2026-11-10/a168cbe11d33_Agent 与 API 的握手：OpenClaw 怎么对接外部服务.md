## 背景

Agent 要产生真实价值，光会聊天不够——它得能查库存、提工单、调内部接口。OpenClaw 定位是连接消息渠道和 agent 的网关，真正的杠杆点在于：怎么把外部 API 变成 agent 手里趁手的工具。这篇整理一次给 OpenClaw agent 接第三方服务的完整路径，从选型到踩坑。

## 问题

直接对接常见三类翻车：

1. 把整份 API 文档塞进 system prompt，token 烧得快，模型还凭幻觉编参数；
2. 鉴权散落各处——key 出现在 prompt、配置、脚本里，泄漏面大；
3. 接口一超时就卡死，或 429 之后 agent 拿到乱码一样的报错，开始自由发挥。

根因是同一个：把"API"直接当成"工具"，没有做握手协议的转换。

## 做法

OpenClaw 提供三层对接方式，按成本从低到高：

**1. 快速验证：内置 exec / HTTP 工具。** 先跑通再说。让 agent 用 curl 调一个只读接口，确认网络、鉴权、返回结构没问题。不要在这一层上生产。

**2. 自定义 skill：内部接口首选。** 在 workspace 的 skills 目录里，一个动作一个工具。关键三点：

- 工具名用“动词 + 对象”，如 `create_ticket`，描述里写清参数单位、时区、日期格式；
- 参数用 JSON Schema 约束，枚举值直接写死，不给模型发挥空间；
- 执行逻辑里读环境变量拿 key，请求模板写死，模型只填参数。

**3. MCP server：标准化第三方服务。** 社区已有的 MCP server（GitHub、Notion 之类）直接挂载，省掉重复造轮子；自家业务接口建议自己包一层 skill 或 MCP，控制返回字段。

通用步骤收敛成五步：先 curl 手动跑通 → 收敛到 3~5 个动作 → schema 定参数 → env 管鉴权 → 看网关日志里的 tool call 记录，再灰度放量。

## 踩坑点

- **工具描述太模糊**。模型会瞎猜参数格式。写描述时假设读者是最较真的新人：写单位、写默认值、写失败时返回什么。
- **一次暴露几十个端点**。选择越多，幻觉越多。只暴露当前任务需要的。
- **返回 JSON 原样进上下文**。一个大响应能吃掉一半 token 预算。在 skill 里做字段裁剪和分页，只回传决策需要的字段。
- **非幂等接口没加确认**。下单、发消息这类操作，agent 失败重试就是重复扣款。要么工具层做幂等键，要么强制人工确认。
- **token 过期没刷新逻辑**。401 时把“需要重新授权”作为结构化信息传回，而不是让 agent 对着 HTML 报错页自由解读。
- **key 硬编码进 skill 提交到仓库**。用环境变量，push 前配 `.gitignore` 检查一遍。

## 可复用建议

- **一个动作一个工具**，粒度宁细勿粗；
- **错误信息里带“下一步建议”**：429 就写“等待 30 秒后重试”，403 就写“权限不足，请人工检查”，agent 的恢复行为会稳定很多；
- **先只读，后写入**：只读接口稳定跑一两周，再开放写接口并加确认环节；
- **MCP 处理标准服务，skill 处理自家接口**，别反过来。

## 总结

对接外部服务的核心不是“能不能调通”，而是三件事：控制面收窄（少而准的工具）、鉴权干净（key 只在 env）、错误可读（结构化 + 带建议）。Agent 与 API 的握手，本质是替模型把一份人类的 API 文档，翻译成一份机器可执行、可恢复的协议。做完这一步，agent 才算真正接上业务。
