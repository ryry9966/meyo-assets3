## 背景

Agent 会推理、会写代码，但在“碰外部世界”这件事上，它只依赖一层很薄的接口：工具调用。在 OpenClaw 里对接外部服务主要有两条路：**MCP server**（标准化协议，工具自动被发现和注入）和**自定义 skill**（在脚本里直接包一层 HTTP 调用）。本文以一个典型场景为例——让 agent 每天查询监控 API 并汇总告警——记录一次从零到稳定运行的对接过程。

## 问题

新手对接通常卡在三处：

1. **认证**：key 放哪，怎么保证不进模型上下文；
2. **工具描述**：模型不是每次都调对，参数经常瞎填；
3. **失败处理**：超时、限流、半截数据，模型拿到 stack trace 就开始自由发挥。

## 做法

**步骤一：选路径。** 能用 MCP 就用 MCP。在 gateway 配置里注册 server 后，工具名、入参 schema、描述会自动暴露给模型。只有 MCP 覆盖不了的场景（比如依赖本地状态的胶水逻辑）才写 skill。

**步骤二：拆工具粒度。** 不要把一整个 REST API 包成万能工具。按模型的视角拆：一个工具一个动作，`alert_list`、`alert_ack`，而不是 `call_api(path, method, body)`。工具多时加统一前缀做命名空间，如 `monitor_alert_list`。

**步骤三：认证走环境。** key 放环境变量或密钥文件，server 进程启动时读取。永远不要让 key 出现在对话里——上下文会被持久化和记日志。

**步骤四：描述写给人看，也写给模型看。** 好的描述 = 使用时机 + 参数约束 + 返回结构：

```json
{
  "name": "monitor_alert_list",
  "description": "查询未恢复告警。仅在用户明确要求告警或故障信息时调用，不支持历史区间查询。"
}
```

“什么时候**不**调用”这句话比“什么时候调用”更省 token，也更防误触。

**步骤五：错误结构化返回。** API 报错时不要把异常直接抛给模型，包一层：`{"error": "rate_limited", "hint": "60s 后重试"}`。模型读得懂 hint，会自行安排节奏。超时设在 server 侧（如 10s），别让挂起的请求占住整轮对话。

## 踩坑点

- **返回数据太大**：一次拉全量列表，几轮就撑爆上下文。默认分页 + 截断 + 只给摘要字段。
- **写操作没确认**：一次幻觉调用就可能删掉配置。所有 POST/DELETE 类工具必须幂等，或强制二次确认参数。
- **重试风暴**：模型看到 `rate_limited` 会立刻重试。退避逻辑放在 server 侧，别指望模型自觉。
- **日志缺失**：把每次工具调用的入参、耗时、状态码落到本地日志，排障时这是唯一真相。

## 可复用建议

对接 checklist，每次新增服务过一遍：

- [ ] key 只存在于环境/密钥文件
- [ ] 每个工具写清“何时用 / 何时不用”
- [ ] 读操作有分页和截断
- [ ] 写操作幂等或需确认
- [ ] 超时、限流在 server 侧兜底
- [ ] 工具调用有本地日志

## 总结

Agent 与 API 的握手，本质是把一个不稳定、有副作用的外部世界，翻译成模型能理解的、边界清晰的工具集合。协议层（MCP）解决“怎么连”，工程层解决“怎么连得稳”。先拆粒度、管好密钥、把错误说成人话，剩下的交给迭代。
