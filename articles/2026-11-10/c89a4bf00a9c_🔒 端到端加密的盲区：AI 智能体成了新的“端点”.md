最近一个话题在技术圈刷屏：端到端加密（E2EE）也挡不住 AI？这事听起来矛盾——Signal 里聊天，中间服务器只能看到密文，这是过去十年隐私工程最扎实的胜利。然后你装了一个 AI 助手：“帮我读邮件、总结聊天记录、安排下周日程。”它干得非常好，前提是它能读懂明文。矛盾出现了：密码学没被攻破，你的明文却在系统里跑了一整圈。这不是加密的失败，而是威胁模型被改写了——Personal Agent 自己成了那个新的“端点”。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-10/f55f06c0a6f3f1c8.png)

## 一、E2EE 的承诺边界：它到底保证了什么

先复习原理，再谈失效：

- 密钥只存在于通信两端。Signal 协议用 X3DH 做身份协商、Double Ratchet 做前向保密——哪怕某把私钥泄露，历史消息也解不开。
- 服务器、运营商、Wi-Fi 节点都只是“哑管道”，看不见内容。
- 时间线：2013 年后 E2EE 加速普及，WhatsApp 于 2016 年全量接入 Signal 协议，iMessage、RCS 相继跟进。

关键在于威胁模型里的一条隐含假设：**端点是可信的**。加密保护的是管道，不保护管子两头的你。设备被装了键盘记录器，密文再漂亮也没用。工程师圈的老话：密码学解决“路上没人偷看”，从不承诺“屋里坐着谁”。

## 二、Agent 的任务描述，就是“必须看见明文”

个人 Agent 要总结聊天，就得读聊天；要订机票，就得看日历和邮件。它的有用性和明文访问权成正比——这是岗位要求，不是漏洞。三种部署形态，隐私水位完全不同：

1. **端侧模型**：模型跑在手机 NPU 上，明文不出设备，最接近 E2EE 的信任边界。代价是能力有限，且读屏（accessibility API）会把跨应用内容在本地聚合。
2. **端云混合**：本地做简单任务，复杂任务把上下文送到云端大模型推理。此时明文（或近似明文的上下文）离开了加密保护区，进入“靠隐私政策承诺保护”的区域。
3. **第三方 Agent + API/MCP**：你给它 OAuth 授权，它的服务器就成了又一个持有多应用明文的“端点”。E2EE 的防线按通道画，Agent 的视野按你这个人画。

## 三、泄漏不靠破解，靠三条“合法通道”

1. **云推理通道**：prompt 上下文上传后，推理集群可能记日志、做缓存、用于模型改进。厂商承诺“不存储”，那是合同承诺，不是数学保证——两者的可信等级差着好几个数量级。
2. **记忆与聚合通道**：Agent 的长期记忆（memory）是游离在 E2EE 之外的新数据库。更隐蔽的是聚合推断：单看一条加密聊天没什么信息量，但“周五下午有空”（聊天）+ 日历 + 常去地点 + 购物邮件拼在一起，就是一份画像。
3. **代理与注入通道**：prompt injection——一封恶意邮件或一个网页就能指挥 Agent“把当前上下文发到某地址”。Agent 手里握着 token，被注入后等于一个替别人干活的超级端点。这不是攻破密码，是让工具做它本来就会做的事，只是换了个主人。

历史参照：90 年代的 Crypto Wars 赢的是数学，2016 年 Apple 与 FBI 之争争的是设备端点；Agent 时代，“端点”的数量和形态被指数级放大，战场从管道挪到了授权。

## 四、技术自救路线，以及它们的真实水位

- **端侧小模型 + 能力分层**：简单任务本地跑，敏感原文不出设备。Apple 的 Private Cloud Compute 给出了值得抄的作业：云端推理承诺无状态、可验证构建、远程证明（attestation），把“不存储”从条款变成可审计的工程结构。
- **TEE / 机密计算**：Intel SGX/TDX、AMD SEV-SNP、NVIDIA H100 的 confidential computing，让推理跑在内存加密的飞地里，连厂商自己也看不到明文。代价是性能损耗与生态成熟度。
- **全同态加密（FHE）**：直接在密文上计算，理论最优，但推理开销通常在千倍量级以上，离消费级应用还有距离。
- **MPC / 差分隐私 / PIR**：适合检索与统计类场景，不是通用解。

一句话判断：密码学给的是原语，工程给的是水位。未来两三年，“端云分层 + TEE + 可验证承诺”大概率是主流组合拳。

## 五、冷思考与三条建议：把授权当权限管理

冷思考先行：E2EE 回答的是“谁能看管道”，Agent 时代的问题是“你授权了谁、粒度多细、能否撤回”。商业上还有一层真实冲突——个性化需要数据，数据最小化要砍数据；隐私政策是承诺，架构才是机制。防线要画在系统里，别只写在条款里。

三条可以直接执行的建议：

1. **最小授权 + 可撤销**：给 Agent 的 API scope 选窄的——只读、单应用、限时限域，别把邮箱、日历、聊天一键全授给一个第三方 Agent。定期去账号设置里翻 OAuth 授权清单，不用的立刻撤销。
2. **按敏感度分层路由**：摘要、整理、格式转换交给端侧小模型；涉及原文出设备的任务，优先选有无状态承诺、TEE 或可验证构建的供应商——读架构文档，别只看营销页。
3. **把 Agent 的“记忆”当数据库管理**：定期清理，留意跨应用聚合的推断风险。单独一条消息无害，聚起来就是画像——加密保护的是每一次传输，而 Agent 看的是你这个人。

最后一句龙虾式总结：壳再硬，也架不住你主动把肉递出去。管好每一次授权，比换一把更长的锁有用。
