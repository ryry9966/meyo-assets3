## 背景

RSS 看起来老旧，但依然是最稳定、不依赖平台算法的分发协议。我的订阅源分布在技术博客、GitHub Releases、几个周刊，加上 RSSHub 兜底的页面，总量 40+ 个源。每天手动刷一遍标题要半小时，不刷又怕漏掉关键版本更新。

OpenClaw 的定时任务 + Agent + MCP 能力，恰好能把「拉取—清洗—摘要—推送」整条链路自动化。这篇记录我踩出来的管线。

## 问题

直接把 RSS 条目丢给模型摘要，效果并不好：

1. **噪音大**：同一个项目可能同时出现在 Releases、博客、周刊里，重复条目多；
2. **正文缺失**：不少源只输出截断的 snippet，模型只能基于标题编；
3. **成本不可控**：40 个源 × 全文喂 LLM，一天轻松几万 token；
4. **产物难消费**：模型输出一堆散文，落到 IM 里还是不想看。

## 做法

管线拆成四个解耦阶段，全部跑在一台 VPS 上：

**1. 拉取（每 30 分钟）**
Agent 定时触发，通过 MCP 的 RSS fetch 工具拉全部源，写入 SQLite，以条目 GUID / 链接 hash 做唯一键，天然去重。没有全文的条目标记 `needs_fetch`。

**2. 正文补全（紧接着）**
对 `needs_fetch` 的条目抓原页，readability 提取正文，超 64KB 截断。抓取失败保留 RSS 自带摘要，状态写 `partial`，重试不超过两次。

**3. 摘要（每天 08:00 一次）**
不要逐条摘要。把一天攒下的条目按源分组，先做一轮「源内粗筛」：Agent 用 JSON 输出每条的 `title / one_line / relevance(0-3) / reason`，低于 2 的直接归档。然后只把 relevance ≥ 2 的条目（通常 10–20 条）汇总成日报：按主题聚类、每条两句话、附原文链接。

**4. 推送（08:10）**
日报渲染成 Markdown，推到 Telegram，同时落一份本地文件留档可检索。

关键设计是**采集高频、消化低频**：拉取便宜，摘要贵，分开调度后成本可控。

## 踩坑点

- **幻觉主要来自空正文**。早期没做 `partial` 标记，模型对着一个标题编出整段摘要。后来在 prompt 里强制：无正文条目只允许输出标题翻译加一句「正文获取失败」。
- **去重不能只靠链接**。同一篇文章在不同源的 URL 带 tracking 参数，先做 URL 规范化（剥掉 `utm_*`）再按 hash 去重，重复率下降明显。
- **结构化输出要校验**。Agent 偶尔在 JSON 里夹带解释文字，解析失败时重试一次并把 temperature 降到 0，基本能救回来。
- **RSSHub 路由会静默挂掉**。失效路由返回的是 HTML 错误页而不是报错，fetch 后加了内容嗅探（是否含 `<item>`），失效源自动标记，并在周报里提示我换路由。

## 可复用建议

1. 状态落库，不要只存「最近一条」——重跑、补采、审计都需要历史；
2. 让 Agent 输出结构化 JSON，下游过滤和渲染才稳定，散文留给最后一层日报；
3. 相关性打分比摘要更省钱：先粗筛再精读，token 成本能砍掉 80% 以上；
4. 每个阶段独立可触发，方便单独重跑某一步排障。

## 总结

管线跑了一个多月，日均日报 15 条左右，token 成本每天不到一块钱。它没有让我「读得更多」，而是让我敢于订阅更多源——反正粗筛会挡掉大部分。RSS 的价值在于稳定和自主，OpenClaw 的价值在于把稳定的原料变成愿意每天看的成品。两者凑一起，刚好。
