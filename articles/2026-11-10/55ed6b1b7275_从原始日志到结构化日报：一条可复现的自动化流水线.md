## 背景

团队每天要一份“昨天发生了什么”的日报：错误计数、慢查询 Top 5、发布记录、未恢复告警。最初靠人肉翻日志拼凑，二十分钟起步，口径还不稳定。后来我们把它交给 OpenClaw 的定时任务 + Agent + 插件链路，做成每天早上自动跑的流水线，稳定运行一个多月。本文记录做法。

## 问题

把日报丢给 Agent 最容易犯的错，是直接说“帮我看看今天的日志”。实际会遇到三类问题：

1. 日志量大，塞不进上下文，模型只能看到片段；
2. 让模型数数（错误多少条、环比多少）不可靠，LLM 不擅长精确统计；
3. 输出格式漂移，今天是 Markdown 明天变成散文，没法归档比对。

结论：**统计交给脚本，解释交给模型，格式交给模板。**

## 做法

流水线四步，前三步是确定性的，只有第四步过模型：

1. **先定 schema，再写代码。** 列清楚日报字段，同时定义中间产物 `digest.json` 的结构，带版本号。
2. **采集与聚合（纯脚本）。** Python/shell 拉取昨天日志，按时间窗过滤，聚合出计数和 Top N，写入 `digest.json`。这一步不经过任何模型，可单测。也可以封装成 MCP 工具给 Agent 调，但我们刻意没这么做——采集是确定性的，放脚本里更稳。
3. **采样。** 按类别从原始日志各抽 3~5 条代表性样本（比如最新几条 ERROR），和 digest 一起作为模型输入。
4. **Agent 撰写。** 定时任务触发 Agent 读取 digest + 样本，按固定模板填报告。提示词明确：数字只能来自 digest，禁止推算；模板段落不可增删；输出写到 `reports/YYYY-MM-DD.md`，随后插件经 webhook 推送到群频道，digest 与报告按日期归档。

## 踩坑点

- **时区。** 日志是 UTC，日报按本地日切，第一天就漏了早上八点前的数据。现在采集层统一转固定时区再做日切。
- **日志格式漂移。** 某服务改了日志结构，解析率掉到 60%，流水线照样“成功”产出半空的报告。加了守门逻辑：解析率低于阈值时告警并把报告标记为 degraded，而不是静默出错报告。
- **空数据 ≠ 失败。** 周末没流量，digest 为空，之前会触发重试刷屏。区分三种状态：正常、空数据（照常出报告并注明）、异常（告警且不出报告）。
- **模板漂移。** 模型偶尔“热心”补分析段落。temperature 调 0，模板列为不可变部分，输出前脚本校验段落标题齐全。
- **定时任务静默挂掉。** cron 死了没人知道。加心跳：任务结束必须发一条推送，哪怕内容是“今日无异常”。

## 可复用建议

- **digest 先行。** 结构化中间层是整条流水线的核心：可单测、可复算、可归档；模型只是它的翻译官。
- **接新数据源 = 加字段，不改流程。** 新服务日志接进来，只是聚合脚本多算几个字段，提示词和模板基本不动。
- **报告可重放。** 保留 digest 归档，换模型或改提示词后可离线重跑对比，不依赖线上日志还在不在。
- **幂等。** 同一天重跑覆盖旧文件而不是追加，文件名带日期天然实现。

## 总结

这条流水线的本质是分层：确定性脚本负责“算”，模型负责“说”，模板负责“稳”。LLM 的价值在于把结构化数字翻译成人愿意读的叙述，而不是替你数日志。把统计从模型手里拿走后，准确性和格式漂移问题基本一次性解决，剩下要维护的只有日志格式变更时的适配。
