## 背景

让模型返回结构化数据是 Agent 插件的日常：OpenClaw 的 skill 里让子任务输出 JSON、MCP 工具结果的汇总、多 agent 之间的中间格式传递，大多靠"约定标签 + 解析"。提示词里写"把结果放在 `<result>` 标签内，只输出 JSON"，看起来很稳。

## 问题

生产环境的模型输出是概率性的。同一个提示词，你可能收到：

- ` ```json ` 围栏包裹的 JSON
- 裸 JSON，前后带一句"以下是结果："
- `<result>` 标签，里面还套了一层围栏
- 两个 JSON 块（一个草稿一个最终）
- 尾逗号、中文引号、字符串值里含换行

happy path 的正则只覆盖其中一种，其余全变成线上 parse error。这类故障的特点：低频、难复现，且常在改提示词或换模型后集中爆发。

## 做法：分层解析，而不是单点正则

核心思路是把"提取"和"校验"分开，提取层按成本从低到高逐级降级：

1. **预处理**：去 BOM、零宽字符、首尾空白，统一换行。
2. **直接 parse**：先试 `json.loads(raw)`，有些模型就是不给围栏。
3. **标签提取**：非贪婪正则匹配 `<tag ...>...</tag>`，取最后一个匹配——模型常在解释文字里复述标签。
4. **围栏提取**：逐行扫描的 ` ``` ` 状态机，别用 `re.DOTALL` 一把梭，字符串值里出现 ` ``` ` 会把贪心匹配撑爆。
5. **括号配平**：从第一个 `{` 或 `[` 起做计数扫描，取出第一个配平片段，兜底"前后带说明文字"的情况。
6. **修复层**：尾逗号、智能引号交给 json-repair 这类库，别手写全局替换。
7. **Schema 校验**：parse 成功 ≠ 数据正确，用 pydantic/zod 校验字段类型，失败同样走降级。
8. **反馈重试**：把报错信息和原始输出回灌给模型，附格式示例再要一次；连续失败则换更强模型或转人工。

每次解析记录命中了哪一层（`source_format`），这就是格式漂移的监控指标。

## 踩坑点

- **贪心正则跨块匹配**：` ```(.*)``` ` 会把两个独立代码块之间的正文也吞进来，用非贪婪并取最后一个闭合。
- **别全局换单引号**：字符串里的撇号（it's）会被一起改坏，交给修复库。
- **返回 list 还是 dict**：`json.loads` 返回数组而代码按对象取键，静默出错，schema 校验兜住。
- **多 JSON 块取第一个**：通常最后一块才是模型"想清楚之后"的版本。
- **标签嵌套围栏**：`<result>` 里包 ` ```json `，先剥标签再剥围栏，顺序别反。

## 可复用建议

- 解析收敛到一个模块，插件内禁止散落 `json.loads`。
- 返回 `ParseResult`（value / source_format / raw / error）而非裸抛异常，失败时把 raw 落盘。
- 用线上真实失败输出建 golden test，每次改提示词跑一遍，失败样本就是最好的测试资产。
- 提示词侧照常加固（few-shot、低温度、"只输出 JSON"），但把它当概率优化，不当正确性保证。
- 运行时支持结构化输出或工具调用约束解码时优先用，标签解析降级为 fallback。
- parse 失败率接入监控，超阈值告警。

## 总结

LLM 输出解析的正确姿势不是"写一个更聪明的正则"，而是承认任何单一格式约定都会被打破：预处理 → 多级提取 → 修复 → schema 校验 → 带反馈重试，每层便宜、独立、可观测。把失败样本沉淀为测试语料，解析层就从最容易坏的胶水代码，变成最让人放心的一层。
