## 背景

OpenClaw 的 agent 默认带文件读写和 shell 执行能力，跑自动化任务时往往长时间无人值守。这类场景最大的风险不是"答错了"，而是"删错了"：一次路径解析失误、一个展开错误的通配符，破坏就是即时且不可逆的。

## 问题：prompt 不是安全边界

"请谨慎删除文件"这类系统提示词属于行为约束，不是安全机制。模型会犯错，注入会改写指令，第三方插件可能携带激进的工具描述。所以 OpenClaw 的设计前提是：不假设 agent 可靠，而是假设它一定会出错，然后用沙箱把出错的爆炸半径限制住。

## 做法：四层防御

1. **路径层**：所有文件工具以 workspace 为根。每个路径先 realpath 归一化，再校验是否落在 root 内，越界一律拒绝。软链接解析之后再校验，防止符号链接逃逸。
2. **工具层**：删除类操作走独立工具，默认 soft-delete（移入 `.trash/` 而非直接 unlink）；批量写入或删除先 dry-run 返回影响清单，确认后才落地。
3. **执行层**：exec/shell 在独立沙箱中运行（容器或受限用户 + 最小化挂载）。关键认知：文件工具的路径校验对 shell 无效，`rm -rf $DIR` 一旦变量为空就能绕过一切，所以 exec 必须单独隔离，敏感目录只读挂载或干脆不挂载。
4. **确认层**：破坏性操作升级到 human channel。确认必须由人在对话里发起，agent 不能调用某个工具"替你批准"自己。

## 踩坑点

- **symlink 逃逸**：workspace 里放一个指向 `$HOME` 的软链接，前缀校验直接失效。必须对最终目标做 realpath，而不是校验传入字符串。
- **只防文件工具、裸奔 shell**：最常见的半吊子方案。shell 是天然的绕过通道，单独给文件工具加校验意义有限。
- **确认闭环**：agent 生成确认请求、又自己回复"yes"，等于没确认。确认事件必须路由到真人会话。
- **挂载过宽**：把整个 HOME 挂进沙箱，沙箱等于白做。按任务需要逐目录挂载。
- **策略滞后**：权限策略热更新后，旧 session 可能还持着旧 policy，改完配置建议重启 agent 再放权。

## 可复用建议

- agent 永远不要跑在你自己的登录用户下，专用用户或容器起步。
- 删除一律先进 trash，定期清空；批量操作前做快照。
- exec 做白名单（允许的命令模式），而不是黑名单——黑名单永远列不全。
- 所有文件变更落审计日志；定期做一次"恢复演练"，备份能还原才算有备份。
- 每个 MCP server、每个插件按最小能力授权，不要共享同一个高权限 agent 身份。

## 总结

OpenClaw 防误删靠的不是模型听话，而是四层互相冗余的机制：路径校验挡越界，工具层软化破坏，沙箱兜住 shell，人审兜住最后一步。任何一层都可能被绕过，但四层同时失效的概率足够低。一句话概括这套模型：**把 prompt 当 UX，把 sandbox 当安全边界**。
