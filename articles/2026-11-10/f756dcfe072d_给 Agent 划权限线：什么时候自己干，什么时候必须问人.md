## 背景

Agent 接上 MCP 和插件之后，能力从"聊天"变成了"动手"：读文件、写文件、调外部 API、发消息、跑 shell。每个接插件的人迟早都会碰到同一个问题——这个工具，到底要不要让模型直接调？

## 问题：两个极端都会翻车

实践中容易走两个极端。

一是什么都要求确认。agent 每调一次工具就弹一次审批，三天之后审批就退化成"全选通过"，等于没审。二是什么都不问。直到某天模型把测试环境的清理脚本跑到了生产库上，才知道炸了。

前者是审批疲劳，后者是爆炸半径失控。根本矛盾在于：模型只判断"这一步能不能做完"，不理解"做错了能不能回来"。

## 做法：三层权限模型

我们在 OpenClaw 环境里按"工具 × 参数"粒度划线，而不是按 agent 整体授权：

| 层级 | 典型操作 | 处理方式 |
|---|---|---|
| 自主执行 | 只读查询、沙箱内可逆写、已开 dry-run 的调用 | 直接放行，不打扰人 |
| 先看再做 | 批量写文件、依赖安装、大范围重构 | 先输出 diff/计划，人工确认后整批执行 |
| 必须人工 | 删数据、生产写入、对外发送、凭据相关操作 | 工具层硬拦截，强制走审批队列 |

划线时问四个问题：做错了能不能一键回滚？影响范围是否只限于本会话？结果是确定的还是模型猜的？失败成本是多少？任何一个答不上来，就往上一层挪。

落地步骤：

1. MCP server 侧给每个工具标注读写属性和作用域（本地/远程、单条/批量）；
2. 工具网关按标注做 allowlist，第三层操作在网关处拦截，不依赖 prompt 约束；
3. 第二层走审批队列，审批界面必须展示关键参数——目标路径、影响条数、目标环境，而不是只给一句"是否允许执行"；
4. 所有调用落审计日志，含参数和审批人。

## 踩坑记录

- **别把权限约束只写进 system prompt。** prompt 是建议不是边界，长上下文里模型会忘。硬边界只能做在工具层。
- **"只读"不等于"无副作用"。** 有些 GET 会触发 webhook 或写统计，接第三方 MCP 前先看文档再定性。
- **diff 太大等于没审。** 一次改 40 个文件，人只会点"通过"。第二层要限制单次批量和单文件 diff 规模，超了就拆批。
- **会话内授权别永久记住。** "本次会话允许"合理，跨天跨任务继续有效就是隐患。
- **审批疲劳是分层错误的信号。** 一天弹窗超过十次，说明该放行的没放进第一层。

## 可复用建议

- 默认最小权限：新工具先挂第二层观察一周，再决定是否下放。
- 按工具+参数控权，不按 agent 控权——同一个 agent 在不同任务里需要的权限不同。
- 给每个不可逆操作配一个"安全版本"（dry-run、回收站、影子环境），让模型先走安全版本。
- 审计日志记全参数，出事后能还原完整决策链。

## 总结

权限边界不是"信不信任模型"的问题，而是工程问题：用可逆性和爆炸半径分层，把硬约束放进工具层而不是 prompt，把人的注意力留给真正不可逆的少数操作。agent 自主性的上限，取决于你为它的失败预留了多少缓冲。
