## 背景

我们的 OpenClaw 助手跑了一年多，`memory_recall` 是调用频率最高的工具之一：用户随口提到"上次那个部署脚本"，agent 需要从几百条历史记忆里捞出对的那一条。最初我们只用了语义搜索（embedding + 向量库），后来加上了全文搜索，本文记录两者的实测差异和最终的混合方案。

## 问题

两条路各有翻车现场：

- **纯语义**：用户问"那个报错怎么修的"，返回了三条内容相近但完全无关的调试记录，还漏掉了唯一含精确错误码 `E-4021` 的那条。向量相似度对"改写过的意思"友好，对"精确 token"不敏感。
- **纯全文**：用户说"帮我找上次聊缓存策略的记录"，但当时原文用的是"Redis 过期"，关键词对不上，直接空手而归。

单选哪边都有明显盲区。

## 做法

最后落地的是**路由 + RRF 融合**，成本不高：

1. **记忆切片规范化**：每条记忆带时间戳、来源、标签，按事件切分而非按对话轮次。
2. **全文索引**：SQLite FTS5，中文场景换 jieba 分词器（默认 tokenizer 会把中文切成整句，必须换）。
3. **语义索引**：sqlite-vec 存向量，embedding 服务单独封装，top-k 取 5，相似度阈值 0.35 起步再调。
4. **查询路由**：查询里包含错误码、文件名、ID 这类高熵 token 时走全文优先；否则双路并发。
5. **RRF 融合**：两路排名用倒数排名融合，取前 5 条返回，严格控制 token 预算。

效果上，语义负责"换个说法也能中"，全文负责"精确标识绝不丢"，融合后的命中率比单路高出一截。

## 踩坑点

- **中文分词是全文搜索的第一坑**。FTS5 默认配置对中文几乎不可用，换成 jieba 或 trigram 后才正常。
- **embedding 模型一换，全量重建索引**。模型版本必须和索引版本绑定存储，否则新旧向量混在一起，相似度分数没有意义。
- **相似度阈值不可跨模型照抄**。0.35 在 A 模型合适，换 B 模型可能全是噪音，只能用自己的数据重新标定。
- **记忆量小时语义优势会消失**。几百条记忆的规模，全文搜索毫秒级返回且零外部依赖，向量检索反而引入了延迟和一次 API 调用的失败面。
- **top-k 给太多会污染上下文**。返回 10 条"可能相关"，agent 反而更容易被带偏，5 条以内 + 带摘要比返回原文更稳。

## 可复用建议

- 记忆库在几千条以内，**先全文搜索，够用就别上向量**。
- 必须上语义时，把 embedding 服务当外部依赖对待：超时、重试、降级到全文，一样都不能少。
- 建一个 20~30 条的**小型评测集**（真实 query + 期望命中的记忆 ID），每次调参后跑一遍，别靠感觉调阈值。
- 给 `memory_recall` 的返回加上"命中原因"字段（全文命中 / 语义命中 / 融合），排查坏 case 时能省一半时间。

## 总结

这不是一道二选一的题。语义搜索解决"怎么说"的多样性，全文搜索守住"是什么"的精确性。小规模先全文，规模化后加语义，中间用最朴素的 RRF 连起来——工程上没有惊喜，但确实管用。
