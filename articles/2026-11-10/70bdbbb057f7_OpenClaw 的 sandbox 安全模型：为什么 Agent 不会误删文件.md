## 背景

OpenClaw 这类网关型 Agent 和聊天窗口里的助手有本质区别：模型是直接拿着工具在你机器上干活的——读写文件、跑 shell、调 MCP。能力越大，"误删"的担心就越真实。社区里被问得最多的一句是：让它执行 `rm` 前，是不是得先全盘 git commit？

其实 OpenClaw 的安全设计思路不是靠提示词求模型"小心一点"，而是分层把它能碰到的世界先缩小。模型聪明与否是第二位的，路径上有没有危险才是第一位的。

## 问题

误删通常不是单一故障，而是来自三条路径：

1. **路径错了**：相对路径、通配符展开、工作目录漂移，`rm -rf build/*` 在错误目录里就变成了灾难；
2. **内容被污染**：MCP 工具返回值或抓取的网页里带注入指令，诱导 Agent 执行"清理"类命令；
3. **边界没划**：虽然跑在容器里，但把 `/home` 整个挂了进去，等于没隔离。

## 做法：四层收窄

以我们 Linux 上的部署为例，按顺序做四件事：

**第一层，工作区收敛。** 所有文件工具的根锚定在 workspace 目录，Agent 眼中的"整个文件系统"实际只有这一棵子树。超出根的路径在工具层直接被拒绝，模型写绝对路径也没用。

**第二层，Docker sandbox。** 把 shell/exec 类工具放进容器执行：只 bind-mount workspace，根文件系统 `--read-only` 挂载，关闭特权，禁用宿主网络。容器里没有 ssh key、没有 crontab、没有任何你需要保护的东西。

**第三层，工具策略。** 每个 agent 单独配 tool policy：exec 默认需要人工确认，`rm`、`dd`、`mkfs`、`shred` 这类进 deny 名单；MCP server 按需启用，且只开它声明过的工具面。

**第四层，审计与快照。** 所有写操作落审计日志；workspace 每天用 `rsync --link-dest` 打一次快照。真出事，恢复成本是分钟级。

**验证方式**：在 workspace 外放一个 `canary.txt`，让 Agent "清理所有不需要的文件"，看它能否碰到。连续几次都碰不到，才算隔离成立。这个测试应该进你的回归清单，每次升级重跑。

## 踩坑点

- **挂载贪大**：为省事把整个用户目录挂进容器，隔离直接失效。最小挂载是底线，别让"方便"破坏模型。
- **只防了 shell**：MCP server 是独立进程，如果它自己走宿主机文件 API，sandbox 管不到它。第三方 MCP 接入前先审权限声明。
- **symlink 逃逸**：workspace 里的软链接指向外部目录，"工作区内"就成了幌子。挂载前清一遍软链，容器内用无特权用户运行。
- **确认门钝化**：天天点 always allow，权限门就只剩仪式感。宁按项目粒度放行，别全局放行。
- **断网的副作用**：网络全禁后 Agent 装不了依赖，会陷入重试循环白烧 token。按需开代理出网，比完全断网更稳。

## 可复用建议

- 按"层"评估安全性，而不是按"有没有开 sandbox"：对每层单独问一句——这层被绕过会怎样？
- deny 名单维护在配置文件里、进版本控制，别散落在各处手改。
- 快照要真的做过一次恢复演练。没恢复过的备份，不算备份。
- canary 文件 + 一条注入用例，是验证隔离最便宜的手段。

## 总结

"Agent 不会误删文件"的真相不是模型变聪明了，而是默认路径上根本没有它能删的东西。路径收窄、容器隔离、工具策略、快照兜底——四层单独看都不完美，叠起来才构成可交付的默认安全态。给 Agent 开权限的正确姿势和给同事开服务器权限一样：先给最小的，有需要再加，而不是反过来。
