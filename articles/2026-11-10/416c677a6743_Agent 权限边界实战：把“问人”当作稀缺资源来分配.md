## 背景

Agent 能做的事越来越多：OpenClaw 接上 MCP 工具和插件后，读写文件、跑 shell、调外部 API、发消息都不再是难事。能力上去了，新问题也来了——哪些动作 agent 可以直接执行，哪些必须停下来问人？

常见做法是两个极端：要么全默认放行，出一次事故后一刀切成全默认确认；要么全默认确认，人被弹窗轰炸后闭着眼睛点“允许”。两个极端都会让权限机制失效。

## 问题：确认是会被耗尽的资源

权限设计的核心矛盾不是“要不要安全”，而是**人的注意力有限**。一个 session 里弹出十几次确认，人就会进入 rubber-stamp 模式——确认框还在，安全价值已经归零。所以“问人”本身是稀缺资源，要用在刀刃上。

判断标准推荐两个维度：**可逆性**（动作能否撤销）和**影响半径**（出问题时波及多大范围）。

## 做法：四层分级

- **L0 自动执行**：只读、沙箱内、可重复。搜索、读仓库、dry-run。注意：只读不等于无害，见踩坑点 3。
- **L1 自动执行 + 审计**：可逆写操作且锁定在工作区内。git 管控下的文件编辑、写草稿、进队列不发送。每次动作落审计日志。
- **L2 首次确认，模式内放行**：对外可逆动作——发消息、开 PR、部署到 staging。同一模式（同收件人/同目标环境）首次人工确认后短期放行，允许清单定期复审。
- **L3 永远问人**：不可逆或高影响半径——删数据、生产部署、支付、群发。确认内容必须带 diff、理由和回滚方案，没有例外。

落地时把边界写成配置而非 prompt：工具权限、MCP server 的 scope、插件白名单进版本库，像代码一样 review。

## 踩坑点

1. **确认框没有上下文**。只弹“是否允许？”等于没弹，必须展示将改变什么、影响谁、怎么回滚，否则人只能盲批。
2. **“总是允许”点一次就永久生效**。允许清单要有过期时间，至少每月人工过一遍。
3. **只读被当成绝对安全**。真正危险的经常是“读 + 外发”的组合：读到凭据再通过别的工具发出去。要卡死的是出口（egress），外发类工具应单独提到 L2/L3。
4. **批量确认掩盖个体**。一次批准十个动作等于一次都没批，逐条展示或拆成多次确认。
5. **边界配置没测试就上生产**。权限规则也是代码，先在测试环境跑典型任务，确认拦截和放行都符合预期。

## 可复用建议

- 默认拒绝，凭审计证据逐步放开，而不是出事后再收紧。
- 给自动动作设数值上限：单次花费、调用频率、单批文件数，超限自动降级为“问人”。
- L1 动作记录输入输出，事故后能回放。
- 一个 session 问人超过 3~5 次，先重新划边界——高频确认说明分类粒度太粗，别怪用户不耐烦。
- 每季度把允许清单当依赖项审一遍，没人记得为什么加的条目直接删。

## 总结

权限边界不是一段 prompt 能解决的，它是和部署策略、code review 同级的工程设计。两个轴（可逆性 × 影响半径）、四层分级，把“问人”集中在不可逆和高影响半径的动作上，其余交给自动化加审计。确认框出现得越少，每次出现时人才会真正去看。
