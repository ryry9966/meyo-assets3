## 背景

Agent 接上 MCP、插件和 shell 之后，能力上限不再取决于模型，而取决于你敢让它碰什么。社区里常见的翻车有两类：一类是 Agent 每写一个文件都要确认，二十步的操作人点了十几次"允许"，最后确认变成人肉橡皮图章；另一类是它很自信地跑了一条 `rm -rf`、给全组发了一封邮件，或者把改动直接推到了生产分支。这两个是同一个问题的两面：权限边界没划清。

## 问题本质：不是"要不要问人"，而是"按什么标准问"

我现在的做法是把所有工具调用按两个维度分级：**可逆性**（操作能不能低成本撤销）和**影响范围**（只影响 Agent 的工作目录，还是波及外部世界）。交叉出一个四级表：

| 级别 | 例子 | 策略 |
|---|---|---|
| 只读 | 读文件、查数据、搜索 | 自动执行，不打扰 |
| 可逆写 | 改本地文件、开分支 | 自动执行 + 留快照/diff 可回滚 |
| 高危不可逆 | 删数据、`git push --force` | 必须确认，默认拒绝 |
| 外部副作用 | 发邮件、支付、第三方写接口 | 必须确认，白名单放行 |

## 做法

落地分三步：

**第一步，给工具打风险标签。** MCP 工具在注册时就声明 risk 级别，不要指望模型自己判断。模型对"这个操作危不危险"的直觉并不可靠，尤其是描述写得含糊的工具。

**第二步，用拦截层兜底，而不是靠提示词。** 把"高危操作需确认"写进 system prompt 当然要做，但它只是建议，不是约束。真正兜底的是工具调用前的 hook：匹配到 deny 规则就暂停，把上下文抛给人。提示词会被长对话稀释，拦截规则不会。

**第三步，把"问人"做成结构化动作。** 这是我踩坑最多的一点。差的确认请求长这样："我想执行 git push，可以吗？"人没法判断，只会习惯性点确认。好的确认请求应该包含：完整命令、影响范围、dry-run 结果或 diff、回滚方式。让确认变成一次十秒的技术评审，而不是掷硬币。

## 踩坑点

- **确认疲劳**：确认请求太频繁、信息太少，人会训练自己无脑点"允许"。宁可低危操作偶尔打扰，也别把高危确认淹没在噪音里。
- **粒度太粗的 allowlist**：放行整个 `shell` 工具等于没设防。按命令模式或按具体工具名放行。
- **会话内惯性**：上次 `push` 被批准了，这次 Agent 就默认还能 push。审批应该是单次生效，或者明确声明有效期。
- **缺 dry-run**：高危工具最好支持 plan/execute 两段式，先给人看计划再执行。

## 可复用建议

- 新接一个 MCP server 时，先跑一遍它的全部工具，逐个标 risk 级别，固化成配置，不要用默认值。
- 把"低危自动、高危必审、外部副作用必过人"写成一行团队原则，所有 Agent 项目共用，避免每个项目自己发明一套。
- 每次误操作后，复盘的问题不是"模型为什么蠢"，而是"这个操作为什么没被拦住"——修拦截规则，不要靠改 prompt 祈祷。

## 总结

权限边界的核心不是信任模型，而是承认模型会犯错，然后让错误的代价可控。可逆的让它干，不可逆的让人看，波及外部的永远要过人。判断标准越机械越好——机械的标准才能写成拦截规则，而拦截规则才是真正守夜的东西。
