## 背景

Agent 跑起来之后，一个很现实的感受是：所有上下文——聊天记录、文件内容、日程、工具返回值——默认都发给了云端 API。除了费用，还有隐私问题。我的思路是给 OpenClaw 配一个"本地日常层"：摘要、提醒、草稿这类琐碎任务走本地模型，复杂编排才上云端。

## 问题

家用硬件的约束很硬：消费级显卡 8–16GB 显存，或者 Mac 的统一内存。而 Agent 场景比纯聊天苛刻得多——system prompt 加上工具 schema 和多轮历史，轻松吃掉上万 token。真正的难点不是"能不能跑起来"，而是跑起来之后，工具调用和结构化输出还靠不靠谱。

## 做法

1. **盘点硬件定档位**：8GB 显存 → 7B 级别 Q4 量化；16GB → 14B；24GB 显存或 32G 统一内存 → 32B Q4。别越级硬上，爆显存后 CPU offload 的速度没法用。
2. **选运行时**：家用环境推荐 Ollama 或 llama.cpp server，都提供 OpenAI 兼容接口。vLLM 的吞吐优化在单用户场景意义不大，不必上。
3. **选模型**：中文 + 工具调用场景优先 Qwen 系列；向量检索配 bge-m3。量化从 Q4_K_M 起步，不够再升。
4. **关键参数必须显式设**：上下文长度设到 8192–16384；keep_alive 设长一点避免反复换模型；不需要思考链时关掉 thinking 模式，否则首 token 延迟很难看。
5. **接入 OpenClaw**：把模型 provider 指到 `http://127.0.0.1:11434/v1` 即可，协议完全兼容。然后做分级路由，而不是全量切换。
6. **用真实 Agent 任务测试**：别拿闲聊测，拿你实际的工具调用链路测。

## 踩坑点

- **默认上下文陷阱**：Ollama 默认上下文很短，超长部分被静默截断，表现为 Agent"失忆"。这是新手最常踩的坑。
- **量化伤工具调用**：Q4 聊天没问题，但要求严格 JSON 输出时容易破格式。选原生支持 function calling 的模型，运行时开 JSON schema 约束能救回一部分。
- **每个工具单独测**：不同运行时对 tool call 的解析实现有差异，某工具在云端好用、本地失灵很常见。
- **笔记本别信峰值**：持续推理几分钟后热节流，速度掉一半是常态，按持续性能估算。
- **keep_alive 默认值太小**：每次请求重新加载模型，凭空多几秒延迟。

## 可复用建议

- 一切模型都抽象成 OpenAI 兼容端点，Agent 代码零改动即可切换本地/云端。
- 路由按任务重量分级，不做全有或全无。
- 从自己的 Agent 日志里抽 20–50 条真实案例做小评测集，比跑通用 benchmark 靠谱得多。
- 显存预算 = 权重 + KV cache，KV cache 随上下文线性增长。升级硬件前先算这笔账。

## 总结

本地模型目前替代不了云端处理复杂编排，但作为隐私优先、零边际成本的日常层已经完全可用。建议从小模型起步、用真实任务度量、保持接口抽象，逐步把能下沉的任务下沉到本地。
