## 背景

做 Agent 和 MCP 自动化的人，早晚都会碰到两件事：一是高频小任务（分类、摘要、格式化）全走云端 API，账单和延迟都不好看；二是一些本地数据——笔记、照片、私人文档——不想离开这台机器。本地部署大模型不是要替代云端，而是在 Agent 体系里加一条"低成本航线"，把量大的活分流下来。

## 问题

真正拦住人的不是"能不能跑起来"，这一步现在很简单。难点有三个：

1. 显存/内存预算直接决定模型上限；
2. 小模型"会聊天"不等于"会调工具"，Agent 场景对这一点极其敏感；
3. Agent 的上下文消耗和单轮对话不是一个量级，默认参数往往不够用。

## 做法

**第一步：盘点硬件。** 粗略预算：7B/8B 模型 Q4 量化约需 6GB 显存或 8GB 内存；14B 约 10–12GB；32B 级别基本要 24GB 显存起步。纯 CPU 能跑 7B，但吞吐掉到个位数 token/s，放进 Agent 循环里体验很差。

**第二步：选运行时。** Ollama 上手最快，自带 OpenAI 兼容接口，适合做常驻服务；llama.cpp 控制粒度更细；调试期可配合 LM Studio 观察显存占用。我最终留在 Ollama。

**第三步：选模型和量化档位。** 中文场景优先 Qwen 系列，务必选官方支持 function calling 的 instruct 版本；量化不要低于 Q4_K_M，再往下压，JSON 输出就开始缺字段。

**第四步：改上下文参数。** Ollama 默认上下文很小，Agent 场景建议直接拉到 8k–16k，代价是内存上涨，需实测：

```bash
OLLAMA_CONTEXT_LENGTH=16384 ollama serve
```

**第五步：接入 OpenClaw。** 模型地址指向本机的 OpenAI 兼容端点，先跑一个只挂单个 MCP 工具的最小 Agent 验证调用链路，再逐步加复杂度。

**第六步：建评测集。** 准备 10–20 条典型工具调用用例（含参数抽取、多步调用、失败重试），每次换模型或量化版本跑一遍看通过率，而不是凭聊天手感。

## 踩坑点

- 聊天很流畅，一调 MCP 工具就开始编造参数名——这种情况换模型比改 prompt 有效；
- 显存够不代表上下文够，KV cache 随会话长度线性增长，长任务中途 OOM 很常见；
- 量化档位压太狠，工具调用的 JSON 格式先坏，再才是聊天质量下滑；
- 别用单条 prompt 测速度，Agent 一轮可能几十次调用，吞吐和稳定性才是指标；
- 模型版本更新后行为会漂移，建议固定版本号，把升级当作一次回归测试。

## 可复用建议

1. **分层路由**：本地跑高频低难度任务，难题回落云端，成本曲线立刻好看；
2. **版本固定 + 小评测集**：把"换模型"变成可验证的操作，而不是赌博；
3. **顺序不能反**：先验证工具调用链路，再优化对话质量。

## 总结

家用电脑跑本地模型，如今已经不是折腾爱好，而是可以稳定服役的基础设施。合理的定位是把它当作 Agent 体系里的经济舱：承运量大、单价低、航线固定，复杂任务仍然交给云端。把硬件预算和工具调用评测这两件事做扎实，接入 OpenClaw 和 MCP 就是顺路的事。
