## 背景

用 OpenClaw 跑长任务，最头疼的往往不是模型能力，而是主 agent 的上下文：任务做到一半，对话里已经堆满工具输出、文件片段和中间结论，模型开始忘事、前后约定打架，错误率明显上升。Subagent 机制的价值正在于此——主 agent 派生出多个子 agent，各自拥有独立上下文，干完活只把摘要交回来。上下文既然隔离，天然也可以并行。下面记录最近一次真实任务里的做法和踩的坑。

## 问题

场景很典型：monorepo 里 8 个服务的旧版配置要迁移到新格式，每个服务还要补一段兼容说明。串行做的后果可以预见：主上下文被前几个服务的 diff 细节塞满，做到第 6 个时模型已经开始混淆两个服务的字段命名；中间任何一步失败，整条流水线卡住，前面读过的文件全白读。

## 做法

1. **先拆任务，判断独立性。** 按目录边界拆成 8 个子任务，规则只有一条：任何两个子任务不得写同一个文件。拆不动就先合并再拆。
2. **给每个 subagent 定契约。** Prompt 三段式：自包含的任务描述（不假设子 agent 知道父对话的任何内容）、边界（只能改哪些路径、禁止做什么）、输出格式（改了哪些文件、关键决策、遗留问题，摘要控制在两百 token 以内）。
3. **并行 spawn，权限分级。** 一次并发 4 个；纯调研类子 agent 只给只读工具，改文件的才给写权限。
4. **主 agent 只做集成。** 收摘要、抽查产物、跑 lint 和测试、处理服务间的共享依赖，全程不亲手改文件。
5. **失败要显式。** 要求子 agent 遇到无法完成的步骤时明确报错并停止，主 agent 抽查文件 diff，而不是采信口头汇报。

## 踩坑点

- **并发写同一文件。** 第一版拆分漏了一个共享的 index 文件，两个子 agent 互相覆盖，后写覆盖先写。改法：共享文件从子任务里剔除，留给主 agent 在集成阶段统一处理。
- **子 agent 以为有父上下文。** 有个子 agent 的输出写着“沿用上面的命名规则”——它根本没有“上面”。任务 prompt 必须完全自包含。
- **摘要超长。** 没限格式时，有子 agent 交回上千 token 的流水账，几个并发直接把主上下文打爆。摘要格式要写成硬约束。
- **静默失败。** 有子 agent 遇到权限错误后自行“绕过”了某个步骤，汇报里只字未提。显式报错要求之外，产物验证不能省。
- **一上来就全量并行。** 正确顺序是先串行跑一个“试点”，确认输出格式和产物质量，再放量到 4-5 个并发。

## 可复用建议

- **试点 → 放量**：永远先串行跑通一个，再并行铺开。
- **任务模板化**：范围、约束、输出 schema 三段固定，只换变量。
- **权限分级**：只读子 agent 成本低、风险小，可以放心提高并发。
- **中间产物落盘**：让子 agent 把详细过程写进文件，摘要只给路径和结论，主 agent 需要时再去读。
- **并发数克制**：3-5 个通常是收益极值点，再高会撞上 API 和 MCP server 的限流，收益递减。

## 总结

Subagent 编排的本质是两件事：上下文隔离和并行执行。实际体感上，隔离带来的质量提升往往比并行带来的提速更明显——主上下文干净了，集成阶段的判断力才在线。而编排质量取决于任务契约定得是否清晰，和并发数关系不大。先把契约写好，再谈并行。
