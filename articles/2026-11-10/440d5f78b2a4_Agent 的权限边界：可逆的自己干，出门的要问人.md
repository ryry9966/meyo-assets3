## 背景

Agent 接上 MCP 工具之后，能力上限不再是"会说"，而是"会做"：读写文件、跑 shell、调第三方 API、发消息、改数据库。能力越大，一个问题越绕不开——哪些动作 Agent 可以直接执行，哪些必须停下来问人。这不是产品哲学问题，是工程问题，而且必须在上线前想清楚。

## 两种失败模式

实践中常见两个极端：

- **过度请示**：每一步都问"我可以继续吗"。Agent 退化成不断把活推回给你的客服，自动化价值归零，用户也开始无脑点"同意"。
- **过度放权**：删数据、给真实用户群发消息、付费 API 烧穿预算、force push——全在没人盯着的时候完成，事后翻日志才发现。

两种都比"没有 Agent"更糟。核心矛盾是：确认有成本（打断人），错误也有成本（不可逆的破坏）。权限边界本质上是在这两种成本之间做定价。

## 分级框架：可逆性 × 影响面

用两个维度给每个工具打标：

1. **可逆性**：这个动作能不能低成本撤销？
2. **影响面**：出错时波及的是沙箱，还是真实世界（人、钱、生产环境）？

据此分三档：

- **Tier 0 只读**：查询、搜索、读文件、dry-run。自动执行，记日志。
- **Tier 1 可逆写**：工作区内写文件、建分支、生成草稿。自动执行，但必须保留完整的 undo 路径。
- **Tier 2 不可逆或出得去门**：付款、发送、删除、改生产配置、schema 变更。必须人工确认。

判断口诀：**可逆且在门里，自己干；不可逆或出了门，问人。**

## 落地五步

1. **盘点工具清单**，在 MCP 工具元数据里给每个 tool 标注风险档位。标注文件进版本管理，像代码一样 review。
2. **在工具调用链上加拦截层**（OpenClaw 的插件/hook 机制都能做），Tier 2 调用强制暂停。关键原则：策略写在代码里，不要只写在 system prompt 里——长上下文中 prompt 约束会被稀释，代码不会。
3. **确认请求必须带上下文**：执行什么、为什么、具体参数或 diff、回滚方案。只弹一个"是否允许？"是无效确认。
4. **高频 Tier 2 改用预授权**：预设限额，比如"单日预算内自动通过，超出即暂停"，把逐次审批变成批量授权，避免确认风暴。
5. **所有调用与确认落日志**，事后用数据回头调整分档。边界是调出来的，不是一次设计出来的。

## 踩坑点

- **确认疲劳**：问得太频繁，用户会养成无脑点同意的习惯，整个机制形同虚设。Tier 2 必须保持稀有，稀缺才有严肃性。
- **静默继承**：子 Agent 或插件自带工具，绕过主流程的拦截。拦截要做在统一出口，不要做在某个 Agent 的 prompt 里。
- **伪回滚**："理论上可以回滚"和"回滚脚本演练通过"是两回事。没测过的 rollback，一律按不可逆处理。
- **伪装成读的操作**：发消息、调计费接口看起来像"查询"，实际是对外部世界的写。按副作用分类，别按工具名字分类。
- **循环里刷确认**：批处理任务产生几十次 Tier 2 调用，确认逻辑要设计到批次粒度，而不是单次调用粒度。

## 可复用建议

- 新接一个 MCP server，先只读跑一段时间看日志，再逐步放权，别一上来给写权限。
- 确认成本要低：一次点击、一条回复完成，且附带上下文。
- 权限配置当代码管：有 diff、有 review、有版本。
- 从严起步，根据日志逐步放宽；收权容易，放权难，顺序别反。

## 总结

权限边界不是给 Agent 设限制，而是给自动化定价：可逆、影响小的交给 Agent 换效率，不可逆、出了门的交给人类确认换安全，高频场景用预授权和限额把两者统一起来。实现顺序是先写进代码，再写进 prompt，最后用日志持续校准。这三个动作做完，你才敢让 Agent 真正替你干活。
