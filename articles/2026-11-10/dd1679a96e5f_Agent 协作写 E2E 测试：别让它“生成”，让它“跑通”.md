## 背景

E2E 测试是大多数团队“都知道该写、但一直没写”的那一块。原因很实际：写起来慢、选择器脆弱、改一版 UI 全线飘红，最后仓库里往往只剩一两个没人敢删的 spec。

有了 Agent 之后，一个自然的想法是让它来写。但直接让模型“生成一套 Playwright 测试”，效果通常很差——它没见过你的页面，选择器基本靠猜，写出来的东西要么跑不起来，要么永远通过。

真正有用的形态是闭环：Agent 不只写，还要能执行测试、读取失败原因、自己修，直到绿灯。

## 问题拆解

- **模型对 DOM 的想象是错的**：没有真实页面反馈，`data-testid` 全靠编。
- **一次性生成整个测试集**：失败日志塞满上下文，越修越乱。
- **缺乏工程约束**：等待方式、断言粒度、fixture 结构不统一，review 成本反而更高。

所以目标不是“AI 写测试”，而是“AI 在你的工程约束里跑通测试”。

## 做法

我们的组合是 Playwright + Agent + 浏览器类 MCP：

1. **铺地基**：手工写 1–2 个“金样本” spec（登录 + 一条核心流程）作为风格参照，再放一份 `TEST_GUIDELINES.md`：统一 `getByTestId`、禁止 `waitForTimeout`、每个 spec 独立构造数据。
2. **给工具，不是只给任务**：Agent 至少要能读写仓库文件、执行 shell（`npx playwright test --reporter=line`）、并通过 MCP 打开真实页面取真实 DOM。第三项是关键，它把“猜选择器”变成“查选择器”。
3. **一次一个 spec**：明确要求每次只覆盖一个功能点，写完立刻跑，失败就读 trace 和截图，修完重跑，直到绿。
4. **裁剪失败信息**：不要把完整测试输出喂回去，只保留失败用例的错误栈和对应文件，上下文干净得多。
5. **人只审断言**：Agent 产出当草稿看，重点确认断言真的验证了业务结果，而不是只确认“页面打开了”。

## 踩坑点

- **永远通过的测试**：Agent 倾向写弱断言。对策是变异验证——临时把被测功能改坏，确认测试真的会红，再改回来。这步不能省。
- **用重试掩盖 flaky**：Agent 修不稳定用例时喜欢加 retries 或干脆 sleep。直接在 guidelines 里禁掉，要求语义等待。
- **登录态拖慢一切**：每个 spec 各自登录很慢，用 `storageState` fixture 做全局登录态，并在 guidelines 里提前说清。
- **放开手脚的 Agent**：限制它只改 `e2e/` 目录。它可能顺手“修”业务代码让测试变绿——我们真实遇到过一次。

## 可复用建议

- `TEST_GUIDELINES.md` + 金样本 spec 是投入最小、收益最大的两件事，先做这个再谈 Agent。
- 闭环的核心是执行反馈：跑不了测试的 Agent，只能产出“看起来像测试的文本”。
- 分工上：断言的正确性归人，机械劳动（选择器、等待、样板结构）归 Agent，这个边界目前最稳。
- 从一条核心链路开始跑顺，再逐步扩大覆盖，不要一上来就全量生成。

## 总结

Agent 写 E2E 的价值不在“写得快”，而在把写—跑—修这个循环自动化掉。人的角色从“敲测试的人”变成“定义什么算测对了的人”。先给约束和真实反馈，再给自由度，产出的测试才敢进 CI。
