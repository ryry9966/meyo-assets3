## 背景

用 OpenClaw 跑了一段时间自动化工作流后，写代码这件事基本已经交给 agent 起草了。但真正烦人的不是写代码，而是收尾：看一遍 diff、切分支、想一句 commit message、push，每次都要手动切上下文。于是干脆把"提交和分支管理"也交给 agent——前提是把权限和流程收窄到可控范围。

## 问题

直接给 agent 一个裸 shell 让它跑 git，很快会出三类事故：

1. `git add -A` 把 `.env`、构建产物一起提交；
2. 直接在 main 上改代码，甚至尝试 `push --force`；
3. commit message 全是 "update files"。

所以核心思路是：**不给裸权限，只给包装好的能力**。

## 做法

分四步：

**1. 独立身份 + 最小权限。** 给 agent 单独配置 git identity（比如 `bot@openclaw.local`），提交一眼能看出是 AI 干的，方便 review 和回滚。push 用仅限单仓库的 fine-grained token，不开 force push 权限。

**2. 把 git 命令包成白名单脚本。** 不让 agent 直接敲 shell，而是提供一个 `git-bot.sh`，只放行 `status / diff / log / branch / switch -c / add <path> / commit -m / push`，显式禁止 `reset --hard`、`push --force`、`clean -f`。在 OpenClaw 里把它注册成 exec 工具，或走 MCP 的 git server 都可以，关键是入口唯一，方便审计。

**3. 提交前自动拦截。** 仓库里加 pre-commit hook：gitleaks 扫密钥、lint 改动文件。hook 失败 agent 自然提交不了，比在 prompt 里反复叮嘱"不要提交密钥"可靠得多。

**4. 分支与流程约定写进 skill。** 要求 agent 只在 `feature/ai-*` 分支工作，开工先 `switch -c`；commit 前必须先跑 `git diff --staged` 读懂改动再写 message，统一 conventional commits 格式；遇到冲突不要自己 rebase，停下来汇报，人来裁决。

## 踩坑点

- **`add <path>` 而不是 `add .`/`-A`**：第一个坑。agent 图省事全量 add，把本地调试用的临时文件带进了历史。
- **detached HEAD**：agent 在某些 checkout 后忘记切回，后续 commit 全丢在游离 HEAD 上。脚本里在 commit 前加一道 `git symbolic-ref -q HEAD` 检查，失败直接拒绝。
- **冲突静默处理**：早期版本 agent 遇到冲突会随手挑一个版本继续，比卡住更危险。现在明确约定：冲突即停。
- **message 空洞**：不先看 diff 直接写 message，基本都是废话。强制"先 diff 后 commit"这一条顺序，质量提升明显。

## 可复用建议

- 白名单脚本 > 裸 shell，入口唯一才好审计；
- 高危命令（force push、reset --hard、branch -D）在脚本层硬拒绝，不靠 prompt 自觉；
- pre-commit hook 是最后防线，密钥扫描必须上；
- bot 身份独立，review 时可以按 author 直接过滤 AI 提交。

## 总结

把提交和分支管理交给 AI 助手，省下的主要是上下文切换成本，收益真实但不必大惊小怪。真正让这套流程敢用的，不是模型能力，而是三层约束：最小权限、白名单命令、hook 拦截。Agent 负责"干活"，规则负责"兜底"，人只在冲突和高危动作时介入——这个分工目前跑下来最稳，欢迎社区里同样在做 git 自动化的同学补充各自的拦截策略。
