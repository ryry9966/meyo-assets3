## 背景

社区每周要发一期「本周动态」：整理仓库 release、热门 issue 和讨论串。此前纯人工，费时且容易漏。思路很直接：用 OpenClaw 起一个 agent，挂几个 MCP 工具（采集、加工、发帖），定时跑，人只做最后把关。本文记录架构设计和一个半月实跑下来的踩坑。

## 问题

起步时最容易把它当成「一个 prompt 加一个 cron」，实际跑起来发现三个硬问题：

- 发帖是**不可逆动作**，重试、重复触发都会出事故；
- 模型生成内容**不可信**，链接可能凭空编造；
- 流水线环节多，出错时必须能**定位到具体步骤**。

## 做法

最终架构分四层，每层只做一件事：

1. **触发层**：cron 启动任务，先抢文件锁，防止重叠执行；
2. **采集层**：MCP 工具抓 GitHub releases、issues、论坛 RSS，原始数据落 SQLite，带唯一 ID；
3. **加工层**：agent 只负责「从原始数据里挑重点、改写语气」，prompt 明确约束：只允许引用采集到的数据，URL 白名单来自抓取结果；
4. **发布层**：发帖前过三道闸——URL 可达性校验、与历史帖相似度比对、格式与敏感词规则，通过后带幂等键调用发帖工具，先写 pending 状态再执行，成功后落 done。

每一步写状态表并带 trace id，挂了能直接定位续跑。

## 踩坑点

1. **重试导致重复发帖**。第一版失败就重试，一次接口超时让同一内容发了三遍。教训：外部写操作必须幂等——先落 pending，用同一幂等键重试，服务端去重。
2. **模型编造链接**。总结 release 时模型补了一个「看起来合理」的 issue 链接，实际不存在。对策：URL 只能来自采集白名单，发布前逐个 HEAD 校验。
3. **cron 重叠执行**。抓取源偶发慢查询，上一轮没跑完下一轮又启动，数据写乱。对策：文件锁 + 任务超时熔断，超时直接标失败并告警。
4. **相似内容反复发**。两周后社区反馈「每周都差不多」。对策：正文与历史记录做 shingle + Jaccard 相似度比对，超阈值转人工决定换角度还是跳过。
5. **一步到位全自动**。最早想直接全自动发，首篇语气就翻车。改成灰度：前两周全进草稿队列人工审，稳定后放开，并保留「拿不准只存草稿」的降级逻辑。

## 可复用建议

- **模型只做加工，不做事实来源**。所有事实、链接、数字必须来自结构化采集数据；
- **外部动作一律幂等化**。凡是「写出去」的操作，先落状态再执行，幂等键贯穿重试链路；
- **灰度放量**。人工审核 → 定时抽检 → 全自动，每阶段至少观察一周；
- **状态落库，不要放内存**。流水线越长越需要落库，才能定位和续跑；
- **保留降级路径**。置信度不够就发草稿不发正式帖，宁可少发，不要发错。

## 总结

这套东西的核心不是 prompt 写得多精，而是把「不可逆动作」包上了幂等、校验和降级。agent 负责聪明的部分，工程负责兜底的部分，边界划清楚，机器人才能长期稳定跑。目前每周动态从约 2 小时人工压缩到 20 分钟审核，稳定运行一个半月，零重复发帖。MCP 工具定义和状态表结构后续整理好再单独开帖分享。
