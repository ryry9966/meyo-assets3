# 背景

OpenClaw 的 agent 默认携带一批系统提示和工具描述。能力一多，两条路都会出问题：常驻上下文的 token 越滚越大，每次对话都在为用不到的内容付费；同时模型面对一堆无关的工具说明，选择质量反而下降。Skills 机制解决的就是这个矛盾——**能力清单常驻，能力正文按需加载**。

# 问题

具体到我的场景：我给助手接了十几个能力（消息处理、日志清理、文件归档、数据抓取……），早期做法是把所有说明写进系统提示。结果是：

- 常驻 prompt 上万 token，成本高、响应也变慢；
- 模型偶尔"抢戏"，比如整理文件的任务里突然调了抓取工具；
- 想改一个能力的说明，得在长 prompt 里搜半天，维护成本高。

# 做法

Skills 的核心约定很简单：每个 skill 是一个目录，里面一个 `SKILL.md`，frontmatter 写 `name` 和 `description`，正文写操作指引。启动时 agent 只读入所有 skill 的元数据，正文只有当任务匹配到某个 skill 时才注入。

1. **建目录**：workspace 下建 `skills/`，一个能力一个子目录，如 `skills/log-cleanup/`。
2. **写 SKILL.md**：frontmatter 的 description 是触发器，直接写清"什么时候用"：`description: 清理应用日志。当用户要求归档、压缩或批量删除日志文件时使用。`
3. **正文短平快**：先写前置检查，再写步骤，最后写验证方式。细节多就拆成辅助文件（`reference.md`、脚本），并在正文里明确指示"执行前先读 reference.md"。
4. **能写脚本的别写散文**：确定性逻辑（压缩命令、文件匹配规则）放脚本里，正文只告诉模型何时调、参数怎么传。
5. **验证触发**：问一句应该命中的话，看日志确认正文被加载；再问一句不该命中的，确认没有误触发。

# 踩坑点

- **description 写成功能介绍而不是触发条件**。"这是一个日志工具"不如"当用户要求 X 时使用"——后者才是模型判断的依据。
- **把所有内容塞进 SKILL.md**，等于把按需加载退化成全量加载，机制白做。
- 正文引用了辅助文件，但没写"先读再动手"，模型有时会跳过直接猜，输出不稳定。
- **skill 名字与内置工具撞名**，触发优先级混乱，改名即解决。
- skill 堆到三四十个后，元数据本身成了噪声。我最后合并同类项砍到十几个，触发准确率反而上来了。

# 可复用建议

- description 模板固定为"做什么 + 何时用"，团队内统一写法，当成接口来维护。
- 一个 skill 只做一件事，宁可多个小 skill，也别做巨型 skill。
- 确定性进脚本、判断性进 markdown，这条边界划清楚，skill 会稳定很多。
- 定期翻日志统计哪些 skill 真被触发过，长期零触发的要么改 description，要么删掉。
- `skills/` 目录用 git 管理，改动走 commit，回溯和分享都方便。

# 总结

Skills 本质上是能力维度的懒加载：元数据常驻、正文按需。它不神秘，工程上的关键是两件事——把 description 当接口写好触发条件，以及坚持渐进式披露，别把正文又写回全量。做到这两点，token 成本和模型选择准确率都会有可感知的改善。
