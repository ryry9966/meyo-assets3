我们平时用 Agent 的方式基本是被动式的：你提问，它回答，对话结束。但如果跑的是 OpenClaw 这类常驻网关型 Agent，它其实一直在线、挂着消息通道和一整套 MCP 工具——让它 24 小时只等你开口，有点浪费。

OpenClaw 提供了一个朴素但容易被忽略的机制：心跳（heartbeat）。网关按固定间隔（默认约 30 分钟，可在配置中调整）唤醒一次 Agent，让它去读工作区里的 HEARTBEAT.md。这个文件就是你的"主动任务清单"：Agent 每次心跳读一遍，判断有没有该做的事，有就执行并汇报，没有就静默返回空转标记（不同版本叫法略有差异，常见是回复 HEARTBEAT_OK 即不向你投递消息）。

## 问题

被动式 Agent 有三个典型痛点：

1. **跟进靠人**。让它"明天提醒我看 PR"，对话结束它就忘了，除非你自己接调度器。
2. **巡检要自己写脚本**。磁盘水位、证书过期、长任务是否跑完，本质都是"查一下，有异常再说一声"。
3. **上下文断裂**。昨天让它整理的资料，今天不问就永远没有下文。

心跳机制给这三类场景一个统一入口：把"什么时候、查什么、怎么汇报"写进一个 Markdown 文件，Agent 自己轮询。

## 做法

**第一步：找到工作区，创建 HEARTBEAT.md。** 工作区默认在 `~/.openclaw/workspace`（以你的安装为准），文件不存在就新建。

**第二步：用"条件 + 动作 + 去重"写任务。** 心跳轮次和普通对话一样带完整工具权限（MCP、插件都能调），所以任务可以落到真实动作上。给我自己在用的模板：

```markdown
# 心跳任务

- 巡检：检查磁盘占用，> 85% 提醒；同一水位线每天最多报 1 次。
- 跟进：若 ~/notes/ 里还没有昨晚说好的会议纪要，提醒一句，最多提醒 2 次。
- 汇总：每天 08:00 后的第一次心跳，推送 3 条 RSS 摘要，推送过的不重复。
- 规则：没触发任何任务就返回 HEARTBEAT_OK，不要给我发消息；汇报合并为一条。
```

**第三步：调间隔。** 30 分钟够大多数巡检场景；要精确定时（"每天 8 点整"）靠轮询是碰运气的，这类交给 cron 触发一次性指令，心跳只做兜底。

**第四步：跑一周观察期。** 先用低频（比如 60 分钟），看触发记录是否符合预期，再收紧规则或调频。

## 踩坑点

- **空文件也烧 token。** 心跳本质上是一次带工具的 LLM 调用，HEARTBEAT.md 里没任务就该关掉心跳或大幅拉长间隔。
- **指令太虚。** 写"多关心我"这种话，Agent 要么沉默要么编工作。每个任务必须有明确阈值、窗口和动作。
- **没有去重。** 磁盘报警每 30 分钟来一遍，三天后你会直接屏蔽它。去重规则要写进文件里。
- **心跳里塞重活。** 心跳轮次和正常对话共享 Agent 上下文，别让它每次心跳都跑十分钟的长任务，重活拆出去。
- **把它当日志堆。** HEARTBEAT.md 每个周期都会进上下文，控制在 30 行以内；同理，别把密钥写进去。

## 可复用建议

- 任务模板归纳为三类：**条件告警**（阈值+去重）、**定时汇总**（时间窗口+推送内容）、**跟进检查**（文件或状态的存在性判断），覆盖 90% 场景。
- 用 git 管理 HEARTBEAT.md，改任务就像改配置，每次调整有 diff 可回溯。
- 心跳汇报发到独立会话或群，避免刷屏主对话。
- 记住分工：心跳是"轮询检查"，不是"任务调度器"。

## 总结

HEARTBEAT.md 的价值不在"自动"，而在"克制"。三五条具体、带去重、可回溯的规则，就能让 Agent 从问答工具变成真正驻场的助手；写多了、写虚了，它只会变成定时骚扰你的机器人。先从一条磁盘巡检开始跑一周，比一次堆十个任务有效得多。
