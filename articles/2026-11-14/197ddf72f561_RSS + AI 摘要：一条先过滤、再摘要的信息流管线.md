## 背景

订阅源没有消失，只是散了。博客、GitHub Release、arXiv、播客都有 RSS，但直接读 feed 成本太高——我订阅 40+ 个源，一天新条目 200 条上下，人工根本筛不过来。AI 摘要看起来是显然的解法，但"每条都让模型总结一遍"很快会崩：贵、慢，而且摘要质量取决于输入质量。

这篇记录我用 OpenClaw 搭的一条管线，核心思路一句话：**摘要不是管线主体，过滤才是**。

## 问题

最初的版本很天真：cron 拉全量 feed → 每条喂给 LLM → 拼成日报。跑了三天暴露三个问题：

1. **成本失控**。200 条/天 × 长上下文，token 花费直线上升，且大部分摘要是废话（"该文章讨论了…"）。
2. **重复和噪音**。同一篇文章在多个源出现，标题党条目挤占摘要位。
3. **输出不稳定**。模型有时给 Markdown 有时给散文，下游解析天天崩。

## 做法

现在的管线分六段，每段独立可测：

1. **抓取**：OpenClaw 定时任务（每天 7:30 / 19:30）触发 fetch 工具逐源拉 XML，每个源的 last_fetched 时间戳写 SQLite，失败不重置。
2. **规范化**：统一为 title / link / published / content；缺全文的源用 readability 类工具抓正文，抓不到就只用 title + description。
3. **去重**：link hash 为主键，title hash 兜底（有些源 GUID 不稳定），SQLite 存已见集合。
4. **打分**：不调模型。规则先跑：关键词表 + 来源权重 + 新鲜度，0–10 分，≥6 分才进下一步。这一步砍掉约 70% 条目。
5. **摘要**：只对过线条目调 LLM，强制 JSON schema 输出 `{title_zh, one_line, why_it_matters, tags[]}`，英文源也输出中文。
6. **投递**：按 tag 分组拼日报，webhook 推到群，同时落一份 Markdown 存档。

```yaml
schedule: "30 7,19 * * *"
pipeline:
  - fetch_feeds      # 从 sqlite 读源列表
  - normalize
  - dedupe           # link_hash 优先
  - score            # 规则打分, 阈值 6
  - summarize        # 仅 score >= 6, schema 强约束
  - digest           # 按 tag 分组 + webhook 推送
```

抓取和摘要这两段可以顺手封成 MCP tool：日报走批处理，日常"帮我查一下某主题最近的更新"让 agent 单条调用，同一套状态复用。

## 踩坑点

- **别让模型处理没过线的条目**。规则打分便宜且可解释，模型只该做规则做不了的事：判断"值不值得读"。
- **GUID 不可信**。有源每次刷新都换 GUID，靠 link+title 的 hash 兜底后，重复率立刻降下来。
- **失败要软**。单源拉取失败只跳过并告警，不要让整个 run 挂掉；失败时也别更新时间戳，否则会漏条目。
- **摘要必须带 schema 校验**。模型偶尔漏字段：校验失败重试一次，再失败进人工队列，别静默丢。
- **全文抓取的坑比想象多**：反爬、付费墙、正文混导航和广告。readability 提取 + 4000 字截断够用了，别追求完美。
- **成本第二杠杆是缓存**：按内容 hash 缓存摘要，同一条目被多源转发时只算一次。

## 可复用建议

- **把管线当数据流设计**：每段输入输出明确、幂等、可单独回放。出问题能定位到具体段，而不是整条链路重跑。
- **状态放 SQLite**，别放内存或临时文件。管线的核心资产是"见过什么"这个状态。
- **阈值是主要成本旋钮**：控成本调阈值，提质量调 prompt，别混着调。
- **先小后大**：5–10 个源、一天一份日报跑稳两周再扩。管线的问题都是规模暴露出来的。

## 总结

这条管线跑了两个月，日报从 200 条缩到每天 10–15 条真正值得看的，token 花费降到初版的 1/8。最大的收获是认知上的：AI 摘要的价值不在"总结"，而在"分诊"——模型只负责最后的判断，前面的脏活（抓取、去重、打分）交给确定性代码。管线越简单、状态越少，活得越久。
