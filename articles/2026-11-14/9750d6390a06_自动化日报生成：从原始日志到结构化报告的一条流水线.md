## 背景

团队每天的运行状态同步，过去靠人肉翻日志、手写日报：漏报、口径不一、还占掉每天固定 20 分钟。OpenClaw 的定时触发 + Agent + MCP 组合正好可以把这件事固化成流水线。核心原则一句话：**计算交给代码，叙述交给模型**。

## 问题

- 日志来源多（服务日志、任务运行日志、CI 输出），格式与时区不统一
- 直接把原始日志丢给 LLM：token 爆炸、成本高，模型算出的数字不可信
- 人工日报受情绪和记忆影响，难以回溯对比

## 做法：五步流水线

1. **采集**：定时任务拉取过去 24h 日志，落地到统一目录，文件名带日期，保证幂等（重跑不产生重复数据）。
2. **结构化**：解析器把每行日志转成 JSON：`{ts, source, level, service, event, count}`。解析失败的行进 `parse_errors`，绝不静默丢弃。
3. **聚合**：纯代码算指标——按 service 分组的错误数、任务成功率、耗时分布。输出一份 200 行以内的结构化摘要，这是给模型的**唯一输入**。
4. **叙事生成**：通过 MCP 把摘要交给 Agent，prompt 中明确约束"只允许引用摘要中的数字，不得推断"。输出三段式日报：总体状态、异常项、待跟进。
5. **分发留档**：推送到群/邮件，同时把结构化摘要归档，供后续回溯与环比。

## 踩坑点

- **别让模型算数**：所有数字在聚合层算好，模型只做措辞。早期我们把原始日志直接塞给模型，错误率数字完全不可信，返工一次。
- **时区**：采集窗口统一用 UTC 存储、展示层转本地，否则日报的"天"边界会漂移。
- **格式漂移**：上游改日志格式后流水线不报错、只悄悄漏数据。加 schema 校验 + `parse_errors` 超阈值告警。
- **静默失败**：cron 挂了没人知道。任务结束必须有心跳或超时告警——日报没按时到达，本身就是异常信号。

## 可复用建议

- **schema 先行**：先定义日报字段，再写采集和解析，反向驱动接口约定
- **计算与叙事分层**：每层可单独测试、单独重跑
- **提供 dry-run 模式**：只打印不推送，调试期间必备
- prompt 和输出模板放进版本管理，变更可 review

## 总结

这条流水线没有黑科技，价值在于把"翻日志写日报"从每天 20 分钟变成每天 0 分钟的**可审计过程**。关键是克制：代码负责事实，模型负责表达，边界划清楚，日报才可信。欢迎大家贴出自己的日志 schema 和 prompt 模板，一起迭代。
