## 背景

团队里的"日报"大多是这样诞生的：早上有人打开好几个面板和日志文件，复制粘贴，再凭记忆补一句"今天整体平稳"。写的人累，看的人也不知道可信度几何。我们的环境里日志来源不少：服务日志、Agent 运行记录、CI 任务、定时脚本输出，格式各异。这篇帖子记录我用 OpenClaw 搭的一条日报流水线，核心思路一句话：让代码做确定性的活，让 Agent 只做它擅长的"解读"。

## 问题

把原始日志直接丢给模型总结，试过一次就放弃了：

- 单日日志几十万行，token 开销失控，关键异常容易淹没在噪音里；
- 模型会"顺手"计算或推断数字，报出来的错误次数、耗时和实际对不上；
- 格式每天漂移，同一指标今天有明天没有，没法横向对比。

所以问题其实分成两半：怎么把日志可靠地变成结构化数据，以及怎么让生成的报告稳定、可校验。

## 做法

流水线分五段，由 OpenClaw 定时任务触发，每段产物都落盘：

1. **采集**：调度入口按 cron 拉起任务，通过 MCP 工具（文件读取、HTTP、数据库查询）把各来源日志拉到工作目录，文件名带明确的起止时间戳。
2. **清洗与聚合**：纯脚本，不经过模型。按既定模板解析出错误计数、耗时分位、任务成败等指标，输出一份 digest JSON；解析失败的行单独计数，超阈值就告警。
3. **生成**：Agent 只读 digest JSON，配合固定 schema 的 prompt，负责写趋势解读和异常归因，输出结构化 Markdown/JSON——它不负责算数。
4. **校验**：脚本校验输出是否符合 schema、引用的数字能否在 digest 中找到，对不上就打回重试，或降级为"仅指标版"报告。
5. **投递与归档**：webhook 推送到群，digest 与成品报告按日期归档，方便回溯。

## 踩坑点

- **时间窗口**：第一版用"自然日"，跨时区任务经常把昨晚的算进今天。改成显式传 start/end 时间戳后问题消失。
- **格式漂移**：上游改了一次日志字段，流水线静默产出空报告。现在解析失败率超过 2% 就直接告警，宁可日报迟到也不出假数据。
- **任务重叠**：跑批偶尔超时，下一次调度又启动，报告重复推送。加了一个简单的锁文件和幂等检查。
- **报告没人看**：全量指标贴出来反而没人读。改成"与昨日/近 7 天基线的差值 + Top 异常"优先，篇幅压在一屏内，明细放归档链接。

## 可复用建议

- **Schema 先行**：先定 digest 和报告的 JSON Schema，Agent 是填空的人，不是定义格式的人。渲染与内容解耦，换模板不动上游。
- **中间产物落盘**：digest JSON 是最有价值的调试现场，出问题可以单独回放、只重跑生成段。
- **prompt 与模板版本化**：和代码一起提交，改口径时能说清"从哪个版本开始数字含义变了"。
- **分层降级**：模型段挂了就发纯指标版，别让整条链路单点依赖 LLM。

## 总结

这条流水线跑了一个多月，日报从"每天半小时手写"变成"早上自动出现在群里"，更重要的是数字终于对得上了。经验归成一句话：能用脚本算清楚的不要交给模型，模型只负责把算清楚的数字讲成人话，再用校验层兜底。实现不复杂，难的是把边界划清楚。
