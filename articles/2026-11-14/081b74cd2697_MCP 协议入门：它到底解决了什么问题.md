## 背景

2024 年底 Anthropic 开源了 Model Context Protocol（MCP），一年内基本成了 Agent 连接外部能力的事实标准。它本质上是一个基于 JSON-RPC 的开放协议，定义了 LLM 应用（client）和工具提供方（server）之间交换「工具、资源、提示」的标准方式。

## 它解决的真实问题

MCP 之前的状态是 **M×N**：M 个 Agent 应用 × N 个工具系统，每个组合都要写一遍胶水代码——schema 定义、鉴权、错误处理各搞一套。你给某个桌面端写的插件，换个框架就得重写。

MCP 把它压成 **M+N**：工具方按协议实现一次 server，应用方实现一次 client，双方即可互认。协议规定了三类原语：**Tools**（模型可调用的动作）、**Resources**（只读上下文）、**Prompts**（可复用模板）；传输上本地走 stdio，远程走 Streamable HTTP。

也要说清楚它**不**解决什么：不解决工具质量——description 写得烂，模型照样选错参数；不解决安全——工具返回内容里的注入攻击仍要自己设防；也不替代 function calling，只是把它上面的连接层标准化了。

## 实践步骤

1. **从现成 server 起步**：filesystem、git、fetch 这类示例最省事，配置即可跑通：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/data/projects"]
    }
  }
}
```

2. **自建 server 用 SDK**：Python 的 FastMCP 或 TS SDK，几十行就能暴露一个内部能力。
3. **工具设计守三条纪律**：数量克制（5–15 个）、参数扁平、把 description 当「写给模型的 API 文档」来写。
4. **权限收敛**：目录白名单、只读开关、写操作加 dry-run 或确认。
5. 用 MCP Inspector 调试，别在 Agent 里盲调。

## 踩坑点

- stdio 启动失败多半是路径问题：Windows 下 `npx` 要套 `cmd /c`，Python 加 `-u` 关缓冲。
- 大返回值撑爆上下文：查询类工具务必分页或截断，返回摘要而非全量。
- 工具结果直接喂给另一个写工具是注入高发路径：读与写之间加人工确认。
- 协议版本更新快（如 Streamable HTTP 替代早期 SSE），client/server 要做能力协商，别硬编码传输细节。

## 可复用建议

把内部系统封装成**少量粗粒度工具**，而不是把 REST API 一比一映射——模型面对 40 个细碎接口的选错率远高于 8 个语义清晰的工具。每个 server 当独立服务对待：有版本号、有日志（记录每次调用的参数与结果摘要）、有测试。经验上，description 的质量对成功率的影响，往往大于换更强的模型。

## 总结

MCP 的价值一句话：**把 M×N 的集成问题降成 M+N**。它是连接层的标准，不是智能层的魔法——真正的工程质量，落在工具边界怎么划分、权限怎么收敛上。建议路径：先用现成 server 跑通认知，再用薄适配层迁移自有插件，最后把工具描述和权限模型当核心资产长期维护。
