## 背景

OpenClaw 的主会话（比如你在 CLI 或 IM 里长期聊的那个 session）是上下文的载体：历史对话、工具调用记录、你的偏好都堆在里面。跑自动化时，主 agent 经常要派子 agent 去干脏活——批量读文件、调 MCP 工具、抓数据、跑长任务。这类操作的中间过程信息量，往往远大于最终结论。

## 问题

如果子 agent 的过程输出直接混进主会话，典型症状有四个：

- 主会话上下文被中间输出撑满，真正重要的历史被挤出窗口；
- 模型开始"记得"子任务的调试噪声，回答风格跑偏、总结质量下降；
- 子 agent 的工具报错混在主对话里，回放审计时分不清谁干的；
- token 成本无意义地上涨。

我最早就是让子任务直接在主会话里跑，两三天后主会话变成一个巨大的杂物间，最后只能重建 session。

## 做法与步骤

OpenClaw 的会话模型里，每个 agent run 都有自己独立的 session 转录文件。隔离的关键是：**子 agent 拿到的是一份任务简报，而不是主会话历史**。具体做法（字段名以你手上的版本为准）：

1. **派生即隔离**：主 agent 派子任务时，让子 agent 走全新 session，不继承主会话历史。它的所有工具调用写进自己的转录。
2. **入参显式**：简报里写清目标、涉及的文件路径、参数、超时和终止条件。不要指望"你看看我们刚才聊的"——隔离之后它也看不到。
3. **出参有 schema**：要求子 agent 只回传结论、关键路径、失败原因，并限定长度，比如"最多 200 字 + 结果文件路径"。
4. **副作用落文件**：需要主会话知道的事实，让子 agent 写进工作区的结果文件，主 agent 按需读取，而不是靠对话历史传递。
5. **转录独立留存**：子 agent 的 session 文件单独落盘，出问题单独回放，不挤占主会话。

## 踩坑点

- **隔离了对话，没隔离记忆**：子 agent 默认还能读工作区的记忆/笔记文件，甚至往里写。它把中间结论写进 notes，主会话一读，等于变相污染。要么给子 agent 只读权限，要么指定独立工作目录。
- **递归派生没上限**：子 agent 再派子 agent，转录和 token 双爆炸。至少在简报里禁止它继续派生。
- **"让它自己总结"不可靠**：不约束输出格式的摘要，回传的往往是大段复述。schema 要写在派生时的简报里，不要事后补救。
- **调试别只盯主会话**：子 agent 的报错在它自己的 session 文件里，主会话只会看到一行失败结果。
- **版本差异**：隔离的默认行为和配置字段在版本间改过，升级后先拿一个最小任务验证一遍再上生产。

## 可复用建议

一句话原则：**把子 agent 当函数调用，不是当同事聊天**。入参显式、出参有 schema、副作用落文件、转录可独立回放。满足这四条，主会话基本不会被拖脏。

## 总结

Session 隔离不是一个开关，而是三层一起闭环：**会话隔离**（子 agent 独立转录）、**工作区隔离**（读写范围受控）、**输出约束**（结构化回传）。做完这三层，主会话才能长期保持干净，自动化跑量的成本和可审计性才有保障。
