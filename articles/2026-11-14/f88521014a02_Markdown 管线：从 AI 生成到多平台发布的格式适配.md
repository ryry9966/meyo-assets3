## 背景

用 Agent 写完一篇技术稿，只是工作的开始。同一篇 Markdown 要同时发到博客、公众号、知乎/掘金这类社区，各平台的格式约束完全不同：有的吃原生 Markdown，有的只认内联样式的 HTML，有的会把外链直接剥掉。手工逐平台改格式，既费时又不可复现。这篇记录一下我们社区内部跑了几个月的自动化发布管线，思路和坑都在这。

## 问题

实际做下来，问题集中在三层：

1. **AI 输出本身不规范**：标题层级跳跃（H1 后直接 H4）、正文里混内联 HTML、脚注写法不统一（`[1]` 和 `[^1]` 混用）、代码块语言标签随意。
2. **平台差异大**：公众号要求 CSS 内联、外链转文末引用；博客需要 front-matter 和图床相对路径；宽表格在移动端普遍溢出。
3. **发布不可逆**：直接推 API，出错后删稿重发的成本很高。

## 做法：四段式管线

整条管线可以封装成 MCP tool 或 OpenClaw 插件，Agent 只负责按顺序调用：

1. **归一化**：生成后先过 lint（markdownlint 规则集 + 自写脚本），统一标题层级、剥掉内联 HTML、脚注统一为 `[^n]`、映射代码块语言标签（`shell`→`bash` 这类）。产出"规范 Markdown"，作为唯一事实源。
2. **元数据抽取**：从正文头部抽出 title/tags/summary 写入 front-matter，正文里的元信息块删除。
3. **平台适配**：用 remark/rehype 插件链或 pandoc 模板，按平台 profile 生成目标格式。公众号走 MD→HTML + CSS 内联；博客走主题模板 + 相对图床路径；外链统一转文末参考列表。
4. **校验与发布**：先渲染预览（HTML + 移动端截图），人工过目后再走各平台 API。发布层带 `dry-run` 参数。

## 踩坑点

- 公众号会剥掉 `<style>` 标签和外链，必须 CSS 全内联、外链转脚注，否则排版直接崩。
- 只靠 system prompt 约束 AI 不输出 HTML 是不靠谱的，归一化兜底必须存在，两层缺一不可。
- 超过 5 列的表格在手机端基本不可读，适配层要把宽表格降级为列表。
- 图片热链会被平台防盗链拦截，每个平台需要单独上传再替换 URL，并维护一张 URL 映射表，重发时不重复传图。
- 管线必须幂等：重复执行不能二次转脚注、二次上传。

## 可复用建议

- **单一规范源 + 每平台一份 YAML profile**：适配逻辑写成声明式插件列表，不要写死在代码里，加平台只改配置。
- **无法归一化的结构直接 fail**，不要静默降级，否则问题会延迟到发布后才暴露。
- **适配器输出预览包而非直接发布**，人工卡点放在最后一步。
- **每次转换生成变更报告**（删了什么、改了什么、传了哪些图），方便审计和回滚。
- 整条管线包成一个带 `dry-run` 的 MCP tool，Agent 的职责收敛为"调用并汇报"。

## 总结

多平台格式适配的本质是三句话：**归一一次、按平台变换、发布前验证**。把这条管线固化下来之后，发布从手工杂活变成一次 review 能覆盖的确定性流程——这才是 Agent 自动化写作真正能落地的部分。
