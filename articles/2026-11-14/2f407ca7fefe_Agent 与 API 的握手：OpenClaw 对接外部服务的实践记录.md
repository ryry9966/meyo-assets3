## 背景

Agent 的价值不在模型本身，而在它能不能触达真实系统：查工单、看 CI 状态、读值班表。OpenClaw 提供了 tool、MCP、插件三种接入方式，但"能接通"和"接得好"之间差得很远。最近我把内部几个服务接进 OpenClaw，把过程整理成这篇记录，供有同样需求的参考。

## 问题

直接把 HTTP 接口包一层丢给 agent，通常会撞上四类问题：

1. 工具描述不清，该调的时候不调，不该调的时候乱调；
2. 鉴权混乱，key 出现在 prompt 或日志里；
3. 返回值不做裁剪，一个大 JSON 直接撑爆上下文；
4. 失败没有约定格式，agent 开始自行编造结果。

## 做法

我是按这个顺序推进的：

**1. 筛接口。** 不是所有 API 都值得接。优先挑语义清晰、幂等、低风险的读操作；写操作一律后置，且必须带确认环节。

**2. 封一层薄的 MCP server。** 不暴露原始 endpoint，而是包成面向意图的工具：`query_ticket` 而不是 `GET /api/v2/ticket?...`。description 用一两句话说清"什么时候该用我"，参数 schema 每个 field 都附 example。

**3. 鉴权下沉到配置层。** key 走环境变量，server 启动时注入，全程不进对话上下文；日志脱敏单独处理。

**4. 约定返回格式。** 统一成 `{ok, data, error, hint}` 四个字段，失败时 hint 告诉 agent 下一步该干嘛（重试 / 换参数 / 放弃）。data 做字段裁剪，列表接口强制分页。

**5. 灰度验证。** 先拿十来个固定 case 跑通，观察 agent 的调用轨迹，再放开到日常使用。

## 踩坑点

- description 里堆关键词没用，agent 认的是语义。一句"用于查询近 7 天工单状态"比一段堆砌话术有效得多。
- 超时要显式设置，且短于框架默认值，否则 agent 会一直挂着等。
- 非幂等写操作踩过一次：网络超时后 agent 自动重试，建了两张一样的工单。加幂等键（请求内容做 hash）后解决。
- 工具数量超过十几个后，选择错误率明显上升。按场景拆成多个 profile 分组挂载，比全量塞进去稳。
- 错误信息别回显原始堆栈和 key，agent 会原样念给用户听。

## 可复用建议

- 先做"最小工具"验证意图识别，再逐步补全参数；
- 所有工具统一错误 schema，agent 对失败路径的处理会稳定很多；
- 危险操作加 `dry_run` 参数，先返回"将要执行什么"；
- 打开调用日志，出问题能回放轨迹，比靠猜快得多。

## 总结

对接外部服务的本质不是"打通 HTTP"，而是给 agent 一个语义清晰、行为可预期的工具面。描述写得像给人看的文档，返回值裁到模型用得上的粒度，失败路径有明确约定——这三件事做到位，对接就从碰运气变成工程。后续我打算把这套封装抽成内部模板，也欢迎大家在评论区交流各自的工具描述写法。
