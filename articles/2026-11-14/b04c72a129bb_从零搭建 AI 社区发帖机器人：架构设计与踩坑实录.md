## 背景

社区每周要发一期「本周精选」：汇总仓库 release、高频 issue、论坛好帖。纯人工做，一期大约 40 分钟，还容易漏项。我的目标是让 OpenClaw agent 定时抓取信息源、生成结构化草稿、经人工确认后发布。定位很明确：**半自动**——机器负责聚合和初稿，人负责最终把关。不追求全自动，社区账号发错东西的代价太高。

## 整体架构

拆成四层：

1. **采集层**：cron 触发 OpenClaw 任务，通过 MCP 工具拉取 GitHub releases、论坛 RSS、issue 列表。
2. **加工层**：agent 做摘要、归类、去重，产出 Markdown 草稿 + 元数据（来源链接、标签、hash）。
3. **状态层**：SQLite 存每条内容的 content hash、发布状态、游标时间戳，作为幂等依据。
4. **发布层**：独立的 MCP 写工具负责发帖，默认 dry-run，人工确认后才真正提交，保留 10 分钟撤回窗口。

一个关键决策：**采集与发布用两个不同权限的工具**。读工具随便调，写工具默认拒绝，需要显式开关加审核通过记录，缺一不可。

## 踩坑实录

**坑 1：模型编造 changelog。** 第一版把 release 原文丢给模型「总结一下」，它补了两个不存在的功能点。改法：prompt 强制「只允许转述输入事实，无法确认就标注待核实」，并把原文链接附在草稿里，方便审核时对照。

**坑 2：重复发帖。** 重试逻辑不严谨，一次网络超时重发，同一内容出现两帖。加了 content hash + 数据库唯一索引，发布前先查库，重试永远走同一条记录。

**坑 3：MCP 返回撑爆上下文。** issue 列表一次拉 100 条带完整 body，上下文直接塞满。改成工具端做字段裁剪和分页，只回传 id、标题、标签和前 200 字摘要。原始数据落盘，需要时再按 id 取。

**坑 4：定时任务与会话状态耦合。** 最初靠 agent 会话里「上次发到哪」记进度，进程重启就丢。把游标全部外置到 SQLite，任务做成无状态，任何时候可安全重跑。

**坑 5：论坛限流。** 连发 5 条触发频控。发布层加了最小间隔加指数退避，批量发布改成单条排队。

**坑 6：无人审核直接上线翻车。** 有一次标签归类错误，帖子进了错误板块。从此流程固化：草稿先进审核频道，人工回复确认后，发布脚本才执行。

## 可复用建议

- 先 dry-run 跑两周，草稿质量稳定后再开写权限
- 幂等键（content hash）+ 状态库，是自动化发帖的地基
- 读写工具分离，写操作默认拒绝
- MCP 工具返回值必须裁剪，别把原始大 JSON 直接交给模型
- 所有失败写日志并带 trace id，方便回放定位

## 总结

这套东西技术难度不高，真正的成本在**信任建立**：让机器人只做确定性高的部分，把判断留给人。目前每周精选耗时从 40 分钟降到 10 分钟（大头是审核），上线以来误发为零。下一步计划把人工审核的修改记录回流成 few-shot 样例，逐步压低干预频率——但写权限的开关，短期内不打算交给模型自己决定。
