## 背景

我在维护一个几百人的技术社区，每天想把群里的讨论、GitHub 动态整理成一条精选帖发出去。人工做了两周，纯体力活：找素材、写摘要、排版、发帖，每天固定花 40 分钟。于是决定用 OpenClaw + MCP 搭一个发帖机器人，目标很明确：每天一条摘要，人只做最后一步确认。

## 问题

最初的版本很天真：写一个 prompt 让 agent「采集素材并直接发布」。跑了三天就出事，某天素材源超时，agent 自作主张换了个来源，连发 7 条质量参差的帖子，其中一条还带着一个编造出来的链接。

复盘的结论是：问题不在模型能力，而在流程设计——生成和发布之间没有任何闸门。

## 做法

重构后的架构分五段，每段只做一件事：

1. **采集器（MCP tool）**：对接 RSS、GitHub Release、站内热帖接口，输出结构化 JSON，强制带来源 URL。
2. **生成 Agent**：只读采集结果，产出草稿；所有链接只允许引用采集 JSON 里的字段。
3. **质检层**：规则校验（域名白名单、长度、敏感词）+ 轻量模型二审，低于阈值直接丢弃。
4. **人工确认队列**：草稿进队列，命令行一键放行或改完放行。
5. **发布器（MCP tool）**：调社区 API，带 request_id 保证幂等，状态写 SQLite。

两个关键设计：Agent 每次运行都是无状态的，跨次运行的上下文全靠落盘文件传递；调度用系统 cron 而不是 agent 内置定时，时区自己控制。

## 踩坑实录

- **幂等缺失导致重帖**：发布 API 超时后重试，同一内容发了两遍。后来在发布工具里加 request_id、先查后发才解决。
- **幻觉链接**：模型会「脑补」看起来合理的文档地址。对策是生成阶段只允许引用采集字段，白名单外域名直接拦截。
- **时区错位**：cron 默认 UTC，帖子总在凌晨四点发出去。统一改为 Asia/Shanghai，并在启动时校验。
- **触发反垃圾**：模板化内容连发一周后被社区限流。改成每天上限 1 条、模板轮换、标题相似度去重（简单指纹比对就够了）。
- **最大的教训**：把「采集 + 生成 + 发布」塞进一个 prompt，等于把所有闸门都拆了。工具粒度宁小勿大。

## 可复用建议

- 每个有外部副作用的动作（发帖、写库、调 API）封装成独立窄接口的 MCP tool，生成与执行物理隔离。
- 一切发布动作先支持 dry-run；前两周全量人工审，稳定后再抽样。
- 状态落盘（SQLite/JSON），不依赖对话记忆，方便排障时回放。
- 盯两个指标：发布成功率、发帖后被删/被踩率。后者往往更早暴露内容质量问题。

## 总结

最终代码不到 400 行。复杂度不在生成，而在可控性：拆步骤、加闸门、保幂等。OpenClaw + MCP 让工具接入变得很轻，但省不掉的是工程纪律。自动化发帖的终点不是「全自动」，而是把人放在唯一有价值的环节，最终确认。
