## 背景：Agent 缺的是“时间驱动”这一环

大多数人用 Agent 还是 pull 模式：你提问，它回答，会话结束它就沉睡。但日常里最有价值的自动化往往是时间驱动的——日志有没有新报错、订阅源有没有更新、目录里有没有新文件，这些事你不会每次都记得去问。OpenClaw 提供了一个朴素但好用的机制：心跳。Agent 每隔固定间隔被唤醒一次，醒来先读工作区里的 HEARTBEAT.md，按里面的条目决定这轮要不要干活、要不要出声。

## 问题：默认状态等于没开

坑在于两极分化。HEARTBEAT.md 保持默认（只有一个 `# Heartbeat` 标题）时，agent 会直接回一个 ack 跳过本轮，机制等于不存在；而另一些人往里塞几十条任务，每次心跳都烧一遍 token，还频繁误报。核心认知：**心跳是“定时唤醒”，不是“定时执行”**。唤醒之后做什么、说不说话，完全取决于你把这份 markdown 写成什么样。

## 做法：把任务写成“哨兵指令”

1. 确认文件：工作区根目录的 HEARTBEAT.md。
2. 每条任务按固定结构写：触发条件 + 动作 + 输出渠道 + 静默条件。示例：

```markdown
# Heartbeat
- 每次心跳：查看 /var/log/app/error.log 末尾 50 行，
  仅当出现上次未记录的新 ERROR 才通知我
- 每天 09:00（本地时区）：汇总 ~/.todos/ 今日到期项，
  没有到期项则保持沉默
```

3. 调间隔：配置里 `agents.defaults.heartbeat.every`，默认 30 分钟。轻量检查 15–30 分钟足够，别为了“勤快”调到 1 分钟。
4. 指明数据源：任务里写清用哪个工具或 MCP 服务（fs、fetch、git 等），agent 才不会靠猜。
5. 跑一周再扩：先看 session 日志确认心跳真的触发了动作，再决定加任务。

## 踩坑点

- token 成本 ≈ 心跳频率 × 文件长度，两头都要克制。
- 最常见的问题是重复通知：同一个错每轮都报。解法是状态外置——给它一个持久化的 state 文件（如 last-state.json），任务里写明“与上次状态对比，有 diff 才说话”。
- 心跳默认在主会话执行，长任务会污染上下文、和实时对话抢工具。心跳只做轻量哨兵，发现事件后让 agent 起后台任务或调脚本去处置。
- 模糊任务（“帮我盯着服务器”）会让 agent 自由发挥，输出不可控。
- “每天一次”和时区语义，先跑两天验证再信任。

## 可复用建议

- 四段式模板：条件、动作、输出、沉默条件。第四项最容易被忽略，但它决定 agent 是哨兵还是复读机。
- 状态外置模式：一切检查类任务都配一个 state 文件，只对 diff 反应。
- 分层设计：心跳负责发现，完整 agent 流程负责处置，别让心跳干重活。
- 从 1–2 条任务起步，稳定运行两周后再加。

## 总结

HEARTBEAT.md 的本质，是把调度逻辑外置成一份人可读、可进版本管理的 markdown：agent 定时醒来，看一眼它，决定干活还是继续沉默。它替代不了 cron 和监控系统的精确性，但补上了“轻量、依赖上下文、需要语义判断”的那一层。用好的姿势就一句话：写得小、写得明确、让沉默成为默认。
