## 背景

Agent 要真正有用，光会应答不够，还得能主动做事：定时摘要、监控告警、任务跟进。让助手自主行动只有两条路：**轮询**（heartbeat，到点醒来自己查）和**推送**（外部事件发生时通知它）。OpenClaw 默认走 heartbeat，但实践中不少场景其实更适合推。这篇记录我在实际部署里的取舍逻辑。

## 问题

两个极端都有代价：

- **纯轮询**：每次心跳都是一次模型调用，间隔短了成本高，长了延迟不可接受。更糟的是，醒来后“没什么可做”的空转占了大头。
- **纯推送**：要求有能收事件的入口（webhook / gateway 端口），网络受限环境（家庭 NAT、设备休眠）根本收不到；而且事件丢了就是丢了，没有兜底。

## 做法

我的方案是分层混合，落地四步：

1. **给事件分类**。按“能容忍多大延迟”分三档：秒级（告警、追问）→ 推送；分钟级（抓取结果、构建状态）→ 短间隔轮询；小时级以上（日报、周报）→ cron 触发。
2. **heartbeat 保持轻**。醒来只做一件事：读一份心跳清单（类似 HEARTBEAT.md），逐条判断“要不要现在动手”。没有到期项就直接结束，不调用任何工具。清单每项维护“上次执行时间 + 幂等键”，避免重复触发。
3. **推送走 gateway 收口**。外部系统（监控、Git hook、MCP server 里的事件型工具）统一打到一个 webhook 入口，鉴权后转成 agent 会话消息。入口必须带 token 校验，不要裸奔公网。
4. **轮询兜底推送**。即使主链路是推，heartbeat 仍保留低频档（比如 30 分钟），负责对账：检查推送队列有没有积压、有没有漏发。

## 踩坑点

- **心跳提示词塞全量上下文**：早期我把完整系统提示注入每次心跳，一天空转烧掉的 token 比正经对话还多。后来拆成独立的精简心跳提示。
- **幂等没做，告警风暴**：推送重试和心跳兜底同时命中同一事件，半夜收到三条重复通知。加幂等键 + 静默窗口解决。
- **推送入口无鉴权**：裸 webhook 被扫描器打了几天才反应过来。必须校验签名。
- **设备休眠导致定时漂移**：依赖本地 cron 的任务在睡眠期间全部跳过，醒来也不补。改用 gateway 常驻，错过的任务在下次心跳补跑。

## 可复用建议

- 默认轮询起步，出现明确延迟痛点再上推送，不要一上来就搭事件总线。
- 推送只负责“递事件”，执行与去重统一交给 agent 侧处理，避免两套逻辑。
- 心跳清单是契约：每项必须有触发条件、间隔、幂等策略三个字段，缺一不可。
- 给所有主动行为加静默时段，否则你会被自己的助手骚扰。

## 总结

轮询和推送不是二选一：推送解决延迟，轮询解决可靠性，而 heartbeat 的真正价值是把“该做什么”变成一份可审计的清单。先用最便宜的轮询跑起来，让痛点告诉你哪里值得加推送，比预先设计一套事件架构更划算。
