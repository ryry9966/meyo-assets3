## 背景

自动化跑起来之后，“只执行一次”是一种奢望。定时任务重叠触发、网络超时后重试、Agent 把同一个工具调了两遍、MCP 断线重连后补发请求、人手动再点一次按钮——重跑不是异常，而是常态。写自动化时如果不把“重复执行”当成前提假设，系统迟早会在某次重试里付出代价。

## 问题

幂等性的定义很朴素：同一操作执行一次和执行多次，最终状态一致。不满足的例子随处可见：

- 日志文件用追加写，重跑一遍内容翻倍；
- 发通知的动作被重试，用户收到三条相同提醒；
- 向下游创建资源，重试后出现两份重复记录；
- 计数器类操作（+1），重跑导致数值漂移。

Agent 场景下更麻烦：模型调用工具有不确定性，同一意图可能被展开成两次几乎相同的调用。工具本身不幂等时，上游的小概率错误会被放大成真实的数据污染。

## 做法

1. **给每次“意图”分配稳定的幂等键。** 用任务 ID + 输入内容的哈希，而不是时间戳或随机数——后者每次重试都会变，等于没有键。
2. **执行前先查状态。** 写之前检查目标是否已存在（文件、记录、已发送标记），存在则跳过，或直接返回上次的结果。
3. **写操作尽量改成幂等形式。** 用 upsert 替代 insert，用覆盖替代追加，用“设置绝对值”替代“增量修改”。
4. **留执行痕迹。** 用 run_id 维护一份轻量执行日志或 marker 文件，每完成一步记录一步，重跑时从断点续走，而不是从头再来。
5. **在工具层声明幂等性。** 每个工具在描述里注明：只读 / 幂等写 / 非幂等。非幂等的操作外面统一包一层去重封装，Agent 不需要各自关心。

## 踩坑点

- **“先检查再执行”有竞态**：两个并发实例都通过了检查，然后各写一次。要么加锁，要么用条件写入（版本号、If-Match 之类），让存储层做仲裁。
- **状态标记与副作用不一致**：结果先缓存了，但真实写入其实失败，下次重跑被误判为“已完成”。关键步骤的完成标记，必须在副作用确认成功之后再写。
- **删除是天然幂等的，但“删除后重建”不是**：重跑会冲掉上一轮刚重建的新数据。
- **输出依赖当前时间或环境的任务**：重复执行内容必然不同。要提前想清楚这是可接受的覆盖式更新，还是需要固定某个快照版本。

## 可复用建议

- 给所有自动化动作做一次分类清单：只读、幂等、非幂等，非幂等项重点治理。
- 在验收流程里加一条固定测试：把整个流程连跑两遍，断言第二遍结束后状态与第一遍一致。跑不干净的流程过不了这一关。
- Agent 编排中，把重试策略和幂等键绑定：同一意图的所有重试共享同一个键，去重层才有据可依。
- 宁可让工具“慢一点但可重入”，也不要追求“快但不安全”的一次性写入。

## 总结

幂等性本质上是在为失败买单：它允许你放心地重试、放心地重跑、放心地让 Agent 再试一次。自动化的可靠性从来不取决于“不出错”，而取决于出错之后重复执行是否安全。把幂等当成设计默认值而不是事后补丁，是这类系统最省心的一条工程纪律。
