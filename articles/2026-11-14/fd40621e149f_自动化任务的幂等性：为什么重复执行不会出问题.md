## 背景

跑自动化的人迟早会遇到同一个场景：定时任务重叠触发了、agent 因为超时重试了、或者你自己手滑又点了一次执行。人类操作员会意识到"这事我已经做过了"，但脚本和 agent 不会——它们只是执行。幂等性（idempotency）就是让"执行一次"和"执行 N 次"最终状态一致的工程设计。在 OpenClaw 这类 agent + MCP + 定时触发的组合里，这不是锦上添花，而是底线。

## 问题

几个常见的翻车形态：

- 每日摘要任务因网络超时重试，群里发了两条一样的消息；
- agent 调 MCP 工具创建工单，重试后出现重复工单；
- 某步骤"往配置文件追加一段配置"，批量任务重跑后配置里出现三份相同段落；
- 批处理跑到一半失败，从头重跑，前一半被处理了两遍。

共同点：这些都是**追加型/创建型**操作——执行次数会改变结果。读操作、把状态设为某个值的 set 语义天然幂等；append、increment、create 不是。

## 做法

1. **给任务定义稳定的幂等键。** 键必须来自业务含义，比如 `task_id + 日期 + 目标对象`，而不是每次尝试随机生成的 UUID——后者在重试时会变，等于没设。
2. **执行前先查状态。** "文档里是否已有这个日期的段落""这个工单是否已存在"。有就跳过或覆盖，没有才执行。
3. **优先 set / replace，少用 append / increment。** 比如同步任务写 `## sync-2025-06-01` 这种确定性标题，重复执行就是覆盖同一段，天然安全。
4. **留下执行记录。** 一张带唯一键的表或一个本地状态文件即可：幂等键 + 结果 + 时间。重跑先查账，这就是"至少一次投递 + 幂等消费"的朴素实现。
5. **批任务记录进度游标。** 处理到哪条就记到哪条，重跑从断点续传，而不是从头再来。

## 踩坑点

- **幂等键里带了 `now()`。** 重试时刻变了，键也变了，去重直接失效。
- **查了再做，但两跑并发。** 两个实例同时通过检查、同时执行。检查只能减少概率，兜底要靠唯一约束或锁。
- **把"记账"和"动手"当成原子的。** 先记录再执行，动作失败记录还在，要预留"已记录但未成功"的重试路径；反过来先执行后记录，中间断了就可能重复执行。发消息、调第三方 API 这类外部副作用无法回滚，只能靠先记账或对端去重。
- **以为上游幂等。** 你这侧重试逻辑没问题，但对方接口调两次就扣两次款。接入 MCP 工具前先确认它的语义。

## 可复用建议

- 写任何自动化步骤时，默认假设"它迟早会被执行两次"，用这个假设倒逼设计。
- 沉淀一个固定模式：**确定性幂等键 → 查状态 → set 语义 → 记账**，大多数任务套进去即可。
- 上线前在 staging 里故意把同一任务跑两遍、跑一遍中断再续跑，作为标准验证项。
- 给 MCP 工具写文档时标注哪些幂等、哪些不幂等，让上层 agent 编排时心里有数。
- 状态记录不必上重型方案，一张带唯一键的表或一个 JSON 文件能撑很久。

## 总结

幂等性不是给系统加保险，而是让"重试、重跑、重复触发"这些自动化里必然发生的事变得无害。它几乎总是比事后清理重复数据的成本低。下次写自动化任务时，先问自己一句：这段代码被执行两次，会发生什么？答不上来，就先补上幂等键再上线。
