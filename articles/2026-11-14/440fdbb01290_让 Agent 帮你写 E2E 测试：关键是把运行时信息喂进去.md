# 让 Agent 帮你写 E2E 测试：关键是把运行时信息喂进去

## 背景

E2E 测试是出了名的“欠账”区：写一条用例要处理登录、造数据、找选择器，页面一改就碎，很多团队最后只保住一两条核心链路。Agent 生态起来之后，一个常见的尝试是把代码丢给模型让它“顺手生成测试”，结果通常是跑不起来，或者跑起来了但什么都不断言。

## 问题出在哪

写 E2E 需要两类信息：**静态的**（代码结构、类型定义、路由）和**运行时的**（真实 DOM、接口返回、报错输出）。纯代码生成只拿到前者，模型只能猜选择器、猜接口、猜等待时机——猜错一处，整条用例崩掉。

思路因此很直接：把运行时信息也接进 Agent 的工具链。在 OpenClaw 里做这件事的自然入口就是 MCP。

## 做法：一条四步闭环

1. **定规范**。先写一份测试约定文档：只允许 role 和 data-testid 定位、禁止固定 sleep、断言业务结果而非纯视觉状态。作为固定上下文注入，人和 Agent 读同一份。
2. **先探查，再生成**。给 Agent 配浏览器类 MCP 工具（比如 Playwright MCP），让它先打开真实页面，收集可访问性角色、可见文本、关键请求，再基于探查结果写用例。选择器是“看到的”，不是“编的”。
3. **本地回路**。Agent 生成后自己执行测试命令、读失败输出、修一轮再跑。设好止损：连续失败两轮就停下交给人，避免它陷入循环改选择器。
4. **人只审三件事**：断言语义对不对、数据准备是否合理、覆盖了哪些分支。定位与样板代码基本不用看。

我们按这个流程试了两周，核心链路单条用例的编写成本明显下降，AI 用例的首跑通过率比“直接让模型写”高出一截。

## 踩坑点

- **假绿**：Agent 容易写出不断言的用例。粗暴但有效的检查：每条用例至少两个有效 expect，生成后先 grep 数量再看代码。
- **fixture 幻觉**：模型会编造不存在的接口和字段。把 OpenAPI 文档或类型定义放进上下文，让它只能引用真实 schema。
- **等待方式**：不加约束它会到处塞固定 sleep，CI 上必炸。规范里写死“只能显式等待”，再配一条 lint 兜底。
- **上下文膨胀**：别整个仓库塞进去。按页面/路由分批喂；探查快照落盘复用，页面改版时 diff 快照就知道哪些用例要跟着改。
- **CI 差异**：时区、视口、预置账号状态——本地能过、CI 挂掉的问题九成出在这三样。

## 可复用建议

- 测试规范文档是整个流程的杠杆点：先写它，再上 Agent。
- AI 生成用例单独打 tag、单独统计 flaky 率，跑稳两周再转正，转正标准和人写用例一致。
- 人的精力放在“断言什么、覆盖什么”这类判断上；找选择器、写样板、失败重试这些机械劳动交给 Agent。
- 探查快照沉淀下来，是后续维护阶段最便宜的资产。

## 总结

Agent 写 E2E 的价值不在“一键生成”，而在分工：运行时探查、样板生成、失败重试自动化，断言语义和覆盖决策留给人。**能否闭环、能否拿到真实运行时信息**，是把这套流程和“把代码丢给模型”区分开的两条硬标准。
