## 背景

Agent 的调用链和普通后端不一样：不是"服务 A 调服务 B"，而是"模型 → 工具/MCP → 外部 API"，而且模型会根据拿到的错误信息决定下一步动作。这意味着外部 API 一挂，故障会被放大——轻则单次任务失败，重则模型陷入无意义的重试循环，烧 token 的同时还可能重复触发副作用。

## 问题

实践中外部 API 故障分三类：

1. **网络层**：超时、连接拒绝、DNS 失败；
2. **协议层**：429 限流、5xx、返回结构突变；
3. **语义层**：HTTP 200 但业务失败（余额不足、内容被风控拦截）。

很多框架默认只处理第一类，后两类往往把原始报错原样塞回上下文，模型开始"自由发挥"，越修越偏。

## 做法

建议分三层处理：

**第一层：传输层兜底**
- 所有外部调用显式设超时（连接 3–5s，读取 15–30s，按 API 特性调），不要依赖库默认值；
- 重试只针对幂等请求，指数退避加随机抖动，上限 3 次；
- 区分错误码：429 读 `Retry-After` 再等，5xx 可重试，4xx 直接上报不重试。

**第二层：逻辑层降级**
- 熔断：连续 N 次失败后短路，冷却期内不再打这个 API；
- 降级路径提前写好：历史缓存结果、备用 provider，或"跳过该步骤并在最终报告里标注"；
- 有副作用的操作（发消息、下单、写库）带幂等键，重试不会重复执行。

**第三层：给模型结构化错误**

不要把堆栈喂给模型，返回结构化摘要：

```json
{"error_type": "rate_limited", "retry_after_s": 30, "recoverable": true}
```

模型看到 `recoverable: false` 会主动走降级分支，而不是反复撞墙。

## 踩坑点

- **重试叠加**：模型层自己重试，代码层又重试，一次故障实际打了 9 个请求。重试只能由一层负责；
- **超时过长**：单个工具 60s 超时，整个 Agent 循环被卡死，并行任务全部排队；
- **429 当 5xx 处理**：立刻重试只会被限得更狠；
- **熔断后没有恢复探测**：API 早就恢复了，Agent 却永远走降级路径；
- **降级结果不标注来源**：下游把缓存数据当实时数据用，错得更隐蔽。

## 可复用建议

1. 每接一个新工具，先回答三个问题：幂等吗？超时多少？挂了走哪条降级路径？答不上来就别上线；
2. 错误返回统一 schema，至少包含 `error_type` / `recoverable` / `retry_after` 三个字段；
3. 熔断状态做持久化，Agent 重启不重置；
4. 给外部调用加独立指标（成功率、P99 延迟、熔断触发次数），排障时比翻模型日志有效得多。

## 总结

Agent 错误恢复的核心不是"重试得更聪明"，而是把故障决策从模型手里收回来：传输层管重试，逻辑层管降级，模型只拿到一个干净的结构化结论。外部 API 一定会挂，区别只在于挂的那一刻，你的 Agent 是优雅退化，还是在烧 token 原地转圈。
