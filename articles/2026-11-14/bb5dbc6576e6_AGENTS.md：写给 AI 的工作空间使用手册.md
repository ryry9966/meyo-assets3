## 背景

AGENTS.md 是一个正被各家编码 Agent 广泛采用的约定：在工作空间根目录放一个同名 Markdown 文件，Agent 进入工作目录时会自动读取。它相当于 README，但读者不是人，而是模型。在 OpenClaw 的工作空间里，这份文件承担的是"入职手册"的角色——你的项目约定、偏好、禁区，都写在这里。

## 问题

没有这份文件时，Agent 每次会话都从零开始：

- 不知道测试怎么跑，凭训练数据里的经验猜命令；
- 不清楚代码风格，生成物和你仓库现有风格不一致；
- 不知道哪些目录不该碰（生成物、vendored 依赖）；
- 提交信息、分支命名各凭运气。

结果是你花在纠正上的时间，超过了它省下的时间。上下文无法跨会话持久化是当前所有 Agent 的共同短板，AGENTS.md 是补这个短板成本最低的手段。

## 做法

**1. 从最小可用版本开始。** 建议五个段落：项目概述、常用命令、代码约定、禁区、验证方式。一个真实感很强的骨架：

```markdown
# 概述
内部任务调度服务，Go 1.22 + Postgres。

# 常用命令
- 测试：make test（勿直接 go test ./...，集成测试需本地 PG）
- Lint：make lint

# 约定
- 错误统一用 fmt.Errorf("%w") 包装
- handler 不写业务逻辑，下沉到 service 层

# 禁区
- 不要修改 gen/ 目录（生成物）
- 不要执行 git push

# 验证
改动后必须通过 make test && make lint
```

**2. 用失败驱动迭代。** Agent 犯一次错，就补一条对应约束，一行即可。这份文件应该像回归测试用例一样随问题增长，而不是试图一次写完。

**3. 分层放置。** 根目录放全局约定，子项目目录可放各自的 AGENTS.md，Agent 通常按就近原则读取。

**4. 当代码管理。** 进版本库、走 review、随重构同步更新。

## 踩坑点

- **太长等于没有。** 几百行的指令会稀释关键约束的权重，经验上控制在 100 行以内，细节链接到 docs 下的具体文件。
- **空话无法执行。** "写出高质量代码""遵循最佳实践"这类话模型没法落地，要写成可判定的事实："错误必须用 %w 包装""测试文件放 test/ 目录"。
- **和实际脚本不一致。** 文件里写的命令跑不过，Agent 会在猜测和报错之间反复横跳，比不写还糟。写完自己先跑一遍。
- **内容过期。** 重构后目录变了、命令换了，手册没跟上，Agent 会拿着旧地图走新路。建议在 CI 里加一条轻量检查，或纳入定期 review。
- **别放敏感信息。** 它会被完整送进模型上下文，密钥、内网地址一律不写。

## 可复用建议

- 把 AGENTS.md 当作"面向 AI 的 API 文档"维护：准确、简短、可执行。
- 多项目团队沉淀一份公共片段，各仓库只写差异部分，减少漂移。
- 每次升级 Agent 工具或更换模型后，回头验证指令是否仍被遵守——不同模型对指令的服从度有明显差异，别默认一份文件永远有效。
- 观察一个指标：同一类纠正动作连续出现两次以上，说明手册缺了一条，立刻补上。

## 总结

AGENTS.md 的本质，是把你的隐性工程习惯显性化、持久化。它不神秘，就是一份维护良好的使用手册，差别只在读者是模型。写得越像"可执行的规范"而不是"愿景宣言"，Agent 的表现就越稳定。在 OpenClaw 的工作空间实践里，它属于典型的"投入十分钟、回报持续数周"的改动——值得每个 workspace 都放一份。
