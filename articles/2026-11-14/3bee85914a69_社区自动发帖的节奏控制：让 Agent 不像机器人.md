## 背景

我们社区里跑着几个 OpenClaw agent，负责每日摘要、新帖索引和部分常规回复，走的是定时任务 + MCP 触发的路子。内容质量本身没问题，但上线两周后收到一条真实反馈："这号一发言我就知道是机器人。"不是内容差，是节奏太机械。

## 问题：机器人感从哪来

拆下来主要是四个特征叠加：

- **固定间隔**：cron 整点触发，分钟级规律一眼可辨；
- **全天候在线**：凌晨三点照发不误；
- **模板化**：标题、格式、表情每次完全一致；
- **秒回**：监听到消息立刻回复，比人快一个数量级。

即使内容是原创的，这些时间特征也会让社区把它归类为灌水号。

## 做法：把"发什么"和"什么时候发"拆开

生成层照常产出内容进队列，发布层单独控节奏：

1. **活跃时段建模**：拉一周频道消息的时间分布，得到社区活跃曲线，只在该分布内采样发布时间，不做全天均匀撒帖。
2. **抖动（jitter）**：目标时间 ±15~40 分钟随机偏移，避开整点、避开固定间隔。
3. **频控**：单账号日发帖上限 + 突发冷却——连续发 3 条后强制间隔 2 小时以上。
4. **回复延迟**：监听到消息不立即回，按重要度加 2~10 分钟延迟；低价值消息直接跳过，不必每条都回。
5. **内容微差异**：同一模板做 2~3 个长度和句式变体轮换，避免每次长得一模一样。
6. **全链路日志**：每次发布记录"为什么此时发"——命中哪个时段、抖动了多少、限流是否生效，事后可审计调参。

节奏参数独立成配置，不硬编码：

```yaml
rhythm:
  active_windows: ["08:30-11:30", "13:30-15:00", "19:30-23:00"]
  jitter_minutes: [15, 40]
  daily_cap: 6
  cooldown_after_burst: 3
  reply_delay_minutes: [2, 10]
```

## 踩坑点

- **均匀随机 ≠ 自然**。直接 uniform 随机会在低活跃时段产生孤帖，凌晨四点的发帖比整点发更假。要用活跃度分布做加权采样。
- **抖动过猛**。±2 小时的随机显得"喝醉了"。persona 的一致性比时间随机更重要，抖动控制在 15~45 分钟比较稳。
- **重试风暴**。发布失败立即重试，三次失败等于连发三帖。重试必须退避且重新排队。
- **多实例同频**。两个 agent 各自抖动但配置相同，偶尔还是会同窗口撞车。给每个实例不同随机种子和错峰基准。
- **时区**。容器里跑 UTC，活跃曲线却是东八区，整体错位。启动时显式校验时区，这个坑我们踩过一次。

## 可复用建议

- 节奏参数（时段表、抖动幅度、上限、冷却）全部配置化，方便按社区调整。
- 用**单帖互动率**做反馈信号：某时段发的帖互动持续偏低，说明时段模型该更新了——社区活跃习惯会漂移，建议每月重算一次分布。
- 保留手动 kill switch：一个开关让所有 agent 静默，出问题先停再说。
- 定期人工看一眼 agent 发帖在时间线上的排布。肉眼看时间线，比翻日志更容易发现规律性。

## 总结

节奏控制的目的不是伪装成真人，而是让自动化行为贴合社区的天然节律，做一个不打扰人的参与者。核心就一句话：**发布时间和发布内容一样值得设计**——生成归生成，发布归发布，中间用带抖动和限流的队列隔开。节奏对了，同样一份摘要，观感从"灌水"变成"值守"。
