## 背景

用 OpenClaw 这类 agent 做内容生产，最常见的产出格式就是 Markdown：报告、教程、发布说明、社区帖子。但"生成完了"和"能发出去"之间隔着一层：公众号不直接支持标准 Markdown，掘金和知乎的代码高亮规则不同，部分平台会剥掉 HTML 标签和脚注。很多团队的做法是让模型"帮我转成公众号格式"，结果每次输出都不稳定，出了问题也没法回归。

## 问题

把格式适配交给模型本身，有三个工程上的硬伤：

1. **不可复现**：同样的输入，两次转换结果可能不同，问题无法定位。
2. **无法测试**：格式转换本质是纯函数式工作，混在 LLM 调用里就写不了单测。
3. **职责错位**：模型擅长内容，不擅长逐字符级的格式规则。这些规则是确定性的，应该由代码执行。

## 做法

核心思路：把 Markdown 当 AST 处理，而不是字符串。管线分五段：

1. **规范化**：AI 输出先过一遍 mdast（remark）清洗——统一标题层级（正文从 h2 开始，h1 留给标题字段）、补齐代码块语言标签、统一列表缩进、剥离模型偶尔夹带的解释性文本。
2. **校验**：用 lint 规则约束"本项目允许的语法子集"。比如不用脚注（公众号不支持）、表格不用对齐语法、图片必须走图床白名单域名。不合规直接报错，不做静默降级。
3. **变体生成**：以 canonical Markdown 为唯一事实源，用 rehype 插件链按目标平台生成变体。公众号走 HTML + 内联样式（遍历 AST 注入 style），掘金/知乎基本只改图片链接和 frontmatter。
4. **资产处理**：图片单独抽出来——先上传到图床或平台，拿到最终 URL 后回写 AST 里的 image 节点，再渲染。顺序不能反。
5. **发布**：把整条管线包成一个 MCP tool，例如 `publish_post(markdown, targets)`。agent 只负责产出 canonical 内容，格式适配对它完全透明。

## 踩坑点

- **不要用正则改 Markdown**。嵌套列表、代码块内的伪语法、转义字符，正则迟早翻车。AST 遍历是唯一稳妥路径。
- 公众号的**内联样式要在 rehype 层注入**，别让模型直接输出 HTML——它会混进不可控的标签和 class。
- **脚注和任务列表**在微信端会被剥掉，提前在校验层拦下，比发布后手改省事得多。
- 图片如果**先渲染后上传**，URL 替换容易误伤代码块里的示例链接；操作 AST 节点没这个问题。
- 转换器要**幂等**：同一输入跑两遍结果一致，否则缓存和重试都会出鬼。

## 可复用建议

- 定义一份 canonical schema（frontmatter：title、tags、targets、cover），所有平台变体从这里派生。
- 写一篇覆盖你全部语法的"烟雾测试文章"，每次改管线后跑一遍各平台变体，diff 确认。
- 变体生成规则落成版本化的模板文件，别硬编码在脚本里。
- 把 `publish_post` 做成 MCP tool 之后，多平台发布就是 agent 的一次工具调用，管线与 agent 彻底解耦。

## 总结

格式适配是确定性工作，交给确定性代码；模型只负责它擅长的内容生成。一条 AST 驱动、带校验、可测试的 Markdown 管线，比反复调 prompt 稳定得多，也让"生成 → 校对 → 发布"能真正串成可自动化的流程。
