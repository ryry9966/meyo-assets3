## 背景

云 API 用久了会有几个不爽：费用随调用量线性增长、隐私敏感数据不敢往外发、网络一抖 Agent 就断线。对 OpenClaw 这类常驻的个人 Agent 来说，模型后端其实不一定非在云端——家用电脑跑一个量化后的开源模型，足以承担相当一部分日常任务。这篇帖记录我在一台 32GB 内存 + 16GB 显存的机器上，把本地模型接进 OpenClaw 工作流的完整过程。

## 问题

直接上手会遇到三个现实约束：

1. 显存/内存有限，大参数模型塞不下；
2. 小模型的工具调用能力明显弱于旗舰云模型，Agent 多步任务容易崩；
3. 长上下文下 KV cache 会额外吃显存，实际可用上下文比标称少。

## 做法

**第一步：盘点硬件。** 选模型的核心公式很简单：权重显存 ≈ 参数量 × 量化位宽 ÷ 8，再留 20–30% 给 KV cache 和激活。16GB 显存跑 14B 级别的 Q4 量化很稳；7B–8B 可以开更高量化或更长上下文。Mac 用户看统一内存，公式相同但内存带宽是瓶颈，M 系列芯片的推理速度意外地能打。

**第二步：选运行时。** 我选 Ollama，理由是 OpenAI 兼容接口开箱即用、模型管理省心。追求极限性能可以直接上 llama.cpp 或 vLLM，但对个人工作站，易用性的收益更大。

**第三步：选模型和量化。** 基线建议 Q4_K_M 的 GGUF，质量和体积的甜点位。优先验证工具调用而不是聊天质量——下载候选模型后，先拿几个带 function calling 的测试 prompt 过一遍再定。

**第四步：接入 OpenClaw。** 把模型后端指向本地 OpenAI 兼容端点（Ollama 默认 `localhost:11434`），注意 context window 参数要和服务端 `n_ctx` 对齐，避免一边以为 32k、一边实际只有 8k。

**第五步：混合路由。** 全本地不一定是终点。我的分工是：日常总结、消息分类、简单工具调用走本地 14B；复杂规划、长文档分析回落到云端模型。OpenClaw 的模型配置支持按 agent/会话区分，正好用上。

## 踩坑点

- **KV cache 是隐形杀手。** 标称 32k 上下文拉满直接 OOM。`n_ctx` 设为预估真实用量的 1.2 倍即可，别无脑开满。
- **小模型工具调用参数会幻觉。** 表现为 JSON 字段拼错或类型不对。解法：工具 schema 收紧枚举值，OpenClaw 侧加一层参数校验加重试。
- **量化对 Agent 任务的影响大于聊天。** Q4 以下闲聊还行，多步推理掉点明显，主力模型不要低于 Q4_K_M。
- **Embedding 也要一起算账。** 做本地 RAG 的话，embedding 模型的显存开销别漏掉。
- **macOS 别拿显卡直觉套用。** 统一内存机器上上下文长度对速度的影响和 NVIDIA 卡完全不同，必须实测。

## 可复用建议

1. 建一个自己的基准脚本：固定 5–10 个真实任务（含工具调用），每次换模型跑一遍，别只看跑分。
2. 本地后端设超时和降级路径，崩了自动切云端，别让 Agent 卡死。
3. 显存预算表化：主模型 + embedding + 系统占用，写下来再决定买卡还是加内存。
4. 用 `keep_alive` 常驻主力模型，避免频繁换模型反复加载。

## 总结

本地 LLM 不是要替代云模型，而是给个人 Agent 补一层“永远在线、数据不出门”的底座。14B Q4 级别已经能接住 OpenClaw 大部分高频轻任务，配上混合路由，体验和成本都能打平。方法论一句话：按显存公式选模型，按工具调用质量验模型，按任务复杂度分流量。
