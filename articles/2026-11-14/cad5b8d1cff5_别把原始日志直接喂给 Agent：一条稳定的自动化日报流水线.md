## 背景

我们团队维护着十几个长期运行的 Agent 任务和一批 cron 脚本，日志散落在应用日志文件、CI 输出、工单系统三处。每天的站会要一份日报，之前靠人肉翻日志，写一份要半小时，还经常漏掉关键错误。于是搭了一条"原始日志 → 结构化日报"的流水线，核心思路一句话：**代码负责算数，Agent 负责说话**。

## 问题

直接把日志丢给 Agent 总结，有三个硬伤：

1. 日志量大，轻松撑爆上下文，只能截断，截断就丢信息；
2. 没有结构化输入时，模型倾向于"编数字"，错误计数、耗时分布基本不可信；
3. 输出格式每天漂移，交付端（群机器人）没法稳定解析。

另外还有个隐蔽问题：定时任务挂了没人知道，日报静默缺失，往往第二天才被发现。

## 做法

流水线分五步，前三步纯脚本，第四步才进 Agent：

1. **采集**：cron 按日期分区拉取三类源日志到 staging 目录，每天一个目录，文件名带来源标识。
2. **归一化**：解析成统一的 JSON 行格式（timestamp / source / level / event_type / payload），过滤 DEBUG 和健康检查噪音，重复堆栈按 pattern 去重。
3. **聚合**：脚本先算出确定性指标——错误总数、Top5 错误模式、各任务成功率、当日代码变更摘要，产出一份约 2KB 的 metrics JSON。
4. **Agent 撰写**：Agent 的输入只有 metrics JSON + 少量代表性错误样本 + 一份版本化的模板 prompt，输出强制为固定 schema 的 JSON，分段为概览 / 异常 / 变更 / 待办。
5. **校验与投递**：schema 校验通过后，脚本核对叙事中的数字与 metrics 是否一致，不一致触发一次带错误信息的重试；随后推送群机器人，并归档到带日期的报告仓库。

## 踩坑点

- **时区坑**：最初按本地日期分区，日志却是 UTC 时间戳，导致每天早 8 点前的日志落到"昨天"，早高峰错误被漏掉。改为统一 UTC 分区，报告中再做本地化显示。
- **格式漂移**：模型偶尔自作主张加"天气建议"之类的段落。靠 schema 严格校验 + 携带校验错误信息重试解决，重试上限 2 次。
- **静默失败**：cron 层加了 last_success 时间戳标记和看门狗脚本，超过 25 分钟没有成功记录就单独告警，告警通道与日报投递分开。
- **幂等性**：手动重跑会在群里发两份。给每次运行生成 run_id，投递前查重。

## 可复用建议

- 别让 Agent 碰原始日志。先在代码层完成过滤、去重、计数，Agent 只接触压缩后的指标和样本，输入控制在 4KB 以内，成本和幻觉率都可控。
- 把报告模板 prompt 当代码管理：进仓库、走 review、带版本号，回溯问题时能对上当时的 prompt 版本。
- staging 原始数据保留 14 天，日报只是派生物，随时可重算。
- 先接一个日志源跑通全链路，再逐个加源，不要一开始就五路齐上。
- 准备固定的 fixtures 日志做离线测试，改 prompt 或解析逻辑后跑一遍回归。

## 总结

这条流水线写完花了大约两天，之后每天稳定出报，站会前自动进群。最大的经验是：自动化的价值来自确定性环节的可靠，Agent 只该做最后一公里的"翻译"，而不是数据处理本身。把数学交给代码，把语言交给模型，校验和告警兜底——这套结构可以直接搬去周报、变更通报等场景。
