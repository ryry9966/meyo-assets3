## 背景

OpenClaw 在我们的部署里更像一个常驻的 Agent 网关：模型负责决策，真正干活的是它挂在身上的工具。工具越接越多之后我们发现，「能不能调通」从来不是难点，难点在于整条链路——工具注册、鉴权、参数传递、错误回传——是否稳定、可维护。这篇整理我们在对接两个内部服务和一个第三方 SaaS 时的做法。

## 问题

最初两周踩的坑很典型：

- **Agent 经常猜参数**：工具描述写得像给人看的 README，模型读不懂字段语义；
- **密钥散落**：有的写在 prompt 里，有的硬编码在插件中，换环境就断；
- **失败不可观测**：API 超时了，Agent 只回一句「调用失败」，日志里找不到 trace。

本质上，Agent 调 API 不是「发个 HTTP 请求」，而是一次三方契约：模型、工具层、外部服务，任何一侧语义不清，握手就失败。

## 做法

我们最后收敛成五步：

1. **先划工具边界，再写代码。** 一个工具对应一个业务动作，而不是把整个 REST API 包成一个「万能调用」。粒度太粗，模型选不对；太细，注册表爆炸。我们按「模型能独立决策的最小动作」来切。
2. **把 tool description 当 prompt 写。** 无论用 MCP server 还是原生插件暴露工具，都同理：每个参数写清楚类型、单位、可选值和反例。比如在 `status` 枚举里注明「closed 不含已取消订单」，比一段漂亮文案有用得多。
3. **鉴权统一收敛到配置层。** API key 只放 OpenClaw 的环境配置，插件里只引用凭据名；不同服务映射不同凭据，按最小权限申请 scope。
4. **错误要设计成「给模型看的」。** 统一返回结构化错误：错误码、人类可读的原因、建议动作。超时和重试放在工具层，且只对幂等接口做指数退避。
5. **每个工具配一个冒烟用例。** 上线前跑一遍最小调用链：参数固定、结果可断言，避免改一处崩一片。

## 踩坑点

- 非幂等接口盲目重试，出现过一次重复建单。后来在工具层加了幂等键，重试才敢放开；
- 大结果直接返回模型，一次报表查询把上下文撑爆。现在一律分页，返回截断摘要 + 数据引用；
- schema 字段名与真实 API 不一致（驼峰/下划线），模型会照着 schema 传参，网关层必须做映射；
- 时间参数忘带时区，跨服务比对时差了八小时。现在约定统一传 UTC。

## 可复用建议

- 工具集合从最小集起步，缺了再加，别一上来铺十个；
- 描述、schema、错误信息，三处都是写给模型的 prompt，按 prompt 的标准打磨；
- 所有外部调用走同一层适配器，鉴权、超时、重试、日志才有统一挂点；
- 日志记 trace id 和脱敏后的参数，排障基本靠它。

## 总结

对接外部服务的本质是契约设计，不是提示词技巧。把工具当成 API 一样认真对待——边界清晰、语义明确、错误可读、调用可观测——Agent 与外部服务的握手才稳。这套流程我们在三个服务上复用后，新服务接入成本基本降到了半天以内。
