## 背景

Agent 本身只会"想"，真正"做"事靠外部调用。OpenClaw 的能力边界，很大程度上取决于它能稳定触达多少外部服务：查库存、发通知、拉数据、建工单。MCP 和插件体系把"工具"标准化了，但从"能调通"到"生产可用"，中间还差一层工程处理。这篇帖子聊的就是这一层：Agent 和 API 之间的握手怎么做才稳。

## 问题

裸对接 API 时，常见症状有四类：

1. **上下文爆炸**：把接口原始响应直接塞给模型，一段 20KB 的 JSON 就把对话撑坏了。
2. **偶发失败没有兜底**：上游偶发 502 或超时，Agent 把失败当结论报告给用户。
3. **非幂等操作重试出事**：重试本是好事，但"发消息""下单"这类操作重试一次，就是重复扣款或重复通知。
4. **凭证管理粗放**：API key 写死在配置里、打进日志，或者申请了远超所需的 scope。

## 做法

建议在 Agent 和真实 API 之间加一个薄的 adapter 层，按以下步骤做：

**第一步：定义工具契约。** 用 MCP server 或插件 schema 把接口暴露成工具：名称、参数、返回结构写清楚。参数描述要具体到格式（比如"日期，YYYY-MM-DD"），模型是照着描述生成参数的，描述含糊就等着收幻觉参数。

**第二步：鉴权收口。** 凭证走环境变量或 secret store，adapter 统一读取，不落 prompt、不落日志。scope 按最小权限申请，先 read-only 跑通再加写权限。

**第三步：超时 + 重试 + 幂等键。** 所有出站调用设硬超时（建议 10–30 秒）。重试只针对幂等操作或带幂等键的写操作，指数退避，最多两三次。非幂等操作失败就直接报错给人处理，别自作聪明。

**第四步：响应裁剪。** adapter 负责把上游响应"翻译"成模型友好的结构：只保留关键字段，超长列表截断并标注总数，返回体控制在 1–2KB 内。

**第五步：错误语义化。** 把 4xx/5xx 翻译成 Agent 能判断的信号：429 告诉它"稍后可重试"，401 告诉它"凭证失效需人介入"，400 则透传上游错误信息——模型拿到准确错误，往往能自己修正参数重调。

## 踩坑点

- **分页忘了截断**：一个"列出全部订单"的工具返回几百条，token 直接打爆。永远在 adapter 层加 limit。
- **Webhook 没验签**：入站回调不校验签名，等于给外部开了个免费触发器。
- **日志记录了完整请求头**：Authorization 头进了日志，等于凭证泄漏。
- **重试不区分 GET 和 POST**：GET 可以无脑重试，POST 必须先想清楚幂等性。
- **契约与实际返回不符**：schema 说返回数组，实际可能返回 null，模型照 schema 用就崩。契约要和真实返回对齐，最好用真实样例回放验证。

## 可复用建议

- adapter 层保持"薄"：只做鉴权、超时、裁剪、错误映射，不做业务逻辑。
- 上线前先做 dry-run：工具调用只打印不执行，人审通过再放行写操作。
- 每次调用记结构化日志（工具名、参数摘要、状态码、耗时、是否重试），排查 Agent 行为基本全靠它。
- 新服务先只读跑一周，错误率和 token 消耗稳定后再放开写操作。

## 总结

对接外部服务的本质，是给模型和真实世界之间装一个"协议转换器 + 安全阀"。OpenClaw 把工具协议标准化了，但鉴权、超时、幂等、响应裁剪这些脏活，仍然要每个接入者自己做好。握手握得稳，Agent 才敢放手做事。欢迎在评论区分享你们对接时的踩坑经历。
