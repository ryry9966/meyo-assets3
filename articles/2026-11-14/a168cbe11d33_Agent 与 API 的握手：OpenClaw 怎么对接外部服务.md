## 背景

Agent 本身只会推理，真正能"做事"靠的是工具调用。OpenClaw 的能力边界，很大程度上取决于它接了哪些外部服务：查工单、读对象存储、发通知，都是通过工具这一层完成的。对接做得好，agent 是一个可靠的自动化节点；做得糙，就是一个会编造参数的随机故障源。

最近我把 OpenClaw 接到几个内部服务上（工单系统、对象存储、通知服务），踩了不少坑，这里把流程和经验整理出来。

## 问题

对接外部 API 时，通常卡在四个地方：

1. **认证**：token 放哪、怎么刷新、权限给多大；
2. **参数幻觉**：工具描述写得含糊，agent 传参就开始自由发挥；
3. **响应膨胀**：一次查询返回几千条数据，直接把上下文撑爆；
4. **异常兜底缺失**：超时、限流没有处理，agent 表现为"卡住"或者"乱猜结果"。

## 做法

我的接入路径是：MCP server 优先，OpenAPI 生成兜底。

**第一步：选接入方式。** 已有 MCP server 的服务直接用，省去自己封装；只有 REST 接口的服务，用 OpenAPI spec 转成工具定义，再包一层薄的 MCP server，业务逻辑不进这一层。

**第二步：裁剪工具面。** 不要把整个 API 全部暴露。一个服务挑 5~8 个高频操作就够了。工具越多，agent 选错的概率越高，这是实测出来的规律。

**第三步：收紧 schema。** 每个参数写清类型、必填性、枚举值；description 用"做什么 + 什么时候用 + 什么时候别用"三段式。比如分页参数明确写"单页最多 50 条，超出请用 cursor 翻页"。

**第四步：认证与超时。** 凭证走环境变量或独立配置文件，不进 git。所有调用强制 10s 超时，最多重试 2 次，且只对幂等操作开放。写操作加 dry-run 参数，先让 agent 走一遍参数校验。

**第五步：冒烟验证。** 上线前用固定问题跑一遍：单条查询、列表分页、一次 dry-run 写操作。确认参数被正确解析、响应能被正确总结，再逐步放开。

## 踩坑点

- **响应不裁剪**：接对象存储时列资源全量返回，几千行把会话直接打崩。后来统一在 server 层截断到 20 条，并提示"请加过滤条件重试"。
- **只写"成功"路径**：通知服务被限流返回 429 时，agent 会自己"脑补"发送成功。工具返回必须显式区分成功 / 失败 / 需重试三种状态。
- **token 静默过期**：定时任务跑了一周突然全挂，排查半天是 access token 过期。补了自动刷新和过期前告警。
- **描述人能看懂、agent 看不懂**："获取数据"这种模糊描述会被拿去查任何东西。改成"按工单 ID 查询详情，不用于列表查询"后，误用率明显下降。

## 可复用建议

1. 每个工具回答三个问题：干什么、什么时候用、什么时候不用；
2. 大响应一律在 server 层分页、过滤、截断，别指望 agent 自己省着用上下文；
3. 写操作默认 dry-run，显式确认才真执行；
4. 每次调用记日志：入参、耗时、状态码，出问题才能回溯；
5. 工具数量克制，宁可封装一个复合工具，也别堆一堆细粒度原语让 agent 自己拼。

## 总结

对接外部服务不是"接上就能用"，本质上是在为 agent 设计一个约束充分的操作面。工具描述、schema、超时、响应裁剪，这些细节决定了它是稳定可靠还是随机出错。先小范围暴露、跑通冒烟用例、逐步放开，是目前验证下来最稳的节奏。欢迎大家把自己对接时的 schema 写法和踩坑记录贴出来，互相抄作业。
