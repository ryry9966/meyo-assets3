## 背景

跑 Agent 自动化的人迟早会撞上这个场景：给 OpenClaw 挂了一个 cron 任务，每天早上拉取 issue 汇总发到群里。某天网关重启，调度器补跑了一次，群里出现两条一模一样的摘要。尴尬事小，暴露的缺口事大——**在重试和重启常态化的环境里，任务被重复执行不是异常，而是日常**。

重复执行的来源很多：HTTP 超时后的客户端重试、调度器重启后的补跑、webhook 的 at-least-once 投递、手动触发和定时触发撞车。你不能指望"它只会跑一次"，只能做到"它跑十次，结果和跑一次一样"。这就是幂等性。

## 问题

不幂等的任务重复执行时通常出三类事：

1. **副作用叠加**：重复发消息、重复建文件、重复调用付费 API；
2. **状态污染**：任务中途失败后重跑，处理了本不该再处理的数据；
3. **静默失败**：第二次执行因"已存在"报错退出，告警系统把它当新故障，噪声掩盖真问题。

## 做法

按投入产出比排序，四个层次：

**1. 优先选天然幂等的操作语义。** 用 upsert 代替 create，用 PUT 代替 POST，用"删除后重建"代替"追加"。同样的逻辑跑多少遍，终态一致。

**2. 给任务加幂等键（去重键）。** 每次触发生成一个稳定 ID——比如 `digest-2025-06-07` 而不是随机 UUID——执行前先查存储（SQLite / 文件 / Redis 都行），键存在就跳过：

```text
key = "digest-" + date
if store.has(key): return
store.put(key)   # 先落键
run_digest()     # 再执行
```

关键是**先写键、再执行**。成功后才写键的话，执行中途一崩溃，重跑时键还没落下。

**3. 执行前做状态检查。** "目标文件已存在且校验和一致就跳过""水位线之后没有新数据就不跑"，让任务变成：读状态 → 算差异 → 补齐差异。

**4. 写操作原子化。** 先写临时文件再 rename，避免重跑时撞上半成品状态。

## 踩坑点

- **check-then-act 竞态**：检查和执行不是原子的，两个触发几乎同时到达时都会通过检查。轻量解法是文件锁，或数据库唯一约束兜底。
- **去重状态放内存**：网关一重启，内存 Set 清零，等于没做。必须落盘。
- **多层重试叠加**：HTTP 客户端在重试，调度器也在重试。设计幂等键之前，先理清重试发生在哪一层。
- **混淆幂等与确定性**：基础设施幂等了，不代表 LLM 两次生成的摘要一字不差。幂等约束的是**副作用**（只发一条），不是输出内容。去重键要绑定触发源和时间窗，而不是绑定生成结果。

## 可复用建议

- 写任何 cron / webhook 任务时，默认假设它至少被执行两次，写完手动连跑一遍验证；
- 幂等键统一用 `{任务名}-{触发源}-{时间窗}` 格式，排查时一眼可读；
- 执行日志带上幂等键，重复触发一目了然；
- 调外部 API 时优先用对方提供的幂等参数/幂等头，没有就自己记录请求 ID。

## 总结

幂等性不是高级优化，而是自动化的入场券。调度器、网络、重启都在制造重复执行，你的任务唯一能做的，是让"多跑几次"和"跑一次"产生相同的结果。下次写自动化任务前先问自己一句：这个任务今晚如果跑三遍，明早我会收到几条消息？
