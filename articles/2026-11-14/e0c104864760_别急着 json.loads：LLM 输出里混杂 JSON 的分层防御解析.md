## 背景

在 OpenClaw 插件和自动化流水线里，LLM 的输出经常被当结构化数据直接消费——让模型返回 JSON，然后 `json.loads` 完事。开发时用几个规整样本测试没问题，一上真实任务就崩：模型可能在 JSON 前后加一句"以下是解析结果"，用 ```json 围栏包住，偶尔还夹杂全角引号或尾逗号。

## 问题

从真实失败样本里归纳，脏输出大致四类：

1. **围栏混合**：```json ... ``` 内外还裹着说明文字；
2. **语法瑕疵**：尾逗号、单引号、全角引号（“”）、中文冒号；
3. **结构异常**：一次返回多个 JSON 对象，或 JSONL；
4. **截断**：max_tokens 不足，JSON 只有前半截。

`json.loads` 对以上全部零容忍，下游任务跟着一起挂。

## 做法：分层解析，逐层降级

核心思路：不指望单一正则或单次尝试解决，写一条解析管线，每层只处理一类问题，失败就降级到下一层。

```python
import json, re

def robust_json_loads(text: str):
    # L0：直接解析
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        pass
    # L1：剥围栏
    m = re.search(r"```(?:json)?\s*(.+?)```", text, re.S)
    if m:
        try:
            return json.loads(m.group(1).strip())
        except json.JSONDecodeError:
            text = m.group(1)
    # L2：括号配对截取第一个完整对象
    frag = extract_balanced(text)      # 栈计数，跳过字符串字面量
    if frag:
        return repair_and_load(frag)   # 去尾逗号、全角转半角后再 loads
    raise JsonParseError(text[:200])
```

解析成功不等于完事：用 pydantic 按 schema 校验字段。解析层只负责"变成合法 JSON"，校验层负责"是不是我要的结构"，职责分开。

调用侧能控的，优先用结构化输出（JSON Schema / 工具调用参数）从源头约束，防御解析是兜底而非主路径。重试要有上限，可以把上一轮的解析错误喂回去让模型自修，两次不成就降级或告警。

## 踩坑点

- 贪婪正则 `\{.*\}` 遇嵌套对象或同屏多对象必出错，`.*?` 碰到字符串里的 `}` 也会断错，老实做括号计数。
- 全角字符修复要克制：只动引号、逗号、冒号这类结构性符号，粗暴替换可能破坏字符串内容。
- 先看 finish_reason 和输出长度再谈修复，截断的 JSON 修不出真数据。
- 无限重试会把偶发问题变成账单问题，设上限、留日志。

## 可复用建议

- 解析逻辑收口到一个模块，不要各插件各写各的。
- 每次线上解析失败，把原始输出截断落盘，攒成回归 fixtures——坏样本是最有价值的测试集。
- 格式敏感的任务把温度压低，0 和 0.7 是两个世界。
- 解析失败单独打点，能提前发现 prompt 改动引起的格式漂移。

## 总结

防御式解析不是纵容模型乱写，而是承认"输出有不确定性"这一工程现实：源头用结构化输出约束，中途用分层管线兜底，末端用 schema 校验收口，再靠失败样本反哺闭环。这套管线在我们多条自动化任务里复用后，解析失败率从百分之几降到千分之一以下，剩下的问题基本都出在 prompt 本身。
