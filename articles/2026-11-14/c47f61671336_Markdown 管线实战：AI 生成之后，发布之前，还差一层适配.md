## 背景

我们这批用 Agent 写技术稿的人，工作流大致相同：让模型产出 Markdown 初稿，人工校对，然后发到公众号、知乎、掘金和个人博客。前两步现在很顺，第三步最烦——同一份 Markdown，在每个平台渲染出来都不太一样。最初的解法是发布前手动修一遍，重复劳动且容易漏，后来我把这一步固化成了管线。

## 问题

Markdown 看似统一，实际各平台只实现了各自认可的方言：

- 公众号编辑器会剥掉大部分 HTML 和 class，样式必须内联；
- 知乎不支持脚注和任务列表，表格列宽靠猜；
- AI 很爱用 `[^1]` 脚注、`==高亮==`、mermaid 图块，这些在目标平台基本全军覆没；
- 图片外链有防盗链，粘过去就裂。

## 做法

核心思路：把 AI 输出当“源码”，平台当编译目标，中间做一次 AST 级适配，而不是字符串替换。

1. **归一化**：统一换行符、去掉 frontmatter、压平标题层级（公众号里 h5 以下基本没法看）。用 remark 的 mdast 遍历，不用正则。
2. **语法降级**：写一组 AST transform——脚注转文内括号注，`==xx==` 转加粗或删除，mermaid 在构建期预渲染成 SVG 再作为图片插入。每个 transform 是独立函数，带 fixture 测试。
3. **平台适配器**：公众号走“MD → HTML + 内联 CSS”（用 juice 这类工具把样式压进标签）；知乎、掘金走“MD → 标准 MD”，只删不改写；博客是 MDX，可保留更多能力。适配器必须幂等，同一输入跑两遍结果一致，否则调试会疯。
4. **图片落地**：管线里加一步，下载所有外链图，统一传到目标平台素材库或自己的 OSS 再替换 URL。公众号必须走它的素材接口，这是硬约束。
5. **校验**：headless 浏览器渲染目标 HTML，截图与上一版做 diff，大面积空白或样式丢失就报警。这一步救过我不止一次。

整套流程在 OpenClaw 里挂成一个 skill 加定时任务：丢一份 canonical markdown 进去，产出 N 份平台产物和一张发布清单。

## 踩坑点

- **别用正则改 Markdown**。嵌套列表、代码块里的假语法会把正则方案打穿，AST 是底线。
- **AI 的缩进不稳定**。同一个会话里列表缩进有时 2 空格有时 4 空格，不同解析器容忍度不同，先 lint 再转换。
- **源头约束比下游兜底便宜**。在给模型的指令里明确“只用 h2-h4、不用脚注/mermaid/高亮语法”，能把 80% 的适配工作消灭在生成阶段。
- **公众号的剪贴板粘贴比导入接口宽容，但不可复现**。要走接口，别依赖手工粘贴。
- **内联 CSS 有标签白名单限制**，复杂样式直接被吞，样式表保持极简。

## 可复用建议

- **单一事实源**：只维护一份 canonical markdown，平台产物全部生成，永远不手改产物。
- **每个 transform 配 fixture**：输入输出落盘成测试用例，升级依赖时跑一遍就知道什么变了。
- **留 manifest**：源稿 hash 到各平台 URL 的映射存档，回溯和更新重发都靠它。

## 总结

这条管线没有黑科技，就是“生成端约束 + AST 适配 + 目标端校验”三段式。AI 把写稿成本压到接近零之后，发布侧的格式适配成了新的瓶颈——值得花一个下午把它工程化。产物稳定之后，你才敢真正让 agent 全自动发稿。
