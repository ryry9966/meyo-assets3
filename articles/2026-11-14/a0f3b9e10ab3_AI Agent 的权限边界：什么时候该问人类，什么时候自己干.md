## 背景

接上 MCP 和插件之后，Agent 的能力从“能说”变成了“能动”：写文件、调 API、发消息、跑 shell。于是新问题来了：哪些动作它可以自己干，哪些必须停下来问人。在 OpenClaw 这类常驻运行的 Agent 网关里，这个问题尤其突出——它不是一次性会话，出错时往往没人盯着。

## 问题：两种失败模式

实践中最常见的两个极端：

1. **凡事都问**。每步都要确认，人很快退化成“批准机器”，闭眼点同意，审批形同虚设。
2. **一律自己干**。删文件、给真实用户发消息、跑生产脚本，全靠模型自觉，出事时已不可逆。

本质是：我们习惯按“工具是否危险”想问题，但真正该评估的是**单次动作的后果**，而不是工具名。

## 做法：按风险分四档

给每个动作打两个维度：**可逆性**（错了能不能撤回）、**爆炸半径**（波及多少数据/用户/钱）。

- **T0 只读无副作用**（查状态、搜索）：默认自动执行，留日志。
- **T1 本环境内可逆**（写草稿、改工作区文件、调测试 API）：自动执行 + 审计日志 + 可回滚。
- **T2 触达外部世界**（给真人发消息、调付费 API）：执行前确认，且确认必须带预览——给 diff、目标地址、参数，而不是一句“我要调 send_message”。
- **T3 不可逆或安全敏感**（删数据、转账、改权限）：永远人工确认；必要时干脆不给 Agent 这个工具。

落地步骤：

1. **盘点工具**：把所有 MCP server、插件、内置工具列全，别漏 shell 和文件系统这种隐含全能的能力。
2. **按参数定档，不按工具定档**：同一个发消息工具，发测试频道是 T2，发客户列表就是 T3。
3. **规则写进配置层**：权限放在工具/网关层，别指望 prompt 里一句“请谨慎”。
4. **确认带上下文**：批量操作要么确认整个计划，要么逐条确认，不允许一个 yes 放过五十个子动作。
5. **留日志、定期复盘**：每周过一遍自动执行记录，出过问题的升档，长期稳定的降档。

## 踩坑点

- **审批疲劳**：确认点太多等于没有确认。宁可少问，也要保证每次问都值得看。
- **权限配置可被 Agent 修改**：把权限文件放进它的可写范围等于没设。配置放在 Agent 够不到的地方，改配置本身设为 T3。
- **自动执行等于无人观察**：T0/T1 不问人，但要有告警——大量重试、越界路径、异常时段要能主动通知到你。
- **批准与执行之间有时间差**：环境可能已变。高危动作建议用 dry-run：Agent 生成完整命令，人一键执行，而不是批准后 Agent 再跑一遍。

## 可复用建议

- 一句话默认策略：**只读默认放行，不可逆默认拦下**。
- 新接的 MCP 工具，接入当天定档；没定档的一律按 T2 对待。
- 审计日志是唯一的反馈回路，没有日志的自动执行就是盲飞。
- 档位标准写成团队文档，让“这个要不要确认”变成查表而不是争论。

## 总结

权限边界不是提示词问题，是系统设计问题。目标不是让 Agent 问得多或少，而是**在对的时间点、带着足够的信息去问**。判断标准始终是两条：错了能不能挽回，错了波及多大。想清楚这两条，剩下的交给分级配置和日志复盘。
