## 背景

常驻 agent 有个绕不开的问题：不能一直醒着烧 token，也不能睡得太死错过事情。目前最常见的两种唤醒机制：一是 heartbeat 定时轮询——按间隔醒来检查 `HEARTBEAT.md`，没事就静默返回；二是推送——插件收到 webhook 等事件后直接注入一条消息，立刻触发一轮运行。两种我都在自己的 OpenClaw 实例上跑过一段时间，谈谈取舍。

## 问题

轮询的痛点：延迟上限等于间隔，30 分钟的 heartbeat 意味着事件最多迟到 30 分钟；空转比例高，大多数唤醒一无所获，但上下文加载和 token 照付。推送的痛点：agent 侧必须能被"叫醒"，意味着要有可入站的 endpoint——公网暴露、鉴权、内网穿透都随之而来；而且推送有可靠性问题，gateway 掉线、重试、去重，事件丢了没人知道。

## 我的做法：混合，推送管时效，heartbeat 兜底

1. **保留低频 heartbeat**。间隔从 30 分钟放宽到 60 分钟，`HEARTBEAT.md` 写成"默认静默：只在发现确需处理的事项时输出"，并限定 active hours。一次空转的成本压到几百 token。
2. **高时效事件走推送**。插件收到 webhook 后给 agent 发一条带 source、event id、时间戳的消息。endpoint 不裸奔：共享密钥签名校验，验不过直接 4xx。
3. **幂等**。推送侧带唯一 id，agent 收到后先查已处理列表；heartbeat 兜底时同样按 id 对账，防止重试 + 兜底造成双跑。
4. **heartbeat 兼任 watchdog**。每轮顺手核对推送水位，发现积压就在心跳里补跑。这样推送链路挂了，最坏损失是一个心跳间隔。

## 踩坑点

- 心跳初期设了 5 分钟，一晚上烧的 token 比白天还多；且每次唤醒都加载完整上下文，单次成本远超预期。心跳 prompt 精简是第一原则。
- 有段时间 heartbeat 每轮都"汇报点东西"，通知轰炸。改成"默认什么都不做"之后才恢复正常。
- webhook endpoint 早期没验签，日志里出现过来路不明的注入尝试。任何能触发 agent 的入口都要当鉴权面看待。
- 推送重试 + 心跳兜底导致同一任务跑了两遍——没有幂等键之前，这种事迟早发生。
- 笔记本休眠、容器重启会让进程内定时器漂移；对时序敏感的场景，用系统 cron 触发比依赖进程内 timer 稳。

## 可复用建议

- **决策一句话**：延迟敏感 → 推送；延迟不敏感 → 只用低频 heartbeat；不确定 → 混合，heartbeat 当对账器。
- **观测三个指标**：唤醒次数、空转率（无输出唤醒占比）、每次唤醒 token；推送链路另看重试成功率。
- **消息带 source + id + 时间戳**，幂等和排障都靠这三个字段。

## 总结

轮询和推送不是二选一。轮询便宜、简单、可靠但慢；推送快，但要为可达性和安全付账。实践里最稳的形态是：推送负责"立刻知道"，heartbeat 负责"最终一定知道"。两条腿走路，agent 才既不烧钱、也不误事。
