## 背景

跑自动化任务和写一次性脚本最大的区别：**重复执行是常态，不是异常**。定时任务被重复拉起、网络超时后的重试、agent 自我纠错时反复调用同一个工具、用户手动"再跑一次"——这些场景里，同一段逻辑被执行两三遍是日常。

所以评价一个自动化任务稳不稳，关键不是"跑一次对不对"，而是"跑十次结果还对不对"。这就是幂等性：同一操作执行一次和执行多次，最终状态一致。

## 问题

副作用累积的典型症状：

- 通知类任务重试后，群里连发三条相同消息
- 同步任务重复运行，目标系统出现重复工单/记录
- agent 重规划后对同一目标调用两次"创建"工具，产生两份资源
- 更隐蔽的一种：本地以为失败了，远端其实已执行成功（响应丢失），盲目重试造成双倍执行

非幂等操作（追加写入、无键创建、直接发送）在单次测试中完全正常，上了生产才暴露，且往往难以回滚。

## 做法

我们的实践按四步走：

1. **定义幂等键。** 每个写操作明确一个业务唯一键，比如 `任务ID + 目标资源ID + 内容hash`，不要用时间戳或随机数。键必须稳定：同一意图两次调用，键要相同。
2. **先查后写。** 工具内部先查询目标状态（是否已存在、是否已发送），存在就跳过并返回"already done"。把判断做在 MCP 工具内部，agent 层无感。
3. **原子兜底。** 应用层判断挡不住并发。把幂等键落到数据库唯一索引或 upsert，重复插入直接失败；没有数据库的场景用文件锁或原子 create（如 `open(..., 'x')`）。
4. **对账机制。** 对"成功但响应丢失"的场景，重试前先调远端查询接口确认，而不是盲目重发。维护一张执行流水表（run ledger），定期对账。

## 踩坑点

- **用全参数 hash 去重**：agent 重试时可能带上了新的时间戳参数，hash 变了，去重失效。要用语义键，把易变参数排除在键之外。
- **去重窗口太短**：五分钟窗口挡不住"一小时后手动重跑"。要么窗口够长，要么状态持久化。
- **只防重试，不防并发**：两个 worker 同时通过"检查不存在"，然后都执行。唯一约束是最后防线。
- **把幂等当事务**：幂等只保证"多次执行结果一致"，不保证"部分失败可回滚"。跨多个外部系统的操作要单独设计补偿步骤。
- **天然不可逆的操作**（发消息、删除）：至少做两阶段——先写"待执行"标记，成功后更新状态，进程重启后能从标记恢复。

## 可复用建议

- 团队内统一约定：所有写类 MCP 工具接受可选的 `idempotency_key` 参数，不传则内部生成稳定键
- 优先用外部 API 自带的幂等机制（支付、云服务的幂等头），别重复造轮子
- 读操作随便重试，写操作必须过幂等层——把这条写进插件的 review 清单
- dry-run 作为标配：先打印将执行的动作，确认后再落副作用

## 总结

幂等不是高级技巧，而是自动化能长期无人值守运行的前提。核心就三句话：**写操作要有稳定幂等键、判断逻辑落在原子层、不可逆操作加确认与对账**。把重复执行当作设计输入而不是异常处理，任务的可靠性会上一个台阶。
