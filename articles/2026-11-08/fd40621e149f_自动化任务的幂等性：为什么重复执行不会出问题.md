## 背景

在 OpenClaw 里做自动化，迟早会遇到"重复执行"：cron 任务在 gateway 重启后被补跑，agent 的工具调用超时后自动重试，用户在频道里手动多触发一次，插件收到重复的 webhook。写脚本时我们默认"只跑一次"，但调度和重试机制的真实承诺通常是"至少跑一次"，而不是"恰好一次"。

## 问题：哪些操作怕重复

幂等性的定义很简单：同一个任务执行一次和执行 N 次，最终状态一样。按这个标准把动作分三类：

- **天然安全**：读文件、查询接口、计算返回结果，重复执行无害；
- **天然幂等**：整文件覆写、设置键值、按条件更新，重复执行结果不变；
- **不幂等**：追加写文件、创建日历事件、发消息、调下单类接口，每执行一次，副作用就多一份。

自动化事故大多出在第三类。一个每天汇总资讯发到频道的 cron 任务，gateway 重启后补跑，用户收到两份重复推送；一个"发现新文件就登记"的插件，重试时不清查状态，登记表里出现重复条目。

## 做法：四个步骤

1. **给每次"逻辑执行"一个稳定的幂等键**。键来自任务本身，而不是运行时随机数：cron 任务用"任务名 + 调度时间点"，事件驱动任务用"事件来源 ID"。注意用调度时刻而不是实际执行时刻，否则补跑会生成不同的键，等于没做。
2. **执行前先查状态**。把已处理的键记在持久化位置——本地 JSON 文件或 SQLite 都够用。流程：生成键 → 查重 → 已存在则直接退出 → 不存在则执行 → 写入键和结果。
3. **把创建类操作改成"确保存在"语义**。写文件用整文件覆写而非追加；调第三方 API 时优先使用它提供的幂等键或客户端去重参数；发消息时带上与幂等键关联的标记，发送前先确认是否已发过。
4. **超时后先确认再补做**。工具调用超时意味着"结果未知"，不代表失败。正确动作是先查询目标状态（事件建了没有、消息发了没有），确认没成功才重做。

## 踩坑点

- **先执行后记录**。如果执行成功但在写记录前崩溃，下次照样重复。更稳的是两阶段：先写 pending，执行完改成 done，恢复时对 pending 状态先查询确认。
- **幂等键不稳定**。用 `Date.now()` 到毫秒或随机 UUID，同一逻辑任务两次运行键不同，去重形同虚设。
- **追加类操作漏网**。日志、配置文件追加行，重复跑一遍内容翻倍，应改成"读—改—全量写"。
- **把幂等当挡箭牌**。查重退出和执行成功是两回事，done 记录里要区分成功与失败，失败要留给告警，不能静默吞掉。

## 可复用建议

- 把"生成键 → 查重 → 执行 → 记录"封装成所有自动化共用的一层 wrapper 或小脚本，新任务直接套用，不要每次手写。
- 对现有自动化做一次审计：列出所有带副作用的动作，逐个标注是否幂等，不幂等的补上键。
- 最简单的验证方式：同一任务连续手动跑三遍，检查第三遍之后的状态和第一遍是否完全一致。

## 总结

分布式系统里"恰好一次"几乎做不到，可靠的做法是把任务设计成"重复执行也安全"。写每个自动化任务时，默认它会被补跑、被重试、被手动多触发一次——按这个假设设计，定时任务才敢放心挂上去。
