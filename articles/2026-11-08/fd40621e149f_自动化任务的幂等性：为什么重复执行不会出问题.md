## 背景

写自动化脚本或给 Agent 挂定时任务时，很多人默认"任务只会跑一次"。现实是：cron 可能因为部署重启触发两次，Agent 遇到超时会自动重试，MCP 工具调用失败后上层框架可能重新投递，用户也会"没反应就再点一下"。重复触发不是异常，而是自动化系统的常态。

## 问题

幂等性指的是：同一个操作执行一次和执行多次，最终结果一致。常见的非幂等写法：

- "追加一条评论/记录"——重跑一次就多一条；
- "把计数器 +1"——重跑就多加；
- "先查有没有，没有就创建"——查和创建之间有间隙，重试或并发时会创建两份。

一次重复触发，轻则产生脏数据，重则给外部系统发了两遍消息、给用户发了两封邮件。这类问题在测试环境往往发现不了，因为测试时很少模拟重试。

## 做法

给自动化任务加幂等性，工程上就三件事：

**1. 给每次业务事件一个稳定的 key。** 来源事件自带 ID（消息 ID、webhook 的 event id、文件内容 hash）就直接用；没有就由触发参数派生一个。注意：每次执行时随机生成的 key 无法去重，等于没做。

**2. 执行前先落盘"处理标记"。** 在真正干活之前，先把 key 写进可靠的地方：SQLite 的唯一索引、一张 processed_keys 表、甚至状态目录下的一个哨兵文件。用 `INSERT ... UNIQUE` 这类原子操作抢占，插入成功才继续执行，冲突则直接跳过。不要"先查再写"两步走——那个间隙正是重复的来源。

**3. 把操作改写成"设成某状态"，而不是"追加/递增"。** "把配置里 enabled 改为 true"天然幂等；"往文件末尾 append 一行"不是。能用覆盖写就不用追加写，能按主键 upsert 就不做裸 insert。

以一个 OpenClaw 定时插件为例：任务入口先 `INSERT INTO seen_events(event_id) VALUES(?)`，冲突即 return；通过后再执行抓取和推送。这样无论 cron 重复触发、Agent 重试多少次，下游只收到一次。

## 踩坑点

- **标记与执行不原子。** 先执行后记标记，一旦执行成功但标记没落盘就崩了，下次照样重跑。正确顺序：先抢占标记（失败即退出）→ 执行 → 失败时回滚标记或标为 failed。
- **标记放在内存里。** 进程一重启就丢，等于没做。去重状态必须落磁盘或数据库。
- **部分成功后盲目重跑。** 任务分三步（抓取、转换、推送），第二步失败后重跑，第一步已经完成。要么每一步独立幂等，要么记录步进状态从断点续跑。涉及外部系统时"全做或全不做"很难，分段幂等更现实。
- **LLM 输出不确定 ≠ 操作不幂等。** 两次调用模型生成的文案可能不同，但只要最终落的是"以事件 ID 为 key 的一次写入"，操作依然是幂等的。别把"结果会变"当成"没法幂等"的借口。

## 可复用建议

接手或评审一个自动化任务时，过一遍这五条：

1. 这个任务被连续触发两次，会产生哪些副作用？逐条列出来。
2. 每个副作用有没有天然的 key 可用于去重？
3. 去重标记存在哪？进程重启后还在吗？
4. 标记写入和实际执行之间，是不是原子抢占？
5. 中途失败重跑，是从头还是从断点？已完成步骤会重复副作用吗？

## 总结

幂等不是锦上添花的高级特性，而是自动化任务敢重试、敢重调度的前提。实现成本很低：一个稳定的 key、一次原子的标记写入、尽量用"设状态"代替"追加"。把它做在前面，你的定时任务、Agent 重试和插件调用才经得起真实环境的反复触发。
