## 背景

社区有几个固定栏目，每周要从素材源里挑内容、排版、发帖，纯重复劳动。我试着用 OpenClaw 的 Agent 加一组 MCP 工具，把「采集素材 → 生成草稿 → 审核 → 定时发布」整条链路自动化。断断续续跑了一个多月，架构推倒重来了三版，这篇把最终设计和踩过的坑都记下来。

## 目标与约束

动手前先明确了边界：

- 每天最多发 2 帖，宁缺毋滥；
- 所有内容发布前必须过一道独立校验（敏感词、外链、格式）；
- 失败可重试、可追溯，Agent 不能有“随时能发”的权限；
- 全程支持 dry-run 开关。

## 架构：四层流水线

最终定型的是四层结构：

1. **采集层**：cron 定时拉取素材源（论坛热帖、RSS、仓库更新），清洗后写入待办表；
2. **生成层**：Agent 读取素材，调用 MCP 工具（查历史帖、查版规、格式化），产出结构化草稿 JSON；
3. **审核层**：独立服务做规则校验 + 相似度去重，拿不准的进人工队列；
4. **发布层**：队列消费，带幂等键调发帖接口，成功后写回执。

关键取舍只有一个：**Agent 只负责“写”，不负责“发”**。发布权限收敛到发布层的单一工具里，Agent 侧根本看不到写操作。

## 实施步骤

1. 先把发帖动作封装成 MCP tool，入参强制走 schema 校验；
2. 生成层 prompt 只给 3~5 篇历史精选帖做风格参考，不给全量；
3. 每篇草稿生成 content_hash 作为幂等键，贯穿审核和发布；
4. 发布层用队列 + 指数退避，连续失败进死信并告警；
5. 上线前用测试账号 dry-run 一周，人工 diff 每一条输出。

## 踩坑实录

**坑一：幻觉重发。** 早期把发帖工具直接挂给 Agent，某天它把同一内容发了两遍，理由是“确保送达”。修复方式：Agent 侧不提供任何写操作，发布只走队列，幂等键冲突直接丢弃并记录。

**坑二：上下文膨胀。** 一开始把最近 50 帖全塞进 prompt，token 翻倍，风格反而学杂了。改成检索 3 篇最相关样本后，输出稳定性明显提升。

**坑三：重试风暴。** 发布接口一次超时，cron 和队列同时重试，短时间打出十几个请求。加了指数退避 + 单飞锁（同一幂等键同时只允许一个在途请求）才稳住。

**坑四：格式静默失败。** 草稿里的代码块在社区渲染时被吞，模型自己完全看不出来。解法是 dry-run 账号每周抽检渲染结果，把格式规则固化进审核层，而不是指望 prompt 里一句“注意格式”。

**坑五：日志缺中间产物。** 最初只记成功/失败，排障时完全不知道 Agent 当时看到了什么。现在采集原始数据、草稿、审核结论、回执全落盘，一条帖子的完整链路可以回放。

## 可复用建议

- **最小权限**：Agent 只给读工具，写操作独立成服务；
- **幂等键贯穿全链路**，比事后去重便宜得多；
- **“合规”不要写在 prompt 里祈祷**，做成独立的审核阶段；
- **先 dry-run 再放量**，把社区当生产环境对待；
- **中间产物落盘**，日志要能回放。

## 总结

这套东西技术上并不复杂，难的是把“模型一定会犯错”当成默认前提来设计架构。收权、幂等、审核前置、可回放，四个原则撑住了整个系统。目前稳定运行，人工只处理审核队列里约 10% 的边缘情况，每周省下两三个小时重复劳动。下一步计划把采集层也统一迁到 MCP 接入，继续减少胶水代码。欢迎在评论区交流你们的自动化实践。
