## 背景

社区需要一个机器人，每天自动整理优质话题并发一篇带观点的帖子到论坛。听起来像“调个 API 就完事”，实际跑起来发现，难点根本不在生成内容，而在发布的可靠性。这篇记录用 OpenClaw 搭建发帖机器人的架构取舍和踩过的坑。

## 问题

核心需求很朴素：

- 定时从若干来源（RSS、站内热帖）收集候选话题；
- 由 Agent 生成草稿，自动发布到论坛，失败可重试；
- 不能刷屏、不能重发、内容不能离谱。

关键矛盾在于：**发帖是不可逆动作**。重试、限流、会话过期、并发冲突，任何一环出问题都会变成“事故现场”。

## 做法与架构

整体分三层，刻意保持简单：

1. **触发层**：cron 每天定时触发，外加一把文件锁防止任务重叠（cron 漂移 + 长任务很容易撞车）。
2. **Agent 层**：OpenClaw Agent 负责编排，能力通过 MCP 工具接入。工具按最小粒度拆：`fetch_sources`、`save_draft`、`publish_post`、`get_post_status`，而不是一个大而全的 `post_to_forum`。
3. **状态层**：SQLite 一张表管所有发布记录，字段含 `idempotency_key`、`post_id`、`status`、`retry_count`。

流程五步：收集 → 过滤去重 → 生成草稿 → 校验（dry-run 下到此为止）→ 发布并落库。

几个关键设计：

- **发布幂等**：`idempotency_key = hash(日期 + 来源链接)`，发布前先查库，论坛侧同时校验重复标题。这条是整个系统的安全带。
- **dry-run 常开**：前两周只生成不发，草稿全部进库人工过目，确认稳定后才打开发布开关。
- **生成与发布解耦**：Agent 写完草稿就结束，由独立的发布 worker 消费队列。这样 LLM 超时或重试不会直接冲击论坛 API。
- **限流冷却**：每天硬上限 2 帖，发布间隔至少 6 小时，超限直接丢弃并记日志，宁缺毋滥。

## 踩坑实录

1. **重复发帖**。第一版在论坛 API 超时后直接重试，同一篇发了三次——超时那次其实已经成功。修复：先 `get_post_status` 再决定是否重试，所有重试必须携带幂等键。
2. **会话过期**。论坛 token 有效期 7 天，失效后机器人静默失败了一周没人发现。修复：token 刷新收进 MCP 工具内部，刷新失败主动发告警消息，而不是只写日志。
3. **并发撞车**。手动触发和定时触发同时跑，两个进程选中了同一候选话题。文件锁解决，锁文件里写入 PID 和启动时间，方便排查残留锁。
4. **内容质量漂移**。模型偶尔把营销腔总结当“观点”发出来，被社区成员点名。修复：prompt 中加负面示例 + 发布前规则校验（长度、禁用词、必须含来源链接），不达标打回重生成，最多两次。
5. **MCP 工具粒度**。最初设计了一个万能工具，Agent 传参经常对不上。拆细之后每次调用参数少而明确，出错率明显下降。

## 可复用建议

- 一切不可逆动作（发帖、发消息）都要有幂等键，先查后写。
- 新机器人先 dry-run 一到两周，把人工审核当默认环节而非可选项。
- 观测优先于功能：每次 LLM 调用、每次工具调用都留痕，翻日志比猜快得多。
- 工具按最小粒度拆，别给 Agent 太大自由度。
- 留一个机器人无法绕过的物理 Kill Switch（环境变量或开关文件）。

## 总结

代码不到三百行，真正的工作量全在边界条件：重试、并发、会话、质量校验。一句话经验：把 Agent 当成会犯错的初级同事来设计系统——给它清晰的工具、有限的权限、必须走的流程，而不是默认它输出可信。跑通后目前每天稳定发一帖，人工只做抽查，维护成本可控。
