## 背景

社区运营里最耗时间的往往不是写内容，而是"定时、定格式、不重复"地把内容发出来。我们维护的周更栏目，之前靠人肉排版加手动发帖，平均每周耗掉三四个小时。于是花了一个周末，用 Agent + MCP 的思路搭了个发帖机器人，跑了一个多月，这里记录架构和踩过的坑。

## 问题定义

目标很克制：不做全自动内容工厂，只做"草稿生成 → 审核 → 定时发布"这条链路的自动化。硬性要求四条：

1. 每周固定时间发帖，失败可重试；
2. 不重复发相似内容；
3. 语气与社区既有帖子一致；
4. 全程留痕，出问题能回溯到哪一步生成。

## 架构与做法

整体拆成三层：

- **调度层**：cron 触发，往 SQLite 落一条带幂等键的任务记录；
- **Agent 层**：OpenClaw Agent 拉取本周素材（issues、精华帖、群聊摘录）生成草稿；再起一个独立的 reviewer agent 按检查单审稿，不通过就打回重写，最多两轮；
- **执行层**：通过自写的 MCP server 调社区发帖 API，工具内内置限流、重试和幂等校验。

两个关键决策：

1. **生成与审核分离**。同一个 agent 自审基本是走过场，通过率 100%。拆成两个会话后，reviewer 按"事实核对 + 链接存在性 + 语气三项"检查单执行，能真正拦住问题稿。审稿用小模型就够，不必上主力模型。
2. **所有外部动作收口到 MCP**。发帖、查重、拉历史帖都封装成工具，Agent 不允许直接访问网络，限流、鉴权、日志就都在一处。

查重用标题加首段的 embedding 相似度，阈值 0.85 以上直接打回。

## 踩坑实录

1. **cron 重叠导致重复发帖**。上线第一天就翻车：任务跑了 90 秒，下一轮 cron 又触发一次，同内容发了两帖。修复：任务表加唯一幂等键，发帖工具先查"本周是否已有 post_id"，没有才执行。
2. **模型编造引用**。草稿里出现过指向不存在的 issue 编号。修复：规定 Agent 只能引用素材工具返回的内容，reviewer 逐条核对链接，核对不过就删。
3. **语气漂移**。跑了几周后帖子越来越像产品通稿。修复：system prompt 固化，塞 5 篇真实社区帖做 few-shot，temperature 降到 0.4，基本稳定。
4. **上下文膨胀**。起初把近三个月帖子全塞进上下文，token 费用翻倍还经常截断。改成只检索 top-5 相关帖，问题消失。

## 可复用建议

- 先做半自动：前四周草稿都人工确认后再发，跑稳了再放开；
- 幂等键加唯一约束，比任何"小心一点"都可靠；
- 每次调用把 prompt、响应、工具参数全量落日志，排查问题时这就是救命稻草；
- 检查单要具体（"链接必须来自素材工具返回"），别写"内容要准确"这种空话。

## 总结

这套东西没有用到复杂技术，价值在于把发帖链路拆成了可观测、可回滚的三层。一个多月跑了 7 期，人工介入从每期 3 小时降到 20 分钟。如果你也在维护社区栏目，建议从"一个 MCP 工具 + 一份检查单"起步，别一上来就追求全自动。
