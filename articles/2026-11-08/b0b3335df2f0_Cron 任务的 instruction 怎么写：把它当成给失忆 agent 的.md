## 背景

OpenClaw 的 cron 任务，本质上是：到点唤醒一个 agent，把你的 instruction 当作当轮输入独立执行，跑完即结束。它不是一行"配置"，而是一段会被真正执行的提示词。很多人写 cron instruction 时用的是聊天语气——"帮我看看今天的邮件"——在会话里这样说是可以的，因为有上下文兜底；交给定时任务，就是在掷骰子。

## 问题

典型的翻车方式有三种：

1. **依赖上下文**。"继续昨天那件事"——agent 每次醒来都是全新会话，它不知道"昨天"指什么。
2. **时间含糊**。"整理今天的日程"——它不知道现在几点、时区是哪个、"今天"从哪一秒算起。
3. **输出没有约束**。任务每天固定发一条"今天没有新动态"，一周后你把通知渠道静音，这个任务等于白跑。

## 做法

我把一条能稳定跑的 cron instruction 拆成六段，按顺序写：

1. **触发语境**：开门见山写清频率和时区，例如"这是一个每天 09:00（Asia/Shanghai）触发的定时任务"。这句话帮 agent 校准所有关于"今天"的判断。
2. **数据来源**：写全工具名、参数、路径。不要写"查一下邮件"，要写"读取收件箱，过滤过去 24 小时的未读邮件"。
3. **处理逻辑**：一步一个动作，编号排列。cron 场景没有追问的机会，歧义只能靠 agent 猜，而猜错没人纠正。
4. **输出渠道**：发给谁、什么格式、什么阈值才发。例如"高优先级事项达到 3 条以上才汇总发送，否则不发言"。
5. **异常分支**：数据为空怎么办、工具调用失败怎么办。明确写出"失败时发一条包含错误摘要的短消息"——否则 agent 很可能编一份看起来像样的总结交差。
6. **静默规则**：默认安静。"没有值得汇报的事情就直接结束，不要输出任何消息。"

另一个关键技巧是**状态落盘**：让任务把上次的结果写到一个固定路径的文件，下次运行先读它、只报增量。没有这一步，每日任务很容易反复汇报同一批内容。

## 踩坑点

- **用聊天语气写任务**。"帮我看下""随便整理下"这类措辞交给定时执行，结果不可复现。
- **忘了时区**。运行环境常跑在 UTC，"每天 9 点"可能实际是下午 5 点，第一次上线就要核对。
- **一个任务塞一整套流程**。长流程容易超时或中途失败，且失败后无从续跑。拆成多个任务，用状态文件衔接。
- **在 instruction 里硬编码密钥**。任务文本会被存储、被日志引用，敏感信息应走环境变量或凭证配置。
- **不手动跑就排期**。先手动触发一次验证输出，再交给调度器。

## 可复用建议

- 把 cron instruction 当代码维护：改一段、跑一次、看一次输出，不要一次改三处。
- 写完自检一个问题：**一个失忆的同事凌晨被叫醒，只看这段话，能不能不动声色地把事办对？** 答案是否定的，就回去补上下文。
- 固化自己的六段模板：触发语境 → 数据来源 → 处理逻辑 → 输出渠道 → 异常分支 → 静默规则。模板写满，八成的坑已经绕开。

## 总结

Cron instruction 的读者不是此刻的你，而是未来那个毫无上下文的 agent。写得越像"交接文档"而不是"聊天记录"，任务就越稳。自包含、时区明确、有失败出口、默认安静——这四件事是回报率最高的投入。
