## 背景

日常开发里有三类 Git 操作是纯机械劳动：写符合 Conventional Commits 的提交信息、按规范建分支、清理已合并分支。这些活儿规则明确、上下文就在仓库里，正好是 AI 助手（Agent + MCP 工具）擅长接管的区间。我们在社区内部项目里跑了一段时间"助手管提交"，把做法和坑整理出来。

## 问题：自动化边界在哪

目标不是让助手全权操作 Git，而是圈定在"低风险、高重复"。真正容易出事的是四类动作：误提交敏感文件、`git add -A` 把构建产物带进去、对主分支 force push、人机同时操作同一仓库产生冲突。所以设计原则只有一条：**助手只做可逆操作，不可逆操作必须有人确认。**

## 做法：三步搭起来

**1. 受限工具通道。** 不直接给 shell，而是通过 MCP 接一个 Git 工具服务，白名单只放行 `status` / `diff` / `add 指定路径` / `commit` / `branch` / `switch` / `log`。push 单独封装成脚本，校验目标分支和远端，主分支直接拒绝。权限层挡住的东西，不会因为模型一次走神而失效。

**2. 规则写进 AGENTS.md。** 要求助手提交前必须先跑 `git status` 和 `git diff --cached`，把改动自己复述一遍；提交信息按 Conventional Commits 生成，一行主题加正文说明动机；测试不过不提交。实测下来，"先复述 diff 再写 message"这一条对提交质量提升最明显。

**3. 分支自动化。** 建分支固定用 `feat|fix|chore/<任务号>-<短描述>`；助手只允许在对应 feature 分支上操作；已合并分支由助手列出清单、人确认后批量删除，不做自动清理。

## 踩坑点

- **密钥泄漏**：助手会把工作区里的 `.env`、调试脚本一起 add。靠 pre-commit 的 secret 扫描兜底，比指望模型自律靠谱。
- **`git add -A` 是重灾区**：改成只允许 add 明确列出的路径，并定期复查 .gitignore。
- **交互式命令卡死**：`rebase -i`、需要输入的 merge 在非交互环境下会挂起，工具层一律禁用。
- **并发冲突**：人和助手同时操作时，助手可能基于过期状态提交。后来约定助手开工前必须先 fetch + status，review 期间人不要同时改代码。
- **提交信息幻觉**：早期版本会编造"修复了 XX 问题"，强制引用 diff 摘要后才收敛。

## 可复用建议

1. **权限白名单 > prompt 约束**：能用工具层挡的，就不要靠模型自觉。
2. **留审计日志**：所有助手触发的 Git 动作记日志，出问题能回放。
3. **爆炸半径要小**：助手只在 feature 分支干活，主分支只接受人工 push。
4. **规则跟着仓库走**：约束沉淀在仓库内的 AGENTS.md，进版本管理，新人和新助手都能直接继承。

## 总结

Git 自动化这件事，AI 助手的价值在于"重复动作零成本执行"，而不是"替你做决定"。把不可逆操作卡在人手里，把机械劳动交给助手，这套配比在我们的日常里是稳定可用的。下一步打算把 release note 生成挂到同一条链路上，欢迎在评论区交流你们的护栏方案。
