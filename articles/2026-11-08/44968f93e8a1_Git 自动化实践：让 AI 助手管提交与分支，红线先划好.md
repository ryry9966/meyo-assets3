## 背景

自从把 OpenClaw 接上 MCP 的 git 工具后，我把日常最琐碎的两件事交给了 Agent：写 commit message、清理分支。跑了一个多月，有收益也有教训，这篇把配置思路和踩过的坑整理出来，供同样想试的朋友参考。

## 问题

手工维护仓库的痛点很具体：

- commit message 质量不稳定，"fix bug" 式提交占了一半；
- feature 分支合完就忘，本地堆了十几个 stale branch；
- 回顾改动时，想不起某次提交到底改了什么。

但直接给 Agent 一个 shell 让它跑 `git` 命令，风险更大：误操作 force push、把 token 提交进仓库、在 main 上直接 rebase，任何一件都够喝一壶。

## 做法

核心原则一句话：**不把裸 shell 交给 Agent，只暴露白名单化的细粒度工具。**

**1. 工具层收窄权限。** 用 MCP git server（或自己包一层插件），只暴露 `git_status`、`git_diff`、`git_log`、`git_add`、`git_commit`、`git_branch_create`、`git_branch_delete` 这几个能力。push 默认不开放，需要时单独开一个带人工确认的工具。

**2. 规则写进仓库文件。** 约定固化下来：

- commit message 遵循 Conventional Commits，scope 从改动文件推断；
- 分支命名用 `feat/`、`fix/`、`chore/` 前缀；
- 禁止 force push、禁止操作 main 等受保护分支；
- 生成的 message 必须基于真实 diff，不允许脑补。

我把这些放在仓库的 `.agent/git-rules.md` 里，Agent 启动时读取。规则随仓库走，团队共享同一份，比散落在个人提示词里可靠。

**3. 按风险分级的工作流。**

- 只读（status / diff / log）：全自动，随问随答；
- 本地写（commit、建分支）：Agent 生成 message 后先输出 dry-run 预览，低风险分支直接执行；
- 远程写（push、merge、删远程分支）：必须人工确认，Agent 只负责准备命令和改动说明。

**4. 全程留痕。** 包一层日志插件，Agent 的每次 git 调用都记录时间、命令、结果，出问题能回溯。

## 踩坑点

- **message 与 diff 不符**：早期图省事只喂 `--stat`，Agent 会根据文件名想象改动内容。必须给真实 diff；diff 被截断时要明确告诉它"以下仅为部分改动"。
- **上下文爆炸**：一次两千行的 diff 直接把会话撑爆。改为先给 stat，再按文件挑关键 hunk 二次喂入。
- **交互式命令**：Agent 有次试图跑 `git rebase -i`，工具直接卡死。所有暴露的工具都要求非交互参数。
- **错分支操作**：Agent 在 detached HEAD 上提交过一次。后来在 commit 工具里加了前置校验：当前分支不符合命名规则就拒绝执行。

## 可复用建议

- 权限分三档（只读 / 本地写 / 远程写），宁可细不可粗；
- 用工具白名单替代 shell 直通，每个工具自带前置校验；
- 规则文件进仓库，和代码一起 review、一起演进；
- 所有自动操作留日志，远程写永远保留人工闸门。

## 总结

AI 助手管 Git，收益最大的不是"全自动提交"，而是把提交规范、分支清理这类低价值高重复的活儿接管掉，同时用工具白名单和人工闸门兜住风险。自动化程度可以逐步放开：先只读，跑稳了再开本地写，远程写始终留确认。按这个节奏推进，Agent 是省心的同事，而不是定时炸弹。
