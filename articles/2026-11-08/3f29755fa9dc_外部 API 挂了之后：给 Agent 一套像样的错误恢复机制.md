# 外部 API 挂了之后：给 Agent 一套像样的错误恢复机制

## 背景

Agent 的能力半径基本取决于它能调多少外部服务：搜索、天气、数据库、第三方 SaaS、自家内部接口。在 OpenClaw 的实践里，工具调用往往占一轮任务 70% 以上的耗时和大部分失败来源。传统后端挂了会报 500，Agent 挂了的表现要糟糕得多——它可能陷入重试循环烧 token，也可能编一个看起来合理的答案糊弄过去。

## 问题

错误恢复不是"让模型再试一次"这么简单。常见的三类失控：

1. **盲目重试**：模型收到报错后原地重试，撞上 429 限流，越试越挂，一轮任务跑几十次同一条失败调用。
2. **幻觉兜底**：工具返回原始堆栈或超时空对象，模型自行"脑补"结果，用户拿到假数据。
3. **级联阻塞**：某个工具超时设了 60 秒，整条 agent loop 被一个坏接口拖死，后续步骤全部超时。

本质上，重试决策发生在代码层，不该交给 LLM 临场发挥。

## 做法

**第一步：让工具快速失败。** 所有工具调用显式设置连接超时和读取超时（建议 3s / 15s 起步，按接口实际 P99 调）。MCP 工具层面加超时，不要指望模型"感觉卡了就换一个"。

**第二步：定义错误契约。** 工具不抛裸异常，统一返回结构化错误：

```json
{
  "ok": false,
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "attempt": 2,
  "hint": "建议 2s 后重试，最多 3 次"
}
```

模型只做一件事：读 `retryable` 字段。为 `false` 就老实告知用户，禁止编结果。

**第三步：有边界的重试。** 只对幂等操作重试；指数退避加抖动（1s → 2s → 4s）；次数封顶 2–3 次；429 必须尊重 `Retry-After` 头。非幂等的写操作（下单、发消息）绝不进重试逻辑，改为"查询确认 + 人工介入"。

**第四步：降级而不是死磕。** 每个关键工具预置降级路径：本地缓存（带 staleness 标记，明确告诉用户数据是 X 分钟前的）、备用数据源，或者干脆跳过该步骤，在最终报告里写明"此项因 API 故障未完成"。

**第五步：熔断。** 单个工具连续失败 N 次（比如 5 次），冷却 60 秒内直接走降级，不再发起真实调用。熔断按工具粒度做，避免一个坏接口拖垮全局。

**第六步：预算护栏。** 每次任务运行设定 token、耗时、调用次数上限，触发即停止，并输出"完成到哪、卡在哪、为什么"的结构化报告。

## 踩坑点

- 在系统提示里写"失败了就重试"：等于打开无限循环。重试逻辑放代码，提示词里只写"如何解读错误"。
- 把原始堆栈直接喂回模型：它一定会试图解释并编造，先在工具层包装成结构化信息。
- 超时一刀切：2 秒会杀死本来就慢但健康的接口，60 秒会拖死整个循环，分接口配置。
- 静默降级：用了缓存却不声明数据陈旧，比直接报错更伤信任。
- 熔断不区分工具：一个搜索 API 抖动，导致数据库工具也被连坐熔断。

## 可复用建议

- 做一层统一的 Tool Client：超时 + 重试 + 熔断 + 错误契约，所有工具注册时走这层，一次写好处处生效。
- 工具元数据里加 `idempotent` 和 `fallback` 字段，让重试和降级策略可以自动化选择。
- 上线前对每个外部依赖做一次手动"拔网线"演练，确认降级路径真的能走通——很多降级逻辑写完从没被执行过。
- 每次故障后看日志：记录工具名、延迟、错误码、第几次尝试，复盘重试策略是否合理。

## 总结

外部 API 挂掉是常态，不是意外。错误恢复是工程问题，不是提示词问题：快速失败、结构化错误、有界重试、诚实降级、按工具熔断。Agent 可以容忍失败，但不能容忍编造和失控。
