## 背景

团队里大多数"日报"其实早就存在于日志中：CI 跑了多少次、哪些服务报错、PR 合并了几个、告警处理到什么程度。问题只是没人愿意每天花二十分钟把它们抄进模板。我们用 OpenClaw 搭了一条定时流水线，把原始日志变成结构化日报，跑了三周多，分享一点工程上的经验。

## 问题

最直觉的做法是直接把日志丢给 LLM，让它"写个日报"。实际效果很差：

- **数字会幻觉**。错误率、构建次数这类硬指标，模型经常改写或四舍五入；
- **日志量大**，超出上下文，模型实际只看到了尾部几行；
- **格式不稳定**，今天多一个标题明天少一个表格，下游没法归档和对比。

核心矛盾在于：数值要准确（确定性工作），叙述要像人写的（生成性工作）。这两件事必须拆开做。

## 做法

流水线分四层，每层独立可测：

1. **采集**。cron 定时触发采集脚本，拉取四类源：服务日志（近 24h ERROR/WARN）、CI 记录、git log、告警平台事件。统一落到 `staging/YYYY-MM-DD/` 目录，原始文件保留不动，方便回溯。
2. **结构化**。用确定性脚本（awk/jq，不要用 LLM）把日志解析成一个 JSON：`{deploys: 3, failed_jobs: [...], errors_by_service: {...}, alerts_closed: 5}`。这一步是整个流水线的地基，所有数字在这里定型。
3. **摘要生成**。OpenClaw agent 通过 MCP 调两个工具：`read_daily_metrics`（返回第 2 步的 JSON）和 `read_error_samples`（返回少量典型错误原文，供叙述引用）。提示词固定报告骨架：今日概况、异常与原因、待跟进。模型只负责把数字串成通顺的话，不负责产生数字。
4. **校验与分发**。生成结果先过 JSON Schema 校验，再做数字交叉核对：正文里出现的每个数值必须能在 metrics JSON 里找到，否则标记 `needs_review` 而不是直接发送。通过后推送到群 webhook，并归档一份 Markdown 到仓库。

## 踩坑点

- **别让模型算数**。第一版把错误计数也交给模型汇总，出现过"约十几个错误"这种表述。所有数字必须来自结构化层，模型只组织语言。
- **时区**。CI 用 UTC、服务日志用本地时间，第一份日报把两天的构建混在了一起。采集层统一转成带时区的 ISO 8601。
- **上游格式漂移**。第二周服务日志改了格式，解析静默失败，日报发出"零错误"。后来在结构化层加了 `parse_failures` 计数，非零就阻断发送。
- **重试幂等**。webhook 超时重试导致同一条日报发了三遍。现在每次运行以日期为幂等键，发送前先查归档目录。

## 可复用建议

- **先定 Schema 再写提示词**。报告的 JSON Schema 是流水线的接口契约，提示词围绕它迭代，而不是反过来。
- **确定性与生成性严格分层**，任何数字不允许穿过 LLM。
- **用固定的"坏日志" fixture 做回归测试**，改提示词或解析逻辑后先跑 fixture 再上线。
- **提示词、Schema、脚本全部进版本库**，日报出问题时能 diff 出"是哪天哪次变更导致的"。

## 总结

这套东西并没有多少"AI 含量"——大部分代码是解析、校验和分发。但恰恰是这些不起眼的工程环节，决定了日报能不能每天稳定出现在群里。LLM 在这里只做一件事：把结构化数据翻译成人话。这个边界划清之后，流水线才真正可靠。
