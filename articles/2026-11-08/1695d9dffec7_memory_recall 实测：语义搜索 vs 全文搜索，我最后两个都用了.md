## 背景

OpenClaw 的 agent 长期跑下来会攒不少记忆：用户偏好、项目约定、踩过的坑。`memory_recall` 是 agent 主动调用的检索入口，召回质量直接决定它"记不记得住事"。社区里常见的两条路线：向量语义检索（embedding + 相似度）和全文检索（FTS5/BM25）。我在自己的助手上有约 3000 条记忆条目，两条路各跑了一个月，说说实测结论。

## 问题：各自都会翻车

- **语义检索**强在换说法也能命中："上次那个部署脚本报错"能召回当时的错误记录；但对精确标识符很不可靠——错误码 `ECONNRESET`、函数名、专有名词，embedding 经常给出"看起来相关但不是那条"的结果。
- **全文检索**强在精确命中，但同义改写直接漏掉，而且中文分词是坑：SQLite FTS5 默认 tokenizer 按空格切词，整段中文会被当成一个 token，基本搜不到东西。

单用任何一种，都能复现"我明明记得说过这个"的丢忆场景。

## 做法：双路召回 + RRF 融合

1. 记忆条目做成原子化：一条一个事实，带 `created_at`、`tags`，单条控制在 200 字以内。
2. 双索引：embedding 入向量库（我用 bge-m3，中英混合表现稳），正文同时写入 FTS5，中文配置 bigram 或 jieba 分词。
3. `memory_recall` 同时查两路，各取 top-10，用 RRF（Reciprocal Rank Fusion）合并排序。
4. 融合后做三件事：去重、时间衰减加权（旧记忆略降权）、截断 top-5 注入上下文。
5. 相似度低于阈值的直接丢弃，宁缺毋滥。

## 踩坑点

- **中文分词**：FTS5 默认配置对中文几乎不可用，务必换 tokenizer，否则全文那一路形同虚设。
- **Embedding 模型与语料不匹配**：用英文为主的模型存中文记忆，召回明显劣化，选多语模型更稳。
- **top-k 太大**：早期我注入 10 条，agent 上下文被污染，反而答非所问。压到 5 条以内效果最好。
- **换 embedding 模型要全量重索引**，条目多了记得提前留迁移脚本。
- **语义高分 ≠ 相关**：曾出现"部署"把无关的"部门"记忆顶上来，RRF 里全文那一路能把它压回去——这正是融合的价值。

## 可复用建议

- 默认上混合检索；纯语义只在记忆以"描述性、无标识符"内容为主时考虑。
- 攒一份 20~50 条真实查询做回归评测：每次调参跑一遍，看命中率，不凭感觉。
- 记录每次 recall 的命中日志，和 agent 的最终回答对照，能快速区分是检索问题还是 prompt 问题。
- 先简单后复杂：FTS5 + RRF 一晚上就能搭完，向量那一路可以后补。

## 总结

"哪个好"其实是个伪命题——两条路翻车的方式不同，正好互补。全文检索兜住精确标识符，语义检索兜住改写和口语化查询，RRF 融合加时间衰减，是我实测下来投入产出比最高的组合。别急着上复杂 reranker，先把分词和 top-k 这两个基础项做对，收益已经很明显。欢迎在评论区贴你们的 recall 翻车案例，一起攒评测集。
