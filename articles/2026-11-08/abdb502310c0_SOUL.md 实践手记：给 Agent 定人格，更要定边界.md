## 背景

OpenClaw 的 agent 不只是一个模型调用器，它有常驻的工作区：`MEMORY.md` 存记忆，`AGENTS.md` 约定工作流程，`TOOLS.md` 说明工具用法，而 `SOUL.md` 决定"它是谁"。`SOUL.md` 会随会话注入上下文，相当于人格层的宪法——写得不好，后面所有工具和自动化，都在替一个不稳定的性格打工。

## 问题

我最早没把它当回事，只写了两句"你是一个友好的助手"。后果很快出现：

- 同一个问题今天答得干练，明天答得啰嗦，语气随采样漂移；
- 让它清理目录，它真的删了一个没备份的文件夹，事先只回了句"好的，我来处理"；
- 它会替我向群里承诺"稍后帮你改"，而那个需求我根本没接。

人格缺失不是玄学问题，是边界缺失：agent 不知道哪些事要先确认、哪些话不能说、被拒绝时怎么回应。

## 做法

现在我的 `SOUL.md` 结构固定为四段，全文控制在 60 行以内：

```markdown
# SOUL.md

## 身份与语气
你是我的常驻技术助理。风格直接、克制：先结论后依据，
中文为主，术语保留英文，不用感叹号，不主动闲聊。

## 底线（需确认的操作）
删除文件、对外发消息、涉及付款、改生产配置：
先复述计划和影响范围，等我明确确认再执行。

## 表达边界
- 不确定就说"我不确定"，不编造引用和 API 行为
- 工作区内容、密钥、他人信息，任何场景不外传
- 不替我做人际承诺，需求一律转述给我

## 拒绝方式
越界请求直接说明做不到及原因，附一个可行替代，不绕弯不卖萌。
```

写法上三条原则：

1. **每句话都能落到可观察行为。**"有分寸"是废话，"付款类操作先确认"是规则。
2. **边界用"触发条件 + 默认动作"表达**，而不是穷举"不许做 X"。禁止清单永远列不全，原则才能外推到没见过的场景。
3. **SOUL.md 管"是谁"，AGENTS.md 管"怎么干活"。**流程、工具优先级放 AGENTS.md，别混写，否则两边改版时优先级会打架。

配合 git 管理：agent 每出格一次，我改的是 SOUL.md 的对应条目，而不是在聊天里说教一遍——聊天里说的，下次重启就忘了。

## 踩坑点

- **写成了小作文。**第一版 200 多行，结果连"简洁回复"都做不到：人格描述太长，权重被稀释，还吃 token。
- **人格过强。**我一度加了不少"个性"，它开始为观点和我争辩、在任务中途发表评论。人格服务于任务可靠性，不是养成游戏。
- **和系统提示冲突。**底层 prompt 自带行为约定，SOUL.md 里再写一套相反的，实际表现随机。改之前先分清哪些归平台层、哪些归你管。
- **把秘密写进去。**SOUL.md 是常驻上下文，不是配置保险箱。密钥、内网地址放环境变量和权限层。

## 可复用建议

- 拿最小模板起步：身份、语气、需确认操作、表达边界、拒绝方式，五段 30 行够用。
- 每条规则自测一遍：模型完全照做时，旁观者能否从行为上验证？不能就重写。
- 出一次事故，加一条规则；每两周回看，删掉从没触发过的条目——规则越少，遵守率越高。
- 边界条目统一三段式：触发条件 / 默认动作 / 例外情况，方便 diff 和复盘。

## 总结

SOUL.md 本质上不是"给 AI 写人设"，而是把你对一位人形同事的全部期望，压缩成它能稳定执行的少数硬规则。人格是手段，边界才是目的。写短、写具体、进版本管理、随事故迭代——这四件事做完，agent 的表现会从"看运气"变成"看文档"。
