## 背景

我日常让 agent 起草技术稿，同一篇要发公众号、知乎、掘金和个人博客。AI 输出的 Markdown 看着挺规范，真发出去就碎：表格挤成一团、脚注变裸文本、代码高亮失效。写稿十分钟，适配两小时。于是我把"格式适配"从发布动作里拆出来，做成一条可复用的管线。

## 问题

三个来源叠加：

- **方言不一致**：公众号不收 Markdown，要转内联样式的 HTML；知乎不支持脚注和多数 HTML；掘金兼容 GFM，但图片得传自家图床。
- **LLM 输出是给人看的，不是给发布器用的**：标题层级乱跳、三层嵌套列表、表格塞长句、代码块语言标签随缘。
- **手动适配不可回归**：每发一次改一遍，下次照错不误。

## 做法

核心思路：**把 Markdown 当 AST 处理，不做字符串替换**。分四步：

1. **归一化**。用 unified/remark 把输出解析成 mdast，做一次规范化：标题从 h2 起步且禁止跳级、嵌套列表最深两层、剥掉 frontmatter 和"以下是……"这类对话残留，产出一份 GFM 子集作为中间方言。
2. **白名单校验**。按目标平台定义支持的节点集合，lint 拦截：脚注转行内引用、HTML 块删除或降级、表格超 4 列转列表。不合规就报错，不静默修。
3. **平台适配器**。每个平台一个纯函数序列化插件：公众号走 md→HTML 加内联样式；知乎走受限语法加自家公式格式；博客直接吐 GFM。
4. **预览与发布**。适配结果落盘生成 diff 预览，人确认后再经 OpenClaw 的发布 skill / MCP 工具推送；发布前自动检查图片，防盗链外链先传平台素材库。

四步在 OpenClaw 里包成一个 skill，调用就是一条命令：`draft.md → wechat.html / zhihu.md / blog.md + 预览链接`。

## 踩坑点

- 公众号会剥掉 class 和外部样式，样式必须全内联；`<pre>` 里的空格换行会被吞，需做空白字符替换。
- 图片最容易翻车：微信防盗链让热链全挂，必须在适配阶段就换源，别等发布时才发现。
- 让 LLM 二次润色会转义 HTML 实体（满屏 `&lt;`），管线里要加一道反转义检测。
- **别让模型直接输出目标平台格式**——它对方言的记忆不可靠，永远先出标准方言，再做确定性转换。
- 脚注和 KaTeX 公式在多数中文平台都要降级，提前在 lint 拦住。

## 可复用建议

- 转换全部基于 AST 写小插件，禁用大段正则替换。
- 每个平台维护 golden file：固定输入→期望输出，适配器一改就能回归。
- 管线保持幂等，同一输入跑两遍结果一致，方便重跑。
- lint 规则独立成配置文件，规则与代码解耦，团队其他人也能加规则。

## 总结

多平台发布本质是方言翻译。靠 prompt 让模型"直接输出公众号格式"既不稳定也不可测；把归一化、校验、适配拆成确定性的 AST 变换，模型只管内容，格式交给管线，发布就从手工艺变成了可回归的工程。
