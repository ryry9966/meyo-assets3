# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

Agent 接上 MCP 之后，能力从"聊天"变成了"动手"：读写文件、执行命令、调外部 API、发消息。能力越强，越绕不开一个问题——哪些动作它可以直接干，哪些必须停下来问人。

实践中常见两个极端：一是"万事都问"，每步弹确认，用户很快退化成无脑点"允许"的机器；二是"全自动"，直到某天 agent 一条 `rm -rf` 或者往客户群里发了一条不该发的消息，才想起来补权限。

## 问题

这本质上是个分类问题，不是开关问题。判断一个动作该不该自动执行，看两个维度：

- **可逆性**：错了能不能退回来？改本地文件能回滚；发出去的消息、扣掉的钱、删掉的线上数据基本不能。
- **影响半径**：只影响 agent 自己的工作目录，还是影响生产环境、真实用户、真金白银？

## 做法

落地分四步：

1. **盘点动作清单**。把 agent 能调的所有东西列出来：MCP tools、shell 命令模式、可写路径、外部 API。别只看工具名，要看实现里有没有副作用。
2. **分四级**：
   - L0 只读（搜索、读取、dry-run）→ 自动执行
   - L1 工作区内写操作（改文件、本地 commit）→ 自动执行 + 记日志留 diff
   - L2 出边界（push 远端、调外部 API、发消息、删数据）→ 必须确认
   - L3 高危（force push、支付、改权限）→ 默认禁止，需人工单独开启
3. **分级写进配置，不写在 prompt 里**。OpenClaw 的工具白名单、命令模式过滤都放到配置层，prompt 只负责解释，不承担管控——模型输出是不可靠的边界。
4. **加自动刹车**：预算上限、调用频率限制、单次 diff 大小阈值。agent 跑偏时，刹车比人盯有用。

## 踩坑点

- **确认疲劳**是最常见的坑。问得太多，确认就失去意义，人会闭眼点"允许"。宁可缩小 L2 范围减少提问次数，也别稀释确认的价值。
- **确认信息缺上下文**。只弹一句"是否执行？"人没法判断。确认框里必须有：要做什么、影响范围、diff 或参数摘要、回滚方式，让人 10 秒内能做决定。
- **权限粒度太粗**。"允许 git"和"允许 git push"差很远，"允许 push"和"允许 force push"差更远。白名单按动作加参数模式给，别按工具整给。
- **链式调用放大风险**。agent A 的输出喂给 agent B，每一环单看都"安全"，连起来可能越界。链路上每一环单独过分级。
- **环境没区分**。开发环境自动执行、生产环境必须确认，这是底线，别用同一套配置跑所有环境。

## 可复用建议

- 确认消息固定模板：**动作 + 目标 + 影响范围 + 成本/风险 + 回滚方案**，缺任何一项就视为不该发起这次确认。
- 每次出事故，先问"这个动作当初为什么被划在 L1"，再决定是升级分级还是补护栏，而不是只改 prompt。
- 定期复审自动放行清单，收回没人用的权限，权限清单和代码一样需要维护。
- 一句话原则：**默认最小权限，显式升级；让"问"便宜且有信息量，让"干"默认是安全的。**

## 总结

权限边界不是一条画死的线，而是动作属性（可逆性 × 影响半径）与环境上下文的函数。判断标准可以很朴素：错了能不能退、退的成本多大、波及多少人。能退的小事让 agent 自己干并留痕，不能退的大事必须问，而且要问得让人看得懂。边界宁可先保守，再根据事故和误报迭代收紧或放宽——别靠"相信它不会乱来"。
