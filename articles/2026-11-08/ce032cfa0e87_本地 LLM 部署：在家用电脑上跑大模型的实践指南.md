## 背景

做 Agent 和自动化的人大概都有体感：流程一旦跑起来，token 消耗远超预期。一个带 MCP 工具调用的循环，一轮下来几万 token 很正常，跑批处理时 API 账单会更直观。另外不少自动化场景涉及本地文件、聊天记录、内部文档，直接丢给云端服务心里总归不踏实。

先说清定位：本地部署不是要替代云端大模型，而是把**高频、低难度、涉隐私**的那部分任务接过来。这是我这段时间实践下来的结论，也是这篇帖子的前提。

## 问题

家用电脑跑大模型，难点不在"能不能跑起来"，而在：

1. Agent 场景对模型的要求比聊天高得多——要稳定的 function calling、要扛得住长上下文、要格式输出不崩；
2. 显存/内存预算有限，模型档位和量化等级需要精确取舍；
3. 网上评测大多是聊天跑分，跟你的实际 agent loop 表现对不上。

## 做法

**第一步：盘点硬件。** 有独显优先看显存：8GB 能跑 7B 级 Q4 量化；12–16GB 可以摸到 14B。纯 CPU 也不是不行，16GB 内存跑 7B Q4 大概每秒几个 token，做异步批处理勉强够用，交互式体验别指望。

**第二步：选运行时。** 图省事用 Ollama，一行命令起服务且自带 OpenAI 兼容端点；想精细控制采样参数、上下文、KV cache 策略就用 llama.cpp 的 server。两个我都在用：日常 Ollama，调优时切 llama.cpp。

**第三步：选模型。** 别只看榜单分数，优先验证工具调用能力。实测 Qwen 系列 7B/14B 的 Q4 量化在工具调用上比较稳，JSON 格式遵守度也够用；中文任务可优先考虑同系列。

**第四步：接入。** 服务起来后就是一个本地 OpenAI 兼容端点，agent 配置里把 base_url 指过去、模型名对齐即可。MCP 工具定义原样下发，协议层不用动。

**第五步：用真实任务压测。** 拿自己平时跑的自动化流程切到本地模型跑一天，重点看三个指标：工具调用成功率、JSON 解析失败率、单轮耗时。这比任何跑分都诚实。

## 踩坑点

- **上下文默认值是隐形炸弹。** Ollama 默认上下文很短，agent loop 跑几轮历史就被截断，工具结果丢失后模型开始瞎编。`num_ctx` 要显式调大，但注意 KV cache 随上下文线性吃显存，不是白给的。
- **量化太狠会先崩工具调用。** Q4 是体积和体验的平衡点；Q2/Q3 聊天还行，一到输出结构化 JSON 就开始少括号、漏字段。
- **别指望 7B 做复杂多工具编排。** 任务一复杂就开始幻觉出不存在的工具、参数填错。多工具编排留给云端大模型，本地模型干抽取、分类、摘要、格式转换这类活。
- **并发默认串行。** 批量任务会排队，要并行得调参数，显存账重新算。
- **长输出会拖死整个 loop。** 生成长摘要之类的内容时，本地模型的速度劣势被放大，这类步骤建议仍走云端。

## 可复用建议

1. **做分层路由。** Agent 入口加一个轻量判断：简单任务走本地，复杂任务走云端。而"判断该不该我来"这件事本身，恰好是本地小模型能干好的活。
2. **显存预算先算后跑。** 模型权重 + KV cache + 系统占用，留 20% 余量；超了就降一档模型，别硬塞。
3. **评测集用真实日志。** 从自己的运行日志里抽几十条真实输入做回归测试，换模型、换量化前后各跑一遍。
4. **模型配置做成 profile。** 不同任务挂不同模型档位，切换成本降下来，路由策略才有意义。

## 总结

本地部署的价值不在"跑通"那一刻，而在于你多了一个零边际成本、数据不出门的算力档位。它接不住所有任务，但接得住自动化里最烧 token 的那部分。先把硬件账算清，再用真实任务验证，最后用路由把两边的长处拼起来——这套思路比任何"一键部署"教程都耐用。
