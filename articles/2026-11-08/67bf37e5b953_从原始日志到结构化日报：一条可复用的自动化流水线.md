## 背景

我们团队每天要在群里发一封日报，内容涵盖昨日代码提交、CI 失败情况、服务告警摘要和待办进展。以前靠值班同学手动拼，平均耗时 20-30 分钟，且格式经常漂移。这篇帖子记录我们用 OpenClaw 定时任务 + MCP 工具 + 本地脚本搭的日报流水线，跑了一个多月，踩过的坑一并分享。

## 问题

直接把"生成日报"丢给 Agent 效果很差，原因有三：

1. **原始日志噪声大**：一天的服务日志几十万行、群消息几百条，直接塞上下文既贵又容易丢重点；
2. **LLM 不擅长精确计数**：让它统计"昨日提交数""失败次数"必然出错；
3. **输出格式不稳定**：下游是 IM webhook 和归档文件，格式一漂就断。

所以核心思路是：**确定性的事交给脚本，语言组织交给模型，中间用 schema 卡住。**

## 做法

整条流水线分五步，每步一个独立脚本，失败可单独重跑：

1. **采集**：cron 定时触发，通过 MCP 工具分别拉取 git log、CI 记录、告警原始数据，落到本地 JSONL，时间窗口显式传参（昨日 00:00–23:59，指定时区）。
2. **清洗**：脚本侧去重（同一告警 10 分钟内的重复项合并）、脱敏（token、内网 IP 正则替换）、打分类标签（build / incident / task）。
3. **统计**：纯 Python 算指标——提交数、失败的 pipeline 列表、告警 Top3。数字一律脚本算好，LLM 只负责"读表说话"。
4. **摘要**：把统计结果和各类限量原文片段组装成结构化输入，交给 Agent 按固定 JSON schema 输出 `summary / highlights / risks / todo` 四个字段。校验失败自动重试一次，再失败降级为纯模板报告。
5. **投递**：渲染成 Markdown，推送群 webhook 并归档到按日期命名的文件，推送带幂等键，重跑不会发重复消息。

## 踩坑点

- **时区坑**：最初用 UTC 的"昨天"，晚间提交被划到了第二天。改为显式传 Asia/Shanghai 时间窗口后解决。
- **上下文爆炸**：第一版把清洗后的日志全量喂给模型，一次跑掉半个月 token 预算。改成"统计表 + 每类限量片段"后成本降了一个数量级。
- **格式漂移**：即使 prompt 写明了 schema，偶尔仍会多字段或少字段。加上 JSON Schema 校验 + 重试 + 降级模板，彻底解决。
- **幻觉风险**：模型曾在 highlights 里"脑补"出没发生的修复。缓解办法是要求每个 highlight 引用输入中的原始条目 ID，校验器检查 ID 是否真实存在。

## 可复用建议

- **Schema 先行**：先定输出契约再写 prompt，Agent 的自由度必须被结构约束。
- **阶段隔离**：采集/清洗/统计/摘要/投递各自独立可重跑，出问题能二分定位。
- **渐进接入**：先接一个数据源跑稳，再逐个扩展，别一上来全量。
- **流水线自身留日志**：每次运行的输入规模、token 消耗、校验结果都记下来，回头排查全靠它。
- **脱敏前置**：敏感数据在进入模型之前就处理掉，别指望 prompt 里写一句"不要输出密钥"。

## 总结

这条流水线的本质，是把"生成日报"拆成"确定性计算 + 受约束的文本组织"：模型只做它擅长的部分，数字和结构由代码兜底。上线后日报编写时间从半小时降到基本为零，格式也稳定了。下一步计划把清洗规则配置化，让其他小组不改代码就能接入自己的数据源。欢迎在评论区交流你们的日报自动化实践。
