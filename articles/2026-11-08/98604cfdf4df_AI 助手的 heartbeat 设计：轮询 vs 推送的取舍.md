## 背景

跑过常驻 agent 的都知道一个尴尬现实：你不主动找它，它就永远沉睡。OpenClaw 这类网关型助手要真正"活着"，必须在两种唤醒机制之间做选择：**定时心跳（轮询）** 和 **事件推送**。

OpenClaw 自带的 heartbeat 是典型的轮询设计：按固定间隔唤醒 agent，检查 `HEARTBEAT.md` 任务清单，有活干活，没活继续睡。这个模型简单可靠，但用久了会暴露一些问题，值得展开聊聊。

## 问题

轮询的核心矛盾是**间隔**：

- 间隔太短，token 成本线性上涨，而且大部分唤醒是空转；
- 间隔太长，对"消息到了 5 分钟内要回"这类需求完全不可用。

推送看起来是正解——webhook、文件 watcher、MCP notification 都是事件驱动，实时且不浪费。但推送有自己的坑：**通道离线期间的事件会丢**、**回调重试导致重复触发**、**每个事件都唤起一次 LLM，成本反而失控**。

结论先行：这不是二选一的问题，而是分层问题。

## 做法与步骤

我的实践是"推送入队 + 心跳统一消费"的混合模型：

**1. 保留心跳作为兜底节拍器。** 默认 30 分钟一次，作为最终一致性保障。所有自动行为必须有这个兜底，推送只是降低延迟的手段，不是替代。

**2. 事件源统一写 inbox，不直接唤起 agent。** Telegram webhook、目录 watcher、MCP 推送，全部落到一个持久化队列。关键设计：事件只入队，不触发推理。

**3. 心跳醒来统一消费 inbox。** 每次唤醒时把待处理事件合并成一个批次交给 agent，一次推理处理 N 个事件。这是成本控制的核心——把"事件数 × 推理次数"压缩成"心跳数 × 推理次数"。

**4. 心跳 prompt 瘦身。** 心跳轮次只带状态摘要和 inbox 增量，不带完整会话历史。空 inbox 时用极短的"无事发生"路径直接返回，不进主模型。

**5. 失败退避加抖动。** 心跳执行失败后指数退避（30min → 1h → 2h），并加随机抖动，避免多个 agent 实例同时醒来打爆上游 API。

## 踩坑点

- **心跳轮次污染上下文。** 最初心跳回复也写进会话历史，几小时后上下文里全是"无事可做"。解决：心跳轮次单独存档或标记为 ephemeral，不进入主对话流。
- **HEARTBEAT.md 任务没有幂等标记。** agent 执行完任务后如果忘了清掉条目，下个心跳会再执行一遍。给每个任务加 ID 和状态字段，执行前先检查。
- **webhook 重试导致重复入队。** 对端 5 秒没收到 200 就重发，同一消息入队三次。入队时用消息 ID 做幂等键去重。
- **重启期间的事件丢失。** inbox 必须落盘，内存队列在进程重启时就是黑洞。
- **静默时段没处理。** 凌晨三点心跳照样跑，又贵又没用。后来加了分级间隔：活跃时段 15 分钟，深夜 2 小时。

## 可复用建议

1. **默认轮询，推送做加速**——不要把正确性押在推送通道的可用性上。
2. **入队和推理分离**——事件聚合是省 token 最有效的一招，比调间隔管用。
3. **心跳是独立子系统**——独立 prompt、独立历史、独立日志，别和主对话混在一起。
4. **给心跳记账**——记录每次心跳的 token 消耗和唤醒原因，一周后你就知道间隔该设多少。
5. **所有自动行为可一键关闭**——心跳失控时的第一需求是立刻闭嘴，这个开关要触手可及。

## 总结

轮询和推送的取舍，本质是**一致性、延迟、成本**三者的权衡。轮询用固定成本买确定性和兜底能力；推送用复杂度买实时性。对 OpenClaw 这类 7×24 常驻助手，我的建议是：心跳打节拍，推送喂事件，队列做缓冲，幂等做保险。先跑通轮询基线，再按延迟需求逐个渠道加推送——别反过来。
