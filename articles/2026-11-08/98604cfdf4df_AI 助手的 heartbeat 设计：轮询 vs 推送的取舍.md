## 背景

OpenClaw 这类本地优先的助手默认是“被动”的：没有消息进来，模型就不会运行。要让 agent 具备主动性——定时巡检服务器、汇总邮件、盯一个长任务——就需要 heartbeat（心跳）机制。OpenClaw 内置的做法很朴素：每隔固定间隔唤醒一次 agent，让它读一份 HEARTBEAT.md 清单，逐条判断“现在有没有必要做事”，没必要就保持沉默。

这是典型的轮询。它简单、可预测、不依赖额外基础设施，但每次醒来都是一次真实的模型调用。于是问题来了：什么时候轮询够用，什么时候必须换成推送？

## 问题：轮询的两个硬伤

- **成本**：间隔 30 分钟，一天约 48 次唤醒，即使 90% 的时候无事可做，token 也照烧。清单越长，每次唤醒携带的上下文越大，固定开销线性上涨。
- **延迟**：平均要等半个周期。用户能接受“每天早上汇总一次邮件”，但很难接受“服务挂了半小时才知道”。

推送（webhook / 消息队列 / MCP 通知）恰好相反：事件发生才唤醒，延迟秒级、无事零成本，但要自己搭事件源、做鉴权、去重、失败重试，基础设施复杂度陡增。

## 做法：先分类，再选型

我的经验是不要二选一，按事件特征分桶：

1. **盘点事件源**。把想做的事列出来，标注两个属性：时效要求（分钟级还是小时级可接受）、事件是否可编程捕获（有没有 webhook、能不能写个脚本探测）。
2. **时效不敏感且事件源分散的**（邮件汇总、日报、目录巡检）→ 留在 heartbeat 里，间隔调到业务能容忍的下限。
3. **时效敏感且可捕获的**（监控告警、CI 失败、特定关键词消息）→ 走推送。webhook 打到一个轻量网关（几十行的 HTTP 服务即可），由网关转发成一条唤醒消息给 agent。
4. **心跳降级为兜底**：间隔放宽到 1–2 小时，清单只留巡检类条目，顺便检查推送链路本身是否还活着。

推送侧两个必做项：**幂等**（事件带唯一 ID，网关层去重）和**冷却窗口**（同类事件 N 分钟内只唤醒一次，防告警风暴）。

## 踩坑点

- **心跳清单写成愿望清单**。条目越多，agent 每次“总得找点事做”，开始输出低价值汇报骚扰用户。收敛到 3–5 条、明确“无事则沉默”，是心跳可用性的分水岭。
- **推送没做去重**。监控重试导致同一告警触发五次唤醒，模型给出五个雷同回答——体验比纯轮询还差。
- **推送成为单点**。网关或队列挂掉后 agent 彻底失聪，而你以为它“只是没事做”。这也是保留低频心跳兜底的核心原因。
- **在心跳里塞重活**。一次唤醒跑十分钟批任务，会阻塞会话响应。心跳里只做“发现 + 派发”，重活交给独立任务队列执行。

## 可复用建议

选型判断可以压缩成三问：**延迟要求秒级还是小时级？事件源能不能主动通知你？能容忍多少固定 token 开销？** 三个答案偏向“秒级 + 可通知 + 敏感”，就上推送；反之轮询足够。多数真实场景的答案是混合：推送负责“叫醒”，心跳负责“兜底”。

## 总结

heartbeat 的本质不是技术选型，而是给 agent 定义“什么值得打扰模型、什么值得打扰用户”。轮询用钱换简单，推送用复杂度换实时。OpenClaw 的心跳机制之所以好用，恰恰因为它默认假设“大多数时候没事”——把这句话刻进推送系统的设计里，两条路线就能各取所长。
