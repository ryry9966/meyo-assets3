最近 36kr 上一条话题讨论度很高：Claude Code 的创造者 Boris Cherny 自述，自己日常约九成代码由 AI 完成。热度很快从“AI 能写多少”转向了一个更尖锐的问题——当机器的产出速度远超人类的阅读速度，谁来审？答案藏在 Claude Code 及其团队公开的工程实践里：与其指望某个“超级审查员”从天而降，不如搭一条多级防线。本文把这套机制归纳成六道关卡，拆开看每道防什么、怎么防，以及普通团队怎么抄作业。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-08/2658c550bc6483da.png)

## 先看清矛盾：生成是指数级，审查是线性级

- 传统开发里，“人写人审”大体是 1:1 的节奏，review 是流程中的一个环节。AI 接管生成后，一个人面对的是数倍甚至数十倍的代码增量，审查从环节变成了瓶颈。
- 数据佐证：Stack Overflow 2024 年开发者调查显示，约 76% 的开发者正在使用或计划使用 AI 编程工具，但只有约 43% 信任其输出的准确性；DORA 2024 年报告算了一笔更扎心的账——AI 采用率每提升 25%，交付吞吐量预计下降 1.5%，交付稳定性下降 7.2%。产出上去了，质量水位反而可能下降。
- 还出现了新型攻击面：slopsquatting（幻觉包抢注）。模型偶尔会“编造”不存在的第三方包名，攻击者抢先把这些名字注册成恶意包，坐等复制粘贴。2025 年的一项学术研究统计，模型生成代码中引用的包名约 20% 是幻觉产物（商用模型约 5%，开源模型更严重）。
- 一句话总结：瓶颈从“写不出来”转移到“看不过来”。写代码像开闸放水，审代码就是修堤——水位涨得比堤快，就只能多级泄洪。

## 六道关卡：一条纵深防御流水线

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-08/4d9016f87f955aa6.png)

把 Claude Code 公开的机制与其背后的工程实践归纳起来，大致是六道关卡，思路接近安全工程里的纵深防御（defense in depth）：任何单道关卡都不可靠，可靠的是让弱点互相抵消。

1. **权限闸门（Permission）**：默认模式下，AI 执行写文件、跑 shell 命令都要人工确认；低危操作可加入 allowlist 放行，删库、改 CI 配置、推送主干这类高危动作永久必审。防的是破坏性副作用。
2. **沙箱隔离（Sandbox）**：让 agent 在容器（devcontainer）或独立 git worktree 里干活，数据库用一次性实例，文件系统与主机隔离。防的是污染主环境。
3. **自动化验证（Test / Type / Lint）**：单元测试、类型检查、静态扫描先行，让机器先审机器。Claude Code 的典型工作流是“写完自测、报错自修”，把确定性检查前移到人介入之前。防的是低级错误与回归。
4. **Hooks 自定义关卡**：在 PreToolUse、PostToolUse 等时机插入团队自己的脚本，比如提交前强制跑密钥扫描、复杂度检查，不通过直接拦截。防的是团队规范被 AI 的“平均水平”稀释。
5. **双重审查（AI 审 AI）**：用另一个上下文隔离的模型实例做 reviewer，避免“作者审自己”的确认偏差，人只做最终裁决。防的是自审盲区。
6. **小步提交与可回滚（Checkpoint）**：改动切成原子颗粒，每步可独立回滚，出问题时定位成本从大海捞针降到撤一步棋。防的是错误被后续改动放大。

注意最后一道的分量：前五道都在压低“错误发生”的概率，第六道在压低“错误造成”的代价。两头一起收，才是完整的防线。

## 原理层：审 AI 代码 ≠ 审同事代码

- **错误分布不同**。人类 bug 多是“手滑”和“没想到”；AI 的 bug 常是“幻觉”——调用不存在的 API、误读上下文、在长任务里静默偏离需求。逐行读很难发现，跑测试才现形。
- **意图缺失**。人写代码带着“为什么”，AI 代码只有“是什么”。传统 review 最依赖的恰恰是意图层信息，而这层在 AI 产出里天然稀薄。
- **局部优秀，全局存疑**。单个函数往往干净、风格统一，甚至比人写的更“体面”。这带来一个认知陷阱——自动化偏见（automation bias）：人会下意识信任看起来规整的东西。反过来，如果对每一行都保持怀疑，AI 的效率优势就归零。所以审查策略本质是信任校准问题：校准的不是对模型的态度，而是每个环节的检查强度。

结论：review 的重心要从“逐行读懂意图”转向“验证行为等价”——测试即审查。

## 团队落地：按风险分级，别一刀切

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-08/ee0653afba276568.png)

- **高危路径**（支付、权限、数据删除、密钥管理）：强制人审 + 独立 AI 复审 + 测试全覆盖，三道全上。
- **中危业务代码**：AI 审 + 按比例抽样人审。
- **低危样板代码**（测试脚手架、文档示例、配置模板）：全自动，人审归零。
- 配两个度量指标防“橡皮图章化”：一是 review 拒绝率，如果 AI 代码长期 100% 通过，大概率审查已经形同虚设；二是缺陷逃逸率，衡量漏网之鱼在生产环境的占比。
- 把提示词和上下文也纳入审查对象：很多 bug 的根因不在生成的代码里，而在喂给模型的上下文里——旧代码的坑、过期的文档、写歪的需求描述。

## 收尾：三条冷思考

1. **先审上下文，再审代码**。上下文错了，模型会精确地实现一个错误的东西。把审查触点前移一级，是性价比最高的改动。
2. **用统计思维代替单点思维**。单个文件正确率高不等于系统可靠，风险总量 = 生成量 × 错误率。小步提交的本质，是让大数定律为己所用，而不是被它反噬。
3. **人的位置在移动**：从 author 变成定义验收标准的人。测试写得越好的人，杠杆越大——因为测试是人对机器说的话里，唯一不会产生歧义的一种。

工具会一直换，但“生成越快、验证越贵”这条守恒律不会变。六道关卡不是某个产品的私货，而是软件工程在 AI 时代的一次重新排布。
