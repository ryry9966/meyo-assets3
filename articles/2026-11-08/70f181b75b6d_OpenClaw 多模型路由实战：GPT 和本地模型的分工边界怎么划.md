## 背景

OpenClaw 跑起来之后会发现一个事实：agent 里的 LLM 调用不是同质的。意图分类、检索改写、工具参数格式化这类任务，一个 7B 本地模型就能干；而多步规划、跨文档推理、代码生成，本地小模型就是扛不住。全走 GPT，账单和延迟都难看；全走本地，长尾任务失败率上去了。多模型路由要解决的就是"哪个任务给谁"。

## 问题

我们早期是"一刀切"：所有节点配同一个旗舰模型。跑了一个月发现，成本占比最高的恰恰是难度最低的高频分类和格式化任务；而偶尔出现的复杂规划反而因为走了默认模型失败重试，重试比首次调用更烧钱。痛点三条：成本失控、长尾成功率低、私有数据不明不白出了域。

## 做法

1. **任务盘点与分级**：把 agent 链路里的 LLM 调用列成清单，按三个维度打标——复杂度（是否多步推理、上下文多长）、敏感度（是否携带私有数据）、时延（是否在工具调用热路径上）。
2. **定档位**：分类/改写/格式化 → 本地 7B 级；RAG 生成、常规补全 → 中档；规划与跨文档推理 → GPT 级旗舰。
3. **配置路由与兜底链**：按任务类型标签路由，本地失败再回落云端。
4. **加观测**：每次调用记录 task_type、model、tokens、latency、retry。没有这份数据，路由策略全是拍脑袋。
5. **固定评测集回归**：留 20–50 条代表性样本，每次切模型后跑一遍，防止"省钱但悄悄变笨"。

配置示意（简化）：

```yaml
route:
  - match: task_type in [classify, rewrite, format]
    model: local/qwen2.5-7b
  - match: task_type in [plan, codegen]
    model: cloud/gpt-flagship
  fallback: cloud/gpt-mid
```

## 踩坑点

- **本地模型不守 schema**：小模型生成 tool call 的 JSON 常有字段漂移，务必在路由层后置 schema 校验，校验失败直接 fallback，别让 agent 拿着坏参数去调工具。
- **上下文长度不匹配**：本地模型 8k 上下文，任务却塞了 30k 检索结果，静默截断比报错更危险。路由条件里要加上下文长度判断。
- **重试风暴**：本地"慢"和本地"挂"是两回事。如果超时就无脑兜底到云端，最贵的模型反而被打满。兜底前先判断失败类型。
- **VRAM 争抢**：本地对话模型和 embedding 服务挤同一张卡，互相 OOM。至少分卡，或给路由层加并发上限。
- **观测缺失**：没有 trace，路由退化成玄学，出了问题既不能复盘也不能调参。

## 可复用建议

- 按"任务类"路由，不按"聪明程度"路由，每类任务定一个明确的 SLA。
- 路由决策写进 trace，事后要能回答"这条为什么走了云端"。
- 敏感字段默认不出域，在路由层做拦截或脱敏，不要指望 prompt 自觉。
- 每个 agent run 设 token 预算，超限自动降档。
- 每月看一次成本分布：通常是前 20% 的高频简单任务贡献了大部分成本——那就是迁往本地的主战场。

## 总结

多模型路由不是炫技，是把"成本—质量—时延"的权衡显式化。先用观测数据说话，再小步切流量，配合评测集回归，GPT 和本地模型各自待在性价比最高的位置上。OpenClaw 的路由层足够薄，策略错了改配置就能回滚。建议从账单里最贵的那类简单任务开始迁，收益最直接。
