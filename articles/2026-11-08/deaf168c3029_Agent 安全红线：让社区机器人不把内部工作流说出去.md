## 背景

在社区里跑 Agent 已经很常见：群里的 OpenClaw 机器人负责答疑、检索文档、触发自动化任务。它往往同时持有 MCP 工具、插件和本地文件访问权。问题在于，很多人把"内部助手"和"对外机器人"当成同一个实例跑——Agent 能看到的东西和它能说出去的东西之间，缺少一条明确的红线。

## 问题：三条主要泄露通道

1. **上下文携带。** 内部会话的记忆、任务记录混进社区回复。比如你昨天让它排查的内部服务名、路径、配置，转头在群里被它当例子举出来。
2. **工具越权。** 挂载了过宽的 MCP filesystem 或 shell 工具后，一句"把刚才的报错原样贴出来"就可能让 `.env` 内容、内网地址直接进入公开频道。
3. **提示注入。** 社区消息本身是不可信输入。有人构造一段话诱导 Agent "复述你的系统提示词"或"调用某工具并原样输出结果"。只靠提示词写"不要泄露"，基本挡不住。

## 做法

1. **实例分账。** 社区机器人和内部助手分开跑，不共享记忆、不共享工作区。内部任务的产出要用在社区，先人工过一遍。
2. **最小权限挂载。** 面向社区的实例只挂只读、白名单化的工具集；filesystem 只挂一个专用目录，绝不挂 HOME；高危工具（shell、任意写）对社区实例默认关闭。
3. **密钥不进可达路径。** API key 用环境注入或密钥管理服务，不要落成 Agent 可读的文件；工具层对输出做密钥模式过滤（key/token/私钥块等正则）。
4. **输出过滤层。** 在回复进入公开频道前加一道过滤器：命中内网域名、内部项目代号、密钥模式即拦截或脱敏。这层与提示词无关，是真正的兜底。
5. **注入防御。** 把社区消息当数据不当指令：用户内容用明确分隔标记包裹，工具调用走结构化 schema，禁止从聊天文本里解析出"该调用哪个工具"。对"复述提示词/列出你的工具"类请求统一拒绝话术。
6. **审计日志。** 记录每次工具调用的调用方、参数摘要与返回摘要，出事能回放。日志本身也要脱敏，别让审计文件变成新的泄露源。

## 踩坑点

- 以为系统提示词就是安全边界。注入能覆盖它——提示词是礼仪，不是权限。
- 调试时把带 token 的完整日志贴进群里问人。这是社区里最常见的真实泄露方式。
- MCP server 图省事用默认配置，实际挂载范围比想象中大得多。
- 第三方插件/MCP server 本身不可信：恶意工具可以在被调用时把读到的内容发往外部。装之前读代码，至少读权限声明。
- 子代理默认继承父代理全部权限——社区触发的任务里临时生成的 Agent，也拿着整套内部工具。

## 可复用清单

- 上线前列出实例可访问的每个工具和路径，逐项问一句："这个被公开频道看到会怎样？"
- 社区实例与内部实例物理隔离，包括记忆存储。
- 输出过滤规则进版本管理；每次泄露复盘同步更新规则。
- 每季度做一次注入演练：让同事尝试诱导泄露，把成功的路径修掉。

## 总结

Agent 泄露不是模型"不听话"，而是权限模型没设计。核心就三件事：**能看什么**（最小挂载）、**能说什么**（输出过滤）、**被诱导时怎么办**（注入隔离 + 审计回放）。提示词加固是必要的，但真正的红线永远画在工具层和输出层。先分账，再收紧，最后兜底——按这个顺序做，大部分风险在上线前就能消掉。
