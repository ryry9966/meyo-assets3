## 背景

OpenClaw 的 cron 任务，本质是"到点投递给 Agent 的一段 instruction"：触发后 Agent 在独立会话里冷启动执行，产物投到指定会话或频道。听起来简单，但很多人把聊天时的口吻直接搬过来——"每天早上帮我看下 GitHub 动态"——结果每次产出质量飘忽：有时很好，有时整段废话，有时干脆编数据。

## 问题在哪

聊天 prompt 有上下文兜底：你说"总结一下"，模型可以结合前面聊的内容，甚至反问你。cron 任务没有这些兜底：

- 冷启动，没有任何会话历史，"上次说的那个"不存在；
- 无人值守，跑错了也没人当场纠正；
- "今天""最近"这类相对时间，依赖触发时刻和机器时区；
- 输出格式、长度、去向，全靠模型自由发挥。

一句话：聊天 prompt 是对话的半句，cron instruction 是一份完整的工作交接单。

## 做法：六段式模板

我目前稳定在用的结构，直接上例子：

```
角色：你是我的仓库情报助理。
目标：汇总我关注仓库近 24 小时的动态。
数据源：仅使用 web_search 和本地文件 ~/watchlist.md，不要访问其他来源。
时间基准：以任务触发时刻为准，"近24小时"指触发时刻往前推 24 小时。
输出：Markdown，全文不超过 300 字，分「重要变更」「其他」两节；无实质更新时只回复"今日无更新"。
失败处理：工具调用失败或结果为空时，明确说明原因，禁止编造内容。
```

四个关键点，缺一不可：

1. **数据源收敛**。明确允许用哪些工具（MCP server、web_search、本地文件），比"帮我查一下"稳定得多。模型不猜测，就不会乱跑。
2. **时间锚点**。把相对时间换算成"以触发时刻为准 + 明确区间"，避开时区和语义歧义。
3. **输出约束**。格式、分节、字数上限都写死。没上限的日报会膨胀到没人看。
4. **失败兜底**。数据源为空时，模型的默认倾向是"完成任务"——也就是编。必须显式写"为空就直说"。

写完先手动触发跑两三次，确认稳定，再挂 cron 表达式。

## 踩坑点

- **"接着上次的"是幻觉**。cron 会话是独立的，需要跨次状态，就让任务读写固定文件（比如上次结果存 `~/reports/last.md`，这次先读它）。
- **一任务多目标**。"汇总动态 + 整理待办 + 发周报"塞进一个任务，输出必然糊。拆成多个 cron，各自单一职责。
- **频率与信息新鲜度不匹配**。每 5 分钟跑一次新闻汇总，烧 token 还制造噪音；频率对齐数据源的更新节奏即可。
- **只写"要做什么"**。"不要访问某来源""不要编造""不超过 300 字"这类否定约束，往往比肯定指令更能救场。

## 可复用建议

- 把 instruction 当小程序写：输入、处理、输出、异常处理，四件事齐了再上线。
- 模板存进 git，改动留痕。效果退化时能 diff 出你改了什么。
- 下游是脚本时，让任务输出固定结构的 JSON（给出字段约定），别让它写散文。
- 调优时一次只改一个变量，跑三轮再下结论，别凭一次手感。

## 总结

Cron instruction 的本质，是给一个没上下文、没人盯着、但非常听话的新同事写交接单。角色、目标、数据源、时间锚点、输出约束、失败兜底——按模板填空，先手动验证，再交给调度器。稳定的自动化从来不是碰运气调出来的，是一个字一个字约束出来的。
