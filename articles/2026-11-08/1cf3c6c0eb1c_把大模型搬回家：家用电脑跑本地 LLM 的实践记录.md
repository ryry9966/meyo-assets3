## 背景

做 Agent 自动化之后，模型调用频率明显上升：一个任务循环跑下来，几十次工具调用、几万 token 很平常。云端 API 按量计费，一个月下来不算便宜；而且不少场景（本地日志分析、私有笔记检索、家庭数据整理）本来就不想把数据发出去。于是试着把一部分负载挪到本地。

## 问题

家用硬件的约束很直接：

- 消费级显卡显存普遍 8–24GB，跑不了满血大模型；
- 小模型在工具调用上的可靠性明显低于旗舰云模型；
- Agent 框架通常默认 OpenAI 兼容端点加较长上下文，本地推理能否扛住要实测。

## 做法

**1. 按显存选型号。** 我的经验值：8GB 显存跑 7B/8B 的 Q4 量化，12GB 上 14B，24GB 可以摸到 32B 的 Q4_K_M，Mac 统一内存可以更宽裕。量化级别别低于 Q4——Q2/Q3 在指令跟随上退化严重，Agent 场景基本不可用。

**2. 选运行时。** 用 Ollama 起步，一行命令拉模型，自带 OpenAI 兼容接口（默认 11434 端口）；追求性能和可控性可以换 llama.cpp 的 server 模式。关键参数只有三个：上下文长度、GPU offload 层数、量化文件。

**3. 接入 OpenClaw。** 把 model provider 指到 `http://localhost:11434/v1`，上下文窗口按实测设置，别虚标 128k——KV cache 会吃掉大量显存。temperature 压到 0.2 以下，工具调用稳定性会好不少。

**4. 用最小 MCP 闭环验证。** 先挂一个 filesystem MCP server，让模型完成「列出目录 → 读文件 → 总结」三步。这一步能快速暴露模型能否正确生成工具参数、会不会死循环。小模型面对十几个工具时选择错误率明显上升，建议给本地模型单独裁剪工具列表，描述尽量短。

**5. 做分层路由。** 本地模型当默认，处理分类、格式化、粗筛这类轻量任务；复杂推理和长链路任务路由到云模型。在 OpenClaw 里按任务配置即可，不必二选一。

## 踩坑点

- **显存估算漏了 KV cache。** 8B Q4 权重约 5GB，但 32k 上下文的 KV cache 还要再吃好几个 GB；爆显存后掉到 CPU 推理，速度直接腰斩。
- **工具调用格式各家不一。** 部分模型对 JSON schema 遵循很松，参数会多引号、缺字段。升级模型版本后提示词模板可能变化，Agent 突然失灵先查这里。
- **长上下文在消费卡上很慢。** 几千 token 的系统提示词加工具描述，prefill 阶段首 token 延迟肉眼可见，精简系统提示词收益很大。
- **别忘了 embedding 模型。** 本地做 RAG 还得单独拉一个 embedding 模型，同样占显存。

## 可复用建议

1. 从 8B Q4 起步，先测 tokens/s 和工具调用成功率，再决定升级路线，别一上来冲 32B。
2. 给每个模型记一张卡：量化级别、显存占用、实测上下文、工具调用可靠性，换模型时对照决策。
3. 锁定运行时版本，小版本更新可能改变推理行为。
4. 本地模型的定位是「降本与隐私兜底」，不是旗舰替代。期望值放对，体验才对。

## 总结

一台 24GB 显存的家用电脑，跑 14B–32B 量化模型，足以承担日常 Agent 自动化中七成左右的轻量调用。本地模型不是用来替代云端的，而是给 Agent 体系加一层成本与隐私可控的底座。先把最小闭环跑通，再谈规模。
