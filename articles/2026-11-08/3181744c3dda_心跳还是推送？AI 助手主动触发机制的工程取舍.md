## 背景

常驻型 AI 助手（比如 OpenClaw 这类 agent 网关）迟早会遇到“主动干活”的需求：定时汇总消息、巡检订阅源、到点提醒。实现上通常两条路：**heartbeat**，agent 按固定间隔醒来自己检查；**push**，外部事件通过 webhook 直接把任务推进 agent 的消息队列。我们在自动化实践里两种都用过，踩了不少坑，这里把取舍讲清楚。

## 问题

轮询的核心矛盾是**成本与延迟**：间隔短了，大量心跳醒来发现无事可做，纯烧 token；间隔长了，响应延迟不可接受。多个插件各自起 timer 还会互相叠加。推送的核心矛盾是**可靠性与复杂度**：要求事件源支持回调、有稳定入口；agent 重启或离线期间事件会丢；webhook 普遍是 at-least-once 投递，重复消息会导致重复执行。单选任何一边，都会在某个场景翻车。

## 做法：心跳兜底，推送走快路径

1. **分层触发。** 延迟敏感的事件（新消息、告警）走 push；时间驱动、分钟级延迟可接受的巡检类任务走 heartbeat。
2. **让心跳尽量便宜。** 每次醒来先在调度层做轻量判断：有无到期任务、有无未消费的排队事件，没有就直接睡下一拍，不进模型推理。给每次心跳设 token 预算。
3. **间隔动态化。** 基础间隔加随机抖动，避免多实例同时醒来；夜间拉长、活跃时段缩短；连续空闲时指数退避，有事件立即恢复。
4. **push 侧做幂等。** 事件携带唯一 ID，agent 侧维护去重表并落盘，重启后依然有效。
5. **失败降级。** webhook 投递失败进持久队列，由下一拍心跳兜底消费。push 通道挂掉时，系统自动退化为轮询，任务不丢。

## 踩坑点

- **心跳风暴**：多个插件各自注册 timer，间隔互质看似分散，实际每小时总有几次撞车，并发触发多个模型调用。后来收敛为单一调度器统一发拍。
- **长任务堵心跳**：在心跳循环里同步执行长任务，后续拍全部顺延。心跳只负责“发现并派发”，执行放异步队列。
- **安静时段失效**：半夜心跳触发了日报推送，把人吵醒。quiet hours 要做在调度层，写进 prompt 里约束不可靠。
- **重复执行**：webhook 重试导致同一事件跑了两遍。幂等键必须持久化，只存内存的话重启即失效。
- **心跳沉默**：心跳挂了比心跳多跑更危险。记录 last_beat 时间戳，watchdog 超时告警。

## 可复用建议

选型看三件事：事件源是否支持回调、延迟要求是多少、能承受多少基础设施复杂度。秒级响应且事件源有 webhook → push 为主；纯时间驱动 → heartbeat 足够；真实系统大多是混合形态。另外把“每次唤醒平均成本”记成一等指标，优化心跳本质就是在优化账单。

## 总结

heartbeat 与 push 不是二选一，而是分层：push 解决延迟，heartbeat 解决覆盖与兜底。先用最便宜的心跳保证系统活着，再按事件源能力逐个接入推送，最后用幂等和 watchdog 兜住两边的失败模式。按这个思路重构后，我们的空转 token 消耗降了一个量级，响应速度反而更快了。欢迎在社区里贴出你们的 heartbeat 间隔和唤醒成本数据，横向对比一下。
