## 背景

OpenClaw 的价值在于把模型、工具、MCP 服务和消息通道编排成一个长期在线的 Agent。但真跑起来之后，你会很快撞上一个现实问题：所有请求都走 GPT，账单涨得比预期快；全部换成本地模型，Agent 又频繁在工具调用上翻车。所以多模型路由不是"省钱技巧"，而是给不同任务分配不同能力等级的工程决策。

## 问题

社区里常见两种极端：

- **一刀切全用 GPT**：月度 token 费用里大半来自摘要、转发、定时任务这类"杀鸡用牛刀"的调用；
- **一刀切全上本地**：主会话质量肉眼可见地下降，多步工具调用经常在第二步迷路，要么死循环要么瞎编参数。

根源在于：任务的能力需求差异极大，而默认配置只有一档。

## 做法

以 `openclaw.json` 为中心，三步走：

**1. 先盘点任务，再谈模型。** 把 Agent 干的活分成四类：

- 主会话、复杂推理、多步工具链 → GPT
- 定时摘要、消息分诊、日志整理 → 本地模型
- 隐私敏感内容（未脱敏的私人数据）→ 本地
- 可用性优先的兜底链路 → 互为 fallback

**2. 注册双 provider。** 本地模型走 Ollama 的 OpenAI 兼容端点，在 models 配置里加一个自定义 provider 指向 `http://127.0.0.1:11434/v1`，模型务必选原生支持 tools 的（qwen2.5 系列、llama3.1 以上）。

**3. 按 agent 绑定模型，而不是全局切换。** OpenClaw 的每个 agent 可以单独指定模型：主会话 agent 用 GPT；另建一个轻量 agent 专门跑 cron 摘要和分诊，绑定本地模型。再加 fallback 链：主链路失败时降级到本地，保证服务不中断。插件层可以做更细的消息级路由，但建议先跑通 agent 级再说。

## 踩坑点

- **本地模型的 tool calling 远比 benchmark 上看起来脆**：参数幻觉、漏调、死循环都遇到过，MCP 工具的参数 schema 越复杂越明显。原则：本地模型只跑零工具或单工具任务，不要放进多步 Agent 循环。
- **上下文长度差异会被静默吞掉**：GPT 128k，本地常见 8k–32k，长会话直接喂本地会被截断，摘要质量骤降且无报错。路由前做长度预判。
- **Ollama 默认 5 分钟卸载模型**，cron 任务每次冷启动干等几十秒。设置 `keep_alive`，或把模型预热放到空闲时段。
- **fallback 是静默的**：降级发生了你不知道，只会觉得"最近怎么变笨了"。务必在日志里记录 provider 字段，每周看一眼分布。

## 可复用建议

- 方向要选对：**默认强模型、显式降级**，而不是默认弱模型期待奇迹。降级是容错手段，不是常态。
- 路由粒度放在 agent 级。全局开关太粗，消息层 if-else 太细——后者大概率会长成没人敢动的祖传代码。
- 记录每次调用的 model、tokens、耗时三件套。跑一个月，你自然知道该把哪类任务挪到哪边，不需要任何玄学。

## 总结

判断标准就三条：**能力够不够、数据敏不敏感、调用频不频繁**。会话和工具链交给 GPT，高频低难度的杂活和隐私数据交给本地模型，用 fallback 保可用性，用日志验证假设。先跑通再优化，路由规则永远从最简单的两条开始。
