## 背景

Agent 的推理能力不直接产出业务结果，落地要靠外部 API：查工单、发告警、读内部知识库、触发流水线。OpenClaw 对接外部服务常见三条路：挂一个 MCP server、在插件里封装工具、把 HTTP 调用直接包成 function tool。三条路都能跑通，差别在维护成本和改动半径。这篇不讲协议细节，只聊怎么把“能调通”做成“能稳定交给 Agent 用”。

## 问题

大多数对接失败不是协议问题，而是三个落差：

1. **模型看到的和接口实际行为不一致**——工具描述含糊，Agent 拿一个通用查询工具去干所有事；
2. **错误对人友好、对 Agent 不友好**——返回一句 "request failed"，模型不知道该重试还是该换路；
3. **响应撑爆上下文**——上游一个列表接口返回几 KB 的 JSON，几轮对话后上下文就满了。

## 做法

按六步走，能把大部分坑提前踩掉：

**1. 选对接层。** 优先 MCP：改配置不改代码，鉴权和限流收在 server 一处。已有内部 SDK 的服务，直接在插件里包成工具更省事。

**2. 写工具 schema。** 命名用“动词+名词”（如 `search_tickets`），description 写清楚什么时候该用、什么时候不该用，参数给枚举值和默认值。这部分是写给模型看的文档，不是写给人的注释。

**3. 鉴权与配置分离。** token、endpoint 走环境变量或配置文件，不进模型上下文，也不落日志。

**4. 错误结构化。** 统一返回 `{ok, error_code, hint, retryable}`。Agent 看到 `retryable: true` 会退避重试，看到 `hint` 会调整参数，而不是原样再发一次。

**5. 超时与裁剪。** 每个工具设明确超时；重试做有限次加退避；分页在工具内部处理完，只返回摘要和关键字段，别透传原始响应。

**6. 留痕。** 每次调用记 request id、耗时、参数摘要，出问题能对账，也能用来分析 Agent 的调用模式。

## 踩坑点

- **description 太泛**：写“查询数据”，模型会拿它查一切。写清边界：“仅用于 XX 系统，时间范围用相对表达”。
- **透传原始 JSON**：上下文爆炸的元凶。做字段投影，默认只返回模型需要的列。
- **吞掉错误**：所有失败都返回 "failed"，Agent 会死循环重试。错误码要能区分“参数错了”和“服务挂了”。
- **工具注册过多**：几十个工具挤在一起，选择准确率明显下降。按场景拆 profile，会话里只挂相关的那组。
- **上游悄悄改字段**：接口没报错但语义变了。给关键接口加契约测试，定时跑。
- **密钥进日志**：调试日志最容易泄露。在日志层做脱敏，别靠自觉。

## 可复用建议

- 每个外部服务包一层**薄适配**：工具只做参数校验、调用、裁剪，业务逻辑放外面；
- 给每个工具加 **dry-run 模式**，先验证 Agent 给的参数再真调；
- 结构化错误码表沉淀成团队约定，新工具直接复用；
- 上线前用固定问题集回归测一轮工具选择准确率，改了 description 就重跑。

## 总结

Agent 与 API 的握手，难点不在“接上”，而在让 Agent 在异常路径上也能做出正确决策：描述准确、错误可读、响应够小、边界清楚。把这几件事做成默认约定，对接第三个、第十个服务时就是体力活，而不是探险。欢迎在回帖里分享你们的错误码表和工具拆分策略。
