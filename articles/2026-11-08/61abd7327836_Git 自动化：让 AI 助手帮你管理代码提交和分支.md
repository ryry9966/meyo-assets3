## 背景

用 OpenClaw 跑了半年个人 Agent 之后，我把它接入的第一个“脏活”就是 Git。不是因为它多智能，而是因为仓库维护里最消耗心智的部分——写提交信息、清理分支、盯未推送的改动——都是规则明确、重复性高的工作，正好适合交给自动化。

## 问题

我此前的真实状态：

- 提交信息大量是 `update`、`fix`、`wip`，回头查历史全靠猜；
- 本地堆了十几个 `feature/*` 分支，合并后忘记删，时间一长不敢删；
- 下班时改到一半的代码留在工作区，第二天自己都忘了改了什么；
- `main` 上偶尔混进本该走分支的小改动。

这些不是技术难题，是纪律问题。而纪律恰恰是 Agent 擅长替你执行的。

## 做法

**第一步：只读观察期。** 先不给写权限，让 Agent 每天定时跑一遍 `git status --porcelain`、`git branch --merged main` 这类只读命令，把"未提交改动、可清理分支、落后远端的仓库”汇总成一条消息发到我的会话里。跑两周，确认它的判断可靠。

**第二步：接管提交信息。** 在 Agent 的 skill 里写死流程：只对已 staged 的内容操作，用 `git diff --cached` 逐块阅读，按 Conventional Commits 起草 message，格式限定为 `type(scope): 摘要`，正文说明动机。草稿先给我确认，确认后才执行 `git commit`。它是"起草者”，我是“签发者”。

**第三步：分支清理。** 定时任务里做三件事：`git fetch --prune`；列出已合并且远端已删除的本地分支，自动删除；列出 squash-merge 疑似残留的分支（用 `git cherry main` 检查 patch 是否已进主干），只汇报、不删除，等我确认。

**第四步：收紧权限面。** 我没让 Agent 直接跑任意 shell，而是包了一层极薄的 MCP 工具，白名单只放行 `status / diff / log / branch / commit / fetch` 几个子命令；`push --force`、`reset --hard`、`rebase` 一律不在名单里，需要时我手动执行。

## 踩坑点

- **提交信息幻觉**：Agent 会根据文件名脑补意图。必须约束它只引用 diff 里实际出现的改动，diff 太大就分块总结，宁短勿编。
- **squash-merge 陷阱**：`git branch --merged` 看不到被 squash 掉的分支，按"已合并”直接删会丢代码。要用 `git cherry` 或比对 patch-id 做二次确认。
- **多仓库路径串台**：Agent 曾在错误目录里执行 `git commit`。现在所有仓库路径写死在配置里，执行前先校验 `git rev-parse --show-toplevel`。
- **凭据安全**：走 SSH agent 和 credential helper，绝不让 Agent 接触 token 明文，日志里对远端 URL 做脱敏。
- **误提交 WIP**：自动提交前检查 `git status --porcelain`，发现未跟踪的可疑文件（如 `.env`、临时脚本）就中止并汇报，而不是一股脑 `git add -A`。

## 可复用建议

1. 权限渐进：只读两周 → 提交需确认 → 低风险操作自动执行，每一步都可回退。
2. 破坏性操作（删除分支、强制推送、重置）永远保留人工确认门槛，做成工具层的硬规则，而不是提示词里的一句“请小心”。
3. Agent 每次操作后写一行决策日志（仓库、动作、原因），出问题能审计。
4. 清理类任务先 dry-run 再真实执行。

## 总结

这套流程上线后，我的提交历史第一次变得可读，本地分支长期保持在个位数。AI 助手在这件事上的价值不是“更聪明”，而是把一套你知道该做、但总懒得做的纪律，变成了不会遗漏的例行流程。建议从只读模式开始，小步放权。
