## 背景：上下文是稀缺资源

跑过一段时间的 Agent 项目都会遇到同一个问题：能力越多，系统提示词越臃肿。把所有工具说明、操作手册、领域知识全塞进 system prompt，轻则 token 成本翻倍，重则模型注意力被稀释，该执行的指令反而漏掉。

OpenClaw 的 Skills 机制本质上是一套**渐进式披露**（progressive disclosure）方案：会话启动时只注入技能的名称和一行描述，完整的技能正文只有在模型判断相关时，才通过 Read 工具加载进来。换句话说，上下文里常驻的是"目录"，不是"全书"。

## 问题：按需加载的前提是"路由"准确

这套机制带来一个新约束：模型决定加载哪个技能，唯一依据就是那行 `description`。描述写得含糊，轻则不触发，重则触发错技能。所以用好 Skills，核心不是写文档，而是**设计触发契约**。

## 做法：一个可复现的技能结构

Skills 放在工作区或 `~/.openclaw/skills` 下，每个技能一个目录，核心是一个 `SKILL.md`：

1. **frontmatter**：`name` 和 `description` 是路由信号。description 必须回答"什么场景该用我"，而不是"我是什么"。
2. **正文**：前置条件（依赖的 CLI、环境变量）、分步操作、禁止事项、示例命令。
3. **加载流程**：启动 → 索引注入 → 模型匹配 → Read 加载正文 → 按指令执行。

写 description 推荐模板：*Use when <触发场景>. Do for <能力>*。

验证方式：换几种说法间接提问（不提技能名，直接说"帮我把这张图压到 500KB 以内"），观察是否命中；必要时开调试日志确认实际加载了什么。

## 踩坑点

- **description 写成了产品简介**。"这是一个图片处理技能"没有路由价值，改成"当用户要求压缩、转格式、去水印时使用"。
- **技能过多且边界重叠**。两个描述都能匹配同一请求时，模型可能随机选或直接纠结。合并同类项，或在描述里写明互斥条件。
- **把机密写进 SKILL.md**。正文一旦触发就进入上下文，密钥放环境变量，文档里只写变量名。
- **误以为正文常驻**。安全红线、全局约定若必须始终生效，应放进常驻的 AGENTS.md，而不是某个技能正文。
- **frontmatter YAML 写错**，技能会静默不加载，表面"什么都没发生"。改完先验证解析。
- **与内置技能重名**，会出现覆盖或冲突，命名加自己的前缀更稳。

## 可复用建议

1. 一个技能只做一件事，宁可拆小，不做大而全。
2. 正文控制在两三百行内，细节用文件引用外链，别把整本手册搬进来。
3. 技能目录进 Git，像代码一样 review 和回滚。
4. 加环境门槛（依赖未装则不加载），避免在缺依赖的机器上误触发。
5. 用改写过的请求做触发测试，别只用描述里的原句——真实用户的说法永远和你预设的不一样。

## 总结

Skills 的价值不在于"能挂多少能力"，而在于用最小的上下文代价换取准确的能力调用。一行 description 是路由表，正文是操作手册，两者的分工决定了整套机制是否可靠。把技能当成**带触发契约的提示词模块**来维护，而不是普通文档来写，效果差得很远。
