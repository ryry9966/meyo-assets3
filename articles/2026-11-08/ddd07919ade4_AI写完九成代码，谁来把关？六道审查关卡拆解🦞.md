最近技术圈刷屏的消息：Anthropic 工程师透露，Claude Code 的代码库里九成代码由 AI 自己生成，Dario Amodei 更早就预言过“未来绝大部分代码将由 AI 写出”。36kr 报道的焦点不是“AI 多能写”，而是一个更现实的问题——谁来审？当代码生产的边际成本趋近于零，整个软件工程里最贵的环节悄悄变成了“读代码、判断对错”。Claude Code 团队给出的答案是六道审查关卡。这篇文章拆解它为什么长成这样，以及普通团队怎么抄作业。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-08/086b0e1ef8a210c5.png)

## 一、瓶颈转移：生产速度跑赢了审查速度

- **写与读的时间不对称**。软件工程的经典结论：代码被读的次数远多于被写，读懂一段陌生代码的时间通常是写它的数倍。AI 把“写”压缩到秒级，“读”却仍是人类的线性时间，于是整条流水线最细的地方，从键盘转移到了 reviewer 的眼睛。
- **PR 积压是一道排队论题**。用 Little's Law 粗算：队列长度 = 到达速率 × 平均处理时间。AI 让到达速率涨了十倍，结果只有两个——要么 review 队列爆炸，要么每个 diff 被草草扫过。"LGTM"三个字母，可能是史上最贵的批准。
- **更危险的是“看起来对”**。大模型最擅长生成结构漂亮、命名规范、注释齐全的代码，但边界条件可能全错。传统 code review 很依赖“顺眼”的直觉，面对 AI 代码恰恰最容易失效：风格越专业，越容易被放行。

## 二、六道关卡：把“审代码”流水线化

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-08/3767f3b9abfb26d7.png)

媒体报道归纳的六道关卡，核心思路不是“更认真地人工读”，而是承认逐行人工审不可扩展，把审查拆成六层串联的过滤器，每层只拦一类错误：

1. **规格先行（spec review）**：动手前先让 AI 产出实现计划，人只审这份几百字的需求拆解。方向错了，后面每行代码都在放大错误，纠偏代价是平方级的；审一份计划只要几分钟。
2. **沙箱与权限**：AI 在隔离环境里干活，文件读写、网络访问、shell 命令全走白名单，先把爆炸半径控制住。
3. **机器审**：linter、类型检查、单元测试、CI 门禁。测试在这里的角色是“可执行的规格”——AI 写的代码骗得过人眼，骗不过断言。
4. **安全扫描**：静态漏洞分析（SAST）、依赖成分分析、密钥泄露检测。大模型特别爱硬编码 API key、引入带 CVE 的旧版本依赖，这类问题机器查比人眼靠谱得多。
5. **人工终审**：人不再逐行读，而是审架构决策、接口契约、并发与边界这些机器判断不了的部分。常见姿势是让 AI 先生成 review 摘要和风险点列表，人类做“抽查 + 终裁”。
6. **事后防线**：灰度发布、feature flag、监控告警、自动回滚。默认前五关总有漏网之鱼，用小流量和可观测性把损失压到最小。

设计哲学一句话：把“一个聪明人拼命看”换成“六个便宜且稳定的过滤器串联”，各层漏检率相乘之后，远低于任何一个疲惫的 reviewer。

## 三、范式转变：审查对象从“行”变成了“契约”

- **从逐行到契约**：人眼最值钱的判断在接口设计、数据流、故障语义上，而不是某行少了个判空。低级错误该由 type checker 和测试兜住。
- **从信任个人到信任系统**：以前代码质量靠资深 reviewer 的个人功力，不可复制；流水线把审查经验固化成配置和门禁，新团队也能踩到及格线。
- **责任并没有转移**：git blame 记的是 commit 的人。AI 写的代码出了线上事故，追责链条仍落在按下 merge 键的那个人身上——这就是“九成 AI 写”喊得震天响、却没有团队敢撤掉人工终审的根本原因。
- 历史总是押韵：高级语言出现时，有人坚持“手写汇编才算真编程”；自动化测试普及时，有人说测试浪费时间。每一次生产力上移，工程重心都会跟着上移，这次移到了“定义什么算对”。

## 四、落地建议：普通团队怎么抄作业

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets3@main/images/2026-11-08/91401080a8e89132.png)

不必照搬大厂全套基建，按团队规模做减法：

1. **最小可用版（个人/小团队）**：补测试 + 控 diff。让 AI 单次改动控制在人 15 分钟能读完的规模，一次只做一件事；没有测试覆盖的模块，不让 AI 碰核心逻辑。
2. **进阶版（中型团队）**：把 linter、类型检查、覆盖率阈值设成 merge 的硬门禁。AI 生成再快，红灯就是红灯。
3. **留溯源记录**：把需求和 AI 的实现计划贴进 PR 描述。三个月后排查“当时为什么这么改”，你会感谢这份备忘。
4. **两个反模式**：不要开多个会话并行生成一大坨代码再一起审，那是把瓶颈升级成灾难；也不要因为 AI 代码“看起来专业”就跳过 review——plausible 不等于 correct。

## 五、三条冷思考

1. **审查能力会成为新的技能分层**。会写 prompt 的人很快饱和，能把模糊需求翻译成可验收规格、能定义“什么算对”的人，会越来越稀缺。
2. **测试从质量工具升格为沟通协议**。当写代码的是模型、审代码的是人，测试用例就成了双方唯一不会产生误解的共同语言。
3. **六道关卡防的不是 AI，是复杂性**。就算 AI 明天能写对 99% 的代码，软件系统的复杂度也会涨到新的高度把它填满。审查流水线不会消失，只会更长。
