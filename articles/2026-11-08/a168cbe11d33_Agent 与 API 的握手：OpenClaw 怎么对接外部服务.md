## 背景

Agent 的价值在于动作，而动作的落点在外部服务：查订单、写工单、调内部数据接口。在 OpenClaw 里，这条链路通常是：模型决定调用某个 tool → 插件 / MCP Server 发起真实请求 → 结果回灌给模型继续推理。链路看着简单，但"调通了"和"能稳定用"之间隔着一大段工程活。

## 问题：三个常见断点

1. **模型不知道边界**。把 API 文档整段塞进 prompt，模型会幻觉出不存在的参数，或者在二十个工具里挑错一个。
2. **Adapter 缺位**。鉴权、限流、重试、分页这些脏活没人管，全靠模型临场发挥。
3. **响应不可控**。一个返回 200KB JSON 的接口直接灌进上下文，两轮对话就把 token 吃完了。

本质是一句话：API 的确定性世界和模型的不确定性输出之间，缺一层契约。

## 做法：把握手拆成三步

**第一步：收敛工具面。** 不要按 endpoint 一比一暴露。一个服务通常 3~6 个语义化工具就够，命名用动宾结构，参数收窄到模型真正需要决策的那几个。

**第二步：写清契约。** 每个工具的 description 要回答三个问题：什么时候该用我、什么时候不该用、失败长什么样。参数说明里写清格式约束（日期格式、ID 来源），比在 system prompt 里兜底有效得多。参考一个最小结构：

```json
{
  "name": "search_orders",
  "description": "按时间范围查询当前用户订单列表。仅当用户明确要求查订单时使用；不用于修改订单。",
  "params": { "start_date": "YYYY-MM-DD", "limit": "1-20，默认10" },
  "returns": "orders[] + total；失败统一 {ok:false, error, hint}"
}
```

**第三步：脏活下沉到 Adapter。** 鉴权放环境变量，永不进 prompt；超时、限流、幂等重试都在插件层处理；返回值做裁剪——只给模型决策需要的字段；错误统一成 `{ok, error, hint}` 三段式，让模型读得懂"下一步该干嘛"。

## 踩坑点

- **工具越多越聪明是错觉**。超过十几个工具后选错率明显上升，按场景拆 profile 比堆工具好。
- **大响应直接回灌**。先在插件层截断或摘要，模型只需要"前 5 条 + 总数"这种结论，不需要原始分页数据。
- **重试没有幂等键**。POST 接口超时重试造成重复下单，是自动化事故的经典来源；写操作务必带 client 生成的幂等 ID。
- **日志里带 token**。Agent 调用链日志很容易把 Authorization 头打出来，脱敏要放在 adapter 出口统一做，别指望每个调用点自觉。
- **慢接口同步等待**。长任务建议先返回任务 ID，再用第二个工具查询进度，别让 agent loop 干等到超时。

## 可复用建议

1. 把工具 schema 当 API 契约维护，改动走 review，不随手改字段和语义。
2. 每次工具调用记录 trace_id、入参摘要和耗时，出问题能回放，不用靠猜。
3. 新服务接入按顺序来：先 curl 打通鉴权和分页，再包 MCP 插件，最后才挂给 agent。
4. Agent 层保持薄：只做选择和编排，不做解析和清洗，那不是它的强项。

## 总结

对接外部服务不是"让模型会调 API"，而是给握手双方立规矩：模型负责判断，adapter 负责可靠，契约负责对齐。把脏活从 prompt 里挪出去、把边界写进工具描述里，agent 才能从 demo 走向生产。这套模式跟具体框架无关，换任何 MCP 实现都成立。
