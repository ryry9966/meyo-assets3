## 背景

Agent 的价值最终落在"能动手"上。OpenClaw 通过 MCP server 和插件机制把外部服务包成工具交给模型调用——查数据、发工单、跑脚本。但"能调通"和"调得稳"之间差着一整个工程层。这篇帖子把最近对接三个外部 REST API 的经验沉淀下来，聊聊握手阶段的设计取舍。

## 问题

把 API 裸暴露给 Agent，典型故障有四类：工具描述含糊，模型开始"猜"参数；超时、限流、4xx 混在一起返回，Agent 要么死循环重试，要么编造结果；一个几万 token 的 JSON 响应直接打爆上下文；写接口没有确认机制，一次误调用就是脏数据。

本质上，Agent 和 API 之间缺的不是 HTTP 客户端，而是一层翻译协议：把服务能力翻译成模型能稳定理解、安全执行的接口。

## 做法

原则只有一条：不让 Agent 直接碰 HTTP。每个外部服务先包一层薄适配器（MCP server 或插件），统一做四件事。

**1. 收窄接口。** 不要照搬 REST，一个 endpoint 对应一个工具。先问 Agent 要完成什么任务，把相关接口合并成语义化工具，比如 `create_work_order(title, priority, assignee)`。参数用严格 JSON Schema，能用 enum 就用，可选参数尽量少。

**2. 统一鉴权与配置。** API key 走环境变量或本地 secret 文件，不进代码库；适配器启动时校验凭据，缺了就 fail fast，不要等第一次调用才报错。

**3. 错误写给模型看。** 捕获异常后不要原样抛出，归一化成模型能据此决策的信息："上游 429，建议 60 秒后重试""400，请检查参数 X"。内置指数退避重试，只对网络错误和 5xx 生效，4xx 一律不重试。

**4. 裁剪响应。** 返回前截断超大字段、只留任务相关字段；分页结果给摘要加游标，不给全量。模型要的是"够用的信息"，不是原始账本。

写操作另加两道闸：工具声明标注 destructive，由框架层要求用户确认；提供 dry-run 参数，先预览将要执行的操作。

## 踩坑点

- 描述写"调用某接口"等于没写，模型传参全靠猜。每个参数要写清业务含义和边界，最好带一个输入示例。
- Agent 自己发起的重试最难拦，适配器要返回"不可重试"的明确信号，否则 400 也会被反复打。
- 日志打了完整请求头，key 泄进日志。鉴权头必须单独脱敏。
- 非幂等 POST 被重试，产生了重复工单。写接口统一带幂等键。
- 工具加到二十多个后，模型选择准确率明显下降，现在单 Agent 控制在 10 个以内。

## 可复用建议

- 沉淀一个适配器模板：鉴权校验、超时、归一化错误、响应裁剪、幂等键五个槽位，接入新服务基本是填空题，目前成本已降到半天以内。
- 先 curl 后接 Agent：接口行为用脚本验证清楚再包装成工具，别拿 Agent 当调试器。
- 每次工具调用记结构化日志（工具名、参数摘要、耗时、错误码），排障时基本不用猜。

## 总结

对接外部服务的本质，是在 Agent 和 API 之间立一份双方都守得住的契约：模型侧要清晰收敛的接口描述，服务侧要可控可审计的调用行为。OpenClaw 的工具体系提供了很好的挂载点，但契约质量取决于适配器这层薄代码写得是否认真。把流程和模板固化下来，后续的服务接入就只是体力活了。
