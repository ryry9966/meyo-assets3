# Agent 与 API 的握手：OpenClaw 怎么对接外部服务

## 背景

Agent 的能力边界，基本取决于它能调到什么。模型本身只负责决策，真正"做事"靠工具调用。在 OpenClaw 里，对接外部服务通常有三条路：直接注册 tool、挂一个 MCP server、复用现成插件。最近我把 OpenClaw 接到了一个内部工单系统和一个公开 REST API 上，这篇帖记录决策过程和踩过的坑，供准备做对接的同学参考。

## 问题

最初的想法很直接：让 Agent 直接发 HTTP 请求。跑起来才发现，几件事没约定就会失控：

- 模型对接口的理解完全来自工具描述，描述含糊，参数就乱填；
- token 放哪、怎么轮换，没有规范就会散落在 prompt 和配置里；
- API 报错返回一大坨原始 JSON，Agent 拿到后经常自由发挥，编出一套不存在的重试逻辑。

## 做法

1. **选通道**。长期使用的内部服务走 MCP server，工具定义、鉴权、日志集中一处，多会话可复用；临时脚本类需求直接注册 tool，成本低。
2. **描述写到"新同事能看懂"**。每个工具说清三件事：什么时候用、参数格式、失败会怎样。宁可啰嗦，别让模型猜。
3. **鉴权收口**。凭据只放环境变量或 OpenClaw 的配置层，由工具封装注入，绝不进对话上下文——否则它会出现在日志甚至回复里。
4. **错误要翻译**。封装层把 HTTP 错误压成一句明确的话加建议动作，比如"限流，30 秒后重试"。短而明确的错误信息，比原始堆栈稳定得多。
5. **写操作加幂等键**。建工单、发通知这类动作，由工具层生成幂等 key，Agent 重试也不会产生重复数据。

## 踩坑点

- 描述里写"可选参数"，模型就真的全不传。改成明确写出默认值和何时必填。
- 返回值太大：一次把整张表丢给模型，上下文立刻爆掉。改成默认返回前 N 条，另配一个分页工具。
- 没设超时：外部 API 卡住，整个会话跟着挂。封装层统一 10 秒超时并明确报错。
- MCP server 改了工具签名后，旧会话还缓存着旧 schema，出现"明明定义了却调不对"。改完记得重启会话验证。

## 可复用建议

- 把每个外部服务的封装当小 SDK 维护：描述、鉴权、错误映射、限流各归其位，不要全塞在一个函数里。
- 用录制好的真实请求/响应对给工具做单测，保证改描述不会悄悄改行为。
- 新接一个服务，先只放开只读操作，跑稳一段时间再开写操作。

## 总结

对接外部服务的本质，不是"让模型能发请求"，而是给它一个边界清晰、行为可预期的接口面。描述写清楚、错误说人话、副作用可控制，这三件事做到了，Agent 和 API 的这次握手才算真正握上。欢迎在评论区交流你们实际对接中遇到的问题。
